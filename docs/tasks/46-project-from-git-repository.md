# 46 · A Project from a git repository, and Sign in with GitHub

Status: in progress

## Goal

The user adds a Project from a git repository as well as by path. Any https or ssh git URL is cloned into the Office data directory, and when signed in they can pick one of their GitHub repositories instead. Every git command The Office runs uses the Office identity only, never the user's own credentials. That identity has two parts. Sign in with GitHub is a GitHub App the user registers from Settings by its manifest and installs once, signed in through the browser by GitHub's web flow; The Office refreshes its user token and Agents never see it. The Office ssh key is generated by The Office, and the user adds its public half to the hosts that need it. Other hosts over https are reached anonymously. Devops' onboarding Proposal may name a Repository URL.

## Definition of Done

- [ ] Every Office git command, whether for a Project (path-added ones too), a Skill's Source or Devops reading a URL, uses only the Office identity. The user's credential helpers are cleared, git never prompts, and ssh runs with the Office ssh key alone: no agent, none of the user's ssh config, and The Office's own known hosts. Check: service tests that a git command run under a user credential helper and a user ssh config reaches neither; `npm run verify:linux`.
- [ ] The Office ssh key is generated once and kept in the Office data directory, readable by its owner only, and Settings › Office identity shows its public half. GitHub's host keys come from GitHub's published list. Any other host's key is trusted only after the user confirms its fingerprint. Check: service tests of the key, the known hosts and an unconfirmed host refused; e2e tests of the section.
- [ ] A git URL (https, `ssh://` or `user@host:path`) is cloned into `<office-data>/repositories/<host>/<owner>/<repo>`, with progress shown while it runs. Other transports are refused. The clone is then added as a Project by path, with its base branch defaulting to the remote's default branch. Chat sessions read a cloned Project's folder as they read a path-added one's. Check: service tests of URL parsing, the clone and its refusals; an Office rules test; the contract's schemas.
- [ ] Settings › Office identity registers the GitHub App by its manifest. The browser comes back to The Office on localhost, The Office converts the code, and it keeps the Client ID and client secret and discards the private key and webhook secret. Sign in sends the browser to GitHub's authorize page and back to The Office, which exchanges the code and shows who is signed in. Sign out forgets the token. Tokens and the client secret are kept in the database and never sent to the web. Check: service tests against a fake GitHub server; e2e tests.
- [ ] The Office refreshes the user token before it expires, one refresh at a time, since GitHub replaces the refresh token on each refresh. A refresh that fails signs the user out and says so. Check: service tests of expiry, rotation and concurrent use.
- [ ] While signed in, GitHub https remotes clone, fetch and push with the token. Git gets it from a credential helper that Office code answers, never from an environment variable, a remote URL, a config file or a command line. Pull requests go through GitHub's REST API, and `gh` is no longer used. Without the sign-in, Push + PR is refused before the push. A Project's page says which part of the identity its remote needs and what is missing. Check: service tests on a local git server that requires the token, and against the fake API; a test that no Project command's environment and no session's options hold the token.
- [ ] Add Project takes a folder, a git URL or, when signed in, a pick from a searchable list of the repositories the App is installed on. Check: service tests of the list; e2e tests of each way.
- [ ] Devops reads a repository by its URL from a shallow bare fetch. The onboarding Proposal may hold a Repository URL instead of a path, and applying it clones the repository, then adds the Project and its Onboard Task. Check: Work and Conversations tests with the scripted engine.
- [ ] Seen once live on the Test Project with the Agent SDK engine and the cheapest model. Check: the run summarised in State. The run covers:
  - registering the App by its manifest on localhost, and signing in through the browser back to localhost;
  - adding the repository from the picker as a clone;
  - publishing a Task by push and pull request into a throwaway base branch with the token;
  - the path-added Test Project fetching with the identity, with none of the user's credentials reachable.

Leave out:
- GitHub Enterprise and other forges' sign-in: other hosts use the Office ssh key, or https anonymously.
- The App's webhooks and installation tokens: a user token only.
- MCP servers getting the token.
- Removing a clone when its Project goes: archive is task 38.
- Shallow or partial clones of a Project.
- Encrypting tokens at rest: they are a database row, as an API endpoint's key is.
- The phone.

Decided with the user on 2026-10-31 and 2026-11-01:
- Tokens are a database row, never sent back, not encrypted.
- A new `github` module, named in spec §5.3.
- The App is registered by GitHub's manifest flow. The Client ID and client secret are kept; the private key and webhook secret are discarded.
- Sign in with GitHub is GitHub's web flow for an App's user token, not the device flow: the browser goes to GitHub's authorize page and back to The Office on localhost; the code is exchanged with the client secret and PKCE. GitHub asks for the client secret to exchange a code and to refresh the token (2026-11-01, replacing the device flow).
- The App's permissions: Metadata read; Contents, Pull requests and Workflows read and write. There is no webhook, and tokens expire.
- git-lfs runs with a home folder of The Office's own, so it can't read `~/.netrc` (LFS settings in the user's global git config don't apply to it); Office git never sends the Windows sign-in (Negotiate and NTLM off) (2026-11-01).
- One Office identity, never the user's credentials. This replaces spec §8's "other hosts keep the machine's credentials" and changes existing path-added Projects: they stop using the user's keys.
- Office fetches that are not for a Project use the same identity.
- The clone folder is `repositories/<host>/<owner>/<repo>`, and the Office rules let chat sessions read clones.
- Devops reads a URL by a shallow bare fetch, and the repository is cloned when the Proposal is applied.
- A failed refresh signs the user out and says so.
- Pull requests go through GitHub's REST API. Without the sign-in there are none, so Push + PR is refused before the push and `gh` goes.
- Chosen while writing, for the user to review: an unknown ssh host's key is trusted only after the user confirms its fingerprint. Sign in with GitHub and the ssh key share one Settings section, "Office identity". The ssh key and the git environment live in `platform/`, outside the `github` module.
