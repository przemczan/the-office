Overview

Issues are Tasks with a Kind

There is no new Issue entity. A Task gets a Kind: Feature, Bug or Chore. A Bug can also record Caused by, Found in version and Found while working on. Dropping a Task takes an optional Drop reason. Bugs come from three places: the user, Agents through a Decision, and the Project's GitHub issues. Write-back to GitHub is set per Project.

What the user sees
  • A Kind mark on every card and a Kind filter on the Work board, kept in Saved views.
  • A Kind choice in New Task and in Shape into a Task. Choosing Bug fills an empty Description with a short template.
  • Kind and the bug details on the Task page, changeable until Done or Dropped.
  • A reason in the Drop window, shown on the Task page and in Archived.
  • Import issues, auto-import by label and three write-back switches on the Project page.
  • A Default Pipeline per Kind in the Project's Pipelines.
What changes underneath
  • tasks gains kind (NOT NULL, default 'feature') and nullable bug and drop columns. The migration only expands, then backfills Chore from made_for.
  • projects gains three Default Pipeline per Kind columns, the auto-import label and the write-back switches.
  • A new projects-owned issue_links table, unique on (repository, issue number), which guarantees import-once. A issue_write_backs outbox retries what GitHub refused.
  • github gains a GitHubIssues entry and issues: "write" in REQUIRED_PERMISSIONS.
  • A new Office action, propose_bug_task, in Agent Stages. The Planner gains write_kind and write_bug_details.

Overview

Points to check at the Gate

The code differs from the Plan in a few places. Each point below follows the code and keeps the Plan's intent. Send the design back if one should go another way.

  1. projects can't import work. work already imports projects, and import/no-cycle forbids the reverse. So projects creates Tasks and hears that one started, was Done or was Dropped the way the module template prescribes. projects offers an IssueTasks registry, and work fills it at start, as it fills TaskBases today. A work adapter forwards Task started, Done and Dropped to projects' IssueWriteBack. The rules for import and write-back stay in projects, and work stores no GitHub data.
  2. Nothing preselects a Pipeline at Mark Ready today. Mark Ready needs a Pipeline already chosen on the rail. "Preselects" therefore means this: the rail's picker lists the Kind's default first, marked Default for Bugs, and opens on it, so one press chooses it. Before Ready names it too: "Choose a Pipeline on the rail: Quick fix is the default for Bugs". A new Task still takes no Pipeline by itself.
  3. Nothing can be created by The Office today. A Task's createdBy is an Author, which is a user or a person. Writing {"kind":"office"} into created_by would break the previous release after a rollback, since its authorOf passes the value through and its contracts refuse it. So created_by keeps a valid Author: the user who pressed Create the Bug Task on a Bug Task Decision, or the user who last set the Project's auto-import label. A new flag, created_by_the_office, makes the read model's createdBy a TaskCreator of { kind: "office" }, as ArchivedBy already has. The Office therefore creates auto-imported Tasks and approved Bug Tasks. An issue imported by hand is created by the user who imported it.
  4. There is no TaskDone or TaskDropped event. The forwarder listens to TaskStarted and to TaskStateChanged into done or dropped. No new event is needed.
  5. In an Initiative, Fixes #n goes in two places. It goes on each Task's merge into the Initiative's branch, and also on the Publishing Task's commit and pull request, which reach the default branch. GitHub closes issues only from the default branch.
  6. Shape into a Task stays one click for a Feature. It becomes a split button whose menu offers all three Kinds: "Shape into a Feature Task", "Shape into a Bug Task" and "Shape into a Chore Task".
  7. The bug details show only on a Bug. Changing the Kind away from Bug keeps them, hidden, so changing it back loses nothing.
  8. A Done card keeps its Kind mark. work-board.md says a Done card shows no marks beyond its Project's. Kind says what the Task is, not what is happening to it, and definition of done 5 asks for it on each card. So it becomes the one exception.
  9. The Work board gains a second way to add Tasks. work-board.md says Tasks are made only from Create. Import issues… adds Tasks from GitHub, so it sits on the filter bar, before the Layout group, as well as on the Project page.
  10. The Bug Task Decision is a new form of the Decision card, as the approval card is. It has editable fields and three actions: Create the Bug Task, Don't create it and Ask me again. Like any Stage Thread's Decision, it can't be dismissed.
  11. The Drop window stays Small (440px). It now holds an optional reason, so it is a short form rather than a bare confirmation. Medium would make the most common case, a Drop with no reason, look heavy. The Gate's Drop step shows the same reason field in its step over the bar.

Overview

Words

The glossary has Command kind, a Project command's kind, and the spec speaks of a Stage's kind. Neither is about a Task, so Task kind is free. On a Task it shows as Kind, with the same word in the code, the API and the database (kind). The card and the Task page always say "Kind" next to a Task's own values, so the word can't be read as a Stage's or a command's kind.

Term Glossary entry (proposed) Avoid
Task kind What a Task is: Feature, new or changed behaviour; Bug, something that doesn't work as it should; Chore, upkeep such as an update or a clean-up. It shows as "Kind" on a Task. New Tasks are Features. The Tasks The Office adds on its own (Onboard, run environment set-up, Publishing, Conflict resolution) are Chores. Type, Issue type, Category, Issue (as an entity)
Drop reason Why a Task was Dropped, optional: Won't fix, Duplicate (of another Task), Can't reproduce, or Other (with words). Resolution, Close reason
Caused by The Task whose change brought a Bug in. The other Task lists it under "Caused bugs". Regression of, Introduced by
Found in version The release a Bug was seen in: one of the Project's v* tags, or free text. Affected version
Found while working on The Task whose Agent found a Bug and proposed the Bug Task. Parent, Origin task
GitHub issue An issue in a Project's GitHub repository. Importing one makes a Task from it, once only, and the Task lists it in its linked records. Ticket, External issue
Bug Task Decision A Decision an Agent opens with propose_bug_task on its own Task, for a big issue outside its scope. "Create the Bug Task" makes a Bug Task in Backlog from the form as edited. It isn't a Proposal: it waits on the user as a Decision does. Bug report, Bug Task proposal

Engineering · work and projects

Data and migration

There are two migrations, one per module, and both only expand. The previous release keeps working: it never reads the new columns, and its inserts take their defaults.

0174_task_kinds_and_drop_reasons.sql (work)

ALTER TABLE tasks ADD COLUMN kind text NOT NULL DEFAULT 'feature';
--> statement-breakpoint
-- Tasks The Office made are Chores (Onboard, run environment set-up, Publishing, Conflict resolution).
UPDATE tasks SET kind = 'chore' WHERE made_for IS NOT NULL;
--> statement-breakpoint
ALTER TABLE tasks
  ADD COLUMN drop_reason text,                          -- 'wont-fix' | 'duplicate' | 'cant-reproduce' | 'other'
  ADD COLUMN drop_reason_text text,                     -- Other's words only
  ADD COLUMN duplicate_of_task_id uuid REFERENCES tasks(id),
  ADD COLUMN caused_by_task_id uuid REFERENCES tasks(id),
  ADD COLUMN found_in_version text,
  ADD COLUMN found_while_working_on_task_id uuid REFERENCES tasks(id),
  ADD COLUMN created_by_the_office boolean NOT NULL DEFAULT false;  -- created_by still names a user
--> statement-breakpoint
CREATE INDEX tasks_kind_idx ON tasks (kind);
CREATE INDEX tasks_caused_by_idx ON tasks (caused_by_task_id) WHERE caused_by_task_id IS NOT NULL;

created_by always holds a valid Author, so the previous release reads every row as it does today and names a user as the creator of The Office's Tasks. Only the new release reads created_by_the_office. No value appears that the previous release's authorOf or its contracts don't know.

  created_at timestamptz NOT NULL,
  done_at timestamptz,
  tries integer NOT NULL DEFAULT 0,
  last_problem text
);
Rule Where it lives
Kind, Caused by and Found in version change in any state but Done and Dropped, and never move the Task. work/domain/task-changes.ts: changeKind, changeCausedBy and changeFoundInVersion, refused as the title is: "A Task keeps its Kind once it is Done or Dropped."
Caused by is another Task, never itself, in any Project and any state, archived ones included. changeCausedBy. A cycle is allowed: two bugs may each have caused the other.
Found in version is 1 to 64 characters, trimmed. Contract and domain. The value isn't checked against tags, since free text is allowed.
Drop reason: Duplicate needs a Task other than itself; Other needs 1 to 500 characters; the others take nothing. work/domain/drop-reason.ts, applied in the drop's state change, so the reason and the move are one write.
Office-made Tasks are Chores. createTaskMadeFor sets kind: "chore".
New Tasks default to Feature. TaskService.create, IdeaService.shape, create_task, Initiative add_task and Proposals: kind ?? "feature".

Engineering · projects

GitHub issue rules

Concern Rule
Import by hand Title, then body as the Description (empty body gives an empty Description). Kind is Bug with a bug label, any case, else Feature. Priority is Normal, state Backlog, and the creator is the user who imported it. Up to 50 per request.
Auto-import IssueWatch runs through Schedule.every(5 min), for each Project with a label and a GitHub remote, while GitHubAccess has a valid token. With no token it skips silently. It imports open issues with the label that aren't yet linked, at most 50 per check, oldest first, created by The Office.
Import-once UNIQUE (remote_url, number). Rows are never deleted when a Task is Dropped or archived. Both paths insert the row first and treat a unique violation as "already imported".
Closed on GitHub The same 5-minute check reads the state of every link whose Task hasn't ended, and sets or clears closed_on_host_at. The Task doesn't move.
Close on Done (on by default) A Fixes #n line goes in the commit message and the pull request body, on the Push + PR path and the merge path. GitHub closes the issue when the change reaches the default branch.
Comment on start and Done (off) On start: "Work on this issue started in The Office: <Task title>." On Done: "Done in #<pull request>." with Push + PR, or "Done in <short sha>." with merge.
Close on Drop (off) A comment giving the reason, then close as not_planned. The comments are: "Closed: won't fix.", "Closed as a duplicate of #m." (or "…of another Task in The Office: <title>." when that Task has no issue), "Closed: can't be reproduced.", "Closed: <Other's words>", and "Closed: the Task was dropped." with no reason.
Failures Every comment and close goes through issue_write_backs and is tried at once. What fails is retried on each 5-minute check for 24 hours, and its problem shows on the Task's GitHub issue record.
Out of scope Two-way sync: edits on GitHub don't change the Task, and edits to the Task don't change the issue.
