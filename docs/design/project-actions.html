What this is

An Action is a named entry in a Project's settings that a signed-in user runs on demand, outside the Task queue: a Project command in a fresh checkout, a Test target launched as a test instance, or a Workflow started on the code host. Each start picks what it runs from (a branch, a Task's branch or an Initiative's branch) with the Branch picker; each run keeps a log and a row in the Action's History. An Action marked Leaves the workstation runs from the base branch only, after a confirm step.

The new spec page is 2.15 Actions (docs/spec/2.15-actions.md), not 2.14 as the Plan said: 2.14 is Activity. Project devices, the device a run or an Install on a device target holds, are part of the same change in 2.13.

Open choices for Review Design

The drawings follow the recommended option of each. Pick another and the screens change as noted.

1 · The term

  • RecommendedAction
  • OtherProject action

Short, and it reads as a button's verb ("Run Release"); the glossary already keeps it apart from Office action, Workflow and a CI run.

2 · The Workflow kind

  • RecommendedInclude it now
  • OtherLeave it out for now

It reuses Start a workflow and the CI run tracking that already exist, and a release is the Action people most want behind a confirm step.

3 · Limits

  • RecommendedA separate Actions at once (2, 1 to 6)
  • OtherShared with Run environments at once
  • RecommendedOver the limit: refuse, naming what holds it
  • OtherOver the limit: queue

A user pressing Run should never wait behind Tasks' checks, nor take a slot a Task needs; a refusal that names the runs is clearer than a silent queue for something started by hand.

4 · Agents

  • RecommendedNo Agent starts an Action at first; start_workflow refuses a Workflow a Leaves the workstation Action starts
  • OtherA run_action Office tool behind a new Hard switch

Actions are what reaches outside; keeping them human-started first costs nothing now, and a Hard switch can be added once the confirm rules have been lived with.

5 · Installing

  • RecommendedReuse the newest Built files of the chosen branch when their commit is the tip, else build first
  • OtherAlways build

Installing the same commit on a second phone, or again after a failed install, takes a minute instead of a full Gradle build; a different commit always builds.

6 · A Project device

  • RecommendedLent to a Task, one environment at a time
  • OtherExclusive to the Project's Actions and test targets

The phone on the desk is the one a Task's Agent needs too; one holder at a time, named in every refusal, keeps it safe without a second pairing.

What the traces found

Closed in the spec after tracing:

  1. Removing an Action removes its runs and their logs, on 2.15 › Defining Actions and project-page.md › The Actions list alike.
  2. A Test target run stopped by its user (its instance Failed, "Stopped by you.") counts as Stopped (2.15 › States).
  3. The device during the build: it is held only while Installing; one taken meanwhile ends the install Failed, naming the holder, and keeps the build for the next launch (2.12 › Install on a device).
  4. A Workflow run finds its CI run (the first one of that Workflow on that branch started by hand by The Office’s sign-in after the start), waits at most 60 seconds for it, maps success / cancelled or skipped / other to succeeded / stopped / failed, and records the commit the CI run reports (2.15 › States).
  5. A user around the confirm step: Work › CI’s Start a workflow refuses a Leaves the workstation Action’s file, as start_workflow does, whatever its inputs (6 › Actions).
  6. The confirm step shows a Workflow’s fixed inputs, so “Release” and “Release dry run” read apart (project-page.md › The Run window).
  7. Glossary: a Test target and a Test instance are on any branch, not only an Initiative’s.
  8. The tile’s Run is disabled while its last run is running, as on The Actions list (project-page.md › Actions tile).
  9. Installing counts toward Test instances at once everywhere it is named: settings.md, the glossary, 2.1.4, 5.1.2 and 5.3 now say Building, Installing or Running, as 2.12 does.
  10. Outcomes: a Project command or Workflow run raises its own; a Test target run raises none, as its test instance does (2.15 › States, 2.7).

Still open, small, for the build Task:

  1. The file, not the inputs: an Agent can’t start release.yml even with dry_run=true. Kept on purpose: it is the safer reading.
  2. An Office update scheduled: whether a new Action start is refused while an update waits (5.1.2 › Updating The Office).
  3. A device’s holder for an Install on a device run is drawn as the Action run.
  4. Who gets a test instance’s Outcome isn’t named in 2.7 › Test instance Outcomes (unchanged by this Task).
  5. Project feature switches have no screen yet: the actions switch joins the registry the feature-switch Task builds.
