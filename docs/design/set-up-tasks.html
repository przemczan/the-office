Onboard, Set up run environment and Set up test targets, on demand

Onboard and Set up run environment become Off-board Tasks: The Office makes the Task and starts it in the same click, keeps it off the Work board and shows it on the Project page, in Activity and on Now. Set up test targets becomes a chat with Devops that ends with its Proposal. The tabs walk each screen; the bar above each drawing switches its states.

Palette
The new term · for the glossary · chosen by the user Off-board Task

A Task The Office makes for a Project’s set-up and starts at once, with no Ready step and no Start: the Project’s Onboard Task and its Set up the run environment Task. It is still a Task, with its page, worktree, Stages, Decisions, Verify and Publish; it is only kept off the Work board, and the user follows it on the Project page, in Activity and on Now. It waits Queued, with its place, while the Project limit or the Office’s queue is full. A Project has at most one of each kind in flight.

Avoid: set-up Task, job, background Task, hidden Task, run (a “run” is already a Stage run). The spec’s loose phrase “set-up Task” (project-page.md, 5.5) becomes “Off-board Task”. The Activity kinds keep their names, Onboarding run and Run environment set-up: each is one kind of Off-board Task.

One status, every kind

One component, OffBoardTaskStatus, draws an Off-board Task in each card: its state badge, its title, its Stages as on a board card, a meta line (who, time in Stage or place in the queue, tokens) and one link.

  • Queued: “Place N in the queue” and the queue’s short reasons.
  • Running: the Stage, its person, time in Stage; link Open the Thread.
  • Waiting on you: the question, Answer opens it on the Task page.
  • Paused: Resume, as on the Task page.
  • Failed: the out-of-tries question and the error, Retry and Open the Decision.
  • Done: when, how it was published, tokens.

One of each kind

  • While an Off-board Task of a kind is in flight (anything but Done or Dropped), the card shows it in place of the button.
  • The service refuses a second one, as the existing partial unique indexes do; pressing twice answers the one in flight.
  • A start that is refused (no Onboard Pipeline, nobody holds the duty, the fire alarm) makes nothing and shows the refusal under the button.

Failed and Retry

  • Failed is the out-of-tries Decision of today, unchanged: it goes to the CTO first, then the user.
  • While the CTO has it, the card says so with no Retry.
  • Retry answers that Decision with its first option (“Run <Stage> once more” or “Give it N more rounds”), no guidance. Open the Decision is for guidance, Continue with the issues, or Drop.

Onboard on the Project page (new)

  • Onboard (primary) while the Project has never had an Onboard Task: one added by hand.
  • Onboard again (secondary) once its latest Onboard Task is Done or Dropped. It is the user’s choice, so it never shows while one is in flight.
  • The Project’s onboarding (the badge here, on the Projects page and in the head) reads from its latest Onboard Task. The earlier ones are listed under Onboarding history, each linking to its Task page.
  • The index tasks_onboard_task_per_project (one for good) becomes one open Onboard Task per Project, as the run environment one already is. This is the user’s call, beyond add-only: see What stays.

Work board

Off-board Tasks are left out of the board: its columns, its counts and tabs, its search, and the Project page’s Work tiles. Every other Task the Office adds (Publishing, Conflict resolution) stays on it. A Bug Task made from an Off-board Task’s propose_bug_task Decision is an ordinary Task, in Backlog, on the board.

Still a Task

  • The Task page opens it from every link (Project page, Activity, Now, Notifications).
  • The Off-board Task badge sits by its Kind, and the one-line note says why it isn’t on the board.
  • Dropping it frees its kind: the Project page’s button comes back.

What stays as it is

PublishUnchanged: the Project’s publishing mode, the Task’s branch, its pull request, merge rules and Delete branches once merged. Nothing pushes outside the Publish Stage.
Out of triesUnchanged: a Stage out of tries goes to the holder of Asked first when a Stage runs out of tries (the CTO), then to the user. Only how the user sees it changes (Failed, Retry).
Bug TasksNo Off-board Task makes a Bug Task on its own; none does today either. An Agent’s propose_bug_task stays a Decision the user answers.

Plain about the record

The spec says it in one line on 2.1.3 and in the glossary: an Off-board Task is a Task, kept off the board; “without a Task” means no Ready step, no Start and no board card, not no record.

  1. Contracts (packages/contracts/src/)
    • work.ts: OFF_BOARD_TASK_MADE_FOR (onboard, run-environment-setup) and isOffBoardTask; offBoardTaskSchema, the Project page’s read model: Task id, title, kind, state (queued with place and short reasons, running, waiting-on-you, paused, failed with Stage, error, Decision id and whether the CTO has it, ready for an old one, done, dropped), current Stage, Stages, person, since, tokens; offBoardTaskStartedSchema, the start’s answer (started, or queued with place).
    • projects.ts: the run environment set-up answer carries the Off-board Task’s start; testTargetsChatSchema (Thread id, Role key, state draft / answering / waiting-on-you / proposal, since).
    • activity.ts: kind run-environment-set-up; tokens and a queued place on both set-up kinds.
    • notifications.ts: Needs you’s Decision item gets offBoardTask (kind, Stage, error) when it is an Off-board Task’s out-of-tries Decision.
  2. Work (apps/service/src/modules/work/)
    • An application service that makes an Off-board Task and starts it in one call, through the existing startOrQueue; a refused start makes nothing. OnboardingService.addOnboardTask and RunEnvironmentSetUps.add use it.
    • POST /projects/:id/onboard: Onboard, and Onboard again once the latest Onboard Task is Done or Dropped; refused while one is open. GET /projects/:id/off-board-tasks, the latest of each kind, with the earlier Onboard Tasks as history.
    • OnboardingService, projectOnboardingOf and GET /onboardings read a Project’s onboarding from its latest Onboard Task.
    • TestTargetsSetUps makes no new Task: its POST goes; its GET .../set-up-task stays for one made before.
    • Migration 0194: drop tasks_onboard_task_per_project and add tasks_open_onboard_task_per_project (made_for = 'onboard' and state not Done or Dropped). made_for and the run environment index already hold the rest.
  3. Projects and Conversations
    • Projects: table test_targets_chats (Project id, Thread id, asked by, asked at), migration 0195; POST and GET /projects/:id/test-targets/chat; ends on the Thread’s test-targets Proposal applied or dismissed.
    • Conversations: a port to start a chat Thread with the duty holder, titled, and to read its state for the card. No tool change: the chat already has propose_test_targets.
  4. Pipelines, Activity, Notifications
    • Pipelines: no change to the walk or the out-of-tries Decision; a read of a Task’s Stage-run tokens, if Work and Activity don’t have one already.
    • Activity: the new kind, tokens, Queued; Off-board Tasks never as Task, Failed Task or Stopped Task items.
    • Notifications: needsYouOf marks the set-up failure; Now’s Running and Queue carry madeFor for the badge.
  5. Web (apps/web/src/)
    • surfaces/projects/: OffBoardTaskStatus, used by the Onboarding card (with Onboard) and run-environment-block.tsx; test-targets-block.tsx asks in a chat and follows it; projects-page.tsx and the Project Proposal card’s applied line.
    • surfaces/work/: isOnBoard leaves Off-board Tasks out (board, groups, tab counts, search); run-environment-question.tsx hint and after-Yes line; the Task page’s badge and note.
    • surfaces/now/: the Off-board Task failed card with Retry (answers the Decision’s first option through the existing answer route); the badge in Running and Queue.
    • surfaces/activity/: the group’s words, the new kind, tokens.
    • shell/chat/ask-in-chat.tsx: an asking that takes a Thread started by the service.
  6. Spec and maps
    • 2.1.1 Onboarding a Project, 2.1.3 (Task, Tasks The Office adds), 2.3.5 Built-ins, 2.12 Set up test targets, 2.14 What is listed, 5.5 Writing the run environment definition; screens project-page.md, projects.md, activity.md, now.md, task-page.md, work-board.md.
    • GLOSSARY.md: Off-board Task; Onboarding, Run environment, Set up test targets, Activity and Task kind reworded. The README’s topic map gets the term; docs/design/README.md lists this drawing.
    • npm run maps for Work, Projects, Conversations, Activity, Notifications and the projects, work, now and activity surfaces.

Order

Contracts first, then the service modules (Work before Activity and Notifications, which read it), then the web, then the spec. Projects and Conversations can go beside Work: they share only the contracts.

Tests that cover it

  • Activity and Notifications: the kinds, tokens, Queued, the set-up failure.
  • Projects: the test targets chat record and its end.
  • Web: isOnBoard, OffBoardTaskStatus states, the Test targets card.
