Free Stage placement, with snapping and Auto-align

A Stage no longer sits in a column and a row: it stands wherever it is dropped on the canvas, snapping to a grid and to the other Stages. Auto-align lays the whole Pipeline out as a layered diagram, left to right, and one Undo puts it back. Where a Stage stands is layout alone: the Pipeline’s order is the Stages’ own list, so moving a Stage never changes how the Pipeline runs.

Position model

The contract stores where each card stands and nothing more. The order, routes and limits stay as they are.

Fieldposition: { x, y } on every Stage of a Pipeline, a Project Pipeline and a Task’s own Stages. It is absent wherever routes is absent (a Stage template’s Stage, a plain list).
What it marksThe top-left corner of the Stage’s card. Cards have different heights (their route rows), so the top-left corner is the one point that doesn’t move when a route row is added.
UnitsCanvas units: one CSS pixel at 100% zoom. Whole numbers only.
Boundsx and y from −20000 to 20000. Anything else is refused: “A Stage’s position is two whole numbers from −20000 to 20000.” The origin has no meaning: the canvas draws the box around all Stages with its own margin, so a drop past the left or top edge just grows the canvas, and the view moves to keep everything in place.
EndendPosition: { x, y } on the Pipeline (and on a Task’s Stages), optional. End can be dragged like a Stage. When it has no position, it stands 76 to the right of the right-most Stage, level with the first final Stage in the order.
Card size232 wide (unchanged). Height: 72 for a card that lists no route rows, otherwise 82 plus 22 per route row. The editor measures the real heights. The service only uses this estimate where it has to (conversion, filling in a missing position).
OverlapsThe editor never drops one Stage onto another (see below). The service doesn’t check overlaps, because it doesn’t know the real heights. Auto-align clears any overlap an Office tool or the previous release left.

A Stage without a position

  • No Stage in the list has one (an Office tool leaving them all out, or a plain list): the Stages stand in one row in the order given, x = index × 308, y = 0. That is today’s straight line.
  • Only some have one: each Stage without one stands 76 to the right of the Stage before it in the order, at that Stage’s y, moving down in steps of 16 until it covers nothing (by the estimated heights). This is the same rule as Add a Stage.
  • It has a place but no position (a Proposal stored before the update, or a list saved by the previous release after a rollback): it is converted from the place (Conversion).

The Pipeline’s order without columns

Today the order comes from the places (columns left to right, then rows). With free positions that would mean a small drag could change the start Stage or turn a route on into a route back. So the order becomes the Stages’ own list, which the editor, the service and the Office tools already pass around in order.

Rule: the Pipeline’s order is the order of its Stages’ list. Positions are layout alone: no rule of the walk, the check, the limits or the summary reads them.

What stays the same

  • The first Stage in the list is the Pipeline’s first Stage, where every walk starts. The start marker is drawn into it wherever it stands.
  • A route back still means a route to its own Stage or an earlier one in the order. Its default limit (3), the “N routes back” summary and the Routes out hints all read the order, never where Stages stand.
  • The Pipeline rail, the Later Stages, every “Goes to” and “What it tests” select, and the panel’s “N of M in the Pipeline’s order” list Stages in this order.
  • The arrow keys still pick the previous or next Stage in the order.
  • The line drawing goes by where Stages stand. A route on can therefore point left if you placed it so. Auto-align straightens that out.

Locks (Edit for this Task)

  • Today “the columns up to the last holding a locked Stage are frozen”. Now: the order up to the last started Stage is frozen. No Stage is added among those Stages or moved earlier into them, and Move earlier / Move later are disabled on a started Stage (“Started, so it keeps its place in the order”).
  • Positions are never locked. A started Stage can be dragged and Auto-align moves it, because where it stands doesn’t touch what has run. The service’s lock check compares a started Stage without its position.
  • The old refusal “<Stage> has started, so it stays where it is.” goes.

Behaviour

  • Where: a secondary button Auto-align in the head, before the host’s Add a Stage. Tooltip: “Lay out the whole Pipeline from left to right in its order”. Not shown on a read-only flow (a Proposal, a locked-only view) or under 560px, where stored positions aren’t drawn. Disabled with “Add a Stage first” on an empty Pipeline.
  • What it moves: every Stage, started ones included, and End. It changes no field, route or limit, and not the order.
  • How it looks: the cards glide to their new places (280ms, none with reduced motion), the lines fade back in at the end, and the view fits the Pipeline.
  • Undo: one edit in the draft. The hint names what happened, with an Undo link. Ctrl/⌘+Z while focus is in the editor does the same. Undo puts every Stage and End back exactly, and the hint says “The Stages are back where they were before Auto-align.” The next edit of any kind replaces that hint and Undo goes with it. Save saves whatever is shown. This Task adds no general undo history.
  • Rounding: positions are rounded to whole units, not to the grid, so the lines it straightened stay straight.
  • Same input, same result: the same Stages, sizes and order always give the same layout.

  • Only the positions are used. ELK’s routed lines are thrown away. The editor draws the lines itself, with today’s rules: a route back in its own lane above the Stages it spans, lanes a mark’s height apart. The next Task, Switchable route-drawing modes, rewrites the drawing.
  • Library: elkjs (EPL-2.0, maintained by the Eclipse ELK team), pinned at its current release. It runs in a Web Worker so the page never stalls, and loads with a dynamic import() on the first press. It is about 1.5 MB unzipped and never part of the main bundle. A Pipeline of 30 Stages lays out in a few milliseconds.
  • Why not dagre or own code: dagre (MIT, smaller) can’t be told the model order or fixed ports, and its cycle breaking would choose its own “routes back”. Our own Sugiyama would be a few hundred lines of crossing minimisation and placement to keep up. ELK is the mature, well-tested option. One thing to note: EPL-2.0 is weak copyleft at the file level. Using it unchanged as a dependency is fine, but it is the user’s call to accept it.
  • A Proposal’s Stages: a Proposal on the flow is read-only, so it offers no Auto-align. A Stage it adds stands where it says, or where the missing-position rule puts it. Once applied, the user can Auto-align as with any Pipeline.

Narrow screens (canvas under 560px)

A freely placed Pipeline zoomed to 390px would be about 20%, too small to read. Laying it out afresh for the phone would show a different picture from the one its owner arranged. So the narrow view turns your own layout a quarter turn, as today’s down view turns the grid:

  • Bands from positions: going through the Stages by x, a Stage joins the current band when its card overlaps the band by at least half a card (116). Otherwise it starts a new band.
  • Bands read top to bottom. Within a band, Stages sit side by side by y, top first, at most 2 to a line, and a third wraps onto a new line.
  • End always stands last, in a band of its own. The start marker comes down into the first Stage.
  • The lines use today’s down rules: routes leave the bottom edge and enter the top edge, and a line that goes back up runs in a lane on the left.
  • A converted Pipeline reads exactly as it does today, because its columns become its bands. After Auto-align, each layer is a band.
  • Nothing is stored: the narrow view never changes a position. Dragging a Stage is off (a touch scrolls). Shift + arrows do nothing, and Auto-align is hidden. Move earlier / Move later, Routes out and drawing from the + all work as today.
  • The hint: “Press a Stage or a route to edit it below. The Pipeline reads top to bottom here, as its Stages stand from left to right on a wider screen. Move and Routes out do everything without dragging; drag from a Stage’s + to draw a route.”

Conversion

One migration gives every stored Stage a position that matches where it stands on today’s grid. It keeps place, so the previous release, which reads only places, still runs after a rollback (AGENTS.md: migrations only expand).

From a column and a row to a position

x = column × 308               // 232 card + 76 gap, today's column pitch
y = Σ over rows r < row of (rowHeight(r) + 22)
rowHeight(r) = the tallest card on row r across the Pipeline
             = 72, or 82 + 22 × its route rows

This matches today’s CSS grid, whose rows are as tall as their tallest card with a 22 gap. Using the estimate over the real height at worst leaves a few units of extra space.

What is converted, and how

Library Pipelines, Project Pipelines, Tasks’ own StagesThe migration, per stored list: sort by place (column, then row, stable, as pipelineOrder does today), add position by the formula, leave place as it is. It skips a Stage that already has a position, so it is safe to run twice.
Built-in PipelinesTheir definitions in built-in-pipelines.ts carry positions laid out once with Auto-align and checked in, listed in their order. Each built-in keeps its order. A test checks that order against the old places and checks for no overlaps by the estimated heights.
Stage templates, built-in Stage templatesNothing to convert: a template keeps no routes and no position, as it kept no place.
Open Proposals, stored before the updateConverted as they are read: a list with places and no positions is sorted by place and positioned by the formula. Apply then saves positions.
Saving, from this release onWrites the list in its order, each position, and place: { column: index, row: 0 }. The previous release, reading only places, then sees exactly the same order and runs the same walk. It draws a straight row, and that is fine for a rollback.
After a rollback and update againA Stage the previous release saved has a place but no position (its schema drops unknown keys), so it is converted from the place when read.
Next releaseDrops place from the schema, the read fallback and the migration code, once no release that reads it can be rolled back to.

The Proposal on the flow

  • It draws the Stages where the Proposal puts them, with a Stage it adds standing where it says or where the missing-position rule puts it. Proposed routes are dashed and taken-away ones dotted, as today.
  • When it changes the order, the banner adds: “It changes the Pipeline’s order to Plan, Implement, Lint, Tests, … .” When it moves Stages: “It also moves 3 Stages on the canvas, which doesn’t change how the Pipeline runs.”
  • Positions changed since the Proposal was made don’t make it stale, because they are layout. Apply change takes the Proposal’s position for each Stage it adds or moves, and keeps the current position of every other Stage.
  • The order and the routes changing since still make it refused, as today.

Spec changes to write with the implementation

2.3.2 Flows, “The Pipeline’s order” (replaces its first two bullets and the column bullet)

- A Pipeline's Stages are a list, and **the Pipeline's order** is that list's
  order.
- It lists the Stages (the Pipeline rail, the Later Stages, the editor's
  selects) and says which route leads back, never which route the walk follows.
- The Pipeline's first Stage is the first in this order, where every walk starts.
- Each Stage keeps its **position** on the flow editor's canvas, which is layout
  alone: moving a Stage, or Auto-align, never changes the order.
- Move earlier and Move later change it; a Stage added goes right after the
  picked one, or last ([its screen](screens/pipeline-flow-editor.md#flow-view-the-canvas)).
- A route may lead to any Stage, its own included; the canvas draws a route back
  as it draws any other.

2.3.5 Library

  • Line 44: “… their order and its place” becomes “… and its place in the Pipeline’s order; its position on the canvas can still change”.
  • Lines 82, 140, 169, 181: “place” becomes “position” (a template keeps no position; a Project Pipeline has its own Stages, routes and positions).
  • Line 178 (the conflict chain’s new row) describes the historical update, so it stays. A new heading, “The move to positions”, records the conversion as the other moves are recorded.

GLOSSARY

  • Pipeline: “Its Stages keep an order, the Pipeline’s order, the order of its Stages’ list; each also has a position on the canvas, which is layout alone.”
  • New Position (a Stage’s): “Where a Stage’s card stands on the flow editor’s canvas, its top-left corner in canvas units; layout alone, never part of how the Pipeline runs.” Avoid: place, coordinates, cell.
  • New Auto-align: “The flow editor’s button that lays out the whole Pipeline as a layered diagram from left to right in the Pipeline’s order, undone by one Undo.” Avoid: tidy up, auto-layout, arrange.

Building it

Contracts

  • stagePositionSchema = z.strictObject({ x: z.int().min(-20000).max(20000), y: … }). Add position to stageFields, and endPosition wherever a Pipeline’s or a Task’s Stages are carried (Pipeline, Project Pipeline, Task Stages edit and answer, the Proposal payloads).
  • stagePlaceSchema stays, marked as kept for the previous release.

Service (pipelines)

  • flow.ts: pipelineOrder becomes the identity on a list, and comparePlaces only sorts a place-only list once as it is converted. orderIndexes and leadsBack read the list index. asFlow fills in missing positions (all, some, from a place). isStraightLine reads routes and order only.
  • One domain function, positionFromPlace, with the estimated height, used by the migration and the read fallback.
  • The migration over pipelines.stages, project_pipelines.stages and the Task Stages table, as above.
  • The save path writes place: { column: index, row: 0 } beside each position.
  • The lock check compares started Stages without their position, and checks that the order is frozen up to the last started Stage.
  • The Office tools and Proposals as described. The Proposal’s Apply merges positions.

Web (shell/pipelines/flow)

  • flow-layout.ts: drop gridCellOf, endCellOf, flowGridSize, dropAt and its slots. Boxes come from positions and measured sizes. Routes back keep their lanes, computed from horizontal spans. Narrow gets narrowBands(positions), which feeds the existing down drawing.
  • A new flow-snap.ts (pure): snapMove(box, others, grid, reach) → position and guides, clearSpot(box, others), and freeSpotBeside(stage, others).
  • A new flow-auto-align.ts: builds the ELK graph (order, sizes, ports, End), runs it in the worker, and maps the result to positions. Lazy-loaded.
  • use-flow-drag.ts: snapping, guides, Alt and Shift, the landing outline. The canvas becomes absolutely positioned cards over the SVG.
  • flow-editor.tsx: Auto-align in the head, the one-step Undo with the hint, Ctrl/⌘+Z, and Move earlier / later only.
  • proposal-flow.ts and converted-flow.ts read positions. The moved-flow note is unchanged.

Tests
