# 2.1.1 Projects

Covers: Project, empty repositories, its settings, a Kind's default Pipeline, test targets, Actions and the `actions` feature switch, Project devices, Project limit, Icon and Logo, Project commands, the re-run command, the install command, feature switches, GitHub issues, onboarding a Project.

## Project

- A Project is a repository The Office works on.
- It has its own feature switches, commands, install inputs, default Pipeline (and one per Task kind), publishing mode, GitHub issues settings, environment, skills setting and Project limit (each below).
- Its commands may be left unset when it is added: the repository and a name are enough.
- A command not set is set later on its page or by Devops' Proposal; once set, a command can be changed but not cleared.
- Until a command is set:
  - a Task installs nothing without an install command;
  - a Script Stage whose command isn't set ends could-not-run, saying how to set it, and never passes;
  - the environment check skips it.

## Empty repositories

- A repository with no commits yet can be added as a Project: a folder whose HEAD names a branch that doesn't exist yet, or a remote that lists no branches.
- Its base branch is typed (default `main`) and only checked to be a valid branch name.
- As the Project is added, The Office makes the base branch with one empty first commit ([5.5](5.5-git-and-isolation.md#defaults)), so Tasks have something to branch from and publish into.
- A clone (git URL or From GitHub) pushes that commit to the remote's base branch, never forced, and its base branch tracks it; if the push fails, nothing is added and the add is refused with git's words and what the Office identity lacks.
- A folder's first commit stays local: nothing is pushed.
- A repository that has commits but not the given base branch is still refused.
- Devops' read of a repository by URL still refuses an empty one, as there is nothing to read.

## Project settings

- **Default Pipeline:** the one its Tasks usually follow, one of its own Project Pipelines or an office-wide one ([2.3](2.3-pipelines.md#defaults)).
  - Every Kind with no default of its own follows it (Default Pipeline per Kind, below).
  - A new Task doesn't take it ([Ready](2.1.3-tasks.md#ready)).
  - A command the default Pipeline, or a Kind's own default, runs can't be removed ([Project commands](#project-commands)).
- **Default Pipeline per Kind:** one row each for Features, Bugs and Chores ([Task kind](2.1.3-tasks.md#task-kind)), each a Pipeline of its own or "Same as every Task", which follows the default Pipeline; none has one of its own until set.
  - One resolver gives a Task's Kind its Pipeline: the Kind's own default, else the Project's default Pipeline.
  - The Planner's Brief names it and the Planner proposes it first ([2.1.5](2.1.5-planning-and-start.md#the-kind-and-the-pipeline-while-planning)); the Pipeline rail's picker lists it first, badged "Default for Features", "Default for Bugs" or "Default for Chores" ("Project default" when the Kind has none of its own).
  - A new Task still takes no Pipeline by itself.
  - Choosing one is checked as the default Pipeline is, for the commands it runs ([2.3.5](2.3.5-library.md#a-pipeline-needs-the-commands-it-runs)), and removing a Pipeline a Kind's row names is refused, naming the row.
- **Feature switches:** which of The Office's features the Project uses ([Feature switches](#feature-switches)).
- **GitHub issues:** importing issues as Tasks, the auto-import label and the write-back switches ([GitHub issues](#github-issues)).
- **Publishing mode:** push + PR, or merge, run by The Office's own code ([2.3](2.3-pipelines.md#defaults)).
- **Delete branches once merged:** deletes a Task's branch, here and on the remote, once it is merged, and an Initiative's once it is Done and published; Off by default ([5.5](5.5-git-and-isolation.md#delete-branches-once-merged)).
- **Install inputs.**
- **Environment.**
- **Skills setting.**
- **Test targets:** what can be launched on a branch to try the work, each a key, a name, a kind and its settings, stored in the database only, never in a repository ([2.12](2.12-test-instances.md#test-target)).
  - Edited in its page's Test targets section, by an Agent's `change_project_settings`, or by Devops' `propose_test_targets` Proposal, which the user applies ([2.12](2.12-test-instances.md#writing-test-targets)).
- **Actions:** what the user runs on demand, outside the Task queue, each a key, a name, a kind and its settings, stored in the database only, never in a repository ([2.15](2.15-actions.md#action)).
  - Edited in its page's Actions section, by an Agent's `change_project_settings`, or by Devops' `propose_actions` Proposal, which the user applies ([2.15](2.15-actions.md#defining-actions)).
  - Switched on and off by the Project feature switch `actions`, on by default ([2.15](2.15-actions.md#the-actions-feature-switch)).
- **Devices:** the Project's devices, edited in its page's Devices section ([2.13](2.13-connected-devices.md#a-projects-device)).

## Project limit

- How many of its Tasks may be started at once.
- 1 by default, and up to the Office-wide limit's maximum.
- Set in its page's Work block.
- Only a Project's own Tasks count against its Project limit ([2.1.7](2.1.5-planning-and-start.md#a-queue-for-start)).

## Icon and Logo

- A Project shows as its mark.
- It may have an **Icon**, shown in place of the mark's letters and colour.
- It may have a **Logo**, the larger image on its page.
- Each comes in a light and a dark version, the one for the palette shown used.
- Each is uploaded or chosen from its repository as a copy ([4](4-ux-direction.md)).

## Project commands

- A Project's commands are an install command and a list of named commands, each of a **Command kind:** build, lint or test.
- Every Project starts with three commands, Build, Lint and Test (keys `build`, `lint`, `test`, of the matching kind), which may be left unset when it is added.
- More are added on its page, by Devops' Proposal or by an Agent's `change_project_settings` ([6 Project settings by Agents](6-permissions-and-safety.md#project-settings-by-agents)), in the order they were added.
- Each added command has:
  - a key: lower-case letters, digits and `-`, starting with a letter, at most 40 characters, unique in the Project; `install` and `publish` are reserved;
  - a name: at most 60 characters;
  - a kind;
  - a command line, which can't be blank once added;
  - for a test command, a **Re-run command** ([below](#the-re-run-command)).
- The key is fixed once added, since Pipelines name a command by it.
- The name, kind, line and re-run command can be changed.
- A command can be removed, unless the Project's default Pipeline or a Kind's own default Pipeline runs it: then removing it is refused, naming the Pipeline and the Kinds it is the default for, until another default is chosen.
- A command another Pipeline runs can be removed, and that Pipeline's Stage then ends could-not-run ([2.3](2.3-pipelines.md#defaults)).
- The install command stays apart from the list: it alone runs before a Stage when its inputs changed.

## The re-run command

- A test command may have a re-run command: one command line, blank for none, set beside its command line on the Project's page or by Devops' Proposal, and cleared at any time.
- A command of another kind has none; one given there is refused ("Only a test command has a re-run command.").
- When a test command ran and failed, The Office runs its re-run command once in its place, as the Stage's second run ([5.5](5.5-git-and-isolation.md#a-worktree-per-task)).
  - It passes: the Stage is done, its result naming both lines and calling the failure a flake.
  - It fails too: the Stage fails, naming both lines, with what the re-run printed.
- With no re-run command, a failed test command fails the Stage at once.
- A test command that couldn't run or ran out of time never gets a second run.
- The Office knows nothing of the Project's tools: the re-run command says how to run only what failed, such as `npm run test:e2e -- --last-failed` for Playwright.
- It finds what the first run wrote where git ignores it, such as Playwright's `.last-run.json`; the untracked files git doesn't ignore have been moved out ([5.5](5.5-git-and-isolation.md#a-worktree-per-task)).

## Feature switches

- Each Project switches The Office's features on or off; a Project has no kind, so one Project may use any mix.
- The features:
  - **Connected devices:** a Task's devices and the Project's own devices ([2.13](2.13-connected-devices.md#a-projects-device)); needs Run environment;
  - **Test targets:** the Project's test targets and their test instances ([2.12](2.12-test-instances.md));
  - **GitHub issues:** importing issues as Tasks and writing back to them ([GitHub issues](#github-issues));
  - **Run environment:** the Project's Run environment setting, On or Off, not a second record;
  - **Actions:** the Project's Actions ([2.15](2.15-actions.md#the-actions-feature-switch)).
- Turning a feature on is refused while a feature it needs is off ("Connected devices need Run environment, …"); turning one off also turns off the features that need it.
- The service refuses what a switched-off feature does with words naming the feature and the Project ("Connected devices are switched off for «the-office»."): issue import and issue settings, test target changes, Proposals of test targets and the test targets set-up Task, launching a test instance, connecting or pairing a device, adding, pairing or lending a Project device, changes and Proposals of Actions, starting an Action.
- Switching off:
  - **GitHub issues:** The Office never touches the Project's issues again: no import or auto-import, no closing or comment on a linked issue, no `Fixes #n` on Publish; the links are kept.
  - **Connected devices:** the Project's open devices become Disconnected, a Project device lent to a Task given back; its Project devices are kept, and the Devices tab is gone ([project-page.md](screens/project-page.md#features)).
  - **Test targets:** the Project's Building and Running test instances stop.
  - **Actions:** the Project's running command runs stop; its Actions and their history are kept ([2.15](2.15-actions.md#the-actions-feature-switch)).
- Set on the Project page's Features tab ([project page](screens/project-page.md#features)) or proposed by Devops at onboarding ([Onboarding a Project](#onboarding-a-project)).
- Agents see each Project's switches in `list_projects`.

## GitHub issues

- With GitHub issues switched off for the Project, none of this happens ([Feature switches](#feature-switches)).
- A Project whose repository is on GitHub can make Tasks from its open issues; one elsewhere says so and offers nothing.
- Whether it is on GitHub is read from the remote its base branch tracks, in git's config, without asking GitHub; the Project's record shows it as its code host, and Import issues… offers only the Projects that have one.
- Reading, commenting on and closing issues need The Office signed in with GitHub ([2.10](2.10-users-and-signing-in.md)) and the GitHub App's Issues permission, read and write ([2.3.4](2.3.4-publish.md#the-office-records-the-pull-requests-it-opens-and-refreshes-them-every-minute)).
- **Import by hand**, from Import issues… on the Project page or the Work board, up to 50 issues at once:
  - each becomes a Task in Backlog in the Project, its title the issue's and its body the Description;
  - its Kind is Bug when the issue has a `bug` label, in any case, else Feature; its priority Normal;
  - its creator is the user who imported it.
- **Auto-import:** with a label set and switched on, The Office imports the open issues with that label that aren't yet linked, at each check of the issue watch ([GitHub issues switches](#github-issues-switches)), at most 50 a check, oldest first, as Tasks created by The Office.
- **Import once:** an issue is imported once only, by its repository and number, and its link is never deleted, not when its Task is Dropped or archived; an issue imported meanwhile is skipped and named.
- **Closed on GitHub:** each check reads the state of each linked issue whose Task hasn't ended; the Task never moves, and its page says the issue was closed, as an alert while the Task hasn't started.
- **Write-back**, by three switches:
  - **Close the issue when the Task is Done:** what Publish lands names the issue with `Fixes #n`, so GitHub closes it when the change reaches the default branch ([2.3.4](2.3.4-publish.md#the-tasks-commit-message));
  - **Comment when the Task starts and when it is Done:** "Work on this issue started in The Office: <Task title>." as it starts, and "Done in #<pull request>." (Push + PR), "Done in <short sha>." (merge) or "Done in The Office." (neither known) once Done;
  - **Close the issue when the Task is Dropped:** a comment giving the Drop reason, then the issue closed as not planned; the comment is "Closed: won't fix.", "Closed as a duplicate of #<m>." (or "Closed as a duplicate of another Task in The Office: <title>." when that Task has no issue in the repository), "Closed: can't be reproduced.", "Closed: <Other's words>" or, with no reason, "Closed: the Task was dropped."
- Every comment and close is kept and tried at once, in order; what GitHub refuses is tried again at each check for 24 hours, its problem shown on the Task's GitHub issue record meanwhile.
- **Out of scope:** two-way sync. Edits on GitHub don't change the Task, and edits to the Task don't change the issue.

## Defaults

### No re-run command

- A test command has no re-run command until one is set, so a failed test run fails its Stage at once.
- A command saved before re-run commands existed reads as having none.

### Feature switches

- Connected devices, Test targets, GitHub issues and Actions are on unless set, so a Project keeps the behaviour it had before the switches existed; Run environment is its setting, Off until turned On.
- The update that dropped "Not decided yet" turned every Project that had it Off.
- Adding a Project by hand leaves Connected devices, Test targets, GitHub issues and Actions on.

### GitHub issues switches

- The auto-import is off: no label is set, and turning it off forgets the label.
- The Tasks the auto-import makes are created by The Office; the user who last set the label is kept with it.
- The issue watch checks every Project every 5 minutes, while a GitHub token is valid now; with none it skips, saying nothing.
- **Close the issue when the Task is Done** is on.
- **Comment when the Task starts and when it is Done** is off.
- **Close the issue when the Task is Dropped** is off.

### Onboarding a Project

- Onboarding is a chat, then an Off-board Task ([2.1.3](2.1.3-tasks.md#off-board-tasks)).
- "Ask Devops to onboard one" on the Projects page, naming the holder of Onboards and repairs Projects, opens a chat with Devops, who drafts the Project (path, name, base branch, commands, install inputs, publishing mode, default Pipeline) as a Proposal.
  - It also proposes Connected devices, Test targets and GitHub issues each on or off, with a reason for each, judged from the repository (`read_repository`) and shown on the Proposal card; applying it stores them ([Feature switches](#feature-switches)).
  - Run environment keeps its own onboarding question and Proposal.
- Applying it adds the Project, then makes its "Onboard" Task on the built-in **Onboard** Pipeline and starts it at once, or queues it; a refused start keeps the Project, and the Project page's Onboarding card offers Onboard to try again.
  - The Onboard Pipeline: Devops makes the Project build and test in a fresh worktree, asking before installing anything → a Verify Script Stage running Test, back to Onboard at most twice → Publish by the Project's publishing mode, so the fixes Devops makes reach the repository.
  - In the Onboard Task Devops sets the Project's commands with `change_project_settings` and, once its commands and test targets are set, its Actions the same way, running `run_environment_check` until it passes; without that tool (Change Project settings Never) it proposes them with `propose_project_commands` and `propose_actions`, as it does an Action that leaves the workstation ([2.15](2.15-actions.md#defining-actions)).
- **Onboard**, on the Project page, makes and starts an Onboard Task while the Project never had one; **Onboard again** does once its latest Onboard Task is Done or Dropped, from the base branch as it is now; neither shows while one is in flight.
- A Project has at most one open Onboard Task (neither Done nor Dropped); earlier ones stay, listed under "Onboarding history".
- The Project's onboarding reads its latest Onboard Task: **Onboarded** once it is Done, none once it is Dropped (even when an earlier one was Done) or for a Project that never had one, and **Onboarding** otherwise.
- Adding a Project by hand stays, with no Onboard Task until Onboard is pressed.
  - While nobody holds Onboards and repairs Projects it is the only way, and the Onboard Pipeline's Onboard Stage names that duty.
  - Adding by hand takes a folder, a URL or a pick from the user's GitHub repositories.
- One Onboard Task per Project for good became one open Onboard Task per Project (migration 0194); on a rollback, the previous release may show a Project's earlier onboarding in its badge, and nothing fails.
- The Project may be a Repository URL instead of a path: Devops reads the repository from a shallow fetch with the Office identity, nothing cloned, and applying the Proposal clones it into the Office data directory before adding the Project.

### Recent activity

- A Project's Overview shows its Tasks done or published, its Ideas captured and its Project setting changes ([6 Project settings by Agents](6-permissions-and-safety.md#project-settings-by-agents)) in the last 7 days, newest first, 10 lines at most ([Project page › Recent activity tile](screens/project-page.md#recent-activity-tile)).
