# 2.1.1 Projects

Covers: Project, its settings, Project limit, Icon and Logo, Project commands, the install command, onboarding a Project.

## Project

- A Project is a repository The Office works on.
- It has its own commands, install inputs, default Pipeline, publishing mode, environment, skills setting and Project limit (each below).
- Its commands may be left unset when it is added: the repository and a name are enough.
- A command not set is set later on its page or by Devops' Proposal; once set, a command can be changed but not cleared.
- Until a command is set:
  - a Task installs nothing without an install command;
  - a Script Stage whose command isn't set ends could-not-run, saying how to set it, and never passes;
  - the environment check skips it.

## Project settings

- **Default Pipeline:** the one its Tasks usually follow, one of its own Project Pipelines or an office-wide one ([2.3](2.3-pipelines.md#defaults)).
  - It is named in the Planner's Brief, and listed first when the user chooses a Pipeline for a Task that has none.
  - A new Task doesn't take it ([Ready](2.1.3-tasks.md#ready)).
  - A command the default Pipeline runs can't be removed ([Project commands](#project-commands)).
- **Publishing mode:** push + PR, or merge, run by The Office's own code ([2.3](2.3-pipelines.md#defaults)).
- **Install inputs.**
- **Environment.**
- **Skills setting.**

## Project limit

- How many of its Tasks may be started at once.
- 1 by default, and up to the Office-wide limit's maximum.
- Set in its page's Work block.
- Only a Project's own Tasks count against its Project limit ([2.1.7](2.1.5-planning-and-start.md#a-queue-for-start)).

## Icon and Logo

- A Project shows as its mark.
- It may have an **Icon**, shown in place of the mark's letters and colour.
- It may have a **Logo**, the larger image on its page and card.
- Each comes in a light and a dark version, the one for the palette shown used.
- Each is uploaded or chosen from its repository as a copy ([4](4-ux-direction.md)).

## Project commands

- A Project's commands are an install command and a list of named commands, each of a **Command kind:** build, lint or test.
- Every Project starts with three commands, Build, Lint and Test (keys `build`, `lint`, `test`, of the matching kind), which may be left unset when it is added.
- More are added on its page or by Devops' Proposal, in the order they were added.
- Each added command has:
  - a key: lower-case letters, digits and `-`, starting with a letter, at most 40 characters, unique in the Project; `install` and `publish` are reserved;
  - a name: at most 60 characters;
  - a kind;
  - a command line, which can't be blank once added.
- The key is fixed once added, since Pipelines name a command by it.
- The name, kind and line can be changed.
- A command can be removed, unless the Project's default Pipeline runs it: then removing it is refused, naming the Pipeline, until another default is chosen.
- A command another Pipeline runs can be removed, and that Pipeline's Stage then ends could-not-run ([2.3](2.3-pipelines.md#defaults)).
- The install command stays apart from the list: it alone runs before a Stage when its inputs changed.

## Defaults

### Onboarding a Project

- Onboarding is a chat, then a Task.
- "Ask Devops to onboard one" on the Projects page, naming the holder of Onboards and repairs Projects, opens a chat with Devops, who drafts the Project (path, name, base branch, commands, install inputs, publishing mode, default Pipeline) as a Proposal.
- Applying it adds the Project and an "Onboard" Task in it, Ready on the built-in **Onboard** Pipeline.
  - The Onboard Pipeline: Devops makes the Project build and test in a fresh worktree, asking before installing anything → a Verify Script Stage running Test, back to Onboard at most twice → Publish by the Project's publishing mode, so the fixes Devops makes reach the repository.
- The user starts the Onboard Task, as any Task.
- The Project page shows the Project's onboarding from that Task: onboarding, onboarded, or none.
- Adding a Project by hand stays, with no Onboard Task.
  - While nobody holds Onboards and repairs Projects it is the only way, and the Onboard Pipeline's Onboard Stage names that duty.
  - Adding by hand takes a folder, a URL or a pick from the user's GitHub repositories.
- The Project may be a Repository URL instead of a path: Devops reads the repository from a shallow fetch with the Office identity, nothing cloned, and applying the Proposal clones it into the Office data directory before adding the Project.
