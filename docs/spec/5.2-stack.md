# 5.2 Stack

Covers: languages and checks, backend, web, data, infrastructure and the bundled Grafana, the telemetry setting, what Telemetry sends, estimated cost, how Stats reads Grafana, System health measurement, signing in libraries.

## Languages and checks

- TypeScript end to end on Node 22, in npm workspaces:
  - `apps/service`;
  - `apps/web`;
  - `packages/contracts`, the HTTP and WebSocket contract as zod schemas, the one thing the service and the web share;
  - `packages/ui`, the design system for React;
  - `tools/`.
- Checks: TypeScript strict, oxlint, Prettier, Vitest, Playwright.

## Backend

- NestJS on Express (modules, DI, ports as interfaces, adapters as providers).
- WebSocket push to the browser (`ws`).
- The Claude Agent SDK, the pinned `@openai/codex` and the MCP SDK for the engines ([5.4](5.4-the-engine.md)).

## Web

- React + Vite, TanStack Query and Router, the design system's components.
- react-markdown for long text.
- PixiJS for the Live view.

## Data

- PostgreSQL with Drizzle (typed SQL, repositories in the adapter layer).
- Full-text search.
- JSONB for Stage results and Attachment metadata.
- Attachments are files in an Office data directory with metadata in Postgres.
- Engine transcripts stay where the engine keeps them, referenced by session id; The Office's own message log per Thread is what the UI shows.

## Infrastructure

- One `docker compose` with PostgreSQL for a checkout.
- `grafana/otel-lgtm`, the bundled Grafana, unless the user turns telemetry off or sends it to their own Grafana.

### The bundled Grafana

- The Office runs it itself, on every install kind (checkout, direct install, Compose install), as its own Compose project `the-office-grafana` from a compose file it writes to `grafana/compose.yaml` in the Office data directory.
- The image is pinned in the service's code.
- Grafana is at `http://localhost:3300` and OTLP at 4317 (gRPC) and 4318 (HTTP), all published on `127.0.0.1` only.
- Its data is in a named volume, with `restart: unless-stopped`.
- It needs a Docker The Office can reach, as run environments do.
- Choosing Bundled Grafana starts it at once in the background; Settings › Telemetry shows it starting, running with its link, or why it couldn't start, with Try again.
- At every start of The Office:
  - it is started when Bundled Grafana is saved or that run exports to it;
  - it is stopped (its container and data kept) when Off or the user's own endpoint is saved and nothing exports to it;
  - while nothing wants it and The Office never started one, The Office doesn't call Docker for it.
- With any of the OTEL_* variables set, The Office neither starts nor stops it.
- An earlier bundled Grafana (the `otel-lgtm` service of Compose project `the-office`, or a container named `the-office-grafana` started by hand) is stopped, never removed, before The Office starts its own, and the log and the card name it.

### The telemetry setting

- The Office exports OpenTelemetry over OTLP, as [Telemetry](#telemetry) lists.
- Telemetry is a setting, in First-run setup and Settings › Telemetry: Off, the bundled Grafana (its OTLP endpoint at `http://127.0.0.1:4318`), or the user's own OTLP over HTTP endpoint with optional headers and export timeout.
- It is saved in the Office data directory readable by its owner only, as headers can hold credentials, never sending a header's value back to the browser.
- The exporters switch to it the next time The Office starts.
- Any of `OTEL_SDK_DISABLED`, `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_HEADERS` in the environment wins over it, and the card then says so, read-only.
- With neither the setting nor those variables, telemetry is off.

## Telemetry

- The service is `the-office`; every name is in the `office.` namespace, as the GenAI conventions count cached tokens inside input tokens.

### Traces

- One trace per Task.
  - Its first span, `walk`, carries `office.task` and `office.pipeline` (the Pipeline's id, as a span may carry ids).
  - It is kept with the Task, so a walk after a restart or a Gate joins the same trace.
- A `stage` span per Stage run, with `office.stage`, `office.stage.kind` and `office.stage.run`.
- An `engine call` span per engine call (a turn), with:
  - `office.engine.session`, `office.engine.model`, `office.prompt.features`, `office.engine.outcome` and `office.engine`;
  - the four token counts (`office.tokens.input`, `office.tokens.output`, `office.tokens.cache_read`, `office.tokens.cache_creation`) and `office.cost.usd`, the estimated cost;
  - the caller's own attributes: on a Task, `office.task`, `office.thread`, `office.role` and, in a Stage, `office.stage`; on an Initiative, `office.initiative`.
- HTTP requests and database queries, traced by OpenTelemetry's HTTP, Express and pg instrumentations.

### Metrics

- `office.tokens` (`{token}`), a counter by `office.token.type` (`input`, `output`, `cache_read`, `cache_creation`).
- `office.cost` (`USD`), a counter of the estimated cost.
- Both carry `office.engine.model`, `office.prompt.features` and `office.conversation.home` (`task`, `initiative`, `chat`), and also ([2.11](2.11-stats.md)):
  - `office.role`, the Role key;
  - `office.stage`, the Stage's name, `""` outside a Stage;
  - `office.pipeline`, the Pipeline's name;
  - `office.project`, the Project's name.
- Each of those is `""` where none applies.
- Metric attributes are names with few values, never ids: a Task, Thread, Initiative or session id goes only on spans and in the `office.engine.call` record.
- `office.engine` is the one id on a metric, as engines are few and their names can change.
- The HTTP instrumentation's request durations, `http.server.request.duration`, with `http.request.method` and `http.route`, the route's template.
- **System health's measurements** ([2.11](2.11-stats.md#system-health)) are observed from the Health readings ([System health](#system-health)) through observable instruments, so they have one measuring path.
  - OpenTelemetry's semantic conventions name them where one exists, `office.*` otherwise:
    - `nodejs.eventloop.delay.p99` and `nodejs.eventloop.delay.max` (`s`);
    - `process.cpu.utilization` (`1`, a share of all the workstation's cores), `process.memory.usage` (`By`, the resident memory) and `v8js.memory.heap.used` (`By`);
    - `system.cpu.utilization` and `system.memory.utilization` (`1`), and `system.cpu.logical.count`, by which Stats turns The Office's share of the workstation into its share of one core;
    - `office.db.query.duration` (`s`), a histogram by `db.operation.name` (`SELECT`, `INSERT`, …) and `db.collection.name` (the table), never the statement or its shape;
    - `db.client.connection.pending_requests` (`{request}`), the queries waiting for one of the pool's connections.

### The usage window gauge

- The `office.usage_window.used` gauge (`%`, 0 to 100) shows how full each Usage window is.
- It carries `office.engine` (the engine's id) and `office.usage_window` (`five_hour`, `seven_day`).
- It is recorded at each reading of the windows, whatever its Reading source.
- A window not begun records 0.

### Logs

- The service's log lines, each with the trace and span it was written in.
- One **`office.engine.call`** record (INFO) per engine call that ends with a turn.
  - It is written in the call's span, so it carries its trace; a call that ends without a turn writes none.
  - It holds:
    - `office.task`, `office.initiative` (the Task's Initiative, or the Initiative whose Thread it is), `office.thread`, `office.stage`, `office.stage.run`;
    - `office.role`, `office.pipeline`, `office.project`;
    - `office.engine`, `office.engine.model`, `office.engine.outcome`, `office.engine.call.duration_ms`;
    - `office.tokens.input`, `office.tokens.output`, `office.tokens.cache_read`, `office.tokens.cache_creation`;
    - `office.cost.estimated_usd`, when the call has an estimated cost, and `office.cost.engine_reported_usd`, when the engine reported a cost; the reported cost is never added to the estimate.
  - An attribute that doesn't apply is `""`.
  - These records are what the full stats total per Task, Initiative, Stage and run, and what draws the lane of what was running.

### Estimated cost

- An engine call's cost is priced from its tokens by Settings › Engines › Model prices (`ModelPrices`), as Daily caps and Usage estimates are.
- The engine's own reported cost is used only for a model with no price.
- Codex, Copilot CLI and OpenAI-compatible engines always report 0, so without a Model price their calls cost 0.
- It is always called "estimated": a subscription doesn't pay list prices.

## Stats reads Grafana

- Stats ([2.11](2.11-stats.md)) reads Grafana.
- **The bundled Grafana** is read at `http://127.0.0.1:3300` with no token, while it runs.
- **Your own Grafana:** with "Your own endpoint" chosen, Settings › Telemetry also takes, under the export fields:
  - a **Grafana read address**, the Grafana the endpoint feeds, such as `https://grafana.example.com`;
  - a **Read token**, a Viewer service account token, made in Grafana under Administration › Service accounts.
- Both are optional: without the read address, Stats shows the basic stats.
- The token is kept as the export headers are, in the Office data directory readable by its owner only.
- The token is never sent back to the browser: its field says "Saved, never shown. Leave it empty to keep it."
- Both apply as soon as they are saved, with no restart, as only Stats reads them; the exporters aren't changed.
- **Test** queries the Grafana with the address and token as typed, before Save, and says one of three things:
  - **Reachable**, "Grafana answered at <address>.", naming the Prometheus and Loki data sources it found;
  - **Rejected**, "Grafana refused the read token (401).";
  - **Unreachable**, "Couldn't reach Grafana at <address>: <reason>."
- A Grafana that answers with no Prometheus or Loki data source the token may query is reported as reachable, with "but it has no Prometheus and Loki data sources the token can query."
- With any OTEL_* variable set, Stats reads no Grafana and shows the basic stats only.
- **Querying:** both Grafanas are read through Grafana's data source query API (`POST /api/ds/query`):
  - PromQL on its Prometheus data source for `office.tokens`, `office.cost` and `office.usage_window.used`;
  - LogQL on its Loki data source for the `office.engine.call` records.
- This sits behind the Telemetry module's port **`StatsSource`** ([5.3](5.3-modules.md#defaults)), with a Grafana adapter and a scripted adapter for tests.
  - The scripted one replays recorded answers: data, empty, unreachable and rejected.
- A query that takes more than 10 seconds counts as unreachable.
- Titles, Projects' chips, people's names and titles (by Role key) and engine names come from The Office's own modules, never from Grafana.
- **System health's 24 h, 7 d and 30 d** are read the same way, through `StatsSource`:
  - with PromQL of their own over the measurements above, in the Grafana adapter's `grafana-queries.ts`: a step's highest event loop lag and connections waiting, its p95 times from the histograms, and the mean of the rest;
  - counts and total times come from the histograms' counts and sums over the range, which are few series;
  - every p95 and Max (each step's, the range's and each slowest row's) comes from one read per block of the histograms' buckets, by bound, route or table and step. The adapter adds them up and takes the quantiles itself, as PromQL's `histogram_quantile` does.
    - The buckets are by far the most series, so a read of every raw sample over 7 d would take longer than the 10 seconds a query gets; they are sampled every quarter step instead (75 s on 24 h, 15 min on 7 d, 90 min on 30 d).
    - What a counter counted between its last sample and a restart is left out of them (at most a quarter step per restart), so on those ranges a p95 or Max can miss the requests or queries just before a restart. Max stays the upper bound of the highest bucket that counted one ("at most") for all the others;
  - they meet the same states as the full stats;
  - the scripted adapter has recorded answers for them too.

## System health

- System health ([2.11](2.11-stats.md#system-health)): The Office measures itself, whether telemetry is On or Off, with no dependency on the OpenTelemetry SDK.
- **The recorder,** `SystemHealthRecorder` in the platform layer ([5.3](5.3-modules.md#defaults)), takes a **Health reading** every 5 seconds:
  - the event loop delay since the last reading, p99 and max, from `perf_hooks.monitorEventLoopDelay`, reset after each reading;
  - the process's CPU (`process.cpuUsage`, against the time since the last reading) and memory (`process.memoryUsage`: resident memory and heap used);
  - the workstation's CPU and memory, from the Workstation platform the status strip reads;
  - the requests and queries of the 5 seconds just closed: their count and p95 time, and the most queries waiting for a connection.
- **It keeps an hour,** 720 readings in a ring buffer, in memory only: no table, no migration, and a restart starts it again.
- **Requests:** an Express middleware records each request's duration when its response finishes, by its method and route template (`req.baseUrl` + `req.route.path`), never its address.
  - A request no route answered counts as "Unmatched".
- **Queries:** the database platform's pool wraps its `query` and `connect` in one place, so no module changes.
  - Each query's duration is recorded by its operation and table and by its **statement shape**: whitespace collapsed, string and number literals and `$n` parameters made `?`, an IN list and a VALUES row each made one `?`.
  - A shape is whole: only a statement's first 8,192 characters are read, and the shape of a longer one ends with `…`.
  - It records the pool's waiting count too.
- **Called from:** each shape keeps up to 3 places in the service's code it was run from, kept and dropped with its row.
  - Each query's call is captured as it is made (an `Error`, with up to 30 frames); its stack is formatted only when the recorder reads it.
  - A Drizzle query is captured where it is built: `await db.select()…` awaits Drizzle's own thenable, which V8 runs with no async stack frames, so by the time the pool sends it the caller is gone.
    - The database platform patches Drizzle's builder methods that answer a runnable query (`from`, `values`, `set`, `delete`, `execute`, `findMany`, `findFirst`, …) to keep the call on the query, and its `then` to hold that call while it sends the query to the pool.
    - It installs once, with the pool's query observer; should a patched method be missing, it installs nothing and logs one warning, and queries run as before.
    - drizzle-orm is pinned to an exact version, and a test fails when an upgrade moves a patched method.
  - A query sent straight to the pool or a held client is captured at the pool, `pool.query`'s at its `connect`.
  - A place is the first stack frame under `apps/service/src/` outside `platform/database/`, as `<path from the repository's root>:<line> (<function>)`; the built service maps its frames to the sources with `--enable-source-maps`.
  - The recorder reads a shape's call stacks only while it has fewer than 3 places and for its first 20 queries while its row is kept, so a hot query never formats a stack each time it runs.
- **Bounds:** the hour's tables keep at most 500 statement shapes and 500 routes, dropping the least seen, so a burst of ad-hoc SQL can't grow them.
- **Its cost:** a unit test bounds the time one reading takes, so the recorder never becomes what slows The Office down.
- **Load now** isn't a reading: Stats asks Conversations for the sessions running, Pipelines for the Stage runs running and the WebSocket platform for the browser connections open, when it answers.

## Signing in libraries

- Signing in ([2.10](2.10-users-and-signing-in.md)) uses:
  - Node's built-in `node:crypto` `scrypt` for password, one-time password and recovery code hashes, and its random bytes and SHA-256 for sign-in tokens;
  - `@simplewebauthn/server` and `@simplewebauthn/browser` for passkeys;
  - `@oslojs/otp` for authenticator codes;
  - `arctic` for Continue with Google and Continue with <name>: its OAuth 2.0 client, with the provider's endpoints read from its discovery document by Node's `fetch`;
  - the GitHub module's existing GitHub App for Continue with GitHub.
- No auth framework: better-auth and its like bring their own user, session and account tables and names, which would split the [glossary](../../GLOSSARY.md)'s one language, and "Session" there means only the engine's session.
