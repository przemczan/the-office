# 5.3 Modules

Covers: the modules and what each owns, layers inside a module, how modules talk, where shared plumbing lives, module boundaries per module.

## Architecture

- Hexagonal + DDD, modules as bounded contexts, each in `apps/service/src/modules/<module>/`.
- Each module is layered inside: domain (entities, rules, events), application (use cases), ports, adapters (Postgres, engine, filesystem, HTTP, WebSocket).
- Modules talk through application services and domain events only; no module reads another's tables.
- Every state change emits a domain event, consumed alike by the WebSocket push, Now, Activity, telemetry and Notifications.
- Shared plumbing (config, database, domain events, telemetry, WebSocket, the operating system) is `src/platform/`.

## The modules

- **Work.**
- **People.**
- **Pipelines:** definitions and the Stage interpreter, an interpreter of Pipeline data, never a class with a method per Stage.
- **Conversations.**
- **Projects:** git, worktrees, environment, commands, and:
  - the pull requests it opens, recorded in its own table and linked to their Task by id;
  - the CI runs on its code host, kept in memory only by `CiRunWatch` and re-run by the Office action `rerun_ci_run`;
  - the Workflows that can be started by hand on a branch or tag, started by the Office action `start_workflow`;
  - all of these behind a host-neutral `CodeHost` port chosen by the remote's URL, GitHub its first adapter;
  - `CodeHost` also lists the `manualWorkflows` at a ref and the repository's `refs` and can `startWorkflow`, lists a pull request's `mergeMethods` and can `merge` or `close` it, in host-neutral types;
  - Projects publishes `PullRequestMerged`, `PullRequestClosed` and `PullRequestReopened`, which Work's `PullRequestOutcomes` listener records on the Task;
  - its worktrees include one on a pull request's own branch for a Conflict resolution Task ([5.5](5.5-git-and-isolation.md));
  - each Project's Actions, in `actions` ([2.15](2.15-actions.md#action)), checked against its commands, test targets and Workflows, with an applied Proposal of Actions going through it; it publishes `ProjectActionsChanged`, naming the removed keys; `list_projects` reads each Action's last run state through a port Actions fills;
  - the GitHub issues imported as Tasks, their write-backs and `Fixes #n` ([2.1.1](2.1.1-projects.md#github-issues)), with the one resolver of a Kind's default Pipeline; it makes the Tasks through an `IssueTasks` registry Work fills at start, and Work forwards a Task's start, Done and Drop to its `IssueWriteBack`, so Work stores no GitHub data.
- **Feature switches:** one registry in Projects (`projects.features`) holds each Project's switches ([2.1.1](2.1.1-projects.md#feature-switches)); Devices and Test instances read them through Projects and react to its `ProjectFeaturesChanged` event.
- **Run environments:** each Project's image and each Task's run environment ([5.5](5.5-git-and-isolation.md)).
- **Test instances:** test instances, their launch, log, stop and sweep, the proxy's ports and hand-off links, Build to install files and their download links, and the Test instances limits ([2.12](2.12-test-instances.md)). It depends on:
  - Projects, which owns the test targets and checks their entry points, and the Project's Test targets switch ([2.1.1](2.1.1-projects.md#feature-switches)), whose `ProjectFeaturesChanged` event stops the Project's instances when it is switched off;
  - Run environments' public interface, for a Hosted instance's compose project and a build in the run environment;
  - Work's events, to stop an Initiative's instances when it is Done or Dropped and to remove its builds 7 days later.
- **Devices:** Connected devices, Project devices with their pairing environment and their holds, the relay channel and the Office device helper's start and stop ([2.13](2.13-connected-devices.md)); Work reads a Task's devices, for `read_task` and a Stage's message, through a port Devices fills, and Actions and Test instances hold a Project device through its public interface. It depends on:
  - Run environments' public interface, to run the helper, to start and remove a pairing environment, and to learn when a Task's run environment starts and stops;
  - Projects' `TaskWorktrees`, to start a Task's run environment for pairing a phone over wireless debugging;
  - Projects' export of the base branch tip's `.devcontainer/`, for a pairing environment's definition;
  - Projects' records for Agents (`list_projects`), which name a Project's devices through a port Devices fills, as Work's `read_task` does;
  - Projects' feature switches, read through a port of Devices' own, and its `ProjectFeaturesChanged` event, to disconnect a Project's devices when Connected devices are switched off;
  - Projects' events, to disconnect a Project's devices when its Run environment is turned Off;
  - Work's events, to disconnect a Task's devices when it is Done or Dropped.
- **Actions:** Action runs, in its own table `action_runs`, their start, log, stop and sweep, and Actions at once ([2.15](2.15-actions.md)); the Actions themselves are Project settings, in `actions`, owned by Projects. It depends on:
  - Projects, for a Project's Actions and settings (commands, environment, Secret variables, Run environment, feature switches) and to resolve what a run runs from (a branch, or a Task's or an Initiative's branch) to the commit at its tip;
  - Run environments' public interface, for a command run's compose project ([Actions uses Run environments through their public interface](#actions-uses-run-environments-through-their-public-interface));
  - Test instances, to launch the instance of a Test target Action;
  - Devices, to hold a Project device for a run and let go of it;
  - Projects' `CodeHost`, to start a Workflow Action's Workflow and follow its CI run;
  - Work, for the Task or Initiative a run runs from and its branch;
  - Projects' `ProjectActionsChanged` event, to stop and remove a removed Action's runs.
- **Engine.**
- **Skills.**
- **MCP servers.**
- **Prompt templates.**
- **GitHub.**
- **Users.**
- **Notifications.**
- **Telemetry.**
- **Activity:** the active sessions per subject and the other running work ([2.14](2.14-activity.md)); no module calls it.
- **Office updates:** Office updates and restarts ([5.1](5.1-shape.md#defaults)); it waits for the busy work and schedules the hold below, and calls Engine for its Office actions.
- **Office identity:** the only credentials The Office's git uses ([5.5](5.5-git-and-isolation.md#the-office-identity)): the Office ssh key, the Trusted and Unconfirmed hosts, the git environment of every Office git command and the credential helper that hands it Sign in with GitHub's token, and Settings › Office identity's routes; every module that runs git imports it, and it calls no module.
- **Workstation:** the status strip's Workstation figure (`GET /workstation/load`), read on demand from the platform's Workstation; no module calls it.
- **Busy work:** what an Office update or restart waits for (the Agent turns, background Sub-agents, Script Stages, Publishes, clones, environment checks, run environments and Action runs the modules report where they start and end them), and the hold on Starts and Stages while an update or restart is scheduled; it calls no module.

## Defaults

### Skills is its own module

- It sits next to People and Engine, since it owns the library, versions and assignment, and builds each session's folder from them.
- The Engine takes the folder and the options from the session's owner and never reads Skills.

### MCP servers is its own module

- It is shaped like Skills: it owns the MCP server library, its review, assignment to Roles, the Server values (Office-wide and per Project) and each session's servers.
- The Engine takes the session's servers in its options and never reads the module.

### Prompt templates is its own module

- It owns the catalog of Prompt templates ([2.2](2.2-people.md)), their versions, the check and the rendering.
- It imports no other module, so every module that owns a prompt depends on it.
- Each module declares its templates in its own domain and registers them at start.
- A module's application layer loads the texts it needs at use time, never at start, and passes them to the domain, which renders them.

### GitHub is its own module

- It owns Sign in with GitHub: the GitHub App registered by its manifest, the web sign-in, the user token and its refresh.
- It owns the list of the user's repositories.
- It holds every REST call to GitHub, the pull requests', the issues', the Actions runs' and the workflow dispatches' too, with the reading of a workflow file's `workflow_dispatch` inputs.
- It maps GitHub's values to the host-neutral ones; Projects' `CodeHost` adapter for GitHub lives here, with the words of its merge refusals.
- It reads the permissions the App's installations were granted, cached five minutes, so Settings can say which a registered App lacks ([2.3](2.3-pipelines.md#defaults)).
- Projects and Skills reach the token through ports of their own, bound to it in the app module.
- The Office ssh key and the git environment that keeps every Office git command to the Office identity are the Office identity module's ([Office identity is its own module](#office-identity-is-its-own-module)); where GitHub is (its website and REST API) is the platform's config, which both read.

### Now lives in the Notifications module

- Needs you and Since you left are the Notifications' inbox ([2.7](2.7-notifications.md)), so Now and the status strip are one read model there, built from the other modules' events and application services.
- Now reads Waiting for you ([2.4.2](2.4.2-decisions.md#waiting-for-you)) through ports of its own bound in the app module:
  - Conversations: the open Proposals, and the shaping Threads waiting on the user's reply;
  - Projects: the pull requests needing attention;
  - Skills: the installed Skills with an update;
  - Office updates: the Office update available.
- Only Telemetry's Stats calls Notifications, for tokens per day.

### The Live view's read model lives in Conversations

- Conversations owns every record it is made from (Threads, Consultations, Decisions) and already tells who is working on each Task.
- So it builds the snapshot of what each person is doing now with no table of its own.
- It reads who is hired from People's `RoleCards`.
- It sends each change whole on the web event stream.

### Users is its own module

- `users` ([2.10](2.10-users-and-signing-in.md)) owns:
  - users and their accounts;
  - signed-in devices;
  - every way to sign in: the password, the one-time password, the authenticator and recovery codes, passkeys, linked identities, Continue with Google and Continue with <name> through `arctic`;
  - the slow-down and lockout;
  - the recovery command.
- Continue with GitHub reaches the GitHub module's App through a port of Users' own, `IdentityProvider`.
  - It is bound in the app module to an application service the GitHub module exports for it.
  - That service runs the App's user authorization flow and answers only who the GitHub user is; it never reads or changes Sign in with GitHub.
- The guard on every request and WebSocket sits in the platform layer behind a port bound to Users, as the GitHub user token is bound.
- Other modules learn who did something from the signed-in user the platform hands each request, never from Users' tables.

### Telemetry owns Stats

- Stats ([2.11](2.11-stats.md)) is in the module `apps/service/src/modules/telemetry/`, whose Nest module is `StatsModule`.
- The telemetry plumbing every module uses (the exporters, `Telemetry`, the logger) stays in the platform layer, `src/platform/telemetry/`.
- Settings › Telemetry's routes (the read, Save and the bundled Grafana's Try again) are the module's; the saved setting, which The Office reads before any module loads, and the bundled Grafana stay in the platform layer.
- The module keeps no table of its own.
- No module calls Telemetry.
- **The basic stats** are built, as Now is, through ports of its own bound in the app module to other modules' application services, each port answering the module's own small types:
  - Notifications: tokens per day;
  - Engine: the Usage windows now;
  - Pipelines: the Stage runs started since a time, with their tokens and whether each is a Stage retry;
  - Work: the Tasks done since a time, and Tasks' titles and Projects.
- **The full stats** are read from Grafana through its port `StatsSource` ([5.2](5.2-stack.md#stats-reads-grafana)), with a Grafana adapter and a scripted adapter for tests; which Grafana, with which Read token, comes from the telemetry setting.
- **System health** (`GET /stats/system-health?range=1h|24h|7d|30d`) is read:
  - for 1 h, from the Health readings, through a port of Telemetry's own bound in the app module to the platform's `SystemHealthRecorder`;
  - for 24 h, 7 d and 30 d, from Grafana through `StatsSource`, with the same states as the full stats;
  - for Load now, through ports of its own bound in the app module: Conversations for the sessions running, Pipelines for the Stage runs running, and the WebSocket platform for the browser connections open.

### Activity reads through ports of its own

- Activity ([2.14](2.14-activity.md)) is in the module `apps/service/src/modules/activity/`, whose Nest module is `ActivityModule`.
- It is built as the basic stats are: through ports of its own, bound in the app module to other modules' application services, each port answering the module's own small types, so a new kind of item plugs in without coupling modules:
  - Work: the started Tasks, every Task by id with its title and Initiative, the Initiatives' titles, and each Project's Off-board Tasks;
  - Pipelines: where a Task's Stages stand, with each Stage's kind;
  - Conversations: the open Decisions, and the active sessions for the signed-in user (the Threads whose Agent takes a turn or with a Decision open, and the user's own chats with an unseen reply);
  - Test instances: those Building or Running;
  - Projects: the CI runs and each Project's latest environment check;
  - Devices: the Connected devices not Disconnected;
  - Actions: the running Project command runs.
- It keeps nothing: its old table, `activity_seen`, is unused and dropped in a later release.
- It reads no other module's tables, and no module calls it.
- It subscribes to the events of the modules it reads and sends `activity.changed`, with nothing, once per burst.

### The System health recorder sits in the platform layer

- It is in `src/platform/system-health/`, as the Workstation's reading of the CPU and memory is ([5.2](5.2-stack.md#system-health)); the Workstation figure's route is the Workstation module's.
- It has no dependency on the OpenTelemetry SDK and knows no module.
- Its Express middleware and the database platform's pool feed it requests and queries, and it reads the Workstation itself.
- When telemetry is On, `src/platform/telemetry/` observes its readings as metrics, so the readings and the metrics are one measuring path.
- It keeps nothing outside memory, so it has no table and no migration.

### Test instances uses Run environments through their public interface

- Test instances reaches Run environments only through that module's exported application service.
- What it needs (start a compose project of its own with an override, publish one port on `127.0.0.1`, stop it and remove its volumes, run a build with a cache volume) is added to that interface.
- It never reads or writes compose files, compose project names or containers itself.
- Office updates stop its Running instances rather than wait for them, so it counts no busy work.

### Devices uses Run environments through their public interface

- Devices reaches Run environments only through that module's exported application service, as Test instances does.
- What it needs (run the helper with `compose exec -i` and hold its input and output, hear a Task's run environment start and stop) is added to that interface.
- It never reads or writes compose files, compose project names or containers itself.
- Starting a Task's run environment, which only pairing over wireless debugging does, goes through Projects' `TaskWorktrees`, which knows the Task's worktree and what its image is made from.
- Work never imports Devices: it reads a Task's devices through a port of its own that Devices fills at start.

### Actions uses Run environments through their public interface

- Actions reaches Run environments only through that module's exported application service, as Test instances does.
- What it needs (start a compose project of its own for a command run's checkout, run a command in it, stop it and remove its volumes) is added to that interface.
- It never reads or writes compose files, compose project names or containers itself.
- It launches a Test target Action's instance through Test instances' application service, and holds a Project device through Devices', never their tables.

### Office identity is its own module

- It is in `apps/service/src/modules/office-identity/`, whose Nest module for git is `GitIdentityModule` and for Settings › Office identity's routes `OfficeIdentityHttpModule`, imported by the app alone.
- It keeps its files in the Office data directory's `identity` folder, readable by its owner only, and no table.
- It reaches Sign in with GitHub's token through its port `GitHubUserToken`, bound in the app module to the GitHub module's access.
- It tells which part of the identity a remote needs in the user's words (the site and its sign-in), so Projects' refusals name no host.

### The domain layers take other modules' values from their domain entries

- A module's domain imports another module's public entry only as types.
- The pure values and rules another module's domain uses (Engine's engine types, People's duties and Authority, Prompt templates' templates) come from that module's domain entry, `index.domain.ts`, which re-exports its own domain alone.
- So a domain loads no other module's Nest module, ports or adapters; the lint rule `office/module-boundaries` checks it.

### Engine types' adapters stay apart

- Each engine type's adapter in the Engine module imports its own folder, the engine-neutral `adapters/shared/` and the engine's other adapters, never another engine type's, so a change to one reaches no other.
- The Agent SDK and `-p` adapters both run Claude Code and share the Claude Code adapter's code.

### Code hosts report their own words

- Each `CodeHost` gives its name and where the user signs in for it, so Projects' refusals take the host's words.
- Projects reads its issues' switch by the domain's name for it, never by the `github-issues` key.

### Modules reach Busy work, never Office updates

- Engine, Conversations, Pipelines, Projects, Run environments and Actions count the busy work an Office update or restart waits for.
- Work and Pipelines hold Starts and Stages while one is scheduled.
- They import `BusyWorkModule`, never the Office updates module itself, which imports Busy work and Engine; so Engine can offer Office updates' actions without an import cycle.
