# 5.3 Modules

Hexagonal + DDD, modules as bounded contexts: **Work**, **People**, **Pipelines** (definitions and the Stage interpreter: an interpreter of Pipeline data, never a class with a method per Stage), **Conversations**, **Projects** (git, worktrees, environment, commands), **Engine**, **Skills**, **MCP servers**, **GitHub**, **Users**, **Notifications**, **Telemetry**.

- Each is layered inside: domain (entities, rules, events), application (use cases), ports, adapters (Postgres, engine, filesystem, HTTP, WebSocket).
- Modules talk through application services and domain events only; no module reads another's tables.
- Every state change emits a domain event, consumed alike by the WebSocket push, Now, telemetry, Notifications and (tier 2) the Office Manager's read-only view.

## Defaults

Gaps no ticket settled, filled with the simplest choice consistent with the tickets and accepted by the user; each says when.

- **Skills is its own module,** next to People and Engine, since it owns the library, versions and assignment, and builds each session's folder from them; the Engine takes the folder and the options from the session's owner and never reads Skills (agreed with the user on 2026-10-25) ([12](../../.scratch/the-office/issues/12-architecture.md) predates [23](../../.scratch/the-office/issues/23-skills.md)). (accepted 2026-10-24)
- **MCP servers is its own module,** shaped like Skills: it owns the MCP server library, its review, assignment to Roles, the Server values (Office-wide and per Project) and each session's servers; the Engine takes the session's servers in its options and never reads the module (the user, 2026-10-31).
- **GitHub is its own module:** it owns Sign in with GitHub (the GitHub App registered by its manifest, the web sign-in, the user token and its refresh) and the list of the user's repositories; Projects and Skills reach the token through ports of their own, bound to it in the app module. The Office ssh key and the git environment that keeps every Office git command to the Office identity sit in the platform layer, with where secrets live ([5.1](5.1-shape.md)) (the user, 2026-11-01).
- **Now lives in the Notifications module** (the user's answer of 2026-10-27): Needs you and Since you left are the Notifications' inbox (2.7), so Now and the status strip are one read model there, built from the other modules' events and application services; no module calls Notifications. (added while building tier 1)
- **The Live view's read model lives in Conversations** (the user's answer of 2026-11-15, Task "Service: what each person is doing now, for the Live view"): Conversations owns every record it is made from (Threads, Consultations, Decisions) and already tells who is working on each Task, so it builds the snapshot of what each person is doing now with no table of its own, reads who is hired from People's `RoleCards`, and sends each change whole on the web event stream.
- **Users is its own module** (proposed by Task 3afd3982, 2026-11-13, for the user's agreement; [2.10](2.10-users-and-signing-in.md)): `users` owns users, their accounts, signed-in devices, every way to sign in (the password, the one-time password, the authenticator and recovery codes, passkeys, linked identities, Continue with Google through `arctic`), the slow-down and lockout, and the recovery command. Continue with GitHub reaches the GitHub module's App through a port of Users' own, `IdentityProvider`, bound in the app module to an application service the GitHub module exports for it, which runs the App's user authorization flow and answers only who the GitHub user is; it never reads or changes Sign in with GitHub. The guard on every request and WebSocket sits in the platform layer behind a port bound to Users, as the GitHub user token is bound; other modules learn who did something from the signed-in user the platform hands each request, never from Users' tables.
