# 5.3 Modules

Hexagonal + DDD, modules as bounded contexts, each `apps/service/src/modules/<module>/`:
**Work**, **People**, **Pipelines** (definitions and the Stage interpreter: an interpreter of Pipeline data, never a class with a method per Stage), **Conversations**, **Projects** (git, worktrees, environment, commands, the pull requests it opens: recorded in its own table and linked to their Task by id, and the CI runs on its code host, kept in memory only by `CiRunWatch` and re-run by the Office action `rerun_ci_run`, all behind a host-neutral `CodeHost` port chosen by the remote's URL, GitHub its first adapter; `CodeHost` also lists a pull request's `mergeMethods` and can `merge` or `close` it, in host-neutral types, and Projects publishes `PullRequestMerged`, `PullRequestClosed` and `PullRequestReopened`, which Work's `PullRequestOutcomes` listener records on the Task; its worktrees include one on a pull request's own branch for a Conflict resolution Task, [5.5](5.5-git-and-isolation.md)), **Run environments** (each Project's image and each Task's run environment, [5.5](5.5-git-and-isolation.md)), **Engine**, **Skills**, **MCP servers**, **Prompt templates**, **GitHub**, **Users**, **Notifications**, **Telemetry** and **Office updates** (Office updates and restarts, and the busy work they wait for, [5.1](5.1-shape.md#defaults)).
Shared plumbing (config, database, domain events, telemetry, WebSocket, the operating system) is `src/platform/`.

- Each is layered inside: domain (entities, rules, events), application (use cases), ports, adapters (Postgres, engine, filesystem, HTTP, WebSocket).
- Modules talk through application services and domain events only; no module reads another's tables.
- Every state change emits a domain event, consumed alike by the WebSocket push, Now, telemetry and Notifications.

## Defaults

- **Skills is its own module,** next to People and Engine, since it owns the library, versions and assignment, and builds each session's folder from them; the Engine takes the folder and the options from the session's owner and never reads Skills.
- **MCP servers is its own module,** shaped like Skills: it owns the MCP server library, its review, assignment to Roles, the Server values (Office-wide and per Project) and each session's servers; the Engine takes the session's servers in its options and never reads the module.
- **Prompt templates is its own module:** it owns the catalog of Prompt templates ([2.2](2.2-people.md)), their versions, the check and the rendering, and imports no other module, so every module that owns a prompt depends on it. Each module declares its templates in its own domain and registers them at start; its application layer loads the texts it needs at use time, never at start, and passes them to the domain, which renders them.
- **GitHub is its own module:** it owns Sign in with GitHub (the GitHub App registered by its manifest, the web sign-in, the user token and its refresh) and the list of the user's repositories, and it holds every REST call to GitHub, the pull requests' and the Actions runs' too, and maps GitHub's values to the host-neutral ones (Projects' `CodeHost` adapter for GitHub lives here, with the words of its merge refusals); it also reads the permissions the App's installations were granted, cached five minutes, so Settings can say which a registered App lacks ([2.3](2.3-pipelines.md#defaults));
Projects and Skills reach the token through ports of their own, bound to it in the app module. The Office ssh key and the git environment that keeps every Office git command to the Office identity sit in the platform layer, with where secrets live ([5.1](5.1-shape.md)).
- **Now lives in the Notifications module:** Needs you and Since you left are the Notifications' inbox ([2.7](2.7-notifications.md)), so Now and the status strip are one read model there, built from the other modules' events and application services; only Telemetry's Stats calls Notifications, for tokens per day.
- **The Live view's read model lives in Conversations:** Conversations owns every record it is made from (Threads, Consultations, Decisions) and already tells who is working on each Task, so it builds the snapshot of what each person is doing now with no table of its own, reads who is hired from People's `RoleCards`, and sends each change whole on the web event stream.
- **Users is its own module** ([2.10](2.10-users-and-signing-in.md)): `users` owns users, their accounts, signed-in devices, every way to sign in (the password, the one-time password, the authenticator and recovery codes, passkeys, linked identities, Continue with Google and Continue with <name> through `arctic`), the slow-down and lockout, and the recovery command. Continue with GitHub reaches the GitHub module's App through a port of Users' own, `IdentityProvider`, bound in the app module to an application service the GitHub module exports for it, which runs the App's user authorization flow and answers only who the GitHub user is; it never reads or changes Sign in with GitHub. The guard on every request and WebSocket sits in the platform layer behind a port bound to Users, as the GitHub user token is bound; other modules learn who did something from the signed-in user the platform hands each request, never from Users' tables.
- **Telemetry owns Stats** ([2.11](2.11-stats.md)). It is the module `apps/service/src/modules/telemetry/`, whose Nest module is `StatsModule`; the telemetry plumbing every module uses (the exporters, `Telemetry`, the logger) stays in the platform layer, `src/platform/telemetry/`. It keeps no table of its own.
  - **The basic stats** are built, as Now is, through ports of its own bound in the app module to other modules' application services, each port answering the module's own small types:
    - Notifications: tokens per day;
    - Engine: the Usage windows now;
    - Pipelines: the Stage runs started since a time, with their tokens and whether each is a Stage retry;
    - Work: the Tasks done since a time, and Tasks' titles and Projects.
  - **The full stats** are read from Grafana through its port `StatsSource` ([5.2](5.2-stack.md), "Stats reads Grafana"), with a Grafana adapter and a scripted adapter for tests. Which Grafana, with which Read token, comes from the telemetry setting.
  - No module calls Telemetry.
- **Office updates is reached through `BusyWork`:** Engine, Conversations, Pipelines, Projects and Run environments count the busy work an Office update or restart waits for; Work and Pipelines hold Starts and Stages while one is scheduled. They import `BusyWorkModule`, never the Office updates module itself.
