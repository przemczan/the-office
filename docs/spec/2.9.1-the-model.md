# 2.9.1 The model

Covers: Sub-agents and Processes, how they are known, what each holds, masking, states, what ends them, background Sub-agents as busy work, Stages, how long and how much is kept.

## Sub-agents and Processes

- The UI spec is [docs/design/sub-agents-and-processes.html](../design/sub-agents-and-processes.html).
- While a session works, its Agent may start Sub-agents and Processes.
- A **Sub-agent** is an agent that does part of the work in its own context and reports back.
- A **Process** is a command run in the background, such as a dev server or a long test run.
- Names are in the [glossary](../../GLOSSARY.md): **Sub-agent** and **Process**.
- A Process is not a Pipeline.
- In code, a Process is never a variable named `process`, which is Node's global: use `startedProcess`, `processes`, `ProcessState` and the like.
- Above the message input, a Thread says how many are running; a press opens a live, read-only view of each ([2.9.3](2.9.3-streaming-and-ui.md#the-ui)).
- The view shows a Sub-agent's messages and tool calls, and a Process's command and its output as it streams.
- Ended ones stay viewable for the rest of the session ([How long they are kept](#how-long-they-are-kept)).

## The model

- A session's Sub-agents and Processes are kept by **Conversations**, beside its Thread.
- The Engine reports them as session events ([2.9.2](2.9.2-session-events.md)) and keeps nothing.
- Pipelines reads nothing of them, as a Stage's session is a Stage Thread, which Conversations owns.
- Conversations is where a session's events are logged (`ThreadRunner`, `StageThreads`), where the Project's mask is applied before anything is stored or sent (`sessionLogLines`), and where a Thread's web events come from (`ThreadWebEvents`).
- So it owns them for the same reasons it owns a Thread's messages ([5.3](5.3-modules.md): Engine talks to no module).

## Ids

- Both kinds are known by the same id, `callId`: the id of the tool call that started them, the one id every engine has, a foreground Sub-agent included.
- Each also keeps the engine's own task id, `engineTaskId`, when the engine has one.
- `engineTaskId` is Claude Code's `task_id`, or the API engine's `b` and 8 hex digits, which TaskStop names.

## What a Sub-agent holds

- Its `callId`, which its messages name as `withinToolCall`, and its `engineTaskId` when there is one.
- Who started it: the Agent, or another Sub-agent (by its id).
- Its description (the call's `description`), its kind (`subagent_type`, such as "general-purpose" or "Explore"), and its prompt, the brief it was given.
- Whether it runs in the background.
- Its state and why it ended ([States](#states)), and when it started and ended.
- Its messages and tool calls, in order, as a Thread logs its Agent's (text, a tool call's summary, a refusal), each with a sequence number, through the Project's mask.
- What it reported back (the starting call's result) and its counts when the engine gives them (tool calls, tokens).

## What a Process holds

- Its `callId` (the `Bash` or `PowerShell` call that started it) and its `engineTaskId` (`b1f9c2e07`).
- Who started it: the Agent or a Sub-agent.
- Its command line, whole, and its description.
- Its state, its exit code when the engine gives one, why it ended, and when it started and ended.
- The API engine gives an exit code; Claude Code's end notice has none.
- Its output, in chunks with sequence numbers, through the Project's mask.

## Masking

- Everything kept of either kind goes through the Project's mask before it is stored or sent, not only the output and the messages.
- That includes a description, a prompt, a command line (`curl -H "Authorization: Bearer …"`), what a Sub-agent reported back and why one failed.
- A Sub-agent's messages are whole when they arrive, and are masked as a Thread's are.
- A Process's output is masked by complete lines only ([Masking a Process's output](#masking-a-processs-output)).

## States

| State | When |
| --- | --- |
| Running | From its start until it ends. |
| Finished | A Sub-agent that reported back; a Process that exited with 0. |
| Failed | A Sub-agent whose call failed; a Process that exited with anything but 0, or couldn't start. |
| Stopped | Ended before it finished: by the Agent (TaskStop), by an interrupt or by the session's end; or no longer seen after The Office restarted. Its ending says which. |

- The Agent stopping its own dev server is ordinary work, so it is Stopped, not Failed.

## What ends them

- **An interrupt** stops what the engine stops with the turn.
  - On Claude Code a foreground Sub-agent stops with it and background work runs on.
  - On the API engine `interrupt` ends every Process (`endAll`).
  - The view shows what happened on each.
- **TaskStop** makes it Stopped, "by the Agent".
- **The session's end** stops whatever still runs, "ended with the session": the engine ends its background work with the session, on both engines.
  - A Thread's session ends after ten idle minutes (`IDLE_MS` in `thread-runner.ts`), and a Stage's session with its run.
  - The idle end waits for background Sub-agents: while any runs, ten idle minutes don't end the session, and the ten minutes start again once the last one ends.
  - It doesn't wait for Processes, so a dev server the Agent left running stops with it.
  - A turn the engine starts by itself, such as on a Sub-agent's report, holds the idle end as a turn the user's message starts does.
- **The Office's restart:** after it, no session is there to report on them, and a background command may still be running on the machine, so nothing claims it stopped.
  - At startup Conversations puts every Process and Sub-agent still Running in the Stopped state with the ending "Ended when The Office restarted", as it recovers interrupted answers.
  - "Ended when The Office restarted" is Conversations' own ending, as no engine sees it.
  - A planning Thread whose background Sub-agents were Stopped this way has its planner woken again, told to run again the ones they still need ([2.4](2.4-conversations.md), "After a restart").

## Background Sub-agents are busy work

- A scheduled Office update ([5.1](5.1-shape.md), "Updating The Office") waits while a Thread of any kind has a background Sub-agent running, since the update's restart would stop it, though the Agent's turn has ended.
- Settings › Updates lists one item per session while any runs, by its Thread, such as "Ada's Sub-agents in an Initiative's Thread, "Planning the Initiative"".
- The item goes once the last one ends, or with the session.
- A foreground Sub-agent runs within its Agent's turn, which already counts.
- A background Process doesn't count, as a dev server may never end.

## In a Stage

- A Stage's result is the end of its Agent's turn ([2.3](2.3-pipelines.md)), so nothing the Agent needs may outlive the turn.
- **Sub-agents run in the foreground**, whatever the call asks.
  - The Office rules hook allows every Sub-agent call of a Stage session with its input set to `run_in_background: false`, each other field as the Agent gave it (`SessionOptions.subAgentsInForeground`, [5.4](5.4-the-engine.md)), so the turn holds until each answers.
  - The engine's stream still shows the call as the model wrote it; the adapters report it, and its Sub-agent, as the foreground one that ran.
  - Chats and every other Thread keep background Sub-agents.
- **Background commands stay allowed:** a Stage may serve the app for its screenshots, and its checks already run through `run_project_command`, which waits for their end.
- The Stage instructions say the Stage ends with the turn, that the Agent waits within it for any output it needs, never ending the turn to wait, and stops the commands it no longer needs.
- Whatever still runs stops with the session.

## Defaults

### How long they are kept

- They are kept for the rest of the session.
- They belong to the Thread's session (`ThreadSession`, the engine session id).
- They are kept across turns, and across the session's end and resume after ten idle minutes, since a resume continues the same session.
- They are kept across The Office's restart: they are stored in the database, not in memory.
- They are kept until the Thread's session is replaced by a fresh one (the Context policy's fresh or hand off, [2.5](2.5-context-policy.md)), when the old session's are removed with it.
- For a Stage, they are kept with its run: a Stage Thread has one session and never gets another, so a run's Sub-agents and Processes stay readable in its Stage history, as its Thread does.

### Caps on what is kept

- A Process keeps the last 256 KB of its output, counted after masking; what came before is dropped, and its size is counted ("1.9 MB of earlier output isn't kept").
- A Sub-agent keeps its last 1,000 messages and tool calls, the earlier ones counted the same way.
- A session keeps its latest 100 Sub-agents and Processes that ended; Running ones are always kept.

### Masking a Process's output

- The mask matches within a text, so a secret split across two output chunks would get past it.
- Conversations masks a Process's output by complete lines only.
- It holds back an unfinished last line until its newline comes, the Process ends, or about a second passes, and masks it then.

### Output batching

- Output is batched in one place only, the engine adapter.
- Each read of the output file, every half second, is one `process-output` event, which Conversations stores and sends as it comes.
- A chatty command so gives two events a second at most.
