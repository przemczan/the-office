# 2.2 People

From [04](../../.scratch/the-office/issues/04-agent-identity.md), [05](../../.scratch/the-office/issues/05-roles.md), [06](../../.scratch/the-office/issues/06-office-manager.md), [21](../../.scratch/the-office/issues/21-role-capabilities.md), [23](../../.scratch/the-office/issues/23-skills.md), [25](../../.scratch/the-office/issues/25-agent-permissions.md).

- **Role:** a job the user hires for, filled by one named person ("Ada · Developer"). Every person is Office-wide. There are no kinds of person, but one exception: the built-in **Caretaker**.
- **Agent:** a person at work on one thing (a Task or a conversation). A person can be at work on several things at once. A person's Agent on a Task stays the same person for each of that Role's Stages on it.
- **Role card:** name and title; its responsibilities in one paragraph; the instructions; effort, and from tier 3 the engine and model as a **Role override** or none ("Office default"), the card showing which engine and model apply and where they come from ([5.4](5.4-the-engine.md#defaults), the engine cascade); **capabilities** (Shared memory, Chat, Consultant, Run environment), each switched freely; **Run environment** gives the person's Agent Stages the Office tool that writes the Project's run environment definition, `write_run_environment_definition` ([5.5](5.5-git-and-isolation.md), [6](6-permissions-and-safety.md)); the permission profile ([6](6-permissions-and-safety.md)); authority rules; **Hard switches**; **Task limit** (1–6, or none: the person only talks and no Pipeline may name the Role); **Skills**.
- **Avatar:** every person, the Caretaker included, can have their own picture, uploaded on their Overview tab: a PNG, JPEG, WebP or SVG of at most 2 MB, the kind read from its contents, shown as uploaded and cropped to the centre of a circle, in place of their initials wherever they are drawn, the initials and tint showing while there is none or it can't be loaded. It sits beside the Role card, not on it: a change adds no card version and no Proposal, and Agents never see it. Someone let go keeps showing theirs, unchanged until hired back. "You" and The Office have none.
- **Authority** in three tiers written as plain rules in the instructions: decide alone, consult *person* first, ask the user. **Hard switches** (run installs, publish outside the Pipeline, change Roles) are each Allowed, Consult *person*, Ask me or Never ([6](6-permissions-and-safety.md)).
- **Escalation:** a Consultant asked to approve answers Allow once, Deny or Pass on, at most two steps up (e.g. Devops → CTO → the user). **A missing person falls back to the user:** whenever an Agent would consult someone not hired, the user is asked.
- **Presets** (hiring starts from a template; the template sets the switches):

  | | Memory | Chat | Consultant | Run environment | Task limit | Tier |
  |---|---|---|---|---|---|---|
  | Planner | on (off until tier 2) | on | on | off | 2 | 1 |
  | Developer | off | off | off | on | 3 | 1 |
  | Reviewer | off | off | off | off | 3 | 1 |
  | CTO | on | on | on | off | 2 | 2 |
  | Devops | on | on | on | on | 2 | 2 |
  | Office Manager | on | on | off | off | none | 2 |

  The CTO owns architecture and shapes Initiatives; Devops onboards and repairs Projects and owns the Pipeline library and Project commands by Proposal; the Planner co-writes Plans; the Reviewer is an optional independent review.
- **Office Manager** (tier 2): the default person to go to. Drafts Roles and Office settings as **Proposals** the user confirms with one click; redirects with a link card and an editable handover note, never relays; captures Ideas; sees all of The Office read-only; never works a Stage. Never alone: Roles, settings, starting, stopping or moving work, publishing, speaking for others.
- **Caretaker:** the built-in person who looks after the workstation and The Office, present on a fresh database under the Role key `caretaker`. Never hired and never let go; not offered as a preset, and nothing else can be hired into its key. Its card: built in, Chat and Shared memory on, not a Consultant, Run environment off, Task limit none, so no Pipeline can name it. Its name, title, responsibilities, instructions, effort, Role override, session default, Skills and MCP servers (with their tool settings) stay editable; its capabilities, permission profile, Hard switches and Task limit are fixed, and a change to them is refused. People pins it first with a "Built in" mark and no Let go action. Its chat only reads until the user turns on **Allow changes** in a Thread ([2.4](2.4-conversations.md), [6](6-permissions-and-safety.md)). (the user's answers of 2026-11-03)
- **Changing a Role** takes effect at the next session start. Before drafting a change to a Role, the Office Manager reads its whole card, instructions included, with `read_role`, since a change gives each field whole; so does an Agent before rewording a Role with `change_role`. **Letting a Role go** (tier 2) pauses its running Tasks behind a Decision and flags Pipelines that name it. **Switching a capability off** keeps its memory or threads, unused and readable; deletion only by explicit, confirmed actions on the Role card (tier 2).
- **Office instructions** (tier 3): one text the user writes in Settings › Office instructions, for general guidelines; every person's session gets it with their Role's instructions, on every engine. They are the general default: where they disagree, a Role's instructions and a Project's `CLAUDE.md` win, and the session is told so; the Office rules stand above all three. Left empty, they add nothing. As with a Role, a change takes effect at the next session start, and a resumed session keeps the version it started with. The Office Manager may draft a change as a Proposal of an Office setting, reading the current text first with `read_office_instructions`, since its session may hold an older version; a text changed since the draft is refused when applied. (the user's answers of 2026-11-06)
- **Shared memory** (tier 2): one append-only memory per person, read at session start, written as small notes. Its form is an open question ([8](8-open-questions-and-risks.md)).
- **Limits:** each person's Task limit, each Project's Project limit on its started Tasks ([2.1](2.1-work.md), "Project"), plus one Office-wide limit on running Tasks to protect quota, and from tier 3 each engine's Window caps and Daily caps ([2.1](2.1-work.md), "Usage estimates"). Talking never counts and is never blocked. A Task Start can't run for a blocker, a limit or a cap waits in the queue, counting against neither until it starts ([2.1](2.1-work.md), "A queue for Start").

## Defaults

Gaps no ticket settled, filled with the simplest choice consistent with the tickets and accepted by the user; each says when.

- **A Task waiting on the user or paused still counts** against its person's Task limit and the Office-wide limit, since it keeps its worktree and session. (accepted 2026-10-24)
- **The Office-wide limit on running Tasks** defaults to 3; the status strip's "desks in use" is the running Tasks against this limit. (accepted 2026-10-24)
- **Preset Task limits** are single numbers within [21](../../.scratch/the-office/issues/21-role-capabilities.md)'s ranges: Planner 2, Developer 3, Reviewer 3, CTO 2, Devops 2. (accepted 2026-10-24)
