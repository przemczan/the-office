# 2.2 People

Covers: Role, Agent, Role card, setting a Project up, Presets, Office Manager, Caretaker, Duty, Authority, Hard switches, Escalation, Calls, chains of calls, changing a Role, Avatar, Office instructions, Prompt templates, Shared memory, Limits, the Live view's snapshot of each person.

## Role

- A Role is a job the user hires for, filled by one named person ("Ada · Developer").
- Every person is Office-wide.
- There are no kinds of person, but one exception: the built-in **Caretaker** ([Caretaker](#caretaker)).

## Agent

- An Agent is a person at work on one thing (a Task or a conversation).
- A person can be at work on several things at once.
- A person's Agent on a Task stays the same person for each Stage on it naming that Role, or naming a duty they hold when the Stage starts.

## Role card

- Name and title.
- Its responsibilities, in one paragraph.
- The instructions: the job's guidance only; what the person may do alone, by asking or by Proposal is their Authority, never words.
- The person's **model and effort** for each engine type, each "Engine's default" unless set; they apply on whichever engine of that type a session lands on ([5.4.5](5.4.5-engines-and-cascade.md#the-model-and-effort-cascade)).
- The card names no engine: where the person runs comes from the Office, the Project, the Initiative or the Task ([5.4.5](5.4.5-engines-and-cascade.md#the-engine-cascade)); the card shows the engine, model and effort that apply and where they come from.
- **Capabilities** (Shared memory, Chat, Consultant, Run environment), each switched freely.
  - **Run environment** gives the person's Agent Stages, and their Consultations on a Task, the Office tool that writes the Project's run environment definition, `write_run_environment_definition` ([5.5](5.5-git-and-isolation.md#writing-the-run-environment-definition), [6](6-permissions-and-safety.md#the-one-exception-the-run-environment-definition)).
- The permission profile ([6](6-permissions-and-safety.md)).
- **Authority:** one authority setting per tool area, with the groups and single tools inside an area where they differ; the Hard switches are among its groups ([Authority and Hard switches](#authority-and-hard-switches)).
- **Task limit:** 1–6, or none (the person only talks and no Pipeline may name the Role).
- **Skills.**

## Authority and Hard switches

- A person's **Authority** is what they may do with Office tools, and when; it is set on their Role card, and The Office rules every call by it ([6 Authority](6-permissions-and-safety.md#authority)).
- Each tool area, group or single tool on the card is Allowed, Consult *person*, Ask me, Proposal or Never ([6 Authority](6-permissions-and-safety.md#authority)).
- In Work, Initiatives and Ideas a setting can differ on the person's own work and on others' work ([6 Authority](6-permissions-and-safety.md#authority), "Own work"; [People › Role card tab](screens/people.md#role-card-tab)).
- The presets put a person's own Tasks, Ideas and Initiatives mostly at Allowed and others' at Ask me: they fix what they made alone and ask the user before Dropping what somebody else created ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).
- A domain rule stays the floor whatever the setting: work that has started is the user's to Drop, which The Office enforces ([2.1.3 Dropping](2.1.3-tasks.md#dropping)).
- **Hard switches** are four named groups of authority settings: Run installs, Publish outside the Pipeline, Change Roles and Change Project settings; where each sits and what enforces it is in [6 Hard switches](6-permissions-and-safety.md#hard-switches).
  - **Change Project settings** lets an Agent change a Project's commands, test targets, Actions, environment variables and Run environment itself, with `change_project_settings` ([6 Project settings by Agents](6-permissions-and-safety.md#project-settings-by-agents)).
  - **Change Roles** is part of the trust anchor, so it is under its cap ([6 The trust anchor](6-permissions-and-safety.md#the-trust-anchor)).
- **The card's marks:** the card marks the followed groups and the capped rows, a capped row linking to its reason ([People › Role card tab](screens/people.md#role-card-tab)).
- A Consult setting, on a group or an MCP tool, names a Role key, not a duty, and may name any hired Role, a preset's or one hired from scratch, not only the preset keys, so a Role hired from scratch can hold Default Consultant for MCP tool hard switches; a Role hired from a preset keeps its settings whoever holds which duty.
- An MCP tool whose setting was never set consults the holder of Default Consultant for MCP tool hard switches ([6 MCP tools](6-permissions-and-safety.md#mcp-tools)).

## Escalation

- A Consultant asked to approve answers Allow once, Deny or Pass on.
- **A missing person falls back to the user:** whenever an Agent would consult someone not hired, the user is asked.
- From a chat, which has no Needs you, the user is asked with the Decision's form inline in the caller's chat ([2.4](2.4-conversations.md)).

## Calls

- A person may call another person who can do what they can't ("ask Devops to set that up"); a call is a consult.
- A call may be a Decision's form, an approval or a **Request**.
- A Request asks the callee to do something: a form of one open question, which they answer in their own words with what they did (such as a Proposal they drafted) or why they can't.
- A Consultant answers a form as the user would, Submit or Ask me again ([2.4](2.4-conversations.md)).
- The callee is a hired person with Consultant on who isn't the caller.
- **A request to oneself** is refused, as a person's own tools are the same in every Thread ([6](6-permissions-and-safety.md#a-persons-office-tools)): "You are the <title>: a request to yourself is never needed. Do it with your own tools, or tell the user plainly what you can't do and why."
- A question or an approval naming the caller's own Role still falls back to the user ([Escalation](#escalation)).
- The holder of Default person to talk to, in any Thread the user talks to them in, still redirects with a Link card rather than relaying, and calls someone only when the user asks them to.
- A person calls only when the user asks them to, or when a setting of theirs at Consult *person* holds a call on that person's approval ([6 Authority](6-permissions-and-safety.md#authority)).

## Chains of calls

- A Consultation may call someone itself.
- The chain is the first asker, every asker up its Consultations and everyone a Decision down it was put to or passed on to.
- At most two people are asked down one chain, nested calls and passes-on counted together (for example Planner → Devops → CTO, or Devops → CTO → the user).
- At the last step a Consultation has no way to call, and an approval passed on goes to the user.
- Calling or passing on to someone already in the chain is refused, naming them.

## Setting a Project up

- A Project's setup (a command that isn't set, no run environment, a missing tool or service) is the work of whoever holds Onboards and repairs Projects, never the user's.
- An Agent Stage whose check can't run because of the setup consults the holder with what it knows (the stack, its versions, the commands it would run), and ends the Stage done once their answer says it is set up ([2.5](2.5-context-policy.md#the-brief)).
- The holder, consulted on a Task, sets it up themselves, as their card's Authority allows, with `change_project_settings`, `write_run_environment_definition` (with the Run environment capability) and `run_environment_check`, fixing what fails until the check passes, then answers with what changed and how the check went ([6](6-permissions-and-safety.md#a-consultations-permissions), [5.5](5.5-git-and-isolation.md#the-environment-check-tool)).
- Consulted off a Task, the holder sets it up the same way with `change_project_settings`, as their Authority allows, and checks the base branch with `run_environment_check`; the change record then has the user who asked and no Task.
- The rest of a Project's settings are Office actions of Projects and settings › Project settings, ruled by the person's Authority like any call: the Project limit, mark and features, its skills, Icon and Logo from the repository, Engine, Default Pipeline (and per Kind), Project Pipelines, Server values that aren't secret, Onboard again and Set up run environment ([6 Project settings by Agents](6-permissions-and-safety.md#project-settings-by-agents)); fetching the base branch, importing GitHub issues and closing a pull request are Project upkeep.
- The user is asked only by the approval card of a call held at Ask me, never to do the setup or to confirm it is done.
- In a chat, a user asking to have a Project set up gets it done, never a list of steps:
  - the holder checks with `run_environment_check` and sets the commands, test targets or Actions with `change_project_settings`, which is a Proposal the user applies where the holder's Authority rules it so;
  - anyone else calls the holder.

## Presets

- Hiring starts from a template; the template sets the card's fields and its Authority's defaults.
- A hire copies the preset's other fields (instructions, profile, capabilities and the rest) into the person's card, so a later release's change to them reaches only new hires; a person already hired keeps them until they are changed.
- Each authority setting is either **the preset's default** or **set**, as a model is "Engine's default" unless set.
  - A setting at the preset's default follows the preset, so a release's new default, a new tool's among them, reaches it at the next session start.
  - A set value stays as it is, whoever set it: the user, an applied Proposal or an approved call.
  - The card shows a default in muted text, as "Preset default (Ask me)", and a set value plainly; **Reset to the preset's default** puts a set value back.
  - A Role hired from scratch follows The Office's default the same way ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).
  - On the update that brought Authority, a card's migrated value equal to its preset's default became the preset's default, and any other became set ([6 Hard switches](6-permissions-and-safety.md#hard-switches)).

  | | Memory | Chat | Consultant | Run environment | Task limit | Holds by default |
  |---|---|---|---|---|---|---|
  | Planner | on | on | on | off | 2 | Plans |
  | Developer | off | off | off | on | 3 | Implements |
  | Reviewer | off | off | off | off | 3 | Reviews |
  | CTO | on | on | on | off | 2 | Shapes Initiatives, Asked first when a Stage runs out of tries |
  | Devops | on | on | on | on | 2 | Onboards and repairs Projects, Default Consultant for MCP tool hard switches |
  | Office Manager | on | on | off | off | none | Default person to talk to |

- The presets do their built-in jobs as these duties' holders by default ([Duties](#duties)).
  - The CTO shapes Initiatives and also owns architecture.
  - Devops onboards and repairs Projects, sets each Project's commands, test targets, Actions, environment variables, Run environment and run environment definition itself, running the environment check until it passes ([Setting a Project up](#setting-a-project-up)), and owns the Pipeline library, Project Pipelines among the Pipelines it proposes.
  - Each preset's Authority, its Hard switches among them, is in [6 Authority by role](6-permissions-and-safety.md#authority-by-role).
  - The Planner co-writes Plans.
  - The Reviewer is an optional independent review.

## Office Manager

- The preset that holds Default person to talk to by default.
- Drafts Roles and Office settings as **Proposals** the user confirms with one click.
- Redirects with a link card and an editable handover note, never relays.
- Captures Ideas.
- Sees all of The Office read-only.
- Never works a Stage, as its Task limit is none.
- Its Office tools come from its Role card's Authority, as every person's do, never from its preset's key or the duties it holds; they are the same in every Thread the user talks to it in ([6 A person's Office tools](6-permissions-and-safety.md#a-persons-office-tools)).
- Its preset's Authority keeps it never alone on Roles, settings, starting, stopping or moving work, publishing and speaking for others ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).
- Link cards (`post_link_card`) and the Office status (`show_office_status`) are the job tools of Default person to talk to, Allowed among that duty's job settings ([Duty](#duty)).
- Reading, the Pipelines and Stage templates among it (`list_pipelines`, `list_stage_templates`), is Core: every session reads them, whatever its Authority ([6 Tool areas](6-permissions-and-safety.md#tool-areas)).

## Caretaker

- The built-in person who looks after the workstation and The Office, present on a fresh database under the Role key `caretaker`.
- It never holds a duty, and is the default person to talk to while nobody holds that duty.
- At any time it may draft hires (Role card Proposals from presets) and duty assignments (Proposals of the Office setting), which the user confirms.
- In every Thread, with Allow changes on or off, it reads and drafts Proposals of:
  - the Office instructions and the other Office settings (`read_office_instructions`, `propose_office_setting`);
  - Role cards (`read_role`, `change_role_card`, `hire_role`);
  - Prompt templates, a new text or a reset to the default (`list_prompt_templates`, `read_prompt_template`, `propose_prompt_template`, `propose_prompt_template_reset`);
  - library Pipelines, Project Pipelines and Stage templates (`list_pipelines`, `list_stage_templates`, `propose_library_pipeline`, `propose_project_pipeline`, `propose_stage_template`).
- It reads the current text right before drafting, and proposes a change rather than pasting text for the user.
- The user applies each Proposal; one is refused when what it changes changed since the draft, and applying one declines the older open ones that change some of the same ([2.4.2 Proposals and approvals](2.4.2-decisions.md#proposals-and-approvals)).
- On an Office with nobody hired it offers to set the Office up ([Setting up an Office with nobody hired](#setting-up-an-office-with-nobody-hired)).
- Never hired and never let go; not offered as a preset, and nothing else can be hired into its key.
- Its card: built in, Chat and Shared memory on, not a Consultant, Run environment off, Task limit none, so no Pipeline can name it.
- Editable: its name, title, responsibilities, instructions, model and effort for each engine type, session default, Skills and MCP servers (with their tool settings).
- Fixed, a change being refused: its capabilities, permission profile, Authority (its Hard switches among them) and Task limit.
- People pins it first with a "Built in" mark and no Let go action.
- Its chat only reads until the user turns on **Allow changes** in a Thread ([2.4](2.4-conversations.md), [6](6-permissions-and-safety.md)).
- **Its fixed Authority** is built in and equals its reach before Authority came, nothing more:

  | Group | Value |
  |---|---|
  | Core (reading, `consult`, `answer_decision` not on an approval) | As for everyone |
  | `remember` | Allowed while Shared memory is on |
  | Work › Task records | Own: Allowed · Others': Ask me |
  | Ideas | Own: Allowed · Others': Ask me; `capture_idea` Allowed |
  | Change Roles: a new Role, a hire from a preset or a card change only (`hire_role`, `change_role_card`), never letting a Role go or hiring one back | Proposal |
  | Office settings (`propose_office_setting`) | Proposal |
  | `propose_office_setup` (its own tool) | Proposal |
  | Library › Skills: a new skill only (`propose_skill`) | Proposal |
  | Library › Pipelines and Stage templates: `propose_library_pipeline` and `propose_stage_template` only | Proposal |
  | Library › Prompt templates (`propose_prompt_template`, `propose_prompt_template_reset`) | Proposal |
  | Projects and settings › Project settings: Project Pipelines only (`propose_project_pipeline`) | Proposal |
  | Run installs | Allowed |
  | Publish outside the Pipeline | Allowed |
  | Every other group and tool | Never |

  - Allow changes isn't an authority setting: it is the user's alone, turned on in the Thread ([6 The user's alone](6-permissions-and-safety.md#the-users-alone)).
  - **Standing in for Default person to talk to adds no tool:** it holds no duty, and its tools come from its own fixed Authority in every Thread, whoever holds the duty; `post_link_card`, `show_office_status` and `create_initiative` never come with it.
  - The card shows its Authority as "Built in: fixed for the Caretaker"; a change is refused.
  - A new Office tool is Never on its card until a later Task decides otherwise.
  - With Allow changes on, a Thread keeps its reach; the no-bypass rule binds it too, which narrows nothing it can do, as it can neither sign in to `/api` nor read the database's password ([6 No bypass](6-permissions-and-safety.md#no-bypass)).

## Duty

- A duty is a built-in job The Office gives to whichever hired Role holds it, set in Settings › Duties.
- It says who does the job and who is asked first:
  - who a Stage naming it runs as;
  - who is asked first (Asked first when a Stage runs out of tries, Default Consultant for MCP tool hard switches);
  - who the buttons naming it point to;
  - its fallback while nobody holds it.
- It adds or removes no Office tool: a person's Authority comes from their Role card alone ([Authority and Hard switches](#authority-and-hard-switches)).
- Each duty's declaration names its job's settings, the authority settings the job needs, next to its default holder; a duty's own tools, such as the planning tools for Plans, are Allowed among them ([Duties](#duties) lists them).
- Settings › Duties reads each duty's job settings, and for the current holder those the card leaves Never (`jobSettings`, `jobSettingsToGive` of `GET /api/settings/duties`); a row is given only where the card says Never, so no setting the user or the preset chose is loosened, and a capped row is given as Proposal.
- **Assigning a duty:** when it moves to a new holder, Settings › Duties shows the job's settings that differ on the new holder's card ("This job needs: Projects and settings › Project upkeep Allowed, …"), with **Give <name> these settings** beside them.
  - Pressing it is a Role card change by the user, under the trust anchor ([6 The trust anchor](6-permissions-and-safety.md#the-trust-anchor)).
  - Moving a duty away removes nothing: Settings › Duties says "<name> keeps the authority on their card".
- The update that brought Authority gave each card the settings its duties granted until then, so nobody lost reach ([6 Hard switches](6-permissions-and-safety.md#hard-switches)); the update that stopped duties granting tools gave each holder, once, in one more card version named "Authority from the duties held", the rows of its job its card left Never; a row the user sets Never later, or a duty assigned later, is theirs to give, and a preset hired for the duties it holds by default starts with them.
- The keys, default holders and fallbacks are in [Duties](#duties); who holds one is in [Who holds a duty](#who-holds-a-duty).

## Changing a Role

- A change takes effect at the next session start.
- Before drafting a change to a Role, the Office Manager reads its whole card, instructions included, with `read_role`, since a change gives each field whole; so does an Agent before changing a Role with `change_role_card`, which is refused wherever the Role card's save is.
- Hiring (`hire_role`), changing a card (`change_role_card`), letting a Role go (`let_go_role`) and hiring one back (`hire_back_role`) are Office actions of People and Roles › Change Roles; a person's call records them as the one who proposed it, apart from the user who allowed or applied it ([5.4.1 Office actions](5.4.1-engine-kinds.md#office-actions)).
- **Letting a Role go** pauses its running Tasks behind a Decision and flags Pipelines that name it.
- Letting a Role go also leaves the duties it held unheld, so each falls back and the Pipelines naming those duties are flagged; hiring the same key back restores them, and renaming a Role changes none of its duties.
- **Switching a capability off** keeps its memory or threads, unused and readable; deletion only by explicit, confirmed actions on the Role card.

## Avatar

- Every person, the Caretaker included, can have their own picture, uploaded on their Overview tab.
- It is a PNG, JPEG, WebP or SVG of at most 2 MB, the kind read from its contents.
- It is shown as uploaded and cropped to the centre of a circle, in place of their initials wherever they are drawn; the initials and tint show while there is none or it can't be loaded.
- It sits beside the Role card, not on it: a change adds no card version and no Proposal, and Agents never see it.
- A person sets theirs from an image Attachment (`set_avatar_from_attachment`; the picture is never shown to them, and the file is judged as an upload is) and removes it (`remove_avatar`), in People and Roles › Memory and Avatar, their own only; the user does either for anyone from the Overview tab.
- Someone let go keeps showing theirs, unchanged until hired back.
- "You" and The Office have none.

## Office instructions

- One text the user writes in Settings › Office instructions, for general guidelines.
- Every person's session gets it with their Role's instructions, on every engine.
- They are the general default: where they disagree, a Role's instructions and a Project's `CLAUDE.md` win, and the session is told so; the Office rules stand above all three.
- Left empty, they add nothing.
- As with a Role, a change takes effect at the next session start, and a resumed session keeps the version it started with.
- A person whose Office settings are at Proposal (the Office Manager by default, and the Caretaker) may draft a change as a Proposal of an Office setting, reading the current text first with `read_office_instructions`, since their session may hold an older version.
- A text changed since the draft is refused when applied.

## Prompt templates

- Each text The Office itself gives an Agent or a session, such as Resolve's Brief, is a Prompt template: a default that ships with The Office and the variables it can use in `{{ }}` (Mustache: a value, a section for a flag or a list, no logic), each with a short description.
- Settings › Prompt templates lists them in a tab per domain (Conversations, Work, Pipelines, Engine).
- A save is checked first and refused, line and column named, for broken syntax, a variable the template doesn't list, an included template or a change of delimiters.
- Each save and each **Reset to default** is kept as a new version with who made it and when; saving the current text again adds none.
- A template's text is read each time it is used, so a change reaches the next use, and a running session isn't pinned to a version.
- A release that changes a default keeps the user's text; one that no longer passes the check after a release renders the default, and Settings shows its problems.
- Everyone lists the templates (`list_prompt_templates`, all or by domain) and reads one (`read_prompt_template`: its text now, its default, its variables and its saved text's problems), as reading is Core ([6 Tool areas](6-permissions-and-safety.md#tool-areas)).
- Only when the user asks, a person whose Library › Prompt templates is at Proposal (the Office Manager by default, and the Caretaker) drafts a new text, given whole, or a reset to the default as a Proposal (`propose_prompt_template`, `propose_prompt_template_reset`).
- A drafted text is checked as a save in Settings is and refused with the same words, and again when applied.
- Applying is refused once the template's text differs from the one it was drafted from.
- The new version keeps the user who applied it.

## Shared memory

- One append-only Memory per person, read at session start.
- Written as small notes, by the person's Agent with `remember` or by the user on the Memory tab, where the user may also delete one note or all; a person deletes one note of their own Memory with `delete_memory_note`, never another's.

## Limits

- Each person's Task limit.
- Each Project's Project limit on its started Tasks ([2.1.1](2.1.1-projects.md#project-limit)).
- One Office-wide limit on running Tasks to protect quota ([The Office-wide limit on running Tasks](#the-office-wide-limit-on-running-tasks)).
- Each engine's Window caps and Daily caps ([2.1.7](2.1.5-planning-and-start.md#usage-estimates)).
- Talking never counts and is never blocked.
- An Action run counts against no person's Task limit, nor the Office-wide limit on running Tasks ([2.15](2.15-actions.md#limits)).
- A Task Start that can't run for a blocker, a limit or a cap waits in the queue, counting against neither until it starts ([2.1.7](2.1.5-planning-and-start.md#a-queue-for-start)).

## What each person is doing now

- The Live view: one snapshot lists everyone filling a Role now, the Caretaker included.
- Anyone let go is left out, so a person joining or leaving the snapshot is a hire, a hire back or a let-go.
- For each person it lists every activity:
  - **Working:** one Agent for each Thread they are answering in that waits on no Decision: a Stage Thread, a Consultation (with the Decision it answers and who asked it) or any other Thread.
    - A Stage Thread waiting on its Decision isn't working.
    - An Initiative's planning Thread is working while its Decisions wait, as the Planner works on.
  - **Consulting:** each open Decision in their Threads put to a Consultant, naming the Consultant it waits on now (the one it was passed on to, if any), its first question, the count of the others ("and 2 more"), and when it was asked.
  - **Waiting on you:** each open Decision in their Threads waiting on the user, with its first question, the count of the others ("and 2 more"), and when it was asked.
    - The Office's own Decision when a Stage runs out of tries, a budget or the Definition of Done shows on the person whose Stage Thread it was opened in, or as consulting while put to someone first.
  - **Idle:** none of these.
- Gates waiting on the user belong to no person and aren't shown.
- The headline state is in [A person's headline state on the Live view](#a-persons-headline-state-on-the-live-view).

## Defaults

### A Task waiting on the user or paused still counts

- It counts against its person's Task limit and the Office-wide limit, since it keeps its worktree and session.

### The Office-wide limit on running Tasks

- It defaults to 3.
- The status strip's "desks in use" is the running Tasks against this limit.

### Preset Task limits

- Planner 2, Developer 3, Reviewer 3, CTO 2, Devops 2, Office Manager none.

### Duties

- A **duty** is a built-in job The Office gives to whichever hired Role holds it, set in Settings › Duties.
- A Role **holds** a duty and is its **holder**.
- Each duty has a key, is held by its default Role, and falls back while nobody holds it; its job's settings are beside them in its declaration ([Duty](#duty)):

  | Duty | Key | Held by default by | While nobody holds it |
  |---|---|---|---|
  | Default person to talk to | `default-person-to-talk-to` | `office-manager` | the Caretaker |
  | Shapes Initiatives | `shapes-initiatives` | `cto` | the user, as "Shaping without a CTO" in [2.1.5](2.1.4-initiatives.md#shaping-without-a-cto) |
  | Asked first when a Stage runs out of tries | `asked-first-when-out-of-tries` | `cto` | the user |
  | Onboards and repairs Projects (owns the Pipeline library, Project commands and Skill installs) | `onboards-projects` | `devops` | the user |
  | Default Consultant for MCP tool hard switches | `mcp-tool-consultant` | `devops` | the user |
  | Plans | `plans` | `planner` | the user plans alone |
  | Implements | `implements` | `developer` | the Pipelines whose Stages name it are flagged and Start is refused, as for a Role nobody fills ([2.3](2.3.1-stages.md#a-stage-names-a-role-or-a-duty), "A Stage names a Role or a duty") |
  | Reviews | `reviews` | `reviewer` | as Implements |

- **Reading the spec:** where the spec names the Planner, the CTO, Devops or the Office Manager for one of these jobs, it means the person holding that duty.
- **Job settings** (the rows each job needs, which the Role card gives and the duty never does; a record row is Own: Allowed · Others': Ask me, a capped row Proposal):

  | Duty | Job settings |
  |---|---|
  | Default person to talk to | Initiative records; Change Roles Proposal; Prompt templates Proposal; Office settings Proposal; `post_link_card` Allowed; `show_office_status` Allowed |
  | Shapes Initiatives | Initiative records; Task records |
  | Onboards and repairs Projects | Publishing settings Proposal; Project settings Proposal; Project upkeep Allowed; Pipelines and Stage templates Proposal; Change Project settings Proposal |
  | Plans | Initiative records |
  | the other four duties | none |

### Who holds a duty

- Each duty has exactly one holder, a hired Role, or none; one Role may hold several.
- It is stored as an Office setting in The Office's records.
- A duty never set is held by its default Role key; it can be set to another hired Role or to none.
- Setting it to a Role not hired, or to the Caretaker, is refused.
- A holder that isn't hired (let go, or never hired) counts as nobody, so letting a Role go leaves its duties unheld and hiring the same key back restores them.
- Duties name Role keys, so renaming a Role's title changes nothing.
- A holder with Consultant off is passed over for Asked first when a Stage runs out of tries and Default Consultant for MCP tool hard switches, and the user is asked; Settings › Duties says so beside it.
- A change reaches only what starts after it: a started Stage, an open Thread and a Consultation already put keep their person.
- A person whose Office settings are at Proposal, the Office Manager by default, drafts a duty change as a Proposal of an Office setting: it keeps the value as it was and as proposed, applies all or nothing, and is refused once the value changed since.

### Duties on screen

- Settings › Duties lists each duty with its holder, picked from the hired Roles or none, and its fallback while none.
- The Role card and People show the duties each person holds.
- Buttons and tabs that name a Role because of its duty ("Ask Devops", the CTO's tab on an Initiative, the default chat person) name the holder, as in "Ask Dwight".
- While the duty is unheld they show the fallback and point to Settings › Duties.
- Details in [4](4-ux-direction.md).

### Setting up an Office with nobody hired

- The Caretaker is present on a fresh database.
- People's empty state and the preset list show which preset to hire for which duties and capabilities.
- The Caretaker's chat offers to set the Office up and drafts the hires and the duty assignments as Proposals the user confirms.

### A person's headline state on the Live view

- With several activities at once, all are listed and the headline is waiting on you first, then consulting, then working, then idle.
- An idle person is idle since the later of their last engine call's end and their hiring.
