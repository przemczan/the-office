# 5.4.4 The Copilot CLI engine

Covers: the Copilot CLI engine, the pre-tool-use hook, Office tools and MCP servers, what is kept out, Sub-agents, usage, capabilities.

## Defaults

### The Copilot CLI engine

- It is checked by the [engine check](../engine-check.md#github-copilot-cli)'s `copilot.*` runs on Linux.
- A **Copilot CLI** engine in Settings › Engines is one GitHub account with Copilot.
- Its sessions run the Copilot CLI runtime that the pinned `@microsoft/copilot-sdk` bundles, through the SDK: one runtime process per session, speaking JSON-RPC over stdio.
- `COPILOT_HOME` is its own folder, `<office-data>/engines/<engine id>/`, where the runtime keeps each session's state (`session-state/`), its logs and plugins.
- So a session resumes only on the engine that started it.
- The runtime is signed in with the engine's token and never with a signed-in user of the machine (`useLoggedInUser: false`).
- So nothing else of the user's (`~/.copilot`, a keychain or `gh` sign-in, `COPILOT*`, `GH_*` and `GITHUB_*` variables) reaches it.
- It does not use `copilot -p`, which takes one prompt per process.
- It does not use ACP (`copilot --acp`), which gives the host no hook before a tool runs.
- A Copilot CLI engine can take any Role, an Agent Stage's included.

### Copilot CLI: the Office rules through the pre-tool-use hook

- The SDK's `onPreToolUse` hook, answered in the service's process, sees every tool call by its id before it runs, after a resume as before.
- Its calls are the runtime's own tools, MCP tools, Office tools, a shell call asking for the background and the call that starts a Sub-agent alike.
- The adapter answers each from the Office rules ([6](6-permissions-and-safety.md)) as the hook does on the Claude Code engines.
- A refusal is `deny` with the rules' reason: the call ends `denied` without running, and the model reads the reason.
- The runtime's tools map onto the tools the Office rules judge:
  - `bash` (`powershell` on Windows) as the shell, its background commands included (`read_bash`, `stop_bash`, `list_bash`);
  - `view` as Read;
  - `glob` as Glob;
  - `grep` and `rg` as Grep;
  - `create` as Write;
  - `edit` as Edit, and `apply_patch` as an Edit or a Write of each file it names;
  - `web_fetch` as WebFetch;
  - `skill` as Skill;
  - `task` and the `*_agent` tools as a Sub-agent;
  - an MCP tool by `<server>-<tool>`;
  - an Office tool by its own name.
- Which of them a session is offered depends on the model.
- A tool the adapter doesn't map is refused.
- The SDK's permission requests answer what the hook allowed; none came beside the hook.
- The runtime emits `tool.execution_start` before it calls the hook, so a call shows as started until the hook's answer.

### Copilot CLI: Office tools and MCP servers

- Each session's Office tools are SDK tools (`defineTool`), answered in the service's process with no server between.
- The Role's MCP servers ([MCP servers for Agents](5.4.1-engine-kinds.md#mcp-servers-for-agents)) are named in the session's own `mcp.servers`, fixed for the session.
- A Project's `.github/mcp.json` and `.vscode/mcp.json` stay out.

### Copilot CLI: kept out

- Sessions start with config discovery, custom instructions, the cross-session store, telemetry and the co-author trailer off.
- The runtime still reads its own folder: an MCP server in its `mcp-config.json` joins every session, and with discovery on, its agents.
- So The Office writes nothing there but the runtime's own files.
- The runtime's bundled skills (`customize-cloud-agent`, `github-pr-media`, `pr-stack`) load beside the session's skills folder on the lean options, so the adapter keeps them out.
- [5.6](5.6-skills-per-session.md)'s start check holds the listing to the session's set.

### Copilot CLI: Sub-agents

- Sub-agents start through the `task` tool (built-in agents `explore`, `general-purpose`, `task` and others).
- The hook sees that call, and refusing it keeps the Sub-agent from starting.
- Whether a Sub-agent's own calls reach the hook isn't recorded yet.
- So sessions start with no built-in agents (`includedBuiltinAgents: []`) and the hook refuses `task` until the engine check shows they do.

### Copilot CLI: usage

- Tokens come from `assistant.usage` (input, output, cache reads and cache writes).
- Cost is priced by Model prices, one per engine and model, as on the OpenAI-compatible API engines.
- The runtime's own cost and premium-request figures aren't used.
- With no price set it shows "no cost".
- It has no usage windows, so no Window caps and no readings of the usage windows.
- Copilot's monthly premium-request quota is left for later.

### Copilot CLI: capabilities as the engine check showed them

- `bargeIn` yes: `send` with `mode: "immediate"` lands before the running turn's next tool call, and one sent during an Office tool is read in the same turn after the tool's result.
- `later` is `mode: "enqueue"`, which waits for the turn's end.
- `interrupt` yes: `abort()` ends the turn and its running command within seconds, and the session takes the next turn.
- `resume` yes: `resumeSession` in a new runtime process continues the same session id with its turns, the hook registered again.
- `contextUsage` yes: `session.usage_info` gives the tokens in the context and its limit.
- `officeTools` yes.
- `outputSchema` yes: `responseSchema` holds the turn's answer to the schema.
- `languageServers` no: there is no LSP tool.
- `usageWindows` no, by decision.
- `carrySession` no, as on the Codex engine.
- Images reach the model as a blob and as a file.
