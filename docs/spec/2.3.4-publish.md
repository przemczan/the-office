# 2.3.4 Publish

Covers: Publish, the Publish Stage and its results, recorded pull requests and merging or closing them, Resolve conflicts, the publishing mode, the Office's credentials for publishing, the Task's commit message, before and after lines, merge mode when the base moved, the Changes tab after Publish, the proof-of-concept target, conflicts in the flow, the Resolve Stage, publishing into an Initiative's branch, a Publishing Task's Publish.

## Publish

- Publish is a Stage kind of its own, the **Publish Stage**, beside the Agent Stage, the Script Stage and the Gate ([2.3.1](2.3.1-stages.md#stage-kinds)).
- The Office runs it by its own git code: push and open a PR, or merge, per Project.
- All the publishing is there: the Before and After publishing lines, the merge of a moved base, the pull request, the landing commit and the published-from ref.
- It runs no Agent and no Project command, so the Office's credentials stay out of every Agent's reach ([The Office's own credentials for publishing](#the-offices-own-credentials-for-publishing)).
- It ends with one of its named results, which its routes test ([Publish's results](#publishs-results)).
- Either way one change is one commit:
  - merge lands the Task on its base as one commit with the Task's commit message;
  - a PR is titled and worded by that message for its squash merge.
- The Stage commits stay on the Task's branch as the detail of how it was done ([The Task's commit message](#the-tasks-commit-message)).
- A Publish Stage may instead push the Task's branch only ([The proof-of-concept publish target](#the-proof-of-concept-publish-target)).
- A Task of an Initiative in a Project where it has a Pipeline publishes into the Initiative's branch, always as one commit ([Publishing into an Initiative's branch](#publishing-into-an-initiatives-branch)).
- A Publishing Task publishes that branch into the base branch by the Project's publishing mode, carrying those commits unchanged ([A Publishing Task's Publish](#a-publishing-tasks-publish)).
- The pull requests it opens are recorded and watched ([The Office records the pull requests it opens](#the-office-records-the-pull-requests-it-opens-and-refreshes-them-every-minute)).

## Publish's results

- **Published**: the work shipped (a pull request opened or updated, a merge landed, or the branch pushed), and the After publishing line, when there is one, passed. The Stage ends Done.
- **Nothing to publish**: the Task's branch holds no change against its base, so nothing left; the After publishing line doesn't run. The Stage ends Done.
- **Conflict**: the Task's branch would conflict with the base as it now is; nothing left and the branch stays as it was. The Stage ends with that result, neither Done nor Failed.
- **After publishing failed**: the work shipped but the After publishing line failed; the worktree stays. The Stage ends with that result, never Failed, as the work did ship.
- **Failed**: nothing shipped, for another reason (the Before publishing line failed, the push or the pull request was refused, Push + PR without Sign in with GitHub, the base couldn't be fetched). The Stage ends Failed.
- Its routes name the results they take ([The route forms](2.3.2-flows.md#the-route-forms)); a Publish Stage with only an Otherwise row follows it on Published and Nothing to publish.
- A result its routes don't take:
  - Published or Nothing to publish follows Otherwise, as any done Stage does;
  - Conflict asks the user directly: resolve it themselves in the worktree, then **Publish again**, or drop the Task;
  - After publishing failed goes to the CTO, then the user, with **Retry** (runs only the After publishing line) or **Continue** (the Stage counts as Published with the failure noted, the worktree is removed, and its routes are weighed as for Published);
  - Failed goes to who is asked, as any Stage's failure ([When a Stage fails](2.3.2-flows.md#when-a-stage-fails)).
- Each result is kept on the run and shown in its Stage history ("Published: pull request #212 opened", "Conflict with main in 3 files").

## Conflicts in the flow

- A conflict is handled by Stages of the Pipeline's own flow, drawn and edited like any, not by Stages The Office puts in.
- The standard **conflict chain**: Publish → (Conflict) **Resolve** → **Test after Resolve** → Publish.
  - Publish's Conflict route leads to Resolve, at most 3 times.
  - Resolve leads on to Test after Resolve, a Script Stage running the Project's `test`.
  - Test after Resolve leads on to Publish, and on failure back to Resolve, at most 2 times.
  - The chain's Stages stand before Publish in the Pipeline's order, so Conflict's route is the route back whose limit ends the loop.
- **Conflict handling** is the Stages the walk runs from a Publish that ended Conflict until it reaches a Publish again, or runs a Stage reached without a conflict too, as a send-back does.
  - The Definition of Done check doesn't run again at the Publish it returns to, and none of its Stages counts as the last Agent Stage before Publish ([2.3.3](2.3.3-gates-and-checks.md#reports-count-across-stages-and-the-check-runs-before-publish)).
  - A Stage in it that fails with no failure route is put to the user directly, not the CTO first: resolve it themselves in the worktree, or drop the Task.
- To review a resolved conflict before it ships, a Gate goes between Test after Resolve and Publish, as any Gate.
- A Proof of concept Publish pushes the branch only, so it never ends Conflict and needs no chain.
- Applies in either publishing mode, and into an Initiative's branch alike.

### The Resolve Stage

- **Resolve** is an ordinary Agent Stage, made from the built-in **Resolve** Stage template and linked to it ([Stage templates](2.3.5-library.md#stage-templates)).
- Its template:
  - names the duty Implements (the Developer by default), in a fresh session;
  - has **Merge the base first** on, so The Office merges the fetched base into the Task's branch with one merge commit as it starts and leaves the conflicted files ([An Agent Stage may merge the base first](2.3.1-stages.md#an-agent-stage-may-merge-the-base-first));
  - briefs the Agent to keep what both sides meant, remove every conflict marker, edit files only and end failed with the reason when it can't.
- Its routes are the Pipeline's own, as for any Stage: Otherwise to Test after Resolve in the standard chain.
- The Office commits the merge as the Stage ends; Test after Resolve then runs, then Publish runs again, landing the merged branch's tree on the base as one commit, never rebasing the merge away.
- A Pipeline whose Tasks are another Role's work names that Role or duty on its Resolve Stage instead, which then differs from its template ([A Stage linked to its Stage template](2.3.1-stages.md#a-stage-linked-to-its-stage-template)).
- Brought back by Test after Resolve's failure route, Resolve's Agent is briefed with the failure to fix what the merge left broken; by a Gate's Send back, with the user's feedback.

## Defaults

### The Office's own credentials for publishing

- The credentials for publishing (git push, the pull request) are the Office identity's ([5.5](5.5-git-and-isolation.md#defaults)): Sign in with GitHub and the Office ssh key, used by Office code only.
- Agents never see them, and The Office's git never reaches the user's own keys or credential helpers.
- Push + PR needs Sign in with GitHub, so it is refused before the push without it.

### Publish is a Stage kind, not a Project command

- Publish is push + PR, or merge, run by The Office's own git code in a Publish Stage, which is what keeps the credentials out of Agents' reach.
- `publish` stays a reserved key: no Project command, Script Stage or condition names it.

### The Task's commit message

- The commit convention belongs to the Project, as its own docs define it (CLAUDE.md, AGENTS.md, README, CONTRIBUTING and the like); The Office decides only when the Project has none.
- Publish lands each Task on its base as one commit, whatever the convention, and the Stage commits stay on the Task's branch as the detail of how it was done.
- That commit's message is kept on the Task ([2.1](2.1-work.md)).
- The Planner suggests it with the Plan through the `write_commit_message` Office tool, following the Project's convention; any person writes it with that tool as their Authority allows (Work › Task records), and an Agent Stage writes only its own Task's.
- It is only a suggestion:
  - every Agent Stage sees it in its Brief and updates it with the same tool when its work changes what it should say;
  - the last Agent Stage before a Publish that lands it (not a proof-of-concept Publish, never a Stage in [conflict handling](#conflicts-in-the-flow)) is told to recheck it against the Task's whole diff and fix it where it no longer fits.
- The user edits it on the Task page until Publish lands it; then it no longer changes and the page shows it as published.
- With none written, Publish uses the Task's title with the Description's first paragraph below it as a short summary.
- With Push + PR, the message's first line is the pull request's title and the rest its body, ready for GitHub's squash merge; the Stage results stay on the Task page.
- Into an Initiative's branch each Task lands the same way, as one commit, and the Publishing Task carries those commits to the base unchanged (its own pull request is merged, not squashed).
- The Office's own merges of the base into an Initiative's branch stay on it and reach the base too.
- A Task made from a GitHub issue, in a Project whose "Close the issue when the Task is Done" switch is on ([2.1.1](2.1.1-projects.md#github-issues)), lands, while its Project's GitHub issues are switched on ([Feature switches](2.1.1-projects.md#feature-switches)), with a `Fixes #n` line for each of its issues in the same repository, in the commit message and the pull request's body, on the Push + PR and the merge paths alike:
  - GitHub closes the issue when the change reaches the default branch;
  - an issue the message already closes, by any of GitHub's closing keywords, gets no second line;
  - a Task of an Initiative carries it in its commit into the Initiative's branch, which the Publishing Task carries to the base unchanged; with Push + PR the Publishing Task's pull request body names its Initiative's Tasks' issues too;
  - the Task's own commit message is left as written, and a branch pushed alone (a proof-of-concept Publish, a Conflict resolution Task's) carries none.

### Publish's before and after lines

- Each Project has two optional one-line commands, **Before publishing** and **After publishing**, set on its Project page in the Commands block's Publish group beside the publishing mode, or by Devops' Proposal of commands.
- They are not Project commands: they have no key, no Pipeline runs them by name, `publish` stays a reserved key, and a blank line means nothing runs (never "could not run").
- The Office's own git still pushes, opens the pull request or merges.
- **Where and how they run:**
  - in the Task's worktree, through the same command runner and time limit as a Script Stage's command (30 minutes);
  - in the run environment when it is On, after the install when its inputs changed;
  - with the Project's own variables, Secret ones included, and never The Office's GitHub token or ssh key: a script that needs a token gets it from a Secret variable;
  - a script that waits on a GitHub Actions run can hit the time limit.
- **Scope:**
  - they run only when Publish ships by the publishing mode, for an ordinary Task or a Publishing Task;
  - never for a fix Task publishing into its Initiative's branch, nor for the proof-of-concept branch-only target.
- **Before publishing** runs before anything leaves.
  - The Office commits what it changed, as for a build-kind command, and that commit is what Publish ships; the Stage then expects HEAD there.
  - Its failure ends the Publish Stage Failed: nothing is published, and its Failed route applies.
- **After publishing** runs once the publication shipped, before the worktree is removed.
  - Shipped means a pull request opened, or a merge landed; in push + PR mode when the pull request opens, not when it merges upstream.
  - It gets `OFFICE_PUBLISHED_BRANCH`, `OFFICE_PUBLISHED_COMMIT` (the commit that shipped: after a merge, the merged commit), `OFFICE_PULL_REQUEST_URL` when a pull request opened, and `OFFICE_PUBLISHING_MODE` (`push-and-pull-request` or `merge`).
  - After Nothing to publish it doesn't run, and the result says so.
- **Runs again:**
  - both lines run again each time Publish runs (after its Failed route came back, or after Resolve), so each must be safe to run twice;
  - what shipped is kept on the Publish run before the after line runs, so a run again after a failed after line runs only that line and never publishes again.
- **A failed after line** ends the Stage with the result After publishing failed, "Published; after publishing failed: <error>", as the work did ship; the worktree stays.
  - Its routes take it like any result, such as to an Agent Stage that fixes the deploy script and back to Publish; with none, it goes to the CTO, then the user ([Publish's results](#publishs-results)).

### Merge mode when the base moved

- Publish fetches the base branch first.
- When the base moved on since the Task's branch left it, The Office merges the fetched base into the Task's branch with one merge commit, under the repository's lock, never a rebase.
- Then it lands the Task on the remote's base branch as one commit: the Task's branch's tree, with the Task's commit message, whose one parent is the fetched base, pushed without force.
- A merge that would conflict ends the Stage Conflict, the branch left as it was ([Conflicts in the flow](#conflicts-in-the-flow)).
- Push + PR pushes the branch as it is and opens the pull request; there too, a branch that would conflict with the base ends the Stage Conflict.

### The Changes tab after Publish shows what Publish shipped

- Publish records where the published branch forked from the base in a ref of The Office's own (`refs/office/published-from/<task>`).
- From then on Changes diffs the Task's branch from that commit, so it still shows the change after a merge, or after its pull request merges upstream.
- That diff is the one commit Publish landed, as the commit holds the branch's tree on that same base.

### The proof-of-concept publish target

- It is a Publish Stage's target, not a third publishing mode: a Publish Stage publishes by the Project's publishing mode (the default) or pushes the Task's branch only, with no pull request and no merge.
- The built-in **Proof of concept** Pipeline (Implement → Tests → Publish, pushing the branch only) uses it.
- This narrows "Publish is a publishing mode": still run by The Office's own git code, its target chosen per Stage.

### The merge order stays first to Publish

- Whichever Task reaches Publish first lands; a Task whose branch then conflicts with the moved base ends its Publish Conflict and goes by its conflict chain ([Conflicts in the flow](#conflicts-in-the-flow)).

### Publishing into an Initiative's branch

- A Task of an Initiative in a Project where it has a Pipeline ([2.1](2.1-work.md#defaults)) publishes into the Initiative's branch ([5.5](5.5-git-and-isolation.md#defaults)), always as one commit and never by a pull request, whatever the Project's publishing mode.
- The Office fetches both branches and brings into the Task's branch first the Initiative's branch, then the base branch, each a fast-forward, or one merge commit when the Task's branch has work of its own.
- Then the Initiative's branch gains one commit of the Task's branch's tree with the Task's commit message:
  - on the Initiative's branch when it holds the base already;
  - else on the base's own merge into the Initiative's branch, made first, so the base stays one merge commit there and the Task's commit holds only its work;
  - and, when that merge would conflict, on the Initiative's branch and the base both, the Task's tree holding the merge Resolve made.
- It never rebases, since the Task's branch can hold a merge of the base: this narrows [Merge mode when the base moved](#merge-mode-when-the-base-moved) for these Tasks.
- A merge that would conflict ends the Stage Conflict, and the conflict chain takes it, as in [Conflicts in the flow](#conflicts-in-the-flow): Resolve merges the Initiative's branch, then the base branch, then Test after Resolve, then Publish.
- Every Publish of one of the Initiative's Tasks so brings the base into the Initiative's branch, which is how the branch keeps up with the base.
- A proof-of-concept Publish still pushes only the Task's branch, so it doesn't reach the Initiative's branch.

### A Publishing Task's Publish

- A Publishing Task's worktree holds the Initiative's branch itself, and its Stages commit there.
- Its Changes tab diffs that branch from where it forks from the fetched base, so its Gate shows the full change; after Publish, Changes reads from the published-from ref ([The Changes tab after Publish shows what Publish shipped](#the-changes-tab-after-publish-shows-what-publish-shipped)).
- It publishes by the Project's publishing mode:
  - Push + PR pushes the Initiative's branch and opens a pull request from `initiative/<short name>`, or updates and links one already open from it;
  - Merge mode merges the moved base into the Initiative's branch with one merge commit (no rebase), then fast-forwards the base, so the one commit each of the Initiative's Tasks landed reaches the base unchanged.
- A conflict in either mode ends its Publish Conflict, and its Pipeline's conflict chain resolves it in its worktree.
- A fix Task's Publish into the branch waits for a running Stage of the Publishing Task to end; The Office then moves the Publishing Task's worktree to the new commit and tells its next Stage's Agent.
- An Initiative's Pipeline without a Gate is allowed: the picker and the Initiative page warn "publishes without your review" for that Project.

### The Office records the pull requests it opens, and refreshes them every minute

- Push + PR records each pull request it opens in Projects, linked to its Task.
- On the first refresh after an update, it adopts the open pull requests already on an `office/<task id>` branch.
- Each pull request has **Checks** (passing, failing, pending, none or unknown) and is mergeable (yes, conflicts or unknown), read through the Project's code host, chosen by its remote's URL (GitHub is the first).
- The job `PullRequestWatch` refreshes them every minute:
  - one list call per repository per round, conditional on its ETag;
  - a pull request's status is read again only when its head or base commit moved, its checks are pending or unknown, or its mergeability is unknown;
  - a pull request that is merged or closed leaves the list.
- With no valid GitHub token the round is skipped and statuses show as out of date, with no error.
- When GitHub can't be reached, or refuses to read checks, the last status is kept with a problem in plain words.
- The Pull requests tab of Work lists them ([4](4-ux-direction.md)).
- The App's manifest asks for `checks:read`, `statuses:read`, `actions:write` and `issues:write` (GitHub's Issues, read and write, to import, comment on and close issues, [2.1.1](2.1.1-projects.md#github-issues)) besides `metadata:read`, `contents:write`, `pull_requests:write` and `workflows:write`.
- For an App registered earlier, Settings › Office identity and the Pull requests page name the permissions an installation lacks, with links to add them on GitHub, and **Check again** reads them anew.

#### Merge or close from Work › Pull requests

- Each open pull request has **Merge…** and **Close…**.
- Merge offers the **Merge methods** the repository allows (a merge commit, squash, rebase; all three when the host doesn't say).
  - It recommends squash for a Task's pull request and a merge commit for a Publishing Task's `initiative/<short name>` pull request, whose Initiative commits squash or rebase would rewrite.
  - The dialog warns when the repository can't merge by commit.
- Merge sends the head commit The Office last read, so a pull request that changed since is refused with words asking to Refresh.
- When the host refuses (failing required checks, branch protection, a required review, conflicts, a method not allowed, no access), the dialog says why in plain words, quoting the host, and the pull request stays open.
- The Office doesn't delete the branch at the merge itself; with the Project's Delete branches once merged On it deletes it once the merge is recorded and the Task is Done ([5.5](5.5-git-and-isolation.md#deleting-merged-branches)); otherwise the dialog says whether the host will.
- The result is kept on the Task as its pull request's end (merged or closed, who, when, the method), never changing its state.
- A pull request merged, closed or reopened on the host is recorded the same way by `PullRequestWatch`, once.
- **A recorded exception:** Merge and Close are plain routes used from the page only, not Office actions, because merging into the base is publishing, which belongs to a Pipeline's Publish Stage, not to an Agent in a Thread.
  - When Agents can read pull requests, a later Task can add a `pull-request` record kind and Office actions.

#### Resolve conflicts

- A pull request whose mergeable status is Conflicts offers **Resolve conflicts** (`POST /tasks/:id/resolve-conflicts`), which makes a Conflict resolution Task for the Task that opened it and starts it at once ([2.1](2.1-work.md#defaults)).
- Resolve conflicts is the user's click, or a person's call in Work › Moving work, ruled by their [Authority](6-permissions-and-safety.md#authority) ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).
- It is refused in plain words when:
  - the Task has no open pull request;
  - its pull request has no conflicts, or The Office hasn't yet worked out whether it has;
  - the Project has no Test command;
  - the pull request's branch is checked out elsewhere (saying so when it is the original Task's own worktree).
- The Task follows the built-in **Resolve conflicts** Pipeline (`resolve-conflicts`):
  - it is seeded by a migration like the other built-ins, skipped when the user already has a Pipeline of that name; it stays in the library and can't be removed;
  - an Agent Stage **Resolve conflicts** (duty Implements, the Developer, a fresh session) runs `update_branch`, resolves each conflicted file keeping what both sides meant, removes every marker and runs the Project's Test, ending failed with the reason in its Handover note when it can't finish;
  - then a Script Stage **Test**, with a route back to the Agent Stage when it fails, at most 2 times;
  - then a Publish Stage with the branch-only target, which pushes the branch without force to the same pull request.
- The pull request watch then reads the pull requests again, so the row updates without a reload.
- With no tries left the usual walk applies: the Task waits on the user with a Decision.
- The branch takes the base by a merge, never a rebase.
