# 5.4.1 Engine port and kinds

Covers: the AgentEngine port, engine types, native features, engine features turned off, cache breakers, pinned versions, Office actions, the `-p` fallback, MCP servers for Agents, language servers for Agents, Sub-agents in the foreground.

## The AgentEngine port

- The port is not Claude-shaped: start a session with a brief, send a message with priority, interrupt, resume, read usage, the tool-permission hook.
- Each adapter declares which capabilities it has, and The Office degrades where one is missing.
- The engine a session runs on comes from the engine cascade, and its model and effort from the model and effort cascade ([5.4.5](5.4.5-engines-and-cascade.md#two-cascades)).

## Engine kinds

- Each engine is one the user adds, one account of an engine type ([5.4.5](5.4.5-engines-and-cascade.md#engines-are-a-list)).
- **Claude Code:** one account, on the TypeScript Claude Agent SDK or, by a switch on the engine, `claude -p`.
- **Codex:** one OpenAI account, on the pinned `codex app-server` ([5.4.3](5.4.3-codex-engine.md)).
- **Copilot CLI:** one GitHub account with Copilot, on the GitHub Copilot CLI runtime driven by the pinned `@microsoft/copilot-sdk` ([5.4.4](5.4.4-copilot-cli-engine.md)).
- **Gemini CLI:** one Gemini API key, on the pinned `@google/gemini-cli` run headless, a process per turn ([5.4.7](5.4.7-gemini-cli-engine.md)).
- **OpenAI-compatible API:** one API endpoint, on The Office's own agent loop ([5.4.2](5.4.2-openai-compatible-api-engine.md)).
- The scripted adapter replays recorded engine output for tests.
- The Claude Code engines run one long-lived streaming `query()` per session.
- The Codex engine runs one app-server process per session.
- The Copilot CLI engine runs one runtime process per session.
- The Gemini CLI engine runs one CLI process per turn, each resuming the session by its id.

## Native features used

- Message `priority` for barge-in: `next` between tool calls, `later` after the turn.
- `interrupt()` for Stop, the only way to stop a running command.
- `now` is not used: it ends the turn but leaves a running command to finish or run on in the background.
- Resume by session id.
- The 1-hour prompt cache on the main conversation.
- In-process Office tools via `createSdkMcpServer()`.
- `rate_limit_event` and the experimental usage query for the 5-hour and 7-day windows, never the CLI's OAuth token.
- Each reading keeps its **Reading source**: the usage endpoint's own answer (a session's first), or one the CLI builds from the last reply's rate-limit headers (the later ones, one per turn's rate-limit event).
- The two sources round differently, so the Office-wide window % per token for usage estimates is learnt only from successive readings of one source, each counted pair kept so the ratio outlives a restart.
- Cost in The Office is priced by the Model prices set per model in Settings → Engines, never the engine's own `total_cost_usd`.
- A Model price has input, output, cache writes and cache reads per million tokens, for every engine's models.
- There is one Model price per Claude model, shared by every Claude Code engine.
- There is one per Codex model, shared by every Codex engine.
- There is one per engine and model on the Copilot CLI, Gemini CLI and OpenAI-compatible API engines.
- A removed engine's Model prices are kept so its history stays priced.

## Engine features turned off

- claude.ai connectors (`disableClaudeAiConnectors`).
- The engine's built-in plugins (each set false in `enabledPlugins`).
- Auto-memory (`autoMemoryEnabled` and `autoDreamEnabled` false): its folder outside the worktree is shared by every worktree of a repository and written without a prompt. Memory is The Office's own (Shared memory).
- The built-in tool set is an explicit `tools` list, the same on both platforms: the engine's Windows default today and `LSP`, PowerShell on Windows only. The engine's Linux default drops Grep and Glob for shell search.

## Cache breakers

- Avoid mid-session: changing model, effort, MCP servers (with tool search off) or the Claude Code version.

## Pinned versions

- The SDK bundles the binary.
- `@openai/codex` is pinned exactly.
- `@microsoft/copilot-sdk` is pinned exactly and bundles the Copilot CLI runtime.
- `@google/gemini-cli` is pinned exactly.
- Versions are bumped deliberately, re-checking what was read from the binary ([5.6](5.6-skills-per-session.md), [6](6-permissions-and-safety.md)) with the engine check ([engine-check.md](../engine-check.md)).

## Defaults

### Office actions

- Each action the user can take on a record (Task, Initiative, Idea, Project, Role, Skill…) is declared once, in the contracts, with its name, record, description, input, route and exactly one cover: the duties that cover it, or the creators of a record.
- Both the HTTP route the web calls and the Agents' Office tool come from that declaration and call the owning module's one handler; the user's clicks go through the same route.
- So whether an action is allowed is decided by the same domain rules for the user's click and the Agent's call, refused in the same words.
- An action covered by duties: a person gets its tool in every Thread the user talks to them in whose person holds one of them: their chat, their Thread on a Task, the planning Threads, an Initiative's Threads, a Consultation.
- An action covered by the creators of a record: a person gets its tool in every Thread whose tools include that record's create tool, `create_task` for a Task, `capture_idea` for an Idea, `create_initiative` for an Initiative, which follow the person's [Office tools](6-permissions-and-safety.md#a-persons-office-tools).
- A person never gets either in an Agent Stage, which does its Stage's work only.
- The actions covered by a Task's creators: `change_task_title`, `change_task_description`, `change_task_kind`, `change_task_priority`, `change_task_plan`, `change_task_definition_of_done`, `drop_task`, `archive_task`, `restore_task` ([2.1.3](2.1.3-tasks.md)).
- By an Idea's creators: `edit_idea`, `drop_idea`, `restore_idea` ([2.1.2](2.1.2-ideas-and-attachments.md)).
- By an Initiative's creators: `write_initiative_outcome`, `drop_initiative`, `archive_initiative`, `restore_initiative` ([2.1.4](2.1.4-initiatives.md)).
- A Drop by an Agent is refused once the work has started, which only the user Drops ([2.1.3 Dropping](2.1.3-tasks.md#dropping)).
- Every edit of a record's fields through them is kept in its History, naming who made it ([2.1.3 History](2.1.3-tasks.md#history)).
- Their Role's authority (decide alone, consult first, ask the user) and the Hard switches still say when they may use one without a Decision, as each tool's description reminds them.
- `add_dependency`, `remove_dependency`, `add_to_initiative` and `take_out_of_initiative` are covered by Shapes Initiatives and Plans.
- They change an active Initiative straight away, while the shaper's other tools (its outcome, a new Task, titles, Descriptions, its Pipeline) draft Proposals.
- Projects' actions are `rerun_ci_run` (a failed or cancelled CI run runs again, all its jobs or only the failed ones) and `start_workflow` (a Workflow that declares a start by hand starts on a branch or tag, with its inputs), covered by Onboards Projects.
- Every new action on a record is made this way, never as a hand-written route plus a hand-written tool.
- Every write route (`POST`, `PUT`, `PATCH`, `DELETE`) is an Office action, or is listed in the contracts' write-route register (`WRITE_ROUTE_REGISTER`) as the user's alone, with the spec heading that says why, or as needing no action, with a one-line reason; routes still missing an Office action are listed there as known gaps, a list that only shrinks, and a test fails for any other route and for an entry whose route is gone.

### The `-p` fallback matches the Agent SDK adapter

- The Office tools reach its sessions through the binary's own stream, as the SDK does: an in-process MCP server answering the binary's `mcp_message` requests.
- The Office rules reach it through a hook that asks the service on `localhost`, so any Role can work with it.
- It is not an MCP endpoint on `localhost`: over HTTP a tool's answer can overtake a barge-in message on the binary's input, which the engine check saw on Windows.
- The hook's token is made per session and reaches its Agent's commands, so it reaches nothing beyond its own session's hook, which judges by that session's rules.
- What it can't match, as the engine check finds, it declares missing.
- It is a switch on each Claude Code engine, off by default, every session on that engine running through it.
- It runs the pinned Claude Code binary the SDK bundles, with the same models.
- It has its own runs in the [engine check](../engine-check.md) on Windows and Linux.

### MCP servers for Agents

- The user adds each MCP server to an Office-wide library in Settings → MCP servers, by a form or by pasting the server's JSON config.
- A server is a local command (stdio: command, arguments, environment) or a remote URL (Streamable HTTP, with headers).
- A server declares its Server values (an environment variable or a header; plain or secret; required or not).
- Each Server value has an Office-wide value that a Project's page may override.
- A secret is kept in the database and never sent back.
- A server is off until the user reviews it: its command or URL, its values, and the tools it lists on a test connection.
- Changing a server turns it off until reviewed again.
- A Role card assigns servers.
- A session starts with its Role's servers that are on, with its Project's values (the Office-wide values in chat), fixed for the session.
- A server missing a required value is left out, and the session's brief says so.
- Every engine runs them:
  - the Claude Code engines through their own MCP config holding only the Office's servers, never a Project's `.mcp.json`;
  - the OpenAI-compatible API engine through an MCP client in its loop;
  - the Codex engine through the service's `office` MCP server ([5.4.3](5.4.3-codex-engine.md#defaults));
  - the Copilot CLI engine through the session's own `mcp.servers` ([5.4.4](5.4.4-copilot-cli-engine.md#defaults)).
- Every MCP tool is judged by the Office rules before it runs ([6](6-permissions-and-safety.md)).

### Language servers for Agents

- Every session on a Claude Code engine, whichever its Role, chats and the Planner too, has the `LSP` tool on the workstation's language servers: TypeScript, C and C++, Kotlin ([language-servers.md](../language-servers.md)).
- A session gets those its `PATH` finds as it starts, fixed for the session as its MCP servers are.
- One not found is left out, the session's brief says so, and it never stops a session starting.
- The servers reach the engine as a plugin of their own beside the skills folder, so a session with no skills still gets them and the skills start check ([5.6](5.6-skills-per-session.md)) stays exact.
- A server starts at the first LSP call or Edit on a file of its language, never with the session, and one stays out of a session that doesn't need it.
- Each LSP call is a read of its file under the Office rules ([6](6-permissions-and-safety.md)).
- The OpenAI-compatible API, Copilot CLI and Gemini CLI engines have no such tool and declare the capability missing.

### A Stage's Sub-agents run in the foreground

- A Stage's result is its Agent's turn's end, held to the Stage result's schema, so a Stage session runs with `subAgentsInForeground`.
- The Office rules hook answers each Sub-agent call it allows with `updatedInput` setting `run_in_background: false` ([2.9](2.9-sub-agents-and-processes.md#the-model)).
- Background commands stay allowed.
- Other sessions don't get the option.
- The API engine has no Sub-agents and takes it unchanged.
- The Copilot CLI engine's sessions start no Sub-agents ([5.4.4](5.4.4-copilot-cli-engine.md#defaults)).
- Nor do the Gemini CLI engine's ([5.4.7](5.4.7-gemini-cli-engine.md#defaults)).
- The engine check's `engine.foreground-sub-agents` and `fallback.foreground-sub-agents` confirm that both routes honour the hook's `updatedInput`.
