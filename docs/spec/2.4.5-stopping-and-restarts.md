# 2.4.5 Stopping and restarts

Covers: Stop, Pause and Resume, Restart from, Start over, shutting The Office down, restarts, a crash loop, a refused turn, Threads after a restart.

## Stop and Pause

- **Stop** interrupts now, discards the Stage's uncommitted edits and holds the Task.
- **Pause** holds the Task once the Agent's current turn ends, mid-Stage, keeping the edits.
- A Project command, such as a Script Stage's, can't be interrupted: Stop waits for it to end and holds the Task as Pause does.
- Resume runs the held Stage on through the Context policy.
- Resume is refused for a Task of a paused Initiative, which Resume the Initiative resumes ([2.1](2.1.4-initiatives.md#pause-the-initiative), "Pause the Initiative").
- Start, Pause, Stop and Resume are the user's click, or a person's call in Work › Moving work, ruled by their [Authority](6-permissions-and-safety.md#authority) ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).
- The user's messages a stopped session never took go with it, so a message and Stop redirect the Agent.

## Restart from

- On a paused or stopped Task, **Restart from…** has the walk run the chosen Stage next, any Stage of the Pipeline, later ones too, with optional feedback.
- The user restarts from the Task page; a person's call is ruled by their Authority for Work › Gates and runs ([6](6-permissions-and-safety.md#authority-by-role)).
- The held run ends, and the uncommitted edits Pause kept are discarded.
- The Task goes on In progress and the walk goes on from the chosen Stage by its routes.
- It is no route and uses none of a route's times ([2.3.2](2.3.2-flows.md#a-routes-limit)).
- An Agent Stage is briefed with the feedback, as with a Gate's Send back; a Script Stage just runs, and the feedback is kept on its run ([2.3.3](2.3.3-gates-and-checks.md#send-back)).
- The Stages the restart jumps over are **Skipped**.
- The Definition of Done check before Publish still runs.
- Refused while the fire alarm, a usage window or a paused Initiative holds the Task, with the reason, as Pause and Stop are.
- History says "Restarted from <Stage> by <who>" ([2.1.3 History](2.1.3-tasks.md#history)); screen: [Task page › Run controls](screens/task-page.md#run-controls).

## Start over

- On a paused or stopped Task, **Start over** takes the Task back, not queued, to the user's choice of:
  - **Ready**, the default, with its Plan, Definition of Done and Pipeline kept as confirmed; the user starts it again.
  - **Backlog**, with its Plan, Definition of Done and Pipeline kept but Not confirmed, its Pipeline as proposed, and the Task no longer planned, as a Task its Initiative took Back to Shaping is ([2.1.4](2.1.4-initiatives.md#back-to-shaping)); it is planned again before it is Ready.
- To Backlog, its Stages edited for this Task are dropped: they are copied again from its Pipeline as built now, so Edit for this Task starts from the Pipeline's.
- The user starts over from the Task page; a person's call is ruled by their Authority for Work › Gates and runs ([6](6-permissions-and-safety.md#authority-by-role)).
- The Stage runs before it stay in the Stage history as history only: the walk, the Pipeline rail, routes' times, Not taken, the Definition of Done's Reported met and the Stages an edit may no longer change count only the runs after the latest Start over.
- The next Start opens fresh Stage sessions.
- With **Reset the branch to <base>**, on by default, the branch is hard-reset to the freshly fetched base: the Initiative's branch for an Initiative Task, else the Project's base branch.
  - The old head is kept under the local ref `refs/office/started-over/<task id>/<n>`, named in History.
- Once a Publish Stage pushed the branch or opened a pull request, the Task is still started over, but its branch isn't reset: the next Publish pushes without force, onto the same branch and pull request ([2.3.4](2.3.4-publish.md#publish)).
  - A reset asked for is refused: "Its work has left the workstation, so its branch isn't reset: the next Publish pushes onto the same branch and pull request."
- Refused for a Publishing Task, whose branch is its Initiative's, pushed as it goes, and for a Conflict resolution Task, which works on the branch of the Task whose pull request has the conflicts; Restart from… is offered instead.
- Refused while the fire alarm, a usage window or a paused Initiative holds the Task, as Restart from is.
- History says "Started over by <who>"; a Dropped Task's **Reopen…** starts it over the same way ([2.1.3](2.1.3-tasks.md#reopen)).
- Judged and done as one move: a Resume or Restart from… asked meanwhile waits for it and is then refused, as the Task is Ready, so no walk goes on on a branch being reset.

## Shutting The Office down

- Shutting The Office down ends running sessions and Project commands at once, but unlike Stop it keeps the Stage's uncommitted edits.
- A Stop asked before the shutdown still discards the edits.

## Restarting

- At the next start things go on by themselves, with no Decision.
- An Agent Stage it restarted during runs again, its session resumed or started fresh as the Context policy decides.
- Its Brief says the restart cut the last turn short and may have left a file half-written, so the Agent checks `git status` and `git diff` first.
- A Script Stage runs its commands again from the start.
- The Stage due to start next starts.
- A restart is no failure and spends no try, correction or Consultation of the CTO.
- Each run still waits for its slot under Running Tasks at once and Run environments at once.
- A Stage the user had paused or stopped stays held, as does one the fire alarm or an engine's usage window holds, with its edits, its last turn cut short.
- A Decision the Agent opened before its run was held stays open and the run keeps it.
  - The Task shows Paused and Waiting on you.
  - Answering it doesn't resume the Task.
  - Its answer goes with the Stage when the user resumes, which runs only once it is answered.
- A Task Waiting on you whose Decision or Gate was answered before The Office stopped, but which hadn't gone on yet, goes on by itself.
- The Office's own Decision is never opened twice: one opened just before The Office stopped is the one the Task waits on, and its answer counts.
- An answer or a Gate action is kept as soon as it is given; if the Task fails to go on from it, The Office tries again by itself a moment later ([Defaults](#an-answer-the-task-didnt-go-on-from)).

## Crash loop

- Against a crash loop, the third restart in a row during the same Stage asks instead.
- The Decision says it restarted three times during this Stage, and asks to run it again or drop the Task.
- A Stage has got past a restart once one of its runs ends any other way.

## Stop in a person's Thread

- Every Thread the user talks to a person in has a **Stop**: a chat, a person's Thread on a Task, the Planning Thread, and an Initiative's shaping and planning Threads.
- A Stage Thread has none: the Task's Stop and Pause hold the Task there. A Consultation has no composer, and its caller is waiting on it.
- Stop ends the turn now, with every Sub-agent and Process it started, in the foreground or the background; they show Stopped, "when the turn was interrupted" ([2.9](2.9-sub-agents-and-processes.md)).
- It uses the same session interrupt as a Stage's Stop; on an engine that can't interrupt, the session ends and the line says so, and the next message starts fresh.
- The session is kept otherwise, so the next message continues it under the Context policy ([2.5](2.5-context-policy.md)).
- What the person already said stays in the log, and the Thread logs a line that the user stopped them.
- Messages waiting to land aren't delivered: each reads "Not delivered: you stopped <name>", and the user's own get **Send again** ([2.4.4](2.4.4-messages.md#barge-in)).
- Stop between turns does nothing.
- One click, with no confirmation: nothing is lost.
- The Office command **/stop** does the same ([2.4.4](2.4.4-messages.md#office-commands)); there is no Esc key for it.
- Only the user stops a person's answer: no Office tool does ([6 The user's alone](6-permissions-and-safety.md#the-users-alone)).
- Screen: [Thread › Composer](screens/thread.md#composer).

## Defaults

### A turn refused for the usage window

- It applies in every Thread on a Claude Code engine or a Codex engine on a ChatGPT plan: a chat, a Consultation, a planning Thread, a Stage Thread.
- A turn the engine refuses because a usage window is used up is logged as its own line, "Claude Code's 5-hour window is used up until 14:00", naming the engine, the window and its reset time, shown as a notice, not as a failure.
- Every Thread goes on on a Stand-in Engine with room instead, the refused message sent again there: a Stage Thread only on one of the same engine type, a chat, a Consultation and a planning Thread on one of any type, starting fresh on another type ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#a-running-stage-switches), [A person's Thread switches](5.4.6-stand-in-engines-and-usage-windows.md#a-persons-thread-switches)).
- A Stage Thread logs a notice line for the switch in the same words as the Stage history: "Claude Code's 5-hour window was used up until 14:00, so the Stage went on on Claude Code 2".
- A chat, a Consultation and a planning Thread log it naming the person who went on: "Claude Code's 5-hour window was used up until 14:00, so Pam went on on Claude Code 2", or on another type "…, so Pam went on on Codex, starting fresh".
- A chat, a Consultation and a planning Thread keep the line above only when no stand-in has room, the carry-over fails or an engine override forces their engine, which has no stand-ins ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#a-forced-engine-has-no-stand-ins)), and aren't resumed by themselves at the reset: the user writes again.
- A chat, a Consultation and a planning Thread whose resume on the stand-in fails move back to their engine and say so in a failure line.

### An answer the Task didn't go on from

- The Office tries again 30 seconds after a Task failed to go on from an answer or a Gate action, and every 30 seconds after that until it goes on.

### After a restart

- A Thread left answering when The Office stopped waits for the user again, "The Office stopped while this was being answered."
- Its background Sub-agents are Stopped, "Ended when The Office restarted" ([2.9](2.9-sub-agents-and-processes.md)).
- A planning Thread works on its own, often in auto mode, so the planner (whoever holds Plans) is woken in it again as The Office starts, when the restart cut it short (mid-turn, or with background Sub-agents running) and it still has a Task in Planning.
  - The Thread is a Task's own planning Thread whose Task is in Planning there, or an Initiative's planning Thread with one of its Tasks in Planning planned in it.
  - It is woken in the same Thread, its session continued or replaced under the Context policy.
  - The planner is told The Office restarted and cut their work short, and that any Sub-agents they had running were stopped and their results lost.
  - They run again the Sub-agents they still need and carry on planning.
- Nothing is woken while the fire alarm is on ASAP, nor for an Initiative the user paused: the user writes in the Thread to go on. Under a softer way of the alarm the planner is woken, as Threads keep their tools ([2.8](2.8-fire-alarm.md#chats-during-the-alarm)).
- A shaping Thread, a chat, a Consultation and a Stage Thread aren't woken: the user is in the conversation, and the failure line and the Sub-agents' "Ended when The Office restarted" tell them (a Stage goes on with its Task, [2.3](2.3-pipelines.md)).
