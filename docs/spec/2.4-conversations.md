# 2.4 Conversations

From [09](../../.scratch/the-office/issues/09-conversations.md) (amended by [21](../../.scratch/the-office/issues/21-role-capabilities.md) and [25](../../.scratch/the-office/issues/25-agent-permissions.md)), [04](../../.scratch/the-office/issues/04-agent-identity.md), [17](../../.scratch/the-office/issues/17-task-page-mockup.md), [18](../../.scratch/the-office/issues/18-people-mockup.md).

- **Three homes:** a **person's chat** (for people with Chat on), a **Task's conversation** (one tab per person, each holding that person's one Thread on the Task; Stage Threads show in the Stage history) and an **Initiative's conversation** (one tab per person, the tabs of the holders of Shapes Initiatives and of Plans always, one tab when one person holds both, and anyone else's with a Thread on it, each holding that person's Threads on the Initiative, the newest the one written to: the shaping Threads and the planning Threads, opened by Plan the Initiative, [2.1](2.1-work.md); the user's request of 2026-11-11; amended 2026-11-13: while a duty is unheld its tab shows the fallback and points to Settings › Duties, [2.2](2.2-people.md#defaults), "Duties"). The Chat button with no Thread open goes to the holder of Default person to talk to, or to the Caretaker while nobody holds it (amended 2026-11-13).
- **Threads:** each is one engine session underneath. A fresh Thread starts a new session: the record and the person's memory stay, the context goes. Old Threads stay readable and can be continued ([2.5](2.5-context-policy.md) decides resume or brief).
- **A person's Thread on a Task** (the user's answers of 2026-11-05, which settle what task 49 asked): the Task's conversation has a tab for the holder of Plans first (amended 2026-11-13), then each person who ran an Agent Stage of the Task in the order they first worked, then each Consultant of a Decision on it, as soon as the Consultation starts. Each tab holds that person's one Thread on the Task, written in at any time while the Task hasn't ended, for asking them about anything in it; a Done or Dropped Task's tabs are read-only. A tab with no Thread yet shows the composer, and the first message opens the Thread: looking at a tab opens nothing (the user's answer of 2026-11-05). The Planner's Thread is the Planning Thread; the Planner there keeps Planning's Brief and tools until the Task starts, Ready included, where its Brief says the Task is Ready and that writing a part takes it back to Planning, so the Planner writes one only when the user asks (the user's words of 2026-11-11, spec 2.1: "If a task is Ready but not yet started it should still be possible to update plan/dod, which should move the task to planning again and require marking as done. Agent should stil lbe able to do these things with the task."); a Ready Task's Planning Thread runs only on the user's messages. Once the Task has started, the Planner there has the read-only tools of the other people's Threads instead of Planning's.
  - **Its session:** its own, under the Context policy like any chat Thread. Its first session's Brief is the record; a later fresh session's is the Context policy's only, as for any chat Thread ([2.5](2.5-context-policy.md)).
  - **Its tokens** count to the Thread and to the Task, never to a Stage's budget, the Planner's Thread included, so Planning's tokens count to no Stage (the user's answer of 2026-11-05); the Usage estimate and the Window caps see them as any session's ([2.1](2.1-work.md)).
  - **It changes no code:** it reads the Task's worktree, as it is at the moment, but doesn't edit it or run commands that change it. Changes go through a Stage: Send back at the Gate, or a running Stage's Thread.
  - **It holds nothing:** asking doesn't hold or release the Task or its Gate; only Continue, Send back and Drop act at the Gate. An MCP tool at Consult or Ask me still opens an approval Decision in the person's Thread, as on any Task Thread; it holds that call and nothing about the Task (the user's answer of 2026-11-05).
  - **Beside a running Stage:** while the person's Stage runs, the two sessions run side by side, and the tab says so and leads to the Stage history to write into that work.
  - **A Consultant's tab** shows their Consultation on the Task above their Thread on the Task: live while it waits on them, then with its note, which is the Consultant's answer in words (the user's answers of 2026-11-05). The composer writes in their Thread, never in the Consultation.
  - **Unseen messages:** a tab whose Thread got a message the user hasn't seen shows a count.
- **Decision** (Initiative "Multiquestion form", 2026-11-16): a form the Agent opens in the Thread it works in, of one or more **questions** in the order it asks them, its context, and any of the Task's or the Initiative's Attachments it is about. Each question is either a **choice**, its options with the Agent's recommended one preselected and the reason it gives for it, or an **open question**, answered in words. Every question takes an optional **comment**, and the form takes one **general comment**. A choice is answered by picking an option, or, picking none, by its comment alone, which is then the answer in words. On the Task page its card is in Needs you and the Thread shows it in short; Now and the Needs you panel show the same card. The user may ask follow-ups in the same Thread before sending it, and sends it one of two ways:
  - **Submit** sends every question's answer with its comment, and the general comment; it needs an answer to every question. The Decision is answered.
  - **Ask me again** sends only the general comment, no answers, saying what to explain or change: the Decision closes as **asked again**, leaves Needs you and its Notification clears, and the Agent explains and asks again in a new form. The Office's own Decisions (a Stage out of tries, a budget, the Definition of Done, a restart loop, a moved branch) have no Ask me again: nobody is there to ask again.

  Either way the whole form reaches the asking session together, as its next message: on Submit each question in order with the answer (the option picked, or the words) and its comment, then the general comment, and who answered; on Ask me again that the user asked again, with the general comment and who asked. A redirect reply ("ask the CTO") turns it into a Consultation. The form is the one Decision everywhere: a Thread on a Task, a Stage (The Office's own Decisions as a form of one choice), a Consultation, which the Consultant answers as the same form, an answer given for the user, and an Initiative's shaping and planning Threads; all show under Needs you, except a chat's, which shows inline in the chat (Consultation, "Calls from chats", below). A Decision recorded before the form reads as a form of one question: a choice with its options, or an open question when it had none. In a Thread on a Task, Decisions are one at a time, a form counting as one. An Initiative's shaping Thread may open one on no Task, one at a time, shown in that Thread and under Needs you with the Initiative's title. In an Initiative's planning Thread ([2.1](2.1-work.md), Plan the Initiative) the Planner may open one on no Task in the same way, and several on Tasks, one per Task, each naming one of the Initiative's Tasks and shown on that Task's page as well; an answer given while the Planner works is recorded at once and handed to its session as its turn ends (the user, 2026-11-10). Dropping a Task closes every Decision still open on it, waiting on the user or put to a Consultant; a closed Decision leaves Needs you and its Notification clears, and its card says the Task was dropped (the user's report of 2026-11-15). Likewise, when an Initiative is done or dropped, every Decision still open on no Task in its shaping or planning Thread closes: it leaves Needs you, its Notification clears, and its card reads "Closed: the Initiative ended".
  - **Answered for the user, at their request** (Task "Let people answer a Decision for the user when the user asks them to"): in any Thread the user talks to a person in (a chat, a person's Thread on a Task, the Planner's, an Initiative's Threads), the user may ask that person to answer a Decision waiting on the user; the person does with the Office tool `answer_decision`, by its id (`read_task` lists a Task's Decisions waiting on the user, each question's options numbered), either submitting it, with each question's answer (an option by its number, or words) and comment and the general comment, or asking again with the general comment alone, as the user's two ways of sending it (Initiative "Multiquestion form", 2026-11-16). The Office trusts the person's word that the user asked (the user's choice over a confirm click), so the record is honest: the Decision and its answer line keep who answered and the Thread the user asked in, its card reads "Answered by <person> at your request", linking to that Thread, the line names the person instead of You, and the asking person is told so. Every rule of the user's own answer holds, and to a Consultation and the Pipeline it is the user's answer. Refused for a Decision put to a Consultant, an approval of a call past a Hard switch or of an MCP tool (the user's own click, [6](6-permissions-and-safety.md)), and one in the person's own Thread; Agent Stages and Consultations have no such tool. An answered Decision, or one asked again, isn't reopened, this one no more than any other: the user changes course by writing to the asking person in their Thread (the user, 2026-11-12).
- **Barge-in:** the user writes into a running Stage Thread at any time, from its Thread in the Stage history (the user's answer of 2026-11-05), and into every other Thread they write in while the person is answering: a chat, a person's Thread on a Task (the Planning Thread included) and an Initiative's Threads (the user's answer of 2026-11-15). The message is logged at once, shown "Lands at the next safe point", and lands at the next safe point (between tool calls) of the turn running, then shows "Delivered"; one sent before its turn took it keeps the person answering until they have answered it too. One that never reached the person, because the answer failed, was stopped or the session ended, shows "Not delivered: <name> finished first" (a Stage Thread's: "the Stage ended first"). Answering a Decision while the person is answering stays refused. **Stop** interrupts now, discards the Stage's uncommitted edits and holds the Task; **Pause** holds it once the Agent's current turn ends, mid-Stage, keeping the edits (a Project command, such as a Script Stage's, can't be interrupted: Stop waits for it to end and holds the Task as Pause does). Resume runs the held Stage on through the Context policy, and is refused for a Task of a paused Initiative, which Resume the Initiative resumes ([2.1](2.1-work.md#defaults), "Pause the Initiative"); the user's messages a stopped session never took go with it, so a message and Stop redirect the Agent (the user's answers of 2026-10-26). Shutting The Office down ends running sessions and Project commands at once, but unlike Stop it keeps the Stage's uncommitted edits. At the next start things go on by themselves, with no Decision (Task 989f7d1f, 2026-11-14): an Agent Stage it restarted during runs again, its session resumed or started fresh as the Context policy decides, its Brief saying the restart cut the last turn short and may have left a file half-written, so the Agent checks `git status` and `git diff` first; a Script Stage runs its commands again from the start; the Stage due to start next starts. A restart is no failure and spends no try, correction or Consultation of the CTO, and each run still waits for its slot under Running Tasks at once and Run environments at once. Against a crash loop, the third restart in a row during the same Stage asks instead: a Decision, saying it restarted three times during this Stage, asks to run it again or drop the Task; a Stage has got past a restart once one of its runs ends any other way. A Stage the user had paused or stopped stays held, as does one the fire alarm or an engine's usage window holds, with its edits, its last turn cut short (the user's answers of 2026-10-26); a Stop asked before the shutdown still discards the edits. A Decision the Agent opened before its run was held stays open and the run keeps it: the Task shows Paused and Waiting on you; answering it doesn't resume the Task, and its answer goes with the Stage when the user resumes, which runs only once it is answered (the user's answer of 2026-10-26).
- **Consultation** (tier 2; in tier 1 every consult goes to the user): a sub-thread between an asking person and a Consultant, labelled with both. It answers a Decision's form, approves a held call past a Hard switch, or takes a Request ([2.2](2.2-people.md)). On a Task the user can read it live or take it over, but not join it (the user's answer of 2026-11-05); on the Task page it shows in the Consultant's tab (above). The Consultant answers in a fresh session with its memory and the brief of its home: the Task's, or their chat's.
  - **Calls from chats** (Task c288eb09; the user, 2026-11-12: "it works in chats, not only on Decisions inside a Task"): a person's chat (the Default person to talk to's included), their Thread on a Task, the Planning Thread and an Initiative's shaping and planning Threads can call a hired Consultant, as Agent Stages consult (amended 2026-11-14). A call from an Initiative's Thread is on no Task, as a chat's is, except a planning Thread's call naming a `taskId`, which is on that Task as its Decisions are. From a chat the call is a Decision on no Task, put to the callee, one at a time per Thread; the callee's Consultation opens in the callee's own chat and shows in its Thread list. The caller's turn ends and the answer comes as their next message, which they tell the user; a message the user writes meanwhile goes to the caller as usual. A chat has no Needs you: a Decision waiting on the user there shows inline in the chat, as the form, answered and sent in place, with no Needs you card and no Notification (Initiative "Multiquestion form", 2026-11-16). The person in a chat may open one asking the user directly, one Decision open at a time per Thread whether a call or not, and a call that falls back to the user (naming nobody who can be called, passed on to the user, or a Consultation that couldn't start) becomes that inline form in the caller's chat. The user takes over a call only on a Task.
  - **Both Threads show it** (the user, 2026-11-12: "the call and the answer show in both Threads"): the caller's Thread shows the Decision card, naming the callee, then their answer; from a chat it links to the Consultation. The Consultation opens with what it was asked as The Office's line ("Angela asks you to: …", the form's questions in order) and logs the callee's answer as another ("Your answer to Angela: …"). The callee answers the same form as the user would, Submit or Ask me again; an approval stays Allow once, Deny or Pass on ([2.2](2.2-people.md)).
  - **The callee's own permissions** (the user, 2026-11-12: "the callee works with their own permissions, never the caller's, so a read-only Thread can't get a change made by calling someone"): see [6](6-permissions-and-safety.md).
- **Office actions in Threads** ([5.4](5.4-the-engine.md)): every Thread the user talks to a person in (a chat, a person's Thread on a Task, the Planner's, an Initiative's shaping and planning Threads, a Consultation) also has the tools of the Office actions the person's held duties cover; an Agent Stage has none (Task "Linking Tasks to Initiatives and to each other", 2026-11-14). In an Initiative's shaping Thread, its Tasks' dependencies and which Tasks it has change straight away through them, even once it is active, the person's Role authority being the gate; its other changes are still drafted as Proposals.
- **Mentions** (tier 2): any Task, Initiative, Idea or Decision can be mentioned in any chat (link or `@`), and the Agent there can read its record.
  - **Agents link what they mention** (the user, 2026-11-13: "a bare, shortened ID is hard to find"): every session's standing instructions say to write a Task, Initiative, Idea or Project as a Markdown link to its page with its full ID, never a shortened one, and to put text the user is meant to copy in a fenced code block. A message shows a link to a Task, Initiative, Idea or Decision as its chip; a link to any other page of the app opens it in place, and any other link in a new tab.
  - **Copy**: every fenced code block and every quote in a message or a Markdown document has Copy in its top-right corner, which copies exactly its text (a code block's code, a quote's words) and says so in a toast; where the browser offers no clipboard, such as over plain http from another computer, the toast says it couldn't be copied. Copy link on a record and the Office ssh key's Copy work the same way.
- **Images in a message** (Task "Paste images into a Thread's message box", 2026-11-16): the user pastes or drops PNG, JPEG, GIF or WebP images into any Thread's message box (a chat, a person's Thread on a Task and its first-message box, a Stage Thread, a Consultation, an Initiative's shaping and planning Threads), up to 3 MB each, 10 per message and 15 MB in all; the message box and The Office both check. A message may be images alone; a skill command carries none. Each is uploaded at Send and kept as an Attachment: of the Task in a Thread on a Task, of the Initiative in an Initiative's Thread, else of the Thread itself; a retry after a failed send reuses the uploaded ones. The message keeps its images and shows them as thumbnails that open full size in the Attachment viewer; one whose Attachment was removed shows "Image removed". A Claude Code engine gets them as pictures with the message, a new session's first message and a barge-in included; an API endpoint model gets them as pictures only when it **Sees images** ([5.4](5.4-the-engine.md)), else the message names each image and its Attachment and says the model can't see pictures. A fresh session's Brief lists a past message's images by name and Attachment id, or "Image removed", and `read_attachment` reads them.
- **Open page**: a message sent from the chat drawer goes with the page open beside it, when that is a Task's (a Decision window on it still the Task), an Initiative's, an Idea open on Work › Ideas, a person's or a Project's page, any tab or section of it. The composer says so on a line, "Open page" with the record's chip, and **Leave out** drops it from the messages sent while that page stays open, whichever Thread or person the drawer shows and though it closes and opens again. The line follows navigation as it happens: once the user opens another page, even to come back to the one left out, it shows again and messages go with the page; any other page has none. The person answering is given its record under its own heading, after the message and its Mentions: a Task's, Initiative's or Idea's as a Mention's, a person's and a Project's as their short records in `list_people` and `list_projects`. A record the message mentions already isn't given twice, and within one session the same Open page is given again only once it changed since the previous message; a session that starts on the message has it in its Brief. A Task's or an Initiative's own conversation sends none, being about its record already. The log keeps the message's Open page, shown under it as "With <chip> open".
- **Commands in the message box** (Task 62cb04a4, 2026-11-15): a message is a command only when "/" is its first character and its first word names an Office command or one of the Thread's skill commands, an Office command first; any other message, a "/" elsewhere or an unknown first word included, is sent and logged as an ordinary message. Every Thread the user writes in offers them but a Stage Thread, where a "/" message stays ordinary. Typing "/" lists the Office commands first, then the skill commands, each labelled by kind with its description, narrowing as the user types.
  - **Office commands** never reach the engine, so they work the same on every engine (Claude Code's own commands are not passed through); each is an action the Thread already has. **/clear** chooses Start fresh for the next message, as the context control does ([2.5](2.5-context-policy.md)): the history stays on screen and the next message starts a new session with the Brief rebuilt from the record; with no session yet to start fresh from, the composer says so. **/help** lists the Office commands and the Thread's skill commands above the composer, with no request and no model call, and nothing is logged. There is no /stop: no action stops the turn of a person's Thread (a Task's Stop holds the Task and discards the Stage's edits), so a Stop for a person's Thread would be its own Task.
  - **Skill commands** ([2.6](2.6-skills.md)): "/<skill> [input]" runs that Skill in the session, as Claude Code's slash commands do. The Thread offers the library Skills the session that takes the next message has (its recorded ones when it continues or resumes, else those a new session would get), never a Project's Skills nor one whose name an Office command takes. It reaches the engine as a skill command, with no user-message heading and no Mentions or Open page around it; a new session's Brief still carries them and goes first, and the command follows. The log keeps the message as written and shows it as a skill command. One sent while the person is answering is refused, saying to send it once they finish, and isn't logged: a skill command is never a barge-in.
- **Only work starts a conversation:** an Agent needing the user opens a Decision on the Task; a person outside any Task writes in their own chat. No idle messages, no talk between Agents outside a Consultation, a call included.
- **Reading the Stage history:** every person's chat, Thread on a Task and Consultation, and every Agent Stage, reads a Task's Stage history with the Office tools, to diagnose its runs: each run in the order they ran, with its Stage, start and end, outcome, Handover note, Decisions and their answers, engine, model and tokens, its Project commands with their filtered output, and for an Agent Stage's run how many messages its Stage Thread logged during it, the earliest runs left out when their words alone would crowd the outputs out of the cap; or one run with each command's whole output, as the Stage history shows it, and for an Agent Stage's run its Stage Thread's messages from the run's start to its end (or to now while it runs), worded as `read_threads` words them. One run's answer is capped at 60 000 characters: the outputs and the messages share what its words leave, each getting at least half and the rest of what the other doesn't need; each output keeps its end, and cut messages say how many are left out and that `read_threads` reads on, with the Task, the run's times and the message to read on after. A Task with no runs gets a plain sentence: The Office has no Task of that id, or the Task hasn't started and the state it is in. It reads the Stage run records and The Office's log only, never a file under the Office data directory or an engine's transcript, and names a test run's moved files by their worktree paths (Task "Let Devops read a Task's stage run logs", 2026-11-09). An Agent Stage reads it so a retry, Review & fix or Verify that needs a command's whole output, or what an earlier Agent tried, doesn't repeat a failed approach: its Brief carries only the last failure's filtered output (Task "read_stage_history: tell an unknown Task from one not started, and include Agent Stage Threads", 2026-11-12).
- **Reading the Threads:** every person's chat, Thread on a Task and Consultation reads the Threads' messages with the Office tool `read_threads` (Task "Let the Caretaker read chat and Stage transcripts without reaching secrets", 2026-11-12): those logged in a range of dates or times, narrowed by a person (their Role), a Task, a Project (its Tasks' Threads and those of the Initiatives spanning it; chats have none) and a text, grouped by Thread with its subject (the Task's or Initiative's title, or whose chat it is), each message with its time, its speaker (the user, the person by name and Role, or The Office) and its text; tool activity as its one-line summary, Decisions as their questions with the answers and comments, or asked again with the general comment, and Proposals as their title with their state. The answer is capped at 60 000 characters: one long message keeps its start and its end, and a full answer says how many messages it leaves out and the message to read on after. A filter that names nothing, a range ending before it starts or one with no messages gets a plain sentence. It reads The Office's log alone, never a file or an engine's transcript, so nobody needs the database; it writes nothing. An Agent Stage doesn't read it: it reads Thread messages only through a run's Stage Thread, in the Stage history.
- **Chats only read** ([6](6-permissions-and-safety.md)): changes happen in a Task's Stages; a person's Thread on a Task only reads too. The one exception is a Caretaker Thread with Allow changes on.
- **What a Thread reads** (2026-11-12, the Initiative 1116efba; details settled with the Plan of Task 12e9ab91): a person's chat reads every Project's base branch, and a Thread on a Task reads its worktree, as before. The shaping and planning Threads on an Initiative (amended 2026-11-13) read its Initiative's branch in each Project it spans with a Pipeline there ([2.1](2.1-work.md#defaults), "An Initiative's Pipeline": one per Project, or None) and the base branch of every other Project, from the first session after Confirm; while shaping there is no branch yet, so they read the base branches ([5.5](5.5-git-and-isolation.md#defaults), "The Initiative's branch"). A Thread on one of its Tasks reads that Task's worktree, which already starts from the Initiative's branch. Stage sessions are unaffected. Once a branch is deleted, the Thread reads that Project's base branch, and its Brief says so. Mentioning the Initiative in another chat doesn't change what that chat reads.
- **What the user has seen in a chat:** The Office keeps, per chat Thread, the last message the user has seen, so it holds across a reload and in another browser. A message counts as seen once the Thread shows in the open chat drawer in a browser tab the user can see; an answer landing in a hidden tab waits for them to come back. A person has **answered** when a Thread has a message after the last one seen that isn't the user's own, a failed turn's line included, and they aren't answering any more; the Chat button and the person picker show it. Threads on a Task or an Initiative take no part: their unseen counts stay per page view.
- **Allow changes** (the Caretaker's chat, [2.2](2.2-people.md)): each Caretaker Thread starts read-only, as any chat; a refused edit or changing command tells the Agent to ask the user to Allow changes. The user turns the switch on in the Thread and confirms it; while on, the Caretaker can do everything on the workstation except touch secrets ([6](6-permissions-and-safety.md)), and the chat shows a banner, "Changes allowed in this Thread: the Caretaker can do anything on the workstation except read your secrets", with a Switch off button. It is kept per Thread; a new Thread starts with it off. Switching it on or off ends the Thread's running session, so the next message starts a fresh one under the new rules ([2.5](2.5-context-policy.md)), and is logged in the Thread as a line, "Changes allowed" or "Changes switched off". The fire alarm still holds every call. (the user's answers of 2026-11-03)
- **Who wrote it** ([2.10](2.10-users-and-signing-in.md)): every message a user writes in a Thread, a barge-in included, is shown and kept with that user's name, and the answer to a Decision with the user who gave it ("Answered by Ana"), whichever user's Decision it was: any user answers any Decision. The session gets each user message with who wrote it, so an Agent knows which user it is talking to.

## Defaults

Gaps no ticket settled, filled with the simplest choice consistent with the tickets and accepted by the user; each says when.

- **Thread titles** come from the first message and can be renamed (tier 1). A Thread The Office opens, which has no message of the user's first, is titled by The Office and shown with the person, as "Planning · Jan" (agreed with the user on 2026-10-25). (accepted 2026-10-24)
- **Agents wait on the user without blocking a tool call:** "open a Decision" and consult return at once and the Agent ends its turn; the answer arrives as the session's next message, continued through the Context policy: a Decision's whole form at once, submitted or asked again (amended by the Initiative "Multiquestion form", 2026-11-16). (added while slicing tier 1, [24](../../.scratch/the-office/issues/24-slice-tier-1.md), accepted 2026-10-24)
- **A Decision belongs to the asking Agent's Thread,** not a Thread of its own ([2.4](2.4-conversations.md)): a Thread is one engine session, and the answer goes into the asking session, as the click-through shows it. (added while building tier 1, accepted 2026-10-25; its card moved to Needs you on the Task page, the user's answer of 2026-11-04)
- **The Decision on Stages waiting for a Stand-in Engine** (Task "Stand-in choice card", 2026-11-18): "Decision: switch Stages to a Stand-in Engine" is The Office's own Decision, and unlike a Decision of an Agent's Thread it is Office-wide, not in one Thread: one card for every Stage waiting for the user's choice ([2.3](2.3-pipelines.md#defaults), "A refused turn is no failure"; [5.4](5.4-the-engine.md#defaults), "Stand-in Engines"). It is answered Stage by Stage, with Switch now on a row, and Switch all now with two or more rows, not once; it has no table and closes on its own, when the last Stage has gone on, been resumed, stopped or dropped. It shows in Needs you on Now and narrowed on that Task's page ([2.7](2.7-notifications.md#defaults)).
- **A turn refused for the usage window** (Task 3de35a58, 2026-11-13): in every Thread on a Claude Code engine or a Codex engine on a ChatGPT plan (a chat, a Consultation, a planning Thread, a Stage Thread) a turn the engine refuses because a usage window is used up is logged as its own line, "Claude Code's 5-hour window is used up until 14:00", naming the engine, the window and its reset time, shown as a notice, not as a failure. A chat or a Consultation isn't resumed by itself at the reset: the user writes again. Only a Stage Thread goes on on a Stand-in Engine instead ([5.4](5.4-the-engine.md), "A running Stage switches"), and it logs a notice line for the switch in the same words as the Stage history, "Claude Code's 5-hour window was used up until 14:00, so the Stage went on on Claude Code 2"; a chat, a Consultation and a planning Thread keep the line above.
- **After a restart** (Task 5e761e3a, 2026-11-14): a Thread left answering when The Office stopped waits for the user again, "The Office stopped while this was being answered.", and its background Sub-agents are Stopped, "Ended when The Office restarted" ([2.9](2.9-sub-agents-and-processes.md)). A planning Thread works on its own, often in auto mode, so the planner (whoever holds Plans) is woken in it again as The Office starts, in the same Thread, its session continued or replaced under the Context policy, when the restart cut it short (mid-turn, or with background Sub-agents running) and it still has a Task in Planning: a Task's own planning Thread whose Task is in Planning there, or an Initiative's planning Thread with one of its Tasks in Planning planned in it. The planner is told The Office restarted and cut their work short, that any Sub-agents they had running were stopped and their results lost, so they run again the ones they still need and carry on planning. Nothing is woken while the fire alarm sounds, nor for an Initiative the user paused: the user writes in the Thread to go on. A shaping Thread, a chat, a Consultation and a Stage Thread aren't woken: the user is in the conversation, and the failure line and the Sub-agents' "Ended when The Office restarted" tell them (a Stage goes on with its Task, [2.3](2.3-pipelines.md)).
