# 2.3.2 Flows

Covers: a Pipeline as a flow, routes, the walk, which route is followed, conditions, the Project-command condition and its file, when no route holds, on failure, when a Stage fails, validation, Proposals of routes, who is asked, the holder of Asked first on failures, a refused turn.

## A Pipeline is a flow

- Its Stages are the flow's nodes, joined by **routes**.
- A route leads from one Stage to another, or to the Pipeline's **End**, and may carry a **condition**; a route with none always holds.
- Several routes may leave a Stage, so paths part.
- Several may lead into one, so paths meet again (a **join**).
- Only one path runs at a time: the **walk** is at one Stage at a time, and as a Stage ends it follows one route out of it.
- A Stage that joins paths runs once each time the walk arrives, never waiting for another path.
- A walk starts at the Pipeline's first Stage and ends when it follows a route to End.
- A Stage with a route to End is a **final Stage**.
- Conditions are data that The Office weighs itself, with no model call and no Agent; the user sets them up in the Stage editor.
- A Stage the walk went past on another path is **Not taken** in that walk: it holds no run, and the Pipeline rail shows it so.

## The Pipeline's order

- The Stages keep an order, **the Pipeline's order**, in which every route leads forward, so routes alone never loop.
- "Earlier" and "later" mean in this order.
- Each Stage also keeps its place on the flow editor's canvas, a column and a row, which draws the flow and gives the Pipeline's order, never which route the walk follows.
- The order reads the columns left to right and a column's Stages top to bottom.
- A route always leads to a later column (or to End), never to a Stage in its own column.
- A Stage's on-failure target is in an earlier column.
- So a column holds only Stages on paths that part, and its top-to-bottom order is only for listing.
- A route that a move leaves leading to its own or an earlier column is refused by [Validation](#validation), naming it.
- The previous Stage a condition tests is the route's own Stage, the one the walk just left, whichever path it arrived by.
- A Project Pipeline's built flow takes its base Pipeline's places: an inserted Stage gets a column of its own just after (or before) its Stage's column, on its row, the later columns moving right by one ([its design](../design/pipeline-flow.html)).

## Which route the walk follows

- The routes out of a Stage are in an order the user sets, and the walk follows the first whose condition holds.
- A route with no condition, which always holds, therefore goes last ("otherwise"): a route after it is refused, as it could never be followed.
- At most one route leads from a Stage to any one place: two cases that lead there are one route whose condition joins them with Any of.
- The routes are weighed:
  - as the Stage ends done (a Gate's Continue, a Publish whose after publishing failure was continued past);
  - as the user skips it;
  - once a failure has nowhere else to go ([When a Stage fails](#when-a-stage-fails)).
- The routes of a Stage that needs a Decision are weighed only once the Decision is answered and the Stage has ended.

## Built-in conditions

- Each tests one Stage, either **the previous Stage** (the one the route leaves) or a Stage named by its key and shown by its name, which must be the route's own Stage or an earlier one, by that Stage's latest run:
  - it **ended Done**;
  - it **ended Failed** (a Script Stage that could not run or timed out among them);
  - it **was Skipped** (by the user's click, [Skipping](2.3.1-stages.md#skipping));
  - it **changed files** (its run left the Task's branch with changes against where the run started) or **changed no files**;
  - it **ran N or more times** (every run its Stage history lists for this Task, its latest included, N from 1).
- Or they test the Definition of Done: **all Reported met**, or **some not Reported met** (an Out of reach statement is not met).
- A named Stage that hasn't run on this Task holds none of the outcome or file tests and has run 0 times.
- Tests combine in groups: **All of** (AND) holds when every test or group in it holds, **Any of** (OR) when one does, and groups nest.
- The Office weighs them in the order given and stops once the result is settled, so a test after it doesn't run.

## The Project-command condition

- It is a test that names one of the Project's commands by its key (the key rules of [2.1](2.1-work.md), never `install` or `publish`), and holds when the command exits 0.
- It runs as a Script Stage's command does:
  - in the Task's worktree, through the same command runner and time limit;
  - in the run environment when it is On, after the install when its inputs changed;
  - with the Project's own variables, Secret ones included, and never The Office's GitHub token or ssh key.
- Like a test-kind command, it leaves the branch as it was.
- It gets the Task's earlier Stage runs as a JSON file whose path is in `OFFICE_STAGE_RUNS_FILE`, written outside the worktree where the command can read it (in the run environment, inside it).
- Any other exit means the test doesn't hold.
- A command that can't be weighed (the key the Project lacks, a blank line, the time limit reached, or the run environment can't start) doesn't count as not holding: the walk stops as when no route holds, the Decision saying why.
- Each run is kept on the run of the Stage the route leaves, with its command line, exit code and output, and shown in its Stage history.
- Its key counts among the commands the Pipeline runs ([A Pipeline needs the commands it runs](2.3.5-library.md#a-pipeline-needs-the-commands-it-runs)).

### The stage runs file

- Its shape is version 1, which later versions only add to:

  ```json
  {
    "version": 1,
    "task": { "id": "6b5af1e7-…", "title": "…", "project": "the-office" },
    "route": { "from": "tests", "to": "review" },
    "definitionOfDone": [
      { "number": 1, "statement": "…", "state": "reported-met" },
      { "number": 2, "statement": "…", "state": "out-of-reach", "why": "…" },
      { "number": 3, "statement": "…", "state": "not-met" }
    ],
    "stageRuns": [
      {
        "stage": "implement",
        "name": "Implement",
        "kind": "agent",
        "run": 1,
        "startedAt": "2026-11-17T10:00:00.000Z",
        "endedAt": "2026-11-17T10:40:00.000Z",
        "outcome": "done",
        "changedFiles": ["docs/spec/2.3-pipelines.md"],
        "handoverNote": "…",
        "error": null,
        "command": null
      },
      {
        "stage": "tests",
        "name": "Tests",
        "kind": "script",
        "run": 1,
        "startedAt": "2026-11-17T10:41:00.000Z",
        "endedAt": "2026-11-17T10:49:00.000Z",
        "outcome": "failed",
        "changedFiles": [],
        "handoverNote": null,
        "error": "…",
        "command": { "key": "test", "exitCode": 1 }
      }
    ]
  }
  ```

- `route.to` is a Stage's key, or `null` for End.
- `stageRuns` holds every run of the Task that ended, Resolve's Stages' among them, in the order they started, the run of the Stage the route leaves last.
- `kind` is `agent`, `script` (Publish's runs too) or `gate`.
- `run` numbers the Stage's runs from 1, as its Stage history does.
- `outcome` is `done`, `skipped`, `failed`, `needs-decision` or `held` (a run a Pause or the usage window held, [A refused turn is no failure](#a-refused-turn-is-no-failure)).
- `changedFiles` lists the paths the run changed in the Task's branch.
- `handoverNote` is the Agent's, else `null`.
- `error` is a failed run's.
- `command` is a Script Stage's key and exit code, the exit code `null` when the command didn't run.

## When no route holds

- It is when every route out of a Stage carries a condition and none holds.
- The walk stops before going on, using no round.
- A Decision is put to the user directly, not the CTO first: a form of one choice.
  - The options: each route out of the Stage, by where it leads ("Go on to Review"), to follow anyway, or drop the Task.
  - Words of their own, the question's comment with no option picked, are kept for the Stage the walk goes on to, as a Gate's notes are.
- The Stage editor warns about a Stage whose routes all carry a condition, but doesn't refuse it.

## On failure

- "On failure go back to Stage X, at most N times" is a Stage setting, apart from routes, so a simple Pipeline stays simple.
- X must be earlier, and a path of routes must lead from X to the Stage.
- It is the only way back: going back, the walk runs X again and goes on from it by its routes, every condition weighed afresh, so the path may differ from the last time.
- It covers test-fix rounds, review-fix rounds and repair after a failed Script Stage (a failed publish or test run hands to an Agent Stage with the error).
- One exception: when Publish shipped the work but its after publishing line failed, the failure never goes back through "on failure go back to Stage X" and uses no round.
  - It is escalated straight away, first to the holder of Asked first when a Stage runs out of tries, then to the user.

## When a Stage fails

- Its on-failure loop goes first, while it has rounds left.
- Then a route counts only if its condition says the Stage ended Failed: the previous Stage's "ended Failed" test on its own or within an All of group at its top.
  - A route with no condition or any other never carries a failure on.
  - The walk follows the first such route that holds.
- With none, the failure goes to who is asked ([Who is asked](#who-is-asked)).
- When they continue with the issues, the Stage's routes are weighed as usual, its outcome staying Failed.

## Who is asked

- Budget limits always ask the user.
- A round limit or a Stage failing with no retries left goes first to the holder of Asked first when a Stage runs out of tries, with Consultant on.
  - They may send the Task back for one more round with guidance, or pass it on.
  - Else it goes to the user.
- Hard switches follow their value.
- More cases: [The holder of Asked first on failures](#the-holder-of-asked-first-on-failures).

## Validation

- The Stage editor and the [Proposals](#route-and-condition-proposals) check a flow by these rules, and Save (or Apply) is refused, naming the Stage and the rule, while one fails.
- **No unreachable Stage**: a path of routes, whatever their conditions, leads from the first Stage to every Stage.
- **A route out of every non-final Stage**: every Stage has at least one route out, a final Stage's to End; a Stage left with none is refused rather than read as an end.
- **Cycles only through on-failure loops**: every route leads to a later Stage or to End, a route back being refused with the on-failure setting named as the way back.
- Also refused:
  - a route after one with no condition;
  - two routes from one Stage to one place;
  - a condition naming a Stage that isn't the route's own or an earlier one;
  - a Project-command condition naming `install`, `publish` or a malformed key.
- A Stage whose routes all carry a condition is warned about ([When no route holds](#when-no-route-holds)).
- The Library's other flags stay as they are ([Library](2.3.5-library.md#library)).
- Going back by a Gate's Send back or the Definition of Done check's one more round is no route and no cycle.

## Route and condition Proposals

- Agents propose route and condition changes the same way they propose Stage changes, and nobody but the user applies them.
- Devops' Proposal of a library Pipeline's new Stages ([The library editor](2.3.5-library.md#the-library-editor)) is a Proposal of its new flow: its Stages and their routes with their conditions, such as "run Review only when Tests changed files or ended Failed, otherwise Publish".
  - Devops is the holder of Onboards and repairs Projects.
- A Proposal of a Project Pipeline carries Stage changes that change routes too ([Project Pipelines](2.3.5-library.md#project-pipelines)).
- The Proposal card shows each route as it was and as proposed, its condition in plain words.
- The user applies it, all or nothing, or declines it, keeping the Pipeline as it is.
- It is refused once any of those values changed since, and checked by the Validation rules above and the editor's own.
- How the card and the editor look is [their design](../design/pipeline-flow.html).

## Defaults

### The holder of Asked first on failures

- A Stage failing with no retries left, its loop's rounds used up or not, is put to the holder of Asked first when a Stage runs out of tries (called the CTO below) when that duty is held by a Role with Consultant on, else to the user.
- It applies to a Script or Publish Stage as well as an Agent one.
- It is The Office's Decision in a Consultation on the Task: a form of one choice, with no Ask me again ([2.4](2.4-conversations.md)).
- The CTO answers in their own words, the question's comment with no option picked, which send the Task back for one round with their guidance, or passes it on to the user.
- The options (more rounds, continue with the issues, drop) stay the user's, who may answer in the CTO's place.
- A round's guidance is the answer's words, the question's comment and the general comment, and names who gave them: the CTO, or the user, an answer given for the user at their request counting as the user's.
- A Stage the CTO sent back once in a walk goes to the user when it fails again.
- These ask the user directly:
  - the Definition of Done not reported met before Publish (or at the end of a Pipeline without one);
  - the third restart in a row during a Stage ([2.4](2.4-conversations.md));
  - a conflict at Publish the Agent gave up on;
  - budget limits.

### A refused turn is no failure

- A Stage whose turn, its first or its correction, is refused because its engine's usage window is used up doesn't fail.
- Its run ends held, as a Pause holds it ([2.1](2.1.5-planning-and-start.md#a-pause-by-the-usage-window), "A pause by the usage window").
- It isn't counted against "on failure go back to Stage X, at most N times", no CTO Consultation opens and no "failed" Outcome is raised.
- The Stage history records the run as held by the usage window.
- A user's Stop still outranks it.
- **A Stand-in Engine takes the Stage on first:**
  - when a Stand-in Engine of the same engine type has room and can carry the session, the Stage goes on in the same run on it, which stays Running, and the run is held only when none has ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#a-running-stage-switches));
  - a stand-in of another engine type never takes a running Stage, as its context would be lost, and an engine override has no stand-ins at all ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#a-forced-engine-has-no-stand-ins));
  - the Stage history shows the switch, "Claude Code's 5-hour window was used up until 14:00, so the Stage went on on Claude Code 2";
  - a Pause, Stop or the fire alarm asked before the refusal holds the run with no switch;
  - a session over the context size set beside the list isn't switched: the Stage is held and marked as waiting for the user's choice to go on on the stand-in or at the reset.
- **The choice is one card:**
  - It is The Office's own Decision, "Decision: switch Stages to a Stand-in Engine" ([2.4](2.4.2-decisions.md#the-decision-on-stages-waiting-for-a-stand-in-engine), "The Decision on Stages waiting for a Stand-in Engine").
  - It lists every such Stage with its Task, Stage, context size, the Engine that ran out with its reset, and the Stand-in Engine it would move to now (the first of the same engine type with room, picked again on every read; "No Stand-in Engine has room now" otherwise).
  - Switch now, on a row, rechecks that the Stage still waits, moves the idle session to the first Stand-in Engine of the same engine type with room, records the stand-in on the Task and, on the held Stage run, the switch with who chose it, and resumes the Task.
  - The Task goes on in its session on the stand-in with the same model and settings, later Stages following.
  - The Stage's Brief says "It goes on on Claude Code 2, as the user Ann Lee chose", and the Stage history line ends ", as the user Ann Lee chose."
  - Each Stage is worked on its own, under the lock Work's automatic resume takes too, and one failing never blocks the others.
  - With none having room, the Stage stays paused until the reset and the card says why beside it.
  - If the move fails, the Thread stays on its own Engine and the Stage paused.
  - If resuming fails after the move, nothing is undone: the Task stays Paused, leaves the card, and the user is told the session is on the stand-in and needs Resume.
  - Stages not switched go on on their own Engine at the reset.
