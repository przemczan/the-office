# 5.4.7 The Gemini CLI engine

Covers: the Gemini CLI engine, its sign-in by API key, the headless transport, the BeforeTool hook, Office tools and MCP servers, answers held to a schema, skills, usage, capabilities.

## Defaults

### The Gemini CLI engine

- It is checked by the [engine check](../engine-check.md#gemini-cli)'s `gemini.*` runs; on Linux they are recorded, and the Windows run is pending.
- A **Gemini CLI** engine in Settings › Engines is one Gemini API key from Google AI Studio.
- Its sessions run the pinned `@google/gemini-cli`'s JS entry (`bundle/gemini.js`) with Node, so no `.cmd` shim stands between on Windows.
- Its folder, `<office-data>/engines/<engine id>/`, is the CLI's home (`GEMINI_CLI_HOME`), where the CLI keeps each session's chat under `.gemini/`.
- So a session resumes only on the engine and in the working folder that started it: `carrySession` is no.
- A Gemini CLI engine can take any Role, an Agent Stage's included.
- Settings › Engines lists it as [5.4.5](5.4.5-engines-and-cascade.md#a-gemini-cli-engine) says: its models, its folder and its key there.

### Gemini CLI: sign-in

- The key is pasted in Settings › Engines, kept in the database, and given to the CLI only as `GEMINI_API_KEY` in its environment, never in a file.
- The key is kept from the model's shell commands, which otherwise see the CLI's environment; the adapter's check confirms it.
- Login with Google isn't offered: Google refuses the CLI for personal Gemini Code Assist accounts ("no longer supported for Gemini Code Assist for individuals").
- A Workspace or Code Assist Standard or Enterprise account, with its Cloud project, waits for a check of its own.
- No browser is opened: the CLI runs with `NO_BROWSER`.

### Gemini CLI: the headless transport

- One `gemini --output-format stream-json --approval-mode yolo` process per turn: the first with `--session-id`, each later one with `--resume <id>`.
- Stop ends the turn's process; the next turn resumes the session.
- ACP (`gemini --acp`) isn't used: over ACP the CLI calls no `BeforeTool` hook, and its permission request carries no arguments and can give the model no reason.
- The settings in the home: folder trust off, so the hook, skills and MCP servers load; no telemetry, usage statistics, auto update, checkpointing, auto memory or chat retention sweep.
- `tools.core` names the core tools (`activate_skill`, `glob`, `grep_search`, `list_directory`, `read_file`, `replace`, `run_shell_command`, `write_file`) and `mcp_<server>_*` for each MCP server, as headless the CLI hides any tool the list leaves out, MCP tools included.
- No variable of the user's `GEMINI*` or `GOOGLE*` reaches the CLI.

### Gemini CLI: the Office rules through the BeforeTool hook

- A `BeforeTool` command hook judges every call, built-in, MCP and Office tool alike, by its name and arguments, before it runs ([6](6-permissions-and-safety.md)).
- A refusal is `deny` with the rules' reason: the call fails without running, the model reads the reason, and the turn goes on.
- The hook reaches the service on a local socket (a named pipe on Windows), never a TCP port, behind a token made per session.
- It refuses (exit 2) when it can't ask the service.
- It also refuses when its own deadline passes, set shorter than the CLI's hook timeout, since the CLI lets a call run when a hook times out.
- The shell tool's background mode is refused, as a background command outlives Stop.

### Gemini CLI: Office tools and MCP servers

- Each session's Office tools come from a stdio MCP server the CLI starts as a child, which relays each call to the service the same way as the hook; never an HTTP endpoint on localhost.
- The Role's MCP servers ([MCP servers for Agents](5.4.1-engine-kinds.md#mcp-servers-for-agents)) are in the session's settings, each value as `$NAME` from the CLI's environment, so no value is written to a file.
- Their values are kept from the model's shell commands as the key is.

### Gemini CLI: answers held to a schema

- The CLI has no schema option.
- An answer held to a schema comes through a `StructuredOutput` Office tool whose input schema is the answer's, checked when it arrives, as on the OpenAI-compatible API engine.

### Gemini CLI: skills and instructions

- A session's skills are written to its home's `.gemini/skills/` ([5.6](5.6-skills-per-session.md)).
- The repository's own `.gemini/skills/` and `.agents/skills/` load beside them.
- The repository's `GEMINI.md` loads as the Project's instructions; none from above the repository.

### Gemini CLI: usage

- Tokens come from the turn's `result` event (`stats`).
- Cost is priced by Model prices, one per engine and model, as on the OpenAI-compatible API engines; with no price set it shows "no cost".
- It has no usage windows, so no Window caps and no readings of the usage windows.
- A used-up quota is a refused turn showing Google's 429 text, with its metric and when to retry.

### Gemini CLI: capabilities as the engine check showed them

- `interrupt` yes: ending the turn's process stops its command, and the next turn answers.
- `resume` yes: `--resume <id>` in the same home and folder keeps the history.
- `bargeIn` no: a headless turn takes no input; a message sent during a turn waits for its end.
- `contextUsage` yes, as each turn's tokens; the context's size isn't given.
- `officeTools` yes.
- `outputSchema` yes, through the `StructuredOutput` Office tool.
- `languageServers` no: there is no language-server tool.
- `usageWindows` no.
- `carrySession` no.
- Sessions start no Sub-agents: `tools.core` leaves the CLI's agents out.
