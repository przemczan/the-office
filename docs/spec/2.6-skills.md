# 2.6 Skills

Covers: the library, adding a skill, Project skills, what a session gets, skill commands, skill uses, versions and updates, frontmatter.

## The library

- It is Office-wide (Settings → Skills): one folder with each skill once in its own subfolder.
- The database holds a record per skill: name, description, source, version, enabled, files hash.
- The database also holds the Role → Skill mapping and an "everyone" flag.

## Adding a skill

- Install from a source (an install, so Devops does it and the user confirms).
- Upload a `.md` or a zipped folder.
- Write one in place.
- Every new skill arrives off; the user reviews its files before turning it on.
- Pinned versions update by Proposal.
- An Agent writes, installs, updates, switches, assigns and deletes skills with the skill actions (`write_skill`, `install_skill`, `update_skill`, `change_skill_state`, `change_skill_everyone`, `change_skill_roles`, `delete_skill`), ruled by their Library › Skills Authority ([6 The library by Agents](6-permissions-and-safety.md#the-library-by-agents)); ruled Proposal, the call is a Proposal the user applies.

## Project skills

- They stay in the repository and apply unless the Project page turns them off, all of them or one by one.
- They are listed read-only, each with its own switch.

## What a session gets

- Its Role's skills, plus the "everyone" skills, plus the Project's that are on, and nothing else (mechanism in [5.6](5.6-skills-per-session.md)).
- Short descriptions matter: the listing gets about 1% of the context window.

## Skill commands

- The user runs one of the session's library skills by sending "/<skill> [input]" in a Thread ([2.4.4](2.4.4-messages.md#commands-in-the-message-box)), as Claude Code's slash commands do.
- An Office command's name wins over a skill of the same name.
- Assigning such a skill to a Role (its Role card or Settings › Skills) warns that it can't run as a skill command.

## Skill uses

- Each skill shows how many times it was used in the last 7 days, wherever skills are listed: Settings › Skills (the library) and the Project skills on a Project's page.

## Defaults

### Skills the user writes or uploads

- They also arrive off and are turned on after review, as every new skill does.
- For one's own text the review is one click.

### A skill's new version waits for review too

- A saved change that changes its files turns it back to off, waiting for review, as a new skill arrives; turning it on again is one click.
- Running sessions keep the version they started with.
- An applied update is the exception (see "An applied update is its review").

### Installing from a source

- A source is a git repository (`owner/repo` on GitHub, or a git URL).
- Devops lists the skills it holds and drafts one Proposal per skill.
- Applying a Proposal is the user's confirmation.
- The Office's own code fetches the skill at its pinned version into the library, off until reviewed.
- Devops never writes to the library.
- While nobody holds Onboards and repairs Projects, Install says installing needs its holder and links to Settings › Duties ([2.2](2.2-people.md#defaults), "Duties").

### The pinned version

- It is the source's newest tag when the skill is installed or updated.
- It is its default branch's newest commit when it has no tags.

### Updates are flagged, then proposed

- The Office checks each pinned source daily with `git ls-remote`, which spends no quota, and only marks the skill "Update available".
- The user asks Devops, who drafts the update Proposal with notes.

### An applied update is its review

- The update Proposal shows the files' diff.
- Applying it saves the skill's next version and leaves it on or off as it was.
- Running sessions keep the version they started with.

### A skill drafted as a Proposal

- Someone in a chat drafts a written skill.
- Applying the Proposal adds the skill off, reviewed as any new skill.

### A skill's description

- It may run to the engine's own limit of 1,536 characters and over several lines, for every skill however it is added, so published skills install as they are.
- Review flags one over 500 characters, a sixteenth of the listing at 200k.

### Editing a skill

- Editing is in its Review.
- Edit is for a written skill (the Write form, filled in).
- Upload a new version is for an uploaded one.

### A skill's frontmatter is read as the engine reads it

- A plain value holding `: `, which YAML refuses, is the text after the first `: `.
- Only what the engine can't read either is refused.

### A skill's frontmatter is flagged, not refused

- Review warns of each key that changes a session, as it does of scripts:
  - its own hooks;
  - model or effort;
  - tool rules;
  - a subagent;
  - `when_to_use`;
  - `disable-model-invocation`.

### A user-only skill

- A skill with `disable-model-invocation: true` isn't offered to the model; only the user runs it, as a skill command.
- Its session starts and resumes as any other.
- The start check leaves it out of what the model must list.
- Review says so instead of warning that it changes the session.

### Project skills turn off one by one

- A Project skill is on unless the Project turned it off, so one added later, or only on a Task's branch, starts on.
- The Project keeps the keys it turned off, as the engine matches them, never a list of what is on.
- "Use this Project's skills" stays as the switch for all of them: off, no session gets any, and each skill's own setting comes back with it.
- Two rows of one key are one skill to the engine and switch together.
- Running sessions keep the set they started with.

### A skill use

- It is one Skill tool call or skill command in any session (a Stage, a Thread, a Consultation), on any engine.
- It counts for the skill that session had under that name: a library skill by its record, and a Project skill per Project.
- A skill the session didn't get from The Office, such as an engine's built-in or a plugin skill, isn't counted.

### The count

- It is a skill's uses in the last 7 days, a rolling window and not since Monday.
