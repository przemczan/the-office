# 6. Permissions and safety

From [25](../../.scratch/the-office/issues/25-agent-permissions.md), amending [05](../../.scratch/the-office/issues/05-roles.md), [08](../../.scratch/the-office/issues/08-pipelines.md), [09](../../.scratch/the-office/issues/09-conversations.md).

- **Threat model:** the rules guard against an Agent's mistakes and keep the user in charge of what leaves the workstation; they do not contain a hostile Agent. Native Windows has no command sandbox, and Linux runs under the same rules so both behave alike; stronger containment (the engine's sandbox on Linux and WSL2, or a separate user) is not planned.
- **Two layers:**
  - **Office rules in code,** which no profile loosens: Agents never change git (read-only `status`, `diff`, `log`, `show` only, every Stage; the one exception is the Caretaker with Allow changes on); the HEAD and branch check; worktree restore after tests; the enforced Hard switches; the secrets refusal; one `PreToolUse` hook that sees every call the engine's own input validation lets through, before any rule decides. The Office sets no path-scoped deny rule, which would refuse before the hook; validation refusals show only in `result.permission_denials` and are logged from there.
  - **A permission profile as data on the Role card:** read, edit, run, web. A Stage may narrow it, and which of the Project's commands it runs ([2.3](2.3-pipelines.md#defaults)), never widen it. Editable in tier 2.
- **Language servers run Project code, outside the hook:** an LSP call is judged as a read of its file, so each profile's read fence covers it, but the server it starts runs on its own: reading a Project may run its Gradle build scripts or tsconfig plugins, in read-only sessions too (a Planner's Thread, a chat). The hook sees the LSP call, never what the server does. The user accepted this under the threat model on 2026-11-07.
- **Hard switches:**

  | | Run installs | Publish outside the Pipeline | Change Roles |
  |---|---|---|---|
  | Developer | Consult Devops | Consult CTO | Never |
  | Reviewer, Planner | Consult Devops | Never | Never |
  | Devops | Allowed | Consult CTO | Never |
  | CTO | Consult Devops | Ask me | Never |
  | Office Manager | Never | Never | Ask me |
  | Caretaker (fixed) | Allowed | Allowed | Never |

  These are the presets' values, and Consult names a Role key, not a duty: a Role hired from a preset keeps them whoever holds which duty. A Hard switch may consult any hired Role, a preset's or one hired from scratch (amended 2026-11-13, [2.2](2.2-people.md#defaults), "Who holds a duty").

  - **Enforced by The Office:** change Roles (an Office tool) and git. **Followed by the Agent:** run installs and publish outside the Pipeline. The Office stays agnostic of each Project's stack, so the brief states them in plain words ("Before you install anything that changes the machine outside the worktree, consult Devops; adding or updating the Project's own dependencies is a code change") and the Agent asks through the consult tool first. The Role card marks which are enforced and which are followed.
  - A held call waits on a Consultation (Consult *person*) or a Decision (Ask me). Approvals by colleagues show on the Task, in the Stage log and as one line in Since you left; never a Notification. A Decision never grants "always"; widening permissions is a Role card change.
- **MCP tools:** each tool of a Role's MCP servers ([5.4](5.4-the-engine.md#defaults)) has its own setting in the Role card's permission profile, set like a Hard switch to Allowed, Consult a person, Ask me or Never, and starting at Consult the holder of Default Consultant for MCP tool hard switches, judged when the call is held, the user being asked while nobody holds it (amended 2026-11-13); a Stage may narrow it, never widen it. A held call waits as a Hard switch's does. Enforced by The Office: the hook judges every MCP tool call (the user, 2026-10-31).
- **Other refusals** are immediate, with a reason the Agent reads ("Not allowed for a Reviewer: editing files. Open a Decision if you need it."), logged on the Thread.
- **Default profiles:**

  | | Read | Edit | Run commands | Web |
  |---|---|---|---|---|
  | Planner (planning on a Task, chat) | The worktree; the base branches in chat | No (a language server may run Project code) | Read-only git | Search and fetch |
  | Developer (Implement, Review & fix) | The worktree | The worktree | Anything in the worktree except git changes; installs and publishing follow the switches | Search and fetch |
  | Reviewer (optional independent review) | The worktree | No | The Project's own commands and read-only git | Search and fetch |
  | Caretaker (fixed; with Allow changes on, else as a chat) | Anything but secrets | Anything but secrets | Anything, every git command included | Search and fetch |

  Everyone also reads their session's skills folder and the engine's output of their own background commands, and uses the Office tools.
  Every session, Agent Stages included, can read every record with the Office tools: Projects, people, Tasks, Ideas, Initiatives, the links between them and all their Attachments, each by what it holds (`read_attachment`, the user, 2026-11-10): a text file, a document among them, and a PDF's text by numbered lines, in slices, a search for a phrase, and a line too long for one answer read on from a character; an image as a picture on an engine that shows pictures (Claude Code), up to the size its answer passes, else in words saying why it isn't shown; any other file by its name, kind and size, saying it can't be read; a link by its address. A person's chat, Thread on a Task and Consultation, and every Agent Stage, also read a Task's Stage history, from its Stage run records and, for one Agent Stage's run, its Stage Thread's messages, from The Office's log alone ([2.4](2.4-conversations.md)). A person's chat, Thread on a Task and Consultation also read the Threads' messages with `read_threads`, from The Office's log alone; an Agent Stage doesn't. Writing tools stay specific to each session, to its own Task, Initiative or chat. The one exception is `answer_decision`: in a Thread the user talks to a person in, that person answers a Decision waiting on the user for them when the user asks, never an approval of a call past a Hard switch or of an MCP tool at Consult or Ask me, which stays the user's own click ([2.4](2.4-conversations.md)).
- **A Consultation works with its callee's own permissions, never the caller's** (Task c288eb09; the user, 2026-11-12: "the callee works with their own permissions, never the caller's, so a read-only Thread can't get a change made by calling someone"): its session is the Consultant's own, built from them alone: their Role card's permission profile, Hard switches and MCP tool settings, and their chat's tools (capture an Idea, create a Task, draft a skill and their Role's Proposals, and call while the chain allows it). It only reads, as its home does (a Task's worktree on a Task, every Project's base branch in a chat), with no `change_role`, no Allow changes and no write access, so all a call can set up is a record or a Proposal the user applies. A Stage that can write lends none of it to its callee.
- **Chats only read:** a chat session reads every Project's base branch (a Thread on an Initiative with a Pipeline reads its Initiative's branch in the Projects it spans instead: [2.4](2.4-conversations.md)), searches the web and uses the Office tools (read records, capture an Idea, open a Task); no edits, read-only commands only, though a language server its LSP calls start may run Project code. The one exception is a Caretaker Thread with Allow changes on ([2.4](2.4-conversations.md)).
- **The Caretaker with Allow changes on** works on the whole workstation: its working folder is the user's home folder; it reads and edits anywhere (The Office's data folder, `.git`, `.claude` and `.mcp.json` included) and runs any command, `git push` too. Only the secrets refusal still holds, for reads and changes alike, and the fire alarm still holds every call: it is the user's stop. With it off, the Caretaker is refused as any chat is (the user's answers of 2026-11-03).
- **Secrets:** the hook refuses reads, by file tools or in command text, of `~/.ssh`; the Claude credentials (`~/.claude/.credentials.json`, and each Claude Code engine's account folder in the Office data, `<office-data>/engines/`, tier 3; a token pasted for an engine is written there as the folder's credentials file, sits in no environment, and is refused to Agents as the folder is, the user's answer of 2026-11-02; the folder stays secret but for each engine's session transcripts, `<office-data>/engines/<id>/projects/`, which the Caretaker's Thread with Allow changes on reads: an allow-list, so the account files (`.credentials.json`, `.claude.json`, `settings.json`) and whatever else Claude Code keeps there stay refused, as do the engines' folder and an engine's folder named whole and a `..` path out of `projects/`, Task "Let the Caretaker read chat and Stage transcripts without reaching secrets", 2026-11-12); `~/.config/gh`; `~/.aws`; browser profiles (where each lives on Windows and on Linux is the platform layer's); the Office identity's folder, `<office-data>/identity/`, which holds its ssh key; and the database credentials (The Office's `.env`). The list is kept apart from The Office's own files: every session but the Caretaker's with Allow changes on is refused The Office's own data as well, exactly as before; that one is refused the secrets only. A `.env` inside the worktree stays readable. The clones of Projects added by Repository URL, in `<office-data>/repositories/`, are left out of The Office's own data, so a cloned Project's folder reads as a path-added one's does (the user, 2026-11-01).
- **Secret variables** ([spec 5.5](5.5-git-and-isolation.md)): a Project's Secret variables reach its commands, its Tasks' sessions and its run environments' install, never a command line, an image layer or the web. They are hidden as `[secret NAME]` in the output The Office keeps and shows and in a Thread's messages. This guards against mistakes, not a hostile Agent: an Agent can use a value, and one that prints it reads it in the tool's result.
- **Build rules:**
  - Runtime decisions (holding, refusing with a reason) are made in hooks: `permissionPrompts: 'none'` skips `canUseTool`, and refuses whatever would prompt, so the Office tools are allowed by rule.
  - Path decisions (secrets, protected paths, what lies outside the worktree) are made in the hook, never in path-scoped deny rules.
  - Refusals are logged from the hook's own decisions, `permission_denied` messages and `result.permission_denials`; the `PermissionDenied` hook is not relied on, since it fires for none of them.
  - Every shell rule has a PowerShell twin on Windows: a Bash rule does not reach the PowerShell tool (with the engine's default tool set a Bash deny rule alone would turn PowerShell off instead). On Linux the Bash rules apply alone.
  - The hook alone fences Read, Grep, Glob and LSP to the session's folders (the worktree, or the base branches in chat) and its skills folder, and lets a session read the engine's output files of its own background commands (the engine's temporary folder, then the working folder's name, the session id and `tasks`). `permissions.blockReadsOutsideWorkingDirectories` is off: under it the engine also judges every shell command and refuses, past the hook's allow, any it can't show reads only inside (a variable in braces, another folder named), with no approval surface to ask (the engine check's `permissions.read-fence-off`; the user's answer of 2026-10-31). Shell reads outside run wherever the profile allows the command, and are accepted under the threat model. Without the fence the engine loads the instruction files (`CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, `.claude/rules/`) of every folder above the session's as the Project's own, the user's `~/.claude/CLAUDE.md` among them when the Office data directory is under their home folder, so `claudeMdExcludes` names each of them; a Project's own instructions, inside the worktree, still load.
  - The Office ends a session's leftover processes (dev servers, watchers) when its Stage ends.
  - `.git`, `.claude` and `.mcp.json` are protected paths: the hook refuses Agents' writes there first (but the Caretaker's with Allow changes on), with a clear reason; the engine's own protection (it never auto-approves them, and its refusal reads like any other prompt refusal) stays as a backstop. It still refuses a Claude Code engine's Edit and Write there for the Caretaker too, who changes those paths by commands instead. The Office's own writes there go through Office code, not Agents.
  - `.devcontainer/`, the repository's run environment definition ([5.5](5.5-git-and-isolation.md)), is written only through The Office (Task e6d52ce4, 2026-11-10): the hook refuses Agents' Write and Edit there, with a reason naming `write_run_environment_definition`, the Office tool an Agent Stage of a Role with the Run environment capability gets ([2.2](2.2-people.md)). The tool takes devcontainer.json and its compose files whole, checks them as The Office reads the definition, and writes them into the Task's worktree only when it is valid; otherwise it writes nothing and answers every problem found. Chats, Planning Threads and Consultations never get it. No allow rule lifts the engine's own protection of `.devcontainer/`, which refuses a Write there past a hook `allow` (the engine check's `permissions.devcontainer`) and stays as the backstop on every other session.
