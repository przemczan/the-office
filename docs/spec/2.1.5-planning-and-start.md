# 2.1.5 Planning and Start

Covers: Plan and Definition of Done, the Kind and the Pipeline while planning, changing a Ready Task, starting Planning, Auto mode, Waiting on you while planning, the queue for Start, Start anyway past the usage caps, Start now past the limits, Overlaps, pause by the usage window, Usage estimates.

## Plan and Definition of Done

- **Plan** (how) and **Definition of Done** (what must be true) are separate first-class parts of the Task.
- They are written by the user, co-written with the Planner in a Thread on the Task, or given with the Task by whoever creates it with the `create_task` Office tool; the user confirms them.
- **Given with the Task:**
  - when it is already known how the Task will be done and what must be true, its creator gives both parts, or neither, as half of the pair helps nobody;
  - the Task lands in Backlog with both **Not confirmed**;
  - the user confirms each on the Task page and marks the Task Ready from Backlog without Planning, as for parts they wrote themselves ([Mark Ready](2.1.3-tasks.md#mark-ready));
  - nothing its creator gives is confirmed by them, and the Task's state changes name its creator, so they show who wrote the Plan;
  - Make a plan and Plan with… start from the given parts, for the Planner to rework rather than start over.
- **Save and Confirm are separate acts:**
  - until the Task starts the user edits a part with Save and Cancel;
  - Confirm, the user's only way to confirm, takes the part as it reads;
  - auto mode confirms on their behalf ([Auto mode](#auto-mode)).
- A Save that changes nothing changes nothing, the confirmation included.
- A changing Save leaves the part unconfirmed in Backlog, Planning and Ready alike, and a Task in Planning stays there.
- Since the Planner may not be the author, an unconfirmed part's badge reads **Not confirmed**.
- Whoever creates Tasks in a Thread may rewrite either part until the Task starts, with `change_task_plan` or `change_task_definition_of_done`, as a changing Save does: the part is Not confirmed ([Office actions on a Task](2.1.3-tasks.md#office-actions-on-a-task)).
- Ready's rules: [2.1.3](2.1.3-tasks.md#ready).

## The Kind and the Pipeline while planning

- The Planner proposes first, with `propose_pipeline`, the Pipeline the Project gives the Task's Kind ([2.1.1](2.1.1-projects.md#project-settings), "Default Pipeline per Kind"), unless the work needs another; its Brief names that Pipeline ([2.5](2.5-context-policy.md#the-brief)).
- The Planner of an Initiative's planning Thread does the same for each Task.
- In Backlog, Before Ready names it too: "Choose a Pipeline on the rail: <name> is the default for Bugs".
- When the Task isn't what its Kind says, the Planner changes it with `write_kind` ([Task kind](2.1.3-tasks.md#task-kind)).
- It sets a Bug's Caused by and Found in version with `write_bug_details`; a field left out stays as it is ([Bug details](2.1.3-tasks.md#bug-details)).
- Neither moves the Task, so a Ready Task stays Ready.

## Changing a Ready Task

- Ready needs both parts confirmed, so a changing Save on a **Ready** Task takes it out of the queue if it was queued and moves it back to **Planning**, in its planning Thread and auto mode, the changed part Not confirmed and the Task no longer marked planned.
  - The user confirms and marks it Ready again, or the Planner marks it planned and auto mode does.
- A Ready Task that was never in Planning (marked Ready from Backlog) has no planning Thread, so a changing Save moves it to **Backlog** instead.
- The editor says beside Save, while the Task is Ready, which of the two a change does and that a queued Task leaves the queue.
- The Planner may also change a Ready Task in its own planning Thread, but only when the user asks:
  - write_plan, write_definition_of_done or propose_pipeline that change something move it back to Planning in the same save, moved by the Planner;
  - mark_planned works as in Planning from there;
  - a write that changes nothing moves nothing, and Tags never move a Task.

## Two ways to start Planning

- Both move the Task to Planning.
- **Make a plan**, in the Planner's empty tab in Backlog and as the **Plan** button on a Backlog card on the board, starts the Planner at once from the title and the Description, and from the Plan and Definition of Done when the Task has them, with nothing more to write.
- **Plan with…**, in the Task's head, opens the Planning Thread and the Planner waits for the user's first message ([The Planner joins on the first message](#the-planner-joins-on-the-first-message)).
- The board's Plan has no room for the Auto mode switch, so it plans in the remembered auto mode, which its tooltip names.
- Make a plan and Plan with… are the user's click, or a person's call in Work › Moving work, ruled by their [Authority](6-permissions-and-safety.md#authority) ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).
- While nobody holds Plans, Make a plan and the board's Plan aren't offered, Plan with… lets the user write the parts alone, and the planning tab shows "Nobody holds Plans" with a link to Settings › Duties.
- On an Initiative: [Plan the Initiative](2.1.4-initiatives.md#plan-the-initiative).
- Shaping an Idea into a Task: [Plan as a Task with the Planner](2.1.2-ideas-and-attachments.md#plan-as-a-task-with-the-planner).

## Auto mode

- An **Auto mode** switch sits beside Make a plan in the Planner's tab.
- It starts at the remembered default, an Office setting that is off until first chosen; the choice made with Make a plan becomes the default.
- Plan with… always plans with auto mode off.
- The Task keeps the choice while it is in Planning, and its card and the Planner's tab read "Planning with …, in auto mode".
- In every planning Thread the Planner says it has finished with the `mark_planned` Office tool, once the Plan, the Definition of Done and the Pipeline are written and nothing is left to ask.
  - It is refused, with the reason, outside Planning, before the Plan and the Definition of Done are written, and while the Task has neither a Pipeline nor a proposed one.
  - It marks the Task planned until it next enters Planning.
- With auto mode off nothing else changes: the user confirms the parts and marks the Task Ready.
- With auto mode on and no Decision on the Task open, The Office:
  - confirms in one save whatever of the Plan and the Definition of Done isn't confirmed yet;
  - confirms the proposed Pipeline (with none proposed, a Task that has a Pipeline keeps it; one that has none can't be marked planned);
  - marks the Task Ready under Ready's rules;
  - records the move to Ready in the Task's state changes as made by auto mode, naming each part it confirmed.
- With a Decision open, `mark_planned` changes nothing and tells the Planner to wait: the user's answer comes as the Planner's next message, the Planner carries on, marks the Task planned again, and auto mode marks it Ready.

## Defaults

### Waiting on you while planning

- A Task in Planning with an open Decision stays in Planning and shows a Waiting on you badge.
- The Waiting on you state stays a side state of In progress.

### The Planner joins on the first message

- Moving a Task to Planning opens its planning Thread but starts no session.
- The Planner's first turn runs on the user's first message there, so a Plan the user writes alone costs no model call.
- This holds for Plan with…; Make a plan starts the Planner at once.

### A queue for Start

- Several Tasks may be in progress in one Project, up to its Project limit ([2.1.1](2.1.1-projects.md#project-limit)).
- When Start can't run a Task now, it puts the Task in one Office-wide queue, shown with its reason on the board and on Now. Start can't run a Task when:
- Taking a Task out of the queue and moving it up or to the top, like the board's order, are the user's click, or a person's call in Work › Moving work, ruled by their [Authority](6-permissions-and-safety.md#authority) ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).
  - a blocker isn't Done or Dropped yet;
  - its person is at their Task limit;
  - its Project already has as many started Tasks (In progress, Waiting on you or Paused) as its Project limit;
  - the Office-wide limit on running Tasks is reached;
  - a Window cap or Daily cap would be passed ([Usage estimates](#usage-estimates)).
- Every other reason (a vacant Role, and the like) refuses Start with the reason.
- Each reason has a short reason too, such as "Office-wide limit reached (3)" or "5-hour window cap (80%) · resets 14:30".
  - A board card's Queued mark shows the short reasons, each once, on hover, and its place and the full reasons on a press, with the Tasks it is queued behind as links.
  - The Task page, Now and Start show the full ones.
- On the board a queued Task sits in a Queued column of its own, between Ready and In progress, and stays Ready, so the Ready column holds only Tasks that wait for the user.
- A blocked Task offers only the queue, as it can't start anyway, and an Overlap it also has queues it behind those Tasks too.
- A queued Task starts by itself, oldest first, when every blocker is Done or Dropped, a desk, its Project and its person free up and its caps allow it.
  - Only a Project's own Tasks count against its Project limit, so a full Project never holds another Project's Task, and lowering the limit stops no started Task.
- The user can take a queued Task out of the queue or move it up, one place or to the top.
- While an engine's usage window is used up, Start and the queue also wait for every Task whose Stages spend on that engine, whatever its Window caps say:
  - the reason is "Claude Code's 5-hour window is used up until 14:00" (short reason "5-hour window used up · until 14:00"), naming the engine and the window;
  - the Task is released at the reset, and Tasks on other engines aren't held.
- **Stand-in Engine:** before a Window cap or a used-up window holds it, a Start hands the Task's Stages on that engine to a **Stand-in Engine** instead, from the list that applies: the Project's own when it uses one, else the Office's ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#stand-ins-at-start)).
  - It is the first in the list's order, of any engine type, that has every capability the Task's Stages need and has room for the Task's estimate moved onto it (its Window caps, its used-up windows and its Daily caps, with the estimates of the Tasks it already takes counted).
  - The Task then starts, and every Agent Stage of that run runs on the stand-in, each person working with their model and effort for its engine type ([5.4.5](5.4.5-engines-and-cascade.md#the-model-and-effort-cascade)).
  - It queues only when no stand-in has room, with the added reason "No Stand-in Engine has room either: Personal: 5-hour window cap (80%) · resets 14:30." (short reason "No stand-in with room"), and is released when the cascade's engine or any stand-in frees.
  - A Daily cap never hands a Task on, as it is a spending limit, not a used-up subscription: it queues, as does a cap that resets within the prompt cache's hour, which starts on the cascade's engine.
  - With no stand-in in the list that applies, the reasons name none.
  - A Task with an engine override gets no stand-in: it waits in the queue for the reset, with the reason "<engine> is set for this Task · resets 14:30" ("… for its Initiative" when the Initiative's override gives it) ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#a-forced-engine-has-no-stand-ins)).
  - Every Start and every release of the queue tries the cascade's engine first, so new work goes back to an engine once its window resets.
  - The Task page marks a Task started on a stand-in ("On a Stand-in Engine: Personal for Work", with why on hover), each Stage run's details show its engine with a "Stand-in for Work" mark and why, and the Live view names the engine each session runs on, "standing in for Work".

### Start anyway past the usage caps

- A queued Task held only by its usage (a Window cap, a Daily cap, a used-up window, "No Stand-in Engine has room either") offers **Start anyway**, on the Task page and in the board's Queued popover.
- Anything else holding it (a blocker, an Overlap it is queued behind, the Office-wide limit, its Project limit, its person's Task limit, the fire alarm, its Initiative's Pause, a scheduled update or restart) takes the offer away.
- It runs on the first engine, the cascade's then the Stand-in Engines of the list that applies in their order (none under an engine override), whose usage window isn't used up: a cap passed doesn't count, as the engine still takes turns, while a used-up window would refuse the first turn and pause the Task at once.
- While every such engine has a used-up window, Start anyway is disabled with why.
- It asks first, naming each cap it passes and the engines its Stages run on.
- It never queues: whatever holds the Task by then refuses it, with the reasons, and the Task stays in the queue.
- The Task leaves the queue, and its Usage estimate counts as usual against the caps for the Starts and the queue after it.

### Start now past the limits

- A Ready Task, queued or not, that the Office-wide limit or its Project limit holds offers **Start now** on the Task page.
- Anything else holding it (a blocker, an Overlap it is queued behind, its person's Task limit, a usage cap, the fire alarm, its Initiative's Pause, a scheduled update or restart, a refusal) disables it, with why.
- It asks first, naming each limit it passes, and each Overlap not yet answered, which it starts anyway past.
- A queued Task's Overlaps were answered as it joined the queue, so Start now doesn't ask about them again.
- It never queues: the Task starts at once, leaving the queue when it was in it, and counts as started for the limits of the Starts and the queue after it.

### Overlaps at Start

- The Planner's Plan lists the files and folders it expects to change.
- Start warns when a Task in progress in the same Project expects to change some of the same, and offers to start anyway or to queue the Task behind that one.
- A Task that overlaps several waits behind all of them, until each is Done or Dropped.
- Real conflicts are handled at Publish, by the Pipeline's conflict chain ([Conflicts in the flow](2.3.4-publish.md#conflicts-in-the-flow)).

### A pause by the usage window

- When a Claude Code engine, or a Codex engine on a ChatGPT plan, refuses a Stage's turn because one of its account's usage windows is used up (its 5-hour window, its weekly window, a model's weekly window, or any other window the engine reports as used up), the Task is paused by itself, as the user's own Pause pauses it:
  - the Stage is held where it is, its uncommitted edits are kept;
  - nothing counts as a failure, so no retry, correction or Consultation of the CTO is spent.
- The Task shows Paused with why and when it resumes: "Usage window used up · resumes 14:00", from the window's reset time, in the user's local time, on the board, the Task page and Now.
- At that time it resumes by itself, also after a restart of the service, and the Stage carries on in its own Thread:
  - the message the engine refused, the Stage's work or its correction, is sent again, with a line that the edits may be half-done, as the turn may have been cut off after some tool calls;
  - when the refused turn left no session to resume, the Stage starts a new one with its full brief.
- When the engine gives no reset time, the latest reading of that window's reset is used, and with none known the Task tries again after one hour.
- A turn refused again pauses it again until the next reset.
- It also resumes sooner, as soon as a reading of its engine's usage windows taken after the pause shows the engine free ([5.4](5.4-the-engine.md): they are read as the service starts and every 5 minutes, as well as on each rate-limit signal), so a window freed early, or still free after a restart, doesn't keep it waiting; a refusal the reading didn't show holds it until that refusal's reset.
- The user can still Resume, Stop or Drop it by hand; Resume clears the resume time.
- A Stage held because its session is over the context size set in Settings › Engines waits for the user's choice on the Stand-in choice card ([2.4](2.4.2-decisions.md#the-decision-on-stages-waiting-for-a-stand-in-engine), "The Decision on Stages waiting for a Stand-in Engine") and still resumes at the reset on its own Engine.
- The automatic resume and the card's Switch now work a Task under one lock, so only one of them resumes it.

### Usage estimates

- A Ready Task shows its **Usage estimate**: what its whole Pipeline is expected to use on the engine the engine cascade gives the Task ([5.4.5](5.4.5-engines-and-cascade.md#the-engine-cascade)).
  - It shows on its card, its page, in the Start flow and in the queue.
  - Measures are ticked in Settings › Office limits: any of tokens, the 5-hour window, the 7-day window and cost in dollars; none turns estimates off; tokens and the 5-hour window by default.
- It is the median of the last 20 done Tasks' Stage runs for the same Project and Pipeline, Stage by Stage, summed, once there are 3.
  - Below that: the Planner's token estimate in the Plan, its cost derived from the Office-wide dollars per token of the done Tasks.
  - With neither: "no estimate".
- A window's estimate is the tokens times the Office-wide window % per token, as `utilization` comes in whole percents and a Stage run never gets a like-with-like pair of readings.
  - The ratio is learnt per engine from successive readings of one Reading source ([5.4](5.4-the-engine.md)): a pair counts when the Office's tokens went up between them, and a window's part when it neither reset nor went down, pooled as the changes summed over the tokens.
  - The ratio mixes models.
- Cost is priced by the Model prices of Settings › Engines; a model with no price gives "no cost".
- Caps are per engine:
  - a **Window cap** on the 5-hour and the 7-day window, which only Claude Code engines and Codex engines on a ChatGPT plan have (a Codex engine on an API key has none); 90% by default;
  - a **Daily cap** on tokens and on dollars; off unless set; today as in [2.7](2.7-notifications.md).
- Start waits in the queue when a ticked measure's cap would be passed, the Task's estimates on the engines under one cap added up:
  - a window's use plus the estimates of Tasks started since its last reading plus this Task's;
  - a day's use plus what is left of the estimates of Tasks in progress plus this Task's.
- It is released when the cap resets, or started by the user past it ([Start anyway past the usage caps](#start-anyway-past-the-usage-caps)), and starts anyway when every exceeded cap resets within the prompt cache's hour ([5.4](5.4-the-engine.md)); the hour exception covers the Daily caps' midnight too.
- "No estimate" and "no cost" never hold a Start.
- A Task started on a Stand-in Engine counts its estimate on the stand-in, its windows by the stand-in's own window % per token, for the Starts and the queue after it.
- There are no per-Stage or Planning estimates.
- A window with no reading, or whose reset has passed, counts as unused.
