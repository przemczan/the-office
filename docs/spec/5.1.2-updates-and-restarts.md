# 5.1.2 Updates and restarts

Covers: updating The Office on each install kind, restarting The Office. Part of [5.1](5.1-shape.md#defaults).

## Defaults

### Updating The Office

- The Office updates itself, never by rebuilding itself while it runs, in the way its install allows, which Settings › Updates names with the version it runs.
- On Windows updating isn't offered (Linux only).
- **A checkout** (`npm start` from git) updates its own git checkout:
  - a daily check (the first at boot) and "Check for updates" in Settings › Updates fetch the checkout's upstream and list the commits it is behind, installing nothing;
  - Update is refused, with the reason, when the checkout has local changes, has diverged from its upstream or has none, or the service runs without its launcher;
  - in a test instance of The Office (`OFFICE_TEST_INSTANCE=true`, [2.12](2.12-test-instances.md#what-the-office-sets)) the launcher gives the service no update folder and acts on no request, so the service runs as without its launcher;
  - an Office release updates to released versions instead.
- **A release install** (a tarball unpacked into `releases/<version>` beside a `current` link, run by its launcher) and **a container install** (Docker Compose) check the GitHub Releases of the repository their `office-release.json` names:
  - daily and on "Check for updates";
  - they list each version newer than theirs with its notes, and leave out drafts, pre-releases and tags that aren't a version;
  - a failed read is the check's problem and installs nothing.
- For a release install the launcher:
  - downloads the CPU's tarball and its `.sha256` (and its `.sha256.sig` once a release key is pinned), within 15 minutes and at most 2 GiB;
  - refuses a signature that isn't the pinned release key's ([releasing.md](../releasing.md#signing-a-release)), or a checksum mismatch, without touching `current`;
  - unpacks it into `releases/<version>`, switches `current` and starts the new version;
  - when it doesn't answer `/api/health` within 5 minutes, switches `current` back and starts the previous version;
  - keeps the current, the previous and its own release and removes the rest.
- For a container install the service starts the Office updater, a short-lived container that:
  - pulls the new image;
  - sets `OFFICE_VERSION` in the compose folder's `.env`;
  - recreates only the `office` service and waits for it to be healthy, else puts the previous version back.
- When the updater ends while the service still runs, the update failed before replacing it; the service reports it and releases the hold with no restart.
- Update is refused, with what to do, for:
  - a release copy not started by its launcher from a `releases/` folder;
  - a release with no tarball for the CPU;
  - a container not started by Docker Compose (with the commands to update by hand);
  - no access to the Docker socket.
- Once the user schedules an Office update:
  - it is held in memory, so a restart cancels it;
  - new Starts join the queue with "An update is scheduled.";
  - each Task waits before its next Stage (a Gate isn't held);
  - Cancel releases both.
- The update waits for the busy work:
  - an Agent mid-turn in a Stage, a chat or a Consultation;
  - a Thread of any kind with a background Sub-agent still running, listed by its Thread, since the restart would stop it ([2.9](2.9-sub-agents-and-processes.md));
  - a Script Stage;
  - an Action's running Project command run, as a Script Stage ([2.15](2.15-actions.md#when-a-run-stops));
  - a Publish;
  - a clone or an environment check.
- It doesn't wait for a Task waiting on the user, a paused Task or an idle Thread with no Sub-agent running.
- Nor for a test instance Building, Installing or Running: the restart stops it, and the sweep at the next start marks it ([2.12](2.12-test-instances.md#when-an-instance-stops)).
- When nothing is busy the service writes the request:
  - a checkout's service stops gracefully and exits with code 75;
  - the launcher (`npm start`, under systemd) fast-forwards to the target commit, runs `npm ci` and the build, and starts the service again;
  - a failed fetch, install or build goes back to the previous commit and rebuilds it.
- Work that began while the request was written, such as a turn already starting, ends first: the service checks again and exits once nothing is busy.
- At its next start the service raises an Office Notification that it updated, or that the update failed at which step, with the log in Settings › Updates.
- A browser tab opened before the update still runs the web app it loaded; the service names the build of the web app it serves in every reply to the event stream's subscription, so once the tab reconnects to a new build its status strip says "The Office was updated" and offers **Reload the page** ([shell.md](screens/shell.md#office-messages-slot)).
- Such a tab reads what it still can: an answer or an event it can't read is read again from the service rather than ending the page, and an answer it can't read says so in plain words, asking for a reload, never tried again.
- How to run it: [docs/running-the-office.md](../running-the-office.md).
- A rollback puts back the code, never the database, so each release's migrations keep the previous release working.
- An update only ever moves to its checkout's upstream (normally `main`).
  - An Initiative's branch in The Office's own repository never reaches the running Office.
  - Its work does only once its Publishing Task has put it into `main` and the user updates ([5.5](5.5-git-and-isolation.md#defaults), "The Initiative's branch").

### Restarting The Office

- Settings › Updates has a Restart card, "Restart The Office", for a setting that applies only at The Office's next start.
  - Settings › Telemetry is such a setting; its card offers the same button beside "Applies the next time The Office starts."
- Restart is offered only where something starts The Office again once its service exits:
  - its launcher (a checkout under `npm start`, or a direct install), on Windows too;
  - for a container install, Docker's restart policy when it is `always`, `unless-stopped` or `on-failure`.
- Elsewhere Restart is off and says why: "Nothing here would start The Office again: … Restart it where it runs."
  - Elsewhere means `npm run dev`, the service run by hand, a test instance of The Office under its launcher, a release copy its launcher didn't start from a `releases/` folder, and a container with no such policy or out of Docker's reach.
- A scheduled Office restart holds work exactly as a scheduled Office update does, through the same hold:
  - new Starts join the queue with "A restart is scheduled.";
  - each Task waits before its next Stage, as for an update;
  - the restart waits for the same busy work.
- An Agent schedules or cancels an Office update or restart with the Office tools `schedule_office_update`, `cancel_office_update`, `schedule_office_restart` and `cancel_office_restart` (Operations › Updates and restarts, Ask me for Devops and the Office Manager, Never on every other preset), and checks for updates with `check_for_updates` (Operations › Checks, Allowed for the CTO, Devops and the Office Manager).
  - The tool's words say the update or restart waits for running work, this session's turn included, and that it ends every session.
  - They are refused in the same words as the user's, and a schedule or cancel answers 204 on the route as before.
- Settings › Updates shows "Restart scheduled" with what it waits for, and the status strip shows it.
- **Cancel** releases what it held, and is refused once the restart is under way ("The Office is restarting.").
- One update or restart is scheduled at a time: scheduling the other is refused with why.
- Like the update's, the schedule is kept in memory.
- When nothing is busy, the service exits with code 75.
  - Under the launcher it first writes `{ "kind": "restart" }` as the request, and the launcher starts the service again without updating or writing a result.
  - In a container the restart policy is read again first; when it no longer starts the container again, or Docker is out of reach, the restart stays scheduled, the log says why and the service doesn't exit.
- A restart reads none of the host's config files again: `office.env` (read by systemd) and a Compose install's `.env` still need the restart on the host.
