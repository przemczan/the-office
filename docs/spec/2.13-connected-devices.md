# 2.13 Connected devices

Covers: Connected device, its kinds and device key, one device to one Task, what it attaches to, the two ways to connect, the relay, the Office device helper and its start and stop, serial boards and what their port carries, the Devices section's notices, Connected device states, its lifecycle, what the run environment's image needs, the adb key, an Android phone over USB, what Agents see, who connects, the serial path, the round trip, the helper's wait, adb steps, adb reconnect, the adb key's size, a dropped relay socket, the browsers supported.

## Connected device

- A **Connected device** is a device the user connects to one Task's run environment, so that Task's commands reach it.
- Its kinds:
  - **Android phone over USB**;
  - **Serial board over USB**;
  - **Android phone over wireless debugging**.
- Its record holds:
  - its kind;
  - its name, as the device reports it;
  - its Task;
  - its state ([States](#states));
  - who connected it, and when;
  - once Disconnected, why, who when a user did, and when.
- Each kind's own details (what a Stage can do with it, its upload tools) are added by that kind's Tasks, following the rules on this page.
- It is never a signed-in device ([2.10](2.10-users-and-signing-in.md#signed-in-devices)), which is a browser a user signed in from.

## One device to one Task

- A device connects to one Task at a time.
- It is recognised by its **device key**, which the browser reports and each kind defines:
  - an Android phone over USB: its USB vendor, product and serial number;
  - a serial board over USB: its USB vendor and product, and an id the tab gives the port, as Web Serial reports no serial number (the system lets only one program open a port anyway);
  - an Android phone over wireless debugging: the phone's address.
- A device key is unique among the records not Disconnected.
- Connecting a device already connected to another Task is refused, naming that Task ([task-page.md](screens/task-page.md#devices)).
- The browser lets go of a device whose connect is refused, so other programs on the computer can open it.
- Once Disconnected, the same device can connect to any Task again, as a new record.

## What it attaches to

- A Task's run environment only ([5.5](5.5-git-and-isolation.md)), so a device needs the Project's Run environment On.
- Never a chat: chats run no commands ([6](6-permissions-and-safety.md#chats-only-read)).
- Never the workstation: a Task's run environment is the one place The Office runs a Project's commands kept apart from it.

## Two ways to connect

- **USB through the browser:**
  - WebUSB for an Android phone, Web Serial for a serial board;
  - in Chrome and Edge only ([Browsers supported](#browsers-supported));
  - the browser's own picker asks the user which device to connect;
  - the bytes travel through [the relay](#the-relay).
- **Android wireless debugging over the network:**
  - the user enters the phone's IP address, its port, its pairing port and its pairing code on the Task page;
  - adb in the run environment pairs with the phone and connects to it directly: no relay and no helper;
  - the run environment must reach the phone's network;
  - the pairing code is used once and never kept.

## The relay

- For a device over USB only.
- The bytes travel: browser ⇄ the signed-in WebSocket ⇄ the service ⇄ the Office device helper in the Task's run environment.
- The **Office device helper** is The Office's own program, which the service runs in the checks' service with `compose exec -i`, its standard input and output carrying the bytes.
- For an Android phone, the helper listens on `127.0.0.1` inside the container and adb connects to it, so `adb devices` lists the phone.
- For a serial board, the helper makes a pseudo-terminal at a stable path ([Serial boards](#serial-boards)).
- No port is published, so only that run environment reaches the device ([6](6-permissions-and-safety.md#connected-devices)).
- The helper runs as the checks' user, except in its serial mode, which runs as the container's root to make the path and hands the pseudo-terminal to the checks' user.

## Serial boards

- The Office is only a bridge: the Project's own upload and monitor commands (avrdude, arduino-cli, PlatformIO…) do the upload and read the output, seeing the board at its path as if it were plugged in.
- The helper's serial mode claims the lowest free `/dev/ttyACM<n>` as a link to its pseudo-terminal ([Serial path](#serial-path)), removing links left by a helper that ended, and the link is removed as it ends.
- The pseudo-terminal belongs to the checks' user, mode 0660, so the Project's commands open it without root.
- The browser opens the board with Web Serial and the helper's frames tell it what to do, in order with the bytes:
  - **baud rate:** a tool's baud rate (and stop bits) reaches the board before the bytes written after it; the browser reopens the port at the new rate and sets DTR and RTS again;
  - **a rate the board refuses:** the browser reopens the port at the rate it had, so the board stays reachable, and the tool's next baud rate tries again; when that reopen fails too, the device ends as error, with the error;
  - **DTR and RTS:** the port's open turns them off then on, and its last close turns them off, as a real ttyACM's do, which resets DTR-reset boards (Uno, Nano, Mega, ATmega boards with a serial bootloader);
  - **reset timing:** the reset and the tool's first bytes travel in order on one channel, so the round trip slows an upload but doesn't break the reset.
- What a pseudo-terminal can't carry:
  - a tool's own DTR/RTS changes: Linux's pseudo-terminal has no modem lines, and avrdude and pyserial carry on without them;
  - data bits and parity: the pseudo-terminal is always 8 bits, no parity;
  - a board that resets into a new USB device to upload (the 1200-baud touch of Leonardo and Micro);
  - esptool's own DTR/RTS sequence for its automatic bootloader entry; the planned fix, not built yet, is an RFC 2217 port (`rfc2217://127.0.0.1:<port>`) in the helper beside the pseudo-terminal, which stays for tools that take only a path.
- The helper pings the browser every 5 seconds and the service keeps the round trip ([The round trip](#the-round-trip)).

## Notices

- The Devices section says in words ([task-page.md](screens/task-page.md#devices)), and `read_task` in short words:
  - **slow round trip:** while the round trip is over 250 ms, uploads are slow;
  - **no answer after a reset:** a tool opened the port, wrote, and the board sent nothing back before the last close, so its bootloader may not wait for the round trip;
  - **1200-baud touch:** the port was closed at 1200 baud;
  - **esptool's sync unanswered:** esptool's SLIP SYNC request (`0xC0 0x00 0x08 …`) was written and its answer never came back, matched on the bytes, never on timing; once per connection;
  - **no upload tool:** neither avrdude nor arduino-cli is on the run environment's `PATH`; informational, as the Project may use another tool.
- The helper's latest notice and the round trip start again at each helper start.

## The helper's start and stop

- The helper starts when a device over USB connects, or when the run environment starts or comes back after a stop while one is connected.
- It ends when the device disconnects.
- **Connecting a device never starts the run environment:** a device connected while it is stopped stays Waiting for the run environment until work starts it.
  - The one exception: pairing over wireless debugging starts the Task's run environment, since the pairing code works once.
  - Reconnecting a paired phone never does, and the environment then stops when idle as usual.

## States

- **Connecting**: the browser or adb is reaching the device.
- **Connected**: commands in the Task's run environment reach it.
- **Waiting for the run environment**: the device is there, but the Task's run environment isn't running.
- **Disconnected**, with why:
  - **by a user**, naming them;
  - **tab closed**;
  - **Task ended**;
  - **device unplugged**;
  - **Run environment turned Off**;
  - **error**, with the error.
- A Disconnected record keeps why, who disconnected it when by a user, and when.
- A Disconnected record stays on the Task as its history; it never connects again.

## Lifecycle

- A Connected device belongs to the Task, not a Stage: it stays through Stage restarts and Stage ends.
- A device over USB lives only while the browser tab that connected it is open; closing the tab disconnects it as tab closed.
- When the run environment stops, the idle stop included, every device shows Waiting for the run environment.
- When it starts again, each comes back: a device over USB while its tab is still open, a phone over wireless debugging while it still answers.
- A device never keeps a run environment running and never holds a Run environments at once slot ([5.5](5.5-git-and-isolation.md#the-other-limits-of-run-environments)).
- The Task Done or Dropped disconnects every device of it, as Task ended.
- Turning the Project's Run environment Off disconnects every device of its Tasks, as Run environment turned Off.
- An Office restart ([5.1.2](5.1.2-updates-and-restarts.md#restarting-the-office)) drops every relay socket:
  - a device over USB ends as tab closed, and the user connects it again;
  - a phone over wireless debugging waits for the run environment and reconnects at its next start, or ends as device unplugged, saying "pair it again", when it doesn't answer.

## What the image needs

- The Office provides the Office device helper:
  - one self-contained static Linux executable, for x64 and arm64;
  - of the release's own version;
  - mounted read-only into the run environment ([5.5](5.5-git-and-isolation.md#the-office-device-helper-in-a-run-environment));
  - no runtime needed in the image.
- The Project's `.devcontainer/` provides adb and the upload tools, such as avrdude and arduino-cli, as part of its toolchain.
- When a tool a device needs is missing from the run environment, the Devices section names it, so the user can fix the definition.

## The adb key

- One adb key per Project, made by The Office.
- Kept in the database as Secret variables are ([5.5](5.5-git-and-isolation.md#secret-variables)); never sent to the web, logged or put in a Handover note.
- Written into the run environment's `~/.android` (mode 0600) at each start.
- Both Android kinds use it, so a phone allows it once per Project.
- An RSA key of 2048 bits ([The adb key's size](#the-adb-keys-size)).

## Android phone over USB

- The browser opens the phone with WebUSB and passes its ADB packets through the relay unchanged; it doesn't run ADB itself.
- The picker lists only phones with USB debugging on.
- Its device key is `usb:<vendor>:<product>:<serial number>`; a phone that reports no serial number is refused.
- The browser opens and claims the phone before the record is made, so a phone it can't open leaves no record:
  - a phone held by adb on the user's computer is refused with "The phone is in use by adb on this computer (Android Studio or adb). Run adb kill-server, then connect again.";
  - a phone the browser may not open is refused with the udev rule (Linux) or the WinUSB driver (Windows) it needs.
- `adb devices` in the run environment lists it as `127.0.0.1:<port>`, the helper's endpoint: its adb serial.
- The service runs adb in the run environment, as the checks' user, each time the helper is ready (the first connect and every run environment start):
  - checks that adb is there, else the device ends Disconnected as error, with "adb isn't in this Project's run environment. Add Android's platform-tools to .devcontainer, then connect again.";
  - writes the Project's adb key, and restarts a running adb server when the key changed;
  - runs `adb connect 127.0.0.1:<port>`, without waiting for the phone to allow it.
- When adb drops the connection while the phone is Connected (an Agent ran `adb kill-server`, say), the service connects it again ([adb reconnect](#adb-reconnect)).
- Disconnecting runs `adb disconnect` for its serial.
- The first time a Project's key reaches the phone, the phone asks to allow USB debugging; the Devices section says so until it does.

## What Agents see

- `read_task` lists the Task's Connected devices: kind, name, state, and where it is reached.
  - Where it is reached is the helper's endpoint while it is Connected: `127.0.0.1:<port>` for an Android phone over USB, which is also its adb serial, and the serial path (`/dev/ttyACM0`) for a serial board.
  - A serial board's line adds its baud rate, its round trip and its notices.
- A Stage's message names the devices Connected at its start.
- Each command run through `compose exec` gets `OFFICE_CONNECTED_DEVICES` set at that run, not at the container's start, so it is never stale.
  - It is a JSON array of `{id, kind, name, endpoint}` of the Connected devices, `[]` with none.
- It also gets `ANDROID_SERIAL` when exactly one Android phone is Connected and the Project's environment doesn't set it.

## Who connects

- Any signed-in user connects a device, from the Task page's Devices section ([task-page.md](screens/task-page.md#devices)).
- Any signed-in user sees every device of the Task and disconnects any of them.
- The record says who connected it.

## Defaults

### Serial path

- A serial board's pseudo-terminal is at `/dev/ttyACM0`, or the next free `/dev/ttyACM<n>` when that one is taken.

### The round trip

- The helper pings the browser every 5 seconds.
- A round trip over 250 ms shows the slow round trip notice.

### The helper's wait

- When the run environment starts, or a device's relay opens, the service waits at most 10 seconds for the helper to be ready.
- A device whose helper isn't ready by then ends as error.

### adb steps

- Each adb step the service runs in the run environment (the check, the key, connect, disconnect) is given at most 20 seconds.

### adb reconnect

- When adb drops an Android phone over USB, the service runs `adb connect` again after 2 seconds.
- At most once per 30 seconds per device.

### The adb key's size

- The Project's adb key is RSA, 2048 bits, named `office@<project>`.

### A dropped relay socket

- A dropped WebSocket ends the device over USB it carried as tab closed; the user connects it again.

### Browsers supported

- Connecting over USB works in Chrome and Edge, which have WebUSB and Web Serial.
- Pairing over wireless debugging works in any browser.
