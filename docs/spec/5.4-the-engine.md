# 5.4 The engine

- **An `AgentEngine` port, not Claude-shaped:** start a session with a brief, send a message with priority, interrupt, resume, read usage, the tool-permission hook; each adapter declares which capabilities it has and The Office degrades where one is missing. The engine and model a session runs on come from the engine cascade (Defaults below).
- **Engine kinds**, each engine one the user adds (Defaults below): **Claude Code**, one account, on the TypeScript Claude Agent SDK or, by a switch on the engine, `claude -p`; **Codex**, one OpenAI account, on the pinned `codex app-server`; **OpenAI-compatible API**, one API endpoint, on The Office's own agent loop. The scripted adapter replays recorded engine output for tests. One long-lived streaming `query()` per session on the Claude Code engines, one app-server process per session on the Codex engine.
- **Native features used:** message `priority` for barge-in (`next` between tool calls, `later` after the turn); `interrupt()` for Stop, the only way to stop a running command (`now` is not used: it ends the turn but leaves a running command to finish or run on in the background); resume by session id; the 1-hour prompt cache on the main conversation; in-process Office tools via `createSdkMcpServer()`; `rate_limit_event` and the experimental usage query for the 5-hour and 7-day windows (never the CLI's OAuth token), each reading keeps its **Reading source**, the usage endpoint's own answer (a session's first) or one the CLI builds from the last reply's rate-limit headers (the later ones, one per turn's rate-limit event), which round differently, so the Office-wide window % per token for usage estimates is learnt only from successive readings of one source, each counted pair kept so the ratio outlives a restart; cost in The Office is priced by the Model prices set per model in Settings → Engines (input, output, cache writes and cache reads per million tokens, for every engine's models; one per Claude model shared by every Claude Code engine, one per Codex model shared by every Codex engine, one per engine and model on the OpenAI-compatible API engines, a removed engine's kept so its history stays priced), never the engine's own `total_cost_usd`.
- **Engine features turned off:** claude.ai connectors (`disableClaudeAiConnectors`); the engine's built-in plugins (each set false in `enabledPlugins`); auto-memory (`autoMemoryEnabled` and `autoDreamEnabled` false), whose folder outside the worktree is shared by every worktree of a repository and written without a prompt. Memory is The Office's own (Shared memory). The built-in tool set is an explicit `tools` list, the same on both platforms (the engine's Windows default today and `LSP`, PowerShell on Windows only), since the engine's Linux default drops Grep and Glob for shell search.
- **Cache breakers to avoid mid-session:** changing model, effort, MCP servers (with tool search off) or the Claude Code version.
- **Versions are pinned** (the SDK bundles the binary; `@openai/codex` is pinned exactly) and bumped deliberately, re-checking what was read from the binary ([5.6](5.6-skills-per-session.md), [6](6-permissions-and-safety.md)) with the engine check ([engine-check.md](../engine-check.md)).

## Defaults

- **Office actions:** each action the user can take on a record (Task, Initiative, Idea, Project, Role, Skill…) is declared once, in the contracts, with its name, record, description, input, route and the duties that cover it. Both the HTTP route the web calls and the Agents' Office tool come from that declaration and call the owning module's one handler, so whether it is allowed is decided by the same domain rules for the user's click and the Agent's call, refused in the same words. A person gets the tools of the actions their held duties cover in every Thread the user talks to them in (their chat, their Thread on a Task, the planning Threads, an Initiative's Threads, a Consultation), never in an Agent Stage, which does its Stage's work only. Their Role's authority (decide alone, consult first, ask the user) and the Hard switches still say when they may use one without a Decision, as each tool's description reminds them. They are `add_dependency`, `remove_dependency`, `add_to_initiative` and `take_out_of_initiative`, covered by Shapes Initiatives and Plans; they change an active Initiative straight away, while the shaper's other tools (its outcome, a new Task, titles, Descriptions, its Pipeline) draft Proposals. Projects' first is `rerun_ci_run` (a failed or cancelled CI run runs again, all its jobs or only the failed ones), covered by Onboards Projects. Every new action on a record is made this way, never as a hand-written route plus a hand-written tool.
- **The `-p` fallback matches the Agent SDK adapter:** the Office tools reach its sessions through the binary's own stream, as the SDK does (an in-process MCP server answering the binary's `mcp_message` requests), and the Office rules through a hook that asks the service on `localhost`, so any Role can work with it. Not an MCP endpoint on `localhost`: over HTTP a tool's answer can overtake a barge-in message on the binary's input, which the engine check saw on Windows. The hook's token is made per session and reaches its Agent's commands, so it reaches nothing beyond its own session's hook, which judges by that session's rules; what it can't match, as the engine check finds, it declares missing. It is a switch on each Claude Code engine, off by default, every session on that engine running through it. It runs the pinned Claude Code binary the SDK bundles, with the same models, and has its own runs in the [engine check](../engine-check.md) on Windows and Linux.
- **The OpenAI-compatible API engine is The Office's own agent loop,** for local LLMs and any server on that API: the user lists the API endpoints in Settings → Engines (a name, the base URL, a key kept in the database and never sent back, empty for a local server, and the models with their context windows and whether each **Sees images**, off by default: on, the model gets a message's images as image parts; off, the message names each image and its Attachment id and says the model can't see pictures), and each API endpoint is an engine of its own, its models the engine's. Replies stream. The loop gives the model the built-in tools under the Claude Code engines' names and inputs (Read, Grep, Glob, Edit, Write, the shells, WebFetch, WebSearch, Skill), so the same Office rules judge every call before the loop runs it, and runs commands in the background as the SDK's sessions do (started, their output read, stopped; ended on Stop and when the session ends). WebSearch goes through a search endpoint set Office-wide behind a port, SearXNG's JSON API the only one built. It lists exactly the session's skills and loads them by name ([5.6](5.6-skills-per-session.md)), keeps the conversation under the session's folder in the Office data directory so it resumes, and reads its context usage for the Context policy ([2.5](2.5-context-policy.md)); it has no usage windows and reports no cost. Any Role may pick it; The Office refuses only what it declares it can't do.
- **MCP servers for Agents:** the user adds each MCP server to an Office-wide library in Settings → MCP servers, by a form or by pasting the server's JSON config: a local command (stdio: command, arguments, environment) or a remote URL (Streamable HTTP, with headers). A server declares its Server values (an environment variable or a header; plain or secret; required or not), each with an Office-wide value that a Project's page may override; a secret is kept in the database and never sent back. A server is off until the user reviews it (its command or URL, its values, and the tools it lists on a test connection), and changing it turns it off until reviewed again. A Role card assigns servers. A session starts with its Role's servers that are on, with its Project's values (the Office-wide values in chat), fixed for the session; a server missing a required value is left out, and the session's brief says so. Every engine runs them: the Claude Code engines through their own MCP config holding only the Office's servers (never a Project's `.mcp.json`), the OpenAI-compatible API engine through an MCP client in its loop, the Codex engine through the service's `office` MCP server (the Codex engine below). Every MCP tool is judged by the Office rules before it runs ([6](6-permissions-and-safety.md)).
- **Language servers for Agents:** every session on a Claude Code engine, whichever its Role, chats and the Planner too, has the `LSP` tool on the workstation's language servers: TypeScript, C and C++, Kotlin ([language-servers.md](../language-servers.md)). A session gets those its `PATH` finds as it starts, fixed for the session as its MCP servers are; one not found is left out, the session's brief says so, and it never stops a session starting. The servers reach the engine as a plugin of their own beside the skills folder, so a session with no skills still gets them and the skills start check ([5.6](5.6-skills-per-session.md)) stays exact. A server starts at the first LSP call or Edit on a file of its language, never with the session, and one stays out of a session that doesn't need it. Each LSP call is a read of its file under the Office rules ([6](6-permissions-and-safety.md)). The OpenAI-compatible API engine has no such tool and declares the capability missing.
- **The Codex engine** (checked by the [engine check](../engine-check.md#the-codex-app-server)'s `codex.*` runs on Linux): a **Codex** engine in Settings › Engines is one OpenAI account. Its sessions run the pinned `codex app-server`, one process per session speaking JSON-RPC over stdio, with `CODEX_HOME` its own folder, `<office-data>/engines/<engine id>/`, where Codex keeps the sign-in, its own state databases and each thread's history, so a session resumes only on the engine that started it; nothing else of the user's (`~/.codex`, `OPENAI_*` and `CODEX_*` variables) reaches it. Settings reach it only as `-c` overrides and `thread/start`'s parameters, never by editing the folder's `config.toml`.
  - **Sign-in:** "Sign in" runs the pinned binary's `codex login --device-auth` for that folder and shows its link and code, which sign in from any browser (ChatGPT, whose plan gives the usage windows); "Use an API key instead" takes an OpenAI API key, kept in the database and never sent back, and signs the folder in with it (`codex login --with-api-key`, the key on its input). "Sign out" is `codex logout`. The engine shows the sign-in kind and plan `account/read` gives, or that it is signed out.
  - **The Office rules through approval requests:** sessions run under the `untrusted` approval policy, the one under which every command, read-only ones included, and every file change comes to the client first (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`; under `on-request` none came). The adapter answers each from the Office rules ([6](6-permissions-and-safety.md)) as the hook does on the Claude Code engines. A refusal is `decline`: the item ends `declined`, nothing is written, and the model reads only that it was declined, as the answer carries no reason; the session's brief says that a declined call was refused by the Office rules. A command's request that carries a `reason` asks to run outside the sandbox, where an accepted command writes anywhere and reaches the network, so the rules decline it unless the Role's profile allows commands outside the worktree (`codex.sandbox`). Each Office tool and MCP tool call comes first as `mcpServer/elicitation/request` (`_meta.codex_approval_kind: "mcp_tool_call"`, with the tool's name and arguments), judged the same way; a declined one fails without reaching the server.
  - **Sandbox kept to the worktree:** threads start with `sandbox: workspace-write` and `cwd` the worktree, with `sandbox_workspace_write.exclude_slash_tmp`, `exclude_tmpdir_env_var` set and `network_access` off, so a command writes only in the worktree and has no network (on Linux it runs under the bundled bubblewrap; writes elsewhere fail with `EROFS`, a name lookup with `EAI_AGAIN`). The worktree's repository is named `untrusted` under `projects` in `thread/start`'s `config`, keyed by its main checkout as Codex keys it: otherwise a thread marks it trusted in the folder's `config.toml` and the Project's own `.codex/config.toml` joins the session's settings. Update checks and web search are off and history isn't persisted beside the threads.
  - **Office tools over MCP:** the service serves each session's Office tools and the Role's MCP servers' tools ([MCP servers for Agents](#defaults)) to it as an MCP server over Streamable HTTP on `127.0.0.1`, named `office` in `thread/start`'s `mcp_servers`, behind a bearer token made for the session and passed only as each server's `Authorization` header in `thread/start`'s and `thread/resume`'s `config` (`http_headers`), so it is on no command line and in no environment the Agent's commands inherit, and it reaches only that session's server.
  - **Stage answers held to the schema:** `turn/start`'s `outputSchema`, the app-server's form of `codex exec --output-schema`; the turn's last agent message is the answer.
  - **Usage windows** come from `account/rateLimits/read`, a Reading source of its own, refreshed by `account/rateLimits/updated` during a turn; each window gives `usedPercent`, its length (`windowDurationMins`) and `resetsAt`, and which windows there are follows the plan (on ChatGPT Free one 30-day window, limit `codex`). An API key has none. A turn refused for a used-up window ends `failed` with `codexErrorInfo: "usageLimitExceeded"`, which is **usage window used up** as on the Claude Code engines.
  - **Cost** is priced by Model prices, one per Codex model shared by every Codex engine, from `thread/tokenUsage/updated`: its input includes the cached input, priced as cache reads, and its output includes the reasoning.
  - **Capabilities as the engine check showed them:** `bargeIn` yes: `turn/steer` with the running turn's id joins the turn without stopping its command (`later` is held by the adapter until the turn ends); `interrupt` yes: `turn/interrupt` ends the turn as `interrupted` within seconds and the thread goes on, but a running command keeps running to its end, so on Stop the adapter also ends the session's app-server process, which ends the command, and the next message resumes the thread; `resume` yes: `thread/resume` in a new process continues the same thread with its turns, its input from the cache; `usageWindows` yes on a ChatGPT sign-in, no on an API key; `contextUsage` yes: `thread/tokenUsage/updated` gives the context window and the tokens in it; `officeTools` yes; `outputSchema` yes; `languageServers` no, as Codex has no LSP tool, and its sessions get none. A Codex engine can take any Role, an Agent Stage's included.
  - **Codex's own features kept out:** every app-server runs with Codex's features that bypass the Office rules or give the model tools The Office doesn't judge turned off by `-c` overrides: its hooks and memories, its apps and plugins, its own sub-agents, image generation and viewing pictures off the disk, browsers and computer use, skill search and installs, goals and tool suggestions; its bundled skills and its listing of skills are off too, so a session lists only its own skills through the `Skill` tool ([5.6](5.6-skills-per-session.md)). A Project's `CLAUDE.md` is read where it has no `AGENTS.md`. A Codex bump re-reads `codex features list` for new ones.
- **Engines are a list:** Settings › Engines lists the engines the user adds, each with a name, an id made from the name when added and kept on a rename, and a default model. A **Claude Code** engine is one account: its sessions run with `CLAUDE_CONFIG_DIR` set to its own folder, `<office-data>/engines/<engine id>/`, so its credentials and transcripts stay there and a session resumes only on the engine that started it; "Sign in" runs the pinned binary's `claude auth login --claudeai` for that folder and shows its sign-in page, which signs in from any browser and gives a code the user pastes into the engine; "Paste a token instead" takes a token the user made with `claude setup-token` (a year long, `sk-ant-oat01-…`) and writes it into that folder as its login, the credentials file the binary reads, in place of any login there, never sending it back, so the engine's sessions are signed in by it and it sits in no environment ([6](6-permissions-and-safety.md), Secrets); "Sign out" removes the folder's login, whether a Sign in or a token made it; the engine shows the email and plan `claude auth status` gives, that a pasted token signs it in, or that it is signed out; the `-p` fallback is its switch. An **OpenAI-compatible API** engine is one API endpoint. Caps, readings of the usage windows, their samples and each day's use are kept per engine ([2.1](2.1-work.md#defaults), "Usage estimates").
- **The engine cascade:** every level names an engine and one of its models, picking an engine filling in its default model; a session's comes from the most specific level set: the **Office default** (Settings › Engines), the **Project default** (the Project page's Engine block), the Office-wide **Role override** (the Role card), the Project's Role override (the Project page's Engine block). A Project's "Use for every Role" forces its default on every Role in it: the Office-wide Role overrides are skipped, its own still apply. Threads without a Project, onboarding a Project not yet added among them, use the Office levels only. Every session follows it: Threads, Stage runs, Consultations, the Planner, Devops, the Office Manager. A Stage has no model of its own ([2.3](2.3-pipelines.md)). Only a Role a Pipeline names needs more of its engine: an Agent Stage's Role in the Pipeline library, which counts outside any Project and in every Project, a Project Pipeline's built Stages counting too ([2.3](2.3-pipelines.md#defaults)), or in an open Task's own Stages, which counts in that Task's Project (a done or dropped Task's don't count). It needs Office tools and an answer held to the Stage result's schema (the `officeTools` and `outputSchema` capabilities); other Roles take any engine. A save at any level that would newly put such a Role on an engine lacking either, outside any Project or in one, is refused, naming the Roles and Projects; so are hiring back a person let go, whose Role override comes back with their card, and a preset hire. The other way round, adding or changing a Stage, in the library or in a Task's own Stages, so that it newly names a Role whose engine lacks either is refused the same way, weighed where that Stage counts. A Stage naming a duty counts the Role that holds it now ([2.3](2.3-pipelines.md#defaults), "A Stage names a Role or a duty"). Changing a duty's holder in Settings › Duties, or applying its Proposal, is checked as a rehire is: refused when it would newly put such a Role on an engine lacking either. A session whose engine changed starts its Thread fresh; a changed model alone resumes.
- **Stand-in Engines:** Settings › Engines holds one Office-wide ordered list of **Stand-in Engines**, saved engines that take over for each other when one runs out of its 5-hour or 7-day window, and beside it the context size in tokens above which a switch of a running Stage asks the user first (100,000 by default, since a switch loses the prompt cache and the whole context is written again; 0 always asks). A switch keeps the model, so only an engine that serves it takes over: in practice Claude Code engines for a Claude model. The Engine module's `engineToRunOn(cascade, settings, hasRoom)` picks the engine to run on: the cascade's engine while it has room, else the first Stand-in Engine in order that is listed, isn't the cascade's own, serves the cascade's model and has room, on that same model, else none. The cascade's engine needn't be in the list to get stand-ins. What "room" means is the caller's: at Start the Window caps with the Usage estimate, mid-run the windows not used up. An engine named twice or not listed is refused, as is a size that isn't a whole number from 0 to 10,000,000; removing an engine drops it from the list. Start and the Queue use it: when a Window cap would be passed or the window is used up, a Start chooses a stand-in for each such cascade engine ([2.1](2.1-work.md#defaults), "A queue for Start") and records the choice on the Task (`engineStandIns`), with why; every Start replaces it, trying the cascade's engines first. `engineThroughStandIns(cascade, standIns, engines)`, from the Engine module's public entry, maps a cascade's engine through that record: to its stand-in while that is listed and serves the model, else back to the cascade's engine. The Usage estimates of a started Task and the Stage Threads both map through it alone, so what is counted and where a session runs can't drift apart. The choice holds for the whole run, Pause and Resume, a restart and the fire alarm included: a continued session stays on its engine, and a session whose engine differs starts fresh with the Brief (`engine-changed`), never resumed on another engine. Each Stage run records the engine and model it ran on and, on a stand-in, the engine it stood in for and why. **A running Stage switches:** when an engine refuses a Stage's turn, its first or its correction, as **usage window used up**, the Stage goes on in the same Stage run on the first Stand-in Engine, in order, that serves the same model, has room (its window not used up, its latest reading free or not read yet) and can carry the session. The run stays Running: the Task isn't paused, and no failure, retry or Notification about the Stage is raised. The session is carried over and resumed with the same model and settings, the refused message is sent again, and the stand-in is recorded on the Task's `engineStandIns`, so the run's next Stages open on it; the next Start replaces that list. A stand-in that refuses too gives way to the next; once none is left, the Task pauses until the latest reset. Four cases don't switch, and the Stage pauses until the reset, never failing: no stand-in has room; the carry-over fails; a user's Pause or Stop, or the fire alarm, was asked before the refusal; the session's context is over the size set beside the list, since the stand-in's account has no prompt cache and would read it all again, in which case the Stage is marked as waiting for the user's choice to go on on the stand-in or at the reset (the choice is made on the Stand-in choice card, [2.4](2.4-conversations.md#defaults), "The Decision on Stages waiting for a Stand-in Engine"; "Switch now" moves the idle session to the first Stand-in Engine with room by the carry-over below, and the Stage goes on on it, recorded on the Stage run as the user's choice). Only Stage Threads switch: chats, Consultations and planning Threads keep the notice of a refused turn. Each switch is recorded on the Stage run (from which engine, to which, and why: the window and its reset), the Stage history shows it, and the Task page and the Live view show the stand-in as the run's engine afterwards. **Carrying a session** is the `carrySession` capability, Claude Code only. The session id is Claude Code's and each engine runs with its own config folder, so the carry copies, never moves, the session's transcript (`projects/<cwd>/<id>.jsonl`) and the sibling `<id>/` folder (Sub-agent transcripts, saved tool results) into the same `projects/<name>/` under the stand-in's folder, each file written beside its target and then renamed into place, with the old folder's path rewritten to the new one in the copied transcripts (tool results are referenced by absolute path); todos are copied and file-history is skipped. Running it again gives the same result, and the source stays intact. It runs only while the session is idle, after the refused turn ended its engine session. The order is copy, then persist the Thread's new engine, then resume: a restart before persisting leaves the Thread on the intact source; after it, the copy is already there and can run again; if the resume fails, the Thread is moved back to the old engine. Codex isn't carried, as it keeps its threads in its own internal store and its reasoning is likely tied to one account: a used-up Codex engine pauses until the reset. The engine check's `engine.session-carry-over` and `fallback.session-carry-over` cases guard against a Claude Code update changing the file layout.
- **A Stage's Sub-agents run in the foreground:** a Stage's result is its Agent's turn's end, held to the Stage result's schema, so a Stage session runs with `subAgentsInForeground`, and the Office rules hook answers each Sub-agent call it allows with `updatedInput` setting `run_in_background: false` ([2.9](2.9-sub-agents-and-processes.md#the-model)). Background commands stay allowed. Other sessions don't get the option; the API engine has no Sub-agents and takes it unchanged. The engine check's `engine.foreground-sub-agents` and `fallback.foreground-sub-agents` confirm that both routes honour the hook's `updatedInput`.
- **A turn refused for a used-up usage window** ([the engine check](../engine-check.md#engineusage-window-refusal)): on both Claude Code adapters, a turn that ends with an error after a `rate_limit_event` with `status: "rejected"` in the same turn ends with the outcome **usage window used up**, naming the window from the event's `rateLimitType` (`five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_overage_included`, `overage`; a type the port doesn't name is carried with the engine's own name, so it still pauses rather than fails) and its reset time (`resetsAt`). Any other failure, including one after an `allowed` event (overloaded, a 5xx), stays an ordinary failure. The engine then publishes **Usage window used up** (the engine, its name, the window, the reset time) once per engine until that reset. Which engines are used up is kept in memory only, with no table: after a restart it is unknown until a turn is refused again, so at most one queued Task starts, is refused, pauses itself and sets the wait again. The Task's own resume time is kept with the Task, so its resume outlives a restart. **The usage windows are checked as the service starts and every 5 minutes,** per engine that has them (a Claude Code engine, a Codex engine signed in with ChatGPT), as well as on each rate-limit signal: each engine's adapter reads them with no session and no model call (the Agent SDK a short-lived query that keeps no session or transcript, `-p` the pinned binary's `get_usage`, Codex a short-lived app-server's `account/rateLimits/read`), one engine at a time, each read ended within 30 seconds, on failure too, a failed read logged and the next engine read. Such a reading is kept and announced as a session's is. The Engine alone judges whether a reading shows the engine **free** (every window below 100%) and announces it with the reading. A free reading taken after a window was used up resets that window at once, as its reset time would, so Start and the queue no longer wait for it. A turn refused while the latest reading shows the engine free is a limit the readings don't show: the engine's readings count as not free until that refusal's reset, so the Tasks it paused wait for their reset rather than resume into another refusal every 5 minutes.
- **Removing an engine:** every reference to it (the Office default, Project defaults, Role overrides, Projects' Role overrides) moves to a replacement the user picks, taking the replacement's default model where the replacement doesn't offer the one named; when it is the only engine they move to none, and no session starts, with words saying so, until one is added. A running session finishes on the old engine and its Thread starts fresh; Stage runs keep the name of the engine they ran on.
