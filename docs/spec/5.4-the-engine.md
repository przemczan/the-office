# 5.4 The engine

- **An `AgentEngine` port, not Claude-shaped:** start a session with a brief, send a message with priority, interrupt, resume, read usage, the tool-permission hook; each adapter declares which capabilities it has and The Office degrades where one is missing. The engine and model a session runs on come from the engine cascade (Defaults below; until tier 3 a Role picked them).
- **Adapters:** the TypeScript Claude Agent SDK on the user's own login (tier 1); `claude -p` as fallback (tier 2); the OpenAI-compatible API (tier 3); from tier 3 every engine is one the user adds (Defaults below); others later. One long-lived streaming `query()` per session.
- **Native features used:** message `priority` for barge-in (`next` between tool calls, `later` after the turn); `interrupt()` for Stop, the only way to stop a running command (`now` is not used: it ends the turn but leaves a running command to finish or run on in the background); resume by session id; the 1-hour prompt cache on the main conversation; in-process Office tools via `createSdkMcpServer()`; `rate_limit_event` and the experimental usage query for the 5-hour and 7-day windows (never the CLI's OAuth token), each reading keeps its **Reading source**, the usage endpoint's own answer (a session's first) or one the CLI builds from the last reply's rate-limit headers (the later ones, one per turn's rate-limit event), which round differently, so the Office-wide window % per token for usage estimates is learnt only from successive readings of one source, each counted pair kept so the ratio outlives a restart (the user, 2026-11-02); cost in The Office is priced by the Model prices set per model in Settings → Engines (input, output, cache writes and cache reads per million tokens, for every engine's models; one per Claude model shared by every Claude Code engine, one per engine and model on the OpenAI-compatible API engines, a removed engine's kept so its history stays priced, the user, 2026-11-01 and 2026-11-02), never the engine's own `total_cost_usd` (the user, 2026-11-01).
- **Engine features turned off:** claude.ai connectors (`disableClaudeAiConnectors`); the engine's built-in plugins (each set false in `enabledPlugins`); auto-memory (`autoMemoryEnabled` and `autoDreamEnabled` false), whose folder outside the worktree is shared by every worktree of a repository and written without a prompt. Memory is The Office's own (Shared memory, tier 2). The built-in tool set is an explicit `tools` list, the same on both platforms (the engine's Windows default today and `LSP`, PowerShell on Windows only), since the engine's Linux default drops Grep and Glob for shell search; trimming it per Role is open, with its cost measured in [engine-check.md](../engine-check.md).
- **Cache breakers to avoid mid-session:** changing model, effort, MCP servers (with tool search off) or the Claude Code version.
- **Versions are pinned** (the SDK bundles the binary) and bumped deliberately, re-checking what was read from the binary ([5.6](5.6-skills-per-session.md), [6](6-permissions-and-safety.md)) with the engine check ([engine-check.md](../engine-check.md)).

## Defaults

Gaps no ticket settled, filled with the simplest choice consistent with the tickets and accepted by the user; each says when.

- **The `-p` fallback matches the Agent SDK adapter:** the Office tools reach its sessions through the binary's own stream, as the SDK does (an in-process MCP server answering the binary's `mcp_message` requests), and the Office rules through a hook that asks the service on `localhost`, so any Role can work with it. Not an MCP endpoint on `localhost`: over HTTP a tool's answer can overtake a barge-in message on the binary's input, which the engine check saw on Windows (amended 2026-10-30). The hook's token is made per session and reaches its Agent's commands, so it reaches nothing beyond its own session's hook, which judges by that session's rules (accepted 2026-10-30); what it can't match, as the engine check finds, it declares missing. From tier 3 it is a switch on each Claude Code engine, off by default, every session on that engine running through it (the user, 2026-11-02, replacing a Role's "Claude Code -p" pick). It runs the pinned Claude Code binary the SDK bundles, with the same models, and has its own runs in the [engine check](../engine-check.md) on Windows and Linux. (added while slicing task 29, accepted 2026-10-30)
- **The OpenAI-compatible API engine is The Office's own agent loop** ([8](8-open-questions-and-risks.md)), for local LLMs and any server on that API: the user lists the API endpoints in Settings → Engines (a name, the base URL, a key kept in the database and never sent back, empty for a local server, and the models with their context windows), and from tier 3 each API endpoint is an engine of its own, its models the engine's (the user, 2026-11-01, replacing a Role's "OpenAI-compatible API" pick with a Model field naming an endpoint and a model). Replies stream. The loop gives the model the built-in tools under the Claude Code engines' names and inputs (Read, Grep, Glob, Edit, Write, the shells, WebFetch, WebSearch, Skill), so the same Office rules judge every call before the loop runs it, and runs commands in the background as the SDK's sessions do (started, their output read, stopped; ended on Stop and when the session ends). WebSearch goes through a search endpoint set Office-wide behind a port, SearXNG's JSON API the only one built. It lists exactly the session's skills and loads them by name ([5.6](5.6-skills-per-session.md)), keeps the conversation under the session's folder in the Office data directory so it resumes, and reads its context usage for the Context policy ([2.5](2.5-context-policy.md)); it has no usage windows and reports no cost. Any Role may pick it; The Office refuses only what it declares it can't do. (added while slicing task 35, accepted 2026-10-31)
- **MCP servers for Agents** ([8](8-open-questions-and-risks.md)): the user adds each MCP server to an Office-wide library in Settings → MCP servers, by a form or by pasting the server's JSON config: a local command (stdio: command, arguments, environment) or a remote URL (Streamable HTTP, with headers). A server declares its Server values (an environment variable or a header; plain or secret; required or not), each with an Office-wide value that a Project's page may override; a secret is kept in the database and never sent back. A server is off until the user reviews it (its command or URL, its values, and the tools it lists on a test connection), and changing it turns it off until reviewed again. A Role card assigns servers. A session starts with its Role's servers that are on, with its Project's values (the Office-wide values in chat), fixed for the session; a server missing a required value is left out, and the session's brief says so. All three engines run them: the Claude Code engines through their own MCP config holding only the Office's servers (never a Project's `.mcp.json`), the OpenAI-compatible API engine through an MCP client in its loop. Every MCP tool is judged by the Office rules before it runs ([6](6-permissions-and-safety.md)). Agents proposing servers is left for later. Accepted by the user on 2026-10-31.
- **Language servers for Agents** (the user, 2026-11-07): every session on a Claude Code engine, whichever its Role, chats and the Planner too, has the `LSP` tool on the workstation's language servers: TypeScript, C and C++, Kotlin ([language-servers.md](../language-servers.md)). A session gets those its `PATH` finds as it starts, fixed for the session as its MCP servers are; one not found is left out, the session's brief says so, and it never stops a session starting. The servers reach the engine as a plugin of their own beside the skills folder, so a session with no skills still gets them and the skills start check ([5.6](5.6-skills-per-session.md)) stays exact. A server starts at the first LSP call or Edit on a file of its language, never with the session, and one stays out of a session that doesn't need it. Each LSP call is a read of its file under the Office rules ([6](6-permissions-and-safety.md)). The OpenAI-compatible API engine has no such tool and declares the capability missing.
- **Engines are a list** (tier 3, the user's answers of 2026-11-01 and 2026-11-02): Settings › Engines lists the engines the user adds, each with a name, an id made from the name when added and kept on a rename, and a default model. A **Claude Code** engine is one account: its sessions run with `CLAUDE_CONFIG_DIR` set to its own folder, `<office-data>/engines/<engine id>/`, so its credentials and transcripts stay there and a session resumes only on the engine that started it; "Sign in" runs the pinned binary's `claude auth login --claudeai` for that folder and shows its sign-in page, which signs in from any browser and gives a code the user pastes into the engine; "Paste a token instead" takes a token the user made with `claude setup-token` (a year long, `sk-ant-oat01-…`) and writes it into that folder as its login, the credentials file the binary reads, in place of any login there, never sending it back, so the engine's sessions are signed in by it and it sits in no environment (the user's answers of 2026-11-02; [6](6-permissions-and-safety.md), Secrets); "Sign out" removes the folder's login, whether a Sign in or a token made it; the engine shows the email and plan `claude auth status` gives, that a pasted token signs it in, or that it is signed out; the `-p` fallback is its switch. An **OpenAI-compatible API** engine is one API endpoint. Caps, readings of the usage windows, their samples and each day's use are kept per engine ([2.1](2.1-work.md), "Usage estimates"). At the upgrade the Claude Code setup becomes the first Claude Code engine (id `claude-code`), in a fresh folder signed in once, so existing Threads start fresh; each API endpoint becomes an engine; Roles on `-p` move to the first Claude Code engine with the switch off; the caps go to the first engine of each kind, the API's set copied to each API engine.
- **The engine cascade** (tier 3, the user, 2026-11-01): every level names an engine and one of its models, picking an engine filling in its default model; a session's comes from the most specific level set: the **Office default** (Settings › Engines), the **Project default** (the Project page's Engine block), the Office-wide **Role override** (the Role card), the Project's Role override (the Project page's Engine block). A Project's "Use for every Role" forces its default on every Role in it: the Office-wide Role overrides are skipped, its own still apply. Threads without a Project, onboarding a Project not yet added among them, use the Office levels only. Every session follows it: Threads, Stage runs, Consultations, the Planner, Devops, the Office Manager. A Stage has no model of its own ([2.3](2.3-pipelines.md)). Only a Role a Pipeline names needs more of its engine: an Agent Stage's Role in the Pipeline library, which counts outside any Project and in every Project, or in an open Task's own Stages, which counts in that Task's Project (a done or dropped Task's don't count). It needs Office tools and an answer held to the Stage result's schema (the `officeTools` and `outputSchema` capabilities); other Roles take any engine. A save at any level that would newly put such a Role on an engine lacking either, outside any Project or in one, is refused, naming the Roles and Projects; so are hiring back a person let go, whose Role override comes back with their card, and a preset hire. The other way round, adding or changing a Stage, in the library or in a Task's own Stages, so that it newly names a Role whose engine lacks either is refused the same way, weighed where that Stage counts (the user, 2026-11-02). A session whose engine changed starts its Thread fresh; a changed model alone resumes. At the upgrade every Role's engine and model and every saved Stage's model are cleared, and everything runs on the Office default, the first Claude Code engine on Sonnet (the user, 2026-11-02).
- **Removing an engine** (tier 3, the user, 2026-11-01): every reference to it (the Office default, Project defaults, Role overrides, Projects' Role overrides) moves to a replacement the user picks, taking the replacement's default model where the replacement doesn't offer the one named; when it is the only engine they move to none, and no session starts, with words saying so, until one is added. A running session finishes on the old engine and its Thread starts fresh; Stage runs keep the name of the engine they ran on.
