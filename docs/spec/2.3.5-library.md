# 2.3.5 Library and Project Pipelines

Covers: the built-in Pipelines, which Pipeline a Task follows, the Library, the library editor, Stage templates, Project commands by Proposal and by hand, the commands a Pipeline needs, Project Pipelines, a Broken Project Pipeline.

## Built-ins

- **Full**: Implement → Tests → Review & fix → Publish.
- **Quick fix**: Implement → Tests → Publish.
- **Document**: Produce → Review & fix.
- Each is a straight line: one route with no condition from each Stage to the next, and from the last to End.
- Other built-ins: **Proof of concept** ([2.3.4](2.3.4-publish.md#the-proof-of-concept-publish-target)), **Resolve conflicts** ([2.3.4](2.3.4-publish.md#resolve-conflicts)), the Onboard Pipeline and the Set up run environment Pipeline.
- Each built-in Agent Stage names a duty:
  - Implement, Review & fix and Produce name Implements;
  - the Onboard Pipeline's Onboard Stage and the Set up run environment Pipeline's Set up Stage name Onboards and repairs Projects;
  - the Resolve conflicts Pipeline's Stage names Implements;
  - the built-in Stage templates likewise.
- Plans and Reviews are for the Pipelines and Stages the user builds.
- Planning is a Task state, not a Stage.
- [Review & fix](2.3.1-stages.md#review--fix-stage) is one fresh-session Stage.

## Which Pipeline a Task follows

- Each Project names a default, the one its Tasks usually follow: one of its own Project Pipelines or an office-wide one.
- The picker lists the Project's default first, then its other Project Pipelines, then the office-wide ones.
  - A Broken one is listed, flagged with why, and can't be chosen ([A Broken Project Pipeline](#a-broken-project-pipeline)).
- A new Task has no Pipeline until one is chosen, either:
  - the Planner proposes one from the Definition of Done, named against the Project's default in its Brief, which the user takes or declines (keeping the Task's Pipeline, when it has one) before the Task can be Ready;
  - or the user chooses one, the default listed first.
- The user can swap it or **edit the flow for this Task**: add a Gate, remove or reorder Stages, change their routes and their conditions, effort, session, budget.
  - A Stage has no model of its own, so a Stage that needs another gets a Role of its own.
  - It is checked by the [Validation](2.3.2-flows.md#validation) rules.
- In that window a swap and an edit are both a draft: Save applies them, closing it drops them.
- Started Stages, and the routes out of them, are locked.
  - A Stage has started once it ran: it has a run of the Task's, ended or not, held or skipped.
  - A started Stage keeps its fields, its routes out (where each leads, its condition and their order) and its place, so no Stage can be put straight after it; a route into it can still be drawn.
  - A Stage not reached yet, or Not taken, can still be changed, moved and removed, wherever it stands in the order.

## Library

- The Library holds the office-wide Pipelines and the Stage templates, which are office-wide.
- Each Project's Project Pipelines are not in it but on that Project's page ([Project Pipelines](#project-pipelines)).
- One Stage editor serves the library, the Project Pipelines and "Edit for this Task".
- It flags, beside the [Validation](2.3.2-flows.md#validation) rules, which refuse Save:
  - a Role with Task limit none or let go (a Stage template's Role too);
  - a duty nobody holds, or held by a Role with Task limit none;
  - "continue" without the same Role or the same duty in the Stage before;
  - failure targets that aren't earlier or from which no path of routes leads to the Stage.
- "The Stage before" means the Stage before it on every path of routes into it: a "continue" Stage that joins paths from different Stages is flagged.
- Saving a library Pipeline changes Tasks that haven't started and the Initiatives that name it in a Project whose Publishing Task hasn't started ([2.1](2.1-work.md#defaults)).
  - Running ones keep their copy; a Task edited for itself keeps its Stages.
- Saving an office-wide Pipeline also changes the Project Pipelines built from it, and so the Tasks that haven't started on them.

## The library editor

- In Settings › Pipelines the user:
  - makes a Pipeline from scratch or by duplicating one;
  - edits any Pipeline's name, description, Stages and routes;
  - removes one, refused while a Project names it as its default, a Task that hasn't started uses it, or a shaping or active Initiative names it in a Project whose Publishing Task hasn't started.
- "Ask Devops" on a Pipeline opens a chat with Devops, who answers with a Proposal of the Pipeline's new Stages and routes that the user applies.
- Each "Ask Devops" here and on Stage templates names the holder of Onboards and repairs Projects; while nobody holds it, it points to Settings › Duties.
- The built-ins are seeded into the library once and are then edited like any.
- The Onboard Pipeline can't be removed, since onboarding uses it.
- Stage templates sit beside the Pipelines there ([Stage templates](#stage-templates)).
- Project Pipelines live on their Project's page, as its commands and skills do:
  - its **Pipelines** section holds the Project's default and its Project Pipelines;
  - there the user makes one from an office-wide Pipeline, edits its name, description, base Pipeline and Stage changes, makes it the default, and removes one ([Project Pipelines](#project-pipelines)).
- Settings › Pipelines lists the office-wide Pipelines only.
  - One that Project Pipelines are built from says "Built on by" and how many, and lists the Projects they belong to, each with how many it has and a link to its Pipelines section.
  - It never lists the Project Pipelines by name: those are listed on their Project's page alone.
- "Ask Devops" on a Project Pipeline, or on a Project's Pipelines section for a new one, opens a chat with Devops, who answers with a Proposal of the Project Pipeline (its name, description, base Pipeline and Stage changes) that the user applies.
  - Such a Proposal keeps each value as it was and as proposed, applies all or nothing, is refused once any of those values changed since, and is checked by the same rules as the editor.
- How the editor looks is [its design](../design/project-pipelines.html), with [the flow editor's](../design/pipeline-flow.html) for the Stages.
- Proposals of routes: [2.3.2](2.3.2-flows.md#route-and-condition-proposals).

## Stage templates

- Stage templates live in Settings › Pipelines, beside the Pipelines.
- The user makes one from scratch, or with **Save as template** on any Stage in a Stage editor (a library Pipeline's or a Task's own Stages), and edits and removes templates there.
- The built-in Stages are seeded into the library once, as templates, like the built-in Pipelines, and are then edited and removed like any.
- A template is added to a Pipeline or to a Task's own Stages as a copy, so a later change to the template never changes a Pipeline or a Task.
- **Ask Devops** on a template opens a chat with Devops, who answers with a Proposal of the template's new Stage, which the user applies.
- Removing a template is never refused, since nothing points at it.
- A template's Role is flagged in the Stage editor like a library Pipeline's (Task limit none or let go).
  - A template is not a Pipeline, so it doesn't count as a Role a Pipeline names for the engine checks of [5.4](5.4-the-engine.md): nothing runs from it, and the Stage it adds is checked when its Pipeline or Task is saved.
  - Letting go is not refused either way, as for Pipelines.

## Defaults

### Project commands by Proposal and by hand

- Once Devops proposes Project commands, the user still edits them on the Project page too.
- "Ask Devops to propose a change" sits beside them, and Devops' Proposal card changes them when applied.
- The button names the holder of Onboards and repairs Projects, as in "Ask Dwight to propose a change"; while nobody holds it, it points to Settings › Duties.
- A Proposal of commands may change the install command and the install inputs, add or change commands (whole, by key) and remove commands by key.
- It keeps each value as it was and as proposed, applies all or nothing, is refused once any of those values changed since, and is checked by the same rules as the Project page.

### A Pipeline needs the commands it runs

- The commands a Pipeline's Stages run are:
  - each Script Stage's key but `publish`;
  - each key an Agent Stage narrows its Project commands to ([2.3.1](2.3.1-stages.md#an-agent-stages-project-commands));
  - each key a route's Project-command condition names ([2.3.2](2.3.2-flows.md#the-project-command-condition));
  - plus `test` where Resolve's Test may run it (a Publish by the publishing mode beside an Agent Stage, as [Conflicts at Publish](2.3.4-publish.md#conflicts-at-publish) runs the Project's Test, which is its `test` command).
- The Office refuses, naming the Pipeline, the Project and each missing key:
  - choosing a Pipeline for a Task (the Planner's proposal, the user's confirm or swap, auto mode's accept, and a Project's "Set up the run environment" Task) when the Task's Project lacks one;
  - making a Pipeline a Project's default (on the Project page, in Add a Project, or by Devops' Project to onboard) when that Project lacks one;
  - saving a library Pipeline, or applying Devops' Proposal of its Stages, when a Project with it as default, or with a Task on it that hasn't started, or where an open Initiative names it and that Project's Publishing Task hasn't started, lacks one, which the editor's check shows on the Stage before Save;
  - an edit of a Task's own flow, for the Stages that haven't started;
  - choosing or changing an Initiative's Pipeline in a Project, while shaping or by the CTO's Proposal, when that Project lacks one.
- The check for an Initiative is per Project: another Project the Initiative spans isn't weighed, and a Project with None is never checked, so adding or moving one of the Initiative's Tasks into a Project it doesn't span yet, which starts with None, checks nothing ([2.1](2.1-work.md#defaults)).
- Removing a command a Project's default Pipeline runs is refused too ([2.1](2.1-work.md)), so a Project's default always runs there, and a Task created, shaped, added by an Initiative or moved takes it unchecked.
- Keys alone count: a command left blank passes and fails could-not-run when it runs.
- Removing a command another Pipeline runs is not refused: that Stage fails could-not-run, naming the key.
- Stage templates aren't checked, since nothing runs from them.
- A Stage is never skipped for a missing command.
- The built-in Pipelines and Stage templates name only `test` and `publish`.
- For a Project Pipeline, "the Projects" above is its own Project only, and saving its base Pipeline weighs each Project Pipeline built from it against its own Project ([A Broken Project Pipeline](#a-broken-project-pipeline)).

### Project Pipelines

- A **Project Pipeline** belongs to one Project.
- It has a name, a description, a **base Pipeline** (one office-wide Pipeline, never another Project Pipeline) and an ordered list of **Stage changes**.
- Each Stage change is one of six:
  - **Insert before** a Stage;
  - **Insert after** a Stage;
  - **Replace** a Stage (each of these three with a whole new Stage);
  - **Change** a Stage (only the fields it gives, such as its brief, Role, limits, session, on failure or permissions);
  - **Remove** a Stage;
  - **Change routes** of a Stage (its whole list of routes out, with their conditions).
- On the routes:
  - Insert before puts the new Stage just before its Stage in the Pipeline's order, the routes that led into that Stage now leading into the new one, and one route with no condition from the new Stage to it;
  - Insert after puts the new Stage just after its Stage, which hands the new Stage its routes out and gets one route with no condition to it;
  - Replace keeps the Stage's place, the routes into it and its routes out;
  - Remove takes the Stage and its routes out away, and each route that led into it leads where its one route out led, or, when it had several, is taken away too, for a Change routes to settle.
- On a straight line each of them builds a straight line again.
- Each Stage change names its Stage by its key, shown by the Stage's name: one of the base Pipeline's Stages, or one an earlier Stage change inserted.
- An inserted Stage's key must be new among the built Stages.
- It is built whenever it is read: the base Pipeline's current Stages and routes, then each Stage change in order, so an edit to the base Pipeline reaches it; only a started Task keeps a copy of its Stages.
- Its name is unique among the office-wide Pipelines and its Project's own.
  - Two Projects may use the same name.
  - Making or renaming an office-wide Pipeline is refused when the name is a Project Pipeline's, naming that Project.
- It is kept in The Office's records, beside the office-wide Pipelines.
- It is checked by the rules of the library's Pipelines on its built flow, which weigh its own Project only:
  - the [Validation](2.3.2-flows.md#validation) rules;
  - the Role flags, "continue" without the same Role, failure targets that aren't earlier ([Library](#library));
  - [A Pipeline needs the commands it runs](#a-pipeline-needs-the-commands-it-runs);
  - [An Agent Stage's Project commands](2.3.1-stages.md#an-agent-stages-project-commands).
- It can be chosen only by a Task of its Project, as that Project's default, and as an Initiative's Pipeline in that Project; another Project is refused it ([2.1](2.1-work.md#defaults)).
- Removing it is refused while it is its Project's default, a Task that hasn't started uses it, or a shaping or active Initiative names it in its Project whose Publishing Task hasn't started.
- Removing an office-wide Pipeline is also refused while a Project Pipeline is built from it, which amends [The library editor](#the-library-editor).
- The built flow's places: [2.3.2](2.3.2-flows.md#the-pipelines-order).

### A Broken Project Pipeline

- A Project Pipeline is **Broken** when building it fails:
  - a Stage change names a key that isn't there;
  - an inserted Stage's key is already there;
  - a loop ("on failure go back to") points at a Stage that isn't in the built Stages or isn't earlier;
  - the built flow fails the [Validation](2.3.2-flows.md#validation) rules, such as a route or a condition naming a Stage the base Pipeline no longer has, or a Stage no route reaches any more.
- Saving an office-wide Pipeline that would break one warns before Save, in the editor and when applying Devops' Proposal of its Stages alike.
  - The warning lists each Project Pipeline it breaks, with its Project and why, and the user can save anyway.
  - The commands check of such a save weighs each Project Pipeline built from it against its own Project, as it weighs Projects ([A Pipeline needs the commands it runs](#a-pipeline-needs-the-commands-it-runs)).
- A Broken one is flagged on its Project's page (in its list, and on the default when it is the default), counted under its Project in its base Pipeline's "Built on by" in Settings › Pipelines, and in the Task's picker.
- It can't be chosen for a Task, made a default or proposed by the Planner until its Stage changes are fixed.
- A Task that hasn't started on it, an Initiative's Task in Backlog among them, is flagged on the Task page, and Start (and Start Ready Tasks, [2.1](2.1-work.md#defaults)) is refused for it, naming the Pipeline and why, until it is fixed or the Task's Pipeline is swapped.
- An Initiative that names it in its Project is weighed as for a Task that hasn't started: that Project's Publishing Task not yet started can't start until it is fixed, and Confirm refuses a Broken one.
- Started Tasks keep their own Stages, and so does a Task edited for itself.
- A Project Pipeline's own save, and applying Devops' Proposal of it, are refused while it would be Broken, so only an office-wide Pipeline's save, which warns first, breaks one.
- Each Stage change keeps the name its Stage had when the Project Pipeline was last saved, for its words alone, so a Stage gone from the base Pipeline still reads by its name ("Changes Produce, which Document no longer has"); the key alone still matches it.
- How it reads and is fixed is [its design](../design/project-pipelines.html).
