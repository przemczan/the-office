# 2.3.5 Library and Project Pipelines

Covers: the built-in Pipelines, which Pipeline a Task follows, the Library, the library editor, Proposals of a Pipeline's Stages, Stage templates, editing a template with linked Stages, Project commands by Proposal and by hand, the commands a Pipeline needs, Project Pipelines, the move to routes back and Publish Stages, the move to positions.

## Built-ins

- **Full**: Implement → Tests → Review & fix → Publish, with the conflict chain.
  - Tests goes back to Implement when it fails, at most 3 times; Review & fix goes back to Implement when it fails, at most once.
  - Publish goes back to Review & fix when it fails, at most once.
- **Quick fix**: Implement → Tests → Publish, with the conflict chain; Tests goes back to Implement when it fails, at most 2 times.
- **Document**: Produce → Review & fix.
- The conflict chain is Publish → (Conflict) Resolve → Test after Resolve → Publish ([Conflicts in the flow](2.3.4-publish.md#conflicts-in-the-flow)).
- Every other route is one with no condition to the next Stage, the last Stage's to End.
- Other built-ins: **Proof of concept** ([2.3.4](2.3.4-publish.md#the-proof-of-concept-publish-target)), **Resolve conflicts** ([2.3.4](2.3.4-publish.md#resolve-conflicts)), the Onboard Pipeline and the Set up run environment Pipeline, which the Off-board Tasks follow ([2.1.3](2.1.3-tasks.md#off-board-tasks)), and the Set up test targets Pipeline.
  - Onboard and Set up run environment end with a Publish Stage and the conflict chain, their Verify going back to their Agent Stage when it fails, at most 2 times.
  - Proof of concept and Resolve conflicts end with a Publish Stage that pushes the branch only, with no chain; their Script Stage before it goes back to their Agent Stage when it fails, at most 2 times.
- **Set up test targets**: one Agent Stage and no Publish; its Agent reads the repository, changes no file and ends by setting the test targets with `change_project_settings`, or with a `propose_test_targets` Proposal without that tool ([6 Project settings by Agents](6-permissions-and-safety.md#project-settings-by-agents)).
  - An update rewords its brief and the Onboard Stage's for the change tools (migration 0214), in the library, the Stage templates and the open Tasks' Stages, only where each still reads as the built-in's did.
  - It stays in the library for the Tasks already on it, and an open one made before keeps working; The Office makes no new Task on it, as test targets are now set up in a chat ([2.12](2.12-test-instances.md#set-up-test-targets)).
- A later update (migration 0216) rewords the briefs of the Onboard, Set up test targets and Set up Stages for `change_project_settings`, in the same places and only where each still reads as the built-in's did; the Onboard and Set up briefs also tell their Agent to run `run_environment_check` until it passes ([5.5](5.5-git-and-isolation.md#the-environment-check-tool)).
- Each built-in Agent Stage names a duty:
  - Implement, Review & fix, Produce and Resolve name Implements;
  - the Onboard Pipeline's Onboard Stage, the Set up run environment Pipeline's Set up Stage and the Set up test targets Pipeline's Stage name Onboards and repairs Projects;
  - the Resolve conflicts Pipeline's Stage names Implements;
  - the built-in Stage templates likewise.
- Each built-in Resolve Stage is linked to the built-in Resolve template.
- Plans and Reviews are for the Pipelines and Stages the user builds.
- Planning is a Task state, not a Stage.
- [Review & fix](2.3.1-stages.md#review--fix-stage) is one fresh-session Stage.

## Which Pipeline a Task follows

- Each Project names a default, the one its Tasks usually follow: one of its own Project Pipelines or an office-wide one.
- The picker lists the default for the Task's Kind first ([2.1.1](2.1.1-projects.md#project-settings), "Default Pipeline per Kind"), then its other Project Pipelines, then the office-wide ones.
- A new Task has no Pipeline until one is chosen, either:
  - the Planner proposes one from the Definition of Done, named against its Kind's default in its Brief, which the user takes or declines (keeping the Task's Pipeline, when it has one) before the Task can be Ready;
  - or the user chooses one, the default listed first.
- The user can swap it or **edit the flow for this Task**: add a Gate, remove or move Stages, change their routes, their conditions and their limits, effort, session, budget.
  - A Stage names no engine and no model, so a Stage that needs another model gets a Role of its own, whose person sets it per engine type ([5.4.5](5.4.5-engines-and-cascade.md#the-model-and-effort-cascade)).
  - It is checked by the [Validation](2.3.2-flows.md#validation) rules.
- In that window a swap and an edit are both a draft: Save applies them, closing it drops them.
- Started Stages, and the routes out of them, are locked.
  - A Stage has started once it ran: it has a run of the Task's, ended or not, held or skipped.
  - A started Stage keeps its fields, its routes out (where each leads, its condition, its limit and their order) and its place in the Pipeline's order: the order is frozen up to the last started Stage, so no Stage is added among those Stages or moved earlier into them; a route into it can still be drawn.
  - Its position on the canvas can still change: positions are never locked ([A Stage's position](2.3.2-flows.md#a-stages-position)).
  - A Stage not reached yet, or Not taken, can still be changed, moved and removed, wherever it stands in the order.

## Library

- The Library holds the office-wide Pipelines and the Stage templates, which are office-wide.
- Each Project's Project Pipelines are not in it but on that Project's page ([Project Pipelines](#project-pipelines)).
- A Pipeline's Stages line, as its lists and pickers show it and the planning and shaping Briefs list it, names its Stages in order but the conflict chain's, which run only after a conflict: "Implement → Tests → Review & fix → Publish".
- One Stage editor serves the library, the Project Pipelines and "Edit for this Task".
- Saving "Edit for this Task" is the user's click, or a person's call in Work › Moving work, ruled by their [Authority](6-permissions-and-safety.md#authority) ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).
- It flags, beside the [Validation](2.3.2-flows.md#validation) rules, which refuse Save:
  - a Role with Task limit none or let go (a Stage template's Role too);
  - a duty nobody holds, or held by a Role with Task limit none;
  - "continue" without the same Role or the same duty in the Stage before;
  - a Publish Stage by the publishing mode with no route for Conflict.
- "The Stage before" means the Stage before it on every path of routes into it: a "continue" Stage that joins paths from different Stages is flagged.
- Saving a library Pipeline changes Tasks that haven't started and the Initiatives that name it in a Project whose Publishing Task hasn't started ([2.1](2.1-work.md#defaults)).
  - Running ones keep their copy; a Task edited for itself keeps its Stages.
- Saving an office-wide Pipeline never changes a Project Pipeline, even one copied from it.

## The library editor

- In Settings › Pipelines the user:
  - makes a Pipeline from scratch or by duplicating one;
  - edits any Pipeline's name, description, Stages and routes;
  - removes one, refused while a Project names it as its default or a Kind's default, a Task that hasn't started uses it, or a shaping or active Initiative names it in a Project whose Publishing Task hasn't started.
- "Ask Devops" on a Pipeline opens a chat with Devops, who answers with a Proposal of the Pipeline's new Stages and routes that the user applies.
- Each "Ask Devops" here and on Stage templates names the holder of Onboards and repairs Projects; while nobody holds it, it points to Settings › Duties.
- The built-ins are seeded into the library once and are then edited like any.
- The Onboard Pipeline can't be removed, since onboarding uses it.
- Stage templates sit beside the Pipelines there ([Stage templates](#stage-templates)).
- Settings › Pipelines lists the office-wide Pipelines only; Project Pipelines live on their Project's page, as its commands and skills do ([Project Pipelines](#project-pipelines)).
- How the editor looks is [the flow editor's design](../design/pipeline-flow.html).
- Proposals of routes: [2.3.2](2.3.2-flows.md#route-and-condition-proposals).

## Proposals

- `list_pipelines` gives each Stage's `position` and, when it is set, the Pipeline's `endPosition`; it gives no place.
- `propose_library_pipeline` and `propose_project_pipeline` take `stages` in the Pipeline's order, each with an optional `position`, and an optional `endPosition`; a position left out is filled in by [A Stage's position](2.3.2-flows.md#a-stages-position).
- `propose_stage_template` takes no position: a template keeps no routes or position.
- A Proposal that gives a `place` is refused: "`place` (column, row) is from before free placement: give each Stage a `position` (x, y) in the Pipeline's order, or leave it out."
- A position out of bounds is refused with the position words of [A Stage's position](2.3.2-flows.md#a-stages-position).
- Positions changed since the Proposal was made don't make it stale; the order and the routes changing since still do ([Route and condition Proposals](2.3.2-flows.md#route-and-condition-proposals)).
- Applying it keeps where each Stage it leaves unmoved stands now, and takes the Proposal's position for each Stage it adds or moves.
- An open Proposal stored with places and no positions is converted as it is read, by [the move to positions](#the-move-to-positions).

## Stage templates

- Stage templates live in Settings › Pipelines, beside the Pipelines.
- The user makes one from scratch, or with **Save as template** on any Stage in a Stage editor (a library Pipeline's, a Project Pipeline's or a Task's own Stages), and edits and removes templates there.
- A template holds a Stage's fields but its key, position and routes; its name is the name a Stage added from it starts with.
- The built-in Stages are seeded into the library once, as templates, like the built-in Pipelines, and are then edited and removed like any; **Resolve** is among them ([The Resolve Stage](2.3.4-publish.md#the-resolve-stage)).
- A Stage added from a template to a Pipeline, office-wide or a Project's, is linked to it; one saved as a template is linked to the new template ([A Stage linked to its Stage template](2.3.1-stages.md#a-stage-linked-to-its-stage-template)).
- A template added to a Task's own Stages is a copy, never linked.
- **Ask Devops** on a template opens a chat with Devops, who answers with a Proposal of the template's new Stage, which the user applies, then chooses the linked Stages that get it as for an edit.
- Removing a template is never refused: its linked Stages are unlinked, keeping their fields, which the confirmation says with their count.
- A template's Role is flagged in the Stage editor like a library Pipeline's (Task limit none or let go).
  - A template is not a Pipeline, so it doesn't count as a Role a Pipeline names for the engine checks of [5.4](5.4-the-engine.md): nothing runs from it, and the Stage it adds is checked when its Pipeline or Task is saved.
  - Letting go is not refused either way, as for Pipelines.

### Editing a template with linked Stages

- Saving an edit of a template that has linked Stages first lists them, each with:
  - its Pipeline, office-wide or "<Project>'s", and the Stage's name;
  - how it differs from the template as it was before the edit ("Same as the template", or "Differs in Budget and Brief");
  - which of the fields the edit changes it differs in, marked "Its own <field> is replaced".
- The user ticks the Stages that get the edit; those that don't differ in the fields it changes are ticked to begin with.
- **Save and apply to N Stages** saves the template and gives each ticked Stage the fields the edit changed, keeping its other differences; **Save the template only** gives none.
- Each Pipeline is saved as its editor saves it: by the [Validation](2.3.2-flows.md#validation) rules and [A Pipeline needs the commands it runs](#a-pipeline-needs-the-commands-it-runs), changing its Tasks that haven't started.
- A Pipeline refused keeps its Stage as it was and is named with why; the others are still applied.
- A Stage left out stays linked, and now differs in those fields.
- A started Task's Stages and a Task's own Stages are never listed: they are copies.

## Defaults

### Project commands by Proposal and by hand

- Once Devops proposes Project commands, the user still edits them on the Project page too.
- "Ask Devops to propose a change" sits beside them, and Devops' Proposal card changes them when applied.
- The button names the holder of Onboards and repairs Projects, as in "Ask Dwight to propose a change"; while nobody holds it, it points to Settings › Duties.
- A Proposal of commands may change the install command and the install inputs, add or change commands (whole, by key) and remove commands by key.
- It keeps each value as it was and as proposed, applies all or nothing, is refused once any of those values changed since, and is checked by the same rules as the Project page.
- An Agent whose Change Project settings allows it changes the install command, the install inputs and the commands itself with `change_project_settings`; Before and After publishing stay by Proposal ([6 Project settings by Agents](6-permissions-and-safety.md#project-settings-by-agents)).

### A Pipeline needs the commands it runs

- The commands a Pipeline's Stages run are:
  - each Script Stage's key, the conflict chain's Test among them;
  - each key an Agent Stage narrows its Project commands to ([2.3.1](2.3.1-stages.md#an-agent-stages-project-commands));
  - each key a route's Project-command condition names ([2.3.2](2.3.2-flows.md#the-project-command-condition)).
- A Publish Stage runs no Project command, so it needs none.
- The Office refuses, naming the Pipeline, the Project and each missing key:
  - choosing a Pipeline for a Task (the Planner's proposal, the user's confirm or swap, auto mode's accept, and making a Project's "Set up the run environment" Off-board Task, which then makes nothing) when the Task's Project lacks one;
  - making a Pipeline a Project's default (on the Project page, in Add a Project, or by Devops' Project to onboard) when that Project lacks one;
  - saving a library Pipeline, applying Devops' Proposal of its Stages, or applying a template's edit to it, when a Project with it as default, or with a Task on it that hasn't started, or where an open Initiative names it and that Project's Publishing Task hasn't started, lacks one, which the editor's check shows on the Stage before Save;
  - an edit of a Task's own flow, for the Stages that haven't started;
  - choosing or changing an Initiative's Pipeline in a Project, while shaping or by the CTO's Proposal, when that Project lacks one.
- The check for an Initiative is per Project: another Project the Initiative spans isn't weighed, and a Project with None is never checked, so adding or moving one of the Initiative's Tasks into a Project it doesn't span yet, which starts with None, checks nothing ([2.1](2.1-work.md#defaults)).
- Removing a command a Project's default Pipeline, or a Kind's own default Pipeline there, runs is refused too ([2.1.1](2.1.1-projects.md#project-commands)), so a Project's defaults always run there, and a Task created, shaped, added by an Initiative or moved takes it unchecked.
- Keys alone count: a command left blank passes and fails could-not-run when it runs.
- Removing a command another Pipeline runs is not refused: that Stage fails could-not-run, naming the key.
- Stage templates aren't checked, since nothing runs from them.
- A Stage is never skipped for a missing command.
- The built-in Pipelines and Stage templates name only `test`.
- For a Project Pipeline, "the Projects" above is its own Project only.

### Project Pipelines

- A **Project Pipeline** is a full Pipeline that belongs to one Project: its own Stages, routes and positions, edited in the same flow editor as an office-wide one.
- It is made as a copy of an office-wide Pipeline, or of another of its Project's own, on that Project's page; it may then be changed in any way.
- It keeps the name of the Pipeline it was copied from and when, for its words alone ("Copied from Full on 12 Nov"); a later edit of either never reaches the other.
- Its name is unique among the office-wide Pipelines and its Project's own.
  - Two Projects may use the same name.
  - Making or renaming an office-wide Pipeline is refused when the name is a Project Pipeline's, naming that Project.
- It is kept in The Office's records, beside the office-wide Pipelines.
- It is checked by the rules of the library's Pipelines, which weigh its own Project only:
  - the [Validation](2.3.2-flows.md#validation) rules;
  - the flags of the [Library](#library);
  - [A Pipeline needs the commands it runs](#a-pipeline-needs-the-commands-it-runs);
  - [An Agent Stage's Project commands](2.3.1-stages.md#an-agent-stages-project-commands).
- It can be chosen only by a Task of its Project, as that Project's default, and as an Initiative's Pipeline in that Project; another Project is refused it ([2.1](2.1-work.md#defaults)).
- Removing it is refused while it is its Project's default or a Kind's default there, a Task that hasn't started uses it, or a shaping or active Initiative names it in its Project whose Publishing Task hasn't started.
- Removing an office-wide Pipeline is never refused for the Project Pipelines copied from it.
- "Ask Devops" on a Project Pipeline, or on a Project's Pipelines section for a new one, opens a chat with Devops, who answers with a Proposal of its new flow, as for an office-wide one ([Route and condition Proposals](2.3.2-flows.md#route-and-condition-proposals)), or of a new Project Pipeline copied from a named one.
- How its page and its Stages look is [the flow editor's design](../design/pipeline-flow.html), in its Project Pipeline scenario.

### The move to routes back and Publish Stages

- One Office update moves every Pipeline to routes back and Publish Stages: the built-ins, the user's office-wide Pipelines, the Project Pipelines and each Task's own Stages, started or edited for it.
- A Task walks a moved Pipeline as before, but for three changes of the Publish Stage:
  - a conflict past the Conflict route's limit (the 4th) goes to the CTO first, then the user, as any route whose limit ran out ([When a limit runs out](2.3.2-flows.md#when-a-limit-runs-out)), where it asked the user directly;
  - a Resolve whose merge of the base is clean commits it and still runs its Agent's turn ([An Agent Stage may merge the base first](2.3.1-stages.md#an-agent-stage-may-merge-the-base-first)), where it ended Done with no turn;
  - a conflict in a Pipeline with no Agent Stage offers Publish again or Drop the Task, no longer Continue without publishing ([Publish's results](2.3.4-publish.md#publishs-results)).
- **On failure becomes a route back**:
  - each "On failure go back to Stage X, at most N times" becomes a route from the Stage to X with the Stage's failure condition and a limit of N, placed first among its routes;
  - a Script Stage's that already had a route for "ended Failed" keeps that route after the new one, as today's loop went first;
  - the rounds a running walk used on a loop count as the times its route back was followed.
- **A Script `publish` Stage becomes a Publish Stage**, keeping its key, name, position, target and routes, its Otherwise now taking Published and Nothing to publish.
  - Its On failure becomes its Failed route back, as above.
  - It gets no route for After publishing failed, which still goes to the CTO, then the user.
- **The conflict chain is drawn in** for each Publish Stage by the publishing mode in a Pipeline with an Agent Stage, as The Office put Resolve in until now:
  - a Conflict route to a new Resolve Stage, at most 3 times, the times a conflict came back so far counting;
  - Resolve, linked to the Resolve template, naming the first Agent Stage's Role or duty, with a budget of the largest Agent Stage budget plus 250k tokens;
  - Test after Resolve, a Script Stage running `test`, going back to Resolve when it fails, at most 2 times;
  - when the Publish's "After a conflict" was "Wait at a Gate for your review", a Gate **Review the resolved conflict** after the Test;
  - then a route on to the Publish, the chain's loop counted by the Conflict route's limit;
  - the chain's Stages take a new row under the Publish, in the columns just before its own, new columns made where there are too few.
- A Publish with no Agent Stage in its Pipeline gets no chain, and a Proof of concept one, pushing the branch only, none either: Proof of concept is otherwise unchanged.
- A walk that is in Resolve's Stages as The Office updates goes on in the drawn chain's Stages, their runs kept.
- **Each Project Pipeline becomes its built flow**: the Stages, routes and positions its base Pipeline and its Stage changes built as the update ran, kept as its own, with its name, description and Project, and "Copied from <base>" as its words.
  - The Tasks, defaults and Initiatives that named it name it still.
  - One that was Broken becomes what its base Pipeline gives with the Stage changes that still applied, and can't be chosen, as before, until the user saves it once; its page names each Stage change that didn't apply.
- Stages are linked to no template by the update, but the Resolve Stages it draws in.
- The "After a conflict" field, the base Pipeline, the Stage changes and the List editor are gone after it.
- The move ran in release 1.1.0, and a later release no longer can: updating from an earlier release to one after 1.1.0 fails while a Project Pipeline isn't moved yet, saying to start 1.1.0 once first.
### The move to positions

- One Office update (migration 0225) moves every Stage from a place, a column and a row, to a [position](2.3.2-flows.md#a-stages-position): the library's Pipelines, the Project Pipelines and each Task's own Stages.
- Each stored list is sorted once by its places (the columns left to right, a column's Stages top to bottom), so the Pipeline's order stays what it was, and its routes back with it.
- A Stage's position comes from its place:
  - `x` is its column × 308 (a card's 232 and a 76 gap);
  - `y` is the sum of the heights of the rows above it, each plus 22;
  - a row's height is its tallest card's across the Pipeline: 72, or 82 plus 22 per route row when a card lists its routes.
- A Stage that already has a position is left as it is, so the move can run twice.
- The place is kept, and every save from then on writes `place` as `{column: <its index in the order>, row: 0}` beside its position, so the previous release, reading places alone, sees the same order after a rollback.
- A Stage the previous release saved, with a place and no position, takes its position from its place as it is read.
- The built-in Pipelines carry the positions their old places give, in the order those places gave, so they open where they stood.
- Stage templates, built-in ones too, keep no position, as they kept no place.
- Open Proposals are converted as they are read ([Proposals](#proposals)).
