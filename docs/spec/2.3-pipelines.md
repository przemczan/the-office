# 2.3 Pipelines

From [08](../../.scratch/the-office/issues/08-pipelines.md) (amended by [25](../../.scratch/the-office/issues/25-agent-permissions.md)), [19](../../.scratch/the-office/issues/19-work-mockup.md), [21](../../.scratch/the-office/issues/21-role-capabilities.md).

- **Stage kinds:** **Agent Stage** (a Role does work), **Script Stage** (a Project command, named by its key, or publish; no model call; result recorded. A key the Project lacks, or a command whose line is blank, ends the Stage could-not-run, naming the key; it is never skipped. A test-kind command, under any key, leaves the branch as it was after its run; a build or lint one commits), **Gate** (the Task waits for the user, showing diff, results, Attachments, screenshots; UI acceptance is a Gate after a Stage that attached screenshots).
- **A Stage declares:** kind; Role, or command: `publish`, kept for Publish, or any key that follows the Project command key rules ([2.1](2.1-work.md)), never `install`, which runs before every Stage on its own; for an Agent Stage, how it narrows its Role card's permission profile, including which of the Project's commands its Agent may run ([6](6-permissions-and-safety.md)); a plain-words brief filled with the Plan, Definition of Done and earlier results; limits (rounds, budget); session (fresh by default, or continue the previous Stage's session only when the same Role did it); on failure. It ends **done**, **needs a Decision** (one the Agent opened with an Office tool, open a Decision or consult: the only way an Agent asks, the user's answer of 2026-10-26), or **failed**.
- **Loops, not branches:** a Pipeline is a straight list. The only control flow is "on failure go back to Stage X, at most N times". That covers test-fix rounds, review-fix rounds and repair after a failed Script Stage (a failed publish or test run hands to an Agent Stage with the error). One exception: when Publish shipped the work but its after publishing line failed, the failure never goes back through "on failure go back to Stage X" and uses no round; it is escalated straight away, to the CTO first, then the user ("Publish's before and after lines" below; the user's answer of 2026-11-13, reviewed by the CTO).
- **At a Gate** the user continues, with notes or none, drops the Task, or sends the work back with feedback to any earlier Stage but a Gate or a Publish (whose work has already left the workstation), using no round (the user's answer of 2026-10-26). An Agent Stage is briefed with the feedback; a Script Stage can't read it, so it simply runs again and the walk goes on from there, the feedback kept on its run and shown on its row. Notes the user continues with, such as which version of a design to build, are kept on the Gate's run and shown in its Stage history, and every later Agent Stage is briefed with them under its earlier Stages; they are offered only when an Agent Stage comes after the Gate, and refused otherwise, as nobody would read them, while blank notes are plain Continue (amended 2026-11-13, Task "Extend pipeline Gate").
- **Built-ins:** **Full** (Implement → Tests → Review & fix → Publish), **Quick fix** (Implement → Tests → Publish), **Document** (Produce → Review & fix). Planning is a Task state, not a Stage. Each Project names a default, the one its Tasks usually follow: one of its own Project Pipelines or an office-wide one (amended 2026-11-12). The picker lists the Project's default first, then its other Project Pipelines, then the office-wide ones; a Broken one is listed, flagged with why, and can't be chosen ("A Broken Project Pipeline" below); a new Task has no Pipeline until one is chosen (the user's words of 2026-11-11: "Pipeline before plannng is Full. I want it to be none with some placeholder-like pipeline... so I can clearly see that the pipeline is not yet determined based on the task."): the Planner proposes one from the Definition of Done, named against the Project's default in its Brief, which the user takes or declines (keeping the Task's Pipeline, when it has one) before the Task can be Ready, or the user chooses one, the default listed first; the user can swap it or **edit the Stage list for this Task** (add a Gate, drop or reorder, effort, session, budget; from tier 3 a Stage has no model of its own, so a Stage that needs another gets a Role of its own, the user, 2026-11-01). In that window a swap and an edit are both a draft: Save applies them, closing it drops them (the user, 2026-11-05). Started Stages are locked.
- **Review & fix** is one fresh-session Developer Stage: the Agent reviews against the Definition of Done and fixes what it finds, consulting (the CTO, then the user) only when it can't fix something itself.
- **Publish** is a Script Stage run by The Office: push and open a PR, or merge, per Project. A proof-of-concept publish target (work stays on a branch) is tier 2. A Task of an Initiative in a Project where it has a Pipeline publishes into the Initiative's branch, always by merge; a Publishing Task publishes that branch into the base branch by the Project's publishing mode (Defaults below: "Publishing into an Initiative's branch", "A Publishing Task's Publish").
- **Skipping:** an optional Stage is skipped when the Definition of Done is already met; otherwise skipping is the user's click.
- **Who is asked:** budget limits always ask the user. A round limit or a Stage failing with no retries left goes to the CTO first, who may send the Task back for one more round with guidance or pass it on (in tier 1: the user). Hard switches follow their value.
- **Library** (editor tier 2): it holds the office-wide Pipelines and the Stage templates, which are office-wide; each Project's Project Pipelines are not in it but on that Project's page ("Project Pipelines" below; amended 2026-11-12); one Stage editor serves the library, the Project Pipelines and "Edit for this Task". It flags a Role with Task limit none or let go (a Stage template's Role too), "continue" without the same Role before, and failure targets that aren't earlier. Saving a library Pipeline changes Tasks that haven't started and the Initiatives that name it in a Project whose Publishing Task hasn't started ([2.1](2.1-work.md#defaults); amended 2026-11-13); running ones keep their copy; a Task edited for itself keeps its Stages. Saving an office-wide Pipeline also changes the Project Pipelines built from it, and so the Tasks that haven't started on them.

## Defaults

Gaps no ticket settled, filled with the simplest choice consistent with the tickets and accepted by the user; each says when.

- **Project commands in tier 1** are edited directly on the Project page; Devops' Proposals join them in tier 2 ([08](../../.scratch/the-office/issues/08-pipelines.md) allows both). (accepted 2026-10-24)
- **The Office's own credentials for publishing** (git push, the pull request) are the Office identity's ([5.5](5.5-git-and-isolation.md#defaults)): Sign in with GitHub and the Office ssh key, used by Office code only; Agents never see them, and The Office's git never reaches the user's own keys or credential helpers. Push + PR needs Sign in with GitHub, so it is refused before the push without it. (accepted 2026-10-24; until tier 3 they were the user's, through git and `gh`; amended 2026-11-01, the user's answer)
- **Publish is a publishing mode, not a Project command:** push + PR, or merge, run by The Office's own git code, which is what keeps the credentials out of Agents' reach. The click-through's "Publish" command row becomes the publishing mode. (added while slicing tier 1, [24](../../.scratch/the-office/issues/24-slice-tier-1.md), accepted 2026-10-24)
- **Publish's before and after lines** (the user's answer of 2026-11-13, reviewed by the CTO): each Project has two optional one-line commands, **Before publishing** and **After publishing**, set on its Project page in the Commands block's Publish group beside the publishing mode, or by Devops' Proposal of commands. They are not Project commands: they have no key, no Pipeline runs them by name, `publish` stays a reserved key, and a blank line means nothing runs (never "could not run"). The Office's own git still pushes, opens the pull request or merges.
  - **Where and how they run:** in the Task's worktree, through the same command runner and time limit as a Script Stage's command (30 minutes), in the run environment when it is On, after the install when its inputs changed, with the Project's own variables, Secret ones included, and never The Office's GitHub token or ssh key: a script that needs a token gets it from a Secret variable. A script that waits on a GitHub Actions run can hit the time limit.
  - **Scope:** they run only when Publish ships by the publishing mode, for an ordinary Task or a Publishing Task; never for a fix Task publishing into its Initiative's branch, nor for the proof-of-concept branch-only target.
  - **Before publishing** runs before anything leaves. The Office commits what it changed, as for a build-kind command, and that commit is what Publish ships; the Stage then expects HEAD there. Its failure is an ordinary Script failure: nothing is published, and the on-failure loop applies.
  - **After publishing** runs once the publication shipped (a pull request opened, or a merge landed; in push + PR mode when the pull request opens, not when it merges upstream), before the worktree is removed, with `OFFICE_PUBLISHED_BRANCH`, `OFFICE_PUBLISHED_COMMIT` (the commit that shipped: after a merge, the merged commit), `OFFICE_PULL_REQUEST_URL` when a pull request opened, and `OFFICE_PUBLISHING_MODE` (`push-and-pull-request` or `merge`). After nothing to publish it doesn't run, and the outcome says so.
  - **Runs again:** both lines run again each time Publish runs (an on-failure retry, or again after Resolve), so each must be safe to run twice. What shipped is kept on the Publish run before the after line runs, so a run again after a failed after line runs only that line and never publishes again.
  - **A failed after line** ends the Stage with an outcome of its own, "Published; after publishing failed: <error>", as the work did ship; the worktree stays. It skips the on-failure loop and goes to the CTO, then the user, with **Retry** (runs only the after line) or **Continue** (the Stage is done with the failure noted, the worktree is removed, and the Pipeline goes on).
- **Merge mode when the base moved** (the user's answer of 2026-10-26): Publish fetches the base branch first. When the base moved on since the Task's branch left it, The Office rebases the branch onto the fetched base itself, under the repository's lock, and then fast-forwards the remote's base branch to it. A rebase that would conflict goes to Resolve, as in "Conflicts at Publish" below. Push + PR pushes the branch as it is and opens the pull request; there too, a branch that would conflict with the base goes to Resolve. (added while building tier 1; the conflict path amended on 2026-10-29)
- **The Changes tab after Publish shows what Publish shipped** (the user's answer of 2026-10-26): Publish records where the published branch forked from the base in a ref of The Office's own (`refs/office/published-from/<task>`). From then on Changes diffs the Task's branch from that commit, so it still shows the change after a merge, or after its pull request merges upstream. (added while building tier 1)
- **The CTO first on failures** (the user's answer of 2026-10-28): a Stage failing with no retries left, its loop's rounds used up or not, is put to the CTO when one is hired with Consultant on, a Script or Publish Stage as well as an Agent one, as The Office's Decision in a Consultation on the Task. The CTO answers in their own words, which send the Task back for one round with their guidance, or passes it on to the user; the options (more rounds, continue with the issues, drop) stay the user's, who may answer in the CTO's place. A Stage the CTO sent back once in a walk goes to the user when it fails again. The Definition of Done not reported met, a restart, a conflict at Publish the Agent gave up on and budget limits ask the user directly. (added while building tier 2)
- **A refused turn is no failure** (Task 3de35a58, 2026-11-13): a Stage whose turn, its first or its correction, is refused because its engine's usage window is used up doesn't fail. Its run ends held, as a Pause holds it ([2.1](2.1-work.md#defaults), "A pause by the usage window"); it isn't counted against "on failure go back to Stage X, at most N times", no CTO Consultation opens and no "failed" Outcome is raised. The Stage history records the run as held by the usage window. A user's Stop still outranks it.
- **Project commands by Proposal and by hand** (the user's answer of 2026-10-28): once Devops proposes Project commands, the user still edits them on the Project page too; "Ask Devops to propose a change" sits beside them, and Devops' Proposal card changes them when applied. This amends "Project commands in tier 1" above. A Proposal of commands may change the install command and the install inputs, add or change commands (whole, by key) and remove commands by key; it keeps each value as it was and as proposed, applies all or nothing, is refused once any of those values changed since, and is checked by the same rules as the Project page (the user, 2026-11-11).
- **The library editor** (the user's answer of 2026-10-28): in Settings › Pipelines the user makes a Pipeline from scratch or by duplicating one, edits any Pipeline's name, description and Stages, and removes one, refused while a Project names it as its default, a Task that hasn't started uses it or a shaping or active Initiative names it in a Project whose Publishing Task hasn't started (amended 2026-11-12; amended 2026-11-13, the Task "Implement initiatives pageredesign"). "Ask Devops" on a Pipeline opens a chat with Devops, who answers with a Proposal of the Pipeline's new Stages that the user applies. The built-ins are seeded into the library once and are then edited like any; the Onboard Pipeline can't be removed, since onboarding uses it. Stage templates sit beside the Pipelines there, as "Stage templates in tier 3" below says. Project Pipelines live on their Project's page, as its commands and skills do: its **Pipelines** section, which replaces its Default Pipeline section, holds the Project's default and its Project Pipelines, and there the user makes one from an office-wide Pipeline, edits its name, description, base Pipeline and Stage changes, makes it the default, and removes one ("Project Pipelines" below). Settings › Pipelines lists the office-wide Pipelines only; one that Project Pipelines are built from says "Built on by" and how many, and lists the Projects they belong to, each with how many it has and a link to its Pipelines section, never the Project Pipelines by name: those are listed on their Project's page alone (the user, 2026-11-12, at the Gate of the Task "Design: the Project Pipeline editor"). "Ask Devops" on a Project Pipeline, or on a Project's Pipelines section for a new one, opens a chat with Devops, who answers with a Proposal of the Project Pipeline (its name, description, base Pipeline and Stage changes) that the user applies. Such a Proposal keeps each value as it was and as proposed, applies all or nothing, is refused once any of those values changed since, and is checked by the same rules as the editor. How the editor looks is the design of the Task "Design: the Project Pipeline editor" (amended 2026-11-12). (added while building tier 2)
- **Stage templates in tier 3** (the user's answers of 2026-11-08): Stage templates live in Settings › Pipelines, beside the Pipelines. The user makes one from scratch, or with **Save as template** on any Stage in a Stage editor (a library Pipeline's or a Task's own Stages), and edits and removes templates there. The built-in Stages are seeded into the library once, as templates, like the built-in Pipelines, and are then edited and removed like any. A template is added to a Pipeline or to a Task's own Stages as a copy, so a later change to the template never changes a Pipeline or a Task. **Ask Devops** on a template opens a chat with Devops, who answers with a Proposal of the template's new Stage, which the user applies. Removing a template is never refused, since nothing points at it. A template's Role is flagged in the Stage editor like a library Pipeline's (Task limit none or let go), but a template is not a Pipeline, so it doesn't count as a Role a Pipeline names for the engine checks of [5.4](5.4-the-engine.md): nothing runs from it, and the Stage it adds is checked when its Pipeline or Task is saved. Letting go is not refused either way, as for Pipelines. (the user's answer of 2026-10-28 moved templates to tier 3; until then the library held Pipelines only and a Stage was added in the editor from its kind; postponed on 2026-11-08 and brought back the same day)
- **The proof-of-concept publish target** (the user's answer of 2026-10-28) is a Publish Stage's target, not a third publishing mode: a Publish Stage publishes by the Project's publishing mode (the default) or pushes the Task's branch only, with no pull request and no merge. The built-in **Proof of concept** Pipeline (Implement → Tests → Publish, pushing the branch only) uses it. This narrows "Publish is a publishing mode" above: still run by The Office's own git code, its target chosen per Stage. (added while building tier 2)
- **Conflicts at Publish** (the user's answer of 2026-10-29): the merge order stays first to Publish. When Publish's branch would conflict with the moved base, in either publishing mode, the Task's person (its Developer, or Devops on an Onboard Task) resolves it in the Task's worktree in a **Resolve** Stage: The Office's own git merges the fetched base into the Task's branch (one merge commit, not a rebase stop by stop) and leaves the conflicted files, the Agent edits files only ([5.5](5.5-git-and-isolation.md)), and The Office commits the merge. Then the Project's Test runs, then Publish runs again, bringing the merged branch to the base as it is (fast-forward in Merge mode), never rebasing the merge away. Proof of concept gets no Resolve, since it only pushes its branch (amended 2026-10-29). A Publish Stage says what follows a resolved conflict in its "After a conflict" field: publish automatically, the default, or wait at a Gate for the user's review between the Test and Publish (the user's answer of 2026-11-06, which replaces the Gate every resolved conflict stopped at). When the Agent gives up, the user is asked directly, not the CTO first: resolve it themselves in the worktree, or drop the Task. This amends "Merge mode when the base moved" above, where such a conflict asked the user.
- **The Task's branch keeps up with the base** (the user's answer of 2026-11-06): planning makes the worktree, so a Task can start long after it. As the Task's first Stage starts, The Office fetches the base and brings the branch to it: a fast-forward when the branch has nothing of its own, one merge commit otherwise. One that would conflict leaves the branch as it was, and the Stage's Agent is told. An Agent in a Stage can ask for the same at any time with the `update_branch` Office tool: The Office commits the Stage's work so far and merges the base in, and a conflict stays in the worktree for the Agent to resolve, editing files only, which The Office commits when the Stage ends. Publish's own handling of a base that moved after that stays as above. For a Task of an Initiative in a Project where it has a Pipeline, "the base" here means the Initiative's branch, then the base branch, brought in in that order, at the first Stage, in `update_branch` and at Resolve alike ("Publishing into an Initiative's branch" below; amended 2026-11-12).
- **A branch moved outside The Office** (the user's answer of 2026-11-06): as a Stage starts, a branch that moved along the base (the new HEAD descends from where The Office left it and is in the freshly fetched base's history, with nothing uncommitted) is taken as it is, and the Stage's Agent is told. Any other move stops the Stage before it runs, using no round, with a Decision put to the user directly, not the CTO first: keep the branch as it is, say they put it back, or drop the Task; words of their own keep the branch and guide the Stage. The check after each Stage stays strict: a Stage that moved the branch itself fails.
- **Script Stages in the run environment** (from the Plan of Task 72807e9a, 2026-11-08): with the Project's Run environment On, a Script Stage's install and command run in the Task's run environment, with only the Project's own variables; Off or Not decided yet runs them on the workstation. When every run environment Run environments at once allows is in use, the Stage waits: its rail state, the small pipeline and the Stage history read "Waiting for a run environment", with no live dot, until its command starts, and its time limit counts from then. A run environment that can't be made or started fails the Stage with why, and nothing runs on the workstation instead.
- **Statements Out of reach** (the user, 2026-11-08, Task 0287a9a5): an Agent Stage's done result may list Definition of Done statements it can't verify where it works, each with why; the last done Agent report counts, as for Reported met, so a later one takes back what it leaves out. When the Pipeline ends with the Definition of Done not reported met, the Decision lists what the Stage it would run again can address apart from what is Out of reach, for the user to check. It recommends running that Stage once more while it can address any, that round's Brief naming only those, and Mark the Task Done, the user checking those statements first, when it can address none.
- **A Pipeline needs the commands it runs** (from the Plan of Task 82081443, 2026-11-11): the commands a list of Stages runs are each Script Stage's key but `publish`, each key an Agent Stage narrows its Project commands to, plus `test` where Resolve's Test may run it (a Publish by the publishing mode beside an Agent Stage, as "Conflicts at Publish" above runs the Project's Test, which is its `test` command). The Office refuses, naming the Pipeline, the Project and each missing key: choosing a Pipeline for a Task (the Planner's proposal, the user's confirm or swap, auto mode's accept, and a Project's "Set up the run environment" Task) when the Task's Project lacks one; making a Pipeline a Project's default (on the Project page, in Add a Project, or by Devops' Project to onboard) when that Project lacks one; saving a library Pipeline, or applying Devops' Proposal of its Stages, when a Project with it as default, or with a Task on it that hasn't started, or where an open Initiative names it and that Project's Publishing Task hasn't started, lacks one, which the editor's check shows on the Stage before Save; an edit of a Task's own Stages, for the Stages not locked yet; and choosing or changing an Initiative's Pipeline in a Project, while shaping or by the CTO's Proposal, when that Project lacks one, the check being per Project: another Project the Initiative spans isn't weighed, and a Project with None is never checked, so adding or moving one of the Initiative's Tasks into a Project it doesn't span yet, which starts with None, checks nothing ([2.1](2.1-work.md#defaults)) (amended 2026-11-12; amended 2026-11-13, the Task "Implement initiatives pageredesign"). Removing a command a Project's default Pipeline runs is refused too ([2.1](2.1-work.md)), so a Project's default always runs there, and a Task created, shaped, added by an Initiative or moved takes it unchecked. Keys alone count: a command left blank passes and fails could-not-run when it runs. Removing a command another Pipeline runs is not refused: that Stage fails could-not-run, naming the key. Stage templates aren't checked, since nothing runs from them. A Stage is never skipped for a missing command. The built-in Pipelines and Stage templates name only `test` and `publish`. For a Project Pipeline, "the Projects" above is its own Project only, and saving its base Pipeline weighs each Project Pipeline built from it against its own Project ("A Broken Project Pipeline" below; amended 2026-11-12).
- **An Agent Stage's Project commands** (from the Plan of Task c45c4de5, 2026-11-11): an Agent Stage's permissions may list the keys of the Project's commands its Agent may run, which narrows the Role card's, never widens it. Without the list the Stage keeps every Project command, as Stages stored before do; an empty list, a key listed twice, a malformed key, `install` and `publish` are refused. The Stage keeps the listed keys the Project has and has set, in the Project's order: a key it lacks or left blank adds nothing. Install stays apart: never listed, run by its key under the Run installs Hard switch as before. Under the run permission **the Project's own commands** the Brief names only the kept commands and the engine allows only their lines; under **anything** the shell stays free, and the Brief says which of the Project's commands to run and names the others as not for this Stage; under **read-only git** the words don't change. Under every one, run_project_command refuses a key outside the list before anything runs, naming the commands the Stage may run; a command line the Agent writes out is judged as any other. A list naming a key the Project lacks is refused by the missing-command check when the Pipeline is chosen for a Task or made the Project's default. Example: the-office's Developer Stages keep `test` (`npm run verify`), not `test-full`.
- **An Agent Stage's message names the Stages after it** (the user's decision of 2026-11-13, Task 4c2cfba7): the message that tells an Agent what its Stage asks, which a new session gets after the Brief and a continued one alone, has a Later Stages section after the Stage's brief. It lists every Stage after this one in the Pipeline's order, as the walk has them: a Script Stage with the command line it runs (Publish as The Office publishing the Task's work), an Agent Stage with its Role and its brief, and a Gate by name, where the user looks at the work. An optional Stage is marked optional, and a Stage whose on-failure loop goes back to this one says that its failure brings the work back here. The last Stage's message says no Stage comes after it. Every run of the Stage gets it, also one an on-failure loop, a Gate's feedback or an answered Decision brought back. The list is plain facts; what an Agent leaves to the later Stages is in its instructions.
- **Publishing into an Initiative's branch** (2026-11-12, the Initiative 1116efba; details settled with the Plan of Task 12e9ab91): a Task of an Initiative in a Project where it has a Pipeline ([2.1](2.1-work.md#defaults)) publishes into the Initiative's branch ([5.5](5.5-git-and-isolation.md#defaults)), always by merge and never by a pull request, whatever the Project's publishing mode. The Office fetches both branches and brings into the Task's branch first the Initiative's branch, then the base branch, each a fast-forward, or one merge commit when the Task's branch has work of its own; then it fast-forwards the Initiative's branch to the result. It never rebases, since the Task's branch can hold a merge of the base: this narrows "Merge mode when the base moved" above for these Tasks. A merge that would conflict goes to **Resolve**, as in "Conflicts at Publish" above: the Task's person in its worktree, then Test, then Publish. Every Publish of one of the Initiative's Tasks so brings the base into the Initiative's branch, which is how the branch keeps up with the base. A proof-of-concept Publish still pushes only the Task's branch, so it doesn't reach the Initiative's branch.
- **A Publishing Task's Publish** (2026-11-12, the Initiative 1116efba; details settled with the Plan of Task 12e9ab91): a Publishing Task's worktree holds the Initiative's branch itself, and its Stages commit there. Its Changes tab diffs that branch from where it forks from the fetched base, so its Gate shows the full change; after Publish, Changes reads from the published-from ref, as "The Changes tab after Publish shows what Publish shipped" above says. It publishes by the Project's publishing mode: Push + PR pushes the Initiative's branch and opens a pull request from `initiative/<short name>`, or updates and links one already open from it; Merge mode merges the moved base into the Initiative's branch with one merge commit (no rebase), then fast-forwards the base. A conflict in either mode goes to Resolve in its worktree. A fix Task's Publish into the branch waits for a running Stage of the Publishing Task to end; The Office then moves the Publishing Task's worktree to the new commit and tells its next Stage's Agent. An Initiative's Pipeline without a Gate is allowed: the picker and the Initiative page warn "publishes without your review" for that Project.
- **Project Pipelines** (2026-11-12, the Initiative 5006c803; details settled with the Plan of Task dcf1ca8c): a **Project Pipeline** belongs to one Project. It has a name, a description, a **base Pipeline** (one office-wide Pipeline, never another Project Pipeline) and an ordered list of **Stage changes**, each one of five: **Insert before** a Stage, **Insert after** a Stage, **Replace** a Stage (each with a whole new Stage), **Change** a Stage (only the fields it gives, such as its brief, Role, limits, session, on failure or permissions) and **Remove** a Stage. Each Stage change names its Stage by its key, shown by the Stage's name: one of the base Pipeline's Stages, or one an earlier Stage change inserted; an inserted Stage's key must be new among the built Stages. It is built whenever it is read: the base Pipeline's current Stages, then each Stage change in order, so an edit to the base Pipeline reaches it; only a started Task keeps a copy of its Stages. Its name is unique among the office-wide Pipelines and its Project's own; two Projects may use the same name, and making or renaming an office-wide Pipeline is refused when the name is a Project Pipeline's, naming that Project. It is kept in The Office's records, beside the office-wide Pipelines. It is checked by the rules of the library's Pipelines on its built Stages (the Role flags, "continue" without the same Role, failure targets that aren't earlier, "A Pipeline needs the commands it runs" and "An Agent Stage's Project commands" above), which weigh its own Project only. It can be chosen only by a Task of its Project, as that Project's default, and as an Initiative's Pipeline in that Project; another Project is refused it ([2.1](2.1-work.md#defaults); amended 2026-11-13, the Task "Implement initiatives pageredesign", replacing "an Initiative's Pipeline is always office-wide"). Removing it is refused while it is its Project's default, a Task that hasn't started uses it, or a shaping or active Initiative names it in its Project whose Publishing Task hasn't started; removing an office-wide Pipeline is also refused while a Project Pipeline is built from it, which amends "The library editor" above.
- **A Broken Project Pipeline** (2026-11-12, the Initiative 5006c803; details settled with the Plan of Task dcf1ca8c): a Project Pipeline is **Broken** when building it fails: a Stage change names a key that isn't there, an inserted Stage's key is already there, or a loop ("on failure go back to") points at a Stage that isn't in the built Stages or isn't earlier. Saving an office-wide Pipeline that would break one warns before Save, in the editor and when applying Devops' Proposal of its Stages alike: the warning lists each Project Pipeline it breaks, with its Project and why, and the user can save anyway. The commands check of such a save weighs each Project Pipeline built from it against its own Project, as it weighs Projects today ("A Pipeline needs the commands it runs" above). A Broken one is flagged on its Project's page (in its list, and on the default when it is the default), counted under its Project in its base Pipeline's "Built on by" in Settings › Pipelines, and in the Task's picker; it can't be chosen for a Task, made a default or proposed by the Planner until its Stage changes are fixed. A Task that hasn't started on it, an Initiative's Task in Backlog among them, is flagged on the Task page, and Start (and Start Ready Tasks, [2.1](2.1-work.md#defaults)) is refused for it, naming the Pipeline and why, until it is fixed or the Task's Pipeline is swapped. An Initiative that names it in its Project is weighed as for a Task that hasn't started: that Project's Publishing Task not yet started can't start until it is fixed, and Confirm refuses a Broken one (amended 2026-11-13). Started Tasks keep their own Stages, and so does a Task edited for itself. A Project Pipeline's own save, and applying Devops' Proposal of it, are refused while it would be Broken, so only an office-wide Pipeline's save, which warns first, breaks one. Each Stage change keeps the name its Stage had when the Project Pipeline was last saved, for its words alone, so a Stage gone from the base Pipeline still reads by its name ("Changes Produce, which Document no longer has"); the key alone still matches it. How it reads and is fixed is the design of the Task "Design: the Project Pipeline editor" (proposed 2026-11-12, `docs/design/project-pipelines.html`).
