# 2.3 Pipelines

From [08](../../.scratch/the-office/issues/08-pipelines.md) (amended by [25](../../.scratch/the-office/issues/25-agent-permissions.md)), [19](../../.scratch/the-office/issues/19-work-mockup.md), [21](../../.scratch/the-office/issues/21-role-capabilities.md); flows from the Initiative 4d4d2101 "More pipeline flexibility" (2026-11-17), whose "A Pipeline is a flow" replaces "Loops, not branches", where a Pipeline was a straight list.

- **Stage kinds:** **Agent Stage** (a Role does work), **Script Stage** (a Project command, named by its key, or publish; no model call; result recorded. A key the Project lacks, or a command whose line is blank, ends the Stage could-not-run, naming the key; it is never skipped. A test-kind command, under any key, leaves the branch as it was after its run; a build or lint one commits), **Gate** (the Task waits for the user, showing diff, results, Attachments, screenshots; UI acceptance is a Gate after a Stage that attached screenshots).
- **A Stage declares:** kind; a Role or a duty (amended 2026-11-13, "A Stage names a Role or a duty" below), or command: `publish`, kept for Publish, or any key that follows the Project command key rules ([2.1](2.1-work.md)), never `install`, which runs before every Stage on its own; for an Agent Stage, how it narrows its Role card's permission profile, including which of the Project's commands its Agent may run ([6](6-permissions-and-safety.md)); a plain-words brief filled with the Plan, Definition of Done and earlier results; limits (rounds, budget); session (fresh by default, or continue the previous Stage's session only when the same person did it); on failure; its routes out ("A Pipeline is a flow" below). It ends **done**, **needs a Decision** (one the Agent opened with an Office tool, open a Decision or consult: the only way an Agent asks, the user's answer of 2026-10-26), or **failed**.
- **A Pipeline is a flow** (the Initiative 4d4d2101 "More pipeline flexibility", 2026-11-17): its Stages are the flow's nodes, joined by **routes**. A route leads from one Stage to another, or to the Pipeline's **End**, and may carry a **condition**; a route with none always holds. Several routes may leave a Stage, so paths part, and several may lead into one, so paths meet again (a **join**). Only one path runs at a time: the **walk** is at one Stage at a time, and as a Stage ends it follows one route out of it, so a Stage that joins paths runs once each time the walk arrives, never waiting for another path. A walk starts at the Pipeline's first Stage and ends when it follows a route to End; a Stage with a route to End is a **final Stage**. The Stages keep an order, **the Pipeline's order**, in which every route leads forward, so routes alone never loop; "earlier" and "later" below mean in this order. A Stage the walk went past on another path is **Not taken** in that walk: it holds no run, and the Pipeline rail shows it so. Conditions are data that The Office weighs itself, with no model call and no Agent: the user sets them up in the Stage editor. Each Stage also keeps its place on the flow editor's canvas, a column and a row, which draws the flow and gives the Pipeline's order, never which route the walk follows: the order reads the columns left to right and a column's Stages top to bottom. A route always leads to a later column (or to End), never to a Stage in its own column, and a Stage's on-failure target is in an earlier column, so a column holds only Stages on paths that part and its top-to-bottom order is only for listing; a route that a move leaves leading to its own or an earlier column is refused by the Validation rules below, naming it. The previous Stage a condition tests is the route's own Stage, the one the walk just left, whichever path it arrived by. The conversion puts each Stage in a column of its own on one row; a Project Pipeline's built flow takes its base Pipeline's places, an inserted Stage getting a column of its own just after (or before) its Stage's column, on its row, the later columns moving right by one (the CTO's answer of 2026-11-17; designed by the Task "Design: the Pipeline flow editor", 2026-11-17, [docs/design](../design/README.md#the-pipeline-flow-editor-what-it-proposes), and built by the Task "The Pipeline flow editor in Settings › Pipelines and on a Project page").
  - **Which route the walk follows:** the routes out of a Stage are in an order the user sets, and the walk follows the first whose condition holds. A route with no condition, which always holds, therefore goes last ("otherwise"): a route after it is refused, as it could never be followed. At most one route leads from a Stage to any one place: two cases that lead there are one route whose condition joins them with Any of. The routes are weighed as the Stage ends done (a Gate's Continue, a Publish whose after publishing failure was continued past), as the user skips it, or once a failure has nowhere else to go ("When a Stage fails" below); the routes of a Stage that needs a Decision are weighed only once the Decision is answered and the Stage has ended.
  - **The built-in conditions** each test one Stage, either **the previous Stage** (the one the route leaves) or a Stage named by its key and shown by its name, which must be the route's own Stage or an earlier one, by that Stage's latest run: it **ended Done**, it **ended Failed** (a Script Stage that could not run or timed out among them), it **was Skipped** (by the user's click, "Skipping" below); it **changed files** (its run left the Task's branch with changes against where the run started) or **changed no files**; it **ran N or more times** (every run its Stage history lists for this Task, its latest included, N from 1). Or they test the Definition of Done: **all Reported met**, or **some not Reported met** (an Out of reach statement is not met). A named Stage that hasn't run on this Task holds none of the outcome or file tests and has run 0 times. Tests combine in groups: **All of** (AND) holds when every test or group in it holds, **Any of** (OR) when one does, and groups nest. The Office weighs them in the order given and stops once the result is settled, so a test after it doesn't run.
  - **The Project-command condition** is a test that names one of the Project's commands by its key (the key rules of [2.1](2.1-work.md), never `install` or `publish`), and holds when the command exits 0. It runs as a Script Stage's command does: in the Task's worktree, through the same command runner and time limit, in the run environment when it is On, after the install when its inputs changed, with the Project's own variables, Secret ones included, and never The Office's GitHub token or ssh key. Like a test-kind command, it leaves the branch as it was. It gets the Task's earlier Stage runs as a JSON file whose path is in `OFFICE_STAGE_RUNS_FILE`, written outside the worktree where the command can read it (in the run environment, inside it). Any other exit means the test doesn't hold. A command that can't be weighed (the key the Project lacks, a blank line, the time limit reached, or the run environment can't start) doesn't count as not holding: the walk stops as when no route holds, the Decision saying why. Each run is kept on the run of the Stage the route leaves, with its command line, exit code and output, and shown in its Stage history. Its key counts among the commands the Pipeline runs ("A Pipeline needs the commands it runs" below). The file's shape, version 1, which later versions only add to:

    ```json
    {
      "version": 1,
      "task": { "id": "6b5af1e7-…", "title": "…", "project": "the-office" },
      "route": { "from": "tests", "to": "review" },
      "definitionOfDone": [
        { "number": 1, "statement": "…", "state": "reported-met" },
        { "number": 2, "statement": "…", "state": "out-of-reach", "why": "…" },
        { "number": 3, "statement": "…", "state": "not-met" }
      ],
      "stageRuns": [
        {
          "stage": "implement",
          "name": "Implement",
          "kind": "agent",
          "run": 1,
          "startedAt": "2026-11-17T10:00:00.000Z",
          "endedAt": "2026-11-17T10:40:00.000Z",
          "outcome": "done",
          "changedFiles": ["docs/spec/2.3-pipelines.md"],
          "handoverNote": "…",
          "error": null,
          "command": null
        },
        {
          "stage": "tests",
          "name": "Tests",
          "kind": "script",
          "run": 1,
          "startedAt": "2026-11-17T10:41:00.000Z",
          "endedAt": "2026-11-17T10:49:00.000Z",
          "outcome": "failed",
          "changedFiles": [],
          "handoverNote": null,
          "error": "…",
          "command": { "key": "test", "exitCode": 1 }
        }
      ]
    }
    ```

    `route.to` is a Stage's key, or `null` for End. `stageRuns` holds every run of the Task that ended, Resolve's Stages' among them, in the order they started, the run of the Stage the route leaves last. `kind` is `agent`, `script` (Publish's runs too) or `gate`; `run` numbers the Stage's runs from 1, as its Stage history does; `outcome` is `done`, `skipped`, `failed`, `needs-decision` or `held` (a run a Pause or the usage window held, "A refused turn is no failure" below); `changedFiles` lists the paths the run changed in the Task's branch; `handoverNote` is the Agent's, else `null`; `error` is a failed run's; `command` is a Script Stage's key and exit code, the exit code `null` when the command didn't run.
  - **When no route holds:** when every route out of a Stage carries a condition and none holds, the walk stops before going on, using no round, with a Decision put to the user directly, not the CTO first, a form of one choice: each route out of the Stage, by where it leads ("Go on to Review"), to follow anyway, or drop the Task; words of their own, the question's comment with no option picked, are kept for the Stage the walk goes on to, as a Gate's notes are. The Stage editor warns about a Stage whose routes all carry a condition, but doesn't refuse it.
- **On failure, a loop apart from routes:** "on failure go back to Stage X, at most N times" stays a Stage setting, apart from routes, so a simple Pipeline stays simple: X must be earlier, and a path of routes must lead from X to the Stage. It is the only way back: going back, the walk runs X again and goes on from it by its routes, every condition weighed afresh, so the path may differ from the last time. That covers test-fix rounds, review-fix rounds and repair after a failed Script Stage (a failed publish or test run hands to an Agent Stage with the error).
  - **When a Stage fails:** its on-failure loop goes first, while it has rounds left. Then a route counts only if its condition says the Stage ended Failed, as the previous Stage's "ended Failed" test on its own or within an All of group at its top, so a route with no condition or any other never carries a failure on; the walk follows the first such route that holds. With none, the failure goes to who is asked ("Who is asked" below); when they continue with the issues, the Stage's routes are weighed as usual, its outcome staying Failed.
  - One exception: when Publish shipped the work but its after publishing line failed, the failure never goes back through "on failure go back to Stage X" and uses no round; it is escalated straight away, first to the holder of Asked first when a Stage runs out of tries, then to the user (amended 2026-11-13; "Publish's before and after lines" below; the user's answer of 2026-11-13, reviewed by the CTO).
- **Validation:** the Stage editor, the Proposals below and the conversion check a flow by these rules, and Save (or Apply) is refused, naming the Stage and the rule, while one fails: **no unreachable Stage**, as a path of routes, whatever their conditions, leads from the first Stage to every Stage; **a route out of every non-final Stage**, so every Stage has at least one route out, a final Stage's to End, and a Stage left with none is refused rather than read as an end; **cycles only through on-failure loops**, as every route leads to a later Stage or to End, a route back being refused with the on-failure setting named as the way back. Beside them: a route after one with no condition, two routes from one Stage to one place, a condition naming a Stage that isn't the route's own or an earlier one, and a Project-command condition naming `install`, `publish` or a malformed key are refused; a Stage whose routes all carry a condition is warned about ("When no route holds" above). The Library's other flags stay as they are ("Library" below). Going back by a Gate's Send back or the Definition of Done check's one more round is no route and no cycle.
- **The optional setting becomes conditions:** a Stage's **optional** setting ("skipped when the Definition of Done is already met") goes; the conversion below writes it as routes. Where the Stage after a Stage X is optional, X's routes are: to that Stage, when the Definition of Done has some not Reported met; otherwise to the first Stage after it that isn't optional, or End. As skipping a Stage changes nothing that is met, this runs and passes by the same Stages the optional setting did. An optional first Stage simply stays first: as the walk starts nothing is Reported met yet, so the setting never skipped it. A Stage the user wants run only while something is unmet gets that route by hand from then on.
- **Converting existing Pipelines** (once, as the release with flows starts): every stored office-wide Pipeline, the built-ins among them, and every Task's own copy of its Stages (a started Task's, or one edited for itself) becomes the same flow drawn as a straight line: its Stages in their order as the Pipeline's order, one route with no condition from each Stage to the next and from the last to End, the optional setting written as above. Each "on failure" setting stays as it was. Project Pipelines keep their Stage changes, which build the same straight line on the converted base ("Project Pipelines" below). Stage templates have no routes and don't change. Tasks already running carry on unchanged: their copy converts the same way, so the Stages left run in the same order by the same rules, their runs and Stage history stay as they were, and their started Stages stay locked; the one difference is that a Stage the optional setting would have skipped shows Not taken instead of a Skipped run. The stored Stages keep their order and what the previous release reads, the optional setting among them, which this release no longer reads or shows, the routes added beside them, so a rollback still walks them as a list ([AGENTS.md](../../AGENTS.md), "Migrations keep the previous release working").
- **Agents propose route and condition changes** the same way they propose Stage changes today, and nobody but the user applies them: Devops' (the holder of Onboards and repairs Projects') Proposal of a library Pipeline's new Stages ("The library editor" below) is a Proposal of its new flow, its Stages and their routes with their conditions, such as "run Review only when Tests changed files or ended Failed, otherwise Publish"; a Proposal of a Project Pipeline carries Stage changes that change routes too ("Project Pipelines" below). The Proposal card shows each route as it was and as proposed, its condition in plain words. The user applies it, all or nothing, or declines it, keeping the Pipeline as it is; it is refused once any of those values changed since, and checked by the Validation rules above and the editor's own. How the card and the editor look is the design of the Task "Design: the Pipeline flow editor" (`docs/design/pipeline-flow.html`).
- **At a Gate** the user continues, with notes or none, drops the Task, or sends the work back with feedback to any Stage the walk ran before the Gate but a Gate or a Publish (whose work has already left the workstation), using no round (the user's answer of 2026-10-26; amended 2026-11-17 for flows). An Agent Stage is briefed with the feedback; a Script Stage can't read it, so it simply runs again and the walk goes on from there by its routes, the feedback kept on its run and shown on its row. Notes the user continues with, such as which version of a design to build, are kept on the Gate's run and shown in its Stage history, and every later Agent Stage is briefed with them under its earlier Stages; they are offered only when an Agent Stage comes after the Gate, and refused otherwise, as nobody would read them, while blank notes are plain Continue (amended 2026-11-13, Task "Extend pipeline Gate").
- **Built-ins:** **Full** (Implement → Tests → Review & fix → Publish), **Quick fix** (Implement → Tests → Publish), **Document** (Produce → Review & fix), each a straight line: one route with no condition from each Stage to the next, and from the last to End. Each built-in Agent Stage names the duty whose default holder is the Role it named before: Implement, Review & fix and Produce name Implements; the Onboard Pipeline's Onboard Stage and the Set up run environment Pipeline's Set up Stage name Onboards and repairs Projects; the built-in Stage templates likewise. An Office with today's Roles sees no change; Plans and Reviews are for the Pipelines and Stages the user builds (amended 2026-11-13). Planning is a Task state, not a Stage. Each Project names a default, the one its Tasks usually follow: one of its own Project Pipelines or an office-wide one (amended 2026-11-12). The picker lists the Project's default first, then its other Project Pipelines, then the office-wide ones; a Broken one is listed, flagged with why, and can't be chosen ("A Broken Project Pipeline" below); a new Task has no Pipeline until one is chosen (the user's words of 2026-11-11: "Pipeline before plannng is Full. I want it to be none with some placeholder-like pipeline... so I can clearly see that the pipeline is not yet determined based on the task."): the Planner proposes one from the Definition of Done, named against the Project's default in its Brief, which the user takes or declines (keeping the Task's Pipeline, when it has one) before the Task can be Ready, or the user chooses one, the default listed first; the user can swap it or **edit the flow for this Task** (add a Gate, remove or reorder Stages, change their routes and their conditions, effort, session, budget; from tier 3 a Stage has no model of its own, so a Stage that needs another gets a Role of its own, the user, 2026-11-01; amended 2026-11-17 for flows), checked by the Validation rules above. In that window a swap and an edit are both a draft: Save applies them, closing it drops them (the user, 2026-11-05). Started Stages, and the routes out of them, are locked. A Stage has started once it ran: it has a run of the Task's, ended or not, held or skipped. A started Stage keeps its fields, its routes out (where each leads, its condition and their order) and its place, so no Stage can be put straight after it; a route into it can still be drawn. A Stage not reached yet, or Not taken, can still be changed, moved and removed, wherever it stands in the order (amended 2026-11-17, Task 3ff93a77; the user's answer of 2026-11-17: the lock is strict).
- **Review & fix** is one fresh-session Stage naming Implements: the Agent reviews against the Definition of Done and fixes what it finds, consulting (the holder of Asked first when a Stage runs out of tries, then the user) only when it can't fix something itself (amended 2026-11-13).
- **Publish** is a Script Stage run by The Office: push and open a PR, or merge, per Project. Either way one change is one commit: merge lands the Task on its base as one commit with the Task's commit message, and a PR is titled and worded by that message for its squash merge; the Stage commits stay on the Task's branch as the detail of how it was done (Defaults below: "The Task's commit message"). A proof-of-concept publish target (work stays on a branch) is tier 2. A Task of an Initiative in a Project where it has a Pipeline publishes into the Initiative's branch, always as one commit; a Publishing Task publishes that branch into the base branch by the Project's publishing mode, carrying those commits unchanged (Defaults below: "Publishing into an Initiative's branch", "A Publishing Task's Publish").
- **Skipping** is the user's click: a skipped Stage ends Skipped, running nothing, and the walk follows its routes. A Stage the Pipeline runs only in some cases is a route with a condition, not a skip ("The optional setting becomes conditions" above; amended 2026-11-17).
- **Who is asked:** budget limits always ask the user. A round limit or a Stage failing with no retries left goes first to the holder of Asked first when a Stage runs out of tries, with Consultant on, who may send the Task back for one more round with guidance or pass it on; else to the user (in tier 1: the user; amended 2026-11-13). Hard switches follow their value.
- **Library** (editor tier 2): it holds the office-wide Pipelines and the Stage templates, which are office-wide; each Project's Project Pipelines are not in it but on that Project's page ("Project Pipelines" below; amended 2026-11-12); one Stage editor serves the library, the Project Pipelines and "Edit for this Task". It flags a Role with Task limit none or let go (a Stage template's Role too), a duty nobody holds or held by a Role with Task limit none, "continue" without the same Role or the same duty in the Stage before, and failure targets that aren't earlier or from which no path of routes leads to the Stage (amended 2026-11-13; amended 2026-11-17), beside the Validation rules above, which refuse Save. "The Stage before" means the Stage before it on every path of routes into it: a "continue" Stage that joins paths from different Stages is flagged. Saving a library Pipeline changes Tasks that haven't started and the Initiatives that name it in a Project whose Publishing Task hasn't started ([2.1](2.1-work.md#defaults); amended 2026-11-13); running ones keep their copy; a Task edited for itself keeps its Stages. Saving an office-wide Pipeline also changes the Project Pipelines built from it, and so the Tasks that haven't started on them.

## Defaults

Gaps no ticket settled, filled with the simplest choice consistent with the tickets and accepted by the user; each says when.

- **A Stage names a Role or a duty** (the user's answers of 2026-11-13, the Initiative b62c4d5e; details settled with the Plan of Task 70a243f5): an Agent Stage names a Role key or a duty ([2.2](2.2-people.md#defaults), "Duties"). A Stage naming a duty runs as whoever holds the duty when the Stage starts, and a started Stage keeps its person. While the duty is unheld, the Pipelines naming it are flagged, and Start (and Start Ready Tasks, [2.1](2.1-work.md#defaults)) is refused for a Task on one, naming the duty and pointing to Settings › Duties. A "continue" Stage whose person differs from the Stage before it runs in a fresh session, and its Stage history says why. Stored Pipelines and templates change once: in the seeded built-in Pipelines and built-in Stage templates, the Stages naming `developer` move to Implements and those naming `devops` to Onboards and repairs Projects; Pipelines and templates the user made keep their Role keys.
- **Project commands in tier 1** are edited directly on the Project page; Devops' Proposals join them in tier 2 ([08](../../.scratch/the-office/issues/08-pipelines.md) allows both). (accepted 2026-10-24)
- **The Office's own credentials for publishing** (git push, the pull request) are the Office identity's ([5.5](5.5-git-and-isolation.md#defaults)): Sign in with GitHub and the Office ssh key, used by Office code only; Agents never see them, and The Office's git never reaches the user's own keys or credential helpers. Push + PR needs Sign in with GitHub, so it is refused before the push without it. (accepted 2026-10-24; until tier 3 they were the user's, through git and `gh`; amended 2026-11-01, the user's answer)
- **Publish is a publishing mode, not a Project command:** push + PR, or merge, run by The Office's own git code, which is what keeps the credentials out of Agents' reach. The click-through's "Publish" command row becomes the publishing mode. (added while slicing tier 1, [24](../../.scratch/the-office/issues/24-slice-tier-1.md), accepted 2026-10-24)
- **The Task's commit message** (the CTO's Task of 2026-11-15): the commit convention belongs to the Project, as its own docs define it (CLAUDE.md, AGENTS.md, README, CONTRIBUTING and the like); The Office decides only when the Project has none. Publish lands each Task on its base as one commit, whatever the convention, and the Stage commits stay on the Task's branch as the detail of how it was done. That commit's message is kept on the Task ([2.1](2.1-work.md)): the Planner suggests it with the Plan through the `write_commit_message` Office tool, following the Project's convention; it is only a suggestion, so every Agent Stage sees it in its Brief and updates it with the same tool when its work changes what it should say, and the last Agent Stage before a Publish that lands it (not a proof-of-concept Publish, never Resolve) is told to recheck it against the Task's whole diff and fix it where it no longer fits. The user edits it on the Task page until Publish lands it; then it no longer changes and the page shows it as published. With none written, Publish uses the Task's title with the Description's first paragraph below it as a short summary. With Push + PR, the message's first line is the pull request's title and the rest its body, ready for GitHub's squash merge; the Stage results stay on the Task page. Into an Initiative's branch each Task lands the same way, as one commit, and the Publishing Task carries those commits to the base unchanged (its own pull request is merged, not squashed). The Office's own merges of the base into an Initiative's branch stay on it and reach the base too.
- **Publish's before and after lines** (the user's answer of 2026-11-13, reviewed by the CTO): each Project has two optional one-line commands, **Before publishing** and **After publishing**, set on its Project page in the Commands block's Publish group beside the publishing mode, or by Devops' Proposal of commands. They are not Project commands: they have no key, no Pipeline runs them by name, `publish` stays a reserved key, and a blank line means nothing runs (never "could not run"). The Office's own git still pushes, opens the pull request or merges.
  - **Where and how they run:** in the Task's worktree, through the same command runner and time limit as a Script Stage's command (30 minutes), in the run environment when it is On, after the install when its inputs changed, with the Project's own variables, Secret ones included, and never The Office's GitHub token or ssh key: a script that needs a token gets it from a Secret variable. A script that waits on a GitHub Actions run can hit the time limit.
  - **Scope:** they run only when Publish ships by the publishing mode, for an ordinary Task or a Publishing Task; never for a fix Task publishing into its Initiative's branch, nor for the proof-of-concept branch-only target.
  - **Before publishing** runs before anything leaves. The Office commits what it changed, as for a build-kind command, and that commit is what Publish ships; the Stage then expects HEAD there. Its failure is an ordinary Script failure: nothing is published, and the on-failure loop applies.
  - **After publishing** runs once the publication shipped (a pull request opened, or a merge landed; in push + PR mode when the pull request opens, not when it merges upstream), before the worktree is removed, with `OFFICE_PUBLISHED_BRANCH`, `OFFICE_PUBLISHED_COMMIT` (the commit that shipped: after a merge, the merged commit), `OFFICE_PULL_REQUEST_URL` when a pull request opened, and `OFFICE_PUBLISHING_MODE` (`push-and-pull-request` or `merge`). After nothing to publish it doesn't run, and the outcome says so.
  - **Runs again:** both lines run again each time Publish runs (an on-failure retry, or again after Resolve), so each must be safe to run twice. What shipped is kept on the Publish run before the after line runs, so a run again after a failed after line runs only that line and never publishes again.
  - **A failed after line** ends the Stage with an outcome of its own, "Published; after publishing failed: <error>", as the work did ship; the worktree stays. It skips the on-failure loop and goes to the CTO, then the user, with **Retry** (runs only the after line) or **Continue** (the Stage is done with the failure noted, the worktree is removed, and the Pipeline goes on).
- **Merge mode when the base moved** (the user's answer of 2026-10-26; amended 2026-11-15 with "The Task's commit message"): Publish fetches the base branch first. When the base moved on since the Task's branch left it, The Office merges the fetched base into the Task's branch with one merge commit, under the repository's lock, never a rebase. Then it lands the Task on the remote's base branch as one commit: the Task's branch's tree, with the Task's commit message, whose one parent is the fetched base, pushed without force. A merge that would conflict goes to Resolve, as in "Conflicts at Publish" below. Push + PR pushes the branch as it is and opens the pull request; there too, a branch that would conflict with the base goes to Resolve. (added while building tier 1; the conflict path amended on 2026-10-29)
- **The Changes tab after Publish shows what Publish shipped** (the user's answer of 2026-10-26): Publish records where the published branch forked from the base in a ref of The Office's own (`refs/office/published-from/<task>`). From then on Changes diffs the Task's branch from that commit, so it still shows the change after a merge, or after its pull request merges upstream. That diff is the one commit Publish landed, as the commit holds the branch's tree on that same base. (added while building tier 1)
- **The holder of Asked first on failures** (formerly "The CTO first on failures"; the user's answer of 2026-10-28, amended 2026-11-13): a Stage failing with no retries left, its loop's rounds used up or not, is put to the holder of Asked first when a Stage runs out of tries, called the CTO below, when that duty is held by a Role with Consultant on (else to the user), a Script or Publish Stage as well as an Agent one, as The Office's Decision in a Consultation on the Task: a form of one choice, with no Ask me again ([2.4](2.4-conversations.md)). The CTO answers in their own words, the question's comment with no option picked, which send the Task back for one round with their guidance, or passes it on to the user; the options (more rounds, continue with the issues, drop) stay the user's, who may answer in the CTO's place. A round's guidance is the answer's words, the question's comment and the general comment, and names who gave them: the CTO, or the user, an answer given for the user at their request counting as the user's (amended by the Initiative "Multiquestion form", 2026-11-16). A Stage the CTO sent back once in a walk goes to the user when it fails again. The Definition of Done not reported met before Publish (or at the end of a Pipeline without one), the third restart in a row during a Stage ([2.4](2.4-conversations.md)), a conflict at Publish the Agent gave up on and budget limits ask the user directly. (added while building tier 2)

- **Publishing into an Initiative's branch** (2026-11-12, the Initiative 1116efba; details settled with the Plan of Task 12e9ab91): a Task of an Initiative in a Project where it has a Pipeline ([2.1](2.1-work.md#defaults)) publishes into the Initiative's branch ([5.5](5.5-git-and-isolation.md#defaults)), always as one commit and never by a pull request, whatever the Project's publishing mode. - **Project Pipelines** (2026-11-12, the Initiative 5006c803; details settled with the Plan of Task dcf1ca8c): a **Project Pipeline** belongs to one Project. It has a name, a description, a **base Pipeline** (one office-wide Pipeline, never another Project Pipeline) and an ordered list of **Stage changes**, each one of six: **Insert before** a Stage, **Insert after** a Stage, **Replace** a Stage (each with a whole new Stage), **Change** a Stage (only the fields it gives, such as its brief, Role, limits, session, on failure or permissions), **Remove** a Stage and **Change routes** of a Stage (its whole list of routes out, with their conditions; added 2026-11-17 for flows). On the routes (2026-11-17): Insert before puts the new Stage just before its Stage in the Pipeline's order, the routes that led into that Stage now leading into the new one, and one route with no condition from the new Stage to it; Insert after puts the new Stage just after its Stage, which hands the new Stage its routes out and gets one route with no condition to it; Replace keeps the Stage's place, the routes into it and its routes out; Remove takes the Stage and its routes out away, and each route that led into it leads where its one route out led, or, when it had several, is taken away too, for a Change routes to settle. On a straight line each of them builds a straight line again. Each Stage change names its Stage by its key, shown by the Stage's name: one of the base Pipeline's Stages, or one an earlier Stage change inserted; an inserted Stage's key must be new among the built Stages. It is built whenever it is read: the base Pipeline's current Stages and routes, then each Stage change in order, so an edit to the base Pipeline reaches it; only a started Task keeps a copy of its Stages. Its name is unique among the office-wide Pipelines and its Project's own; two Projects may use the same name, and making or renaming an office-wide Pipeline is refused when the name is a Project Pipeline's, naming that Project. It is kept in The Office's records, beside the office-wide Pipelines. It is checked by the rules of the library's Pipelines on its built flow (the Validation rules, the Role flags, "continue" without the same Role, failure targets that aren't earlier, "A Pipeline needs the commands it runs" and "An Agent Stage's Project commands" above), which weigh its own Project only. It can be chosen only by a Task of its Project, as that Project's default, and as an Initiative's Pipeline in that Project; another Project is refused it ([2.1](2.1-work.md#defaults); amended 2026-11-13, the Task "Implement initiatives pageredesign", replacing "an Initiative's Pipeline is always office-wide"). Removing it is refused while it is its Project's default, a Task that hasn't started uses it, or a shaping or active Initiative names it in its Project whose Publishing Task hasn't started; removing an office-wide Pipeline is also refused while a Project Pipeline is built from it, which amends "The library editor" above.
- **A Broken Project Pipeline** (2026-11-12, the Initiative 5006c803; details settled with the Plan of Task dcf1ca8c): a Project Pipeline is **Broken** when building it fails: a Stage change names a key that isn't there, an inserted Stage's key is already there, a loop ("on failure go back to") points at a Stage that isn't in the built Stages or isn't earlier, or the built flow fails the Validation rules above, such as a route or a condition naming a Stage the base Pipeline no longer has, or a Stage no route reaches any more (amended 2026-11-17). Started Tasks keep their own Stages, and so does a Task edited for itself. A Project Pipeline's own save, and applying Devops' Proposal of it, are refused while it would be Broken, so only an office-wide Pipeline's save, which warns first, breaks one. Each Stage change keeps the name its Stage had when the Project Pipeline was last saved, for its words alone, so a Stage gone from the base Pipeline still reads by its name ("Changes Produce, which Document no longer has"); the key alone still matches it.
