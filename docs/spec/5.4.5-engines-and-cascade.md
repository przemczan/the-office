# 5.4.5 Engines and the engine cascade

Covers: the engine list, sign-in per engine kind, the engine cascade (a Task's and an Initiative's engine among its levels), Roles that need Office tools and a held answer, removing an engine.

## Defaults

### Engines are a list

- Settings › Engines lists the engines the user adds.
- Each engine has a name, an id made from the name when added and kept on a rename, and a default model.
- Caps, readings of the usage windows, their samples and each day's use are kept per engine ([2.1](2.1.5-planning-and-start.md#usage-estimates), "Usage estimates").

### A Claude Code engine

- A **Claude Code** engine is one account.
- Its sessions run with `CLAUDE_CONFIG_DIR` set to its own folder, `<office-data>/engines/<engine id>/`, so its credentials and transcripts stay there and a session resumes only on the engine that started it.
- "Sign in" runs the pinned binary's `claude auth login --claudeai` for that folder and shows its sign-in page, which signs in from any browser and gives a code the user pastes into the engine.
- "Paste a token instead" takes a token the user made with `claude setup-token` (a year long, `sk-ant-oat01-…`).
- It writes the token into that folder as its login, the credentials file the binary reads, in place of any login there, never sending it back.
- So the engine's sessions are signed in by it and it sits in no environment ([6](6-permissions-and-safety.md), Secrets).
- "Sign out" removes the folder's login, whether a Sign in or a token made it.
- The engine shows the email and plan `claude auth status` gives, that a pasted token signs it in, or that it is signed out.
- The `-p` fallback is its switch ([5.4.1](5.4.1-engine-kinds.md#the--p-fallback-matches-the-agent-sdk-adapter)).

### A Copilot CLI engine

- A **Copilot CLI** engine is one GitHub account with Copilot.
- Its sessions run with `COPILOT_HOME` set to its own folder, `<office-data>/engines/<engine id>/` ([5.4.4](5.4.4-copilot-cli-engine.md#the-copilot-cli-engine)).
- "Sign in" runs GitHub's device flow for that folder and shows GitHub's page and the one-time code the user enters there, with nothing pasted back.
- The engine shows itself signed in once the user has.
- "Paste a token instead" takes a fine-grained personal access token with the "Copilot Requests" permission; without it the runtime signs in but refuses every model call.
- The token is kept in the database and never sent back, and handed to the runtime only through the SDK's `github.token` on its input, so it is on no command line, in no environment and not in the folder.
- "Sign out" removes the token and the folder's sign-in.
- The engine shows the GitHub login the runtime's sign-in status gives, that a pasted token signs it in, or that it is signed out.
- Its models are those the runtime lists for the account and **Auto**, which names no model and lets the runtime choose.
- Auto is its default model, since a token-signed account may list none and the runtime refuses any model it doesn't list.

### A Gemini CLI engine

- A **Gemini CLI** engine is one Gemini API key from Google AI Studio ([5.4.7](5.4.7-gemini-cli-engine.md#gemini-cli-sign-in)).
- Its folder, `<office-data>/engines/<engine id>/`, is made when it is added and removed once its sessions have ended, as the other kinds' are; no sign-in lies there.
- It has no Sign in: "Use an API key" takes the key, kept in the database and never sent back, and "Sign out" forgets it.
- The engine shows that a Gemini API key signs it in, or that it is signed out.
- Its models are the pinned Gemini CLI's aliases, **Auto**, **Pro**, **Flash** and **Flash-Lite**: the CLI resolves each to the newest Gemini model of that line the key may use, so a new model comes with the CLI, with no list in The Office.
- Auto, which lets the CLI pick per request, is its default model.
- Each model has its own Model price on the engine, as an API endpoint's has.
- Its sessions run on the pinned Gemini CLI ([5.4.7](5.4.7-gemini-cli-engine.md)); it can be picked at every level of the engine cascade, where the capability check weighs what the engine check found it can do.

### An OpenAI-compatible API engine

- An **OpenAI-compatible API** engine is one API endpoint ([5.4.2](5.4.2-openai-compatible-api-engine.md)).

### The engine cascade

- Every level names an engine and one of its models, picking an engine filling in its default model.
- A session's engine and model come from the most specific level set, from least to most specific:
  - the **Office default** (Settings › Engines);
  - the **Project default** (the Project page's Engine block);
  - the **Initiative's engine** (the Initiative page's Engine fold);
  - the **Task's engine** (the Task page's Engine fold);
  - the Office-wide **Role override** (the Role card);
  - the Project's Role override (the Project page's Engine block).
- A Project's "Use for every Role" forces its default on every Role in it: the Office-wide Role overrides are skipped, its own still apply.
- The Task's and the Initiative's engine take the Project default's place, so with "Use for every Role" on they also win over the Office-wide Role overrides.
- "Use for every Role" can be on only while the Project has a default, so with none the Office-wide Role overrides win over the Task's and the Initiative's engine.
- Role overrides win over the Task's and the Initiative's engine in every other case, the Project's Role override first.
- Threads without a Project, onboarding a Project not yet added among them, use the Office levels only.
- Every session follows it: Threads, Stage runs, Consultations, the Planner, Devops, the Office Manager.
- Which sessions a Task's engine covers, and until when it can change: [2.1.3](2.1.3-tasks.md#a-tasks-engine).
- Which sessions an Initiative's engine covers, and until when it can change: [2.1.4](2.1.4-initiatives.md#an-initiatives-engine).
- Stand-in Engines take over from whatever engine the cascade gives; the usage estimate and Start's choice of a Stand-in Engine use the Task's resolved engine ([2.1](2.1.5-planning-and-start.md#usage-estimates), [5.4.6](5.4.6-stand-in-engines-and-usage-windows.md)).
- A Stage has no model of its own ([2.3](2.3-pipelines.md)).
- Only a Role a Pipeline names needs more of its engine: Office tools and an answer held to the Stage result's schema (the `officeTools` and `outputSchema` capabilities). Other Roles take any engine.
- A Role counts as named by a Pipeline when it is:
  - an Agent Stage's Role in the Pipeline library, which counts outside any Project and in every Project, a Project Pipeline's built Stages counting too ([2.3](2.3-pipelines.md#defaults));
  - or in an open Task's own Stages, which counts in that Task's Project (a done or dropped Task's don't count).
- A save at any level that would newly put such a Role on an engine lacking either, outside any Project or in one, is refused, naming the Roles and Projects.
- Saving a Task's engine is refused when a Role its Stages name, with no Role override of its own, would land on such an engine, naming the Roles: "On “<Task>”, the Developer would run on <engine>, which can't use Office tools, as their Pipelines' Agent Stages need."
- Saving an Initiative's engine is checked the same way over its open Tasks that set no engine of their own, Publishing Tasks included ("In <Initiative>, …").
- Adding a Task to an Initiative or taking it out, changing a Task's Stages, and choosing or proposing its Pipeline (a Publishing Task's too, as its Initiative's Pipeline changes) are weighed against the Task's effective level.
- Removing an engine weighs the open Tasks whose engine, or whose Initiative's, it moves, at the moved levels, the same way.
- Every save above a Task (Settings › Engines, a Role override, a Project's levels, a duty's holder, a Stage in the library or a Project Pipeline) is also weighed at each open Task it reaches that sets an engine, or whose Initiative does, by the Roles its Stages name ("On “<Task>”, …"). A Role a Pipeline newly names counts at each such Task in the place, whichever Pipeline it follows.
- Done and Dropped Tasks are skipped by these checks.
- So is hiring back a person let go, whose Role override comes back with their card, and a preset hire.
- Adding or changing a Stage, in the library or in a Task's own Stages, so that it newly names a Role whose engine lacks either is refused the same way, weighed where that Stage counts.
- A Stage naming a duty counts the Role that holds it now ([2.3](2.3.1-stages.md#a-stage-names-a-role-or-a-duty), "A Stage names a Role or a duty").
- Changing a duty's holder in Settings › Duties, or applying its Proposal, is checked as a rehire is: refused when it would newly put such a Role on an engine lacking either.
- A session whose engine changed starts its Thread fresh; a changed model alone resumes.
- That is decided in one place: the [Context policy](2.5-context-policy.md#choosing-a-move) compares the engine of the Thread's last session with the newly resolved one.
- `GET /tasks/:id/engine-cascade` lists what the Planner and each Role the Task's Stages name run on for the Task, and which level gave it; `PUT /tasks/:id/engine` and `PUT /initiatives/:id/engine` set or clear a level with `{ engine: { engineId, model } | null }`.
- Either is refused for an engine Settings › Engines doesn't list ("There is no engine "<id>".") or a model it doesn't offer ("Choose a model the engine offers."), as a Project's levels are.

### Removing an engine

- Every reference to it (the Office default, Project defaults, Initiatives' and Tasks' engines, Done and Dropped ones included, Role overrides, Projects' Role overrides) moves to a replacement the user picks.
- A reference takes the replacement's default model where the replacement doesn't offer the one named.
- When it is the only engine, the references move to none, and no session starts, with words saying so, until one is added.
- A running session finishes on the old engine and its Thread starts fresh.
- Stage runs keep the name of the engine they ran on.
- What the Remove engine window shows: [Settings › Engines](screens/settings.md#engines).
