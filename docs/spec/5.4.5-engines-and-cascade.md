# 5.4.5 Engines and the engine cascade

Covers: the engine list, engine types, sign-in per engine type, the models an engine lists, where a session runs (the engine cascade of engine type and account), how a person works (the model and effort cascade), engine overrides on an Initiative and a Task, Roles that need Office tools and a held answer, removing an engine, moving the earlier engine settings over.

## Defaults

### Engines are a list

- Settings › Engines lists the engines the user adds.
- Each engine has a name, an id made from the name when added and kept on a rename, a default model and a default effort.
- Each engine is one account of an **engine type**: Claude Code, Codex, Copilot CLI, Gemini CLI or OpenAI-compatible API.
- Caps, readings of the usage windows, their samples and each day's use are kept per engine ([2.1](2.1.5-planning-and-start.md#usage-estimates), "Usage estimates").

### Models and efforts of an engine type

- An engine type's models are those its engines offer, together: Claude models on Claude Code, Codex models on Codex, each Copilot CLI account's listed models and Auto, the Gemini CLI's aliases, each API endpoint's own models.
- An engine type's efforts are those its runtime takes, in its own order; a type that takes none shows no Effort anywhere.
- An engine's default effort is one of its type's efforts, or **Not set**, which leaves it to the runtime.
- A model or effort that names something the engine a session landed on doesn't offer gives way to that engine's default, and the session's Thread says so in a line ("Pam works with <default model> on <engine>, which doesn't offer <model>.").

### Models an engine lists

- A Claude Code, Codex or Copilot CLI engine offers the models its account lists, asked of the account with no session and no model call: the Agent SDK's model list (the `-p` fallback's `initialize` answer), Codex's `model/list` without its hidden models, the Copilot SDK's `listModels` with Auto first.
- The answer is kept per engine, with when it was listed, so showing the models never waits on an engine.
- Until an engine's account has listed its models, its type's fixed list stands in.
- An engine is asked when it is added, and again when its account, token or key changes, since the account decides the list.
- As the service starts, and whenever its models are shown (Settings › Engines, the Role card), each engine whose list is missing or older than a day is asked in the background, one engine at a time, the list kept meanwhile.
- That background ask leaves an engine asked within the last hour be, whatever it answered, so one that fails or lists none isn't asked each time the models are shown.
- **Refresh models** on the engine in Settings › Engines asks it at once ([Settings › Engines](screens/settings.md#engines)); `POST /settings/engines/:id/models/refresh` answers 204, 404 for an engine not listed, 422 for a type not asked, 502 with the engine's words when asking failed.
- A session refused for its model asks its engine again in the background, at most once in 5 minutes per engine.
- A failed or empty answer keeps the list kept before, so the models never empty.
- A removed engine's list is forgotten.
- A test instance of The Office asks no engine.
- A saved default model, a person's model or a Project's model the engine no longer lists stays as it was, shown "No longer offered", until someone picks another; a session naming it gives way as any model not offered does.
- Claude models' and Codex models' shared prices cover every model any engine of the type lists.
- The Gemini CLI's aliases and an API endpoint's own models aren't asked.

### A Claude Code engine

- A **Claude Code** engine is one account.
- Its sessions run with `CLAUDE_CONFIG_DIR` set to its own folder, `<office-data>/engines/<engine id>/`, so its credentials and transcripts stay there and a session resumes only on the engine that started it.
- "Sign in" runs the pinned binary's `claude auth login --claudeai` for that folder and shows its sign-in page, which signs in from any browser and gives a code the user pastes into the engine.
- "Paste a token instead" takes a token the user made with `claude setup-token` (a year long, `sk-ant-oat01-…`).
- It writes the token into that folder as its login, the credentials file the binary reads, in place of any login there, never sending it back.
- So the engine's sessions are signed in by it and it sits in no environment ([6](6-permissions-and-safety.md), Secrets).
- "Sign out" removes the folder's login, whether a Sign in or a token made it.
- The engine shows the email and plan `claude auth status` gives, that a pasted token signs it in, or that it is signed out.
- The `-p` fallback is its switch ([5.4.1](5.4.1-engine-kinds.md#the--p-fallback-matches-the-agent-sdk-adapter)).

### A Copilot CLI engine

- A **Copilot CLI** engine is one GitHub account with Copilot.
- Its sessions run with `COPILOT_HOME` set to its own folder, `<office-data>/engines/<engine id>/` ([5.4.4](5.4.4-copilot-cli-engine.md#the-copilot-cli-engine)).
- "Sign in" runs GitHub's device flow for that folder and shows GitHub's page and the one-time code the user enters there, with nothing pasted back.
- The engine shows itself signed in once the user has.
- "Paste a token instead" takes a fine-grained personal access token with the "Copilot Requests" permission; without it the runtime signs in but refuses every model call.
- The token is kept in the database and never sent back, and handed to the runtime only through the SDK's `github.token` on its input, so it is on no command line, in no environment and not in the folder.
- "Sign out" removes the token and the folder's sign-in.
- The engine shows the GitHub login the runtime's sign-in status gives, that a pasted token signs it in, or that it is signed out.
- Its models are those the runtime lists for the account and **Auto**, which names no model and lets the runtime choose.
- Auto is its default model, since a token-signed account may list none and the runtime refuses any model it doesn't list.

### A Gemini CLI engine

- A **Gemini CLI** engine is one Gemini API key from Google AI Studio ([5.4.7](5.4.7-gemini-cli-engine.md#gemini-cli-sign-in)).
- Its folder, `<office-data>/engines/<engine id>/`, is made when it is added and removed once its sessions have ended, as the other types' are; no sign-in lies there.
- It has no Sign in: "Use an API key" takes the key, kept in the database and never sent back, and "Sign out" forgets it.
- The engine shows that a Gemini API key signs it in, or that it is signed out.
- Its models are the pinned Gemini CLI's aliases, **Auto**, **Pro**, **Flash** and **Flash-Lite**: the CLI resolves each to the newest Gemini model of that line the key may use, so a new model comes with the CLI, with no list in The Office.
- Auto, which lets the CLI pick per request, is its default model.
- Each model has its own Model price on the engine, as an API endpoint's has.
- Its sessions run on the pinned Gemini CLI ([5.4.7](5.4.7-gemini-cli-engine.md)); it can be picked at every level of the engine cascade and as a Stand-in Engine, where the capability check weighs what the engine check found it can do.

### An OpenAI-compatible API engine

- An **OpenAI-compatible API** engine is one API endpoint ([5.4.2](5.4.2-openai-compatible-api-engine.md)).

### Two cascades

- Where a session runs and how its person works there are decided apart, each by a cascade of its own.
- The **engine cascade** gives the engine: an engine type and one of its accounts.
- The **model and effort cascade** then gives the model and the effort, for the engine type the session landed on.
- Every session follows both: Threads, Stage runs, Consultations, the Planner, Devops, the Office Manager.
- Threads without a Project, onboarding a Project not yet added among them, use the Office levels and the person's own settings only.
- A Stage names no engine and no model; it may set its effort ([2.3](2.3-pipelines.md)).
- No Role names an engine: the earlier Role override, a Project's Role overrides and "Use for every Role" are gone, replaced as [Moving the earlier engine settings over](#moving-the-earlier-engine-settings-over) says.

### The engine cascade

- A session's engine comes from the most specific level set, from least to most specific:
  - the **Office default** (Settings › Engines): an engine type and one of its accounts, always set while any engine is listed;
  - the **Project default** (the Project page's Engine block): an engine type and one of its accounts, each "Office's default" unless set;
  - the **Initiative's engine override** (the Initiative page's Engine fold): one engine;
  - the **Task's engine override** (the Task page's Engine fold): one engine.
- A Project default's account is "Office's default" only while its engine type is too; once it names an engine type, it names one of that type's accounts.
- Every person in a place runs on the same engine there, whatever their Role.
- An engine from the Office default or the Project default may give way to a Stand-in Engine; an engine override never does ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#a-forced-engine-has-no-stand-ins)).
- Which sessions a Task's engine override covers, and until when it can change: [2.1.3](2.1.3-tasks.md#a-tasks-engine).
- Which sessions an Initiative's engine override covers, and until when it can change: [2.1.4](2.1.4-initiatives.md#an-initiatives-engine).
- The usage estimate and Start's choice of a Stand-in Engine use the Task's resolved engine ([2.1](2.1.5-planning-and-start.md#usage-estimates), [5.4.6](5.4.6-stand-in-engines-and-usage-windows.md)).

### The model and effort cascade

- Once the engine is known, the model and the effort each come from the most specific level that sets them, from least to most specific:
  - the **engine's default** model and effort (Settings › Engines, on each engine);
  - the **person's model and effort** for that engine type (the Role card), each "Engine's default" unless set;
  - the **Project's setting for the person** on that engine type (the Project page's Engine block), each "Person's setting" unless set;
  - the Project's **force this model and effort for everyone**, on its default's engine type;
  - the **Stage's effort**, effort only.
- The model and the effort resolve apart: a level that sets only one leaves the other to the levels below it.
- A person has one model and effort per engine type, never per account, so they know how to work on whichever engine of the type they land on.
- The force can be on only while the Project default names an engine type, and applies only to sessions on that type: a session that landed on another type, through an override or a Stand-in Engine, takes the levels below it.
- The force's model and effort are each "Engine's default" unless set; forcing "Engine's default" sets every person in the Project to the engine's default.
- A Stage's effort the engine type doesn't take gives way to the level below it.
- An engine override names no model: a Task or an Initiative on its own engine still works with each person's model and effort for its type.

### A session whose engine changes

- A session whose engine changed starts its Thread fresh; a changed model or effort alone resumes.
- A change of engine type is a change of engine: the fresh session works with the person's model and effort for the new type.
- That is decided in one place: the [Context policy](2.5-context-policy.md#choosing-a-move) compares the engine of the Thread's last session with the newly resolved one.

### Roles that need Office tools and a held answer

- Only a Role a Pipeline names needs more of its engine: Office tools and an answer held to the Stage result's schema (the `officeTools` and `outputSchema` capabilities). Other Roles take any engine.
- A Role counts as named by a Pipeline when it is:
  - an Agent Stage's Role in the Pipeline library, which counts outside any Project and in every Project, a Project Pipeline's Stages counting too ([2.3](2.3-pipelines.md#defaults));
  - or in an open Task's own Stages, which counts in that Task's Project (a done or dropped Task's don't count).
- A Stage naming a duty counts the Role that holds it now ([2.3](2.3.1-stages.md#a-stage-names-a-role-or-a-duty), "A Stage names a Role or a duty").
- Capabilities belong to the engine, never to the model or the effort, so only saves that name an engine are weighed: no change to a model or an effort is refused for them.
- A save that would newly put a Role a Pipeline names on an engine lacking either is refused, naming the engine, the Roles and where; it is weighed at the levels it reaches:
  - the **Office default** (Settings › Engines), outside any Project and in each Project whose default names no engine type;
  - a **Project default**, in that Project;
  - a **Task's engine override**, over the Roles the Task's Stages name;
  - an **Initiative's engine override**, over its open Tasks with no override of their own, Publishing Tasks included;
  - a **Stand-in Engine list**, the Office's outside any Project and in each Project that doesn't use its own, a Project's own in that Project, since a stand-in may take over any session there.
- The refusals read:
  - at the Office default or a Project default: "<engine> can't use Office tools, which the Agent Stages of the Developer and the Reviewer need in <Project>." ("outside any Project" for the Office's own reach);
  - at a Task: "On “<Task>”, <engine> can't use Office tools, which the Agent Stages of the Developer need.";
  - at an Initiative: "In <Initiative>, <engine> can't use Office tools, which the Agent Stages of the Developer need on “<Task>”.";
  - at a Stand-in Engine list: "<engine> can't stand in: it can't use Office tools, which the Agent Stages of the Developer need in <Project>.";
  - for an answer held to a schema, "can't hold its answer to the Stage result's schema" in place of "can't use Office tools".
- Every save above a Task (Settings › Engines, a Project's levels, a duty's holder, a Stage in the library or a Project Pipeline) is also weighed at each open Task it reaches that has an engine override, or whose Initiative has, by the Roles its Stages name ("On “<Task>”, …"). A Role a Pipeline newly names counts at each such Task in the place, whichever Pipeline it follows.
- A Task or an Initiative with an engine override is weighed at its override alone: it uses no Stand-in Engine, so no list is weighed for it.
- Adding a Task to an Initiative or taking it out, changing a Task's Stages, and choosing or proposing its Pipeline (a Publishing Task's too, as its Initiative's Pipeline changes) are weighed against the Task's engine and, without an override, the Stand-in Engines in its reach.
- Adding or changing a Stage, in the library or in a Task's own Stages, so that it newly names a Role is weighed the same way, where that Stage counts.
- Changing a duty's holder in Settings › Duties, or applying its Proposal, is weighed the same way when it newly names a Role in a place.
- Removing an engine weighs the levels and lists it moves, at the moved levels, the same way.
- Done and Dropped Tasks are skipped by these checks.
- Hiring a person, a preset's or one hired back, is never weighed: a person names no engine.
- Picking a Stand-in Engine at run time passes over one lacking a capability the session needs, as a last guard ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#picking-the-engine-to-run-on)).

### The API

- `GET /tasks/:id/engine-cascade` gives what the Task's sessions run on:
  - `engine`: the engine (`engineId`, `engineType`, its name) and the level that gave it (`office`, `project`, `initiative` or `task`);
  - `standIns`: whose Stand-in Engine list applies (`office`, `project`) or `none` under an engine override;
  - `people`: the Planner and each Role the Task's Stages name, each with its model and its effort and the level that gave each (`engine`, `person`, `projectPerson` or `projectForce`), and each Stage that sets its own effort with that effort (`stage`).
- `PUT /tasks/:id/engine` and `PUT /initiatives/:id/engine` set or clear the engine override with `{ engineId: string | null }`; it names an engine only, as the model comes from each person.
- Either is refused for an engine Settings › Engines doesn't list ("There is no engine "<id>".").
- A Project's engine levels are set with `PUT /projects/:id/engine`: `{ default: { engineType, engineId } | null, force: { model: string | null, effort: string | null } | null, people: [{ roleKey, engineSettings: { [engineType]: { model: string | null, effort: string | null } } }], standIns: { useOwnList: boolean, engineIds: string[] } }`; `useOwnList` off keeps `engineIds` for next time ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#a-projects-own-list)).
- Each person in `people` carries their settings for every engine type at once, in the Role card's shape; a person with no model or effort set on any type isn't kept.
- That save is refused for an engine not listed, an account of another type than the default's, a force without a default engine type ("Pick an engine type first."), a model or effort the type doesn't offer ("Choose a model <type> offers.", "Choose an effort <type> takes."), a person named twice, and an engine named twice in its list.
- A person's model and effort are fields of the Role card, `engineSettings: { [engineType]: { model: string | null, effort: string | null } }`, saved with it and refused the same way for a model or effort the type doesn't offer.

### Removing an engine

- Every reference to it moves to a replacement the user picks: the Office default, Project defaults, Initiatives' and Tasks' engine overrides (Done and Dropped ones included), and the Office's and the Projects' Stand-in Engine lists.
- The replacement may be of another engine type; the Office default and a Project default then take the replacement's type with it.
- A Stand-in Engine list that already names the replacement just drops the removed engine.
- People's and Projects' model and effort settings name engine types, not engines, so they stay as they are.
- When it is the only engine, the references move to none, and no session starts, with words saying so, until one is added.
- When it is the last engine of its type, people's and Projects' settings for that type are kept, unused until an engine of that type is listed again.
- A running session finishes on the old engine and its Thread starts fresh.
- Stage runs keep the name of the engine they ran on.
- What the Remove engine window shows: [Settings › Engines](screens/settings.md#engines).

### Moving the earlier engine settings over

- The update that brings the two cascades moves every earlier setting over once, as the service starts, so no session's engine, model or effort changes unless a line below says so:
  - **each engine** keeps its default model and gets the default effort Not set;
  - **the Office default** (an engine and a model) becomes that engine's type and that engine, and a model other than the engine's default becomes the engine's default model;
  - **a Project default** (an engine and a model) becomes that engine's type and that engine;
  - **"Use for every Role"** on becomes the force, with the Project default's model and the effort "Engine's default";
  - a Project default's model with "Use for every Role" off, other than its engine's default model once the Office default has moved, becomes the Project's setting, on that type, for each person who had neither a Role override nor a Project's Role override there;
  - **each Role override** (Office-wide, on the Role card) becomes the person's model for its engine's type;
  - **the Role card's effort** becomes the person's effort on each engine type that takes it, and "Engine's default" on the others;
  - **each Project's Role override** becomes the Project's setting for that person on its engine's type, with the model it named and the effort "Person's setting";
  - **an Initiative's or a Task's engine**, Done and Dropped ones included, becomes its engine override on the same engine, and its model is dropped.
- The Office's Stand-in Engine list stays as it is, and no Project uses a list of its own.
- A Role override or a Project's Role override whose engine is no longer listed has no engine type to move to, so it is dropped.
- A Role override's or a Project's Role override's account is dropped with the Role levels: its person runs on the place's engine from then on, which is the one change of engine the move makes.
- Each Role card that moved gets a line on its Changes, "Engine settings moved over", naming any Role override dropped or any account its sessions no longer run on.
- "Use for every Role" let a Project's Role overrides win over its default; the force wins over the Project's settings for each person, so a Project that had both moves with its force on and its per-person settings below it.
- The earlier settings stay stored, unread, until a later release drops them, so a rollback to the release before finds them as they were ([5.1](5.1-shape.md#defaults), "Updating The Office").
