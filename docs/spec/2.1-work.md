# 2.1 Work

- **Project:** a repository The Office works on, with its own commands (an install command, and a list of named commands, each of a **Command kind:** build, lint or test), install inputs, default Pipeline (the one its Tasks usually follow, one of its own Project Pipelines or an office-wide one, [2.3](2.3-pipelines.md#defaults): named in the Planner's Brief, and listed first when the user chooses a Pipeline for a Task that has none; a new Task doesn't take it, see Ready below), publishing mode (push + PR, or merge, run by The Office's own code, [2.3](2.3-pipelines.md#defaults)), environment, skills setting and **Project limit:** how many of its Tasks may be started at once, 1 by default and up to the Office-wide limit's maximum, set in its page's Work block. It shows as its mark, and may have an **Icon**, shown in place of the mark's letters and colour, and a **Logo**, the larger image on its page and card, each in a light and a dark version, the one for the palette shown used, and each uploaded or chosen from its repository as a copy ([4](4-ux-direction.md)). Its commands may be left unset when it is added: the repository and a name are enough, and a command not set is set later on its page or by Devops' Proposal; once set, a command can be changed but not cleared. Until then a Task installs nothing without an install command, a Script Stage whose command isn't set ends could-not-run, saying how to set it, and never passes, and the environment check skips it. Every Project starts with three commands, Build, Lint and Test (keys `build`, `lint`, `test`, of the matching kind), which may be left unset when it is added. More are added on its page or by Devops' Proposal, in the order they were added, each with a key (lower-case letters, digits and `-`, starting with a letter, at most 40 characters, unique in the Project; `install` and `publish` are reserved), a name (at most 60 characters), a kind and a command line, which can't be blank once added. The key is fixed once added, since Pipelines name a command by it; the name, kind and line can be changed, and a command can be removed, unless the Project's default Pipeline runs it: then removing it is refused, naming the Pipeline, until another default is chosen; a command another Pipeline runs can be removed, and that Pipeline's Stage then ends could-not-run ([2.3](2.3-pipelines.md#defaults)). The install command stays apart from the list: it alone runs before a Stage when its inputs changed.
- **Idea:** captured quickly, in a Project or Office-wide. States: new, shaped, dropped. Its title, notes and Project are editable until it is shaped. Shaping makes an Initiative or a Task and keeps the Idea as the origin link; its Attachments move with it. A Task shaped from an Idea takes the Idea's notes as its Description, editable until Start.
- **Initiative:** Office-level, spans Projects; each of its Tasks is in one Project. States: shaping (with the CTO), active, done (all Tasks done), dropped. It is shaped from an Idea, or created with `create_initiative` by the CTO or the Office Manager in their chat when the user asks ("Creating an Initiative" below). Order inside it is dependencies plus manual order. Each Project it spans may have a Pipeline of its own for it, the **Initiative's Pipeline** in that Project: there it works on the **Initiative's branch** ([5.5](5.5-git-and-isolation.md#defaults)), and that Project's **Publishing Task** publishes the whole change ("An Initiative's Pipeline" and "Publishing Tasks" below).
- **Task:** one unit of work in one Project, done when its **Definition of Done** is met: a published change, an Attachment, or both.
  - States: **Backlog → Planning → Ready → In progress → Done**, side states **Waiting on you** and **Paused**, exit **Dropped**; before Backlog, **Shaping**, for a Task of an Initiative still being shaped (below). Ready requires a Plan and a Definition of Done, both confirmed by the user, or by auto mode on their behalf (below), or confirmed as they stand, even empty, by the user's Mark Ready without them (below), no Pipeline proposal left open and no Decision on the Task left open, and a Pipeline: a Task has none until one is chosen, from the Planner's proposal confirmed by the user or by auto mode, or by the user, and its page shows a placeholder where the Stages will be until then. **Planning is optional:** a Task whose Plan and Definition of Done were written by the user or given with the Task, and confirmed by the user, goes from Backlog straight to Ready by **Mark Ready**, under Ready's other rules; Mark Ready shows in Backlog and Planning once a Pipeline is chosen, which the user does there on the Pipeline rail, and no Decision on the Task is open; its checklist names "Choose a Pipeline" while there is none. The user may **Mark Ready without a confirmed Plan or Definition of Done:** Mark Ready then asks first in a dialog naming what is missing (a Plan or a Definition of Done not written, or written and not confirmed), and going on confirms both as they stand, even empty, by that user, in the same change that moves the Task to Ready; the Pipeline and open Decision conditions still hold. Work moves forward; the two ways back are a change to the Plan, the Definition of Done or the Pipeline proposal of a Ready Task that hasn't started, by the user's **Save** or by the Planner, which takes it back to **Planning** to be marked Ready again, and a **Move** of a Ready Task to another Project, both below. In progress shows the current Stage.
  - **Description** (what the user wants, in their own words): optional, written in "New Task" (the top bar's Create › Task) under the title and edited on the Task page, where it sits above the Plan; the CTO writes one on an Initiative's Tasks too, by their changes below. It is part of the Planner's Brief and of every Agent Stage's Brief ([2.5](2.5-context-policy.md)); with none, the title alone is enough to plan from. A Description can mention a Task, Initiative, open Decision or Idea, picked with `@` as in the chat or pasted as the link to its page; it is saved as a Markdown link to the record's page and shown on the Task page as the record's chip. "New Task" also takes optional Attachments, files or links, added to the Task in the order chosen once it is added; if one can't be, trying again adds only those left, never the Task a second time.
  - **Commit message:** a Task holds the message of the one commit Publish lands it as, following the commit convention its Project's own docs define. The Planner suggests it with the Plan, every Agent Stage may update it, and the user edits it on the Task page in any state until Publish lands it or the Task is Done or Dropped; it never moves the Task, so a Ready Task stays Ready. With none written, Publish uses the title with a short summary below it ([2.3](2.3-pipelines.md#defaults), "The Task's commit message").
  - **Plan** (how) and **Definition of Done** (what must be true) are separate first-class parts of the Task, written by the user, co-written with the Planner in a Thread on the Task, or given with the Task by whoever creates it with the `create_task` Office tool, confirmed by the user. **Given with the Task:** when it is already known how the Task will be done and what must be true, its creator gives both parts, or neither, as half of the pair helps nobody; the Task lands in Backlog with both **Not confirmed**, and the user confirms each on the Task page and marks the Task Ready from Backlog without Planning, as for parts they wrote themselves. Nothing its creator gives is confirmed by them, and the Task's state changes name its creator, so they show who wrote the Plan. Make a plan and Plan with… start from the given parts, for the Planner to rework rather than start over. **Save and Confirm are separate acts:** until the Task starts the user edits a part with Save and Cancel, and Confirm, the user's only way to confirm, takes the part as it reads; auto mode confirms on their behalf (below). A Save that changes nothing changes nothing, the confirmation included; a changing Save leaves the part unconfirmed in Backlog, Planning and Ready alike, and a Task in Planning stays there. Ready needs both parts confirmed, so a changing Save on a **Ready** Task takes it out of the queue if it was queued and moves it back to **Planning**, in its planning Thread and auto mode, the changed part Not confirmed and the Task no longer marked planned; the user confirms and marks it Ready again, or the Planner marks it planned and auto mode does. A Ready Task that was never in Planning (marked Ready from Backlog) has no planning Thread, so a changing Save moves it to **Backlog** instead. The editor says beside Save, while the Task is Ready, which of the two a change does and that a queued Task leaves the queue. The Planner may also change a Ready Task in its own planning Thread, but only when the user asks: write_plan, write_definition_of_done or propose_pipeline that change something move it back to Planning in the same save, moved by the Planner, and mark_planned works as in Planning from there; a write that changes nothing moves nothing, and Tags never move a Task. Since the Planner may not be the author, an unconfirmed part's badge reads **Not confirmed**.
  - **Two ways to start Planning**, both moving the Task to Planning: **Make a plan**, in the Planner's empty tab in Backlog and as the **Plan** button on a Backlog card on the board, starts the Planner at once from the title and the Description, and from the Plan and Definition of Done when the Task has them, with nothing more to write; **Plan with…**, in the Task's head, opens the Planning Thread and the Planner waits for the user's first message. The board's Plan has no room for the Auto mode switch, so it plans in the remembered auto mode, which its tooltip names. While nobody holds Plans, Make a plan and the board's Plan aren't offered, Plan with… lets the user write the parts alone, and the planning tab shows "Nobody holds Plans" with a link to Settings › Duties.
  - **Auto mode:** an **Auto mode** switch sits beside Make a plan in the Planner's tab. It starts at the remembered default, an Office setting that is off until first chosen, and the choice made with Make a plan becomes the default; Plan with… always plans with auto mode off. The Task keeps the choice while it is in Planning, and its card and the Planner's tab read "Planning with …, in auto mode". In every planning Thread the Planner says it has finished with the `mark_planned` Office tool, once the Plan, the Definition of Done and the Pipeline are written and nothing is left to ask; it is refused, with the reason, outside Planning, before the Plan and the Definition of Done are written, and while the Task has neither a Pipeline nor a proposed one. It marks the Task planned until it next enters Planning. With auto mode off nothing else changes: the user confirms the parts and marks the Task Ready. With auto mode on and no Decision on the Task open, The Office confirms in one save whatever of the Plan and the Definition of Done isn't confirmed yet, confirms the proposed Pipeline (with none proposed, a Task that has a Pipeline keeps it; one that has none can't be marked planned) and marks the Task Ready under Ready's rules; the Task's state changes record the move to Ready as made by auto mode, naming each part it confirmed. With a Decision open, `mark_planned` changes nothing and tells the Planner to wait: the user's answer comes as the Planner's next message, the Planner carries on, marks the Task planned again, and auto mode marks it Ready.
  - **Plan the Initiative:** an active Initiative's page has a **Plan the Initiative** action with the same **Auto mode** switch as Make a plan, starting at the remembered default; the choice becomes the default. It opens one planning Thread with the Planner on the Initiative: one session, reading every Project's base branch (the Initiative's branch in each Project where it has a Pipeline: [2.4](2.4-conversations.md)) and changing no file, as the CTO's shaping Thread does. The Planner plans the Initiative's Backlog Tasks in dependency order, where only blockers inside the Initiative count: a Task's turn comes once each of them is marked planned, Ready or beyond, or Dropped. Where the engine has subagents, the Planner hands each Task's research and drafting to one and plans the Tasks whose blockers are planned in parallel; without them it plans them one after another. As each Task's turn comes, the Planner moves it from Backlog to Planning with the `start_planning` Office tool, refused with the reason for a Task outside the Initiative or not in Backlog, while a blocker inside the Initiative isn't planned yet, and outside the Initiative's latest planning Thread. It writes the Task's Plan with its files to change, Definition of Done, Pipeline and Tags itself, with the planning tools naming the Task by its id, and marks it planned with `mark_planned`; auto mode then works as for a single Task, and without it the Task waits in Planning for the user's Confirm. The Initiative's Thread counts as the planning Thread of each Task planned in it: the Task's Planner's tab links to it, no Planner's Thread opens on the Task meanwhile, and the Task has no worktree until Start makes one. The page links to the Thread and shows each Task's progress (Waiting, Planning, Planned, Ready), with a count of the Tasks planned. **Decisions in this Thread:** the Planner opens a Decision, the form of [2.4](2.4-conversations.md), with `open_decision` naming one of the Initiative's Tasks by its `taskId`, one per Task, several open at once; one naming a Task outside the Initiative is refused with the reason. One naming no Task is about the Initiative as a whole, one at a time, and shows in the Thread and under Needs you with the Initiative's title. Its card shows in the Thread naming its Task, on that Task's page in Needs you, linking to this Thread, and in Mark Ready's checklist, where it keeps the Task from Ready until answered; it is answered in any of these places. While a Decision on a Task is open, that Task isn't marked planned and the Tasks of the Initiative that wait for it are refused `start_planning`, as their blocker isn't planned; the Planner plans the other Tasks and ends its turn only when every Task left waits for an answer, or all are planned. An answer given while the Planner waits resumes the session at once. One given while it works is recorded at once, so the Decision is answered and the Task is free for Ready, and reaches the session when its turn ends, every waiting answer in one message, each naming its Task; if that message never reaches a session, those Decisions open again. **Rewrites:** when an answer or a later decision changes Tasks already planned, the Planner rewrites their Plan, Definition of Done or Pipeline from this Thread. A Task in Planning marked planned, in this or an earlier planning Thread of the Initiative, is rewritten and marked planned again. A Ready Task goes back to Planning in this Thread in one move, as on a changing Save, the rewritten part Not confirmed, and is marked planned again; auto mode then accepts it and marks it Ready again, and without it it waits for the user's Confirm. Writing any part of a Task marked planned clears its marked planned in every Thread; Tags never move a Task. A Task that has started (In progress, Waiting on you, Paused, Done), is Dropped or is being planned in its own planning Thread is never rewritten: the write is refused with the reason, and the Planner opens a Decision on that Task instead, saying what changed and what it recommends. The action is refused with the reason when the Initiative isn't active, nobody holds Plans, none of its Tasks is in Backlog, or one of its Tasks is still being planned in an earlier planning Thread (in Planning there, not yet marked planned). **Plan with…:** beside Plan the Initiative, as a Task has beside Make a plan, the page offers **Plan with <Planner>**, and the Planner's tab on the Initiative offers it too while it has no Thread there. It opens a new planning Thread on the Initiative where the Planner waits for the user's first message: no session starts and no model is called until the user writes there how to plan it (order, depth, what to ask, subagents or not). The Planner's first turn starts from that message, with the Initiative's planning Brief saying the user opened the Thread to plan with them, so their messages say how to plan and the Planner follows them where they differ from the default way, asking in the Thread what is unclear. It plans with auto mode off and leaves the remembered default unchanged. It is offered and refused as Plan the Initiative is, with the same reasons, and its Thread is the Initiative's latest planning Thread like any other: `start_planning`, Decisions, rewrites and the page's progress work the same, and a restart of The Office wakes it only once a Task is being planned there.
  - **Dependencies:** on any Task in any Initiative or Project; a blocked Task cannot start, but can be queued until its blockers are Done or Dropped. They are set before the Task starts, never on an Archived Task, and never closing a cycle; the user adds and removes them on the Task's page, whose Add window leaves Archived Tasks out, and whoever shapes Initiatives or holds Plans with the Office actions `add_dependency` and `remove_dependency`. A Task waits directly only for Tasks it doesn't already wait for through another Task: if C waits for B and B waits for A, C doesn't wait for A directly. Every way a dependency is added follows it: the user's, `add_dependency`, a new Task's waiting list (`create_task`, an Initiative's added Task) and an Initiative's Proposals. A wait the Task already has through another Task is left out, and `add_dependency`'s answer says through which Task; otherwise the new wait takes out the direct waits it covers, on the Task itself and on every not-started Task that waits for it, and the answer names each. A new Task waits directly only for those of its blockers no other of them waits for. Started Tasks keep their dependencies, and a Publishing Task, which waits for every Task of its Initiative by design, keeps its own; a wait through a Publishing Task, or through a Task Done or Dropped, doesn't count. Redundant waits are not cleaned up on their own; they go when the Task's dependencies next change this way.
  - **Joining and leaving an Initiative:** a Task is in at most one Initiative, and joins or leaves one only before it starts; one The Office made (an Onboard, a run environment set-up or a Publishing Task) never does. The user adds a Task to an Initiative, or takes it out, on the Task's page and on the Initiative's page (Add an existing Task, Take out a Task); whoever shapes Initiatives or holds Plans does with the Office actions `add_to_initiative` and `take_out_of_initiative`. A Task joins an Initiative being shaped only from Backlog, moving to Shaping, and an active one keeping its state; a done or dropped Initiative takes none. Taking a Task out moves one in Shaping to Backlog, and one planned in the Initiative's planning Thread loses it: from Planning it goes to Backlog, as a changing Save does with no planning Thread, and a Ready one stays Ready. The Publishing Task in its Project waits for a Task that joins and stops waiting for one taken out; its other dependencies stay. Joining is refused once the Task has a worktree and the Initiative has a Pipeline in its Project (the worktree came from the base branch), and leaving once its worktree came from the Initiative's branch. Each move is kept in the Task's state changes, named by who made it.
  - **Organisation:** three priority levels plus manual order per Project; tags, full-text search, saved views; **Archive**, below.
    - **The board's Done column:** its Done and Dropped Tasks show the one that ended last on top, ungrouped and grouped by Initiative alike; a Task's end is its last move to Done or Dropped, and one whose end was never recorded follows the dated ones in the board's order (priority, then manual order). Every other column keeps the board's order. With Group by Initiative off, each column gathers an Initiative's cards into one block headed by its name, placed where its first card falls in the column's order, its cards in that order (in Queued its head names their places); Tasks with no Initiative stay outside the blocks, in their place. While the Initiative filter is set, the columns show no blocks ([its design](../design/board-initiative-blocks.html)).
  - **Moving** a Task to another Project: see "Moving a Task" below.
- **Attachment:** a document (Markdown), image or screenshot, file or link, attached by the user or an Agent to an Idea, Initiative or Task, or by the user to a message in a Thread (an image pasted into it, kept as an Attachment of the Task or Initiative the Thread is on, else of the Thread itself, [2.4](2.4-conversations.md)); can be a Task's result. Diffs and Stage logs are parts of a Task, not Attachments. A Task's Attachments are shown by round, each the work between one Gate send-back and the next. An Agent attaching a file to a Task (with `attach_file`, or a screenshot its Stage result lists) **replaces** the Attachment an Agent attached from the same worktree path to that Task since the user last acted at a Gate on it (any Gate action; before any, since the work started), so a Gate shows each file once, at its latest copy; what a Gate already showed the user is never changed. The replaced Attachment keeps its id and its place (`addedAt`, so its round stays), and takes the new file's bytes, size, media type, text judgement and text, and who attached it last; the old copy isn't kept. Links, anything the user attached and anything on an Idea or an Initiative are never replaced. A file Attachment is a **text file** when its bytes are text: valid UTF-8 with no NUL byte in the first 8 KB, the NUL test being the one the API engine's Read and Grep use; a document is always one, and an image or a PDF never is, as each is read and shown as what it is. The Office judges it once, as the file is attached, and keeps it with the Attachment; its kind doesn't change, so a `.css` is still a file. A PDF's text is pulled out once as it is attached, a page marker line before each page, and kept beside the file; a PDF with none, such as a scan, reads as having no text. An image, such as a screenshot, can be pasted from the clipboard in "New Task", Capture an Idea and Attach; one without a real file name is named "Pasted image <date> <time>.png", with no character Windows forbids in a file name. A paste that also holds plain text pastes the text and attaches nothing.
- **Who did what** ([2.10](2.10-users-and-signing-in.md)): every record that says the user did something names which user: who captured an Idea, created a Task or an Initiative, started a Task or moved it from one state to another (its state changes say "by Ana" where they said "by the user"), passed or sent back a Gate, attached an Attachment, and changed a setting (a Role card's version, a Pipeline, a Project's settings, the Office instructions, any Office setting). Work an Agent or The Office did still names the person or The Office.

## Defaults

- **Waiting on you while planning:** a Task in Planning with an open Decision stays in Planning and shows a Waiting on you badge; the Waiting on you state stays a side state of In progress.
- **Plan as a Task with the Planner** on an Idea shapes it into a Task and opens its planning at once.
- **The Planner joins on the first message:** moving a Task to Planning opens its planning Thread but starts no session; the Planner's first turn runs on the user's first message there, so a Plan the user writes alone costs no model call. This holds for Plan with…; Make a plan starts the Planner at once.
- **Tasks of an Initiative still being shaped** wait in **Shaping**, the first state of a Task added to a shaping Initiative, by the user or the CTO; one added to an active Initiative, by the user or a Proposal, starts in Backlog. A Task in Shaping has no card on the Work board and isn't in its counts or its note of other Projects, can't be planned, marked Ready, queued or started, and its Plan, Definition of Done and Pipeline can't be changed, except that it can be moved to another Project, which leaves it with no Pipeline and in Shaping ("Moving a Task" below); no session works on it, so a Thread it already has can be read but not continued until Confirm; it is still seen on the Initiative page and its own page, which says what it waits for, found by search and dropped, alone or with its Initiative ("An Initiative is done" below), and its title, Description and dependencies still change. Confirming the Initiative says its outcome and Task list are agreed, makes it active and moves its Tasks in Shaping to Backlog, in one step; nothing else makes that move.
- **Archive:** the user archives a Done or Dropped Task, and Done and Dropped Tasks are also archived automatically once finished for the **Archive period**, a number of days set Office-wide in Settings › Office limits, 30 until changed; Tasks already finished longer ago than that are archived at the first run. **Archived** is not a state: the Task stays Done or Dropped, so dependencies, Initiatives and Usage estimates read it as any Done or Dropped Task. An archived Task leaves the Work board, its counts and its lists, and shows in a view of archived Tasks. Its page and Threads stay readable, read-only as for any Done or Dropped Task ([2.4](2.4-conversations.md)); the top bar's search finds it (the Work board's can't, as it has no card there), and its Initiative's page still shows it. **Restore**, one click, returns it to the board in the state it had, and it gets a full period again from that moment. Initiatives are archived the same way: a Done or Dropped Initiative is archived by Archive in its More menu, or automatically once it has ended for the same Archive period, counted from when it became Done or Dropped or was last restored; Initiatives that ended longer ago than the period are archived at the first run, and so are those whose end nothing dates. An archived Initiative stays Done or Dropped, leaves the Initiatives tab's board and shows in the Archived tab beside the archived Tasks; its page and Threads stay readable, the Work board still names its Tasks by it, and Restore returns it to Done or Dropped on the board.
- **Moving a Task:** **Move** on the Task page puts a Task in another Project. It is refused with the reason once the Task has ever entered Planning, has started or has a worktree in its Project; also for an Onboard Task, which belongs to its Project, and for a Dropped Task, as returning to Backlog would undo the Drop. A moved Task has no Pipeline until one is chosen there, as the new Project's commands differ, and keeps its Initiative, dependencies, Attachments and Threads. It returns to Backlog with its Plan and Definition of Done Not confirmed; a Ready Task leaves Ready and the queue in the same save, as a changing Save takes one, though to Backlog, since a Task that can move was never in Planning. A Task in Shaping stays in Shaping instead, and goes to Backlog only by Confirm. The move is kept in the Task's record, and an Initiative's Projects follow from its Tasks. A Publishing Task can't be moved either, as an Onboard Task can't. Moving a Task of an Initiative into a Project the Initiative doesn't span yet gives that Project no Pipeline: it starts with None, so no Initiative's branch is made there and no command is checked, until the CTO's Proposal gives it one ("An Initiative's Pipeline" below). A Project the Initiative stops spanning keeps its branch.
- **Shaping without a CTO:** an Idea is shaped into an Initiative whether or not anyone holds Shapes Initiatives ([2.2](2.2-people.md#defaults), "Duties"). With a holder, the shaping Thread opens at once and they start on it; while nobody holds it, the user writes the Initiative by hand, and its Thread opens when they start it once someone holds Shapes Initiatives.
- **Creating an Initiative:** the holders of Shapes Initiatives and Default person to talk to, and no other Role, have `create_initiative` in their chat, and use it only when the user asks for an Initiative or agrees to one. It takes a title and an outcome, the outcome naming the Projects meant; no Projects are stored, as an Initiative spans its Tasks' Projects, and the CTO adds the Tasks while shaping. The Initiative lands in shaping, created by that person, with no origin Idea, and waits for the user's Confirm on its page like one shaped from an Idea. Its shaping Thread opens as above, with or without a CTO; its opening has the CTO check the outcome with the user, then agree on the Projects and the Tasks. Its page shows no Origin.
- **The CTO's changes to an Initiative:** while it is shaping, the CTO writes the outcome, Tasks and dependencies straight onto it, and the user confirms the whole once; once it is active, each change the CTO wants is a Proposal the user applies. Its Tasks' dependencies and which Tasks it has are the exception: those Office actions change an active Initiative straight away too, as the user's own click does, gated by the person's Role authority (the CTO's card says to ask the user before changing an active Initiative, so they ask with a Decision first, opened in the shaping Thread). The title and Description of one of its Tasks are among these changes, and both change only until that Task starts. So is the Initiative's Pipeline in each of its Projects, under "An Initiative's Pipeline" below.
- **Decisions in the shaping Thread:** whoever holds Shapes Initiatives asks the user with a Decision, the form of [2.4](2.4-conversations.md), opened in the Initiative's shaping Thread on no Task, while it is shaping or active, one at a time. It shows in that Thread and under Needs you with the Initiative's title, and its answer comes as the Thread's next message.
- **An Initiative starts in its Idea's Project:** an Initiative shaped from an Idea captured in a Project starts in that Project. The CTO's shaping Brief says so, and the CTO asks only whether it reaches other Projects too, not which Project it is for; Add a Task on its page chooses that Project until the Initiative has Tasks. Nothing new is stored: an Initiative still spans the Projects of its Tasks.
- **The user writes the outcome:** with or without a CTO, the user edits an Initiative's outcome on its page while it is shaping; once it is active, the outcome changes only by a Proposal the user applies, as the CTO's other changes do.
- **A Dropped blocker** no longer blocks; the Task that waited for it still lists it, marked as dropped.
- **Onboarding a Project** is a chat, then a Task. "Ask Devops to onboard one" on the Projects page, naming the holder of Onboards and repairs Projects, opens a chat with Devops, who drafts the Project (path, name, base branch, commands, install inputs, publishing mode, default Pipeline) as a Proposal. Applying it adds the Project and an "Onboard" Task in it, Ready on the built-in **Onboard** Pipeline (Devops makes the Project build and test in a fresh worktree, asking before installing anything → a Verify Script Stage running Test, back to Onboard at most twice → Publish by the Project's publishing mode, so the fixes Devops makes reach the repository); the user starts it, as any Task. The Project page shows the Project's onboarding from that Task: onboarding, onboarded, or none. Adding a Project by hand stays, with no Onboard Task; while nobody holds Onboards and repairs Projects it is the only way, and the Onboard Pipeline's Onboard Stage names that duty. The Project may also be a Repository URL instead of a path: Devops reads the repository from a shallow fetch with the Office identity, nothing cloned, and applying the Proposal clones it into the Office data directory before adding the Project; adding by hand takes a folder, a URL or a pick from the user's GitHub repositories.
- **Tags** are on Tasks only; the user sets them on the Task page and in "New Task", and the Planner while planning.
- **Search** is two boxes over one full-text search: the Work board's narrows Tasks by title, Plan, Definition of Done and Tags; the top bar's (⌘K) finds Tasks, Initiatives, Ideas, people and document Attachments and opens the one picked. Both follow the Project filter and say how many more matches are in other Projects. Both also find a record by its ID: typed whole or by its first 8 characters or more, or as a pasted link to its page, it finds that Task (and, in the top bar, that Idea or Initiative) and lists it first, ahead of the records whose text matches.
- **Saved views and the Project filter:** Saved views are stored by The Office and never hold the Project filter; the Project filter is remembered per browser, so two browsers can show different Projects.
- **Group by Initiative** ([its design](../design/board-by-initiative.html)): a switch at the end of the Work board's filter bar lays the board out in a group per Initiative with a card on the board, newest first with the Active ones before those that ended, then No Initiative last. Each group has a header (its name as a fold, its state, its Projects, its progress over every Task of the Initiative, how many of its cards show, and a link to the Initiative) and its Tasks in the state columns, under column heads shown once. The switch is remembered in this browser and also kept in the board's address (`?group=initiative`) apart from the filters: a board opened without `group` in its address is grouped as last chosen here, a Saved view never holds it, and Clear leaves it. A group's fold is remembered in this browser, a Done or Dropped Initiative's starting folded. The Initiative filter shows its group alone, saying why when it has no card; the other filters leave out a group with no card shown, naming those search, Priority and Blocked left out. A card drags only within its column inside its own group: the board never changes a Task's Initiative. With the switch off, the columns show each Initiative's cards in a block (the board's order, above); a card is dragged only within its block, or among the cards outside the blocks.
- **The Initiatives tab is a board** ([its design](../design/initiatives-tab.html)): Shaping, Active and Done, each newest first but Done, the one that ended last on top, with Dropped folded at its foot; its search (of names and outcomes) and Waiting on you are kept in the address; the Dropped fold is remembered in this browser. Every column always shows, with its count and a line saying why it is empty; the Project filter narrows the board and the archive. The Archived tab shows the archived Tasks or, switched, the archived Initiatives: a search, a Done / Dropped / All filter with counts, the one that ended last on top under a line per month, 25 to a page, all kept in the address.
- **An Initiative is done** once it is active and every one of its Tasks that isn't Dropped is Done, at least one of them; a shaping one waits for Confirm, which makes it done at once when its Tasks already are. Dropping an Initiative, shaping or active, drops every one of its Tasks not yet Done or Dropped with it: those in Shaping, Backlog, Planning, Ready (queued too), In progress, Waiting on you and Paused, its Publishing Tasks included, each as that Task's own Drop would, so a queued one leaves the queue and a started one has its running Stage stopped; each change is recorded as the user's. Its Done and Dropped Tasks stay as they are. Its Publishing Tasks, in its Projects with a Pipeline, count among its Tasks, so it is done only once they are Done too; after a Drop no Publishing Task is added, and its Initiative's branches are kept ([5.5](5.5-git-and-isolation.md#defaults)).
- **An Initiative's Pipeline:** **each Project the Initiative spans has a Pipeline of its own, or None**, chosen while shaping from the office-wide Pipelines and that Project's own Project Pipelines, as a Task of that Project chooses; a Project Pipeline of another Project is refused, and so is a Broken one. It is chosen by the user on the Initiative page or by the CTO with an Office tool, each naming the Project, both straight onto the Initiative. It starts as **None** in each Project; no Project's default applies, Confirm fixes, for each Project it spans then, whether it has one, and is refused while one it has is Broken. A Project with None publishes its Tasks one by one, each by its own Pipeline. The Initiative's **Short name** stays one for the whole Initiative, made once any Project has a Pipeline ([5.5](5.5-git-and-isolation.md#defaults)). A Project the Initiative comes to span after Confirm, by a Task added or moved there, starts with None, and gets a Pipeline only by the CTO's Proposal. Once the Initiative is active, which Pipeline a Project has changes only by the CTO's Proposal, naming the Project, applied by the user. Applying it is refused once that Project's Publishing Task has started ("the Pipeline starts"), when that Project lacks a command the Pipeline runs ([2.3](2.3-pipelines.md#defaults)), for another Project's Project Pipeline, and when it would change whether that Project has a Pipeline, which Confirm fixed: a Proposal never proposes None, nor a Pipeline for a Project that had None at Confirm. Another Project's Publishing Task doesn't block it. A Proposal giving a Project spanned after Confirm its first Pipeline is allowed as long as that Project has no Publishing Task that started, and makes the Initiative's branch there. An applied Proposal also changes the Pipeline of that Project's Publishing Task not yet started, unless the user edited its Stages for that Task. In each Project the Initiative names an office-wide Pipeline or a Project Pipeline, as a Task that hasn't started does, so an edit to it changes it; that Project's Publishing Task takes it as its own Pipeline under a Task's rules, a Project Pipeline as it is built when the Task starts. The Initiative's other Tasks keep Pipelines of their own: the Initiative's Pipeline in a Project runs only in that Project's Publishing Task. Those Tasks, in a Project with a Pipeline or with None, choose from their own Project's Project Pipelines and the office-wide ones, like any Task. A base Pipeline edit that breaks a Project Pipeline does to the Initiative's Tasks still in Backlog on it what it does to any Task that hasn't started: each is flagged and its Start, and Start Ready Tasks for it, is refused until the Project Pipeline is fixed or the Task's Pipeline is swapped ([2.3](2.3-pipelines.md#defaults), "A Broken Project Pipeline"). One that breaks a Project Pipeline the Initiative names in its Project is weighed the same way, as for a Task that hasn't started: that Project's Publishing Task, once added, can't start until it is fixed.
- **Publishing Tasks:** only a Project where the Initiative has a Pipeline gets one, following that Project's Pipeline; a Project with None gets none. They are added in the same step that makes the last of the Initiative's other Tasks Done or Dropped, and only while it is active. A Project with a Pipeline gets one when its Initiative's branch holds commits its last Done Publishing Task didn't publish (or, with none yet, commits the base branch doesn't have) and it has no unfinished Publishing Task; so a Project whose Tasks were all Dropped gets none, and a dropped Publishing Task isn't added again until another of the Initiative's Tasks ends. It is titled "<Initiative> → <Project>", in the Initiative and that Project, and its Description is the Initiative's outcome. Its Plan is The Office's own words: the Initiative's branch, the base branch, the publishing mode and the Initiative's Done Tasks in that Project. Its Definition of Done is every statement of those Tasks plus "The whole change is in <base branch> by <publishing mode>", and its Files to change are the union of theirs. It is added **Ready**, its parts confirmed by The Office as the Onboard Task's are, and its state change records it; it never enters Planning. The user starts it, or Start Ready Tasks does; it isn't started on its own. It works on the Initiative's branch itself and publishes it into the base branch ([2.3](2.3-pipelines.md#defaults), "A Publishing Task's Publish"). A fix that needs new work is a new Task in the Initiative, added by the user or by the CTO's Proposal; while its Project's Publishing Task isn't Done or Dropped, The Office makes the new Task a blocker of it. A Publishing Task with an unfinished blocker queues like any blocked Task; once started, it waits before its next Stage, with the blocker as the reason.
- **A queue for Start:** several Tasks may be in progress in one Project, up to its Project limit. When Start can't run a Task now because a blocker isn't Done or Dropped yet, its person is at their Task limit, its Project already has as many started Tasks (In progress, Waiting on you or Paused) as its Project limit, the Office-wide limit on running Tasks is reached or a Window cap or Daily cap would be passed ("Usage estimates" below), Start puts the Task in one Office-wide queue, shown with its reason on the board and on Now. Each reason has a short reason too, such as "Office-wide limit reached (3)" or "5-hour window cap (80%) · resets 14:30": a board card's Queued mark shows the short reasons, each once, on hover, and its place and the full reasons on a press, with the Tasks it is queued behind as links, while the Task page, Now and Start show the full ones. On the board a queued Task sits in a Queued column of its own, between Ready and In progress, and stays Ready, so the Ready column holds only Tasks that wait for the user. A blocked Task offers only the queue, as it can't start anyway, and an Overlap it also has queues it behind those Tasks too. A queued Task starts by itself, oldest first, when every blocker is Done or Dropped, a desk, its Project and its person free up and its caps allow it; only a Project's own Tasks count against its Project limit, so a full Project never holds another Project's Task, and lowering the limit stops no started Task; the user can take it out of the queue or move it up, one place or to the top. While an engine's usage window is used up, Start and the queue also wait for every Task whose Stages spend on that engine, whatever its Window caps say, with the reason "Claude Code's 5-hour window is used up until 14:00" (short reason "5-hour window used up · until 14:00"), naming the engine and the window; the Task is released at the reset, and Tasks on other engines aren't held. Before a Window cap or a used-up window holds it, a Start hands the Task's Stages on that engine to a **Stand-in Engine** ([5.4](5.4-the-engine.md#defaults)) instead: the first in the list's order that serves every model the Task uses there and has room for the Task's estimate moved onto it (its Window caps, its used-up windows and its Daily caps, with the estimates of the Tasks it already takes counted). The Task then starts, and every Agent Stage of that run runs on the stand-in with the cascade's model; it queues only when no stand-in has room, with the added reason "No Stand-in Engine has room either: Personal: 5-hour window cap (80%) · resets 14:30." (short reason "No stand-in with room"), and is released when the cascade's engine or any stand-in frees. A Daily cap never hands a Task on, as it is a spending limit, not a used-up subscription: it queues, as does a cap that resets within the prompt cache's hour, which starts on the cascade's engine. With no stand-in serving the model, the reasons name none. Every Start and every release of the queue tries the cascade's engines first, so new work goes back to an engine once its window resets. The Task page marks a Task started on a stand-in ("On a Stand-in Engine: Personal for Work", with why on hover), each Stage run's details show its engine with a "Stand-in for Work" mark and why, and the Live view names the engine each session runs on, "standing in for Work". Every other reason (a vacant Role, and the like) refuses Start with the reason.
- **Overlaps at Start:** the Planner's Plan lists the files and folders it expects to change. Start warns when a Task in progress in the same Project expects to change some of the same, and offers to start anyway or to queue the Task behind that one; a Task that overlaps several waits behind all of them, until each is Done or Dropped. Real conflicts are handled at Publish ([2.3](2.3-pipelines.md), "Conflicts at Publish").
- **Start Ready Tasks:** on an active Initiative's page with at least one of its Tasks Ready, one action starts every Ready Task of the Initiative through the normal Start, so blockers, the queue, the Office-wide limit, Project limits, each person's Task limit, usage caps, a scheduled update and the fire alarm apply as they do to each Start; it is refused, with the reason, for an Initiative that isn't active or has no Ready Task. A blocker inside the Initiative starts before the Tasks that wait for it, so its queue place is ahead of theirs; otherwise the board's order applies (priority, then manual order). A Task that would change the same files as a Task already started, including one started earlier in the same run, is queued behind it without the user being asked; a Task that has to wait is queued, and the queue starts it later as it does any other. A Task Start refuses (a vacant Role, a Pipeline no longer in the library) is listed with its reasons, and the rest still start or queue. Afterwards the page shows, until closed or reloaded, what started, what was queued with its place and reasons, and what was refused with its reasons, each Task linked to its page; nothing about the run is kept on the Initiative. The queue's release doesn't weigh Overlaps, so two Tasks of one run both queued for a limit may later start together, as two queued by hand can.
- **Pause the Initiative:** nothing of a paused Initiative runs or starts until it is resumed. On an active Initiative's page, **Pause the Initiative** marks it Paused, beside its state, as Archive marks a Task. Each of its Tasks In progress or Waiting on you is paused as the user's own Pause pauses it: the running Stage is held once the Agent's current turn ends, and its edits are kept. None of its Tasks starts while it is paused: a Start, Start Ready Tasks or a turn in the queue waits with "The Initiative is paused.", so the Task is queued, and so is a Task added to it meanwhile. **Resume the Initiative** clears the mark, resumes exactly the Tasks its Pause paused, and releases the queue; a Task the user had paused themselves before stays Paused, as the fire alarm leaves it ([2.8](2.8-fire-alarm.md)). Pause is offered only while the Initiative is active and not paused, Resume only while it is paused; otherwise each is refused with the reason. While it is paused, Resume on one of its Tasks is refused with "The Initiative is paused: resume it to go on.", and Stop and Drop still work on a single Task. Dropping a paused Initiative clears the mark and drops the Tasks its Pause paused with its other open Tasks ("An Initiative is done" above); its move to Done, once its paused Tasks were dropped and the rest are Done, clears the mark too. Pausing raises no "Task paused" Notification and no Outcome for each Task, as the user paused them all at once; the Initiative shows Paused on its page, its card in the Initiatives tab and its group on the Work board. Planning goes on while it is paused: its planning Thread isn't held. It isn't offered for a shaping Initiative, which has no started Tasks, nor from the Work board or an Initiative's card, nor to Agents.
- **A pause by the usage window:** when a Claude Code engine, or a Codex engine on a ChatGPT plan, refuses a Stage's turn because one of its account's usage windows is used up (its 5-hour window, its weekly window, a model's weekly window, or any other window the engine reports as used up), the Task is paused by itself, as the user's own Pause pauses it: the Stage is held where it is, its uncommitted edits are kept, and nothing counts as a failure, so no retry, correction or Consultation of the CTO is spent. The Task shows Paused with why and when it resumes: "Usage window used up · resumes 14:00", from the window's reset time, in the user's local time, on the board, the Task page and Now. At that time it resumes by itself, also after a restart of the service, and the Stage carries on in its own Thread: the message the engine refused, the Stage's work or its correction, is sent again, with a line that the edits may be half-done, as the turn may have been cut off after some tool calls; when the refused turn left no session to resume, the Stage starts a new one with its full brief. When the engine gives no reset time, the latest reading of that window's reset is used, and with none known the Task tries again after one hour. A turn refused again pauses it again until the next reset. It also resumes sooner, as soon as a reading of its engine's usage windows taken after the pause shows the engine free ([5.4](5.4-the-engine.md): they are read as the service starts and every 5 minutes, as well as on each rate-limit signal), so a window freed early, or still free after a restart, doesn't keep it waiting; a refusal the reading didn't show holds it until that refusal's reset. The user can still Resume, Stop or Drop it by hand; Resume clears the resume time. A Stage held because its session is over the context size set in Settings › Engines waits for the user's choice on the Stand-in choice card ([2.4](2.4-conversations.md#defaults), "The Decision on Stages waiting for a Stand-in Engine") and still resumes at the reset on its own Engine; the automatic resume and the card's Switch now work a Task under one lock, so only one of them resumes it.
- **Usage estimates:** a Ready Task shows its **Usage estimate**, what its whole Pipeline is expected to use on each engine the engine cascade gives its Stages' Roles in its Project ([5.4](5.4-the-engine.md#defaults)), on its card, its page, in the Start flow and in the queue, in the measures ticked in Settings › Office limits (any of tokens, the 5-hour window, the 7-day window and cost in dollars; none turns estimates off; tokens and the 5-hour window by default). It is the median of the last 20 done Tasks' Stage runs for the same Project and Pipeline, Stage by Stage, summed, once there are 3; below that the Planner's token estimate in the Plan, its cost derived from the Office-wide dollars per token of the done Tasks; with neither, "no estimate". Either way, a window's estimate is the tokens times the Office-wide window % per token, as `utilization` comes in whole percents and a Stage run never gets a like-with-like pair of readings: learnt per engine from successive readings of one Reading source ([5.4](5.4-the-engine.md)), a pair counting when the Office's tokens went up between them and a window's part when it neither reset nor went down, pooled as the changes summed over the tokens. The ratio mixes models. Cost is priced by the Model prices of Settings › Engines; a model with no price gives "no cost". Caps are per engine: a **Window cap** on the 5-hour and the 7-day window, which only Claude Code engines and Codex engines on a ChatGPT plan have, a Codex engine on an API key having none (90% by default), and a **Daily cap** on tokens and on dollars (off unless set; today as in [2.7](2.7-notifications.md)). Start waits in the queue when a ticked measure's cap would be passed, the Task's estimates on the engines under one cap added up: a window's use plus the estimates of Tasks started since its last reading plus this Task's; a day's use plus what is left of the estimates of Tasks in progress plus this Task's. It is released when the cap resets, and starts anyway when every exceeded cap resets within the prompt cache's hour ([5.4](5.4-the-engine.md)). "No estimate" and "no cost" never hold a Start. A Task started on a Stand-in Engine counts its estimate on the stand-in, its windows by the stand-in's own window % per token, for the Starts and the queue after it. There are no per-Stage or Planning estimates. A window with no reading, or whose reset has passed, counts as unused; the hour exception covers the Daily caps' midnight too.
