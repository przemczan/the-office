# 2.1 Work

From [07](../../.scratch/the-office/issues/07-work-model.md), with [08](../../.scratch/the-office/issues/08-pipelines.md) and [19](../../.scratch/the-office/issues/19-work-mockup.md).

- **Project:** a repository The Office works on, with its own commands (install, build, lint, test), install inputs, default Pipeline, publishing mode (push + PR, or merge, run by The Office's own code; see [9](README.md#defaults)), environment, skills setting and **Project limit**: how many of its Tasks may be started at once, 1 by default and up to the Office-wide limit's maximum, set in its page's Work block (the user, 2026-11-08). It shows as its mark, and may have an **Icon**, shown in place of the mark's letters and colour, and a **Logo**, the larger image on its page and card, each in a light and a dark version, the one for the palette shown used, and each uploaded or chosen from its repository as a copy ([4](4-ux-direction.md)). Its commands may be left unset when it is added: the repository and a name are enough, and a command not set is set later on its page or by Devops' Proposal; once set, a command can be changed but not cleared. Until then a Task installs nothing without an install command, a Script Stage whose command isn't set ends could-not-run, saying how to set it, and never passes, and the environment check skips it (the user, 2026-11-09).
- **Idea:** captured quickly, in a Project or Office-wide. States: new, shaped, dropped. Shaping makes an Initiative or a Task and keeps the Idea as the origin link; its Attachments move with it. A Task shaped from an Idea takes the Idea's notes as its Description, editable until Start (the user, 2026-11-05).
- **Initiative** (tier 2): Office-level, spans Projects; each of its Tasks is in one Project. States: shaping (with the CTO), active, done (all Tasks done), dropped. Order inside it is dependencies plus manual order.
- **Task:** one unit of work in one Project, done when its **Definition of Done** is met: a published change, an Attachment, or both.
  - States: **Backlog → Planning → Ready → In progress → Done**, side states **Waiting on you** and **Paused**, exit **Dropped**; before Backlog, **Shaping**, for a Task of an Initiative still being shaped (below). Ready requires a Plan and a Definition of Done, both confirmed by the user, no Pipeline proposal left open and no Decision on the Task left open (the user's answer of 2026-10-26). **Planning is optional** (the user, 2026-11-05): a Task whose Plan and Definition of Done were written by the user or given with the Task, and confirmed by the user, goes from Backlog straight to Ready by **Mark Ready**, under Ready's other rules; Mark Ready shows in Backlog only once both parts are confirmed. Work moves forward; the two ways back are a changing **Save** on a Ready Task and a **Move** of a Ready Task to another Project, both below. In progress shows the current Stage.
  - **Description** (what the user wants, in their own words): optional, written in "New Task" (the top bar's Create › Task) under the title and edited on the Task page, where it sits above the Plan; the CTO writes one on an Initiative's Tasks too, by their changes below (the user, 2026-11-06). It is part of the Planner's Brief and of every Agent Stage's Brief ([2.5](2.5-context-policy.md)); with none, the title alone is enough to plan from (the user, 2026-11-05). A Description can mention a Task, Initiative, open Decision or Idea, picked with `@` as in the chat or pasted as the link to its page; it is saved as a Markdown link to the record's page and shown on the Task page as the record's chip (the user, 2026-11-09).
  - **Plan** (how) and **Definition of Done** (what must be true) are separate first-class parts of the Task, written by the user, co-written with the Planner in a Thread on the Task, or given with the Task by whoever creates it with the `create_task` Office tool, confirmed by the user. **Given with the Task** (the user, 2026-11-09): when it is already known how the Task will be done and what must be true, its creator gives both parts, or neither, as half of the pair helps nobody; the Task lands in Backlog with both **Not confirmed**, and the user confirms each on the Task page and marks the Task Ready from Backlog without Planning, as for parts they wrote themselves. Nothing its creator gives is confirmed by them, and the Task's state changes name its creator, so they show who wrote the Plan. Make a plan and Plan with… start from the given parts, for the Planner to rework rather than start over. **Save and Confirm are separate acts** (the user, 2026-11-05): until the Task starts the user edits a part with Save and Cancel, and Confirm, the only way to confirm, takes the part as it reads. A Save that changes nothing changes nothing, the confirmation included; a changing Save leaves the part unconfirmed in Backlog, Planning and Ready alike, and a Task in Planning stays there. Ready needs both parts confirmed, so a changing Save on a **Ready** Task moves it to **Backlog**, out of the queue if it was queued, and the user confirms and marks it Ready again; the editor says so beside Save while the Task is Ready. Since the Planner may not be the author, an unconfirmed part's badge reads **Not confirmed**.
  - **Two ways to start Planning** (the user, 2026-11-05), both moving the Task to Planning: **Make a plan**, in the Planner's empty tab in Backlog and as the **Plan** button on a Backlog card on the board (the user, 2026-11-08), starts the Planner at once from the title and the Description, and from the Plan and Definition of Done when the Task has them, with nothing more to write; **Plan with…**, in the Task's head, opens the Planning Thread and the Planner waits for the user's first message.
  - **Dependencies** (tier 2): on any Task in any Initiative or Project; a blocked Task cannot start, but can be queued until its blockers are Done or Dropped (the user, 2026-11-06).
  - **Organisation:** three priority levels plus manual order per Project (tier 1); tags, full-text search, saved views (tier 2); **Archive** (tier 3), below.
  - **Moving** a Task to another Project (tier 3): see "Moving a Task" below.
- **Attachment:** a document (Markdown), image or screenshot, file or link, attached by the user or an Agent to an Idea, Initiative or Task; can be a Task's result. Diffs and Stage logs are parts of a Task, not Attachments. A Task's Attachments are shown by round, each the work between one Gate send-back and the next; versions of one Attachment are postponed by the user until after tier 3 (2026-11-08). A file Attachment is a **text file** when its bytes are text: valid UTF-8 with no NUL byte in the first 8 KB, the test the API engine's Read and Grep use; a document is always one, and an image or a PDF never is, as each is read and shown as what it is. The Office judges it once, as the file is attached, and keeps it with the Attachment; its kind doesn't change, so a `.css` is still a file. A PDF's text is pulled out once as it is attached, a page marker line before each page, and kept beside the file; a PDF with none, such as a scan, reads as having no text (the user, 2026-11-10).

## Defaults

Gaps no ticket settled, filled with the simplest choice consistent with the tickets and accepted by the user; each says when.

- **Start in tier 1** is refused with the reason when the Project already has a Task in progress, the person is at their Task limit or the Office-wide limit is reached (as the click-through does); no queue. (accepted 2026-10-24)
- **Waiting on you while planning:** a Task in Planning with an open Decision stays in Planning and shows a Waiting on you badge; the Waiting on you state stays a side state of In progress. (added while building tier 1, accepted 2026-10-25)
- **Plan as a Task with the Planner** on an Idea shapes it into a Task and opens its planning at once, as the click-through does. (added while building tier 1, accepted 2026-10-25)
- **The Planner joins on the first message** (the user's answer of 2026-10-30): moving a Task to Planning opens its planning Thread but starts no session; the Planner's first turn runs on the user's first message there, so a Plan the user writes alone costs no model call. This holds for Plan with…; Make a plan starts the Planner at once (the user, 2026-11-05).
- **Tasks of an Initiative still being shaped** (the user, 2026-11-07, replacing their answer of 2026-10-28) wait in **Shaping**, the first state of a Task added to a shaping Initiative, by the user or the CTO; one added to an active Initiative, by the user or a Proposal, starts in Backlog. A Task in Shaping has no card on the Work board and isn't in its counts or its note of other Projects, can't be planned, marked Ready, queued or started, and its Plan, Definition of Done and Pipeline can't be changed, except that it can be moved to another Project, which gives it that Project's default Pipeline and leaves it in Shaping ("Moving a Task" below; the user, 2026-11-07); no session works on it, so a Thread it already has can be read but not continued until Confirm; it is still seen on the Initiative page and its own page, which says what it waits for, found by search and dropped, and its title, Description and dependencies still change. Confirming the Initiative says its outcome and Task list are agreed, makes it active and moves its Tasks in Shaping to Backlog, in one step; nothing else makes that move. Tasks of a shaping Initiative already in Planning or beyond when this rule came stay where they are, as work only moves forward.
- **Archive** (tier 3, the user, 2026-11-07): the user archives a Done or Dropped Task, and Done and Dropped Tasks are also archived automatically once finished for the **Archive period**, a number of days set Office-wide in Settings › Office limits, 30 until changed; Tasks already finished longer ago than that are archived at the first run. **Archived** is not a state: the Task stays Done or Dropped, so dependencies, Initiatives and Usage estimates read it as before. An archived Task leaves the Work board, its counts and its lists, and shows in a view of archived Tasks. Its page and Threads stay readable, read-only as for any Done or Dropped Task ([2.4](2.4-conversations.md)); the top bar's search finds it (the Work board's can't, as it has no card there), and its Initiative's page still shows it. **Restore**, one click, returns it to the board in the state it had, and it gets a full period again from that moment. Initiatives are archived the same way (the user's agreement with the Task "Implement initiatives redesign", 2026-11-09): a Done or Dropped Initiative is archived by Archive in its More menu, or automatically once it has ended for the same Archive period, counted from when it became Done or Dropped or was last restored; Initiatives that ended longer ago than the period are archived at the first run, and so are those that ended before their end was kept and nothing dates. An archived Initiative stays Done or Dropped, leaves the Initiatives tab's board and shows in the Archived tab beside the archived Tasks; its page and Threads stay readable, the Work board still names its Tasks by it, and Restore returns it to Done or Dropped on the board.
- **Moving a Task** (tier 3, the user, 2026-11-07): **Move** on the Task page puts a Task in another Project. It is refused with the reason once the Task has ever entered Planning, has started or has a worktree in its Project; also for an Onboard Task, which belongs to its Project, and for a Dropped Task, as returning to Backlog would undo the Drop. A moved Task takes the new Project's default Pipeline and keeps its Initiative, dependencies, Attachments and Threads. It returns to Backlog with its Plan and Definition of Done Not confirmed; a Ready Task leaves Ready and the queue the way a changing Save does. A Task in Shaping stays in Shaping instead, and goes to Backlog only by Confirm. The move is kept in the Task's record, and an Initiative's Projects follow from its Tasks.
- **Shaping without a CTO** (the user's answer of 2026-10-28): an Idea is shaped into an Initiative whether or not a CTO is hired. With one, the shaping Thread opens at once and the CTO starts on it; without one, the user writes the Initiative by hand, and its Thread opens when they start it once a CTO is hired.
- **The CTO's changes to an Initiative** (the user's answer of 2026-10-28): while it is shaping, the CTO writes the outcome, Tasks and dependencies straight onto it, and the user confirms the whole once; once it is active, each change the CTO wants is a Proposal the user applies. The title and Description of one of its Tasks are among these changes, and both change only until that Task starts (the user, 2026-11-06).
- **The user writes the outcome** (the user's answer of 2026-10-28): with or without a CTO, the user edits an Initiative's outcome on its page while it is shaping; once it is active, the outcome changes only by a Proposal the user applies, as the CTO's other changes do.
- **A Dropped blocker** (the user's answer of 2026-10-28) no longer blocks; the Task that waited for it still lists it, marked as dropped.
- **Onboarding a Project** (the user's answer of 2026-10-28) is a chat, then a Task. "Ask Devops to onboard one" on the Projects page opens a chat with Devops, who drafts the Project (path, name, base branch, commands, install inputs, publishing mode, default Pipeline) as a Proposal. Applying it adds the Project and an "Onboard" Task in it, Ready on the built-in **Onboard** Pipeline (Devops makes the Project build and test in a fresh worktree, asking before installing anything → a Verify Script Stage running Test, back to Onboard at most twice → Publish by the Project's publishing mode, so the fixes Devops makes reach the repository); the user starts it, as any Task. The Project page shows the Project's onboarding from that Task: onboarding, onboarded, or none. Adding a Project by hand stays, with no Onboard Task. (added while building tier 2) From tier 3 the Project may be a Repository URL instead of a path: Devops reads the repository from a shallow fetch with the Office identity, nothing cloned, and applying the Proposal clones it into the Office data directory before adding the Project; adding by hand takes a folder, a URL or a pick from the user's GitHub repositories (the user, 2026-10-31 and 2026-11-01).
- **Tags** (the user's answer of 2026-10-28) are on Tasks only; the user sets them on the Task page and in "New Task", and the Planner while planning.
- **Search** (the user's answer of 2026-10-28) is two boxes over one full-text search: the Work board's narrows Tasks by title, Plan, Definition of Done and Tags; the top bar's (⌘K) finds Tasks, Initiatives, Ideas, people and document Attachments and opens the one picked. Both follow the Project filter and say how many more matches are in other Projects.
- **Saved views and the Project filter** (the user's answer of 2026-10-28): Saved views are stored by The Office and never hold the Project filter; the Project filter is remembered per browser, so the desk and the phone can show different Projects.
- **Group by Initiative** (the user's approval of [its design](../design/board-by-initiative.html), 2026-11-09): a switch at the end of the Work board's filter bar lays the board out in a group per Initiative with a card on the board, newest first with the Active ones before those that ended, then No Initiative last. Each group has a header (its name as a fold, its state, its Projects, its progress over every Task of the Initiative, how many of its cards show, and a link to the Initiative) and its Tasks in the state columns, under column heads shown once. The switch is remembered in this browser and also kept in the board's address (`?group=initiative`) apart from the filters: a board opened without `group` in its address is grouped as last chosen here, a Saved view never holds it, and Clear leaves it. A group's fold is remembered in this browser, a Done or Dropped Initiative's starting folded. The Initiative filter shows its group alone, saying why when it has no card; the other filters leave out a group with no card shown, naming those search, Priority and Blocked left out. A card drags only within its column inside its own group: the board never changes a Task's Initiative.
- **The Initiatives tab is a board** (the user's approval of [its design](../design/initiatives-tab.html), Proposed: Board, 2026-11-09): Shaping, Active and Done, each newest first but Done, the one that ended last on top, with Dropped folded at its foot; its search (of names and outcomes) and Waiting on you are kept in the address; the Dropped fold is remembered in this browser. Every column always shows, with its count and a line saying why it is empty; the Project filter narrows the board and the archive. The Archived tab shows the archived Tasks or, switched, the archived Initiatives: a search, a Done / Dropped / All filter with counts, the one that ended last on top under a line per month, 25 to a page, all kept in the address.
- **An Initiative is done** (the user's answer of 2026-10-28) once it is active and every one of its Tasks that isn't Dropped is Done, at least one of them; a shaping one waits for Confirm, which makes it done at once when its Tasks already are. Dropping a shaping Initiative drops its Tasks still in Shaping with it (the user, 2026-11-07) and leaves its other Tasks as they are; dropping an active one changes no Task.
- **A queue for Start** (the user's answer of 2026-10-29): several Tasks may be in progress in one Project, up to its Project limit (the user, 2026-11-08). When Start can't run a Task now because a blocker isn't Done or Dropped yet (the user, 2026-11-06), its person is at their Task limit, its Project already has as many started Tasks (In progress, Waiting on you or Paused) as its Project limit, the Office-wide limit on running Tasks is reached or a Window cap or Daily cap would be passed (tier 3, "Usage estimates" below), Start puts the Task in one Office-wide queue, shown with its reason on the board and on Now. On the board a queued Task sits in a Queued column of its own, between Ready and In progress, and stays Ready, so the Ready column holds only Tasks that wait for the user (the user, 2026-11-07). A blocked Task offers only the queue, as it can't start anyway, and an Overlap it also has queues it behind those Tasks too. A queued Task starts by itself, oldest first, when every blocker is Done or Dropped, a desk, its Project and its person free up and its caps allow it; only a Project's own Tasks count against its Project limit, so a full Project never holds another Project's Task, and lowering the limit stops no started Task; the user can take it out of the queue or move it up, one place or to the top (the user, 2026-11-09). Every other reason (a vacant Role, and the like) still refuses Start with the reason. This replaces "Start in tier 1" above.
- **Overlaps at Start** (the user's answer of 2026-10-29): the Planner's Plan lists the files and folders it expects to change. Start warns when a Task in progress in the same Project expects to change some of the same, and offers to start anyway or to queue the Task behind that one; a Task that overlaps several waits behind all of them, until each is Done or Dropped (amended 2026-10-29). Real conflicts are handled at Publish ([2.3](2.3-pipelines.md), "Conflicts at Publish").
- **Usage estimates** (tier 3, the user's answers of 2026-11-01): a Ready Task shows its **Usage estimate**, what its whole Pipeline is expected to use on each engine the engine cascade gives its Stages' Roles in its Project ([5.4](5.4-the-engine.md#defaults)), on its card, its page, in the Start flow and in the queue, in the measures ticked in Settings › Office limits (any of tokens, the 5-hour window, the 7-day window and cost in dollars; none turns estimates off; tokens and the 5-hour window by default). It is the median of the last 20 done Tasks' Stage runs for the same Project and Pipeline, Stage by Stage, summed, once there are 3; below that the Planner's token estimate in the Plan, its cost derived from the Office-wide dollars per token of the done Tasks; with neither, "no estimate". Either way, a window's estimate is the tokens times the Office-wide window % per token (the user, 2026-11-02, as `utilization` comes in whole percents and a Stage run never gets a like-with-like pair of readings): learnt per engine from successive readings of one Reading source ([5.4](5.4-the-engine.md)), a pair counting when the Office's tokens went up between them and a window's part when it neither reset nor went down, pooled as the changes summed over the tokens. The ratio mixes models, a limit the user accepted. Cost is priced by the Model prices of Settings › Engines; a model with no price gives "no cost". Caps are per engine (the user, 2026-11-01 and 2026-11-02, each Claude Code account and each API endpoint being an engine): a **Window cap** on the 5-hour and the 7-day window, which only Claude Code engines have (90% by default), and a **Daily cap** on tokens and on dollars (off unless set; today as in [2.7](2.7-notifications.md)). Start waits in the queue when a ticked measure's cap would be passed, the Task's estimates on the engines under one cap added up: a window's use plus the estimates of Tasks started since its last reading plus this Task's; a day's use plus what is left of the estimates of Tasks in progress plus this Task's. It is released when the cap resets, and starts anyway when every exceeded cap resets within the prompt cache's hour ([5.4](5.4-the-engine.md)). "No estimate" and "no cost" never hold a Start. There are no per-Stage or Planning estimates. Chosen while writing task 37, for the user to review: a window with no reading, or whose reset has passed, counts as unused; the hour exception covers the Daily caps' midnight too.
