# 2.1 Work

From [07](../../.scratch/the-office/issues/07-work-model.md), with [08](../../.scratch/the-office/issues/08-pipelines.md) and [19](../../.scratch/the-office/issues/19-work-mockup.md).

- **Project:** a repository The Office works on, with its own commands (an install command, and a list of named commands, each of a **Command kind**: build, lint or test), install inputs, default Pipeline (the one its Tasks usually follow: named in the Planner's Brief, and listed first when the user chooses a Pipeline for a Task that has none; a new Task doesn't take it, see Ready below), publishing mode (push + PR, or merge, run by The Office's own code; see [9](README.md#defaults)), environment, skills setting and **Project limit**: how many of its Tasks may be started at once, 1 by default and up to the Office-wide limit's maximum, set in its page's Work block (the user, 2026-11-08). It shows as its mark, and may have an **Icon**, shown in place of the mark's letters and colour, and a **Logo**, the larger image on its page and card, each in a light and a dark version, the one for the palette shown used, and each uploaded or chosen from its repository as a copy ([4](4-ux-direction.md)). Its commands may be left unset when it is added: the repository and a name are enough, and a command not set is set later on its page or by Devops' Proposal; once set, a command can be changed but not cleared. Until then a Task installs nothing without an install command, a Script Stage whose command isn't set ends could-not-run, saying how to set it, and never passes, and the environment check skips it (the user, 2026-11-09). Every Project starts with three commands, Build, Lint and Test (keys `build`, `lint`, `test`, of the matching kind), which may be left unset when it is added. More are added on its page or by Devops' Proposal, in the order they were added, each with a key (lower-case letters, digits and `-`, starting with a letter, at most 40 characters, unique in the Project; `install` and `publish` are reserved), a name (at most 60 characters), a kind and a command line, which can't be blank once added. The key is fixed once added, since Pipelines name a command by it; the name, kind and line can be changed, and a command can be removed, unless the Project's default Pipeline runs it: then removing it is refused, naming the Pipeline, until another default is chosen; a command another Pipeline runs can be removed, and that Pipeline's Stage then ends could-not-run ([2.3](2.3-pipelines.md#defaults)). The install command stays apart from the list: it alone runs before a Stage when its inputs changed (the user, 2026-11-11).
- **Idea:** captured quickly, in a Project or Office-wide. States: new, shaped, dropped. Shaping makes an Initiative or a Task and keeps the Idea as the origin link; its Attachments move with it. A Task shaped from an Idea takes the Idea's notes as its Description, editable until Start (the user, 2026-11-05).
- **Initiative** (tier 2): Office-level, spans Projects; each of its Tasks is in one Project. States: shaping (with the CTO), active, done (all Tasks done), dropped. It is shaped from an Idea, or created with `create_initiative` by the CTO or the Office Manager in their chat when the user asks ("Creating an Initiative" below). Order inside it is dependencies plus manual order. It may have a Pipeline of its own, the **Initiative's Pipeline**: with one, it works on the **Initiative's branch** in each Project it spans ([5.5](5.5-git-and-isolation.md#defaults)), and its **Publishing Tasks** publish the whole change ("An Initiative's Pipeline" and "Publishing Tasks" below).
- **Task:** one unit of work in one Project, done when its **Definition of Done** is met: a published change, an Attachment, or both.
  - States: **Backlog → Planning → Ready → In progress → Done**, side states **Waiting on you** and **Paused**, exit **Dropped**; before Backlog, **Shaping**, for a Task of an Initiative still being shaped (below). Ready requires a Plan and a Definition of Done, both confirmed by the user, or by auto mode on their behalf (below), no Pipeline proposal left open and no Decision on the Task left open (the user's answer of 2026-10-26), and a Pipeline: a Task has none until one is chosen, from the Planner's proposal confirmed by the user or by auto mode, or by the user, and its page shows a placeholder where the Stages will be until then (the user's words of 2026-11-11: "Pipeline before plannng is Full. I want it to be none with some placeholder-like pipeline... so I can clearly see that the pipeline is not yet determined based on the task."). **Planning is optional** (the user, 2026-11-05): a Task whose Plan and Definition of Done were written by the user or given with the Task, and confirmed by the user, goes from Backlog straight to Ready by **Mark Ready**, under Ready's other rules; Mark Ready shows in Backlog only once both parts are confirmed and a Pipeline is chosen, which the user does there on the Pipeline rail; its checklist names "Choose a Pipeline" while there is none. Work moves forward; the two ways back are a change to the Plan, the Definition of Done or the Pipeline proposal of a Ready Task that hasn't started, by the user's **Save** or by the Planner, which takes it back to **Planning** to be marked Ready again (the user's words of 2026-11-11: "If a task is Ready but not yet started it should still be possible to update plan/dod, which should move the task to planning again and require marking as done. Agent should stil lbe able to do these things with the task."), and a **Move** of a Ready Task to another Project, both below. In progress shows the current Stage.
  - **Description** (what the user wants, in their own words): optional, written in "New Task" (the top bar's Create › Task) under the title and edited on the Task page, where it sits above the Plan; the CTO writes one on an Initiative's Tasks too, by their changes below (the user, 2026-11-06). It is part of the Planner's Brief and of every Agent Stage's Brief ([2.5](2.5-context-policy.md)); with none, the title alone is enough to plan from (the user, 2026-11-05). A Description can mention a Task, Initiative, open Decision or Idea, picked with `@` as in the chat or pasted as the link to its page; it is saved as a Markdown link to the record's page and shown on the Task page as the record's chip (the user, 2026-11-09).
  - **Plan** (how) and **Definition of Done** (what must be true) are separate first-class parts of the Task, written by the user, co-written with the Planner in a Thread on the Task, or given with the Task by whoever creates it with the `create_task` Office tool, confirmed by the user. **Given with the Task** (the user, 2026-11-09): when it is already known how the Task will be done and what must be true, its creator gives both parts, or neither, as half of the pair helps nobody; the Task lands in Backlog with both **Not confirmed**, and the user confirms each on the Task page and marks the Task Ready from Backlog without Planning, as for parts they wrote themselves. Nothing its creator gives is confirmed by them, and the Task's state changes name its creator, so they show who wrote the Plan. Make a plan and Plan with… start from the given parts, for the Planner to rework rather than start over. **Save and Confirm are separate acts** (the user, 2026-11-05): until the Task starts the user edits a part with Save and Cancel, and Confirm, the user's only way to confirm, takes the part as it reads; auto mode confirms on their behalf (below). A Save that changes nothing changes nothing, the confirmation included; a changing Save leaves the part unconfirmed in Backlog, Planning and Ready alike, and a Task in Planning stays there. Ready needs both parts confirmed, so a changing Save on a **Ready** Task takes it out of the queue if it was queued and moves it back to **Planning** (the user's words of 2026-11-11, above), in its planning Thread and auto mode, the changed part Not confirmed and the Task no longer marked planned; the user confirms and marks it Ready again, or the Planner marks it planned and auto mode does. A Ready Task that was never in Planning (marked Ready from Backlog) has no planning Thread, so a changing Save moves it to **Backlog** instead. The editor says beside Save, while the Task is Ready, which of the two a change does and that a queued Task leaves the queue. The Planner may also change a Ready Task in its own planning Thread, but only when the user asks: write_plan, write_definition_of_done or propose_pipeline that change something move it back to Planning in the same save, moved by the Planner, and mark_planned works as in Planning from there; a write that changes nothing moves nothing, and Tags never move a Task. Since the Planner may not be the author, an unconfirmed part's badge reads **Not confirmed**.
  - **Two ways to start Planning** (the user, 2026-11-05), both moving the Task to Planning: **Make a plan**, in the Planner's empty tab in Backlog and as the **Plan** button on a Backlog card on the board (the user, 2026-11-08), starts the Planner at once from the title and the Description, and from the Plan and Definition of Done when the Task has them, with nothing more to write; **Plan with…**, in the Task's head, opens the Planning Thread and the Planner waits for the user's first message. The board's Plan has no room for the Auto mode switch, so it plans in the remembered auto mode, which its tooltip names.
  - **Auto mode** (the user, 2026-11-10): an **Auto mode** switch sits beside Make a plan in the Planner's tab. It starts at the remembered default, an Office setting that is off until first chosen, and the choice made with Make a plan becomes the default; Plan with… always plans with auto mode off. The Task keeps the choice while it is in Planning, and its card and the Planner's tab read "Planning with …, in auto mode". In every planning Thread the Planner says it has finished with the `mark_planned` Office tool, once the Plan, the Definition of Done and the Pipeline are written and nothing is left to ask; it is refused, with the reason, outside Planning, before the Plan and the Definition of Done are written, and while the Task has neither a Pipeline nor a proposed one. It marks the Task planned until it next enters Planning. With auto mode off nothing else changes: the user confirms the parts and marks the Task Ready. With auto mode on and no Decision on the Task open, The Office confirms in one save whatever of the Plan and the Definition of Done isn't confirmed yet, confirms the proposed Pipeline (with none proposed, a Task that has a Pipeline keeps it; one that has none can't be marked planned) and marks the Task Ready under Ready's rules; the Task's state changes record the move to Ready as made by auto mode, naming each part it confirmed. With a Decision open, `mark_planned` changes nothing and tells the Planner to wait: the user's answer comes as the Planner's next message, the Planner carries on, marks the Task planned again, and auto mode marks it Ready.
  - **Plan the Initiative** (the user, 2026-11-10): an active Initiative's page has a **Plan the Initiative** action with the same **Auto mode** switch as Make a plan, starting at the remembered default; the choice becomes the default. It opens one planning Thread with the Planner on the Initiative: one session, reading every Project's base branch (the Initiative's branch in the Projects it spans, when it has a Pipeline: [2.4](2.4-conversations.md)) and changing no file, as the CTO's shaping Thread does. The Planner plans the Initiative's Backlog Tasks in dependency order, where only blockers inside the Initiative count: a Task's turn comes once each of them is marked planned, Ready or beyond, or Dropped. Where the engine has subagents, the Planner hands each Task's research and drafting to one and plans the Tasks whose blockers are planned in parallel; without them it plans them one after another. As each Task's turn comes, the Planner moves it from Backlog to Planning with the `start_planning` Office tool, refused with the reason for a Task outside the Initiative or not in Backlog, while a blocker inside the Initiative isn't planned yet, and outside the Initiative's latest planning Thread. It writes the Task's Plan with its files to change, Definition of Done, Pipeline and Tags itself, with the planning tools naming the Task by its id, and marks it planned with `mark_planned`; auto mode then works as for a single Task, and without it the Task waits in Planning for the user's Confirm. The Initiative's Thread counts as the planning Thread of each Task planned in it: the Task's Planner's tab links to it, no Planner's Thread opens on the Task meanwhile, and the Task has no worktree until Start makes one. The page links to the Thread and shows each Task's progress (Waiting, Planning, Planned, Ready), with a count of the Tasks planned. **Decisions in this Thread** (the user, 2026-11-10): the Planner opens a Decision with `open_decision` naming one of the Initiative's Tasks by its `taskId`, one per Task, several open at once; one naming no Task or a Task outside the Initiative is refused with the reason. Its card shows in the Thread naming its Task, on that Task's page in Needs you, linking to this Thread, and in Mark Ready's checklist, where it keeps the Task from Ready until answered; it is answered in any of these places. While a Decision on a Task is open, that Task isn't marked planned and the Tasks of the Initiative that wait for it are refused `start_planning`, as their blocker isn't planned; the Planner plans the other Tasks and ends its turn only when every Task left waits for an answer, or all are planned. An answer given while the Planner waits resumes the session at once. One given while it works is recorded at once, so the Decision is answered and the Task is free for Ready, and reaches the session when its turn ends, every waiting answer in one message, each naming its Task; if that message never reaches a session, those Decisions open again. **Rewrites:** when an answer or a later decision changes Tasks already planned, the Planner rewrites their Plan, Definition of Done or Pipeline from this Thread. A Task in Planning marked planned, in this or an earlier planning Thread of the Initiative, is rewritten and marked planned again. A Ready Task goes back to Planning in this Thread in one move, as on a changing Save (the user's words of 2026-11-11, above), the rewritten part Not confirmed, and is marked planned again; auto mode then accepts it and marks it Ready again, and without it it waits for the user's Confirm. Writing any part of a Task marked planned clears its marked planned in every Thread; Tags never move a Task. A Task that has started (In progress, Waiting on you, Paused, Done), is Dropped or is being planned in its own planning Thread is never rewritten: the write is refused with the reason, and the Planner opens a Decision on that Task instead, saying what changed and what it recommends. The action is refused with the reason when the Initiative isn't active, no Planner is hired, none of its Tasks is in Backlog, or one of its Tasks is still being planned in an earlier planning Thread (in Planning there, not yet marked planned).
  - **Dependencies** (tier 2): on any Task in any Initiative or Project; a blocked Task cannot start, but can be queued until its blockers are Done or Dropped (the user, 2026-11-06).
  - **Organisation:** three priority levels plus manual order per Project (tier 1); tags, full-text search, saved views (tier 2); **Archive** (tier 3), below.
    - **The board's Done column** (the user's words of 2026-11-11, "order done tasks from most recent"): its Done and Dropped Tasks show the one that ended last on top, ungrouped and grouped by Initiative alike; a Task's end is its last move to Done or Dropped, and one whose end was never recorded follows the dated ones in the board's order (priority, then manual order). Every other column keeps the board's order.
  - **Moving** a Task to another Project (tier 3): see "Moving a Task" below.
- **Attachment:** a document (Markdown), image or screenshot, file or link, attached by the user or an Agent to an Idea, Initiative or Task; can be a Task's result. Diffs and Stage logs are parts of a Task, not Attachments. A Task's Attachments are shown by round, each the work between one Gate send-back and the next; versions of one Attachment are postponed by the user until after tier 3 (2026-11-08). A file Attachment is a **text file** when its bytes are text: valid UTF-8 with no NUL byte in the first 8 KB, the NUL test being the one the API engine's Read and Grep use; a document is always one, and an image or a PDF never is, as each is read and shown as what it is. The Office judges it once, as the file is attached, and keeps it with the Attachment; its kind doesn't change, so a `.css` is still a file. A PDF's text is pulled out once as it is attached, a page marker line before each page, and kept beside the file; a PDF with none, such as a scan, reads as having no text (the user, 2026-11-10).

## Defaults

Gaps no ticket settled, filled with the simplest choice consistent with the tickets and accepted by the user; each says when.

- **Start in tier 1** is refused with the reason when the Project already has a Task in progress, the person is at their Task limit or the Office-wide limit is reached (as the click-through does); no queue. (accepted 2026-10-24)
- **Waiting on you while planning:** a Task in Planning with an open Decision stays in Planning and shows a Waiting on you badge; the Waiting on you state stays a side state of In progress. (added while building tier 1, accepted 2026-10-25)
- **Plan as a Task with the Planner** on an Idea shapes it into a Task and opens its planning at once, as the click-through does. (added while building tier 1, accepted 2026-10-25)
- **The Planner joins on the first message** (the user's answer of 2026-10-30): moving a Task to Planning opens its planning Thread but starts no session; the Planner's first turn runs on the user's first message there, so a Plan the user writes alone costs no model call. This holds for Plan with…; Make a plan starts the Planner at once (the user, 2026-11-05).
- **Tasks of an Initiative still being shaped** (the user, 2026-11-07, replacing their answer of 2026-10-28) wait in **Shaping**, the first state of a Task added to a shaping Initiative, by the user or the CTO; one added to an active Initiative, by the user or a Proposal, starts in Backlog. A Task in Shaping has no card on the Work board and isn't in its counts or its note of other Projects, can't be planned, marked Ready, queued or started, and its Plan, Definition of Done and Pipeline can't be changed, except that it can be moved to another Project, which leaves it with no Pipeline and in Shaping ("Moving a Task" below; the user, 2026-11-07); no session works on it, so a Thread it already has can be read but not continued until Confirm; it is still seen on the Initiative page and its own page, which says what it waits for, found by search and dropped, alone or with its Initiative ("An Initiative is done" below), and its title, Description and dependencies still change. Confirming the Initiative says its outcome and Task list are agreed, makes it active and moves its Tasks in Shaping to Backlog, in one step; nothing else makes that move. Tasks of a shaping Initiative already in Planning or beyond when this rule came stay where they are, as work only moves forward.
- **Archive** (tier 3, the user, 2026-11-07): the user archives a Done or Dropped Task, and Done and Dropped Tasks are also archived automatically once finished for the **Archive period**, a number of days set Office-wide in Settings › Office limits, 30 until changed; Tasks already finished longer ago than that are archived at the first run. **Archived** is not a state: the Task stays Done or Dropped, so dependencies, Initiatives and Usage estimates read it as before. An archived Task leaves the Work board, its counts and its lists, and shows in a view of archived Tasks. Its page and Threads stay readable, read-only as for any Done or Dropped Task ([2.4](2.4-conversations.md)); the top bar's search finds it (the Work board's can't, as it has no card there), and its Initiative's page still shows it. **Restore**, one click, returns it to the board in the state it had, and it gets a full period again from that moment. Initiatives are archived the same way (the user's agreement with the Task "Implement initiatives redesign", 2026-11-09): a Done or Dropped Initiative is archived by Archive in its More menu, or automatically once it has ended for the same Archive period, counted from when it became Done or Dropped or was last restored; Initiatives that ended longer ago than the period are archived at the first run, and so are those that ended before their end was kept and nothing dates. An archived Initiative stays Done or Dropped, leaves the Initiatives tab's board and shows in the Archived tab beside the archived Tasks; its page and Threads stay readable, the Work board still names its Tasks by it, and Restore returns it to Done or Dropped on the board.
- **Moving a Task** (tier 3, the user, 2026-11-07): **Move** on the Task page puts a Task in another Project. It is refused with the reason once the Task has ever entered Planning, has started or has a worktree in its Project; also for an Onboard Task, which belongs to its Project, and for a Dropped Task, as returning to Backlog would undo the Drop. A moved Task has no Pipeline until one is chosen there, as the new Project's commands differ, and keeps its Initiative, dependencies, Attachments and Threads. It returns to Backlog with its Plan and Definition of Done Not confirmed; a Ready Task leaves Ready and the queue in the same save, as a changing Save takes one, though to Backlog, since a Task that can move was never in Planning. A Task in Shaping stays in Shaping instead, and goes to Backlog only by Confirm. The move is kept in the Task's record, and an Initiative's Projects follow from its Tasks. A Publishing Task can't be moved either, as an Onboard Task can't. Moving a Task of an Initiative with a Pipeline into a Project the Initiative doesn't span yet makes the Initiative's branch there ([5.5](5.5-git-and-isolation.md#defaults)); the Move is refused, with the reason, when the branch can't be made or the Project lacks a command the Initiative's Pipeline runs ([2.3](2.3-pipelines.md#defaults)). A Project the Initiative stops spanning keeps its branch. (amended 2026-11-12)
- **Shaping without a CTO** (the user's answer of 2026-10-28): an Idea is shaped into an Initiative whether or not a CTO is hired. With one, the shaping Thread opens at once and the CTO starts on it; without one, the user writes the Initiative by hand, and its Thread opens when they start it once a CTO is hired.
- **Creating an Initiative** (the user's answers of 2026-11-12): the CTO and the Office Manager, and no other Role, have `create_initiative` in their chat, and use it only when the user asks for an Initiative or agrees to one. It takes a title and an outcome, the outcome naming the Projects meant; no Projects are stored, as an Initiative spans its Tasks' Projects, and the CTO adds the Tasks while shaping. The Initiative lands in shaping, created by that person, with no origin Idea, and waits for the user's Confirm on its page like one shaped from an Idea. Its shaping Thread opens as above, with or without a CTO; its opening has the CTO check the outcome with the user, then agree on the Projects and the Tasks. Its page shows no Origin.
- **The CTO's changes to an Initiative** (the user's answer of 2026-10-28): while it is shaping, the CTO writes the outcome, Tasks and dependencies straight onto it, and the user confirms the whole once; once it is active, each change the CTO wants is a Proposal the user applies. The title and Description of one of its Tasks are among these changes, and both change only until that Task starts (the user, 2026-11-06). So is the Initiative's Pipeline, under "An Initiative's Pipeline" below (amended 2026-11-12).
- **An Initiative starts in its Idea's Project** (the user's answer of 2026-11-12): an Initiative shaped from an Idea captured in a Project starts in that Project. The CTO's shaping Brief says so, and the CTO asks only whether it reaches other Projects too, not which Project it is for; Add a Task on its page chooses that Project until the Initiative has Tasks. Nothing new is stored: an Initiative still spans the Projects of its Tasks.
- **The user writes the outcome** (the user's answer of 2026-10-28): with or without a CTO, the user edits an Initiative's outcome on its page while it is shaping; once it is active, the outcome changes only by a Proposal the user applies, as the CTO's other changes do.
- **A Dropped blocker** (the user's answer of 2026-10-28) no longer blocks; the Task that waited for it still lists it, marked as dropped.
- **Onboarding a Project** (the user's answer of 2026-10-28) is a chat, then a Task. "Ask Devops to onboard one" on the Projects page opens a chat with Devops, who drafts the Project (path, name, base branch, commands, install inputs, publishing mode, default Pipeline) as a Proposal. Applying it adds the Project and an "Onboard" Task in it, Ready on the built-in **Onboard** Pipeline (Devops makes the Project build and test in a fresh worktree, asking before installing anything → a Verify Script Stage running Test, back to Onboard at most twice → Publish by the Project's publishing mode, so the fixes Devops makes reach the repository); the user starts it, as any Task. The Project page shows the Project's onboarding from that Task: onboarding, onboarded, or none. Adding a Project by hand stays, with no Onboard Task. (added while building tier 2) From tier 3 the Project may be a Repository URL instead of a path: Devops reads the repository from a shallow fetch with the Office identity, nothing cloned, and applying the Proposal clones it into the Office data directory before adding the Project; adding by hand takes a folder, a URL or a pick from the user's GitHub repositories (the user, 2026-10-31 and 2026-11-01).
- **Tags** (the user's answer of 2026-10-28) are on Tasks only; the user sets them on the Task page and in "New Task", and the Planner while planning.
- **Search** (the user's answer of 2026-10-28) is two boxes over one full-text search: the Work board's narrows Tasks by title, Plan, Definition of Done and Tags; the top bar's (⌘K) finds Tasks, Initiatives, Ideas, people and document Attachments and opens the one picked. Both follow the Project filter and say how many more matches are in other Projects.
- **Saved views and the Project filter** (the user's answer of 2026-10-28): Saved views are stored by The Office and never hold the Project filter; the Project filter is remembered per browser, so the desk and the phone can show different Projects.
- **Group by Initiative** (the user's approval of [its design](../design/board-by-initiative.html), 2026-11-09): a switch at the end of the Work board's filter bar lays the board out in a group per Initiative with a card on the board, newest first with the Active ones before those that ended, then No Initiative last. Each group has a header (its name as a fold, its state, its Projects, its progress over every Task of the Initiative, how many of its cards show, and a link to the Initiative) and its Tasks in the state columns, under column heads shown once. The switch is remembered in this browser and also kept in the board's address (`?group=initiative`) apart from the filters: a board opened without `group` in its address is grouped as last chosen here, a Saved view never holds it, and Clear leaves it. A group's fold is remembered in this browser, a Done or Dropped Initiative's starting folded. The Initiative filter shows its group alone, saying why when it has no card; the other filters leave out a group with no card shown, naming those search, Priority and Blocked left out. A card drags only within its column inside its own group: the board never changes a Task's Initiative.
- **The Initiatives tab is a board** (the user's approval of [its design](../design/initiatives-tab.html), Proposed: Board, 2026-11-09): Shaping, Active and Done, each newest first but Done, the one that ended last on top, with Dropped folded at its foot; its search (of names and outcomes) and Waiting on you are kept in the address; the Dropped fold is remembered in this browser. Every column always shows, with its count and a line saying why it is empty; the Project filter narrows the board and the archive. The Archived tab shows the archived Tasks or, switched, the archived Initiatives: a search, a Done / Dropped / All filter with counts, the one that ended last on top under a line per month, 25 to a page, all kept in the address.
- **An Initiative is done** (the user's answer of 2026-10-28) once it is active and every one of its Tasks that isn't Dropped is Done, at least one of them; a shaping one waits for Confirm, which makes it done at once when its Tasks already are. Dropping an Initiative, shaping or active, drops every one of its Tasks not yet Done or Dropped with it (the user's answer of 2026-11-12, replacing "dropping an active one changes no Task"): those in Shaping, Backlog, Planning, Ready (queued too), In progress, Waiting on you and Paused, its Publishing Tasks included, each as that Task's own Drop would, so a queued one leaves the queue and a started one has its running Stage stopped; each change is recorded as the user's. Its Done and Dropped Tasks stay as they are. Initiatives dropped before this rule have their Tasks not yet Done or Dropped dropped once by The Office, with the reason "its Initiative was dropped". With an Initiative's Pipeline, its Publishing Tasks count among its Tasks, so it is done only once they are Done too; after a Drop no Publishing Task is added, and its Initiative's branches are kept ([5.5](5.5-git-and-isolation.md#defaults)). (amended 2026-11-12)
- **An Initiative's Pipeline** (2026-11-12, the Initiative 1116efba; details settled with the Plan of Task 12e9ab91): it is chosen while shaping from the Pipeline library, as a Task's is: by the user on the Initiative page or by the CTO with an Office tool, both straight onto the Initiative. It starts as **None**, which publishes Task by Task as before; no Project's default applies, and Initiatives confirmed before this rule have none. Confirm fixes whether it has one. Once the Initiative is active, which Pipeline it has changes only by the CTO's Proposal, applied by the user; applying it is refused once its first Publishing Task has started ("the Pipeline starts"), or when a Project it spans lacks a command the Pipeline runs ([2.3](2.3-pipelines.md#defaults)). An applied Proposal also changes the Pipeline of its Publishing Tasks not yet started, unless the user edited their Stages for that Task. The Initiative names a library Pipeline, as a Task that hasn't started does, so a library edit changes it; a Publishing Task takes it as its own Pipeline under a Task's rules. The Initiative's other Tasks keep Pipelines of their own: the Initiative's Pipeline runs only in its Publishing Tasks.
- **Publishing Tasks** (2026-11-12, the Initiative 1116efba; details settled with the Plan of Task 12e9ab91): an Initiative with a Pipeline gets them in the same step that makes the last of its other Tasks Done or Dropped, and only while it is active. A Project gets one when its Initiative's branch holds commits its last Done Publishing Task didn't publish (or, with none yet, commits the base branch doesn't have) and it has no unfinished Publishing Task; so a Project whose Tasks were all Dropped gets none, and a dropped Publishing Task isn't added again until another of the Initiative's Tasks ends. It is titled "<Initiative> → <Project>", in the Initiative and that Project, and its Description is the Initiative's outcome. Its Plan is The Office's own words: the Initiative's branch, the base branch, the publishing mode and the Initiative's Done Tasks in that Project. Its Definition of Done is every statement of those Tasks plus "The whole change is in <base branch> by <publishing mode>", and its Files to change are the union of theirs.
