# 5.1 Shape

- **One long-running Node service** on the workstation hosts the API, the web UI, the agent supervisor and the database connection. Agents are child processes (the SDK spawns the Claude Code binary per session). No separate runner, no remote protocol; the supervisor sits behind its own boundary so it could become a separate host later. The service listens on `localhost` unless the user sets `OFFICE_HOST` to an IP address (decided with the user on 2026-10-31, for a host that runs The Office away from the workstation). The Office is used in three ways (the Initiative "User authentication", 2026-11-12): at `localhost`; by IP on the local network over plain HTTP, a trusted network; or at its **public address**, behind a reverse proxy the user sets up with HTTPS and a domain. Setting up the proxy is the user's job; The Office needs from it HTTPS to the browser, the original `Host` passed on, `X-Forwarded-Proto: https`, and WebSocket upgrades on `/api/events` passed through ([docs/running-the-office.md](../running-the-office.md) says how). Every HTTP request to `/api` and every WebSocket needs a signed-in user, `localhost` included, except the sign-in pages and their callbacks ([2.10](2.10-users-and-signing-in.md)). Any page the user opens in a browser can still reach The Office (browsers apply no cross-origin rule to WebSockets, and DNS rebinding points a site's own name at `127.0.0.1` or a local network address), so before any sign-in is looked at the service refuses every HTTP request and WebSocket whose `Host` is not `localhost`, `127.0.0.1`, the IP address it arrived at, at its port, or the public address's name, or that carries an `Origin` other than one of those addresses' own. A request at the public address's name counts as HTTPS only with `X-Forwarded-Proto: https`.
- **Windows and Linux.** The workstation runs either, and every tier is built and checked on both. What differs (the Office data directory, shells and their rules, finding a command that can't run, ending a process tree, path length limits, where secrets live) sits behind one platform layer in the service; nothing else branches on the operating system.
- **Fresh code; functionality copied, not code.** What [03](../../.scratch/the-office/issues/03-factory-reference.md) marks "keep" is re-implemented from its described behaviour ([research/factory-reference.md](../../.scratch/the-office/research/factory-reference.md)): the lean harness with a stable cached prefix, the resume-vs-fresh rule with a standalone brief, the flat Stage result envelope, Office-owned git with a worktree per Task, the environment as data verified in a fresh worktree, loop limits and budgets, telemetry tagged with prompt features, tool output filtering and the flaky-test re-run, the screenshot trust model, the layered settings merge. Dropped: remote runners, leases, the runner protocol, the `/factory` plugin and MCP entry.

## Defaults

Gaps no ticket settled, filled with the simplest choice consistent with the tickets and accepted by the user; each says when.

- **Windows and Linux** are both supported from tier 1 ([5.1](5.1-shape.md)). (added while slicing tier 1, [24](../../.scratch/the-office/issues/24-slice-tier-1.md), accepted 2026-10-24)
- **Only The Office's own pages reach the service:** the `Host` and `Origin` checks of [5.1](5.1-shape.md), for HTTP and WebSocket alike, accepting `localhost`, `127.0.0.1` and the IP address a request arrived at, at The Office's port, and the public address. A request with no `Origin` (a local tool such as `curl`) passes the `Origin` check; it still needs a signed-in device ([2.10](2.10-users-and-signing-in.md)), and the threat model leaves local processes out ([6](6-permissions-and-safety.md)). (added while building tier 1, accepted 2026-10-25; the public address and signing in added 2026-11-13)
- **The public address** (proposed by Task 3afd3982, 2026-11-13, for the user's agreement): given to The Office as `OFFICE_PUBLIC_ADDRESS` in its `.env`, an `https://` origin with no path (`https://office.example.com`); an invalid one stops the start with a config problem. Unset, The Office has no public address. Addresses The Office builds for the public address (GitHub's and Google's callbacks, a passkey's relying party) come from it, never from the request's headers.
- **Released versions** (Task 627cfcac, 2026-11-15): The Office is released from `main` by the hand-run Release workflow, with semantic-release: the version comes from the Conventional Commits since the last `v*` tag (none of `feat`, `fix`, `perf` or `refactor`, no release), `npm run verify` runs in the run environment before anything is tagged, and an Office release is the tag `v<version>`, a GitHub Release whose notes are those commits, a prebuilt tarball for glibc Linux on x64 and on arm64 (with its production `node_modules` and its own CPU's Claude Code, nothing to build on the target) and the image `ghcr.io/<owner>/the-office:<version>` and `:latest` for `linux/amd64` and `linux/arm64`, made from the same tarball. A release carries `office-release.json`, its version and commit, which Settings › Updates shows; a checkout shows its commit. Before the first tag only the commits after the one that added `.releaserc.json` count. Windows and macOS run from a checkout. How: [docs/releasing.md](../releasing.md).
- **Updating The Office:** The Office updates itself, never by rebuilding itself while it runs, in the way its install allows, which Settings › Updates names with the version it runs. A **checkout** (`npm start` from git) updates its own git checkout: a daily check (the first at boot) and "Check for updates" in Settings › Updates fetch the checkout's upstream and list the commits it is behind, installing nothing. Update is refused, with the reason, when the checkout has local changes, has diverged from its upstream or has none, or the service runs without its launcher; on Windows updating isn't offered (Linux only). Once the user schedules an Office update (held in memory, so a restart cancels it), new Starts join the queue with "An update is scheduled." and each Task waits before its next Agent or Script Stage; Cancel releases both. The update waits for the busy work (an Agent mid-turn in a Stage, a chat or a Consultation; a Thread of any kind with a background Sub-agent still running, listed by its Thread, since the restart would stop it ([2.9](2.9-sub-agents-and-processes.md), added 2026-11-14); a Script Stage; a Publish; a clone or an environment check), not for a Task waiting on the user, a paused Task or an idle Thread with no Sub-agent running. When nothing is busy the service writes the request; a checkout's service stops gracefully and exits with code 75; the launcher (`npm start`, under systemd) fast-forwards to the target commit, runs `npm ci` and the build, and starts the service again. A failed fetch, install or build goes back to the previous commit and rebuilds it. At its next start the service raises an Office Notification that it updated, or that the update failed at which step, with the log in Settings › Updates. How to run it: [docs/running-the-office.md](../running-the-office.md). (added with the Office update task, accepted 2026-11-03) Amended 2026-11-15 (Task 14e9b3bc, Self-update from released versions): an Office release updates to released versions instead. A **release install** (a tarball unpacked into `releases/<version>` beside a `current` link, run by its launcher) and a **container install** (Docker Compose) check the GitHub Releases of the repository their `office-release.json` names, daily and on "Check for updates", list each version newer than theirs with its notes, and leave out drafts, pre-releases and tags that aren't a version; a failed read is the check's problem and installs nothing. For a release install the launcher downloads the CPU's tarball and its `.sha256`, refuses a checksum mismatch without touching `current`, unpacks it into `releases/<version>`, switches `current` and starts the new version; when it doesn't answer `/api/health` within 5 minutes it switches `current` back and starts the previous version. It keeps the current, the previous and its own release and removes the rest. For a container install the service starts the Office updater, a short-lived container that pulls the new image, sets `OFFICE_VERSION` in the compose folder's `.env`, recreates only the `office` service and waits for it to be healthy, else puts the previous version back; when the updater ends while the service still runs, the update failed before replacing it, and the service reports it and releases the hold with no restart. Update is refused, with what to do, for a release copy not started by its launcher from a `releases/` folder, a release with no tarball for the CPU, a container not started by Docker Compose (with the commands to update by hand) and no access to the Docker socket. A rollback puts back the code, never the database, so each release's migrations keep the previous release working. An update only ever moves to its checkout's upstream (normally `main`): an Initiative's branch in The Office's own repository never reaches the running Office, and its work does only once its Publishing Task has put it into `main` and the user updates ([5.5](5.5-git-and-isolation.md#defaults), "The Initiative's branch"; amended 2026-11-12).
