# 5.1 Shape

- **One long-running Node service** on the workstation hosts the API, the web UI, the agent supervisor and the database connection. Agents are child processes (the Claude Code binary, the Codex app-server or the Copilot CLI runtime, one per session), but for the OpenAI-compatible API engine's, whose loop runs in the service ([5.4](5.4-the-engine.md)). No separate runner, no remote protocol. The service listens on `localhost` unless the user sets `OFFICE_HOST` to an IP address, for a host that runs The Office away from the workstation. The Office is used in three ways: at `localhost`; by IP on the local network over plain HTTP, a trusted network; or at its **public address**, behind a reverse proxy the user sets up with HTTPS and a domain. Setting up the proxy is the user's job; The Office needs from it HTTPS to the browser, the original `Host` passed on, `X-Forwarded-Proto: https`, and WebSocket upgrades on `/api/events` passed through ([docs/running-the-office.md](../running-the-office.md) says how). Every HTTP request to `/api` and every WebSocket needs a signed-in user, `localhost` included, except the sign-in pages and their callbacks ([2.10](2.10-users-and-signing-in.md)). Any page the user opens in a browser can still reach The Office (browsers apply no cross-origin rule to WebSockets, and DNS rebinding points a site's own name at `127.0.0.1` or a local network address), so before any sign-in is looked at the service refuses every HTTP request and WebSocket whose `Host` is not `localhost`, `127.0.0.1`, the IP address it arrived at, at its port, or the public address's name, or that carries an `Origin` other than one of those addresses' own. A request at the public address's name counts as HTTPS only with `X-Forwarded-Proto: https`.
- **Windows and Linux.** The workstation runs either, and everything is built and checked on both. What differs (the Office data directory, shells and their rules, finding a command that can't run, ending a process tree, path length limits, where secrets live) sits behind one platform layer in the service; nothing else branches on the operating system.
- **Built on what worked:** the lean harness with a stable cached prefix, the resume-vs-fresh rule with a standalone brief, the flat Stage result envelope, Office-owned git with a worktree per Task, the environment as data verified in a fresh worktree, loop limits and budgets, telemetry tagged with prompt features, tool output filtering and the flaky-test re-run, the screenshot trust model, the layered settings merge. No remote runners, leases or runner protocol.

## Defaults

- **Windows and Linux** are both supported. On Windows The Office runs from a checkout; the releases and installs below are for Linux.
- **Only The Office's own pages reach the service:** the `Host` and `Origin` checks of [5.1](5.1-shape.md), for HTTP and WebSocket alike, accepting `localhost`, `127.0.0.1` and the IP address a request arrived at, at The Office's port, and the public address. A request with no `Origin` (a local tool such as `curl`) passes the `Origin` check; it still needs a signed-in device ([2.10](2.10-users-and-signing-in.md)), and the threat model leaves local processes out ([6](6-permissions-and-safety.md)).
- **The public address:** given to The Office as `OFFICE_PUBLIC_ADDRESS` in its `.env`, an `https://` origin with no path (`https://office.example.com`); an invalid one stops the start with a config problem. Unset, The Office has no public address. Addresses The Office builds for the public address (GitHub's, Google's and the OpenID Connect provider's callbacks, a passkey's relying party) come from it, never from the request's headers.
- **Released versions:** The Office is released from `main` by the hand-run Release workflow, with semantic-release: the version comes from the Conventional Commits since the last `v*` tag (none of `feat`, `fix`, `perf` or `refactor`, no release; a commit's header, its type, scope and subject, is at most 100 characters, or the Conventional Commits check refuses it), `npm run verify` runs in the run environment before anything is tagged, and an Office release is the tag `v<version>`, a GitHub Release whose notes are those commits, a prebuilt tarball for glibc Linux on x64 and on arm64 (with its production `node_modules` and its own CPU's Claude Code, nothing to build on the target) and the image `ghcr.io/<owner>/the-office:<version>` and `:latest` for `linux/amd64` and `linux/arm64`, made from the same tarball. A release carries `office-release.json`, its version and commit, which Settings › Updates shows; a checkout shows its commit. Before the first tag only the commits after the one that added `.releaserc.json` count. Windows and macOS run from a checkout. How: [docs/releasing.md](../releasing.md).
- **Installing on Debian/Ubuntu:** `curl -fsSL https://github.com/przemczan/the-office/releases/latest/download/install.sh | sudo bash` installs the newest release on a fresh Debian 12 or 13 or Ubuntu 22.04 or 24.04 machine (a VM, an LXC guest with nesting, or bare metal), on x64 or arm64 with systemd; anything else, or a run without root, is refused with the reason before anything changes. Each release carries its own `install.sh` stamped with its version, which it installs unless `--version` names another. It installs only what is missing: `git`, the ssh client, Node 22 (22.18 or later, from NodeSource, at `/usr/bin/node`), Docker Engine with Compose and buildx from Docker's repository at the versions [container-runtime.md](../container-runtime.md) holds, held (a Docker already there is kept, and one lacking Compose or buildx stops the installer), and PostgreSQL 18 from PGDG as the machine's own cluster, not a container; each repository's key is checked against its fingerprint. It follows the shared install layout: the release in `/opt/the-office/releases/<version>`, after its sha256, its top folder and its `office-release.json` check out, with `current` switched to it in one rename; the non-root system user `the-office`, in the `docker` group, owning `/opt/the-office` and the data folder; a Postgres role `office` and database `the_office` with a random password; `/etc/the-office/office.env`, readable by root alone, with `OFFICE_HOST`, `OFFICE_PORT`, `OFFICE_DATA_DIR` and `DATABASE_URL`; and `the-office.service`, run as `the-office` through the launcher. It asks only for the address (`127.0.0.1`, this machine alone, unless the user opens it up), the port (`4310`) and the data folder (`/var/lib/the-office`), at the terminal even when piped, or takes them from `--host`, `--port`, `--data-dir` or `OFFICE_HOST`, `OFFICE_PORT`, `OFFICE_DATA_DIR`; `--yes` asks nothing. Before the start it makes a setup token (`setup-token.js --quiet`), so the service's first start prints none, waits up to 3 minutes for `/api/health` to report the database up (else it fails, pointing to `journalctl -u the-office`), and prints the address to open and the token. Running it again is safe: it keeps the answers, the database password, the installed version and the lines the user added to `office.env`, restarts The Office only when the release, `office.env` or the unit changed, installs a newer `--version` and refuses an older one, and prints a new setup token only while no user exists. The data folder can't be changed by a rerun; moving the data is by hand. In an LXC guest it warns that Docker needs nesting, and stops with `pct set <id> --features nesting=1,keyctl=1` when Docker can't start. The public address and anything else The Office reads are lines the user adds to `office.env`, which a rerun keeps; the installer doesn't ask for them, nor installs the language servers. **Uninstalling:** `install.sh --uninstall` stops and removes the service and its unit, `/opt/the-office`, the install log and this Office's run environment containers, networks, volumes and images (by `office.managed` and its `office.instance`), and keeps the data folder, the database and its role, `office.env` and the user `the-office`, so running the installer again brings the same Office back; `--uninstall --purge` also drops the database and its role and removes `/etc/the-office`, the user and the data folder, the last only when it is below a top-level folder, outside the system's own folders, and owned by `the-office` (a data folder it keeps inside the user's home keeps the home too). Neither removes Node, Docker, PostgreSQL or their apt sources, which the install docs say how to remove by hand. It lists what it removes and keeps and asks at the terminal; without one it refuses unless given `--yes`. The user's guide to both installs is [docs/installing.md](../installing.md).
- **Installing with Docker Compose:** the **Compose install** is a folder holding `docker-compose.yml` and its `.env`, which each release carries as `docker-compose.yml` and `the-office.env`, the latter with `OFFICE_VERSION` set to it; the checkout's copies are in `deploy/compose/`. It is Compose project `the-office` with the services `office`, The Office's released image `ghcr.io/przemczan/the-office:${OFFICE_VERSION}` (the tag comes only from `.env`'s `OFFICE_VERSION`), `postgres`, the dev stack's pinned Postgres in the named volume `postgres-data`, published on `127.0.0.1` alone, with its password from `.env`; the bundled Grafana isn't one of its services, as The Office runs it itself on every install kind ([5.2](5.2-stack.md), Infrastructure); a one-shot `data-folder` step runs first as root, creating the data folder if needed and making its top (never what is inside) owned by uid 10001, and The Office starts only once that step has finished and Postgres is healthy. The Office runs as the image's non-root user `office` (uid 10001), on the **host's network**, since the Host check above accepts the IP address a request arrived at, at its port: behind Docker's bridge that address would be the container's own, so `OFFICE_HOST` and `OFFICE_PORT` behave as on a direct install only on the host's network (localhost, the LAN IP, the public address), and the image's health check asks at `OFFICE_HOST` and `OFFICE_PORT`. It mounts the host's Docker socket and joins its group (`DOCKER_GID`), which is reaching the host as root ([container-runtime.md](../container-runtime.md)), and the data folder at the **same absolute path** on the host and in the container, since run environments bind-mount a Task's worktree by its path, read by the host's Docker daemon; so only Projects inside the data folder (those added by Repository URL) mount. Its container gets only its own variables, listed one by one, so nothing else in `.env` reaches Project commands. `restart: unless-stopped` and `stop_grace_period: 1m`; moving to another release is `OFFICE_VERSION` in `.env` and `docker compose up -d --no-deps office`, which recreates The Office alone. The install, update and uninstall walkthrough is the install docs' part.
- **Updating The Office:** The Office updates itself, never by rebuilding itself while it runs, in the way its install allows, which Settings › Updates names with the version it runs; on Windows updating isn't offered (Linux only). A **checkout** (`npm start` from git) updates its own git checkout: a daily check (the first at boot) and "Check for updates" in Settings › Updates fetch the checkout's upstream and list the commits it is behind, installing nothing. Update is refused, with the reason, when the checkout has local changes, has diverged from its upstream or has none, or the service runs without its launcher. Once the user schedules an Office update (held in memory, so a restart cancels it), new Starts join the queue with "An update is scheduled." and each Task waits before its next Agent or Script Stage; Cancel releases both. The update waits for the busy work (an Agent mid-turn in a Stage, a chat or a Consultation; a Thread of any kind with a background Sub-agent still running, listed by its Thread, since the restart would stop it ([2.9](2.9-sub-agents-and-processes.md)); a Script Stage; a Publish; a clone or an environment check), not for a Task waiting on the user, a paused Task or an idle Thread with no Sub-agent running. When nothing is busy the service writes the request; a checkout's service stops gracefully and exits with code 75; the launcher (`npm start`, under systemd) fast-forwards to the target commit, runs `npm ci` and the build, and starts the service again. A failed fetch, install or build goes back to the previous commit and rebuilds it. At its next start the service raises an Office Notification that it updated, or that the update failed at which step, with the log in Settings › Updates. How to run it: [docs/running-the-office.md](../running-the-office.md). An Office release updates to released versions instead. A **release install** (a tarball unpacked into `releases/<version>` beside a `current` link, run by its launcher) and a **container install** (Docker Compose) check the GitHub Releases of the repository their `office-release.json` names, daily and on "Check for updates", list each version newer than theirs with its notes, and leave out drafts, pre-releases and tags that aren't a version; a failed read is the check's problem and installs nothing. For a release install the launcher downloads the CPU's tarball and its `.sha256`, refuses a checksum mismatch without touching `current`, unpacks it into `releases/<version>`, switches `current` and starts the new version; when it doesn't answer `/api/health` within 5 minutes it switches `current` back and starts the previous version. It keeps the current, the previous and its own release and removes the rest. For a container install the service starts the Office updater, a short-lived container that pulls the new image, sets `OFFICE_VERSION` in the compose folder's `.env`, recreates only the `office` service and waits for it to be healthy, else puts the previous version back; when the updater ends while the service still runs, the update failed before replacing it, and the service reports it and releases the hold with no restart. Update is refused, with what to do, for a release copy not started by its launcher from a `releases/` folder, a release with no tarball for the CPU, a container not started by Docker Compose (with the commands to update by hand) and no access to the Docker socket. A rollback puts back the code, never the database, so each release's migrations keep the previous release working. An update only ever moves to its checkout's upstream (normally `main`): an Initiative's branch in The Office's own repository never reaches the running Office, and its work does only once its Publishing Task has put it into `main` and the user updates ([5.5](5.5-git-and-isolation.md#defaults), "The Initiative's branch").
- **Restarting The Office:** Settings › Updates has a Restart card, "Restart The Office", for a setting that applies only at The Office's next start (such as Settings › Telemetry, whose card offers the same button beside "Applies the next time The Office starts."). It is offered only where something starts The Office again once its service exits: its launcher (a checkout under `npm start`, or a direct install), on Windows too, or, for a container install, Docker's restart policy when it is `always`, `unless-stopped` or `on-failure`. Elsewhere (`npm run dev`, the service run by hand, a release copy its launcher didn't start from a `releases/` folder, a container with no such policy or out of Docker's reach) Restart is off and says why: "Nothing here would start The Office again: … Restart it where it runs." A scheduled Office restart holds work exactly as a scheduled Office update does, through the same hold: new Starts join the queue with "A restart is scheduled.", each Task waits before its next Agent or Script Stage (a Gate isn't held), and the restart waits for the same busy work; Settings › Updates shows "Restart scheduled" with what it waits for, the status strip shows it, and **Cancel** releases what it held, refused once the restart is under way ("The Office is restarting."). One update or restart is scheduled at a time: scheduling the other is refused with why. Like the update's, the schedule is kept in memory. When nothing is busy, the service exits with code 75: under the launcher it first writes `{ "kind": "restart" }` as the request, and the launcher starts the service again without updating or writing a result; in a container the restart policy is read again first, and when it no longer starts the container again, or Docker is out of reach, the restart stays scheduled, the log says why and the service doesn't exit. A restart reads none of the host's config files again: `office.env` (read by systemd) and a Compose install's `.env` still need the restart on the host.
