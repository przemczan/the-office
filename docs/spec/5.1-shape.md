# 5.1 Shape

Covers: the service and its processes, the ways to reach The Office, the Host and Origin checks, the test instance proxy, Windows and Linux, what The Office is built on, the public address, releases, installs, updates and restarts.

## The service

- One long-running Node service on the workstation hosts the API, the web UI, the agent supervisor and the database connection.
- Agents are child processes (the Claude Code binary, the Codex app-server or the Copilot CLI runtime, one per session), except the OpenAI-compatible API engine's, whose loop runs in the service ([5.4](5.4-the-engine.md)).
- No separate runner, no remote protocol.

## Ways to reach The Office

- The service listens on `localhost` unless the user sets `OFFICE_HOST` to an IP address, for a host that runs The Office away from the workstation.
- The Office is used in three ways:
  - at `localhost`;
  - by IP on the local network over plain HTTP, a trusted network;
  - at its **public address**, behind a reverse proxy the user sets up with HTTPS and a domain.
- Setting up the proxy is the user's job ([docs/running-the-office.md](../running-the-office.md) says how). The Office needs from it:
  - HTTPS to the browser;
  - the original `Host` passed on;
  - `X-Forwarded-Proto: https`;
  - WebSocket upgrades on `/api/events` passed through.
- Every HTTP request to `/api` and every WebSocket needs a signed-in user, `localhost` included, except the sign-in pages and their callbacks ([2.10](2.10-users-and-signing-in.md)).

## Host and Origin checks

- Any page the user opens in a browser can still reach The Office: browsers apply no cross-origin rule to WebSockets, and DNS rebinding points a site's own name at `127.0.0.1` or a local network address.
- So before any sign-in is looked at, the service refuses every HTTP request and WebSocket:
  - whose `Host` is not `localhost`, `127.0.0.1`, the IP address it arrived at (at its port), or the public address's name;
  - or that carries an `Origin` other than one of those addresses' own.
- A request at the public address's name counts as HTTPS only with `X-Forwarded-Proto: https`.

## The test instance proxy

- The service runs a proxy for Hosted test instances ([2.12](2.12-test-instances.md#reaching-a-hosted-instance)), listening on `OFFICE_HOST` at each port it has given out.
- **Ports:** a port from the Proxy ports range is given out when an instance starts and freed when it stops, recorded on the instance's row.
  - A port is never tied to a target.
  - The proxy refuses a request at a port with no Running instance.
- It forwards to the port the instance's run environment published on `127.0.0.1`.
- It asks for the instance's own cookie, never The Office's sign-in ([2.10](2.10-users-and-signing-in.md#signing-in-to-a-test-instance)).
- **Forwarding:** it strips The Office's own sign-in cookie from every request it forwards, and rewrites `Host` and `Origin` to the instance's own address.
- **Upstream cookie names:** it namespaces the app's cookies, prefixing each name in `Set-Cookie` and mapping it back on requests.
  - Browsers don't separate cookies by port, so without it a test instance of The Office would overwrite the real Office's sign-in cookie.
- WebSocket upgrades are forwarded alike.
- The Host and Origin checks above guard The Office's own port; a proxy port is guarded by its instance's cookie, which `SameSite=Strict` keeps from other sites' requests.
- Each forwarded request counts as the instance's activity ([Idle time](2.12-test-instances.md#idle-time)).

## Operating systems

- The workstation runs Windows or Linux, and everything is built and checked on both.
- What differs sits behind one platform layer in the service, and nothing else branches on the operating system:
  - the Office data directory;
  - shells and their rules;
  - finding a command that can't run;
  - ending a process tree;
  - path length limits;
  - where secrets live.

## What The Office is built on

- The lean harness with a stable cached prefix.
- The resume-vs-fresh rule with a standalone brief.
- The flat Stage result envelope.
- Office-owned git with a worktree per Task.
- The environment as data, verified in a fresh worktree.
- Loop limits and budgets.
- Telemetry tagged with prompt features.
- Tool output filtering and the flaky-test re-run.
- The screenshot trust model.
- The layered settings merge.
- No remote runners, leases or runner protocol.

### Windows and Linux

- Windows and Linux are both supported.
- On Windows The Office runs from a checkout; the releases and installs ([5.1.1](5.1.1-releases-and-installs.md)) are for Linux.

### Only The Office's own pages reach the service

- The `Host` and `Origin` checks ([Host and Origin checks](#host-and-origin-checks)) hold for HTTP and WebSocket alike.
- They accept `localhost`, `127.0.0.1` and the IP address a request arrived at, at The Office's port, and the public address.
- A request with no `Origin` (a local tool such as `curl`) passes the `Origin` check.
- It still needs a signed-in device ([2.10](2.10-users-and-signing-in.md)).
- The threat model leaves local processes out ([6](6-permissions-and-safety.md)).

### The public address

- It is given to The Office as `OFFICE_PUBLIC_ADDRESS` in its `.env`, an `https://` origin with no path (`https://office.example.com`).
- An invalid one stops the start with a config problem.
- Unset, The Office has no public address.
- Addresses The Office builds for the public address come from it, never from the request's headers: GitHub's, Google's and the OpenID Connect provider's callbacks, and a passkey's relying party.
