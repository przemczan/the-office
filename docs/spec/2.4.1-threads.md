# 2.4.1 Threads

Covers: the three homes, Threads, a person's Thread on a Task, what each Thread adds, what a Thread reads, what the user has seen, Allow changes, who wrote a message.

## Homes

- **A person's chat**, for people with Chat on.
- **A Task's conversation**: one tab per person, each holding that person's one Thread on the Task; Stage Threads show in the Stage history.
- **An Initiative's conversation**: one tab per person.
  - The tabs of the holders of Shapes Initiatives and of Plans always show; one tab when one person holds both; anyone else's with a Thread on it shows too.
  - Each tab holds that person's Threads on the Initiative, the newest the one written to: the shaping Threads and the planning Threads, opened by Plan the Initiative ([2.1](2.1-work.md)).
  - While a duty is unheld its tab shows the fallback and points to Settings › Duties ([2.2](2.2-people.md#defaults), "Duties").
- The Chat button with no Thread open goes to the holder of Default person to talk to, or to the Caretaker while nobody holds it.

## Threads

- Each Thread is one engine session underneath.
- A fresh Thread starts a new session: the record and the person's memory stay, the context goes.
- Old Threads stay readable and can be continued ([2.5](2.5-context-policy.md) decides resume or brief).
- Only work starts a conversation: an Agent needing the user opens a Decision on the Task; a person outside any Task writes in their own chat.
- There are no idle messages, and no talk between Agents outside a Consultation, a call included.
- Chats only read ([6](6-permissions-and-safety.md#chats-only-read)): changes happen in a Task's Stages; a person's Thread on a Task changes no file either.
- Whoever the user talks to has the same Office tools in every Thread they talk in, records and Proposals among them, which change no file ([6](6-permissions-and-safety.md#a-persons-office-tools)).
- The one exception is a Caretaker Thread with Allow changes on.

## A person's Thread on a Task

- The Task's conversation has a tab for the holder of Plans first, then each person who ran an Agent Stage of the Task in the order they first worked, then each Consultant of a Decision on it, as soon as the Consultation starts.
- Each tab holds that person's one Thread on the Task, written in at any time while the Task hasn't ended, for asking them about anything in it.
- A Done or Dropped Task's tabs are read-only.
- A tab with no Thread yet shows the composer, and the first message opens the Thread: looking at a tab opens nothing.
- The Planner's Thread is the Planning Thread.
  - The Planner there keeps Planning's Brief and tools until the Task starts, Ready included.
  - For a Ready Task its Brief says the Task is Ready and that writing a part takes it back to Planning, so the Planner writes one only when the user asks.
  - A Ready Task's Planning Thread runs only on the user's messages.
  - Once the Task has started, the Planner there has only their [Office tools](6-permissions-and-safety.md#a-persons-office-tools), as in the other people's Threads, instead of Planning's.
- **Its session:** its own, under the Context policy like any chat Thread; its first session's Brief is the record, and a later fresh session's is the Context policy's only ([2.5](2.5-context-policy.md#defaults), "A person's Thread on a Task's Brief").
- **Its tokens** count to the Thread and to the Task, never to a Stage's budget.
  - That holds for the Planner's Thread too, so Planning's tokens count to no Stage.
  - The Usage estimate and the Window caps see them as any session's ([2.1](2.1-work.md)).
- **It changes no code:** it reads the Task's worktree, as it is at the moment, but doesn't edit it or run commands that change it.
  - Changes go through a Stage: Send back at the Gate, or a running Stage's Thread.
- **It holds nothing:** asking doesn't hold or release the Task or its Gate; only Continue, Send back and Drop act at the Gate.
  - An MCP tool at Consult or Ask me still opens an approval Decision in the person's Thread, as on any Task Thread; it holds that call and nothing about the Task.
- **Beside a running Stage:** while the person's Stage runs, the two sessions run side by side, and the tab says so and leads to the Stage history to write into that work.
- **A Consultant's tab** shows their Consultation on the Task above their Thread on the Task: live while it waits on them, then with its note, which is the Consultant's answer in words ([2.4.3](2.4.3-consultations.md)).
  - The composer writes in their Thread, never in the Consultation.
- **Unseen messages:** a tab whose Thread got a message the user hasn't seen shows a count.

## What each Thread adds

- Each kind of Thread loads, from the start, Core, its home's [tool areas](6-permissions-and-safety.md#tool-areas) and its own job tools, which are in Core; and reads what [What a Thread reads](#what-a-thread-reads) says.
- Every other area the person's [Authority](6-permissions-and-safety.md#authority) allows is loaded by area when the Agent needs it ([5.4.1](5.4.1-engine-kinds.md#loading-by-area)).
- The Thread kind grants no authority: what the person may do, and when, is their Authority, the same in every Thread ([6](6-permissions-and-safety.md#a-persons-office-tools)).
- **A chat** loads no area from the start; its job tool asks the user a Decision's form inline (`open_decision`; [2.4.3](2.4.3-consultations.md#calls-from-chats)).
- **A person's Thread on a Task** loads Work from the start, and has no job tool of its own.
  - It reads the Task's worktree and changes no file in it ([A person's Thread on a Task](#a-persons-thread-on-a-task)).
  - It opens no Decision on the Task, since that would hold it.
- **The Planner's Planning Thread** loads Work, and its job tools are the planning tools and `open_decision`, until the Task starts ([2.1.5](2.1.5-planning-and-start.md)).
- **An Initiative's shaping Thread and its planning Thread** load Work and Initiatives, and their job tools are their own Initiative tools and `open_decision` ([2.1.4](2.1.4-initiatives.md)).
- **A Consultation** loads its home's areas from the start: Work on a Task, none in a chat.
  - It has the person's tools but `answer_decision`, and its job tool is `answer_consultation` ([6](6-permissions-and-safety.md#a-consultations-permissions)).
- **An Agent Stage's Thread** loads its Stage's tools, and none of the person's other areas ([2.3.1](2.3.1-stages.md#an-agent-stages-office-tools)).

## What a Thread reads

- A person's chat reads every Project's base branch.
- A Thread on a Task reads its worktree.
- The shaping and planning Threads on an Initiative read, from the first session after Confirm:
  - its Initiative's branch in each Project it spans with a Pipeline there ([2.1](2.1.4-initiatives.md#an-initiatives-pipeline), "An Initiative's Pipeline": one per Project, or None);
  - the base branch of every other Project.
- While shaping there is no branch yet, so those Threads read the base branches ([5.5](5.5-git-and-isolation.md#defaults), "The Initiative's branch").
- A Thread on one of an Initiative's Tasks reads that Task's worktree, which already starts from the Initiative's branch.
- Stage sessions are unaffected.
- Once a branch is deleted, the Thread reads that Project's base branch, and its Brief says so.
- Mentioning the Initiative in another chat doesn't change what that chat reads.
- Every Thread, a Stage's included, also reads the [knowledge base](6-permissions-and-safety.md#the-knowledge-base), read-only.

## What the user has seen in a chat

- The Office keeps, per chat Thread, the last message the user has seen, so it holds across a reload and in another browser.
- A message counts as seen once the Thread shows in the open chat drawer in a browser tab the user can see; an answer landing in a hidden tab waits for them to come back.
- A person has **answered** when a Thread has a message after the last one seen that isn't the user's own, a failed turn's line included, and they aren't answering any more.
- The Chat button and the person picker show it.
- Threads on a Task or an Initiative take no part: their unseen counts stay per page view.

## Allow changes

- It is the Caretaker's chat switch ([2.2](2.2-people.md)).
- Each Caretaker Thread starts read-only, as any chat; a refused edit or changing command tells the Agent to ask the user to Allow changes.
- The user turns the switch on in the Thread and confirms it; no Agent does, since it is [the user's alone](6-permissions-and-safety.md#the-users-alone): a Thread switch with no Office tool, which widens the Caretaker's reach past Office tools.
- While on, the Caretaker can do everything on the workstation except touch secrets ([6](6-permissions-and-safety.md)).
- While on, the chat shows a banner, "Changes allowed in this Thread: the Caretaker can do anything on the workstation except read your secrets", with a Switch off button.
- It is kept per Thread; a new Thread starts with it off.
- Switching it on or off ends the Thread's running session, so the next message starts a fresh one under the new rules ([2.5](2.5-context-policy.md)).
- Switching it off also stops an answer under way, even one whose session is still starting: no turn runs with changes allowed after the switch, and the log says "Changes were switched off, so the answer stopped."
- No Agent switches it off either: only the user does, on the banner ([6 The user's alone](6-permissions-and-safety.md#the-users-alone)).
- Switching it on is refused while the Caretaker is answering, checked as it switches, so no answer starts in between; it stops no answer.
- The switch is logged in the Thread as a line, "Changes allowed" or "Changes switched off".
- The fire alarm still holds every call.

## Who wrote it

- Every message a user writes in a Thread, a barge-in included, is shown and kept with that user's name ([2.10](2.10-users-and-signing-in.md)).
- The answer to a Decision is kept with the user who gave it ("Answered by Ana"), whichever user's Decision it was: any user answers any Decision.
- The session gets each user message with who wrote it, so an Agent knows which user it is talking to.

## Deleting a chat Thread

- Only a Thread in a person's chat can be deleted; a Task's or an Initiative's Threads, the Planning Thread included, belong to their record and stay.
- A Thread is locked, and can't be deleted yet, while it is a Consultation still waiting on the person, or while its call to someone is still out: both ends of a Consultation must stay. The refusal says why.
- The user deletes one Thread or several at once, all or nothing: one locked Thread refuses them all, with the reason.
- A running answer is stopped first ([2.4.5](2.4.5-stopping-and-restarts.md#stop-in-a-persons-thread)), one whose session is still starting too, so nothing it prepared stays.
- What goes: its messages, images, context choices, Sub-agent and Process records, and the engine's session.
- A Decision waiting in it is withdrawn, and its open Proposals are declined, "Declined as its Thread was deleted".
- What stays: the records made in it (Tasks, Ideas, Memory notes, applied Proposals) and its tokens in Stats.
- There is no Undo.
- Every browser drops the Thread from its lists; one with it open shows "This Thread was deleted".
- Only the user deletes ([6 The user's alone](6-permissions-and-safety.md#the-users-alone)).
- Screens: [Shell › A person's chat](screens/shell.md#a-persons-chat), [Thread › Head](screens/thread.md#head).

## Defaults

### Thread titles

- A title comes from the first message and can be renamed.
- A Thread The Office opens, which has no message of the user's first, is titled by The Office and shown with the person, as "Planning · Jan".
