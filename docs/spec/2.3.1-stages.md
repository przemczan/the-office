# 2.3.1 Stages

Covers: Stage kinds, what a Stage declares, how a Stage ends, skipping, the Review & fix Stage, a Stage linked to its Stage template, a Stage's Role or duty, its Project commands, its message, merging the base first, running in the run environment, the Task's branch at a Stage's start.

## Stage kinds

- **Agent Stage**: a Role does work, and may choose its route out ([How an Agent chooses its route](2.3.2-flows.md#how-an-agent-chooses-its-route)).
- **Script Stage**: runs a Project command, named by its key; no model call; the result is recorded.
  - A key the Project lacks, or a command whose line is blank, ends the Stage could-not-run, naming the key; the Stage is never skipped.
  - A test-kind command, under any key, leaves the branch as it was after its run; a build or lint one commits.
  - It never publishes: `publish` is no Project command, and publishing is the Publish Stage's.
- **Gate**: the Task waits for the user, showing the diff, results, Attachments and screenshots ([Gates](2.3.3-gates-and-checks.md#gates)).
  - UI acceptance is a Gate after a Stage that attached screenshots.
- **Publish Stage**: The Office publishes the Task's work by its own git code, with its own credentials out of every Agent's reach, and ends with one of its named results ([Publish](2.3.4-publish.md#publish)).

## What a Stage declares

- Its kind and its name.
- An Agent Stage: a Role or a duty.
- A Script Stage: a command, any key that follows the Project command key rules ([2.1](2.1-work.md)), never `install`, which runs before every Stage on its own, nor `publish`.
- A Publish Stage: its target, by the Project's publishing mode or the Task's branch only ([2.3.4](2.3.4-publish.md#the-proof-of-concept-publish-target)).
- For an Agent Stage, how it narrows its Role card's permission profile, including which of the Project's commands its Agent may run ([6](6-permissions-and-safety.md); [An Agent Stage's Project commands](#an-agent-stages-project-commands)).
- For an Agent Stage, a plain-words brief, filled with the Plan, the Definition of Done and earlier results.
- For an Agent Stage, its budget and its context limits ([2.5](2.5-context-policy.md#a-stages-session-has-a-soft-limit-and-a-hard-limit)).
- For an Agent Stage, its session: fresh by default, or continue the previous Stage's session only when the same person did it.
- For an Agent Stage, whether it merges the base first ([An Agent Stage may merge the base first](#an-agent-stage-may-merge-the-base-first)).
- Its routes out, each with its condition and its limit ([The route forms](2.3.2-flows.md#the-route-forms)).
- The Stage template it is linked to, if any ([A Stage linked to its Stage template](#a-stage-linked-to-its-stage-template)).

## How a Stage ends

- **Done.**
- **Needs a Decision**: one the Agent opened with an Office tool (open a Decision or consult), the only way an Agent asks.
- **Handing over** (an Agent Stage's `handing_over` result): not an end of the Stage but a restart of its run ([A Stage run restarts in a fresh session at its limits](#a-stage-run-restarts-in-a-fresh-session-at-its-limits)).
- **Failed.**
- A Publish Stage ends with one of its results ([Publish's results](2.3.4-publish.md#publishs-results)).
- A Stage the user skips ends Skipped ([Skipping](#skipping)).
- A run a Pause or the usage window held ends held ([A refused turn is no failure](2.3.2-flows.md#a-refused-turn-is-no-failure)).

## Skipping

- Skipping is the user's click: a skipped Stage ends Skipped, running nothing, and the walk follows its routes.
- A Stage the Pipeline runs only in some cases is a route with a condition, not a skip ([Routes](2.3.2-flows.md#which-route-the-walk-follows)).

## Review & fix Stage

- Review & fix is one fresh-session Stage naming Implements.
- Its Agent reviews against the Definition of Done and fixes what it finds.
- It consults (the holder of Asked first when a Stage runs out of tries, then the user) only when it can't fix something itself.

## A Stage linked to its Stage template

- A Stage added from a [Stage template](2.3.5-library.md#stage-templates), or saved as one, stays **linked** to it.
- The link covers the Stage's fields but its name, key, place and routes, which stay the Pipeline's own.
- A linked Stage can still be edited in its Pipeline: it then **differs** from its template in those fields, and the Stage editor says which ("Linked to the template Resolve · Differs in Budget and Brief").
- **Take the template's** sets one field, or all, back to the template's.
- An edit of the template never changes a linked Stage by itself: its Save lists the linked Stages, and the user chooses which get the edit ([Editing a template with linked Stages](2.3.5-library.md#editing-a-template-with-linked-stages)).
- **Unlink** makes the Stage a plain copy, its fields as they are; removing the template unlinks every Stage linked to it.
- Only Pipelines' Stages are linked: a Task's own Stages, edited for it or started, are copies.

## Defaults

### A Stage names a Role or a duty

- An Agent Stage names a Role key or a duty ([2.2](2.2-people.md#defaults), "Duties").
- A Stage naming a duty runs as whoever holds the duty when the Stage starts, and a started Stage keeps its person.
- While the duty is unheld, the Pipelines naming it are flagged, and Start (and Start Ready Tasks, [2.1](2.1-work.md#defaults)) is refused for a Task on one, naming the duty and pointing to Settings › Duties.
- A "continue" Stage whose person differs from the Stage before it runs in a fresh session, and its Stage history says why.

### An Agent Stage's Project commands

- An Agent Stage's permissions may list the keys of the Project's commands its Agent may run, which narrows the Role card's list, never widens it.
- Without the list the Stage keeps every Project command.
- An empty list, a key listed twice, a malformed key, `install` and `publish` are refused.
- The Stage keeps the listed keys the Project has and has set, in the Project's order: a key it lacks or left blank adds nothing.
- Install stays apart: never listed, run by its key under the Run installs Hard switch.
- Under the run permission **the Project's own commands**, the Brief names only the kept commands and the engine allows only their lines.
- Under **anything**, the shell stays free, and the Brief says which of the Project's commands to run and names the others as not for this Stage.
- Under **read-only git**, the words don't change.
- Under every one, run_project_command refuses a key outside the list before anything runs, naming the commands the Stage may run.
- A command line the Agent writes out is judged as any other.
- A list naming a key the Project lacks is refused by the missing-command check when the Pipeline is chosen for a Task or made the Project's default ([A Pipeline needs the commands it runs](2.3.5-library.md#a-pipeline-needs-the-commands-it-runs)).
- Example: the-office's Developer Stages keep `test` (`npm run verify`), not `test-full`.

### An Agent Stage's message names the Stages after it

- The message that tells an Agent what its Stage asks, which a new session gets after the Brief and a continued one alone, has a Later Stages section after the Stage's brief.
- It lists every other Stage the walk can reach from this one by routes, in the Pipeline's order:
  - a Script Stage with the command line it runs;
  - a Publish Stage as The Office publishing the Task's work (or pushing its branch only);
  - an Agent Stage with its Role and its brief;
  - a Gate by name, where the user looks at the work.
- A Stage reached only by routes that carry a condition says when it runs, each condition in plain words.
- A Stage with a route back to this one says when it brings the work back here, its condition in plain words, and at most how many times.
- A Stage reached only through a Publish's Conflict says it runs only after a conflict.
- A Stage from which only End can be reached says no Stage comes after it.
- An Agent Stage with choice rows then has its Routes out section ([How an Agent chooses its route](2.3.2-flows.md#how-an-agent-chooses-its-route)).
- Every run of the Stage gets it, also one a route back, a Gate's feedback or an answered Decision brought back.
- When a later Script Stage runs a Project command, the Agent is told to run only the tests that cover the files it changes while iterating, as a later Stage runs the Project's full command.
- The list is plain facts; what an Agent leaves to the later Stages is in its instructions.

### A Stage run restarts in a fresh session at its limits

- On `handing_over`, Pipelines checks the Budget and reads the Task's record again, and the same Stage run goes on in a fresh session in the same Stage Thread.
- The fresh session's Brief is the Brief plus a section "Handover note from this Stage's earlier session" (Prompt template `pipelines.stage-handover`).
- The Task, the branch and the worktree stay; tokens add up across the sessions of the run.
- No commit is made at a restart: the Stage ends with the one commit The Office makes, as before.

### An Agent Stage may merge the base first

- An Agent Stage's **Merge the base first** setting, off by default, has The Office merge the base into the Task's branch as the Stage starts, before its Agent's turn.
- The Office's own git makes one merge commit, never a rebase, and leaves the files that conflict for the Agent.
- The Brief names the base and each conflicted file (Prompt template `pipelines.resolve-brief`), and the Agent edits files only, never running git ([5.5](5.5-git-and-isolation.md)).
- The Office commits the merge when the Stage ends; a marker left in a file fails the Stage, naming the file.
- A merge with no conflict is committed at once, and the Brief says the base came in cleanly.
- "The base" is the base branch, or for a Task of an Initiative in a Project where it has a Pipeline, the Initiative's branch, then the base branch, brought in in that order ([Publishing into an Initiative's branch](2.3.4-publish.md#publishing-into-an-initiatives-branch)).
- A run the walk brought back after the merge was committed, by a failure route or a Gate's Send back, merges only what the base gained since.
- The built-in Resolve template has it on ([Conflicts in the flow](2.3.4-publish.md#conflicts-in-the-flow)).

### Script Stages in the run environment

- With the Project's Run environment On, a Script Stage's install and command run in the Task's run environment, with only the Project's own variables.
- Off or Not decided yet runs them on the workstation.
- When every run environment Run environments at once allows is in use, the Stage waits.
  - Its rail state, the small pipeline and the Stage history read "Waiting for a run environment", with no live dot, until its command starts.
  - Its time limit counts from then.
- A run environment that can't be made or started fails the Stage with why, and nothing runs on the workstation instead.

### The Task's branch keeps up with the base

- Planning makes the worktree, so a Task can start long after it.
- As the Task's first Stage starts, The Office fetches the base and brings the branch to it: a fast-forward when the branch has nothing of its own, one merge commit otherwise.
- A merge that would conflict leaves the branch as it was, and the Stage's Agent is told.
- An Agent in a Stage can ask for the same at any time with the `update_branch` Office tool.
  - The Office commits the Stage's work so far and merges the base in.
  - A conflict stays in the worktree for the Agent to resolve, editing files only, which The Office commits when the Stage ends.
- Publish's own handling of a base that moved after that stays as in [Merge mode when the base moved](2.3.4-publish.md#merge-mode-when-the-base-moved).
- For a Task of an Initiative in a Project where it has a Pipeline, "the base" here means the Initiative's branch, then the base branch, brought in in that order, at the first Stage, in `update_branch` and in a Stage that merges the base first alike ([Publishing into an Initiative's branch](2.3.4-publish.md#publishing-into-an-initiatives-branch)).

### A branch moved outside The Office

- As a Stage starts, a branch that moved along the base is taken as it is, and the Stage's Agent is told.
  - It moved along the base when the new HEAD descends from where The Office left it and is in the freshly fetched base's history, with nothing uncommitted.
- Any other move stops the Stage before it runs, using no round.
  - A Decision is put to the user directly, not the CTO first: a form of one choice.
  - The options: keep the branch as it is, say they put it back, or drop the Task.
  - Words of their own, the question's comment with no option picked, keep the branch and guide the Stage.
- The check after each Stage stays strict: a Stage that moved the branch itself fails.
