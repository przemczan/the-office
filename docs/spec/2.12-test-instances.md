# 2.12 Test instances

Covers: Test target, its kinds (Hosted, Build to install, Install on a device, Deployed elsewhere), commands before the entry point, what The Office sets, a target's memory, tool settings, entry points only, writing test targets by Proposal, Set up test targets, Test instance, its branch, linking to an Initiative, its states, its log and when it stops, Hosted in the run environment, reaching a Hosted instance, Build to install files and their QR link, safety, Test instances at once, Idle time, Proxy ports, Build time, Kept Build to install files.

## Test target

- A **Test target** is a named entry in a Project's settings: what the user can launch on a branch to try the work.
- It has:
  - a key, by the same rules as a Project command's key ([2.1.1](2.1.1-projects.md#project-commands)), fixed once added;
  - a name, at most 60 characters;
  - a kind ([Kinds](#kinds));
  - the settings of that kind.
- It is stored in the database only, as a Project setting, never in a repository.
- Each value records who set it last: the user, or a Proposal, naming the Agent who drafted it.
- It is edited in the Project page's Test targets section ([project-page.md](screens/project-page.md#test-targets)), or by a Proposal ([Writing test targets](#writing-test-targets)).
- Agents read a Project's test targets in its record (`list_projects`), with the target's Secret variables by name and whether a value is set, never their values.

## Kinds

- **Hosted** (built now): an app that runs and is opened in a browser. Its settings:
  - the start entry point;
  - the port the app listens on inside its container;
  - the target's own variables, plain and secret;
  - optional: the commands before the entry point ([Commands before the entry point](#commands-before-the-entry-point)), the port variable ([What The Office sets](#what-the-office-sets)) and its own Memory per service ([A target's memory](#a-targets-memory)).
- **Build to install** (built now): an app that is built into files the user installs, such as an Android APK. Its settings:
  - the build entry point;
  - output file patterns, relative to the repository's root, such as `composeApp/build/outputs/apk/debug/*.apk`;
  - the target's own variables, plain and secret;
  - optional: the commands before the entry point and its own Memory per service.
- **Install on a device** (outlined only): a build on a Task's branch that The Office would install on a device connected to that Task ([2.13](2.13-connected-devices.md)). It would take the build entry point, the output file patterns and which of the Task's Connected devices; nothing is built for it yet.
- **Deployed elsewhere** (outlined only): an app The Office would deploy to a host the user names. It would take the deploy entry point, the host and the address to open; nothing is built for it yet.
- A target of an outlined kind is refused when written, naming the kind as not built yet.
- A target's own Secret variables follow the Project's Secret variables' rules: one line of at least 6 characters, never sent back, shown as `[secret NAME]` ([5.5](5.5-git-and-isolation.md#secret-variables)).

## Commands before the entry point

- A Hosted or Build to install target may list, in order, some of the Project's own commands by their keys ([2.1.1](2.1.1-projects.md#project-commands)), such as `install` then `build`; none by default.
- `install` runs the Project's install command, offered when it has one: the image's install runs in its own folder, so the instance's checkout starts with nothing installed.
- Saving a target that names a key the Project doesn't have is refused, naming it.
- At each launch The Office runs them one after another in the instance's checkout, before the entry point:
  - in the definition's service of the instance's run environment, or on the workstation for a Build to install with Run environment Off, as checks run there;
  - with the target's own variables and what The Office sets ([What The Office sets](#what-the-office-sets)), never the Project's variables;
  - their output going to the instance's log, masked, each named there first;
  - with a `.devcontainer/` service entry point, that service starts only once they have run; they can't run before an entry point that is the definition's own service, so such a launch fails, naming it.
- The first that doesn't end with 0 ends the launch Failed, and the entry point never runs: "The Project's command <name> ended with exit code N."
- A Hosted instance's command gets 60 minutes; past them the launch fails: "The Project's command <name> took too long."
- A Build to install's commands share the build's 60 minutes with its entry point ([Build time](#build-time)).
- A listed key the Project no longer has fails the launch, naming it: "The Project's command <key> that runs before the entry point is gone; …".

## What The Office sets

- In every test instance, in the commands before the entry point and the entry point alike:
  - `OFFICE_TEST_INSTANCE=true` ([Safety](#safety));
  - for a Hosted instance, its **port variable** set to the target's port, in the app's service.
- The port variable is `PORT` unless the target names another ([Defaults](#port-variable)).
- It must be a valid variable name, not `OFFICE_TEST_INSTANCE` and not one of the target's own variables; a target breaking that is refused when written, naming it.

## A target's memory

- A Hosted or Build to install target may set its own **Memory per service**, 512 MB to 64 GB in steps of 0.5 GB, as the Office-wide setting takes.
- Left empty, the Office-wide value applies (Settings › Office limits › Run environments, [5.5](5.5-git-and-isolation.md#the-other-limits-of-run-environments)).
- Set, it applies to every service of that instance's run environment alone ([5.5](5.5-git-and-isolation.md#the-other-limits-of-run-environments)); a Build to install on the workstation ignores it.

## Tool settings

- A target has no field of its own for a tool's settings: they go in its plain variables and in the entry point's arguments.
- A Gradle build that runs out of memory takes `-Dorg.gradle.jvmargs=-Xmx2g` in the Gradle task's arguments, which outranks the repository's `gradle.properties`, or more Memory per service ([A target's memory](#a-targets-memory)).

## Entry points only

- A target names one of the Project's own entry points, never a command line:
  - a file in the repository, such as `./gradlew` or `./scripts/start-test.sh`, run with the arguments the target gives;
  - a script named in the package manifest (`package.json`'s `scripts`);
  - a Gradle task, run through the repository's Gradle wrapper;
  - a service of the repository's `.devcontainer/` (Hosted only).
- Inline shell is never allowed: no pipes, `;`, `&&`, redirections or substitutions, and no program outside the repository.
- The rule is checked when a target is written, on the page or by a Proposal, against the base branch's tree.
- It is checked again at each launch, against the tree of the branch being launched; a launch whose entry point is missing there fails at once, naming it.

## Writing test targets

- Agents write test targets only through the Office tool `propose_test_targets`, a Proposal of kind `test-targets`, made as Devops' Proposal of Project commands is ([2.3.5](2.3.5-library.md#project-commands-by-proposal-and-by-hand)).
- It may add targets, change a target's values (by key) and remove targets by key.
- It keeps each value as it was and as proposed.
- The user applies it, all or nothing, from its card; nothing changes until then.
- It is refused once any value it changes has changed since it was drafted, naming each.
- It is checked by the same rules as the Project page, the entry-points-only rule among them.
- **A value the user set is never overwritten silently:**
  - a Proposal changes a value the user set only when the Agent names that value on purpose;
  - its card flags each such value "You set this", beside what it was and what it becomes.
- A Proposal carries a Secret variable by name alone; the user types its value on the Project page after applying it, and the target says which values are missing until then.

## Set up test targets

- **Set up test targets**, in the Project page's Test targets section, adds a Task in the Project on the built-in Pipeline "Set up test targets" ([2.3.5](2.3.5-library.md#built-ins)), Ready for the user's Start.
- Its one Agent Stage names Onboards and repairs Projects (Devops by default); it has no Publish.
- Its Agent reads the repository, changes no file, and ends with a `propose_test_targets` Proposal.
- The Task is Done once the Agent has proposed; applying the Proposal is the user's, on its card.
- A Project has at most one open "Set up test targets" Task; while one is open, the button is replaced by a link to it.

## Test instance

- A **Test instance** is one launch of one test target, on one branch, in one Project.
- It is launched from either page:
  - the Initiative's page ([initiative-page.md](screens/initiative-page.md#test-instances)), on its branch in a Project where the Initiative has one ([5.5](5.5-git-and-isolation.md#the-initiatives-branch));
  - the Project page's Test instances card ([project-page.md](screens/project-page.md#test-instances)), on any branch of the repository or its remote, with no Initiative.
- A launch on a branch neither the repository nor its remote has fails: "The branch X isn't in <Project> or on its remote."
- It runs the branch's tip, fetched first.
- It runs on its own detached checkout of that commit, `<office-data>/test-instances/<id>/` ([5.5](5.5-git-and-isolation.md#a-test-instances-checkout)).
- Every instance records its branch; an old row with none reads as its Initiative's branch.
- Its row records the target, its branch, the Project, the Initiative when linked, the commit, who launched it, its state, its times and, for a Hosted instance, the port it was given.

## Linking to an Initiative

- An instance launched on a branch that is an active Initiative's branch in that Project is **linked** to the Initiative, whichever page launched it.
- A linked instance also shows on the Initiative's page, and the Project page shows it "in <Initiative>", linking to it.
- An instance on any other branch is **unlinked**.

## Test instance states

- **Hosted:** **Building** → **Running** → **Stopped**, or **Failed** from Building or Running.
- **Build to install:** **Building** → **Built**, or **Failed**.
- **Built** means its files are ready to download; it holds nothing running.
- **Failed** says why: the entry point missing, the branch's `.devcontainer/` invalid (with its problems), a command before the entry point ending with an error, missing or taking too long, the build or start ending with an error, the app not answering on its port, The Office restarting while it was Building.
- Becoming Running, Built or Failed raises an Outcome Notification, but none for a build failed by the user's Stop or its Initiative ending ([2.7](2.7-notifications.md#test-instance-outcomes)).

## Log

- Each instance has one log: the checkout, then the output of the commands before the entry point, then the entry point's, then how it ended.
- It is masked as Stage runs are: a Secret variable's value shows as `[secret NAME]` ([5.5](5.5-git-and-isolation.md#secret-variables)).
- It streams while the instance is Building or Running, and is kept with the instance.

## When an instance stops

- A Hosted instance stops:
  - when the user presses Stop;
  - after the Idle time with no activity ([Defaults](#idle-time));
  - when its Initiative is Done or Dropped, if it is linked to one;
  - in the sweep when The Office starts, which stops every instance left Building or Running.
- An unlinked Hosted instance stops only on Stop, after the Idle time and in the sweep.
- A Build to install instance that is Building stops on the user's Stop (Failed, "Stopped by you"), when its linked Initiative is Done or Dropped, and in the sweep.
- A Running instance doesn't hold back an Office update or restart: the update stops it ([5.1.2](5.1.2-updates-and-restarts.md#updating-the-office)).
- Stopping removes its containers, its volumes and its checkout, frees its port and ends its cookie; its log stays.

## Hosted runs in the run environment

- A Hosted target needs the Project's Run environment On; otherwise its launch is refused, saying so.
- It needs a valid `.devcontainer/` on the branch being launched too; that is read from the instance's checkout, so an invalid one fails the instance, listing its problems.
- Each instance is its own compose project with its own volumes, removed when it stops, and publishes only the target's port, on `127.0.0.1` ([5.5](5.5-git-and-isolation.md#a-test-instances-checkout)); the proxy forwards to it ([Reaching a Hosted instance](#reaching-a-hosted-instance)).
- **Rule:** the Test instances module uses Run environments only through that module's public interface; what it needs is added to that interface, and it never reaches into compose files, project names or containers itself ([5.3](5.3-modules.md#test-instances-uses-run-environments-through-their-public-interface)).

## Reaching a Hosted instance

- Each Running instance gets its own port on the workstation, served by a proxy The Office owns, listening on `OFFICE_HOST` ([5.1](5.1-shape.md#the-test-instance-proxy)).
- The user opens it with **Open** on the Initiative's page or the Project page, which signs the browser in to that instance alone ([2.10](2.10-users-and-signing-in.md#signing-in-to-a-test-instance)).
- It is reached from the workstation and the local network only: `localhost:<port>`, or `<LAN IP>:<port>` when `OFFICE_HOST` is on the network.
- **Why not a path under The Office's own address:** the test app's JavaScript would run on The Office's origin, with the user's sign-in cookie in reach, and most apps assume they are served at `/`.
- **Why not the container's port directly:** nothing would sit behind sign-in, and browsers don't separate cookies by port, so the app's cookies and The Office's would mix.
- **Outlined, not built:** reaching an instance at a public address, through a wildcard domain (`*.test.example.com`) the user's reverse proxy forwards to the proxy.

## Build to install

- It builds in the Project's run environment when Run environment is On, otherwise on the workstation, the way checks run ([2.3.1](2.3.1-stages.md#script-stages-in-the-run-environment)).
- Besides its checkout, a build in the run environment gets one named Docker volume per Project for the build tool's caches and `~/.android`, never a host folder ([5.5](5.5-git-and-isolation.md#the-build-cache-volume)).
  - So builds stay fast, and the Android debug signing key stays the same, so a newer APK installs over an older one.
- On the workstation (Run environment Off) the entry point runs in the Bash Agents use, as `./<file> args`, `npm run <script> -- args` in the manifest's folder, or `./gradlew <task> args`.
- A `.devcontainer/` service entry point builds nothing, in the run environment or on the workstation, and fails the instance.
- It sees only the target's own variables, never the Project's; its secrets are masked in the log ([5.5](5.5-git-and-isolation.md#secret-variables)).
- It needs no Run environment On and no Proxy port, and counts toward [Test instances at once](#test-instances-at-once) from the moment it is Building.
- It ends the instance Failed, saying why:
  - "The build ended with exit code N." for a non-zero exit;
  - "The build ran out of its 60 minutes." ([Build time](#build-time));
  - "No file matched <patterns>.";
  - "<match> resolves outside the checkout, so no file was kept." (nothing is copied);
  - "Stopped by you." when the user presses Stop while it is Building.
- Once it ends with exit 0 and at least one output pattern matched, the files matching the output patterns are copied to `<office-data>/test-builds/<id>/` under their base names (a repeated name becomes `<stem>-2<ext>`, `-3`, ...), and the instance is Built.
- A match that resolves outside the checkout (a link, a `..`) is refused, naming it; no match at all fails the instance, naming the patterns.
- The files are downloaded from the Initiative's page or the Project page behind sign-in, as attachments (`.apk` as `application/vnd.android.package-archive`); a name not in the instance's list is refused as not found.
- **The QR code** beside each file holds a link for a phone, which isn't signed in:
  - it works for that one file only;
  - it expires after 1 hour;
  - it is served under `/api/sign-in/test-builds/`, so the rule that only `/api/sign-in/**` is open without sign-in holds ([2.10](2.10-users-and-signing-in.md#what-every-request-needs));
  - it is signed with an HMAC-SHA256 of the instance, the file name and the expiry, under a random key kept in `<office-data>/test-builds/.link-key`, readable by its owner only, and checked in constant time; any other link is answered as not found;
  - it uses the address the page was opened at; at `localhost` the page says to open The Office by its LAN address instead, since a phone can't reach `localhost`.

## Safety

- A test instance runs code an Agent wrote, so it is kept from everything real: its own data, only its target's own variables, nothing mounted from the host but its checkout, and `OFFICE_TEST_INSTANCE=true` refusing push, pull request, merge and an engine's start in a test instance of The Office ([6](6-permissions-and-safety.md#test-instances)).

## Defaults

### Port variable

- The variable a Hosted target's port is set in when the target names none: `PORT` ([What The Office sets](#what-the-office-sets)).

### Test instances at once

- How many test instances may be Building or Running together across The Office: 2 by default, 1 to 6.
- Set in Settings › Office limits' Test instances card ([settings.md](screens/settings.md#office-limits)).
- Building counts; Built, Stopped and Failed don't.
- A launch over it is refused, naming the instances that are Building or Running, a linked one "<target> in <Initiative>" and an unlinked one "<target> on <branch>": "2 test instances are building or running: Web in Checkout redesign, Web on fix-login, …. Stop one to launch another."
- It is counted apart from Run environments at once: a Hosted instance takes no run environment slot, and a Task's checks take no test instance slot.

### Idle time

- How long a Running Hosted instance may go with no activity before it stops: 30 minutes by default, 5 to 240.
- Set in the same card.
- Each request the proxy forwards counts as activity.

### Proxy ports

- The ports the proxy gives out, one per Hosted instance, the lowest free one at its launch, held while it is Building or Running: 4400 to 4419 by default, set in the same card as a first port and a last.
- Each is a whole number from 1024 to 65535, the last not below the first, at most 100 ports, and never The Office's own port; the service refuses any other, naming the field.
- A launch when every port is taken is refused, saying so.

### Build time

- How long a Build to install build may run, its commands before the entry point included: 60 minutes, not set anywhere.
- A build that runs past it is stopped and the instance Failed: "The build ran out of its 60 minutes."

### Kept Build to install files

- A linked build keeps the Initiative's rules:
  - the newest 3 builds per target per Initiative are kept; an older one's files are removed as a newer one is Built;
  - all of an Initiative's builds are removed 7 days after it is Done or Dropped.
- An unlinked build keeps the newest 3 per target per branch, an older one's files removed as a newer one is Built.
- The daily run also removes an unlinked build's files 7 days after it was Built, its log saying "The files were removed: they were Built 7 days ago."
- A build's row and log stay after its files are removed, saying they were.

### Implementation notes

- Storage:
  - `test_targets`, owned by Projects: `project_id`, `key`, `name`, `kind`, `settings` (jsonb) and who set each value;
  - `test_instances`, owned by Test instances, with its branch (the Initiative optional, so an instance on a branch with no Initiative has none), the port it was given and, for a Build to install instance, the files it kept;
  - the three limits above, as Office settings.
- Module: `apps/service/src/modules/test-instances/` ([5.3](5.3-modules.md#the-modules)).
- The Proposal kind `test-targets`; the tool's name constant sits beside `PROPOSE_PROJECT_COMMANDS_TOOL`.
- HTTP routes:
  - `GET` and `PUT /projects/:id/test-targets`;
  - `POST /projects/:id/test-targets/set-up`;
  - `GET` and `POST /initiatives/:id/test-instances`;
  - `GET /projects/:id/test-instances`, the Project's targets, its branches with instances and each branch's last commit known here, and the linked Initiatives' names;
  - `POST /projects/:id/test-instances`, `{branch, targetKey}`;
  - `POST /test-instances/:id/stop`;
  - `GET /test-instances/:id/log`;
  - `POST /test-instances/:id/open`;
  - `GET /test-instances/:id/files/:name`, signed in;
  - `POST /test-instances/:id/files/:name/link`, answering `{kind: "link", url, expiresAt}`, or `{kind: "needs-lan-address"}` when the page was opened at `localhost`;
  - `GET /sign-in/test-builds/:token`, open without sign-in, the QR link's route;
  - `GET` and `PUT /settings/test-instances`.
- Web event: `test-instance.changed`, carrying the Project and, when linked, the Initiative.
