# 2.9 Sub-agents and processes

The UI spec is [docs/design/sub-agents-and-processes.html](../design/sub-agents-and-processes.html).

While a session works, its Agent may start **Sub-agents** (an agent that does part of the work in its own context and reports back) and **Processes** (a command run in the background, such as a dev server or a long test run). Above the message input, a Thread says how many are running; a press opens a live, read-only view of each: a Sub-agent's messages and tool calls, a Process's command and its output as it streams. Ended ones stay viewable for the rest of the session.

**Names** (in the [glossary](../../GLOSSARY.md)): **Sub-agent** and **Process**. A Process is not a Pipeline. In code, a Process is never a variable named `process`, which is Node's global: `startedProcess`, `processes`, `ProcessState` and the like.

## The model

A session's Sub-agents and Processes are kept by **Conversations**, beside its Thread. The Engine reports them as session events and keeps nothing; Pipelines reads nothing of them, as a Stage's session is a Stage Thread, which Conversations owns. Conversations is where a session's events are logged (`ThreadRunner`, `StageThreads`), where the Project's mask is applied before anything is stored or sent (`sessionLogLines`), and where a Thread's web events come from (`ThreadWebEvents`), so it owns them for the same reasons it owns a Thread's messages (spec [5.3](5.3-modules.md): Engine talks to no module).

**Both kinds are known by the same id**, `callId`: the id of the tool call that started them, the one id every engine has, a foreground Sub-agent included. Each also keeps the engine's own task id, `engineTaskId`, when the engine has one (Claude Code's `task_id`, the API engine's `b` and 8 hex digits, which TaskStop names).

**A Sub-agent** holds:

- its `callId`, which its messages name as `withinToolCall`, and its `engineTaskId` when there is one;
- who started it: the Agent, or another Sub-agent (by its id);
- its description (the call's `description`), its kind (`subagent_type`, such as "general-purpose" or "Explore"), and its prompt, the brief it was given;
- whether it runs in the background;
- its state and why it ended (below), and when it started and ended;
- its messages and tool calls, in order, as a Thread logs its Agent's (text, a tool call's summary, a refusal), each with a sequence number, through the Project's mask;
- what it reported back (the starting call's result) and its counts when the engine gives them (tool calls, tokens).

**A Process** holds:

- its `callId` (the `Bash` or `PowerShell` call that started it) and its `engineTaskId` (`b1f9c2e07`);
- who started it: the Agent or a Sub-agent;
- its command line, whole, and its description;
- its state, its exit code when the engine gives one (the API engine does; Claude Code's end notice has none), why it ended, and when it started and ended;
- its output, in chunks with sequence numbers, through the Project's mask.

**Masking.** Everything kept of either kind goes through the Project's mask before it is stored or sent, not only the output and the messages: a description, a prompt, a command line (`curl -H "Authorization: Bearer …"`), what a Sub-agent reported back and why one failed. **Whole lines:** the mask matches within a text, so a secret split across two output chunks would get past it. Conversations masks a Process's output by complete lines only: it holds back an unfinished last line until its newline comes, the Process ends, or about a second passes, and masks it then. A Sub-agent's messages are whole when they arrive, and are masked as a Thread's are.

**States:**

| State | When |
| --- | --- |
| Running | From its start until it ends. |
| Finished | A Sub-agent that reported back; a Process that exited with 0. |
| Failed | A Sub-agent whose call failed; a Process that exited with anything but 0, or couldn't start. |
| Stopped | Ended before it finished: by the Agent (TaskStop), by an interrupt or by the session's end; or no longer seen after The Office restarted. Its ending says which. |

The Agent stopping its own dev server is ordinary work, so it is Stopped, not Failed.

What ends what:

- **An interrupt** stops what the engine stops with the turn. On Claude Code a foreground Sub-agent stops with it and background work runs on. On the API engine `interrupt` ends every Process (`endAll`). The view shows what happened on each.
- **TaskStop** makes it Stopped, "by the Agent".
- **The session's end** stops whatever still runs ("ended with the session"): the engine ends its background work with the session, on both engines. A Thread's session ends after ten idle minutes (`IDLE_MS` in `thread-runner.ts`), and a Stage's session with its run. The idle end waits for background Sub-agents: while any runs, ten idle minutes don't end the session, and the ten minutes start again once the last one ends. It doesn't wait for Processes, so a dev server the Agent left running stops with it. A turn the engine starts by itself, such as on a Sub-agent's report, holds the idle end as a turn the user's message starts does.
- **The Office's restart:** after it, no session is there to report on them, and a background command may still be running on the machine, so nothing claims it stopped. At startup Conversations puts every Process and Sub-agent still Running in the Stopped state with the ending "Ended when The Office restarted", as it recovers interrupted answers. A planning Thread whose background Sub-agents were Stopped this way has its planner woken again, told to run again the ones they still need ([2.4](2.4-conversations.md), "After a restart").

**Background Sub-agents are busy work:** a scheduled Office update ([5.1](5.1-shape.md), "Updating The Office") waits while a Thread of any kind has a background Sub-agent running, since the update's restart would stop it, though the Agent's turn has ended. Settings › Updates lists one item per session while any runs, by its Thread, such as "Ada's Sub-agents in an Initiative's Thread, "Planning the Initiative"". It goes once the last one ends, or with the session. A foreground Sub-agent runs within its Agent's turn, which already counts; a background Process doesn't count, as a dev server may never end.

**In a Stage:** a Stage's result is the end of its Agent's turn ([2.3](2.3-pipelines.md)), so nothing the Agent needs may outlive the turn.

- **Sub-agents run in the foreground**, whatever the call asks. The Office rules hook allows every Sub-agent call of a Stage session with its input set to `run_in_background: false`, each other field as the Agent gave it (`SessionOptions.subAgentsInForeground`, [5.4](5.4-the-engine.md)), so the turn holds until each answers. The engine's stream still shows the call as the model wrote it; the adapters report it, and its Sub-agent, as the foreground one that ran. Chats and every other Thread keep background Sub-agents.
- **Background commands stay allowed**: a Stage may serve the app for its screenshots, and its checks already run through `run_project_command`, which waits for their end. The Stage instructions say the Stage ends with the turn, that the Agent waits within it for any output it needs, never ending the turn to wait, and stops the commands it no longer needs; whatever still runs stops with the session.

**How long they are kept: for the rest of the session.** They belong to the Thread's session (`ThreadSession`, the engine session id). So they are kept:

- across turns, and across the session's end and resume after ten idle minutes, since a resume continues the same session;
- across The Office's restart: they are stored in the database, not in memory;
- until the Thread's session is replaced by a fresh one (the Context policy's fresh or hand off, spec [2.5](2.5-context-policy.md)), when the old session's are removed with it;
- for a Stage, with its run: a Stage Thread has one session and never gets another, so a run's Sub-agents and Processes stay readable in its Stage history, as its Thread does.

**Caps on what is kept:**

- a Process keeps the **last 256 KB** of its output, counted after masking; what came before is dropped, and its size is counted ("1.9 MB of earlier output isn't kept");
- a Sub-agent keeps its **last 1,000** messages and tool calls, the earlier ones counted the same way;
- a session keeps its **latest 100** Sub-agents and Processes that ended; Running ones are always kept.

Output is batched in one place only, the engine adapter: each read of the output file, every half second, is one `process-output` event, which Conversations stores and sends as it comes. A chatty command so gives two events a second at most.

## Session events

On the `SessionEvent` port (`engine/ports/session-events.ts`), the same on every adapter:

| Event | Fields |
| --- | --- |
| `sub-agent-started` | `callId`, `engineTaskId` (or undefined), `withinToolCall` (the Sub-agent that started it, or undefined for the Agent), `description`, `agentKind` (or undefined), `prompt`, `background` |
| `sub-agent-changed` | `callId`, what the engine added since the start: `engineTaskId`, `background` |
| `sub-agent-progress` | `callId`, `totalTokens`: its context size so far, from Claude Code's `task_progress` (`usage.total_tokens`); Conversations folds it into the Sub-agent's `totalTokens` as a revision |
| `sub-agent-ended` | `callId`, `ending`, `reportedBack` (what it reported back, or undefined), `toolCallCount` and `totalTokens` (or undefined) |
| `process-started` | `callId`, `engineTaskId`, `withinToolCall`, `commandLine`, `description` |
| `process-output` | `callId`, `text` (what the adapter read since its last read, in order) |
| `process-ended` | `callId`, `ending`, `exitCode` (or undefined) |

and `withinToolCall` on `tool-result`, so a Sub-agent's tool results are told from the Agent's. `sub-agent-changed` is there because a Sub-agent starts with its call, before the engine says more about it (below). An `ending` is `{ state: "finished" }`, `{ state: "failed", reason }` or `{ state: "stopped", by: "agent" | "interrupt" | "session-end" }`. "Ended when The Office restarted" is Conversations' own ending, as no engine sees it. These events may come between turns, while the session waits for a message: whoever reads a session's events keeps reading while it lives.

- **Claude Code** (the Agent SDK adapter and the `-p` fallback, which share `sessionEvents` in `adapters/claude-code/sdk-events.ts` and `BackgroundTasks` in `adapters/claude-code/background-tasks.ts`): a Sub-agent **starts with its `Task` (or `Agent`) tool call**, which reaches the session for sure on both adapters, foreground or background; its input gives the description, kind, prompt and `run_in_background`. Its messages are the assistant messages whose `parent_tool_use_id` is that call's id. The engine's `system` task messages only add to it: `task_started` with `task_type` `local_agent`, matched by `tool_use_id`, gives `sub-agent-changed` with its `engineTaskId` (and `is_backgrounded`). A Process starts with `task_started` with `task_type` `local_bash`, its command line taken from the `Bash` call kept by `tool_use_id`; `ambient` tasks are left out. `task_notification` gives the end (`completed` finished, `failed` failed, `stopped` stopped, by the Agent after a TaskStop call or by the interrupt that came before it; `reason: "worker_restart"`, the engine's own restart orphaning the task, is stopped with the session); a foreground Sub-agent's end is also its call's result, whichever comes first. What a Sub-agent reported back is its call's result for a foreground one, and the notification's `summary` for a background one, whose call's result is only the `async_launched` placeholder; the counts are the call result's (`AgentOutput`) or the notification's `usage`. The notification carries no exit code, so a Process's `exitCode` is undefined on Claude Code unless the `summary` names one; the view then says "Failed" without one. A task that leaves `background_tasks_changed` with no end is ended Stopped. A Process's output is read from the output file its `Bash` result names, every half second from the offset already read, and once more at its end; each read is one `process-output` event, the only batching there is. This mapping follows the pinned SDK's types; the engine check's `engine.background-tasks` and `fallback.background-tasks` scenarios test it on the live engine ([docs/engine-check.md](../engine-check.md)).
- **The API engine** (`adapters/openai-compatible-api/background-commands.ts`): `BackgroundCommands` runs a `Bash` or `PowerShell` call with `run_in_background`, gives it an id like the SDK's (`b` and 8 hex digits), and writes its output and errors to `<id>.output` in the session's folder (`<temp>/office-sessions/<session id>/`). It reports each start (the call's id and its own id), reads that file the same way, and reports the end: exit 0 finished, any other exit failed, `stop` stopped by the Agent, `endAll` on interrupt stopped by the interrupt, `close` stopped by the session's end. A command that ends by itself also leaves Claude Code's `<task-notification>` for the model, with its exit code. The loop has no `Task` tool, so this engine has no Sub-agents, and its line counts Processes only.
- **The Codex engine** reports neither.
- **The scripted engine** replays them as recorded (`ScriptStep` `{ step: "event" }`, checked by the zod `sessionEvent` union in `session-script.ts`), with a step that waits for the test (`{ step: "wait", mark: "…" }`, released by `ScriptedSession.reach(mark)`), so a Process can stay running between turns. The agent engine contract has a scenario with a background command that outputs, is read, and ends, run on every adapter (the Claude Code ones live-gated).

## Live streaming to the web

The pattern is the Conversations web events' (`ThreadWebEvents`, through the platform's `WebEventForwarding` and `EventStream`): each event names the Thread and its home. Unlike a Thread's other events, which are signals to refetch, these carry what changed, as `thread.tokens-counted` carries its tokens, since output is too frequent to refetch.

**Reads** (Conversations' controller):

- `GET /api/threads/:threadId/sub-agents-and-processes`: the Thread's current session's Sub-agents and Processes, each with its `callId`, `engineTaskId`, kind, who started it, description or command line, state, ending, times, and the sequence of its last message or output chunk; no messages and no output.
- `GET /api/threads/:threadId/sub-agents/:callId/messages?after=<sequence>`: its messages and tool calls after that sequence (all of them, as kept, without it).
- `GET /api/threads/:threadId/processes/:callId/output?after=<sequence>`: its output after that sequence, with how much earlier output wasn't kept.

**Web events:**

| Web event | Carries | Sent to |
| --- | --- | --- |
| `thread.sub-agent-started`, `thread.sub-agent-changed`, `thread.sub-agent-ended` | `threadId`, `home`, `item`: the whole Sub-agent as the list reads it | every page subscribed to the type |
| `thread.process-started`, `thread.process-ended` | `threadId`, `home`, `item`: the whole Process as the list reads it | the same |
| `thread.sub-agent-messages` | `threadId`, `home`, `callId`, its new messages and tool calls, each with its sequence | only pages subscribed to that type **for that Thread** |
| `thread.process-output` | `threadId`, `home`, `callId`, `chunk`: one chunk of new output with its `sequence` (masked, whole lines) | the same |

**Output reaches only the Thread it belongs to.** A subscription is an event type with an optional `threadId` (`platform/websocket/event-stream.ts`, the contracts' `clientMessageSchema`, the web's `apps/web/src/api/event-stream.ts`). `thread.sub-agent-messages` and `thread.process-output` are sent only to subscriptions scoped to their `threadId`; a subscription without a scope gets the other types. A page subscribes to the two, scoped to its Thread, while the view is open, and unsubscribes as it closes.

**The list needs no catch-up of its own.** Each start, change and end event carries the whole item, and the page puts it in its list by `callId` (the contracts' `withSubAgentOrProcess`). A state only moves forward: once ended, an item never goes back to Running, and an older copy never replaces a newer one: each item counts its changes (`revision`), and the higher wins. So these events apply safely in any order, before, during or after the list's read.

**A page that opens late catches up a Sub-agent's messages and a Process's output without missing or doubling anything:**

1. It subscribes first, scoped to the Thread, and holds the events that arrive.
2. It reads the open item's messages or output, which answer up to a sequence.
3. It applies what it holds, and then each live event, only after that sequence; an event at or before it is already in the read and is dropped.
4. An event whose sequence skips ahead (a missed one), or the WebSocket reconnecting, reads again from the last sequence it has (`?after=`).

## Read-only

The view has no stop controls: no Stop on a Process, no Stop on a Sub-agent, no Stop all. Only the Agent stops them (TaskStop), or the session's end does. The window says so in its bar ("Only the Agent can stop them").

## The UI

- **The line**, above the message input of a Thread, wherever a Thread has one: in the chat drawer, on a Task page's conversation and in a Stage run's Thread tab in the Stage history; where a Thread takes no message, above the line saying why. It shows only once the session has had a Sub-agent or a Process. While any runs: a live dot and "2 sub-agents, 1 process running", singular "1 sub-agent running", a kind with none left out, then "· 3 ended" when some ended, with "1 failed" in red. Once none runs: "3 sub-agents, 1 process ended", no dot. The whole line is one button. It shares its row with the context reading ([2.5](2.5-context-policy.md)), which keeps the row's right end at its own width, so neither moves the other.
- **The view** is a list and details. In the chat drawer and on the Task page it opens in a large window, "Sub-agents and processes", which keeps one height; in the Stage history, which is already a window, it is the run's third tab, beside Summary and Thread. The list has Running on top, then Ended, the one that ended last first, each in a line or two: a mark for its kind, the description or command, its state and how long it ran, and for a Sub-agent its context size beside the time ("3m 12s · 45k context"), updated while it runs as the engine reports progress and kept from its end; with no figure from the engine nothing shows, never a 0. Picked, a Sub-agent shows its prompt's first lines with "Read it in full", then its messages and tool calls in Rows with the Details switch on its row, as a Thread has them; a Process shows its command whole, then its output in monospace, following the end while it runs until the user scrolls up, with Jump to the end. On a narrow page the list and the details stack, with a "‹ All" row back to the list.
