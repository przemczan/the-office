# 2.9 Sub-agents and processes

From the Initiative "Sub agents and processes view" and its design Task (2026-11-10); the model and the streaming were reviewed with the CTO, whose changes are folded in (one id for both kinds, a Sub-agent started by its call, masking whole lines, one batching, output scoped to its Thread, list events in any order, the restart's ending). Proposed: it becomes the spec once the user accepts the design at its Gate. The UI sketch is [docs/design/sub-agents-and-processes.html](../design/sub-agents-and-processes.html); what it proposes and the build Tasks are in [the design README](../design/README.md#sub-agents-and-processes-what-it-proposes).

While a session works, its Agent may start **Sub-agents** (an agent that does part of the work in its own context and reports back) and **Processes** (a command run in the background, such as a dev server or a long test run). Above the message input, a Thread says how many are running; a press opens a live, read-only view of each: a Sub-agent's messages and tool calls, a Process's command and its output as it streams. Ended ones stay viewable for the rest of the session.

**Names** (in the [glossary](../../GLOSSARY.md)): **Sub-agent** and **Process**, the user's own words. "Process" was in Pipeline's _Avoid_ list, meant as a synonym for a Pipeline; that entry now says so, as a Process is something else. "Background command" was weighed (it is the API engine's code name, `BackgroundCommands`, and Claude Code's notice words), but it is longer on a narrow line, and the user said "process". In code, a Process is never a variable named `process`, which is Node's global: `startedProcess`, `processes`, `ProcessState` and the like.

## What each engine reports today

Read in the code on 2026-11-10, with the pinned Agent SDK 0.3.310 (`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts`, `sdk-tools.d.ts`).

### Claude Code (the Agent SDK adapter and the `-p` fallback)

Both adapters map the engine's stream through one function, `sessionEvents` in `adapters/claude-code/sdk-events.ts`, called by `StreamEvents.of` (`stream-events.ts`), so whatever is said here holds for both.

**Sub-agents, today:**

- A Sub-agent starts as a call of the `Task` tool (its newer name, `Agent`, is the same tool; `session-settings.ts` lists `Task` among the built-in tools). The call's input holds `description`, `prompt` and `subagent_type`.
- Its messages reach the session as the parent's do: an assistant message with `parent_tool_use_id` set to the starting call's id. `assistantEvents` turns its text and tool calls into `TextEvent` and `ToolCallEvent` with `withinToolCall` set to that id (`session-events.ts`: "The tool call of the subagent that made it").
- Its end is the starting call's tool result: `AgentOutput` in `sdk-tools.d.ts`, `status: "completed"` with its `content`, `totalToolUseCount`, `totalDurationMs` and `totalTokens`, or, for one started in the background (`run_in_background`), `status: "async_launched"` at once, with `agentId`, `description` and `outputFile`.
- Conversations drops all of it from the Thread: `sessionLogLines` (`conversations/application/session-log.ts`) returns nothing for a text or a tool call with `withinToolCall`.

**Missing for Sub-agents:**

- `ToolResultEvent` has no `withinToolCall`, though the engine's user message carries `parent_tool_use_id`: a Sub-agent's tool results can't be told from the Agent's.
- No event says a Sub-agent started or ended. Its `Task` call marks the start for sure, but nothing reports a background one's end, nor its engine task id (below).
- No state: running, finished or failed are nowhere.

**Processes, today:** nothing reaches the port. `sessionEvents` drops every `system` message (`default: return []`), and the pinned SDK sends its background work as `system` messages:

| Message | Fields The Office needs |
| --- | --- |
| `SDKTaskStartedMessage`, `subtype: "task_started"` | `task_id` (the id TaskStop names), `tool_use_id` (the call that started it), `description`, `task_type` (`local_bash` for a background command, `local_agent` for a Sub-agent), `subagent_type`, `is_backgrounded`, `parent_task_id` (the Sub-agent that started it, if any), `prompt`, `ambient` (housekeeping, to be left out) |
| `SDKTaskProgressMessage`, `"task_progress"` | `task_id`, `usage` (`total_tokens`, `tool_uses`, `duration_ms`), `last_tool_name`, `summary` (only with `agentProgressSummaries`, which costs model calls: left off) |
| `SDKTaskUpdatedMessage`, `"task_updated"` | `task_id`, `patch.status` (`pending`, `running`, `completed`, `failed`, `killed`, `paused`), `patch.error`, `patch.end_time`, `patch.is_backgrounded` |
| `SDKTaskNotificationMessage`, `"task_notification"` | `task_id`, `tool_use_id`, `status` (`completed`, `failed`, `stopped`), `reason` (`worker_restart`), `output_file`, `summary`, `usage` |
| `SDKBackgroundTasksChangedMessage`, `"background_tasks_changed"` | `tasks[]`: every live background task (replace, don't merge); a safety net for a missed end |

A background `Bash` call's result carries `backgroundTaskId` (`BashOutput` in `sdk-tools.d.ts`), and its text names the output file the command writes to. The output itself never comes in the stream. Two ways to read it: the output file (named in that result, and again in the notification's `output_file`), or the `get_task_output` control request (`SDKControlGetTaskOutputRequest`: the last 8 KiB, `total_bytes`, `truncated`). `get_task_output` isn't a method of the SDK's `Query`, only of the control protocol, which the `-p` fallback can send (`StreamJson.request`) and the SDK adapter can't.

**Missing for Processes:** every event: a start, its output, its end. The command line is in the `Bash` call's input, which the adapter has to keep by call id until the start arrives.

**To confirm in the engine check** (two new scenarios, `engine.background-tasks` and `fallback.background-tasks`, run once on the cheapest model, not here): that `task_started` and `task_notification` come for a background `Bash`, a foreground Sub-agent and a background Sub-agent, on both adapters; whether a background Sub-agent's own messages stream with `parent_tool_use_id` like a foreground one's (if not, they are read from its `outputFile`); the `task_type` of a `Monitor` call; where the output file is and that the service can read it; and what an interrupt does to each (Claude Code is expected to stop a foreground Sub-agent with the turn and leave background work running).

### The API engine

`adapters/openai-compatible-api/background-commands.ts`:

- **Processes:** `BackgroundCommands.start` runs a `Bash` or `PowerShell` call with `run_in_background`, gives it an id like the SDK's (`b` and 8 hex digits), writes its output and errors to `<id>.output` in the session's folder (`<temp>/office-sessions/<session id>/`), and keeps its command line and description. `stop` ends it for TaskStop; `endAll` ends every one on `interrupt`; `close` ends them and removes the folder when the session ends. A command that ends by itself leaves Claude Code's `<task-notification>` for the model (`endedNotice`), with its exit code.
- **Missing for Processes:** no event for a start, the output or an end. Everything needed is already in `RunningCommand`; only the reporting is missing.
- **Sub-agents:** the loop has no `Task` tool (`SessionTools.of`), so it reports none. That is not a gap in the reporting: there is nothing to report. A Sub-agent on this engine needs a new tool in The Office's own loop (a nested conversation with the session's tools), which is out of scope here and named as later work. The line on this engine counts Processes only.

### The scripted engine

`adapters/scripted/`: a script replays `SessionEvent`s in order (`ScriptStep` `{ step: "event" }`, checked by the zod `sessionEvent` union in `session-script.ts`), waiting at each of the caller's steps. To play Sub-agents and Processes it needs:

- the new events in the `sessionEvent` union, and `withinToolCall` on `tool-result`, so scripts and recordings (`RecordingEngine`, `apps/web/e2e/sessions.jsonl`) carry them;
- a step that waits for the test (`{ step: "wait", mark: "…" }`, released by `ScriptedSession.reach(mark)`), since events after `turn-ended` otherwise play at once: a test needs a Process to stay running between turns, a page to open late, then the output to go on.

## The model

A session's Sub-agents and Processes are kept by **Conversations**, beside its Thread. The Engine reports them as session events and keeps nothing; Pipelines reads nothing new, as a Stage's session is a Stage Thread, which Conversations already owns. Conversations is where a session's events are logged (`ThreadRunner`, `StageThreads`), where the Project's mask is applied before anything is stored or sent (`sessionLogLines`), and where a Thread's web events come from (`ThreadWebEvents`), so it owns them for the same reasons it owns a Thread's messages (spec [5.3](5.3-modules.md): Engine talks to no module).

**Both kinds are known by the same id**, `callId`: the id of the tool call that started them, the one id every engine has, a foreground Sub-agent included. Each also keeps the engine's own task id, `engineTaskId`, when the engine has one (Claude Code's `task_id`, the API engine's `b` and 8 hex digits, which TaskStop names), so that stopping one later has what it needs.

**A Sub-agent** holds:

- its `callId`, which its messages name as `withinToolCall`, and its `engineTaskId` when there is one;
- who started it: the Agent, or another Sub-agent (by its id);
- its description (the call's `description`), its kind (`subagent_type`, such as "general-purpose" or "Explore"), and its prompt, the brief it was given;
- whether it runs in the background;
- its state and why it ended (below), and when it started and ended;
- its messages and tool calls, in order, as a Thread logs its Agent's (text, a tool call's summary, a refusal), each with a sequence number, through the Project's mask;
- what it reported back (the starting call's result) and its counts when the engine gives them (tool calls, tokens).

**A Process** holds:

- its `callId` (the `Bash` or `PowerShell` call that started it) and its `engineTaskId` (`b1f9c2e07`);
- who started it: the Agent or a Sub-agent;
- its command line, whole, and its description; the shell it runs in;
- its state, its exit code when it exited, why it ended, and when it started and ended;
- its output, in chunks with sequence numbers, through the Project's mask.

**Masking whole lines.** The Project's mask matches within a text, so a secret split across two output chunks would get past it. Conversations masks a Process's output by complete lines only: it holds back an unfinished last line until its newline comes, the Process ends, or about a second passes, and masks it then. A Sub-agent's messages are whole when they arrive, and are masked as a Thread's are.

**States:**

| State | When |
| --- | --- |
| Running | From its start until it ends. |
| Finished | A Sub-agent that reported back; a Process that exited with 0. |
| Failed | A Sub-agent whose call failed; a Process that exited with anything but 0, or couldn't start. |
| Stopped | Ended before it finished: by the Agent (TaskStop), by an interrupt or by the session's end; or no longer seen after The Office restarted. Its ending says which. |

Stopped is a fourth state beside the three asked for: the Agent stopping its own dev server is ordinary work, and Failed would cry wolf. The SDK makes the same split (`status: "stopped"`).

What ends what:

- **An interrupt** stops what the engine stops with the turn. On Claude Code a foreground Sub-agent stops with it and background work runs on (to confirm in the engine check). On the API engine `interrupt` ends every Process (`endAll`). The view shows what happened; it doesn't change either engine.
- **TaskStop** makes it Stopped, "by the Agent".
- **The session's end** stops whatever still runs ("ended with the session"): the engine ends its background work with the session, on both engines. A Thread's session ends after ten idle minutes (`IDLE_MS` in `thread-runner.ts`), and a Stage's session with its run.
- **The Office's restart:** after it, no session is there to report on them, and a background command may still be running on the machine, so nothing claims it stopped. At startup Conversations puts every Process and Sub-agent still Running in the Stopped state with the ending "Ended when The Office restarted", as it recovers interrupted answers.

**How long they are kept: for the rest of the session.** They belong to the Thread's session (`ThreadSession`, the engine session id). So they are kept:

- across turns, and across the session's end and resume after ten idle minutes, since a resume continues the same session;
- across The Office's restart: they are stored in the database, not in memory;
- until the Thread's session is replaced by a fresh one (the Context policy's fresh or hand off, spec [2.5](2.5-context-policy.md)), when the old session's are removed with it;
- for a Stage, with its run: a Stage Thread has one session and never gets another, so a run's Sub-agents and Processes stay readable in its Stage history, as its Thread does.

**Caps on what is kept:**

- a Process keeps the **last 256 KB** of its output, counted after masking; what came before is dropped, and its size is counted ("1.9 MB of earlier output isn't kept");
- a Sub-agent keeps its **last 1,000** messages and tool calls, the earlier ones counted the same way;
- a session keeps its **latest 100** Sub-agents and Processes that ended; Running ones are always kept.

Output is batched in one place only, the engine adapter: each read of the output file, every half second, is one `process-output` event, which Conversations stores and sends as it comes. A chatty command so gives two events a second at most.

## New session events

On the `SessionEvent` port (`engine/ports/session-events.ts`), the same on every adapter:

| Event | Fields |
| --- | --- |
| `sub-agent-started` | `callId`, `engineTaskId` (or undefined), `withinToolCall` (the Sub-agent that started it, or undefined for the Agent), `description`, `agentKind` (or undefined), `prompt`, `background` |
| `sub-agent-changed` | `callId`, what the engine added since the start: `engineTaskId`, `background` |
| `sub-agent-ended` | `callId`, `ending` |
| `process-started` | `callId`, `engineTaskId`, `withinToolCall`, `commandLine`, `description` |
| `process-output` | `callId`, `text` (what the adapter read since its last read, in order) |
| `process-ended` | `callId`, `ending`, `exitCode` (or undefined) |

and `withinToolCall` on `tool-result`. `sub-agent-changed` is there because a Sub-agent starts with its call, before the engine says more about it (below). An `ending` is `{ state: "finished" }`, `{ state: "failed", reason }` or `{ state: "stopped", by: "agent" | "interrupt" | "session-end" }`. "Ended when The Office restarted" is Conversations' own ending, as no engine sees it. These events may come between turns, while the session waits for a message: whoever reads a session's events keeps reading while it lives.

- **Claude Code** (shared by both adapters in `adapters/claude-code/`): a Sub-agent **starts with its `Task` (or `Agent`) tool call**, which reaches the session for sure on both adapters, foreground or background; its input gives the description, kind, prompt and `run_in_background`. Whether `task_started` comes for a foreground Sub-agent is still for the engine check to confirm, so the `task_*` messages only add to it: `task_started` with `task_type` `local_agent`, matched by `tool_use_id`, gives `sub-agent-changed` with its `engineTaskId` (and `is_backgrounded`). A Process starts with `task_started` with `task_type` `local_bash` (and `Monitor`'s, once the check names it), its command line taken from the `Bash` call kept by `tool_use_id`; `ambient` tasks are left out. `task_notification` gives the end (`completed` finished, `failed` failed, `stopped` stopped, by the Agent after a TaskStop call or by the interrupt that came before it); a foreground Sub-agent's end is also its call's result, whichever comes first. A task that leaves `background_tasks_changed` with no end is ended Stopped. A Process's output is read from its output file while it runs, every half second from the offset already read, and once more at its end; each read is one `process-output` event, the only batching there is.
- **The API engine:** `BackgroundCommands` reports each start (the call's id and its own id), reads its own output file the same way, and reports the end: exit 0 finished, any other exit failed, `stop` stopped by the Agent, `endAll` on interrupt stopped by the interrupt, `close` stopped by the session's end. No Sub-agent events.
- **The scripted engine** replays them as recorded, and the agent engine contract gets a scenario with a background command that outputs, is read, and ends, run on every adapter (the Claude Code ones live-gated).

## Live streaming to the web

The pattern is the Conversations web events' (`ThreadWebEvents`, through the platform's `WebEventForwarding` and `EventStream`): each event names the Thread and its home. A Thread's events today are signals to refetch; these carry what changed, as `thread.tokens-counted` carries its tokens, since output is too frequent to refetch.

**Reads** (Conversations' controller):

- `GET /api/threads/:threadId/sub-agents-and-processes`: the Thread's current session's Sub-agents and Processes, each with its `callId`, `engineTaskId`, kind, who started it, description or command line, state, ending, times, and the sequence of its last message or output chunk; no messages and no output.
- `GET /api/threads/:threadId/sub-agents/:callId/messages?after=<sequence>`: its messages and tool calls after that sequence (all of them, as kept, without it).
- `GET /api/threads/:threadId/processes/:callId/output?after=<sequence>`: its output after that sequence, with how much earlier output wasn't kept.

**Web events:**

| Web event | Carries | Sent to |
| --- | --- | --- |
| `thread.sub-agent-started`, `thread.sub-agent-changed`, `thread.sub-agent-ended` | `threadId`, `home`, the whole Sub-agent as the list reads it | every page subscribed to the type, as today |
| `thread.process-started`, `thread.process-ended` | `threadId`, `home`, the whole Process as the list reads it | the same |
| `thread.sub-agent-messages` | `threadId`, `home`, `callId`, its new messages and tool calls, each with its sequence | only pages subscribed to that type **for that Thread** |
| `thread.process-output` | `threadId`, `home`, `callId`, `fromSequence`, the new text (masked, whole lines) | the same |

**Output reaches only the Thread it belongs to.** `EventStream` subscribes by event type alone today (`platform/websocket/event-stream.ts`, `receive` and `send`): a page subscribed to `thread.process-output` would get every Thread's output. So a subscription gains a scope: an event type with an optional `threadId`. `thread.sub-agent-messages` and `thread.process-output` are sent only to subscriptions scoped to their `threadId`; a subscription without a scope gets the other types as today. A page subscribes to the two, scoped to its Thread, while the view is open, and unsubscribes as it closes. It is a small platform change with tests of its own: `event-stream.ts`, the contracts' subscribe message (`clientMessageSchema`) and the web's event client (`apps/web/src/api/event-stream.ts`).

**The list needs no catch-up of its own.** Each start, change and end event carries the whole item, and the page puts it in its list by `callId`. A state only moves forward: once ended, an item never goes back to Running, and an older copy never replaces a newer one. So these events apply safely in any order, before, during or after the list's read.

**A page that opens late catches up a Sub-agent's messages and a Process's output without missing or doubling anything:**

1. It subscribes first, scoped to the Thread, and holds the events that arrive.
2. It reads the open item's messages or output, which answer up to a sequence.
3. It applies what it holds, and then each live event, only after that sequence; an event at or before it is already in the read and is dropped.
4. An event whose sequence skips ahead (a missed one), or the WebSocket reconnecting, reads again from the last sequence it has (`?after=`).

## Read-only

The view has no stop controls: no Stop on a Process, no Stop on a Sub-agent, no Stop all. Only the Agent stops them (TaskStop), or the session's end does. The window says so in its bar ("Only the Agent can stop them"). **Stopping them from the UI is later work**: the SDK's `Query.stopTask(taskId)`, the fallback's `stop_task` control request and the API engine's `BackgroundCommands.stop` already exist for it, each taking the `engineTaskId` the model keeps. What it needs is a decision on what the Agent is told when the user stops its work, and when a stop needs confirming.

## The UI

The design is [docs/design/sub-agents-and-processes.html](../design/sub-agents-and-processes.html); in short:

- **The line**, above the message input of a Thread, wherever a Thread has one: in the chat drawer, on a Task page's conversation and in a Stage run's Thread tab in the Stage history; where a Thread takes no message, above the line saying why. It shows only once the session has had a Sub-agent or a Process. While any runs: a live dot and "2 sub-agents, 1 process running", singular "1 sub-agent running", a kind with none left out, then "· 3 ended" when some ended, with "1 failed" in red. Once none runs: "3 sub-agents, 1 process ended", no dot. The whole line is one button.
- **The view** is a list and details. In the chat drawer and on the Task page it opens in a large window, "Sub-agents and processes", which keeps one height; in the Stage history, which is already a window, it is the run's third tab, beside Summary and Thread. The list has Running on top, then Ended, the one that ended last first, each in a line or two: a mark for its kind, the description or command, its state and how long it ran. Picked, a Sub-agent shows its prompt's first lines with "Read it in full", then its messages and tool calls in Rows with the Details switch on its row, as a Thread has them; a Process shows its command whole, then its output in monospace, following the end while it runs until the user scrolls up, with Jump to the end. On a narrow page the list and the details stack, with a "‹ All" row back to the list.

## Later work

- Stopping a Sub-agent or a Process from the view.
- Sub-agents on the API engine: a `Task` tool in The Office's own loop.
- Claude Code's other background work: workflows (`local_workflow`), MCP tasks, remote agents.
- A Sub-agent's one-line progress summary (`agentProgressSummaries`), which costs model calls.

## Open questions

- **A running Process and the idle end.** A Thread's session ends ten minutes after its last turn, ending a dev server the Agent left running. This design shows it "Stopped, ended with the session" but keeps the idle end; keeping a session alive while a Process runs is a change to the Context policy for the user to decide.
- **The interrupt differs per engine** (Claude Code leaves background work running, the API engine ends it). The view shows each as it is; making them the same is a change to the API engine.
