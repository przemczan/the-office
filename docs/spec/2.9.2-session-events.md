# 2.9.2 Session events

Covers: the session events of Sub-agents and Processes, the endings, what each engine reports.

## Session events

- They are on the `SessionEvent` port (`engine/ports/session-events.ts`), the same on every adapter.
- `withinToolCall` is also on `tool-result`, so a Sub-agent's tool results are told from the Agent's.
- These events may come between turns, while the session waits for a message: whoever reads a session's events keeps reading while it lives.

| Event | Fields |
| --- | --- |
| `sub-agent-started` | `callId`, `engineTaskId` (or undefined), `withinToolCall` (the Sub-agent that started it, or undefined for the Agent), `description`, `agentKind` (or undefined), `prompt`, `background` |
| `sub-agent-changed` | `callId`, what the engine added since the start: `engineTaskId`, `background` |
| `sub-agent-progress` | `callId`, `totalTokens`: its context size so far, from Claude Code's `task_progress` (`usage.total_tokens`); Conversations folds it into the Sub-agent's `totalTokens` as a revision |
| `sub-agent-ended` | `callId`, `ending`, `reportedBack` (what it reported back, or undefined), `toolCallCount` and `totalTokens` (or undefined) |
| `process-started` | `callId`, `engineTaskId`, `withinToolCall`, `commandLine`, `description` |
| `process-output` | `callId`, `text` (what the adapter read since its last read, in order) |
| `process-ended` | `callId`, `ending`, `exitCode` (or undefined) |

- `sub-agent-changed` is there because a Sub-agent starts with its call, before the engine says more about it.

## Endings

- An `ending` is `{ state: "finished" }`, `{ state: "failed", reason }` or `{ state: "stopped", by: "agent" | "interrupt" | "session-end" }`.
- "Ended when The Office restarted" is Conversations' own ending, as no engine sees it ([2.9.1](2.9.1-the-model.md#what-ends-them)).

## Claude Code

- It is the Agent SDK adapter and the `-p` fallback, which share `sessionEvents` in `adapters/claude-code/sdk-events.ts` and `BackgroundTasks` in `adapters/claude-code/background-tasks.ts`.
- **A Sub-agent starts with its `Task` (or `Agent`) tool call**, which reaches the session for sure on both adapters, foreground or background.
  - Its input gives the description, kind, prompt and `run_in_background`.
  - Its messages are the assistant messages whose `parent_tool_use_id` is that call's id.
  - The engine's `system` task messages only add to it: `task_started` with `task_type` `local_agent`, matched by `tool_use_id`, gives `sub-agent-changed` with its `engineTaskId` (and `is_backgrounded`).
- **A Process starts with `task_started` with `task_type` `local_bash`**, its command line taken from the `Bash` call kept by `tool_use_id`; `ambient` tasks are left out.
- **`task_notification` gives the end:**
  - `completed` is finished, `failed` is failed.
  - `stopped` is stopped, by the Agent after a TaskStop call or by the interrupt that came before it.
  - `reason: "worker_restart"`, the engine's own restart orphaning the task, is stopped with the session.
  - A foreground Sub-agent's end is also its call's result, whichever comes first.
- **What a Sub-agent reported back:** its call's result for a foreground one, and the notification's `summary` for a background one, whose call's result is only the `async_launched` placeholder.
- **The counts** are the call result's (`AgentOutput`) or the notification's `usage`.
- The notification carries no exit code, so a Process's `exitCode` is undefined on Claude Code unless the `summary` names one; the view then says "Failed" without one.
- A task that leaves `background_tasks_changed` with no end is ended Stopped.
- A Process's output is read from the output file its `Bash` result names, every half second from the offset already read, and once more at its end; each read is one `process-output` event, the only batching there is.
- This mapping follows the pinned SDK's types; the engine check's `engine.background-tasks` and `fallback.background-tasks` scenarios test it on the live engine ([docs/engine-check.md](../engine-check.md)).

## The API engine

- It is `adapters/openai-compatible-api/background-commands.ts`.
- `BackgroundCommands` runs a `Bash` or `PowerShell` call with `run_in_background`, gives it an id like the SDK's (`b` and 8 hex digits), and writes its output and errors to `<id>.output` in the session's folder (`<temp>/office-sessions/<session id>/`).
- It reports each start (the call's id and its own id), reads that file the same way, and reports the end:
  - exit 0 is finished, any other exit is failed;
  - `stop` is stopped by the Agent;
  - `endAll` on interrupt is stopped by the interrupt;
  - `close` is stopped by the session's end.
- A command that ends by itself also leaves Claude Code's `<task-notification>` for the model, with its exit code.
- The loop has no `Task` tool, so this engine has no Sub-agents, and its line counts Processes only.

## The Codex engine

- It reports neither Sub-agents nor Processes.

## The scripted engine

- It replays them as recorded (`ScriptStep` `{ step: "event" }`, checked by the zod `sessionEvent` union in `session-script.ts`).
- A step that waits for the test (`{ step: "wait", mark: "…" }`, released by `ScriptedSession.reach(mark)`) lets a Process stay running between turns.
- The agent engine contract has a scenario with a background command that outputs, is read, and ends, run on every adapter (the Claude Code ones live-gated).

## Defaults

### What the adapters report

- The events are the same on every adapter.
- An engine that reports neither Sub-agents nor Processes (Codex) sends none of these events.
