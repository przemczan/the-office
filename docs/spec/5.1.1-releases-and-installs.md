# 5.1.1 Releases and installs

Covers: released versions, the Debian/Ubuntu install, uninstalling, the Compose install. Part of [5.1](5.1-shape.md#defaults).

## Defaults

### Released versions

- The Office is released from `main` by the hand-run Release workflow, with semantic-release.
- The version comes from the Conventional Commits since the last `v*` tag.
  - With none of `feat`, `fix`, `perf` or `refactor`, there is no release.
  - A commit's header (type, scope and subject) is at most 100 characters, or the Conventional Commits check refuses it.
- `npm run verify` runs in the run environment before anything is tagged.
- An Office release is:
  - the tag `v<version>`;
  - a GitHub Release whose notes are those commits;
  - a prebuilt tarball for glibc Linux on x64 and on arm64, with its production `node_modules` and its own CPU's Claude Code, nothing to build on the target;
  - the image `ghcr.io/<owner>/the-office:<version>` and `:latest` for `linux/amd64` and `linux/arm64`, made from the same tarball.
- A release carries `office-release.json`, its version and commit, which Settings › Updates shows; a checkout shows its commit.
- Before the first tag only the commits after the one that added `.releaserc.json` count.
- Windows and macOS run from a checkout.
- How: [docs/releasing.md](../releasing.md).

### Installing on Debian/Ubuntu

- `curl -fsSL https://github.com/przemczan/the-office/releases/latest/download/install.sh | sudo bash` installs the newest release.
- Machines: a fresh Debian 12 or 13 or Ubuntu 22.04 or 24.04 (a VM, an LXC guest with nesting, or bare metal), on x64 or arm64 with systemd.
- Anything else, or a run without root, is refused with the reason before anything changes.
- Each release carries its own `install.sh` stamped with its version, which it installs unless `--version` names another.
- It installs only what is missing:
  - `git` and the ssh client;
  - Node 22 (22.18 or later, from NodeSource, at `/usr/bin/node`);
  - Docker Engine with Compose and buildx from Docker's repository, at the versions [container-runtime.md](../container-runtime.md) holds, held; a Docker already there is kept, and one lacking Compose or buildx stops the installer;
  - PostgreSQL 18 from PGDG as the machine's own cluster, not a container.
- Each repository's key is checked against its fingerprint.
- It follows the shared install layout:
  - the release in `/opt/the-office/releases/<version>`, after its signature (once a release key is pinned), its sha256, its top folder and its `office-release.json` check out, with `current` switched to it in one rename;
  - the non-root system user `the-office`, in the `docker` group, owning `/opt/the-office` and the data folder;
  - a Postgres role `office` and database `the_office` with a random password;
  - `/etc/the-office/office.env`, readable by root alone, with `OFFICE_HOST`, `OFFICE_PORT`, `OFFICE_DATA_DIR` and `DATABASE_URL`;
  - `the-office.service`, run as `the-office` through the launcher.
- It asks only for:
  - the address (`127.0.0.1`, this machine alone, unless the user opens it up);
  - the port (`4310`);
  - the data folder (`/var/lib/the-office`).
- It asks at the terminal even when piped, or takes the answers from `--host`, `--port`, `--data-dir` or `OFFICE_HOST`, `OFFICE_PORT`, `OFFICE_DATA_DIR`; `--yes` asks nothing.
- Before the start it makes a setup token (`setup-token.js --quiet`), so the service's first start prints none.
- It waits up to 3 minutes for `/api/health` to report the database up, else it fails, pointing to `journalctl -u the-office`.
- It prints the address to open and the token.
- Running it again is safe:
  - it keeps the answers, the database password, the installed version and the lines the user added to `office.env`;
  - it restarts The Office only when the release, `office.env` or the unit changed;
  - it installs a newer `--version` and refuses an older one;
  - it prints a new setup token only while no user exists;
  - the data folder can't be changed by a rerun; moving the data is by hand.
- In an LXC guest it warns that Docker needs nesting, and stops with `pct set <id> --features nesting=1,keyctl=1` when Docker can't start.
- The public address and anything else The Office reads are lines the user adds to `office.env`, which a rerun keeps; the installer doesn't ask for them, nor installs the language servers.
- The user's guide to both installs is [docs/installing.md](../installing.md).

### Uninstalling

- `install.sh --uninstall` stops and removes:
  - the service and its unit;
  - `/opt/the-office` and the install log;
  - this Office's run environment containers, networks, volumes and images (by `office.managed` and its `office.instance`).
- It keeps the data folder, the database and its role, `office.env` and the user `the-office`, so running the installer again brings the same Office back.
- `--uninstall --purge` also drops the database and its role and removes `/etc/the-office`, the user and the data folder.
  - The data folder goes only when it is below a top-level folder, outside the system's own folders, and owned by `the-office`.
  - A data folder it keeps inside the user's home keeps the home too.
- Neither removes Node, Docker, PostgreSQL or their apt sources, which the install docs say how to remove by hand.
- It lists what it removes and keeps and asks at the terminal; without one it refuses unless given `--yes`.

### Installing with Docker Compose

- The **Compose install** is a folder holding `docker-compose.yml` and its `.env`.
  - Each release carries them as `docker-compose.yml` and `the-office.env`, the latter with `OFFICE_VERSION` set to it.
  - The checkout's copies are in `deploy/compose/`.
- It is Compose project `the-office` with these services:
  - `office`: The Office's released image `ghcr.io/przemczan/the-office:${OFFICE_VERSION}`, the tag coming only from `.env`'s `OFFICE_VERSION`;
  - `postgres`: the dev stack's pinned Postgres in the named volume `postgres-data`, published on `127.0.0.1` alone, with its password from `.env`;
  - a one-shot `data-folder` step, which runs first as root, creating the data folder if needed and making its top (never what is inside) owned by uid 10001.
- The Office starts only once the `data-folder` step has finished and Postgres is healthy.
- The bundled Grafana isn't one of its services, as The Office runs it itself on every install kind ([5.2](5.2-stack.md#infrastructure)).
- The Office runs as the image's non-root user `office` (uid 10001), on the **host's network**.
  - The Host check ([5.1](5.1-shape.md#host-and-origin-checks)) accepts the IP address a request arrived at, at its port; behind Docker's bridge that address would be the container's own.
  - So `OFFICE_HOST` and `OFFICE_PORT` behave as on a direct install only on the host's network (localhost, the LAN IP, the public address).
  - The image's health check asks at `OFFICE_HOST` and `OFFICE_PORT`.
- It mounts the host's Docker socket and joins its group (`DOCKER_GID`), which is reaching the host as root ([container-runtime.md](../container-runtime.md)).
- It mounts the data folder at the **same absolute path** on the host and in the container, since run environments bind-mount a Task's worktree by its path, read by the host's Docker daemon; so only Projects inside the data folder (those added by Repository URL) mount.
- Its container gets only its own variables, listed one by one, so nothing else in `.env` reaches Project commands.
- It runs with `restart: unless-stopped` and `stop_grace_period: 1m`.
- Moving to another release is `OFFICE_VERSION` in `.env` and `docker compose up -d --no-deps office`, which recreates The Office alone.
- The install, update and uninstall walkthrough is the install docs' part ([docs/installing.md](../installing.md)).
