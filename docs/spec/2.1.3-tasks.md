# 2.1.3 Tasks

Covers: Task, Task kind, bug details, Found while working on, Task states, Ready, Mark Ready, Title, Description, Commit message, Dependencies, Dropping, Drop reason, Reopen, GitHub issue, joining and leaving an Initiative, a Task's engine override and its models and efforts, priority and order, who did what, History, Office actions on a Task, Off-board Tasks, setting up the run environment, Archive, Moving a Task, Conflict resolution Tasks.

## Task

- One unit of work in one Project, done when its **Definition of Done** is met: a published change, an Attachment, or both.
- Its Plan and Definition of Done are in [2.1.4](2.1.5-planning-and-start.md#plan-and-definition-of-done).

## Task kind

- Every Task has a **Kind**: **Feature** (new or changed behaviour), **Bug** (something that doesn't work as it should) or **Chore** (upkeep such as an update or a clean-up).
- Which Kind a new Task starts as: [New Tasks are Features](#new-tasks-are-features).
- The user changes it on the Task page, the Planner with `write_kind`, and whoever creates Tasks in a Thread with the Office action `change_task_kind` ([Office actions on a Task](#office-actions-on-a-task)), in any state until Done or Dropped; a Done or Dropped Task is refused: "A Task keeps its Kind once it is Done or Dropped."
- A change of Kind never moves the Task, so a Ready Task stays Ready.
- The Kind names the commit type the Planner suggests: Feature `feat`, Bug `fix`, Chore `chore` ([2.5](2.5-context-policy.md#the-brief)).
- It picks the Pipeline proposed first, when the Project gives the Kind a default of its own ([2.1.1](2.1.1-projects.md#project-settings)).
- The Work board filters by it and its search finds it by its word ([2.1.6](2.1.6-board-and-search.md#search)).

## Bug details

- A Bug has two linked records of its own, each optional:
  - **Caused by**: the Task whose change brought the Bug in, any other Task in any Project and state, Done and archived ones too; the other Task lists it under "Caused bugs"; a Task can't be caused by itself;
  - **Found in version**: the release the Bug was seen in, one of the Project's `v*` tags or free text, 1 to 64 characters.
- The user changes them on the Task page, and the Planner with `write_bug_details`, until the Task is Done or Dropped, never moving it.
- They show only on a Bug; changing the Kind away keeps them, hidden, so changing it back loses nothing.

## Found while working on

- A Task of any Kind, and an Idea ([2.1.2](2.1.2-ideas-and-attachments.md#idea)), may record the Task it was **found while working on**, optional.
- It is set only as the record is made:
  - by a Bug Task Decision, to the Task whose Agent proposed it ([2.4.2](2.4.2-decisions.md#the-bug-task-decision));
  - by creating the Task or capturing the Idea in a person's Thread on that Task ([6](6-permissions-and-safety.md#a-persons-office-tools)).
- It is never changed afterwards.
- The Task page lists it in the Task's linked records whenever it is set ([Task page](screens/task-page.md)).

## Task states

- **Backlog → Planning → Ready → In progress → Done.**
- Side states: **Waiting on you** and **Paused**.
- Exit: **Dropped**.
- Before Backlog: **Shaping**, for a Task of an Initiative still being shaped ([Tasks of an Initiative still being shaped](#tasks-of-an-initiative-still-being-shaped)).
- In progress shows the current Stage.
- Done or Dropped disconnects the Task's Connected devices ([2.13](2.13-connected-devices.md#lifecycle)).
- Work moves forward. The ways back:
  - a change to the Plan, the Definition of Done or the Pipeline proposal of a Ready Task that hasn't started, by the user's **Save** or by the Planner, takes it back to **Planning** to be marked Ready again ([2.1.4](2.1.5-planning-and-start.md#changing-a-ready-task));
  - a **Move** of a Ready Task to another Project ([Moving a Task](#moving-a-task));
  - **Restart from…** and **Start over** on a paused or stopped Task ([2.4.5](2.4.5-stopping-and-restarts.md#restart-from)), the second taking it to Ready;
  - **Reopen** of a Dropped Task ([Reopen](#reopen)).

## Ready

- Ready requires all of:
  - a Plan and a Definition of Done, both confirmed by the user, or by auto mode on their behalf ([2.1.4](2.1.5-planning-and-start.md#auto-mode)), or confirmed as they stand, even empty, by the user's Mark Ready without them ([Mark Ready](#mark-ready));
  - no Pipeline proposal left open;
  - no Decision on the Task left open;
  - a Pipeline.
- A Task has no Pipeline until one is chosen: from the Planner's proposal confirmed by the user or by auto mode, or by the user.
- Until then its page shows a placeholder where the Stages will be.
- A new Task doesn't take its Project's default Pipeline, nor its Kind's ([2.1.1](2.1.1-projects.md#project-settings)).

## Mark Ready

- **Planning is optional:** a Task whose Plan and Definition of Done were written by the user or given with the Task, and confirmed by the user, goes from Backlog straight to Ready by **Mark Ready**, under Ready's other rules.
- Mark Ready shows in Backlog and Planning once a Pipeline is chosen, which the user does there on the Pipeline rail, and no Decision on the Task is open.
- Its checklist names "Choose a Pipeline" while there is none.
- Mark Ready, confirming the Plan and the Definition of Done, choosing the Pipeline and the engine, and Move to another Project are the user's click, or a person's call in Work › Moving work, ruled by their [Authority](6-permissions-and-safety.md#authority) ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).
- The user may **Mark Ready without a confirmed Plan or Definition of Done:**
  - Mark Ready then asks first in a dialog naming what is missing (a Plan or a Definition of Done not written, or written and not confirmed);
  - going on confirms both as they stand, even empty, by that user, in the same change that moves the Task to Ready;
  - the Pipeline and open Decision conditions still hold.

## Title

- A Task's title can be changed in any state except Done and Dropped, by the user on the Task page ([Task page › Head](screens/task-page.md#head)) and with `change_task_title` ([Office actions on a Task](#office-actions-on-a-task)).
- A Done or Dropped Task is refused: "A Task keeps its title once it is Done or Dropped."

## Description

- What the user wants, in their own words.
- Optional; written in "New Task" (the top bar's Create › Task) under the title, and edited on the Task page, where it sits above the Plan, or with `change_task_description` ([Office actions on a Task](#office-actions-on-a-task)).
- It can be changed until the Task starts.
- The CTO writes one on an Initiative's Tasks too, by their changes ([The CTO's changes to an Initiative](2.1.4-initiatives.md#the-ctos-changes-to-an-initiative)).
- It is part of the Planner's Brief and of every Agent Stage's Brief ([2.5](2.5-context-policy.md)); with none, the title alone is enough to plan from.
- It can mention a Task, Initiative, open Decision or Idea, picked with `@` as in the chat or pasted as the link to its page; it is saved as a Markdown link to the record's page and shown on the Task page as the record's chip.
- An Idea's notes and an Initiative's outcome take Mentions the same way ([2.1.2](2.1.2-ideas-and-attachments.md), [2.1.4](2.1.4-initiatives.md#the-user-writes-the-outcome)).
- "New Task" also takes optional Attachments, files or links, added to the Task in the order chosen once it is added; if one can't be, trying again adds only those left, never the Task a second time.

## Commit message

- A Task holds the message of the one commit Publish lands it as, following the commit convention its Project's own docs define.
- The Planner suggests it with the Plan, and every Agent Stage may update it.
- The user edits it on the Task page in any state until Publish lands it or the Task is Done or Dropped.
- It never moves the Task, so a Ready Task stays Ready.
- With none written, Publish uses the title with a short summary below it ([2.3](2.3.4-publish.md#the-tasks-commit-message), "The Task's commit message").

## Dependencies

- A dependency can be on any Task in any Initiative or Project.
- A blocked Task cannot start, but can be queued until its blockers are Done or Dropped.
- They are set before the Task starts, never on an Archived Task, and never closing a cycle.
- The user adds and removes them on the Task's page, whose Add window leaves Archived Tasks out; whoever shapes Initiatives or holds Plans does with the Office actions `add_dependency` and `remove_dependency`.
- A Task waits directly only for Tasks it doesn't already wait for through another Task: if C waits for B and B waits for A, C doesn't wait for A directly.
- Every way a dependency is added follows this: the user's, `add_dependency`, a new Task's waiting list (`create_task`, an Initiative's added Task) and an Initiative's Proposals.
  - A wait the Task already has through another Task is left out, and `add_dependency`'s answer says through which Task.
  - Otherwise the new wait takes out the direct waits it covers, on the Task itself and on every not-started Task that waits for it, and the answer names each.
  - A new Task waits directly only for those of its blockers no other of them waits for.
- Started Tasks keep their dependencies.
- A Publishing Task, which waits for every Task of its Initiative by design, keeps its own.
- A wait through a Publishing Task, or through a Task Done or Dropped, doesn't count.
- Redundant waits are not cleaned up on their own; they go when the Task's dependencies next change this way.

## Dropping

- The user Drops a Task in any state but Done and Dropped, from its page or a Gate's Drop step.
- An Agent Drops one with `drop_task` only before it starts: a started Task is refused, "\"<title>\" has started, so only the user Drops it: ask them to."
- The acting Author decides, so the same Task the user may Drop is refused to an Agent.
- The floor is `drop_task`'s and `drop_initiative`'s. A Drop at a Gate (`drop_at_gate`) is a Gate choice, ruled by Work › Gates and runs ([2.3.3](2.3.3-gates-and-checks.md#gates)): held for the user's approval by default, and the Stage history names the person and the user who asked.
- One exception: a Consultant's Drop answer to a Decision The Office put to their duty, such as a staffing Decision, Drops a started Task, recorded as theirs, since the user delegated that Decision.
- Whether an Agent Drops a Task alone or holds the call first is its [Authority](6-permissions-and-safety.md#authority) for Work › Task records, on its own work and on others'.
- A Dropped Task can be picked up again: it is **reopened** ([Reopen](#reopen)).

## Reopen

- **Reopen…**, on a Dropped Task, takes it to **Backlog** or to **Ready**.
- Reopen is the user's click, or a person's call in Work › Gates and runs, ruled by their [Authority](6-permissions-and-safety.md#authority), with a preset default ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).
- Ready is offered only when its Plan, Definition of Done and Pipeline are confirmed; otherwise it is disabled with the reason.
- A Task that had started is started over as by Start over ([2.4.5](2.4.5-stopping-and-restarts.md#start-over)), with the same choice to reset the branch, and refused once Publish pushed its branch or opened a pull request: "Its work has left the workstation."
- The Drop reason stays in History and is cleared from the Task's head.
- A GitHub issue the Drop closed is reopened ([2.1.1](2.1.1-projects.md#github-issues)).
- Decisions the Drop closed stay closed.
- Refused with the reason for:
  - a Publishing Task and a Conflict resolution Task;
  - a Task of a Done or Dropped Initiative;
  - a Task of an active Initiative whose Project's Publishing Task has started.
- Otherwise, while that Publishing Task hasn't started, the reopened Task becomes its blocker again, as a new Task in the Initiative does ([Publishing Tasks](2.1.4-initiatives.md#publishing-tasks)).
- An archived Dropped Task is Restored first ([Archive](#archive)); Restore only brings it back to the board in the state it had, and is not a Reopen.
- History says "Reopened to <Backlog|Ready> by <who>" ([History](#history)); screen: [Task page › Reopen window](screens/task-page.md#reopen-window).

## Drop reason

- The user may say why a Task is Dropped, in the Drop window and in a Gate's Drop step, and an Agent with `drop_task`; the reason is optional.
- It is one of: **Won't fix**; **Duplicate**, naming the other Task, any Task but this one in any Project and state; **Can't reproduce**; **Other**, with the user's words, 1 to 500 characters.
- It is kept with the move to Dropped, in the same change.
- The Task page and the Archived tab show it; a Duplicate's other Task lists this one under "Duplicates".
- Dropping an Initiative drops its open Tasks with no reason.
- With its Project's switch on, a Task made from a GitHub issue closes the issue with the reason ([2.1.1](2.1.1-projects.md#github-issues)).

## GitHub issue

- A Task made from a GitHub issue lists the issue in its linked records: its state, number and title, its author, and who imported it and when.
- Importing, the issue's state and what The Office writes back on GitHub: [GitHub issues](2.1.1-projects.md#github-issues); the Project's GitHub issues switch stops all of it ([Feature switches](2.1.1-projects.md#feature-switches)).

## Joining and leaving an Initiative

- A Task is in at most one Initiative, and joins or leaves one only before it starts.
- One The Office made (an [Off-board Task](#off-board-tasks), a "Set up test targets" Task made before, a Conflict resolution or a Publishing Task) never does.
- The user adds a Task to an Initiative, or takes it out, on the Task's page and on the Initiative's page (Add an existing Task, Take out a Task); whoever shapes Initiatives or holds Plans does with the Office actions `add_to_initiative` and `take_out_of_initiative`.
- A Task joins an Initiative being shaped only from Backlog, moving to Shaping, and an active one keeping its state; a done or dropped Initiative takes none.
- Taking a Task out moves one in Shaping to Backlog, and one planned in the Initiative's planning Thread loses it: from Planning it goes to Backlog, as a changing Save does with no planning Thread, and a Ready one stays Ready.
- The Publishing Task in its Project waits for a Task that joins and stops waiting for one taken out; its other dependencies stay.
- Joining is refused once the Task has a worktree and the Initiative has a Pipeline in its Project (the worktree came from the base branch), and leaving once its worktree came from the Initiative's branch.
- Each move is kept in the Task's state changes, named by who made it.

## A Task's engine

- A Task can force one engine of its own, its **engine override**, turned on with the switch "Override the engine", which every session about it runs on: its Stage runs, its planning Thread and Consultations on it.
- It names an engine only, no model: each person still works with their model and effort for its engine type ([5.4.5](5.4.5-engines-and-cascade.md#the-model-and-effort-cascade)).
- It uses no Stand-in Engine: when its usage window is used up, the Task waits or pauses until the reset ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#a-forced-engine-has-no-stand-ins)).
- It is set and cleared on the Task page until the Task is Done or Dropped, and applies from the next session; a Done or Dropped Task keeps it as history.
- A second switch, "Override models and efforts", works apart from it, with or without an engine override: it sets a model and an effort for each person the Task's work names (the Planner and each Role its Stages name), each "Unchanged" unless set.
- These are the **Task's setting for the person**, kept per engine type and covering every session about the Task from its next turn; they win over the Project's force and a Stage's effort ([5.4.5](5.4.5-engines-and-cascade.md#the-model-and-effort-cascade)). Turning the switch off clears them; a Done or Dropped Task keeps them as history. Only a Task has them, not an Initiative.
- Where it stands in the engine cascade, what a Task that sets none follows, and the checks a save or a move into or out of an Initiative passes: [5.4.5](5.4.5-engines-and-cascade.md#the-engine-cascade).

## Priority and order

- Three priority levels plus manual order per Project.
- The user changes the priority on the Task page, and a person with `change_task_priority` ([Office actions on a Task](#office-actions-on-a-task)).
- Tags, full-text search and saved views: [2.1.8](2.1.6-board-and-search.md#search).
- Archive: [Archive](#archive).
- Moving a Task to another Project: [Moving a Task](#moving-a-task).

## Who did what

- Every record that says the user did something names which user ([2.10](2.10-users-and-signing-in.md)): who captured an Idea, created a Task or an Initiative, started a Task or moved it from one state to another (its state changes say "by Ana" where they said "by the user"), passed or sent back a Gate, attached an Attachment, and changed a setting (a Role card's version, a Pipeline, a Project's settings, the Office instructions, any Office setting).
- Work an Agent or The Office did still names the person or The Office.
- A Task can be **created by The Office**: a Bug Task made by Create the Bug Task ([2.4.2](2.4.2-decisions.md#the-bug-task-decision)) and a Task the auto-import made from a GitHub issue ([GitHub issues](2.1.1-projects.md#github-issues)); a Task imported by hand names the user who imported it.

## History

- A Task's, an Idea's and an Initiative's **History** lists, oldest first, its state changes and every edit of its fields, each naming who made it and when.
- An edit is kept, whoever made it (the user, an Agent through an Office action, or the Planner's `write_plan`, `write_definition_of_done` and `write_kind`), for:
  - a Task's title, Description, Kind, priority, Plan and Definition of Done;
  - an Idea's title, notes and Project;
  - an Initiative's outcome.
- An edit keeps the field's name, when and who, never the old or the new text.
- Each entry names who: "by the user Ann Lee", "by the person in the Role planner", "by The Office".
- A direct change by a person also names the user who asked: "by the person in the Role cto, asked by Ann Lee".
- Who asked follows where the call is made:
  - in a Thread a user talks in, the user who wrote the newest user message in the Thread before the call's turn;
  - in a Consultation, the user the chain of calls started from, when it started from a user's message, and otherwise none;
  - in an Agent Stage, no user: the entry names the Stage run instead ("in a Stage of <Pipeline>").
- A call held at Ask me also names the user who allowed it ([2.4.2](2.4.2-decisions.md#proposals-and-approvals)).
- An applied Proposal names the applying user and "proposed by <person>".
- Ideas and Initiatives record who asked the same way; so do a Project setting change, a Role card version and an Office setting version ([6](6-permissions-and-safety.md#project-settings-by-agents)).
- It reads "Moved from Ready to Planning by …" for a state change and "Title edited by …" for an edit.
- It shows in the Task page's Overview, the Idea view and the Initiative page ([task-page.md](screens/task-page.md#history), [ideas.md](screens/ideas.md#history), [initiative-page.md](screens/initiative-page.md#history)).
- `read_task`, `read_idea` and `read_initiative` give it to Agents, and `GET /tasks/:id/history`, `GET /ideas/:id/history` and `GET /initiatives/:id/history` serve it.

## Office actions on a Task

- A person changes Tasks with the Office actions of Work › Task records ([5.4.1](5.4.1-engine-kinds.md#office-actions)), each the same route as the user's click, under the same rules:
  - `change_task_title` and `change_task_kind`, until Done or Dropped;
  - `change_task_description`, `change_task_plan` (its text and files to change) and `change_task_definition_of_done`, until the Task starts;
  - `change_task_priority`;
  - `drop_task`, with an optional Drop reason, Duplicate included ([Dropping](#dropping));
  - `archive_task` and `restore_task` ([Archive](#archive)).
- A Plan or a Definition of Done written this way is Not confirmed, as after the user's changing Save ([2.1.5](2.1.5-planning-and-start.md#plan-and-definition-of-done)).
- Each call is ruled by the person's [Authority](6-permissions-and-safety.md#authority) for Work › Task records, which can differ on their own work and on others' ([6 Authority by role](6-permissions-and-safety.md#authority-by-role)).

## Off-board Tasks

- An **Off-board Task** is a Task The Office makes and starts at once, kept off the Work board.
- There are two kinds: a Project's Onboard Task, titled "Onboard" ([2.1.1](2.1.1-projects.md#onboarding-a-project)), and its "Set up the run environment" Task ([Setting up the run environment](#setting-up-the-run-environment)).
- It is still a Task: its page, worktree, Stages, Verify, Decisions, Pause, Stop, Resume and Drop, its commit message and Publish (branch, pull request, merge rules) are any Task's.
- Where the spec or the screens say "without a Task" of these, it means no Ready step for the user, no Start and no board card, never no record.
- The Office writes and confirms its Plan and Definition of Done and gives it its built-in Pipeline; it is a Chore ([New Tasks are Features](#new-tasks-are-features)).
- It is made by:
  - Onboard, and Onboard again, on the Project page ([2.1.1](2.1.1-projects.md#onboarding-a-project));
  - applying Devops' Project Proposal, which adds the Project, then makes its Onboard Task;
  - Set up run environment, on the Project page or as the Yes in Add a Project, when the base branch has no valid `.devcontainer/` ([Setting up the run environment](#setting-up-the-run-environment)).
- It goes through Start at once, as the user who asked, by the same start-or-queue as any Start ([2.1.5](2.1.5-planning-and-start.md#a-queue-for-start)).
  - Every limit holds: the desks, the Project limit, the person's Task limit, the usage caps and the fire alarm.
  - With no room it is Queued with its place, on Now's Queue, where Move up and Move to top work as for any queued Task.
  - It names no files to change, so it starts past any Overlap ([2.1.5](2.1.5-planning-and-start.md#overlaps-at-start)).
- A refused Start makes nothing, and the refusal shows under the button that asked.
  - After a Project Proposal is applied, a refused start keeps the Project, and its Onboarding card offers Onboard to try again.
- A Project has at most one open (neither Done nor Dropped) of each kind: asking again while one is in flight answers that one, and the Project page's card follows it in place of the button ([project-page.md](screens/project-page.md#following-an-off-board-task)).
- Routes: `POST /projects/:id/onboard`; `GET /projects/:id/off-board-tasks`, the latest of each kind with the earlier Onboard Tasks as history; `POST /projects/:id/run-environment/set-up` ([Setting up the run environment](#setting-up-the-run-environment)).
- **Failed** is a Stage out of tries with its out-of-tries Decision open, as for any Task, asked first of the holder of Asked first when a Stage runs out of tries (the CTO), then the user ([2.3.2](2.3.2-flows.md#who-is-asked)).
  - While the CTO has it, the Project page's card says so, with no Retry.
  - Once it is the user's, the card and Needs you show it as "Off-board Task failed", with the error, **Retry** (which answers the Decision with its first option, no guidance) and **Open the Decision** ([now.md](screens/now.md#needs-you)).
  - Any other Decision an Off-board Task opens is an ordinary Decision card.
- It creates no Bug Task on its own; an Agent's `propose_bug_task` in it stays a Bug Task Decision ([2.4.2](2.4.2-decisions.md#the-bug-task-decision)).
- Where it shows:
  - never in the Work board's columns, counts, tabs or search, nor in the Project page's Work tiles ([work-board.md](screens/work-board.md#board-columns));
  - on its Project's page, on the Onboarding or Run environment card;
  - on Now's Running and Queue, with an "Off-board Task" badge ([now.md](screens/now.md#running));
  - in Activity, as its own kind ([2.14](2.14-activity.md#what-is-listed));
  - on its own Task page, with the "Off-board Task" badge and a note ([task-page.md](screens/task-page.md#head)).
- Stats and usage count it as a Task.
- Publishing and Conflict resolution Tasks aren't Off-board Tasks: they stay on the board.
- One made before Off-board Tasks started at once and still Ready waits for the user's Start, which its Project page's card offers; one already started goes on; a Done or Dropped one stays readable.

## Setting up the run environment

- **Set up run environment** turns the Project's Run environment On at once when its base branch has a valid `.devcontainer/` ([2.3.1](2.3.1-stages.md#script-stages-in-the-run-environment)).
- Otherwise it makes and starts the Project's "Set up the run environment" Off-board Task on the built-in Set up run environment Pipeline, whose Set up Stage names Onboards and repairs Projects (Devops by default), who writes the definition with `write_run_environment_definition` ([5.5](5.5-git-and-isolation.md#writing-the-run-environment-definition)).
- It runs its checks in its run environment even while the setting is Off ([2.3.1](2.3.1-stages.md#script-stages-in-the-run-environment)).
- Its Done turns the setting On when the `.devcontainer/` on its branch is valid; otherwise the setting stays as it was and the Project page says why.
- No other Task's Done or merged pull request changes the setting.
- While it runs it takes one of the Project's running slots, so with a Project limit of 1 another Task's Start queues behind it.
- `POST /projects/:id/run-environment/set-up` answers the Project's run environment and the start: started, queued with its place, the one already in flight, or refused.

## Defaults

### New Tasks are Features

- A new Task is a Feature unless its creator picks another Kind: in New Task, in Shape into a Task's menu, with `create_task`, or by the Kind a GitHub issue imports as.
- The Tasks The Office adds on its own (the Off-board Tasks, "Set up test targets" Tasks made before, Publishing and Conflict resolution Tasks) are Chores.
- A Bug Task created by a Bug Task Decision is a Bug.
- On the update that brought Kinds, every Task became a Feature, and those The Office made a Chore.

### Tasks of an Initiative still being shaped

- They wait in **Shaping**, the first state of a Task added to a shaping Initiative, by the user or the CTO.
- A Task added to an active Initiative, by the user or a Proposal, starts in Backlog.
- A Task in Shaping:
  - has no card on the Work board and isn't in its counts or its note of other Projects;
  - can't be planned, marked Ready, queued or started;
  - has a Plan, Definition of Done and Pipeline that can't be changed, except that it can be moved to another Project, which leaves it with no Pipeline and in Shaping ([Moving a Task](#moving-a-task));
  - has no session working on it, so a Thread it already has can be read but not continued until Confirm;
  - is still seen on the Initiative page and its own page, which says what it waits for, found by search and dropped, alone or with its Initiative ([An Initiative is done](2.1.4-initiatives.md#an-initiative-is-done));
  - still has its title, Description and dependencies changeable.
- Confirming the Initiative says its outcome and Task list are agreed, makes it active and moves its Tasks in Shaping to Backlog, in one step; nothing else makes that move.
- The one other move into Shaping is **Back to Shaping** on an active Initiative, from Backlog, Planning or Ready ([2.1.4](2.1.4-initiatives.md#back-to-shaping)).

### Archive

- The user archives a Done or Dropped Task, and whoever creates Tasks in a Thread with `archive_task`; any other Task is refused.
- Done and Dropped Tasks are also archived automatically once finished for the **Archive period**: a number of days set Office-wide in Settings › Office limits, 30 until changed; Tasks already finished longer ago than that are archived at the first run.
- **Archived** is not a state: the Task stays Done or Dropped, so dependencies, Initiatives and Usage estimates read it as any Done or Dropped Task.
- An archived Task leaves the Work board, its counts and its lists, and shows in a view of archived Tasks.
- Its page and Threads stay readable, read-only as for any Done or Dropped Task ([2.4](2.4-conversations.md)).
- The top bar's search finds it; the Work board's can't, as it has no card there.
- Its Initiative's page still shows it.
- **Restore**, one click or `restore_task`, returns it to the board in the state it had, and it gets a full period again from that moment.
- Initiatives are archived the same way:
  - a Done or Dropped Initiative is archived by Archive in its More menu or `archive_initiative`, or automatically once it has ended for the same Archive period, counted from when it became Done or Dropped or was last restored;
  - Initiatives that ended longer ago than the period are archived at the first run, and so are those whose end nothing dates;
  - an archived Initiative stays Done or Dropped, leaves the Initiatives tab's board and shows in the Archived tab beside the archived Tasks;
  - its page and Threads stay readable, and the Work board still names its Tasks by it;
  - Restore, or `restore_initiative`, returns it to Done or Dropped on the board.

### Moving a Task

- **Move** on the Task page puts a Task in another Project.
- It is refused with the reason:
  - once the Task has ever entered Planning, has started or has a worktree in its Project;
  - for an Off-board Task, which belongs to its Project;
  - for a Dropped Task, which is reopened instead ([Reopen](#reopen));
  - for a "Set up test targets" Task made before, a Publishing and a Conflict resolution Task, as for an Off-board Task.
- A moved Task has no Pipeline until one is chosen there, as the new Project's commands differ.
- It keeps its Initiative, dependencies, Attachments and Threads.
- It returns to Backlog with its Plan and Definition of Done Not confirmed.
- A Ready Task leaves Ready and the queue in the same save, as a changing Save takes one, though to Backlog, since a Task that can move was never in Planning.
- A Task in Shaping stays in Shaping instead, and goes to Backlog only by Confirm.
- The move is kept in the Task's record, and an Initiative's Projects follow from its Tasks.
- Moving a Task of an Initiative into a Project the Initiative doesn't span yet gives that Project no Pipeline: it starts with None, so no Initiative's branch is made there and no command is checked, until the CTO's Proposal gives it one ([An Initiative's Pipeline](2.1.4-initiatives.md#an-initiatives-pipeline)).
- A Project the Initiative stops spanning keeps its branch.

### A Dropped blocker

- It no longer blocks.
- The Task that waited for it still lists it, marked as dropped.

### Tags

- Tags are on Tasks only.
- The user sets them on the Task page and in "New Task", and the Planner while planning.

### Conflict resolution Tasks

- Resolve conflicts on a pull request with conflicts makes a Task "Resolve conflicts: <Task>" for the Task that opened the pull request.
- It is Ready on the built-in **Resolve conflicts** Pipeline, with its Plan and Definition of Done written by The Office and confirmed, and it starts at once.
  - Task limits queue it like any Start; when Start refuses it stays Ready and the page says why.
- At most one is open for a Task: pressing again shows the open one.
- It never joins an Initiative and can't be moved to another Project.
- It records its original Task, which lists "Conflicts resolved by: <Task> (<state>)" in its linked records; the Conflict resolution Task lists "Resolves the conflicts of: <Task> (<state>)".
- Dropping it aborts a merge left in its worktree, removes the worktree and leaves the branch as its last commit.
