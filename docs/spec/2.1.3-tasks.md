# 2.1.3 Tasks

Covers: Task, Task kind, bug details, Task states, Ready, Mark Ready, Title, Description, Commit message, Dependencies, Drop reason, GitHub issue, joining and leaving an Initiative, priority and order, who did what, Archive, Moving a Task, Conflict resolution Tasks.

## Task

- One unit of work in one Project, done when its **Definition of Done** is met: a published change, an Attachment, or both.
- Its Plan and Definition of Done are in [2.1.4](2.1.5-planning-and-start.md#plan-and-definition-of-done).

## Task kind

- Every Task has a **Kind**: **Feature** (new or changed behaviour), **Bug** (something that doesn't work as it should) or **Chore** (upkeep such as an update or a clean-up).
- Which Kind a new Task starts as: [New Tasks are Features](#new-tasks-are-features).
- The user changes it on the Task page, and the Planner with the Office action `write_kind`, in any state until Done or Dropped; a Done or Dropped Task is refused: "A Task keeps its Kind once it is Done or Dropped."
- A change of Kind never moves the Task, so a Ready Task stays Ready.
- The Kind names the commit type the Planner suggests: Feature `feat`, Bug `fix`, Chore `chore` ([2.5](2.5-context-policy.md#the-brief)).
- It picks the Pipeline proposed first, when the Project gives the Kind a default of its own ([2.1.1](2.1.1-projects.md#project-settings)).
- The Work board filters by it and its search finds it by its word ([2.1.6](2.1.6-board-and-search.md#search)).

## Bug details

- A Bug has three linked records of its own, each optional:
  - **Caused by**: the Task whose change brought the Bug in, any other Task in any Project and state, Done and archived ones too; the other Task lists it under "Caused bugs"; a Task can't be caused by itself;
  - **Found in version**: the release the Bug was seen in, one of the Project's `v*` tags or free text, 1 to 64 characters;
  - **Found while working on**: the Task whose Agent proposed the Bug Task, set only when a Bug Task Decision creates it ([2.4.2](2.4.2-decisions.md#the-bug-task-decision)), and never changed.
- The user changes Caused by and Found in version on the Task page, and the Planner with `write_bug_details`, until the Task is Done or Dropped, never moving it.
- They show only on a Bug; changing the Kind away keeps them, hidden, so changing it back loses nothing.

## Task states

- **Backlog → Planning → Ready → In progress → Done.**
- Side states: **Waiting on you** and **Paused**.
- Exit: **Dropped**.
- Before Backlog: **Shaping**, for a Task of an Initiative still being shaped ([Tasks of an Initiative still being shaped](#tasks-of-an-initiative-still-being-shaped)).
- In progress shows the current Stage.
- Done or Dropped disconnects the Task's Connected devices ([2.13](2.13-connected-devices.md#lifecycle)).
- Work moves forward. The two ways back:
  - a change to the Plan, the Definition of Done or the Pipeline proposal of a Ready Task that hasn't started, by the user's **Save** or by the Planner, takes it back to **Planning** to be marked Ready again ([2.1.4](2.1.5-planning-and-start.md#changing-a-ready-task));
  - a **Move** of a Ready Task to another Project ([Moving a Task](#moving-a-task)).

## Ready

- Ready requires all of:
  - a Plan and a Definition of Done, both confirmed by the user, or by auto mode on their behalf ([2.1.4](2.1.5-planning-and-start.md#auto-mode)), or confirmed as they stand, even empty, by the user's Mark Ready without them ([Mark Ready](#mark-ready));
  - no Pipeline proposal left open;
  - no Decision on the Task left open;
  - a Pipeline.
- A Task has no Pipeline until one is chosen: from the Planner's proposal confirmed by the user or by auto mode, or by the user.
- Until then its page shows a placeholder where the Stages will be.
- A new Task doesn't take its Project's default Pipeline, nor its Kind's ([2.1.1](2.1.1-projects.md#project-settings)).

## Mark Ready

- **Planning is optional:** a Task whose Plan and Definition of Done were written by the user or given with the Task, and confirmed by the user, goes from Backlog straight to Ready by **Mark Ready**, under Ready's other rules.
- Mark Ready shows in Backlog and Planning once a Pipeline is chosen, which the user does there on the Pipeline rail, and no Decision on the Task is open.
- Its checklist names "Choose a Pipeline" while there is none.
- The user may **Mark Ready without a confirmed Plan or Definition of Done:**
  - Mark Ready then asks first in a dialog naming what is missing (a Plan or a Definition of Done not written, or written and not confirmed);
  - going on confirms both as they stand, even empty, by that user, in the same change that moves the Task to Ready;
  - the Pipeline and open Decision conditions still hold.

## Title

- A Task's title can be changed in any state except Done and Dropped, by the user on the Task page ([Task page › Head](screens/task-page.md#head)).
- A Done or Dropped Task is refused: "A Task keeps its title once it is Done or Dropped."

## Description

- What the user wants, in their own words.
- Optional; written in "New Task" (the top bar's Create › Task) under the title, and edited on the Task page, where it sits above the Plan.
- The CTO writes one on an Initiative's Tasks too, by their changes ([The CTO's changes to an Initiative](2.1.4-initiatives.md#the-ctos-changes-to-an-initiative)).
- It is part of the Planner's Brief and of every Agent Stage's Brief ([2.5](2.5-context-policy.md)); with none, the title alone is enough to plan from.
- It can mention a Task, Initiative, open Decision or Idea, picked with `@` as in the chat or pasted as the link to its page; it is saved as a Markdown link to the record's page and shown on the Task page as the record's chip.
- "New Task" also takes optional Attachments, files or links, added to the Task in the order chosen once it is added; if one can't be, trying again adds only those left, never the Task a second time.

## Commit message

- A Task holds the message of the one commit Publish lands it as, following the commit convention its Project's own docs define.
- The Planner suggests it with the Plan, and every Agent Stage may update it.
- The user edits it on the Task page in any state until Publish lands it or the Task is Done or Dropped.
- It never moves the Task, so a Ready Task stays Ready.
- With none written, Publish uses the title with a short summary below it ([2.3](2.3.4-publish.md#the-tasks-commit-message), "The Task's commit message").

## Dependencies

- A dependency can be on any Task in any Initiative or Project.
- A blocked Task cannot start, but can be queued until its blockers are Done or Dropped.
- They are set before the Task starts, never on an Archived Task, and never closing a cycle.
- The user adds and removes them on the Task's page, whose Add window leaves Archived Tasks out; whoever shapes Initiatives or holds Plans does with the Office actions `add_dependency` and `remove_dependency`.
- A Task waits directly only for Tasks it doesn't already wait for through another Task: if C waits for B and B waits for A, C doesn't wait for A directly.
- Every way a dependency is added follows this: the user's, `add_dependency`, a new Task's waiting list (`create_task`, an Initiative's added Task) and an Initiative's Proposals.
  - A wait the Task already has through another Task is left out, and `add_dependency`'s answer says through which Task.
  - Otherwise the new wait takes out the direct waits it covers, on the Task itself and on every not-started Task that waits for it, and the answer names each.
  - A new Task waits directly only for those of its blockers no other of them waits for.
- Started Tasks keep their dependencies.
- A Publishing Task, which waits for every Task of its Initiative by design, keeps its own.
- A wait through a Publishing Task, or through a Task Done or Dropped, doesn't count.
- Redundant waits are not cleaned up on their own; they go when the Task's dependencies next change this way.

## Drop reason

- The user may say why a Task is Dropped, in the Drop window and in a Gate's Drop step; the reason is optional.
- It is one of: **Won't fix**; **Duplicate**, naming the other Task, any Task but this one in any Project and state; **Can't reproduce**; **Other**, with the user's words, 1 to 500 characters.
- It is kept with the move to Dropped, in the same change.
- The Task page and the Archived tab show it; a Duplicate's other Task lists this one under "Duplicates".
- Dropping an Initiative drops its open Tasks with no reason.
- With its Project's switch on, a Task made from a GitHub issue closes the issue with the reason ([2.1.1](2.1.1-projects.md#github-issues)).

## GitHub issue

- A Task made from a GitHub issue lists the issue in its linked records: its state, number and title, its author, and who imported it and when.
- Importing, the issue's state and what The Office writes back on GitHub: [GitHub issues](2.1.1-projects.md#github-issues).

## Joining and leaving an Initiative

- A Task is in at most one Initiative, and joins or leaves one only before it starts.
- One The Office made (an Onboard, a run environment set-up, a test targets set-up, a Conflict resolution or a Publishing Task) never does.
- The user adds a Task to an Initiative, or takes it out, on the Task's page and on the Initiative's page (Add an existing Task, Take out a Task); whoever shapes Initiatives or holds Plans does with the Office actions `add_to_initiative` and `take_out_of_initiative`.
- A Task joins an Initiative being shaped only from Backlog, moving to Shaping, and an active one keeping its state; a done or dropped Initiative takes none.
- Taking a Task out moves one in Shaping to Backlog, and one planned in the Initiative's planning Thread loses it: from Planning it goes to Backlog, as a changing Save does with no planning Thread, and a Ready one stays Ready.
- The Publishing Task in its Project waits for a Task that joins and stops waiting for one taken out; its other dependencies stay.
- Joining is refused once the Task has a worktree and the Initiative has a Pipeline in its Project (the worktree came from the base branch), and leaving once its worktree came from the Initiative's branch.
- Each move is kept in the Task's state changes, named by who made it.

## Priority and order

- Three priority levels plus manual order per Project.
- Tags, full-text search and saved views: [2.1.8](2.1.6-board-and-search.md#search).
- Archive: [Archive](#archive).

## Who did what

- Every record that says the user did something names which user ([2.10](2.10-users-and-signing-in.md)): who captured an Idea, created a Task or an Initiative, started a Task or moved it from one state to another (its state changes say "by Ana" where they said "by the user"), passed or sent back a Gate, attached an Attachment, and changed a setting (a Role card's version, a Pipeline, a Project's settings, the Office instructions, any Office setting).
- Work an Agent or The Office did still names the person or The Office.
- A Task can be **created by The Office**: a Bug Task made by Create the Bug Task ([2.4.2](2.4.2-decisions.md#the-bug-task-decision)) and a Task the auto-import made from a GitHub issue ([GitHub issues](2.1.1-projects.md#github-issues)); a Task imported by hand names the user who imported it.

## Defaults

### New Tasks are Features

- A new Task is a Feature unless its creator picks another Kind: in New Task, in Shape into a Task's menu, with `create_task`, or by the Kind a GitHub issue imports as.
- The Tasks The Office adds on its own (Onboard, run environment set-up, test targets set-up, Publishing and Conflict resolution Tasks) are Chores.
- A Bug Task created by a Bug Task Decision is a Bug.
- On the update that brought Kinds, every Task became a Feature, and those The Office made a Chore.

### Tasks of an Initiative still being shaped

- They wait in **Shaping**, the first state of a Task added to a shaping Initiative, by the user or the CTO.
- A Task added to an active Initiative, by the user or a Proposal, starts in Backlog.
- A Task in Shaping:
  - has no card on the Work board and isn't in its counts or its note of other Projects;
  - can't be planned, marked Ready, queued or started;
  - has a Plan, Definition of Done and Pipeline that can't be changed, except that it can be moved to another Project, which leaves it with no Pipeline and in Shaping ([Moving a Task](#moving-a-task));
  - has no session working on it, so a Thread it already has can be read but not continued until Confirm;
  - is still seen on the Initiative page and its own page, which says what it waits for, found by search and dropped, alone or with its Initiative ([An Initiative is done](2.1.4-initiatives.md#an-initiative-is-done));
  - still has its title, Description and dependencies changeable.
- Confirming the Initiative says its outcome and Task list are agreed, makes it active and moves its Tasks in Shaping to Backlog, in one step; nothing else makes that move.
- The one other move into Shaping is **Back to Shaping** on an active Initiative, from Backlog, Planning or Ready ([2.1.4](2.1.4-initiatives.md#back-to-shaping)).

### Archive

- The user archives a Done or Dropped Task.
- Done and Dropped Tasks are also archived automatically once finished for the **Archive period**: a number of days set Office-wide in Settings › Office limits, 30 until changed; Tasks already finished longer ago than that are archived at the first run.
- **Archived** is not a state: the Task stays Done or Dropped, so dependencies, Initiatives and Usage estimates read it as any Done or Dropped Task.
- An archived Task leaves the Work board, its counts and its lists, and shows in a view of archived Tasks.
- Its page and Threads stay readable, read-only as for any Done or Dropped Task ([2.4](2.4-conversations.md)).
- The top bar's search finds it; the Work board's can't, as it has no card there.
- Its Initiative's page still shows it.
- **Restore**, one click, returns it to the board in the state it had, and it gets a full period again from that moment.
- Initiatives are archived the same way:
  - a Done or Dropped Initiative is archived by Archive in its More menu, or automatically once it has ended for the same Archive period, counted from when it became Done or Dropped or was last restored;
  - Initiatives that ended longer ago than the period are archived at the first run, and so are those whose end nothing dates;
  - an archived Initiative stays Done or Dropped, leaves the Initiatives tab's board and shows in the Archived tab beside the archived Tasks;
  - its page and Threads stay readable, and the Work board still names its Tasks by it;
  - Restore returns it to Done or Dropped on the board.

### Moving a Task

- **Move** on the Task page puts a Task in another Project.
- It is refused with the reason:
  - once the Task has ever entered Planning, has started or has a worktree in its Project;
  - for an Onboard Task, which belongs to its Project;
  - for a Dropped Task, as returning to Backlog would undo the Drop;
  - for a run environment set-up, a test targets set-up, a Publishing and a Conflict resolution Task, as for an Onboard Task.
- A moved Task has no Pipeline until one is chosen there, as the new Project's commands differ.
- It keeps its Initiative, dependencies, Attachments and Threads.
- It returns to Backlog with its Plan and Definition of Done Not confirmed.
- A Ready Task leaves Ready and the queue in the same save, as a changing Save takes one, though to Backlog, since a Task that can move was never in Planning.
- A Task in Shaping stays in Shaping instead, and goes to Backlog only by Confirm.
- The move is kept in the Task's record, and an Initiative's Projects follow from its Tasks.
- Moving a Task of an Initiative into a Project the Initiative doesn't span yet gives that Project no Pipeline: it starts with None, so no Initiative's branch is made there and no command is checked, until the CTO's Proposal gives it one ([An Initiative's Pipeline](2.1.4-initiatives.md#an-initiatives-pipeline)).
- A Project the Initiative stops spanning keeps its branch.

### A Dropped blocker

- It no longer blocks.
- The Task that waited for it still lists it, marked as dropped.

### Tags

- Tags are on Tasks only.
- The user sets them on the Task page and in "New Task", and the Planner while planning.

### Conflict resolution Tasks

- Resolve conflicts on a pull request with conflicts makes a Task "Resolve conflicts: <Task>" for the Task that opened the pull request, as The Office makes an Onboard Task.
- It is Ready on the built-in **Resolve conflicts** Pipeline, with its Plan and Definition of Done written by The Office and confirmed, and it starts at once.
  - Task limits queue it like any Start; when Start refuses it stays Ready and the page says why.
- At most one is open for a Task: pressing again shows the open one.
- It never joins an Initiative and can't be moved to another Project.
- It records its original Task, which lists "Conflicts resolved by: <Task> (<state>)" in its linked records; the Conflict resolution Task lists "Resolves the conflicts of: <Task> (<state>)".
- Dropping it aborts a merge left in its worktree, removes the worktree and leaves the branch as its last commit.
