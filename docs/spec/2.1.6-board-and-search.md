# 2.1.6 Board and search

Covers: organisation, the Kind filter, the board's Done column, Initiative blocks, Tags, search, Saved views, the Project filter, Group by Initiative, the Pull requests tab, the CI tab.

## Organisation

- Three priority levels plus manual order per Project; Tags; full-text search; Saved views; **Archive** ([2.1.3](2.1.3-tasks.md#archive)).
- Tags are on Tasks only ([2.1.3](2.1.3-tasks.md#tags)).
- Moving a Task to another Project: [2.1.3](2.1.3-tasks.md#moving-a-task).

## The Kind filter

- Each card shows its Task's Kind ([2.1.3](2.1.3-tasks.md#task-kind)), Done cards too.
- The board filters by one Kind at a time: Feature, Bug or Chore, kept in its address as `kind`.
- A Saved view keeps it; a view saved before Kinds has none and shows every Kind.
- Import issues… on the board's filter bar makes Tasks from GitHub issues, as on the Project page ([2.1.1](2.1.1-projects.md#github-issues)).

## The board's Done column

- Its Done and Dropped Tasks show the one that ended last on top, ungrouped and grouped by Initiative alike.
- A Task's end is its last move to Done or Dropped; one whose end was never recorded follows the dated ones in the board's order (priority, then manual order).
- Every other column keeps the board's order.

## Initiative blocks

- Design: [its design](../design/board-initiative-blocks.html).
- With Group by Initiative off, each column gathers an Initiative's cards into one block headed by its name, placed where its first card falls in the column's order, its cards in that order (in Queued its head names their places).
- Tasks with no Initiative stay outside the blocks, in their place.
- While the Initiative filter is set, the columns show no blocks.
- A card is dragged only within its block, or among the cards outside the blocks.

## Defaults

### Search

- Search is two boxes over one full-text search:
  - the Work board's narrows Tasks by title, Plan, Definition of Done, Tags and the Kind's word, so "bug" finds Bug Tasks;
  - the top bar's (⌘K) finds Tasks (by their Kind's word too), Initiatives, Ideas, people and document Attachments and opens the one picked.
- Both follow the Project filter and say how many more matches are in other Projects.
- Both also find a record by its ID: typed whole or by its first 8 characters or more, or as a pasted link to its page, it finds that Task (and, in the top bar, that Idea or Initiative) and lists it first, ahead of the records whose text matches.
- An archived Task is found by the top bar's search, not the board's ([2.1.3](2.1.3-tasks.md#archive)).

### Saved views and the Project filter

- Saved views are stored by The Office and never hold the Project filter.
- The Project filter is remembered per browser, so two browsers can show different Projects.

### Group by Initiative

- Design: [its design](../design/board-by-initiative.html).
- A switch at the end of the Work board's filter bar lays the board out in a group per Initiative with a card on the board, newest first with the Active ones before those that ended, then No Initiative last.
- Each group has:
  - a header: its name as a fold, its state, its Projects, its progress over every Task of the Initiative, how many of its cards show, and a link to the Initiative;
  - its Tasks in the state columns, under column heads shown once.
- The switch is remembered in this browser and also kept in the board's address (`?group=initiative`) apart from the filters:
  - a board opened without `group` in its address is grouped as last chosen here;
  - a Saved view never holds it;
  - Clear leaves it.
- A group's fold is remembered in this browser, a Done or Dropped Initiative's starting folded.
- The Initiative filter shows its group alone, saying why when it has no card; the other filters leave out a group with no card shown, naming those search, Priority and Blocked left out.
- A card drags only within its column inside its own group: the board never changes a Task's Initiative.
- With the switch off, the columns show each Initiative's cards in a block ([Initiative blocks](#initiative-blocks)).

### The Pull requests tab

- At `/work/pull-requests`, beside Tasks, Ideas, Initiatives and Archived.
- It lists each open pull request The Office opened ([2.3](2.3-pipelines.md#defaults)): `#number title` linking to GitHub, its Task, its Project, branch → base, then:
  - **Checks**: Passing, Failing, Running, No checks, Can't read;
  - **Mergeable**: Can merge, Conflicts, Checking…;
  - **Checked**: the time since the last read, or "Out of date" when it is stale.
- Each row has **Merge…** and **Close…**, each opening a dialog.
- A row whose Mergeable is Conflicts also has **Resolve conflicts** ([2.3](2.3-pipelines.md#defaults); [Conflict resolution Tasks](2.1.3-tasks.md#conflict-resolution-tasks)); while a Conflict resolution Task is open the row says "Resolving: <Task> (<state>)" with a link to it.
- **Refresh** reads them now.
- Problems show as Alerts.
- The top bar's Project filter narrows the list.
- When the App lacks permissions, a prompt at the top says which, as in Settings › Office identity.

### The CI tab

- At `/work/ci`, after Pull requests.
- It lists each Project's recent CI runs on its code host, up to 30 per Project, newest first. A row has:
  - a status: Queued, Waiting, Running, Succeeded, Failed, Cancelled, Skipped or Unknown (the same words for any code host);
  - `Workflow #number · title` linking to the run's logs on GitHub (with its attempt after a re-run);
  - its Project;
  - its branch (with a link to the Task for an `office/<task id>` branch);
  - its short commit;
  - what triggered it and when it started.
- The top bar's Project filter narrows the list, with the note on runs in other Projects; a Project page's Overview links to its CI runs.
- A failed or cancelled run has **Re-run all jobs** and **Re-run failed jobs**; a re-run the code host refuses shows its refusal in the row.
- **Refresh** lists them now.
- The list also refreshes by itself: every 15 seconds for a Project with a run queued, waiting or running, every minute otherwise, with one conditional request per repository.
- With no GitHub token valid now nothing is asked and the runs show as Out of date; when GitHub can't be reached or refuses to read Actions, the last runs stay and an Alert says why.
- Runs are the code host's records: The Office keeps them in memory only.
- The permission prompt is the Pull requests tab's.
- **Start a workflow** starts a Workflow by hand:
  - choose the Project (preset when the filter narrows to one);
  - choose a branch or tag from the repository's, in a searchable list with tags marked, the Project's base branch first chosen;
  - choose one of the active Workflows whose file there declares a start by hand (GitHub's `workflow_dispatch`);
  - the form then shows one control per input the file declares (text and environment a text field, yes-no a switch, choice a list of its options, number a number field), each with its description, its default filled in and the required ones marked;
  - **Start** stays off until every required one has a value.
- Inputs go to the code host as text.
  - An undeclared input, a missing required one, a choice outside its options, a yes-no that isn't true or false or a number that isn't one is refused in plain words before the code host is asked.
  - A start the code host refuses shows its refusal in the dialog.
- The new run shows in the list as soon as the code host lists it, as its Project is listed again at once and every 15 seconds for a minute.
- Agents start one with the Office action `start_workflow`.
- With no GitHub token valid now, the dialog says so and lists nothing.
