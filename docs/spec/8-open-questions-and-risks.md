# 8. Open questions and risks

## Open questions, by the tier that needs them

None blocks tier 1. Each becomes a ticket when its tier starts.

- **Tier 2:** the form of shared memory and how the user reads and edits it; whether Tasks of an Initiative still being shaped can be planned and started; whether the Office Manager can be let go; folding a Proposal's Role card in chat.
- **Tier 3:** usage estimates are a Task's at Start only, for its whole Pipeline, in the measures the user ticks Office-wide from tokens, the 5-hour window, the 7-day window and cost in dollars, cost priced by Model prices set per model; each is the median of done Tasks' Stage runs for the same Project and Pipeline, Stage by Stage, summed, and below 3 done Tasks the Planner's token estimate in the Plan; Window caps and Daily caps on tokens and dollars are per account for the Claude Code engines, one set for the OpenAI-compatible API, and a Start that would pass one waits in the queue until it resets, starting anyway when every exceeded cap resets within the prompt cache's hour (the user, 2026-11-01, settling 2026-10-31's "what is estimated set Office-wide by the user"); the API-based engine, on the OpenAI-compatible API, is The Office's own agent loop: it runs each tool call itself after the Office rules judge it, lists and loads skills, and keeps the Context policy; its endpoints and models are set Office-wide, and any Role may pick it, refused only what the engine cannot do (the user, 2026-10-31); MCP servers for Agents come from an Office-wide library, each reviewed before use, assigned on the Role card, with per-Project values, and every tool of theirs starts at Consult in the permission profiles (the user, 2026-10-31); chat apps, WhatsApp first (the user, 2026-10-31); adding a Project from a git repository as well as by path: any https or ssh git URL is cloned into the Office data directory, and GitHub gets a picker of the user's repositories; private repositories through Sign in with GitHub, a GitHub App the user registers and installs once, signed in through the browser by GitHub's web flow (the user, 2026-11-01, replacing the device flow), its user token refreshed by The Office and never seen by Agents; once signed in, every GitHub Project (those added by path too) fetches, pushes and opens pull requests with it; Add Project takes a URL or a pick, and Devops' onboarding Proposal may name a repository URL (the user, 2026-10-31). The Office's git uses only the Office identity, never the user's own credentials: the GitHub sign-in and an Office ssh key The Office generates, whose public half the user adds to GitHub or another host; other hosts over https are reached anonymously, public repositories only; the GitHub App is registered by its manifest from Settings (the user, 2026-11-01, replacing "other hosts keep the machine's credentials"). Engines are a list the user adds to (the user, 2026-11-01): Claude Code is one kind, one engine per account, each with its own config folder and a simple sign-in, the `-p` fallback an option of it; each OpenAI-compatible endpoint is another. Every level names an engine and a model, each engine with a default model; the one a session runs on comes from a cascade, the most specific winning: the Office default, then the Project default, then the Office-wide Role override, then the Project's Role override; a Project may force its default on every Role in it, so Office-wide Role overrides skip it while its own Role overrides still apply; a Stage's own model stays the last word. The Role card shows the engine that applies and where it comes from. Threads without a Project use the Office levels only. Removing an engine moves every reference to a replacement the user picks, or to none when it is the only one, and then nothing runs until one is added; a running session finishes on the old engine and its Thread starts fresh; Stage runs keep the name they ran on. Whatever the cascade lands on must pass the capability check the Role card has today.

## Risks

- **Subscription terms** for programmatic use are being revised; a 24/7 multi-agent office is a gray zone under "ordinary, individual usage". Mitigation: the engine boundary, pinned versions, the `-p` fallback in tier 2 ([02](../../.scratch/the-office/issues/02-agent-engines.md)).
- **Undocumented internals:** the skills allowlist's suffix matching and plugin detection were read from the binary, and the permission behaviour comes from docs fetched as summaries. Re-check on every version bump; the spike checks them first.
- **No sandbox** (none on native Windows, none used on Linux): an Agent's shell can read and write outside the worktree; installs and outside publishing rest on Agents following rules. Backstops: per-Stage commits, the HEAD check, the Office tools.
- **Quota:** parallel sessions spend quota about N times as fast, and plan windows are account-wide, so per-session quota is only an estimate.
- **The PowerShell tool is a preview** with its own rule quirks.
- **Cache:** a Decision answered after more than an hour resumes on a cold cache; the label shows it, and the Context policy may start fresh.
