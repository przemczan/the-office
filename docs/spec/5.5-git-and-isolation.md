# 5.5 Git and isolation

- **A worktree per Task** at a stable path under the Office data directory; The Office owns every git change: branch and worktree creation, a commit per Stage (message from the Stage result and handover note), worktree restore after each test run (a run of any command of kind test, whatever its key, which also re-runs once on failure and moves the files it wrote out of the worktree; build and lint commands get none of it), discarding an interrupted Stage's uncommitted edits, push and PR or merge at Publish. A Task of an Initiative in a Project where it has a Pipeline makes its branch from the Initiative's branch, fetched first, whether its worktree is made at Planning or at Start, and a Publishing Task's worktree holds the Initiative's branch itself; The Office makes the Initiative's branch, merges into it and pushes it, and never deletes it (Defaults below, "The Initiative's branch").
- **Guards:** a git-mutation deny list for Agents plus a HEAD and branch check after every Stage, since command patterns can be bypassed, and before every Stage, where a move along the base is taken as it is and any other asks the user ([2.3](2.3-pipelines.md#defaults), "A branch moved outside The Office").
- **Environment as data:** the Project's environment (`set`, `unset`, `prependPath`) is stored outside the checkout and applied to every command and Agent; the environment check runs in a fresh worktree of the base branch before it is saved: the install, then every command of the Project in its list's order, each shown by its name and skipped when its line is blank.
- **Secret variables:** a variable in `set` may be a Secret variable, edited in its own list on the Environment block. Its value is one line of at least 6 characters, so hiding it can't hide ordinary text, and a name is plain or secret, never both. Once saved, it is kept in the database and never sent back: the Project API, the environment check API and every event give its name and whether a value is set; a save that leaves the value empty keeps the one kept (the last check's try, else the Project's). It is given as the other variables are:
  - to host commands and to the sessions of the Project's Tasks, in their environment;
  - in a run environment, to `compose exec` by name alone: each `set` value travels in the compose CLI's own environment under a carrier name (`OFFICE_VARIABLE_<n>`, so a Project's `PATH` or `DOCKER_HOST` can't change how the CLI runs), passed as `--env OFFICE_VARIABLE_<n>`, and the script takes it back under its own name; no value is in a command line or the script;
  - to the install as the run environment's image builds, every `set` variable as a BuildKit secret (`RUN --mount=type=secret,id=…,env=NAME`), so no value lands in a layer, the image's history or a build argument. The image's key takes plain variables by name and value and Secret variables by name alone.
  Wherever it would show, it shows as `[secret NAME]`: in each command's recorded and streamed output (stage runs, the environment check, the `run_project_command` answer and its output file, on the host and in a run environment, a value cut across chunks included), and in what a session writes into a Thread: an Agent's text and its tool calls' summaries, before they are stored or sent live. Left out: the engine's own transcript files, and the tool results the model reads; an Agent that prints a value sees it (spec §6).

## Defaults

Gaps no ticket settled, filled with the simplest choice consistent with the tickets and accepted by the user; each says when.

- **Install inputs:** a Project lists the files whose change makes a worktree install again (a lockfile, say), given when it is added and edited on its page beside the install command. A worktree installs when it is created and again when the install command or one of those files changes; with none listed, once. (added while building tier 1, accepted 2026-10-25)
- **The base branch's upstream** is where the freshly fetched base comes from: worktrees start at the remote branch it tracks, fetched first. A base branch that tracks nothing is used as it is, unfetched, and the environment check says so. (added while building tier 1, accepted 2026-10-25) A Task of an Initiative in a Project where it has a Pipeline starts at the Initiative's branch instead, fetched first (amended 2026-11-12; amended 2026-11-13).
- **Clones** (tier 3): a Project added by Repository URL is cloned, in full, into `<office-data>/repositories/<host>/<owner>/<repo>`, so a second add of the same URL is caught; the clone runs in the background with its progress shown, and a folder left by a failed add is reused. (the user, 2026-11-01)
- **The Office identity** (tier 3, the user's answer of 2026-11-01): every git command The Office runs, for a Project (added by path too) or not (a Skill's Source, Devops reading a URL), uses only The Office's own credentials, shared by all Projects and separate from the user's:
  - a GitHub https remote: the Sign in with GitHub user token, handed to git for that one command by a credential helper Office code answers; never in an environment variable, a remote URL, a git config file or a command line, which hooks, filters and Agents could read;
  - an ssh remote, on any host: the Office ssh key alone, generated and kept by The Office in its data directory, its public half shown in Settings, hidden until the user shows it, for the user to add to the host; the user can regenerate it in Settings after confirming its consequences (the current key is gone for good, and every ssh host refuses The Office until the new public half is added there), and a failed regeneration keeps the current key; ssh runs with no agent, none of the user's ssh config or keys, and The Office's own known hosts: GitHub's host keys from GitHub's published list, any other host's key trusted only once the user confirms its fingerprint;
  - any other https remote: anonymously, so public repositories only.

  git is kept from the user's credentials: their credential helpers are cleared for every command, and git never prompts (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`). Every Office git command runs with a home folder of The Office's own, so neither curl nor git-lfs can read the user's `~/.netrc`; the user's global git config still applies, through an Office global config file (`GIT_CONFIG_GLOBAL`) that includes their XDG `git/config` and `~/.gitconfig` by absolute path, and `XDG_CONFIG_HOME` stays theirs, so their global ignore and attributes files apply too. A `~` in the user's config then means The Office's home folder. Office git never sends the Windows sign-in: `http.emptyAuth` is off, without which curl has no user name to answer a 401 with NTLM or Negotiate, and git's own default would turn it on once a 401 offers NTLM; no git setting turns those methods off on the pinned git. `KRB5CCNAME` names a credential cache that doesn't exist, so on Linux neither curl nor git-lfs finds the user's Kerberos tickets. Known gap: git-lfs answers a server that offers Negotiate with the Windows sign-in (SSPI), whatever git's settings say, and no setting stops it (the user, 2026-11-01, replacing a home folder for git-lfs alone and Negotiate and NTLM off by a setting). Sign in with GitHub signs in by GitHub's web flow for an App's user token: the browser goes to GitHub's authorize page and comes back to The Office on localhost, at a callback URL the manifest names, with a code The Office exchanges with the App's client secret and PKCE. The client secret is kept like an API key, a database row never sent to the web; the App's private key and webhook secret are discarded (the user, 2026-11-01, replacing the device flow). A Project's page says which part of the identity its remote needs and what is missing. Pull requests are opened through GitHub's API with the token; without Sign in with GitHub there are none.
- **The CPU limit** of run environments (the user's answer of 2026-11-09), set Office-wide in Settings › Office limits, Automatic until changed: Automatic gives each run environment's checks' service this computer's cores less 2 (`os.availableParallelism()`, at least 1) and every other service, such as Postgres, 2, never more than the checks' service. Every run environment gets the same CPUs rather than a share of the cores, so one running Task uses the idle cores and two split them; no service gets `cpu_shares`, as the container runtime already weighs containers equally and an explicit 1024 would lower their cgroup v2 weight. Fixed gives every service one whole number, from 1 to this computer's cores, kept while Automatic is chosen, and held to the cores at a start on a computer with fewer. The limit is read as a run environment starts, so a change reaches a running one at its next start.
- **The other limits of run environments** (Task 231f6c70, 2026-11-10), set Office-wide in Settings › Office limits' Run environments card beside the CPU limit, each saved as it changes: Run environments at once (2 by default, 1 to 12), Memory per service (4096 MB by default, 512 MB to 65 536 MB in steps of 512 MB, shown in GB, with no swap above it) and Processes per service (1024 by default, 256 to 65 536 in steps of 256); the service refuses a value outside them, naming the field. Memory and processes, like the CPU limit, reach each run environment at its next start. Raising Run environments at once lets a Stage waiting for a run environment start at once; lowering it takes no slot from a running one, and new ones wait until fewer are running. When Run environments at once is below Running Tasks at once, the card says the running Tasks past it wait on their checks ("Waiting for a run environment").
- **The repository's git data in a run environment** (the user's ask in Task 27c293ac, 2026-11-12): a Task's run environment mounts the repository's shared git folder read-only at the path the worktree's `.git` file leads to, beside the worktree, so git in a check reads the worktree's history (`status`, `log`, `diff`) but can't commit, move a branch or write objects: every git change stays The Office's. The path comes from git run by The Office on the host, never from the worktree's `.git` file, which an Agent could point at any other folder.
- **Writing the run environment definition** (Task e6d52ce4, 2026-11-10): Agents write `.devcontainer/` only with the Office tool `write_run_environment_definition`, in an Agent Stage of a Role with the Run environment capability ([2.2](2.2-people.md), [6](6-permissions-and-safety.md)). The Agent gives each file whole, its path from the repository's root inside `.devcontainer/`; The Office reads the definition as it would at a check, the given files in place of the worktree's and any other file it names from the worktree, and writes the files only when it is valid, leaving the folder's other files. Otherwise, or for a path outside the folder, it writes nothing and answers every problem in the definition check's words. It builds and starts nothing. The built-in Set up Stage's brief and the set-up Task's Plan tell Devops to write with it.
- **The Initiative's branch** (2026-11-12, the Initiative 1116efba; details settled with the Plan of Task 12e9ab91): an Initiative has a branch named `initiative/<short name>` in each Project it spans where it has a Pipeline ([2.1](2.1-work.md#defaults)), and none in a Project with None (amended 2026-11-13, the Task "Implement initiatives pageredesign"). Its Short name is one for the whole Initiative, made once any of its Projects has a Pipeline. Its **Short name** is made from the title: accents dropped, lower-case a–z, 0–9 and `-`, at most 40 characters cut at a word; with nothing left, it is the first 8 characters of the Initiative's id. It is shown and editable while shaping and fixed at Confirm, and is unique Office-wide among Initiatives that have one, whatever their state: a derived name that is taken gets `-2`, `-3` and so on, and an edited name that is taken is refused, with the reason.
  - **Made:** Confirm makes the branch from the freshly fetched base in every Project the Initiative spans where it has a Pipeline. Confirm is refused, naming the Project and why, when a branch can't be made or already exists there, locally or on the remote; the branches that attempt made are removed again, since they hold nothing. A Project the Initiative comes to span after Confirm starts with None and gets no branch when the Task is added or moved there; it gets its branch when the CTO's Proposal, applied, gives it its first Pipeline, and applying it is refused, with the reason, when the branch can't be made (amended 2026-11-13).
  - **Pushed:** the branch lives on the base branch's remote whenever the base branch tracks one, pushed with the Office identity after each Publish into it and after each Stage of a Publishing Task ([2.3](2.3-pipelines.md#defaults)); otherwise it stays local.
  - **Kept:** The Office never deletes it, so it is kept when the Initiative is dropped or done. The user deletes it, and the Initiative page lists each one. Once it is gone, a Task that needs it is refused Start, or its Publish fails, naming the branch.
  - **Read by Threads:** the Initiative's Threads ([2.4](2.4-conversations.md)) read a detached, read-only checkout of it per Project, under `<office-data>/initiative-bases/<short name>/<project>`, refreshed as each session's first answer starts, as the base checkouts are.
