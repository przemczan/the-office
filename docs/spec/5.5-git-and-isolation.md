# 5.5 Git and isolation

Covers: worktree per Task, Office-owned git changes, guards, the Project's environment, Secret variables, the Office identity, run environments' limits, the Initiative's branch, a test instance's checkout, the build cache volume.

## A worktree per Task

- Each Task has a worktree at a stable path under the Office data directory.
- The Office owns every git change: branch and worktree creation, a commit per Stage (message from the Stage result and handover note), worktree restore after each test run, discarding a stopped Stage's uncommitted edits, push and PR or merge at Publish.
- Worktree restore after a test run applies to a run of any command of kind test, whatever its key; it also moves the files the run wrote out of the worktree; build and lint commands get none of it.
- A failed test command runs its re-run command in its place once, when it has one ([2.1.1](2.1.1-projects.md#the-re-run-command)); that second run is restored and its files moved out the same way, into `<stage run id>/2` beside the first run's `/1`.
- The restore keeps the files git ignores, so the re-run command finds what the first run wrote there.
- The uncommitted edits of a Stage the user stopped are discarded; a Pause, the fire alarm, a usage window and The Office restarting keep them.
- The Stage commits stay on the Task's branch as the detail of how the work was done.
- Publish lands the Task on its base, or its Initiative's branch, as one commit with the Task's commit message; a pull request is titled and worded by that message for its squash merge ([2.3.4](2.3.4-publish.md#the-tasks-commit-message)).
- A Task of an Initiative in a Project where it has a Pipeline makes its branch from the Initiative's branch, fetched first, whether its worktree is made at Planning or at Start.
- A Publishing Task's worktree holds the Initiative's branch itself.
- A Conflict resolution Task's worktree holds its pull request's own branch (`office/<task id>`, or `initiative/<short name>` for a Publishing Task's): fast-forwarded first to the remote's copy when that is ahead, recreated from the remote when deleted locally, refused when the two diverged or the branch is checked out elsewhere (naming where); the base branch alone is its fresh base.
- The Office makes the Initiative's branch, merges into it and pushes it, and never deletes it ([The Initiative's branch](#the-initiatives-branch)).

## Guards

- A git-mutation deny list for Agents, plus a HEAD and branch check after every Stage, since command patterns can be bypassed.
- The HEAD and branch check also runs before every Stage: a move along the base is taken as it is, and any other asks the user ([2.3.1](2.3.1-stages.md#a-branch-moved-outside-the-office)).

## The Project's environment

- The Project's environment (`set`, `unset`, `prependPath`) is stored outside the checkout and applied to every command and Agent.
- It is edited in the Environment section of the Project's page, the plain and the Secret variables together.
- It is saved only by its **Save**, at once and as a whole; a change breaking a rule is refused with every reason and nothing saved; **Discard** drops the edits.
- The environment check, run from the same section, tries the saved environment in a fresh worktree of the base branch and changes nothing: the install, then every command of the Project in its list's order, each shown by its name and skipped when its line is blank.

## Secret variables

- A variable in `set` may be a Secret variable, edited in its own list in the Environment section.
- Its value is one line of at least 6 characters, so hiding it can't hide ordinary text.
- A name is plain or secret, never both.
- Once saved, it is kept in the database and never sent back: the Project API, the environment check API and every event give its name and whether a value is set; a save that leaves the value empty keeps the Project's.
- An Agent reads the Secret variables by name and whether a value is set in the Project's record (`list_projects`), never their values.
- To host commands and to the sessions of the Project's Tasks, it is given in their environment.
- In a run environment, it goes to `compose exec` by name alone: each `set` value travels in the compose CLI's own environment under a carrier name (`OFFICE_VARIABLE_<n>`, so a Project's `PATH` or `DOCKER_HOST` can't change how the CLI runs), passed as `--env OFFICE_VARIABLE_<n>`, and the script takes it back under its own name; no value is in a command line or the script.
- To the install as the run environment's image builds, every `set` variable is a BuildKit secret (`RUN --mount=type=secret,id=…,env=NAME`), so no value lands in a layer, the image's history or a build argument.
- The image's key takes plain variables by name and value and Secret variables by name alone.
- Wherever it would show, it shows as `[secret NAME]`: in each command's recorded and streamed output (stage runs, the environment check, the `run_project_command` answer and its output file, on the host and in a run environment, a value cut across chunks included), and in what a session writes into a Thread (an Agent's text and its tool calls' summaries, before they are stored or sent live).
- Left out: the engine's own transcript files, and the tool results the model reads; an Agent that prints a value sees it ([6](6-permissions-and-safety.md#secret-variables)).

## The Initiative's branch

- An Initiative has a branch named `initiative/<short name>` in each Project it spans where it has a Pipeline ([2.1](2.1-work.md#defaults)), and none in a Project with None.
- Its **Short name** is one for the whole Initiative, made once any of its Projects has a Pipeline.
- The Short name is made from the title: accents dropped, lower-case a–z, 0–9 and `-`, at most 40 characters cut at a word; with nothing left, it is the first 8 characters of the Initiative's id.
- It is shown and editable while shaping and fixed at Confirm.
- It is unique Office-wide among Initiatives that have one, whatever their state: a derived name that is taken gets `-2`, `-3` and so on; an edited name that is taken is refused, with the reason.
- **Made:** Confirm makes the branch from the freshly fetched base in every Project the Initiative spans where it has a Pipeline.
- Confirm is refused, naming the Project and why, when a branch can't be made or already exists there, locally or on the remote; the branches that attempt made are removed again, since they hold nothing.
- A Project the Initiative comes to span after Confirm starts with None and gets no branch when the Task is added or moved there; it gets its branch when the CTO's Proposal, applied, gives it its first Pipeline, and applying it is refused, with the reason, when the branch can't be made.
- **Pushed:** the branch lives on the base branch's remote whenever the base branch tracks one, pushed with the Office identity after each Publish into it and after each Stage of a Publishing Task ([2.3.4](2.3.4-publish.md)); otherwise it stays local.
- **Kept:** The Office never deletes it, so it is kept when the Initiative is dropped or done; the user deletes it, and the Initiative page lists each one.
- Once it is gone, a Task that needs it is refused Start, or its Publish fails, naming the branch.
- **Read by Threads:** the Initiative's Threads ([2.4.1](2.4.1-threads.md)) read a detached, read-only checkout of it per Project, under `<office-data>/initiative-bases/<short name>/<project>`, refreshed as each session's first answer starts, as the base checkouts are.

## Defaults

### Install inputs

- A Project lists the files whose change makes a worktree install again (a lockfile, say), given when it is added and edited on its page beside the install command.
- A worktree installs when it is created and again when the install command or one of those files changes; with none listed, once.

### The base branch's upstream

- It is where the freshly fetched base comes from: worktrees start at the remote branch it tracks, fetched first.
- A base branch that tracks nothing is used as it is, unfetched, and the environment check says so.
- A Task of an Initiative in a Project where it has a Pipeline starts at the Initiative's branch instead, fetched first.

### Clones

- A Project added by Repository URL is cloned, in full, into `<office-data>/repositories/<host>/<owner>/<repo>`, so a second add of the same URL is caught.
- The clone runs in the background with its progress shown.
- A folder left by a failed add is reused.

### The Office identity

- Every git command The Office runs, for a Project (added by path too) or not (a Skill's Source, Devops reading a URL), uses only The Office's own credentials, shared by all Projects and separate from the user's.
- A GitHub https remote: the Sign in with GitHub user token, handed to git for that one command by a credential helper Office code answers; never in an environment variable, a remote URL, a git config file or a command line, which hooks, filters and Agents could read.
- An ssh remote, on any host: the Office ssh key alone, generated and kept by The Office in its data directory.
- The key's public half is shown in Settings, hidden until the user shows it, for the user to add to the host.
- The user can regenerate the key in Settings after confirming its consequences (the current key is gone for good, and every ssh host refuses The Office until the new public half is added there); a failed regeneration keeps the current key.
- ssh runs with no agent, none of the user's ssh config or keys, and The Office's own known hosts: GitHub's host keys from GitHub's published list, any other host's key trusted only once the user confirms its fingerprint.
- Any other https remote: anonymously, so public repositories only.
- git is kept from the user's credentials: their credential helpers are cleared for every command, and git never prompts (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`).
- Every Office git command runs with a home folder of The Office's own, so neither curl nor git-lfs can read the user's `~/.netrc`.
- The user's global git config still applies, through an Office global config file (`GIT_CONFIG_GLOBAL`) that includes their XDG `git/config` and `~/.gitconfig` by absolute path; `XDG_CONFIG_HOME` stays theirs, so their global ignore and attributes files apply too.
- A `~` in the user's config then means The Office's home folder.
- Office git never sends the Windows sign-in: `http.emptyAuth` is off, without which curl has no user name to answer a 401 with NTLM or Negotiate, and git's own default would turn it on once a 401 offers NTLM; no git setting turns those methods off on the pinned git.
- `KRB5CCNAME` names a credential cache that doesn't exist, so on Linux neither curl nor git-lfs finds the user's Kerberos tickets.
- Known gap: git-lfs answers a server that offers Negotiate with the Windows sign-in (SSPI), whatever git's settings say, and no setting stops it.
- Sign in with GitHub signs in by GitHub's web flow for an App's user token: the browser goes to GitHub's authorize page and comes back to The Office on localhost, at a callback URL the manifest names, with a code The Office exchanges with the App's client secret and PKCE.
- The client secret is kept like an API key, a database row never sent to the web; the App's private key and webhook secret are discarded.
- A Project's page says which part of the identity its remote needs and what is missing.
- Pull requests are opened through GitHub's API with the token; without Sign in with GitHub there are none.

### The CPU limit

- It is for run environments, set Office-wide in Settings › Office limits, Automatic until changed.
- Automatic gives each run environment's checks' service this computer's cores less 2 (`os.availableParallelism()`, at least 1) and every other service, such as Postgres, 2, never more than the checks' service.
- Every run environment gets the same CPUs rather than a share of the cores, so one running Task uses the idle cores and two split them.
- No service gets `cpu_shares`, as the container runtime already weighs containers equally and an explicit 1024 would lower their cgroup v2 weight.
- Fixed gives every service one whole number, from 1 to this computer's cores, kept while Automatic is chosen, and held to the cores at a start on a computer with fewer.
- The limit is read as a run environment starts, so a change reaches a running one at its next start.

### The other limits of run environments

- They are set Office-wide in Settings › Office limits' Run environments card beside the CPU limit, each saved as it changes.
- **Run environments at once:** 2 by default, 1 to 12.
- **Memory per service:** 4096 MB by default, 512 MB to 65 536 MB in steps of 512 MB, shown in GB, with no swap above it.
- **Processes per service:** 1024 by default, 256 to 65 536 in steps of 256.
- The service refuses a value outside them, naming the field.
- Memory and processes, like the CPU limit, reach each run environment at its next start.
- Raising Run environments at once lets a Stage waiting for a run environment start at once; lowering it takes no slot from a running one, and new ones wait until fewer are running.
- When Run environments at once is below Running Tasks at once, the card says the running Tasks past it wait on their checks ("Waiting for a run environment").

### A test instance's checkout

- Each test instance ([2.12](2.12-test-instances.md#test-instance)) runs on its own detached checkout of the commit it launched, under `<office-data>/test-instances/<id>/`, made by The Office from the Project's repository after fetching the Initiative's branch.
- It is an export of the branch tip's tree (`git read-tree` into an index of its own, then `git checkout-index` into the folder), not a linked worktree, so it has no `.git` at all, no git folder has to be mounted with it, and the repository's own index and worktrees stay as they are.
- It is removed when the instance stops, fails or is Built.
- The instance's log is `<office-data>/test-instances/<id>.log`, beside its checkout, and stays with the instance.
- A Hosted instance is its own compose project, `office-<office>-test-<instance id>`, where `<office>` is the part that names this Office's run environments, with its own volumes, removed when it stops.
- Its services are labelled `office.test-instance=<id>`.
- Only the target's port is published, `127.0.0.1::<container port>` (a free host port Docker picks), through a compose override The Office writes; the proxy reaches it there ([5.1](5.1-shape.md#the-test-instance-proxy)).
- The override mounts only the checkout, and gives `OFFICE_TEST_INSTANCE=true` and the target's own variables under carrier names, as a command in a run environment gets them ([Secret variables](#secret-variables)).
- Nothing else from the host is mounted ([6](6-permissions-and-safety.md#test-instances)).

### The build cache volume

- A Build to install build in the run environment gets one named Docker volume per Project, `office-<office>-test-cache-<project id>`, for the build tool's caches and `~/.android`, never a host folder.
- It is kept between builds, so builds stay fast and the Android debug signing key stays the same.
- A build on the workstation, with Run environment Off, uses the workstation's own caches as the Project's checks there do.
- The files it makes are copied to `<office-data>/test-builds/<id>/` and kept as [2.12](2.12-test-instances.md#kept-build-to-install-files) says.

### The repository's git data in a run environment

- A Task's run environment mounts the repository's shared git folder read-only at the path the worktree's `.git` file leads to, beside the worktree.
- So git in a check reads the worktree's history (`status`, `log`, `diff`) but can't commit, move a branch or write objects: every git change stays The Office's.
- The path comes from git run by The Office on the host, never from the worktree's `.git` file, which an Agent could point at any other folder.

### The file of earlier Stage runs in a run environment

- The file a route's Project-command condition reads from `OFFICE_STAGE_RUNS_FILE` ([2.3.2](2.3.2-flows.md#the-project-command-condition)) is `<office-data>/stage-runs/<task id>/stage-runs.json`, written to a temporary file in that folder and renamed over the old one.
- The Task's run environment mounts the folder, never the file, read-only at the same path, so the command reads the same path on the host and inside it, and a rewrite is seen there (a file's bind mount keeps the file it found).
- The folder is made before the environment starts and removed with the Task's worktree.
- A condition command never runs in an environment started without the mount: it couldn't run, saying to stop and start the Task's run environment.

### Run environments with a non-root Office

- Installed Offices run as a user of their own, not root.
- The checks keep the user the definition or the image names, so images that rely on root's home, caches or named volumes work.
- After each check, however it ended (passed, failed, timed out or stopped), The Office gives every file and folder in the worktree that another user or group owns back to its own user and group, as root in the checks' service, before the check's result is returned; files it already owns are left untouched.
- A hand-back that fails ends the check as could-not-run with why and stops the run environment; the next check hands back what was left.
- git in a check trusts every repository (`safe.directory`, given by the check's environment, added to any git config the Project gives), so the worktree and the read-only git folder, owned by The Office's user, aren't refused.
- A root Office, and Windows, change nothing: the same user, the same script, and no extra command.
- Not supported: rootless Docker and userns-remap (root in the container isn't the host's root, so the hand-back can't give files away); a check user other than root that can't write a worktree it doesn't own; files a process left running writes after its check ends.

### Writing the run environment definition

- Agents write `.devcontainer/` only with the Office tool `write_run_environment_definition`, in an Agent Stage of a Role with the Run environment capability ([2.2](2.2-people.md), [6](6-permissions-and-safety.md)).
- The Agent gives each file whole, its path from the repository's root inside `.devcontainer/`.
- The Office reads the definition as it would at a check, the given files in place of the worktree's and any other file it names from the worktree, and writes the files only when it is valid, leaving the folder's other files.
- Otherwise, or for a path outside the folder, it writes nothing and answers every problem in the definition check's words.
- It builds and starts nothing.
- The built-in Set up Stage's brief and the set-up Task's Plan tell Devops to write with it.
