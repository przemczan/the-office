# 2.10 Users and signing in

Covers: users, First-run setup, adding users, ways to sign in, linking, Continue with GitHub, Google and OpenID Connect, which ways work on which address, signed-in devices, wrong tries, recovery, what is per user and shared, signing in to a test instance, what every request needs.

## Users

- The Office has several **users**, and everyone signs in before using it, localhost included.
- Every user can do everything.
- A user is never a person of The Office: people are the Roles the users hire ([2.2](2.2-people.md)).
- Emails are unique, compared without case.
- Records name the user who did each thing ([2.1](2.1-work.md), [2.4](2.4-conversations.md)), and an Agent's Brief says which user asked ([2.5](2.5-context-policy.md)).

## First-run setup

- The first user is created at first run, in **First-run setup**.
- While no user exists, the sign-in page asks for the **setup token** and the first user's name, email and password instead.
- The installer creates no user.
- The setup token unlocks that step, so whoever reaches The Office first over the network can't claim it.
- The service's first start (or `npm run setup-token` on the host) makes one and prints it with the address to open, and The Office keeps only its hash.
- A missing, wrong or replaced token is refused with how to print a new one, before any field is checked.
- A start with a token already waiting prints none, only how to get one, so a restart never replaces the installer's.
- The first user uses the token up.
- Then First-run setup walks the first user through the basics, each skippable: the engine and its login, Sign in with GitHub for git, and telemetry ([5.2](5.2-stack.md)).
- Every signed-in page leads there until they finish or skip the rest, which closes it for good.
- An Office that already had users never sees it.

## Adding and removing users

- After the first, any signed-in user adds an account for someone else in Settings › Users with their name and email.
- The Office shows a **one-time password** once, which the adding user passes on, and the new user sets their own password at their first sign-in.
- A user can be removed in Settings › Users, which signs out all their signed-in devices at once; what they did keeps their name.

## Ways to sign in

- A password, **Continue with GitHub**, **Continue with Google**, **Continue with <name>** (through an **OpenID Connect provider**) or a **passkey**.
- After a password, Continue with GitHub, Continue with Google or Continue with <name>, The Office asks for an **authenticator code** once the user has set up an **authenticator** on their account.
- A passkey is enough on its own.
- A **recovery code** may stand in for an authenticator code.

## Linking

- Each user links their own GitHub, Google and OpenID Connect identities and adds their passkeys from their account, signed in.
- Continue with GitHub, Continue with Google and Continue with <name> sign in only a **linked identity**.
- An identity is found by the provider's own id for it (GitHub's numeric user id, the `sub` of Google's or the OpenID Connect provider's), never by matching an email or a login.
- An identity linked to one user can't be linked to another.
- Unlinking or removing a passkey is the user's own, from their account.

## Continue with GitHub

- Continue with GitHub is not Sign in with GitHub.
- Sign in with GitHub is The Office's own git identity ([5.5](5.5-git-and-isolation.md)), one and shared.
- Continue with GitHub signs a user in through the same GitHub App, by its user authorization flow, with no new registration.
- The Office reads who the GitHub user is, revokes the token GitHub handed out at once and keeps nothing of it.
- It never touches the git identity's sign-in or token.
- It is offered whenever the App is registered.

## Continue with Google

- It needs a Google OAuth client the user creates and enters in Settings › Signing in, one shared by every user.
- Its secret is kept as the GitHub App's is ([6](6-permissions-and-safety.md)).

## Continue with an OpenID Connect provider

- Continue with <name> is the user's own OpenID Connect provider (Zitadel, Authentik, Keycloak and others).
- One provider is set up in Settings › Signing in, one shared by every user.
- Its fields: a name (1 to 40 characters, shown as "Continue with <name>"), the issuer URL, a client ID and a client secret.
- The secret is kept as Google's is and never shown again (saving with it empty keeps it).
- The issuer URL is HTTPS, or `http://localhost`, `127.0.0.1` or `[::1]` for a provider on the same machine.
- Saving reads the provider's `.well-known/openid-configuration`, checks its `issuer` is the URL entered and keeps its authorization and token endpoints (which follow the same URL rule).
- Saving again reads them anew.
- A provider that can't be reached, isn't an OpenID Connect provider or names another issuer is refused with why.
- The flow is the authorization code with PKCE, asking for `openid email profile`, the secret sent to the token endpoint by HTTP Basic.
- The ID token's issuer, audience and expiry are checked; its signature isn't, as it comes straight from the token endpoint over TLS.
- The identity is found by the `sub` only and shown by its email, else its preferred username, else the `sub`.
- The Office keeps none of the provider's tokens.
- Removing the provider keeps the linked identities.
- Saving one with another issuer than the one saved last, even after a removal, removes the old issuer's identities, as a `sub` means something only at its own issuer; the card says so before saving.

## Which ways work on which address

- The Office is used at `localhost`, by IP on the local network over plain HTTP (a trusted network), or at its **public address**, behind a reverse proxy the user sets up with HTTPS and a domain ([5.1](5.1-shape.md)).
- The sign-in page shows only the ways that work on the address it was opened at:

  | Address | Password | Continue with GitHub | Continue with Google | Continue with <name> | Passkey |
  |---|---|---|---|---|---|
  | `localhost` | Yes | Yes | Yes | Yes | Yes |
  | A loopback IP (`127.0.0.1`) | Yes | Yes | No | Yes | No |
  | A local network IP over HTTP | Yes | Yes | No | Yes | No |
  | The public address (HTTPS) | Yes | Yes | Yes | Yes | Yes |

- Passkeys need a secure page and a name, not an IP.
- Google sends a user back only to `localhost` or HTTPS.
- A passkey works only at the address it was added at (its relying party is that name), so a user who uses both `localhost` and the public address adds one at each.
- GitHub sends a user back only to a callback URL listed in the App's settings, so Settings › Office identity shows the URLs to add for this address and the public address.
- The OpenID Connect provider likewise lists only the redirect URIs it has been given, so Settings › Signing in shows the ones to add for this address and the public address.
- Some providers, Zitadel among them, take a plain-HTTP redirect URI only with the app's Development mode on.
- An authenticator code is asked for wherever the way before it works.

## Staying signed in

- Signing in sets a cookie that is `HttpOnly`, `SameSite=Lax` (so GitHub's, Google's and the OpenID Connect provider's redirects back carry it), `Path=/`, and `Secure` when the page came through the public address over HTTPS.
- Its token is random and stored only as a hash, one per **signed-in device**.
- A device keeps the browser it came from, the kind of address, when it signed in and when it was last used.
- A signed-in device is never called a session ([glossary](../../GLOSSARY.md)).

## Signed-in devices

- Each user sees theirs on their account, this one marked, and signs out any of them.
- A device signed out answers its next request with the sign-in page, and its open WebSocket closes.
- **Sign out** in the top bar's user menu signs out this device.
- Removing a user or the host command signs out every device of that user.

## Wrong tries

- Wrong passwords, authenticator codes and recovery codes count against the user they were for.
- The first few cost nothing; then each try waits longer, and then the user's password and codes are locked for a while, with the time to try again shown.
- An unknown email gets the same answer, in about the same time, as a wrong password.
- The count is kept in the database, so a restart doesn't reset it.
- A passkey still signs in during a lockout.
- The numbers are in [Slow-down and lockout](#slow-down-and-lockout).

## Recovery

- A user who lost their authenticator signs in with a recovery code.
- Each recovery code is used once, shown once when the authenticator is set up, and made anew on request (the old set then stops working).
- A user who lost their password, or every way in, gets back in through a command on the host, `npm run set-password -- --email <email>`.
- It asks for a new password twice, lifts the lockout and signs out all that user's devices.
- With `--clear-authenticator` it also removes their authenticator and recovery codes, for a user who lost both.
- Anyone who can run commands on the host can already read The Office's data, so the command asks for nothing more.
- A lost setup token is printed anew the same way, `npm run setup-token`, which ends the earlier one.
- Once a user exists, `npm run setup-token` refuses and points to `set-password`.

## Per user and shared

- Each user's own: their account (name, email, password, authenticator, recovery codes, linked identities, passkeys, signed-in devices), their palette and density ([4](4-ux-direction.md)), and where Since you left begins for them ([2.7](2.7-notifications.md)).
- Shared by every user: The Office's people, Projects, Pipelines, Memory, Office instructions, Notifications and Needs you (a Notification handled by one user is handled for all), and every Decision, which any user can answer.
- The Office identity, Sign in with GitHub and the Office ssh key, stays one, shared, for git.

## Signing in to a test instance

- A Hosted test instance ([2.12](2.12-test-instances.md#reaching-a-hosted-instance)) sits behind its own sign-in, given from The Office's.
- **Hand-off link:** **Open** asks the service (`POST /test-instances/:id/open`, signed in) for a link to the instance's port.
  - It is single-use.
  - It expires after about 60 seconds.
  - It is bound to the instance's id, so it signs in to no other instance.
- **Cookie:** the proxy exchanges the link for a cookie of that instance alone, `HttpOnly` and `SameSite=Strict`, and redirects to the app's `/`.
  - Stopping the instance ends it.
  - A request to the instance's port without it is refused, saying to open the instance from The Office.
- **Download link:** a Build to install file's QR code holds a link under `/api/sign-in/test-builds/` that works for that one file only and expires after 1 hour ([2.12](2.12-test-instances.md#build-to-install)).
- Each link's token is random and stored only as a hash.

## What every request needs

- Every HTTP request to `/api` and every WebSocket needs a signed-in device, from `localhost` too.
- Exceptions:
  - the sign-in pages and their callbacks (`/api/sign-in/**`), the download links of Build to install files (`/api/sign-in/test-builds/**`) among them;
  - `/api/health`, which says only whether the database is up, and which the launcher and the tests poll;
  - the Claude Code `-p` hook, which has its own token ([5.4](5.4-the-engine.md)).
- The web app's own files (`index.html`, scripts, styles) are served to anyone: they hold no Office data, and the sign-in page needs them.

## Defaults

### Password rules

- At least 12 characters and at most 256, any characters, no other rule.
- A password that equals the user's email is refused.
- Hashed with Node's `scrypt` ([6](6-permissions-and-safety.md)).
- Changing one's own password asks for the current one and signs out every other device of the user.

### The one-time password

- 16 random characters from an alphabet without look-alikes.
- Shown once to the user who added the account, with Copy.
- It works for one sign-in within 7 days, which goes straight to setting the new user's own password.
- An unused one can be made anew in Settings › Users, which ends the old one.

### Slow-down and lockout

- Per user, the first 3 wrong tries in a row cost nothing.
- Each further one waits 2, 4, 8 and then 16 seconds before the next try is taken (the service answers when to try again, never sleeps).
- The 10th wrong try in a row locks the user's password and codes for 15 minutes, and each lockout after that, before a right try, for twice as long, up to 24 hours.
- A right sign-in resets the count.
- The host command lifts it.

### How long a device stays signed in

- 30 days after its last use, so a device used at least once a month stays signed in until it is signed out.
- The last use is written at most once a minute.

### Recovery codes

- 10, each 10 characters in two groups of 5, from an alphabet without look-alikes, stored only as hashes.

### The authenticator

- The standard 6-digit, 30-second codes (TOTP, SHA-1), with one step of drift either side.
- Set up by scanning a QR code or typing its key, and confirmed with a first code.
- A code is taken once.
- Removing the authenticator asks for a current code or a recovery code.

### Removing users

- A user can't remove themselves, and the last user can't be removed.

### The setup token

- 24 random characters from the one-time password's alphabet (about 119 bits), printed in groups of four and read with or without the dashes, in either case.
- Kept only as its SHA-256, compared in constant time, in no log record or event.
- One at a time, with no expiry: a new one ends the old, and the first user uses it up.
- The service writes a new one straight to standard output, never through its logger, so journald and `docker logs` show it and telemetry never exports it.
- `npm run setup-token -- --quiet` prints the token alone, for an installer; it exits with 1 once a user exists and 2 for other arguments.

### Skipping the basics

- `OFFICE_SKIP_SETUP_BASICS=true` lets an automated install leave out First-run setup's basics; never the setup token or the first user.
- Like every Office variable, no Project command inherits it.

### Records from before users

- Whatever a record says the user did before users existed names the first user.

### Since you left per user

- The Office keeps each user's last activity, so Since you left begins after each user's own five idle minutes ([2.7](2.7-notifications.md#defaults)).
