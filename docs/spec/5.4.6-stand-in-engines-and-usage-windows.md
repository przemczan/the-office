# 5.4.6 Stand-in Engines and usage windows

Covers: Stand-in Engines, a Project's own Stand-in Engine list, stand-ins of another engine type, picking the engine to run on, a forced engine with no stand-ins, a running Stage switching, a person's Thread switching, carrying a session, a turn refused for a used-up usage window, checking the usage windows.

## Defaults

### Stand-in Engines

- Settings › Engines holds one Office-wide ordered list of **Stand-in Engines**: saved engines that take over for each other when one runs out of its 5-hour or 7-day window.
- A stand-in may be of any engine type, whatever the engine it takes over for.
- Beside the list is the context size in tokens above which a switch of a running Stage asks the user first; it applies only to Stages, and to every Project.
- It is 100,000 by default, since a switch loses the prompt cache and the whole context is written again; 0 always asks.
- An engine named twice or not listed is refused, as is a size that isn't a whole number from 0 to 10,000,000.
- A list naming an engine that lacks a capability a Role a Pipeline names needs is refused ([5.4.5](5.4.5-engines-and-cascade.md#roles-that-need-office-tools-and-a-held-answer)).
- Removing an engine drops it from every list.

### A Project's own list

- A Project's Engine block can turn on **Use this Project's own list**, which replaces the Office's list in that Project.
- The Project's list starts empty, so with nothing added the Project's work gets no stand-in.
- It is ordered and refused as the Office's list is; the ask-above size stays the Office's.
- It may name engines of any type, the Project default's or another.
- Turned off, the Project's list is kept, unused, and the Office's applies again.
- A Thread without a Project uses the Office's list.

### Stand-ins of another engine type

- A stand-in of the same engine type as the engine it takes over for keeps the session where the type can be carried, Claude Code only: a running Stage or a Thread is carried over and resumed with the same model and settings ([Carrying a session](#carrying-a-session)).
- A stand-in of another engine type, or of a type that can't be carried, can't take the session, since no engine reads another account's: it starts fresh, with the Brief, working with the person's model and effort for its type ([5.4.5](5.4.5-engines-and-cascade.md#the-model-and-effort-cascade)).
- So a Thread and a new session go on there, fresh; a running Stage doesn't switch to one, and pauses until the reset instead of restarting without its context.

### Picking the engine to run on

- The Engine module's `engineToRunOn(cascade, standIns, hasRoom)` picks the engine to run on, `standIns` being the list that applies: the Project's own, else the Office's, and none under an engine override.
- It picks the cascade's engine while it has room.
- Else it picks the first Stand-in Engine in order that is listed, isn't the cascade's own, has every capability the session needs and has room, whatever its engine type.
- Else it picks none.
- The cascade's engine needn't be in the list to get stand-ins.
- The caller passes `sameEngineType` when the session must be carried, as a running Stage's must; then only stand-ins of the cascade's engine type count.
- What "room" means is the caller's: at Start the Window caps with the Usage estimate, mid-run the windows not used up.

### A forced engine has no stand-ins

- An Initiative's or a Task's engine override forces that one engine: its sessions never run on a Stand-in Engine.
- At Start, a Window cap that would be passed, or a used-up window, makes the Task wait in the Queue for the reset, with the reason "<engine> is set for this Task · resets 14:30" ("… for its Initiative" when the Initiative's override gives it).
- When its window is used up mid-run, the Task pauses until the latest reset, with no switch and no Stand-in choice.
- A Thread on a forced engine (the Initiative's or Task's planning Thread, a Consultation on the Task) shows the notice of a refused turn and isn't resumed by itself at the reset: the user writes again ([2.4.5](2.4.5-stopping-and-restarts.md#a-turn-refused-for-the-usage-window)).
- Turning the override on while the Task runs on a stand-in takes effect from its next session, as any change of engine does; turning it off lets the next Start choose stand-ins again.

### Stand-ins at Start

- Start and the Queue use the stand-ins of the list that applies to the Task: when a Window cap would be passed or the window is used up, a Start chooses a stand-in for the cascade's engine, which every session of the Task runs on ([2.1](2.1.5-planning-and-start.md#a-queue-for-start), "A queue for Start").
- A Task with an engine override gets none ([A forced engine has no stand-ins](#a-forced-engine-has-no-stand-ins)).
- A stand-in chosen at Start may be of another engine type, since every Stage opens a session of its own.
- The Start records the choice on the Task (`engineStandIns`), with why.
- Every Start replaces it, trying the cascade's engine first.
- `engineThroughStandIns(cascade, standIns, engines)`, from the Engine module's public entry, maps a cascade's engine through that record: to its stand-in while that is still listed in the list that applies and the cascade's engine is no override, else back to the cascade's engine.
- It compares engines by id alone: no model is weighed, as each session's model comes from the person for the stand-in's type.
- The Usage estimates of a started Task and the Stage Threads both map through it alone, so what is counted and where a session runs can't drift apart.
- The choice holds for the whole run, Pause and Resume, a restart and the fire alarm included.
- A continued session stays on its engine, and a session whose engine differs starts fresh with the Brief (`engine-changed`), never resumed on another engine.
- Each Stage run records the engine and model it ran on and, on a stand-in, the engine it stood in for and why.

### A running Stage switches

- When an engine refuses a Stage's turn, its first or its correction, as **usage window used up**, the Stage goes on in the same Stage run on the first Stand-in Engine, in order, of the same engine type, that has room and can carry the session.
- Stand-ins of another engine type are passed over: the Stage's context would be lost.
- Room means its window not used up, its latest reading free or not read yet.
- The run stays Running: the Task isn't paused, and no failure, retry or Notification about the Stage is raised.
- The session is carried over and resumed with the same model and settings, and the refused message is sent again.
- The stand-in is recorded on the Task's `engineStandIns`, so the run's next Stages open on it; the next Start replaces that list.
- A stand-in that refuses too gives way to the next; once none is left, the Task pauses until the latest reset.
- Five cases don't switch, and the Stage pauses until the reset, never failing:
  - no stand-in of the same engine type has room;
  - the engine is an override, which has no stand-ins;
  - the carry-over fails;
  - a user's Pause or Stop, or the fire alarm, was asked before the refusal;
  - the session's context is over the size set beside the list, since the stand-in's account has no prompt cache and would read it all again.
- In the last case the Stage is marked as waiting for the user's choice to go on on the stand-in or at the reset.
- The choice is made on the Stand-in choice card ([2.4](2.4.2-decisions.md#the-decision-on-stages-waiting-for-a-stand-in-engine), "The Decision on Stages waiting for a Stand-in Engine").
- "Switch now" moves the idle session to the first Stand-in Engine of the same engine type with room by the carry-over below, and the Stage goes on on it, recorded on the Stage run as the user's choice.
- A Stage paused this way resumes at the reset on its own engine, its session resumed with its context.
- Each switch is recorded on the Stage run (from which engine, to which, and why: the window and its reset).
- The Stage history shows it, and the Task page and the Live view show the stand-in as the run's engine afterwards.

### A person's Thread switches

- A chat, a Consultation and a planning Thread (an Initiative's or a Task's) switch too, in `ThreadRunner`, to the first Stand-in Engine with room of any engine type, unless an engine override gives its engine.
- When the engine refuses a turn as usage window used up, a stand-in of the same type carries the session over, recorded there and resumed with the same model and settings.
- A stand-in of another type starts the Thread fresh there instead, with the Brief the Context policy gives a fresh start ([2.5](2.5-context-policy.md#choosing-a-move)) and the person's model and effort for its type.
- The refused message is sent again there, followed by the user's messages the refused turn never took.
- The Thread stays answering through the switch.
- It switches whatever its context size: the user is there to see the line.
- The Thread logs the switch line naming the person who went on: "Claude Code's 5-hour window was used up until 14:00, so Pam went on on Claude Code 2", or on another type "…, so Pam went on on Codex, starting fresh".
- Once its engine is known used up, the Thread doesn't wait for a refusal:
  - a new session opens straight on the first Stand-in Engine with room, of any type, recorded as standing in for the cascade's engine, with no switch line;
  - a resumed session is carried over to a stand-in of the same type, or started fresh on one of another type, with the switch line, before the message is sent.
- A session on a stand-in keeps resuming there, as the engine it stands in for counts as its own; a fresh session opens on the cascade's engine again once that has room.
- No stand-in with room, or a failed carry-over, leaves the session where it was, with the notice of a refused turn ([2.4.5](2.4.5-stopping-and-restarts.md#a-turn-refused-for-the-usage-window)).
- A failed resume on the stand-in moves the session back and says so in a failure line.
- A stand-in that refuses too gives way to the next, until none is left.
- The Live view shows the stand-in as the person's engine, standing in for the cascade's.

### Carrying a session

- Carrying a session is the `carrySession` capability, Claude Code only.
- The session id is Claude Code's and each engine runs with its own config folder, so the carry copies, never moves, the session's transcript (`projects/<cwd>/<id>.jsonl`) and the sibling `<id>/` folder (Sub-agent transcripts, saved tool results).
- The copy goes into the same `projects/<name>/` under the stand-in's folder, each file written beside its target and then renamed into place.
- The old folder's path is rewritten to the new one in the copied transcripts, as tool results are referenced by absolute path.
- Todos are copied and file-history is skipped.
- Running it again gives the same result, and the source stays intact.
- It runs only while the session is idle, after the refused turn ended its engine session.
- The order is copy, then persist the Thread's new engine, then resume.
- A restart before persisting leaves the Thread on the intact source; after it, the copy is already there and can run again.
- If the resume fails, the Thread is moved back to the old engine.
- Codex isn't carried, as it keeps its threads in its own internal store and its reasoning is likely tied to one account: a Stage on a used-up Codex engine pauses until the reset, and a Thread goes on fresh on a stand-in.
- A Copilot CLI session isn't carried either, kept in its engine's folder's `session-state/`; a Copilot CLI engine has no usage windows to use up.
- Nor is a Gemini CLI session, kept in its engine's folder under `.gemini/`; a Gemini CLI engine has no usage windows to use up either.
- The engine check's `engine.session-carry-over` and `fallback.session-carry-over` cases guard against a Claude Code update changing the file layout.

### A turn refused for a used-up usage window

- See [the engine check](../engine-check.md#engineusage-window-refusal).
- On both Claude Code adapters, a turn that ends with an error after a `rate_limit_event` with `status: "rejected"` in the same turn ends with the outcome **usage window used up**.
- The outcome names the window from the event's `rateLimitType` (`five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_overage_included`, `overage`) and its reset time (`resetsAt`).
- A type the port doesn't name is carried with the engine's own name, so it still pauses rather than fails.
- Any other failure, including one after an `allowed` event (overloaded, a 5xx), stays an ordinary failure.
- The engine then publishes **Usage window used up** (the engine, its name, the window, the reset time) once per engine until that reset.
- Which engines are used up is kept in memory only, with no table.
- After a restart it is unknown until a turn is refused again, so at most one queued Task starts, is refused, pauses itself and sets the wait again.
- The Task's own resume time is kept with the Task, so its resume outlives a restart.

### Checking the usage windows

- The usage windows are checked as the service starts and every 5 minutes, as well as on each rate-limit signal.
- They are checked per engine that has them: a Claude Code engine, a Codex engine signed in with ChatGPT.
- Each engine's adapter reads them with no session and no model call:
  - the Agent SDK a short-lived query that keeps no session or transcript;
  - `-p` the pinned binary's `get_usage`;
  - Codex a short-lived app-server's `account/rateLimits/read`.
- Engines are read one at a time, each read ended within 30 seconds, on failure too; a failed read is logged and the next engine read.
- Such a reading is kept and announced as a session's is.
- The Engine alone judges whether a reading shows the engine **free** (every window below 100%) and announces it with the reading.
- A free reading taken after a window was used up resets that window at once, as its reset time would, so Start and the queue no longer wait for it.
- A turn refused while the latest reading shows the engine free is a limit the readings don't show.
- Then the engine's readings count as not free until that refusal's reset, so the Tasks it paused wait for their reset rather than resume into another refusal every 5 minutes.
