# 5.4.3 The Codex engine

Covers: the Codex engine, its sign-in, approval requests, sandbox, Office tools over MCP, Stage answers, usage windows, cost, capabilities, features kept out.

## Defaults

### The Codex engine

- It is checked by the [engine check](../engine-check.md#the-codex-app-server)'s `codex.*` runs on Linux.
- A **Codex** engine in Settings › Engines is one OpenAI account.
- Its sessions run the pinned `codex app-server`: one process per session, speaking JSON-RPC over stdio.
- `CODEX_HOME` is its own folder, `<office-data>/engines/<engine id>/`, where Codex keeps the sign-in, its own state databases and each thread's history.
- So a session resumes only on the engine that started it.
- Nothing else of the user's (`~/.codex`, `OPENAI_*` and `CODEX_*` variables) reaches it.
- Settings reach it only as `-c` overrides and `thread/start`'s parameters, never by editing the folder's `config.toml`.
- A Codex engine can be picked at every level of the engine cascade and as a Stand-in Engine, and runs any person's sessions, an Agent Stage's included ([5.4.5](5.4.5-engines-and-cascade.md#the-engine-cascade)).
- A person works on it with their model and effort for Codex ([5.4.5](5.4.5-engines-and-cascade.md#the-model-and-effort-cascade)).

### Codex sign-in

- "Sign in" runs the pinned binary's `codex login --device-auth` for that folder and shows its link and code, which sign in from any browser (ChatGPT, whose plan gives the usage windows).
- "Use an API key instead" takes an OpenAI API key, kept in the database and never sent back, and signs the folder in with it (`codex login --with-api-key`, the key on its input).
- "Sign out" is `codex logout`.
- The engine shows the sign-in kind and plan `account/read` gives, or that it is signed out.

### Codex: the Office rules through approval requests

- Sessions run under the `untrusted` approval policy, the one under which every command, read-only ones included, and every file change comes to the client first (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`; under `on-request` none came).
- The adapter answers each from the Office rules ([6](6-permissions-and-safety.md)) as the hook does on the Claude Code engines.
- A refusal is `decline`: the item ends `declined`, nothing is written, and the model reads only that it was declined, as the answer carries no reason.
- The session's brief says that a declined call was refused by the Office rules.
- A command's request that carries a `reason` asks to run outside the sandbox, where an accepted command writes anywhere and reaches the network.
- The rules decline it unless the Role's profile allows commands outside the worktree (`codex.sandbox`).
- Each Office tool and MCP tool call comes first as `mcpServer/elicitation/request` (`_meta.codex_approval_kind: "mcp_tool_call"`, with the tool's name and arguments), judged the same way.
- A declined one fails without reaching the server.

### Codex: sandbox kept to the worktree

- Threads start with `sandbox: workspace-write` and `cwd` the worktree, with `sandbox_workspace_write.exclude_slash_tmp`, `exclude_tmpdir_env_var` set and `network_access` off.
- So a command writes only in the worktree and has no network.
- On Linux a command runs under the bundled bubblewrap; writes elsewhere fail with `EROFS`, a name lookup with `EAI_AGAIN`.
- The worktree's repository is named `untrusted` under `projects` in `thread/start`'s `config`, keyed by its main checkout as Codex keys it.
- Otherwise a thread marks it trusted in the folder's `config.toml` and the Project's own `.codex/config.toml` joins the session's settings.
- Update checks and web search are off.
- History isn't persisted beside the threads.

### Codex: Office tools over MCP

- The service serves each session's Office tools and the Role's MCP servers' tools ([MCP servers for Agents](5.4.1-engine-kinds.md#mcp-servers-for-agents)) to it as an MCP server over Streamable HTTP on `127.0.0.1`.
- The server is named `office` in `thread/start`'s `mcp_servers`.
- It sits behind a bearer token made for the session and passed only as each server's `Authorization` header in `thread/start`'s and `thread/resume`'s `config` (`http_headers`).
- So the token is on no command line and in no environment the Agent's commands inherit, and it reaches only that session's server.

### Codex: Stage answers held to the schema

- `turn/start`'s `outputSchema` is the app-server's form of `codex exec --output-schema`.
- The turn's last agent message is the answer.

### Codex: usage windows

- Usage windows come from `account/rateLimits/read`, a Reading source of its own, refreshed by `account/rateLimits/updated` during a turn.
- Each window gives `usedPercent`, its length (`windowDurationMins`) and `resetsAt`.
- Which windows there are follows the plan; on ChatGPT Free it is one 30-day window, limit `codex`.
- An API key has none.
- A turn refused for a used-up window ends `failed` with `codexErrorInfo: "usageLimitExceeded"`, which is **usage window used up** as on the Claude Code engines ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#a-turn-refused-for-a-used-up-usage-window)).
- A Codex session isn't carried, so a stand-in for a Codex engine starts fresh ([5.4.6](5.4.6-stand-in-engines-and-usage-windows.md#stand-ins-of-another-engine-type)).

### Codex: cost

- Cost is priced by Model prices, one per Codex model shared by every Codex engine, from `thread/tokenUsage/updated`.
- Its input includes the cached input, priced as cache reads.
- Its output includes the reasoning.

### Codex: capabilities as the engine check showed them

- `bargeIn` yes: `turn/steer` with the running turn's id joins the turn without stopping its command; `later` is held by the adapter until the turn ends.
- `interrupt` yes: `turn/interrupt` ends the turn as `interrupted` within seconds and the thread goes on, but a running command keeps running to its end.
- So on Stop the adapter also ends the session's app-server process, which ends the command, and the next message resumes the thread.
- `resume` yes: `thread/resume` in a new process continues the same thread with its turns, its input from the cache.
- `usageWindows` yes on a ChatGPT sign-in, no on an API key.
- `contextUsage` yes: `thread/tokenUsage/updated` gives the context window and the tokens in it.
- `officeTools` yes.
- `outputSchema` yes.
- `languageServers` no, as Codex has no LSP tool, and its sessions get none.

### Codex's own features kept out

- Every app-server runs with Codex's features that bypass the Office rules or give the model tools The Office doesn't judge turned off by `-c` overrides.
- They are its hooks and memories, its apps and plugins, its own sub-agents, image generation and viewing pictures off the disk, browsers and computer use, skill search and installs, goals and tool suggestions.
- Its bundled skills and its listing of skills are off too, so a session lists only its own skills through the `Skill` tool ([5.6](5.6-skills-per-session.md)).
- A Project's `CLAUDE.md` is read where it has no `AGENTS.md`.
- A Codex bump re-reads `codex features list` for new ones.
