# Contracts: map

**Owns:** the HTTP and WebSocket contract, as zod schemas and their types: the one thing the service and the web share. Also the links to a record's page (`record-links.ts`), which the web writes and the service reads as mentions, the Open page a chat drawer message goes with (`open-page.ts`), and the Project filter's rule (`project-filter.ts`), which the web narrows by and `GET /search` will, and the id a new engine is given (`engineIdFor`, in `engines.ts`, mirroring the Engine module's domain), so the web names a new engine's models before Save. A mark's colour is one of the four names or a custom `#rrggbb` in lower case (`projects.ts`), `isCustomMarkColour` telling them apart. Only the service's adapters import it. The duties (`people.ts`: `dutyKeySchema`, `dutySchema` with its holder or fallback, `dutyChangeSchema`, and the `duty.changed` web event among `roleWebEventSchema`), for `GET`/`PUT /settings/duties`.

**Device frames** (`device-frames.ts`, spec 2.13 "The relay"): the frames the Office device helper speaks on its standard input and output, `u8 type | u32 channel | u32 length | payload` big-endian, `DEVICE_FRAME_TYPES` (HELLO with the helper's version, READY with its endpoint and, for a serial board, a second line with its `rfc2217://127.0.0.1:<port>` address, read by `readyEndpoints`, OPEN, DATA, CLOSE, ENDED with why, and on channel 0 SETTINGS, SIGNALS, PING, PONG and NOTICE), channel 0 the helper's own, a payload over `DEVICE_FRAME_MAX_PAYLOAD_BYTES` refused by `encodeFrame` and by the streaming `FrameReader`, which reads frames however the bytes are chunked. `tools/device-helper/frames.go` mirrors it: change both together. Plain bytes, no zod.

**Device control** (`device-control.ts`, spec 2.13 "Serial boards"): the JSON payloads of the channel-0 control frames, a serial port's `SETTINGS` (baud rate, data bits, parity, stop bits) and `SIGNALS` (DTR, RTS), each stamped by the helper with `at`, µs on its monotonic clock (`serialSettingsFrameSchema`, `serialSignalsFrameSchema`), so the browser replays them with their timing, `PING`/`PONG` ids and the helper's `NOTICE` codes (`helperNoticeCodeSchema`), with `controlFrame` and `controlPayload` to write and read them and `BROWSER_CONTROL_FRAME_TYPES`, the ones the service passes to the browser. `tools/device-helper/pty.go` and `rfc2217.go` write the same JSON: change both together.

**Connected devices** (`devices.ts`, spec 2.13): the kinds (`android-usb`, `serial-usb`, `android-wireless`), the states (`connecting`, `connected`, `waiting-for-run-environment`, `disconnected`) and the reasons a device is Disconnected (`by-user`, `tab-closed`, `task-ended`, `device-unplugged`, `run-environment-turned-off`, `error`), with `connectedDeviceSchema` (the endpoint while Connected, `127.0.0.1:<port>` for a relayed device or a serial board's path, with a serial board's `rfc2217Url` beside it, the adb serial `<address>:<port>` for a phone over wireless debugging, which keeps it while Waiting too; its baud rate, round trip and `notices`, `deviceNoticeSchema` with `slow-round-trip` over `SLOW_ROUND_TRIP_MS`; who and when it was connected and disconnected). `GET` and `POST /tasks/:taskId/devices` (`taskDevicesPath`), `POST /tasks/:taskId/devices/wireless` (`taskWirelessDevicesPath`, `pairWirelessDeviceSchema`: `address` an IPv4 or IPv6 literal, `port`, `pairingPort` and the 6-digit `pairingCode`, which no response, event or record carries; it answers the record, Connecting) and `POST /devices/:id/disconnect` (`disconnectDevicePath`); a refused connect or pairing is 409 when another Task's open record holds the device key, naming that Task in `otherTask`, else 422 (`connectDeviceRefusalSchema`, every reason in `reasons`). The relay is the signed-in socket `DEVICE_RELAY_PATH_PATTERN` (`deviceRelayPath`), one per device: binary messages are device frames, text messages are `{"type":"state"}` to the browser and `{"type":"unplugged"}` or `{"type":"error",problem}` (at most `DEVICE_RELAY_PROBLEM_MAX_LENGTH`) from it; a second socket closes with 4409 (`DEVICE_RELAY_TAKEN_CLOSE_CODE`), one for a device not there or Disconnected with 4410 (`DEVICE_RELAY_ENDED_CLOSE_CODE`). The `connected-device.changed` web event names the Task and the device. **Project devices** (same file, spec 2.13 "A Project's device"): `projectDeviceSchema` (kind, device key, the user's name of at most `PROJECT_DEVICE_NAME_MAX_LENGTH`, a phone's address and Port, its state at rest `paired`, `didnt-answer`, `not-paired`, `over-usb` or `in-use` with `inUseBy`, the pairing's `pairingStep` and `pairingProblem`, who added it, its `lastUse`); `GET` and `POST /projects/:id/devices` (`projectDevicesPath`, `addProjectDeviceSchema`: a USB device by its key, or a phone with the four pairing values, paired at once), `PATCH` and `DELETE /project-devices/:id` (`projectDevicePath`, `changeProjectDeviceSchema`), `POST /project-devices/:id/pair` (`projectDevicePairPath`) and `POST /tasks/:id/devices/lend` (`taskLendDevicePath`, `lendProjectDeviceSchema`), a Connected device naming its `projectDeviceId`; a refusal is 409 naming the `holder`, else 422 (`projectDeviceRefusalSchema`); the `project-device.changed` web event names the Project.

**Activity** (`activity.ts`, spec 2.14): `activityItemSchema`, a union on `kind` (`task`, `onboarding`, `stopped-task`, `failed-task`, `test-instance`, `ci-run`, `environment-check`, `connected-device`, `pull-request`), each with its stable `id`, `projectId`, `title`, `since`, `ended`, `endedAt` and `link` (`activityLinkSchema`: a Task, an Initiative, a Project or a url); `activitySchema`, what `GET /activity` answers for the signed-in user, `{ items, count }`; `activitySeenSchema`, `POST /activity/seen`'s `{ itemIds }`, 1 to 500; `activityWebEventSchema`, `activity.changed`, with no payload, as what was seen differs per user. The user being active, which Now reads, is `userActivityReportSchema` in `notifications.ts` (`POST /activity`), named apart so "Activity" means one thing.

**Office actions** (`office-actions.ts`, spec 5.4): each action the user can take on a record is declared once with `officeAction` (name, record, description, input, answer, route, the duties that cover it), beside its record's contract (Work's in `work.ts`, `WORK_OFFICE_ACTIONS`; Projects' in `ci-runs.ts`, `PROJECT_OFFICE_ACTIONS`, whose `runId` is coerced from the route's path and whose `start_workflow` takes a Workflow's inputs as a record of strings, beside the manual Workflows and refs that `GET /projects/:projectId/workflows` and `/refs` answer), and listed in `OFFICE_ACTIONS` (`office-action-list.ts`). The service derives both its route and its Office tool from the declaration, and the web calls it with `callOfficeAction`, its path and body from `officeActionPath` and `officeActionBody`: every new action on a record is made this way, never as a hand-written route plus a hand-written tool. `officeAction` throws for a path naming a parameter its input lacks, a DELETE with a body, or no covering duty.

**Commands** (`commands.ts`, spec §2.4): the Office commands (`OFFICE_COMMANDS`, /clear and /help, which the web carries out) and `messageCommand`, the one rule both sides read a message by ("/" first, the first word an Office command before a skill command, else an ordinary message); `officeCommandClash` names a skill an Office command's name takes. A Thread carries its `skillCommands`, and a user message a skill command ran as carries `skillCommand`.

**Images in a message** (`message-images.ts`, spec §2.4): the rules both the message box and the service check, so the user reads the same words from either: `MESSAGE_IMAGE_MEDIA_TYPES` (PNG, JPEG, GIF, WebP; no SVG), `MESSAGE_IMAGE_BYTES` (3 MB each), `MESSAGE_IMAGES_PER_MESSAGE` (10) and `MESSAGE_IMAGES_TOTAL_BYTES` (15 MB together), worded by `messageImageProblem`, `messageImagesProblem` and `SKILL_COMMAND_IMAGES_PROBLEM`. `POST /threads/:id/images` takes the bytes as `application/octet-stream` with `messageImageUploadQuerySchema` and answers a `MessageImage` (`attachmentId`, `name`, `mediaType`), the snapshot a user message keeps in `images`; a sent message names them by id (`images` in `conversations.ts`). The Attachment it is kept as may be owned by a Thread (`attachmentOwnerSchema`'s `thread` kind, `work.ts`) when the Thread is on no Task or Initiative. An API endpoint model's `seesImages` (`engines.ts`, default false) is its Sees images setting.

**Stand-in Engines** (`engines.ts`, spec 5.4): `engineSettingsSchema` carries `standInEngines` (engine ids in order) and `askBeforeSwitchAbove` (tokens, 0 always asks); `engineSettingsEditSchema` takes both as optional, one left out keeping the stored value, and the service refuses an unknown or twice-listed engine or a size that isn't a whole number from 0 to 10,000,000 with words (422). A Project's own list is `projectStandInsSchema` (`useOwnList`, `engineIds`, `projects.ts`), the Project `engine`'s `standIns` and an optional key of `PUT /projects/:id/engine`; `GET /tasks/:id/engine-cascade` names the list that applies (`standInsApplyingSchema`, `from` `office` or `project`, `people.ts`).

**Office default and Default effort** (`engines.ts`, spec 5.4.5): `officeDefault` is `officeDefaultSchema`, an engine type and one of its engines (`{ engineType, engineId }`), which runs on that engine's own default model; the engine's discriminator stays `kind`. Each engine carries `defaultEffort` (null is Not set), one of `ENGINE_TYPE_EFFORTS[kind]`, which mirrors the Engine module's `effortsTakenBy`; an engine edit may leave it out to keep the stored one. `effortSchema` lives here and `people.ts` re-exports it, so the two files don't import each other.

**A Project's engine levels** (`projects.ts`, `people.ts`, spec 5.4.5): `Project.engine` is `projectEngineSchema`, `{ default: { engineType, engineId } | null, force: { model, effort } | null, people: [{ roleKey, engineSettings }] }`, `engineSettings` in the Role card's shape. `PUT /projects/:id/engine` takes `projectEngineChangeSchema`, every field optional, so a field left out keeps the Project's; one web event, `project.engine-changed`. `taskEngineCascadeSchema` gives one top-level `engine` for the Task and each person's `work` (model and effort with their levels), as everyone in a place runs on the same engine.

**Engine overrides** (`work.ts`, `people.ts`, spec 5.4.5): a Task's `engineOverride` and `initiativeEngineOverride` and an Initiative's `engineOverride` are engine ids, no model; `PUT /tasks/:id/engine` and `PUT /initiatives/:id/engine` take `workEngineChangeSchema`, `{ engineId: string | null }`, and the web events are `task.engine-override-set` and `initiative.engine-override-set`. `GET /tasks/:id/engine-cascade` gives the level `office`, `project`, `initiative` or `task`, and `standIns.from` `none` under an override, which uses no Stand-in Engine.
