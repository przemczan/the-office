# Contracts: map

**Owns:** the HTTP and WebSocket contract, as zod schemas and their types: the one thing the service and the web share. Also the links to a record's page (`record-links.ts`), which the web writes and the service reads as mentions, the Open page a chat drawer message goes with (`open-page.ts`), and the Project filter's rule (`project-filter.ts`), which the web narrows by and `GET /search` will, and the id a new engine is given (`engineIdFor`, in `engines.ts`, mirroring the Engine module's domain), so the web names a new engine's models before Save. A mark's colour is one of the four names or a custom `#rrggbb` in lower case (`projects.ts`), `isCustomMarkColour` telling them apart. Only the service's adapters import it.

**Traps:** A Project's commands are `installCommand` apart and `commands`, a list in the order added (`projectCommandSchema`: key, name, `kind` of `projectCommandKindSchema`, command line), never fixed build, lint and test fields; a Script Stage's `command` (`scriptStageCommandSchema`, `stages.ts`) is `publish` or any key `projectCommandKeySchema` (`projects.ts`) allows, the same key rules the service words in its own check, never `install`; a change sends the name, kind and line whole by key (`commandChangeSchema`), never a key. A Proposal of commands (`proposedProjectCommandsSchema`) gives each command by key with `from` null for one added and `to` null for one removed, and an environment check's `checks` are a union by `step`: `worktree`, `install`, then a `command` step per command, with its key, name and kind. A Project's `icon` and `logo` are never null: each is `{ light, dark }` (`projectImageVersionsSchema`), either version null, and `project.image-changed` names the `palette` changed. `PROJECT_IMAGE_EXTENSIONS` only narrows what the Repository file browser offers for an Icon or a Logo; the service still reads what a file is from its contents. `baseBranchFolderQuerySchema` turns the comma-joined `extensions` into a list, so what the web sends is a string and what the service reads an array. A subscribe or unsubscribe message (`events.ts`) may carry a `threadId`, its scope; a type in `THREAD_SCOPED_EVENT_TYPES` reaches only subscriptions scoped to its event's `threadId`, so its events must carry one. An event the web sees needs its schema in the union the web parses, and the service's WebSocket adapter forwarding it ([module template](../../../apps/service/docs/module-template.md)). The files import each other without a cycle: `pipelines.ts` imports `conversations.ts`, so a Stage's schema lives in `stages.ts`, which a Proposal of a Pipeline's Stages or of a Stage template's Stage (`stage-template`) names. `stages.ts` imports `projects.ts` for `projectCommandKeySchema`, the key rule (install and publish refused) an Agent Stage's `permissions.commands` lists; absent keeps every Project command, and an empty list is refused. A Project's run environment joins a Project's setting and a Task's state, so it lives in `run-environments.ts`, which imports `projects.ts` and `work.ts`. Where a Task in Planning is planned is on both sides of the Task page: the Task's `initiativePlanningThreadId` (`work.ts`) and the Planner's tab's `planningThreadElsewhere` (`conversations.ts`) name the same Initiative's planning Thread, and `markedPlanned` with the Initiative's `planningThreadId` gives the Initiative page its planning progress. Start Ready Tasks' answer (`readyTasksStartedSchema`, `work.ts`) names each Task by id and title, so the Initiative page lists and links them without the Task list, and a queued one's `place` counts from 1 as `GET /queue` numbers it, read after the run.
