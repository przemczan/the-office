# Contracts: map

**Owns:** the HTTP and WebSocket contract, as zod schemas and their types: the one thing the service and the web share. Also the links to a record's page (`record-links.ts`), which the web writes and the service reads as mentions, the Open page a chat drawer message goes with (`open-page.ts`), and the Project filter's rule (`project-filter.ts`), which the web narrows by and `GET /search` will, and the id a new engine is given (`engineIdFor`, in `engines.ts`, mirroring the Engine module's domain), so the web names a new engine's models before Save. A mark's colour is one of the four names or a custom `#rrggbb` in lower case (`projects.ts`), `isCustomMarkColour` telling them apart. Only the service's adapters import it.

**Users** (`users.ts`, spec §2.10): linked identities and Continue with a provider are generic over `identityProviderSchema` (`github`, `google`): `identityCallbackPath(provider)` is the one callback under `/api/sign-in`, the GitHub module lists it in the App's manifest and the users module serves it; `SIGN_IN_FAILED_PARAMETER` and `LINK_FAILED_PARAMETER` carry why to the sign-in page and to `LINKED_IDENTITIES_PATH`; `signInWaySchema` has `github` and `google`; the linked identity list carries `unavailableHere` (`wayUnavailableSchema`, shared with the sign-in page's `unavailable`), and `identityCallbackUrlsSchema`'s `thisAddress` is null where the provider doesn't work. The Google OAuth client is `googleClientSchema` (`clientId`, `secretSet`, never the secret), `GET` answers it in `googleClientSettingSchema` (null before one is saved) and `PUT` sends `saveGoogleClientSchema`, an empty secret keeping the saved one. the sign-in outcome is a union on `outcome`, `signed-in` or `set-password` (a right one-time password, which sets no cookie), and the sign-in refusal's `refusal` adds `expired`; a user in Settings › Users is `userSchema` (`you`, and `oneTimePasswordExpiresAt` while they haven't set their own password), and a one-time password is only ever in the answer that made it (`addedUserSchema`, `oneTimePasswordSchema`); the account carries the user's `appearance`, ids from `PALETTE_IDS` and `DENSITY_IDS` or null; `userWebEventSchema` is `user.created`, `user.changed` and `user.removed`, each naming the user. The sign-in page lists `ways` (`password`, `passkey`) and `unavailable` (a way set up that doesn't work at this address, `reason` `ip-address` or `needs-https-domain`, `elsewhere` where it does); the refusal `passkey` is one answer for every failed passkey sign-in. **Passkeys** (`passkeys.ts`): the WebAuthn JSON in its own zod shapes, independent of any library (creation and request options, the registration and authentication answers, base64url throughout, no extensions), a passkey on the account with `at` (`this-address`, `other-address` with `otherAddress`, `old-address`), the list with `addingUnavailable`, and `PASSKEY_NAME_MAX_LENGTH`.

**Traps:** A Project's commands are `installCommand` apart and `commands`, a list in the order added (`projectCommandSchema`: key, name, `kind` of `projectCommandKindSchema`, command line), never fixed build, lint and test fields; a Script Stage's `command` (`scriptStageCommandSchema`, `stages.ts`) is `publish` or any key `projectCommandKeySchema` (`projects.ts`) allows, the same key rules the service words in its own check, never `install`; a change sends the name, kind and line whole by key (`commandChangeSchema`), never a key. A Proposal of commands (`proposedProjectCommandsSchema`) gives each command by key with `from` null for one added and `to` null for one removed, and an environment check's `checks` are a union by `step`: `worktree`, `install`, then a `command` step per command, with its key, name and kind. A Project's `icon` and `logo` are never null: each is `{ light, dark }` (`projectImageVersionsSchema`), either version null, and `project.image-changed` names the `palette` changed. `PROJECT_IMAGE_EXTENSIONS` only narrows what the Repository file browser offers for an Icon or a Logo; the service still reads what a file is from its contents. `baseBranchFolderQuerySchema` turns the comma-joined `extensions` into a list, so what the web sends is a string and what the service reads an array. A subscribe or unsubscribe message (`events.ts`) may carry a `threadId`, its scope; a type in `THREAD_SCOPED_EVENT_TYPES` reaches only subscriptions scoped to its event's `threadId`, so its events must carry one. An event the web sees needs its schema in the union the web parses, and the service's WebSocket adapter forwarding it ([module template](../../../apps/service/docs/module-template.md)). The files import each other without a cycle: `pipelines.ts` imports `conversations.ts`, so a Stage's schema lives in `stages.ts`, which a Proposal of a Pipeline's Stages or of a Stage template's Stage (`stage-template`) names; a Proposal of a Project Pipeline (`project-pipeline`) carries `projectPipelineFieldsSchema` (name, description, `basePipelineId`, Stage changes of `stageChangeSchema`) as `from` (null for a new one) and `to`, and `pipelineId` null until a new one is applied; `PROPOSE_PROJECT_PIPELINE_TOOL` names its tool, hidden behind the card. `stages.ts` imports `projects.ts` for `projectCommandKeySchema`, the key rule (install and publish refused) an Agent Stage's `permissions.commands` lists; absent keeps every Project command, and an empty list is refused. A Project's run environment joins a Project's setting and a Task's state, so it lives in `run-environments.ts`, which imports `projects.ts` and `work.ts`. Where a Task in Planning is planned is on both sides of the Task page: the Task's `initiativePlanningThreadId` (`work.ts`) and the Planner's tab's `planningThreadElsewhere` (`conversations.ts`) name the same Initiative's planning Thread, and `markedPlanned` with the Initiative's `planningThreadId` gives the Initiative page its planning progress. Start Ready Tasks' answer (`readyTasksStartedSchema`, `work.ts`) names each Task by id and title, so the Initiative page lists and links them without the Task list, and a queued one's `place` counts from 1 as `GET /queue` numbers it, read after the run. Project Pipelines (`pipelines.ts`): a Stage change is `stageChangeSchema` as an edit gives it (its `stageName` optional, refreshed by the service on save) and `keptStageChangeSchema` as read (with it), both in `stages.ts` beside the Stage so a Proposal can name them; a Change's `fields` are a strict object that needs at least one field, `null` clearing an optional one, never `key` or `kind`. A Project Pipeline reads with `rows` (every row, a removed one kept, each with its `origin` and the base Pipeline's Stage) and `stages` (what a Task gets) side by side, and `broken`; the web never builds Stages itself. `GET /pipelines` answers `officeWidePipelineSchema` (with `builtOnBy`), whose extra field `pipelineSchema` strips, so today's readers of `pipelineListSchema` are unchanged; `pipelineCheckSchema` carries `breaks`, which a Stage template's check answers empty. An Initiative's `pausedAt` is a mark beside its active state, as `archivedAt` is beside an ended one; Pause and Resume the Initiative answer `initiativePauseAnswerSchema` (the Initiative and the ids of the Tasks changed). A Task and Now's running Task carry what holds a Paused one (`pausedBy`, `taskHolderSchema`: `alarm`, `initiative`, `usage-window`, or null for the user's own Pause) and `resumesAt`, when a Task the usage window holds resumes by itself; a Task its Initiative's Pause holds shows plain Paused. `usageWindowWords` (`engines.ts`) mirrors the Engine module's own, so the web words a usage window as the service's queue reasons and Notifications do. A Decision (`decisionSchema`) has a `kind` (`question`, `approval`, `request`, the last with no options) and a `taskId` that is null for a call made from a chat; `answeredByTheOffice` marks a chat call that fell back to the user and went back to its caller. Work's `authorSchema` names a user's record by `user: userRefSchema.nullable()` (`users.ts`: their id and their name then), null on a record from before users existed until the first user claims it: the web words that "the user". Conversations names its users the same way: a user message's `writtenBy`, a `changes-allowed` line's `by`, a Decision's `answeredByUser` (the user who answered it themselves; null for a Consultant's, The Office's or one at the user's request, whose `atUsersRequest.user` names the user who asked) and a Proposal status's `by`.
