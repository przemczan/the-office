# GitHub: module map

**Owns:** Sign in with GitHub (spec §5.3): the GitHub App the user registers from Settings › Office identity by GitHub's manifest flow, kept in one row (`github_app`: Client ID, slug, owner). `GET /github/app/manifest` hands the browser a form to post to GitHub's new-App page with an unguessable state (`AppRegistration.manifestForm`, states kept in memory for GitHub's hour); GitHub sends the browser back to `GET /github/app/registered?code&state`, which converts the code (`POST /app-manifests/{code}/conversions`), replaces any App kept before, publishes `GitHubAppRegistered` and redirects to Settings › Office identity, a failure carrying why in `registrationFailed`. Later steps of task 46 add the device flow, the user token and its refresh, and the repository list.

**Talks to:** GitHub, on the base URLs `GitHubModule.register(urls)` is given (`GitHubUrls`, GitHub's own by default), through the `GitHubApi` port (`GitHubRestApi`); the web, through `github.changed`. Tests use `FakeGitHub` from `index.fixtures.ts`: one server on 127.0.0.1 standing for GitHub's website and its REST API (under `/api/v3`, so a client dropping its base's path is caught), registering an App from a posted manifest and converting each code once.

**Traps:** the conversion's answer holds the App's private key, client secret and webhook secret. `GitHubRestApi` parses only the Client ID, slug and owner, and a failure names GitHub's status, never its body, so no secret reaches a log, an event or the database. The manifest leaves out a name (unique on GitHub, so the user picks one on GitHub's page) and a webhook; Device Flow can't be asked for in a manifest, so the App needs it turned on in its settings. `redirect_url` is built from the address the request reached The Office on, not the address the service listens on.
