# Busy-work: module map

**Owns:** the work going on now that a scheduled Office update or restart waits for (spec §5.1 Defaults, "Updating The Office"; §5.3 Modules), and the hold a scheduled one puts on new work. `BusyWork` (in memory, so a restart ends it all): each module counts its own item (`BusyItem`: a `BusyKind` and its label) where it starts and ends it, with `begin`, whose `EndBusyWork` ends it, or `during`, and announces `BusyWorkChanged` with the count in the background; `list` gives what is going on. `ScheduledExitHold` holds the one `ScheduledExit` (an update or a restart; generic over the target an update carries, which this module never reads) so Work's Start conditions and Pipelines' Stage interpreter wait while one is scheduled, with `waitWords()` (`OFFICE_UPDATE_SCHEDULED`, `OFFICE_RESTART_SCHEDULED`; `ScheduledExitWait`) and `isScheduled()`. `BusyWorkModule` provides and exports both.

**Talks to:** nothing but the platform (`EventBus`, `DomainEvent`). Engine, Conversations, Pipelines, Projects, Run environments, Actions and Work import `BusyWorkModule` and its services from `index.ts`; Office updates (the one module that schedules an exit) sets the hold through `ScheduledExits` and reacts to `BusyWorkChanged`. It never imports Office updates: that would make a cycle with Engine, which Office updates imports.

**Traps:** `BusyWork.begin` announces `BusyWorkChanged` in the background, so a turn counted mid-call never waits on the reactions. `ScheduledExitHold.hold` is for Office updates' `ScheduledExits` alone, which announces the change. `ScheduledExit`'s `target` is `unknown` here; the module that schedules an update casts it back to its own type.
