# Projects: module map

**Owns:** Projects (`projects`): path, the Repository URL of a cloned one (given only with its clone's folder as the path), the mark (label and colour together, the colour one of the four names or a custom `#rrggbb` in lower case, `PUT /projects/:id/mark`, one rule with adding a Project: `markProblem`), its Icon and Logo, each in a light and a dark version (`ProjectImages`: `POST`/`DELETE /projects/:id/images/:image/:palette`, `POST …/:image/:palette/from-repository`, each version changed on its own, a copy of a committed file read through `BaseBranchFiles.file` and then an upload in all but its source, nothing of the path or commit kept; `GET …/:imageId/content`, answering only for an image the Project holds now in either version; each file `<office-data>/project-images/<image id>`, what it is read from its bytes alone by the platform's `images/` rules, and the row keeping `{ light, dark }` per image as jsonb, each its id and media type or null; migration 0113 made every image held before its light version), the install command (`PUT /projects/:id/install-command`) and the list of commands (`commands` as jsonb, in the order added: each a key fixed once added, a name, a kind, `build`, `lint` or `test`, and a command line; `POST /projects/:id/commands`, `PUT`/`DELETE /projects/:id/commands/:key`; every Project starts with `STARTING_COMMANDS`, and migration 0121 moved the old build, lint and test columns into the list and rewrote stored environment checks and Proposals), install inputs, publishing mode, Publish's before and after lines (`beforePublishingCommand`, `afterPublishingCommand`, `PUT /projects/:id/before-publishing-command` and `…/after-publishing-command`, one line each and blank clearing it, as they aren't Project commands, `changePublishingLine`; the run environment question's answer, given with `POST /projects` (`runEnvironmentAnswer`, not part of `NewProject`, so a Project Devops onboards is added with none and asked at its first Start) and applied once the Project is added: No sets Off here, Yes runs Set up run environment through `RunEnvironmentSetUpRegistry`, which Run environments fills as it starts, and an answer that fails is logged and leaves "not-decided"), the committed files another module reads (`CommittedFiles`: the base branch's last commit known here or fetched now, a Task's branch tip, and a text file at a commit, at most 1 MB), the engine cascade's Project levels (the Project default, "Use for every Role" allowed only with one, and the Project's Role overrides, each an engine id and a model, at most one per Role key; the environment check of the saved environment, which changes nothing (`environment_checks`: steps `worktree`, `install`, then a `command` step, with its key, name and kind, for each command in the list's order); The Office's own git (`ports/git.ts`, `CommandLineGit`) under per-repository locks, every command on the Office identity through `GitProcess`; which part of the identity the base branch's remote needs (`ProjectRemotes`: `GET /projects/:id/remote-needs` and the environment check's failed fetch); **Traps:** `PostgresProjectRepository.find` and `list` go through the platform's read scope (`readOnce`, platform MAP): within one GET they answer the same objects to every caller, who never changes them, and every write of their tables runs through `forgettingReads`, a new writer too.

- `ProjectService.add(given, answered?)`: only the user's add (`POST /projects`) answers the run environment question, with who answered (`RunEnvironmentAnswered`), which a Yes passes to Run environments' set-up; any other add, such as a Proposal's, leaves it Not decided yet.
- A Project's command may be not set: install and the three starting commands may be blank when it was added (`newProjectProblems` checks only that a command given is one line, `commandLineProblem`), while a change (`PUT /projects/:id/install-command`, `PUT /projects/:id/commands/:key`, Devops' Proposals) and any command added later refuse a blank one (`commandProblem`, `commandFieldsProblems`), so a set command is never cleared. A new command's key passes `commandKeyProblems` (`install` and `publish` reserved); a key is never changed, since Pipelines name commands by it. Nothing runs a blank line: with no install command `Worktrees.installOnce` installs nothing and writes no record, so setting it installs at the next Stage; a Script Stage's `ScriptCommands.run`, given a key the Project lacks or a blank line, answers `could-not-run` naming the key, with how to set it and an empty `commandLine`, which `scriptStageOutcome` gives as the failure alone; `AgentCommands` answers `no-command`; the environment check starts it `skipped` and still passes (`isCommandSet`).
- A Project's default Pipeline always runs there: `ProjectChecks` refuses a default that runs a key the Project lacks, and removing a command the default runs, by hand or by Devops' Proposal (`removedCommandKeys`). The default may be one of its own Project Pipelines, weighed by its built Stages; another Project's and a Broken one are refused (`defaultPipelineOwnerProblems`), and a new Project (Add a Project, onboarding) takes an office-wide one only. `KnownPipelines.commandsNamedBy` answers any Project's Project Pipeline with its Project, so `ProjectChecks` reads the owner's name from `ProjectRepository`. Removing a command another Pipeline runs isn't refused; its Stage fails could-not-run. Keys alone count, so a blank command passes.
- The test handling (one re-run on failure, tracked files restored, written files moved out, the screenshots folder put back) goes by the command's kind, not its key: `ScriptCommands.run` gives it to every command of kind `test` (a `test-full` too) and none to build or lint kinds.
- A condition command (`ScriptCommands.runCondition`) runs once, never again on failure, even of kind `test`, and whatever its kind gets the rest of the test handling (restore, written files moved out to `<stageRunId>/condition-<key>-<8 hex>` under `test-output`, an id per run since one Stage run may weigh the same key twice, the screenshots folder put back), as weighing a route must leave the work as it was. A missing key or blank line gives `could-not-run` as `run` does (`setCommandOf`). Its run tells the run environment it reads the Stage runs' file (`readsStageRuns`): one already running without that folder mounted refuses it `could-not-run`, nothing run, saying to stop and start the Task's run environment.
- Devops' Proposal of commands (`ProposedCommands`, `proposedCommandsProblems` in `domain/proposed-commands.ts`) keeps each field it changes as it was (`from`) and as proposed (`to`): the install command, the install inputs, the before and after publishing lines (blank `to` clearing one), and each command by key, `from` null for an added one and `to` null for a removed one. It applies all or nothing and is refused once any `from` no longer holds, by the same rules as the Project page.
- An image's bytes never change: every upload is a new id, so its address is cached for good and replacing one needs no cache busting; don't overwrite a file under an id. Its size limit is held twice, `IMAGE_SIZE_LIMIT` in the platform, for what doesn't come through the upload route, and the contracts' `IMAGE_UPLOAD_BYTES` for `uploadBody` and the web, as only adapters import the contracts; the controller's test at exactly the limit keeps them equal. The content route's headers are what stop an SVG's script when its address is opened directly, so keep them.
- A Secret variable's value never leaves the service (spec 5.5, "Secret variables"): responses and events take the environment through `shownEnvironment` (`toEnvironmentResponse`), and the environment check events carry no environment at all. The environment is saved only by the user's Save (`PUT /projects/:id/environment`, `ProjectService.changeEnvironment`), where a Secret variable sent without a value keeps the Project's (`editedEnvironment`); the environment check tries the saved one and saves nothing. The stored check record keeps the values it ran with. `ProjectRecords` (`list_projects`) names each Secret variable and secret Server value without its value. Rows saved before Secret variables have no `secret` flag (`environmentOfStored`). Output is masked by one `OutputMask` (domain, exported for the run environment's command): in `commandRunOf` and, chunk by chunk, in every file written while a command runs; Conversations gets it through `ProjectService.outputMaskOf`, bound to its `ProjectOutputMasks` port in app.module.ts.
- A `CommandRun` carries a command's output twice: `output`, filtered for an Agent to read, and `wholeOutput`, the last 64 KB for the user's Stage history. The shell runner's 16 MB tail feeds both, so `filteredOutput` sees failures long before the end; don't shrink it to the 64 KB. An environment check keeps only the first (`CheckedCommandRun`).
- A worktree's install record (`installFingerprint`) holds where the install ran: the host, or the run environment's image by its key (`TaskRunEnvironments.imageOf`, nothing built). Turning the setting on or off, or a new image, installs again, so what was installed in one place is never used in the other; the host's leaves the place out, so records made before run environments still hold.
- A run environment that can't be made or started gives the command `could-not-run` with why in its output, never a run on the host; a stop while waiting gives `stopped` with nothing run. Both come back as a `CommandRun`, so the test re-run, restore, moved files and screenshots work as on the host.
- An Agent's command (`TaskWorktrees.runForAgent`) runs as given: Projects never judges a command line, Pipelines asks the session's Office rules first, as the session's Bash call. So on the host a written line runs in the Bash Agents have (`inAgentBash`), never cmd.exe, which would read `^` and `%VAR%` past the rules; in a run environment it runs in the image's sh, as every command does. Its output file is the caller's, in the session's folder its rules let it read; the shell runner writes every byte there as it comes, besides its 16 MB tail, and in a run environment the runtime appends to it, so `ProjectsTaskRunEnvironments` empties it first and keeps it after. The install by its key runs even when up to date, without updating the install record.
- The Project limit's maximum is held twice, `PROJECT_LIMIT_MAX` in the domain and in the contracts (the Office-wide limit's), as only adapters import the contracts; the controller's test at exactly the contract's maximum keeps the domain's no lower.
- The module is registered once in `AppModule`, so every git change on a repository goes through the same locks.
- Publish lands a Task as one commit with the Task's commit message (`CommitMessage`, spec §2.3 "The Task's commit message"): merge mode takes a moved base into the Task's branch by one merge commit (`takeInByMerge`), never a rebase, which would drop a merge Resolve made and bring its conflicts back; then `Git.writeCommit` (`commit-tree`) writes the branch's tree on the fetched base alone and `Git.pushCommit` pushes that commit, no local branch moving, so the Stage commits stay on the Task's branch. The `merged` Publication's `commit` is the landed commit and `head` where the Task's branch is left, which Pipelines expects HEAD at. Since the base then doesn't hold the Task's branch, "nothing to publish" asks `Git.addsNothing` (the base holds the branch, or merging it leaves the base's tree as it is), not `contains`. `published-from` stays the fork point of the branch, whose diff is the landed commit's. A commit The Office writes takes git's identity as `git commit` does (the repository's or the user's config); the Linux run environment has none, so test repositories set their own. Push + PR takes the message's subject as the title and the rest as the body.
- A Task of an Initiative with a Pipeline has two bases, its Initiative's branch then the base branch (`Worktrees.freshBases`, spec §2.3): its worktree starts at the fresh Initiative's branch, at Planning or at Start alike, and the branch update, Resolve and Publish take in the Initiative's branch first, then the base, each a fast-forward or one merge commit, the first conflict ending it and naming its branch (`BranchUpdate.conflicted.from`, `ResolveStart.base`). A clean first merge has moved HEAD: `BranchUpdate.conflicted.commit`, `ResolveStart.commit` and a `base-moved` Publication's `commit` carry it (a give-back aborts only the conflicting merge), or Pipelines' after-turn check fails the Stage. Resolve's `finish` names the base by what `MERGE_HEAD` is in (`mergingBase`). `TaskBases.of` throws while no lookup is registered and never falls back to the base branch, which would publish an Initiative's Task there: Projects' fixtures register one (`TaskBasesForTests`, `startProjectsApplication`).
- Publish of such a Task (`mergeIntoInitiativeBranch`, with the `publishing-mode` target) lands it as one commit whatever the Project's publishing mode: never a rebase, never a pull request; `branch-only` still pushes the Task's branch alone. The commit's parents (`landingParents`) are the Initiative's branch when it holds the base; else the base's own merge into it, written first (`Git.mergedTree`, then `writeCommit` with `mergeMessage`); else, when that merge would conflict, the Initiative's branch and the base both. It pushes that commit to `initiative/<short name>` on the base branch's remote without force first (`Git.pushCommit`), then moves the local branch with `Git.moveRef` (`update-ref <ref> <new> <old>`, never `setRef`), so a refused push or a branch moved meanwhile leaves both as they were; with no remote only the local branch moves. It fails when the branch is checked out in any worktree but this Project's Publishing Task's, the user's own checkout among them (`Git.worktreeOf`), since moving it would change a checkout under someone; see the Publishing Task's trap below. All of it, like every Publish, runs in `git.exclusively`.
- Changes and a Brief's diff of such a Task diff from both bases (`Git.branchChanges` and `diffSummary` take revisions, which `Worktrees.changeBases` resolves without fetching: the newer known of the local and the fetched Initiative's branch, `TaskBases.knownInitiativeBranch`, then the base branch's tracking ref): from the newer fork point, or from the two merged (`merge-tree --write-tree`) when neither holds the other, the first's on a conflict. After Publish they diff from the pair `published-from` (the Initiative's old tip) and `published-from-base` (the base commit taken in), so base commits taken in never show as the Task's.
- A Publishing Task's worktree holds the Initiative's branch itself (`Worktrees.addOnInitiativeBranch`, in `git.exclusively`): fast-forwarded first to its remote's copy when that is ahead (`moveRef` from the commit read), refused, saying where, while any other worktree or the user's checkout has it (`initiativeBranchCheckedOut`). Removing it keeps the branch, and a dropped one's worktree must go, or the next Publishing Task can't check the branch out. Never call a sync `office/<task>` for a Task's branch.
- A Publishing Task's Publish (`publishPublishingTask`, chosen in `publish` by its `publishing-task` base, all of it in `git.exclusively`): `freshBase`, then `freshInitiativeBranch` (gone or diverged fails), the worktree fast-forwarded to a remote that is ahead; nothing to publish when the base holds the branch; `branch-only` pushes the Initiative's branch alone; Push + PR asks `whyCannotOpen`, goes to Resolve on `conflictsOf` the base, pushes `initiative/<short name>` and opens or links the pull request from it; merge takes in the base by one merge commit in the worktree (never a rebase), pushes the branch, then the base on the remote without force, then the local base only when nothing has it checked out and it holds nothing of its own. A base branch tracking no remote fails with `noRemoteError`. It records `published-from` (the merge base with the base, after the merge) and `refs/office/published/<task>` (the tip): Changes then read `published-from...published`, so a branch fix Tasks moved on after Publish doesn't change them; before Publish they diff the branch from the base's tracking ref (the local base without an upstream). Branch updates and Resolve take in the base branch only, a fast-forward or one merge commit.
- A fix Task's Publish into an Initiative's branch that this Project's Publishing Task's worktree holds (`Publishing.holderOf`, the Task found by the worktree's path, `Worktrees.taskOfWorktree`) fails while that worktree has changes not committed; otherwise it pushes the remote first, then fast-forwards that worktree to the new commit (never a ref moved under its files), sets `refs/office/moved-to/<publishing task>` and answers `merged` with `movedWorktreeOf`. `movedAlongBase` takes a Publishing Task's HEAD at that ref as a move along its base. Held anywhere else, the user's own checkout among them, it still fails, saying where. Pipelines must keep it from running during the Publishing Task's Stage.
- After Publish, Changes diffs from `refs/office/published-from/<task>` (spec [2.3 Defaults](../../../../../docs/spec/2.3-pipelines.md#defaults)), the branch-only push (a Publish Stage's `branch-only` target) included.
- A clone is made in a hidden folder beside its own and moved there when complete (`adapters/git/git-clone.ts`), so a folder found there is a whole clone, used again, with `origin` pointed at the URL given last (one folder holds every spelling and transport of a URL) and fetched, so branches made on the remote since are there. A clone, `ls-remote` and their failure reasons decide the identity on the URL git reaches (`Git.reachedUrlOf`, `insteadOf` applied): the user's config may rewrite https to ssh, or, in the tests and e2e, a made-up host to a local folder. Only the default branch exists locally after a clone: adding it as a Project accepts a base branch that is only `origin/<branch>` and makes it locally, tracking that (`ProjectService.add`); a path-added repository's base branch must already be local.
- `GitProcess.output` decodes as UTF-8, which damages a picture: read bytes with `GitProcess.bytes` (`CommitTree.bytesOf`). Ask `sizeOf` before reading a file of unknown size, as output over 64 MB fails as if git couldn't run. A link's `kindOf` is "file" and its bytes are the target's path, so an image from one is refused by its contents; Git LFS pointers are too.
- `CommitTree.kindOf` asks `ls-tree` by a literal pathspec, since a path is someone's words: bare `:(…)` makes git fail. `readBranchTip` shares it (`adapters/git/git-commit-tree.ts`).
- An Initiative's branch is made by `Git.createRef` (`update-ref <ref> <commit> ""`), never `setRef`, which overwrites: git refuses a ref already there, so two Confirms can't take one branch, and the loser's refusal names it taken. `remoteHasBranch` asks the remote itself (`ls-remote`), not the remote-tracking refs known here, so a name taken there since the last fetch is refused too. `InitiativeBranches` never pushes; `removeRef` checks the expected commit, so a rollback can't drop a branch someone moved.
- A fetch or push runs on the URL git resolves for the remote name (`ls-remote --get-url`, `remote get-url --push`), never the name itself, which `parseGitRemote` would read as a local path; a remote with several URLs gets the identity of its first.
