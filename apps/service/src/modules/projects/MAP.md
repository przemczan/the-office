# Projects: module map

**Owns:** each Project's recent CI runs, in memory only (`CiRunWatch`, no table): every 15 s (`Schedule.every("ci runs")`, `CI_RUN_WATCH_EVERY`) a round lists again, as `recentRuns(remote, 30)` on the code host that reaches the base branch's remote, each Project with a run queued, waiting or running (`isGoing`), each tried 60 s ago or more (`IDLE_CI_RUNS_EVERY`), and each a refresh or a re-run asked for; `whyCannotRead` giving a reason marks its runs stale with no problem and asks nothing; a `CodeHostRefused` keeps the last runs, stale, and holds a `cannot-read` problem in the host's words (any other failure an `unreachable` one with the host's name and when it first failed); `CiRunsChecked` only when the runs, their staleness or the problem changed, reaching the web as `ci-runs.changed`. `GET /ci-runs?projectId=` answers the runs newest first (`startedAt ?? updatedAt`, then id), each with the Task of its `office/<task id>` branch (`taskIdOf`), and each Project's listing (`checkedAt`, `stale`, `problem`); `POST /ci-runs/refresh?projectId=` answers 202 at once, coalesced and skipped within 10 s of the same refresh (`CI_REFRESH_AT_MOST_EVERY`). Projects' first Office action, `rerun_ci_run` (`ProjectOfficeActions`, its routes in `ProjectOfficeActionsController`, `POST /projects/:projectId/ci-runs/:runId/rerun`): the run found in the watch's last listing or else listed from the host, refused unless failed or cancelled (`ensureRerunnable`), re-run with all its jobs or the failed ones, then the Project listed again at once (`refresh(projectId, { force: true })`); the host's refusal, such as GitHub's 403 without Actions write, answered as a `ProjectRefused` (422, the Agent's tool an error) in its words. Starting a Workflow by hand, the Office action `start_workflow` (`POST /projects/:projectId/workflows/:workflow/start`, beside the re-run): the Workflow found by its file name among `manualWorkflows(remote, ref)`, refused when its file at the ref declares no `workflow_dispatch`; the inputs checked and sent as text, defaults filling the rest (`inputsToSend`, every reason refused at once before the host is asked); then `expectRun(projectId)` lists the Project at once and every round for 60 s (`EXPECTED_RUN_WITHIN`, asked again starting again), as the host answers a start with no run. What a start offers, read through `ManualWorkflows` (application) on the same code host: `GET /projects/:projectId/workflows?ref=` (the base branch when left out, the ref answered) and `GET /projects/:projectId/refs` (with `baseBranch`), both on `CiRunsController`, answering empty lists with `problem` in plain words, never an error, when the host can't be read (`whyCannotRead`), refuses or fails. The pull requests The Office opened (`pull_requests`, one row per remote URL and number, the Task by id alone with no foreign key, `ended_at` once merged or closed; `PullRequestRepository`): Push + PR's Publish records each it opens or finds open (`record` upserts on the remote and number, keeping the status read last) and publishes `PullRequestOpened`, a failure to record logged and never failing the Publish; `PullRequestWatch` refreshes them every minute (`Schedule.every("pull requests")`) and on `POST /pull-requests/refresh` (202, coalesced, skipped within 10 s of the last round): per Project, the base branch's remote URL as git resolves it, skipped without one or when no code host reaches it; `whyCannotRead` giving a reason marks its open rows stale and holds the reason as its problem; else one `openPullRequests` list, an `office/<task id>` branch with no row adopted, `pullRequestStatus` only for a row whose head or base commit moved or whose checks are pending or unknown or mergeable unknown (`needsStatus`), and one last read for an open row no longer listed, which ends it through the repository's conditional `end` (`UPDATE … WHERE ended_at IS NULL RETURNING`, the only way a row ends; `save` writes the status alone, never `state` or `ended_at`), publishing `PullRequestMerged`/`PullRequestClosed` by `ON_THE_CODE_HOST` only when that update ended it; a row kept as ended that is listed open again is reopened (`reopen`, conditional on `ended_at IS NOT NULL`) with `PullRequestReopened`; a `CodeHostRefused` keeps the last status, marks the rows stale and holds an `unreachable` problem with when it failed and when the list was last read, which the web words in the user's own time ("GitHub couldn't be reached at 14:02; showing what it said at 13:58."), until a good round (problems in memory only, dropped with their Project); `PullRequestsChecked` only when something shown changed; Work › Pull requests' Merge and Close (`PullRequestActions`: `GET /pull-requests/:id/merge-methods`, the host's allowed methods with `recommendedMergeMethod`, merge for an `initiative/` branch and squash otherwise, warning when an Initiative's can't be merged by a merge commit; `POST /pull-requests/:id/merge` `{ method }` at the row's `headCommit` as `expectedHeadCommit`, and `POST /pull-requests/:id/close`, each 204, refusing an ended row, a method not allowed and a status not read yet, then ending the row by the same `end` and publishing `PullRequestMerged`/`PullRequestClosed` by the user only when it ended it; The Office never deletes a branch; a refusal, `PullRequestRefused`, answers 409 `{ reason, refresh }` through `PullRequestRefusalsFilter`, never logged, `refresh` true for `CodeHostChangedSince` and an ended or unread row); every one of these events reaches the web as `pull-requests.changed`. `GET /pull-requests?projectId=` answers the open rows newest first and the problems, narrowed to one Project when named. Projects (`projects`): path, the Repository URL of a cloned one (given only with its clone's folder as the path), the mark (label and colour together, the colour one of the four names or a custom `#rrggbb` in lower case, `PUT /projects/:id/mark`, one rule with adding a Project: `markProblem`), its Icon and Logo, each in a light and a dark version (`ProjectImages`: `POST`/`DELETE /projects/:id/images/:image/:palette`, `POST …/:image/:palette/from-repository`, each version changed on its own, a copy of a committed file read through `RepositoryFiles.file` and then an upload in all but its source, nothing of the path or commit kept; `GET …/:imageId/content`, answering only for an image the Project holds now in either version; each file `<office-data>/project-images/<image id>`, what it is read from its bytes alone by the platform's `images/` rules, and the row keeping `{ light, dark }` per image as jsonb, each its id and media type or null; migration 0113 made every image held before its light version), the install command (`PUT /projects/:id/install-command`) and the list of commands (`commands` as jsonb, in the order added: each a key fixed once added, a name, a kind, `build`, `lint` or `test`, and a command line; `POST /projects/:id/commands`, `PUT`/`DELETE /projects/:id/commands/:key`; every Project starts with `STARTING_COMMANDS`, and migration 0121 moved the old build, lint and test columns into the list and rewrote stored environment checks and Proposals), install inputs, publishing mode, Publish's before and after lines (`beforePublishingCommand`, `afterPublishingCommand`, `PUT /projects/:id/before-publishing-command` and `…/after-publishing-command`, one line each and blank clearing it, as they aren't Project commands, `changePublishingLine`; run by `TaskWorktrees.runPublishingLine` with the Script Stage's time limit and extra variables over the Project's own, `TaskCommand.variables`); a route's condition command (spec §2.3, "The Project-command condition"), one of the Project's commands by its key, run by `TaskWorktrees.runConditionCommand` (`ScriptCommands.runCondition`, Pipelines' `TaskCommands` port, which installs first) where a Script Stage's command runs, with its time limit and `OFFICE_STAGE_RUNS_FILE` (`STAGE_RUNS_FILE_VARIABLE`) naming the file of the Task's earlier Stage runs Pipelines wrote under `<office-data>/stage-runs/<task>/`, set through `TaskCommand.variables` on the host and in the run environment alike, where that folder is mounted read-only at the same path (`TaskInRunEnvironment.stageRunsFolder`, `OfficeDataDirectory.stageRunsFolder`), default Pipeline, which of the repository's skills it uses ("Use this Project's skills", `PUT /projects/:id/use-project-skills`, and the keys turned off one by one, `projectSkillsOff`, `PUT /projects/:id/skill-use`; the skills themselves are never stored, so only what is off is kept and a new skill starts on), the Project limit (`projectLimit`: how many of its Tasks may be started at once, 1 by default, 1 to `PROJECT_LIMIT_MAX`, `PUT /projects/:id/project-limit`, announced by `ProjectLimitChanged`, on which Work's queue releases; Work weighs it at Start through its `KnownProjects` port), and the Run environment setting (`runEnvironment`: `not-decided` for every Project until the user picks On or Off, and `runEnvironmentSetUpProblems`, why a set-up Task's Done left it as it was; `changeRunEnvironment` refuses On with the definition's problems, which Run environments reads and passes in, so the rule lives here and the reading there; announced by `ProjectRunEnvironmentChanged`; the run environment question's answer, given with `POST /projects` (`runEnvironmentAnswer`, not part of `NewProject`, so a Project Devops onboards is added with none and asked at its first Start) and applied once the Project is added: No sets Off here, Yes runs Set up run environment through `RunEnvironmentSetUpRegistry`, which Run environments fills as it starts, and an answer that fails is logged and leaves "not-decided"), the committed files another module reads (`CommittedFiles`: the base branch's last commit known here or fetched now, a Task's branch tip, and a text file at a commit, at most 1 MB), the engine cascade's Project levels (the Project default, "Use for every Role" allowed only with one, and the Project's Role overrides, each an engine id and a model, at most one per Role key; `PUT /projects/:id/project-default`, `…/use-for-every-role`, `…/role-overrides/:roleKey`, null clearing; given to People's engine cascade by `ProjectService.engineLevelsOf`, bound to its `KnownProjectLevels` port in app.module.ts; a removed engine's levels moved by `ProjectLevelMoves`, registered in Engine's `EngineReferenceMoves` with `projectLevelMovesOf` for the removal's preview, past the checks (`moveEngineLevels`: to the replacement, or to none with the only engine, "Use for every Role" turned off before the default clears)); the environment check of the saved environment, which changes nothing (`environment_checks`: steps `worktree`, `install`, then a `command` step, with its key, name and kind, for each command in the list's order); The Office's own git (`ports/git.ts`, `CommandLineGit`) under per-repository locks, every command on the Office identity through `GitProcess`; which part of the identity the base branch's remote needs (`ProjectRemotes`: `GET /projects/:id/remote-needs` and the environment check's failed fetch); cloning a repository by its Repository URL into `<office-data>/repositories/<host>/<path>` before it is added (`RepositoryClones`: `POST /repositories/clones`, `GET …/:id`, in memory while the service runs, told to the web as `repository-clone.changed`); the files committed on a Project's branches, for the Repository file browser and the Files tab (`RepositoryFiles`: `POST /projects/:id/base-branch/fetch` fetches by `Worktrees.freshBase`, a failed fetch answering the last commit known here with why; `GET /projects/:id/branches?fetch=` the base branch first at its freshest commit known here, then the other local branches and the upstream remote's as `<remote>/<branch>`, each by name (`Git.branchTips`, symbolic refs left out), `fetch=1` fetching every branch of that remote first, pruning none (`Git.fetchRemote`), a failed fetch answering what is known here with `fetchProblem`; `GET /projects/:id/commits/:commit/folder` reads one folder from the Project's own objects, `Git.commitTree`, at most 1,000 entries; `GET …/:commit/file?path=&download=` its bytes, refused over git's 64 MB output cap (`GIT_OUTPUT_LIMIT_BYTES`, size asked first), typed by the bytes alone: a picture or an SVG by the platform's `images/` rules, UTF-8 with no NUL in its first 8 KB as `text/plain`, else `application/octet-stream`, always `nosniff`, a sandboxing CSP and kept for good, as a commit's file never changes; `GET …/:commit/file-preview?path=` `text`, `image`, `binary` or `too-large` over 1 MB without reading it; `file` reads one file's bytes for `ProjectImages`, its size asked first; a path outside the repository or a commit not here is refused); an Initiative's branch `initiative/<short name>` in a Project (`InitiativeBranches`: `make` refuses a name the repository has, fetches the base by `Worktrees.freshBase`, refuses a name the base branch's remote has, `Git.remoteHasBranch`, asked only when the base branch tracks one, then makes the local branch at the fresh base, `Git.createRef`; `Publishing`, `Resolving`); what each Task's branch starts from and publishes into (`TaskBases`, a registry Work fills as it starts with its lookup of the Task's Initiative, since Work reads Projects: the base branch, or `initiative/<short name>` for a Task of an Initiative with a Pipeline, spec §5.5; **Talks to:** the code hosts behind its `CodeHost` port, chosen by the remote's URL through `CodeHosts` (application, the first adapter whose `reaches` holds the URL; built in projects.module.ts from the adapters, today `GitHubCodeHost`, a thin wrapper of the github module's `GitHubPullRequests` and `GitHubIssues` turning their errors into `CodeHostRefused`, the github module's one instance given in `imports` by [app.module.ts](../../app.module.ts); a GitLab adapter would be one more entry there):
Publish asks `whyCannotOpen` before the push, on the URL git resolves for the base's remote, and pushes nothing when no host reaches it or no one is signed in, then opens the pull request; the watch reads them (`whyCannotRead`, `openPullRequests`, `pullRequestStatus`); `PullRequestActions` merges and closes them (`mergeMethods`, `merge`, `close`); the CI run watch lists runs (`recentRuns`) and `rerun_ci_run` re-runs one (`rerun`, `GitHubCodeHost` passing "failed" as only the failed jobs); `ManualWorkflows` and `start_workflow` read the Workflows declaring a start by hand and the refs, and start one (`manualWorkflows`, `refs`, `startWorkflow`, `GitHubCodeHost` mapping GitHub's input types to kinds and the file name to the id); registers `rerun_ci_run`'s and `start_workflow`'s Office tools on Engine's `OfficeToolRegistry` (`officeActionTool`), covered by `onboards-projects`; checks a default Pipeline, and that the Project has every command it runs (`commandsNamedBy`, refusing a change of the default, a new Project and a removed command the default runs, `domain/pipeline-commands.ts`), through its `KnownPipelines` port, bound to Pipelines' `PipelineLibrary` in [app.module.ts](../../app.module.ts); checks that an engine level's engine is listed and offers its model through Engine's `EngineModels` (`ProjectChecks.checkEngineModel`), but not that a Role is filled under a Role override's key, since People reads these levels and Projects can't import People; refuses a save of the engine levels that a check registered in `EngineLevelsChecks` refuses (People's capability check of the Roles a Pipeline names, registered through its `ProjectLevelsSaves` port, which [app.module.ts](../../app.module.ts) binds to the registry), weighing the Project read just before the save; moves the levels naming an engine being removed to its replacement (`ProjectLevelMoves`, registered in Engine's `EngineReferenceMoves`, `moveEngineLevels` with each change's own event, past the checks, which Engine's removal ran first); calls Engine, Skills and MCP servers (the Project page's Server values, `GET`/`PUT /projects/:id/server-values`, in `ProjectServerValuesController`; the library's refusals answered as the Project's).
Serves Work (`ProjectService`, `TaskWorktrees`, `InitiativeBranches`, bound to its `ProjectInitiativeBranches` port in [app.module.ts](../../app.module.ts) by `useExisting`, so its signatures are that port's, and `ProjectsFromRepositories` as `NewProjects`: a Proposal's Project by its folder, or by its Repository URL judged from the remote's branches with nothing cloned and, applied, cloned through `RepositoryClones.clone`, which waits, then added), Pipelines (`TaskWorktrees` as `TaskGit`, `TaskCommands` and `TaskPublishing`; `ProjectService` as `ProjectDefaults`, which the library asks before removing a Pipeline) and Conversations (`BaseCheckouts`; `ProjectRecords`, a Project's record as `list_projects` gives them all, for a Project's Open page: what its page shows, its last environment check and its Server values, read through MCP servers' `ProjectServerValues`, included; Devops' `read_repository` in their chat, reading a repository's local branches and the names and manifest files of its top level or one folder inside it before it is a Project (`LocalRepositories`, refusing a repository folder as adding a Project does, and a folder that leaves the repository or is git's own), or one on a host by its Repository URL: the remote's branches and the same of its default branch, read from that branch's last commit fetched alone into a bare repository in a temp folder removed after each read, nothing cloned (`RepositoriesByUrl`, `Git.readBranchTip`); and `ProjectService` for Devops' Proposals of commands and install inputs: `proposedCommandsProblems` and `changeCommandsAsProposed`; and Work's `NewProjects` for a Project to onboard: `add` and its dry run `newProjectProblems`, which applies the whole Proposal or none of it: judged against the row as it is held and saved in one update, each field still announced with its own event as the Project page announces it). **Kinds and issues** (docs/design/issues-as-tasks.html): each Project's default Pipeline per Kind (`feature_default_pipeline`, `bug_default_pipeline`, `chore_default_pipeline`, null following `default_pipeline`), resolved only by `defaultPipelineFor` (`domain/kind-default-pipeline.ts`), which `ProjectService.defaultPipelineFor` answers for Work's `KnownProjects`; `PUT /projects/:id/kind-default-pipeline` (`changeKindDefaultPipeline`, checked as the Project's default is, `ProjectKindDefaultPipelineChanged`, on the web as `project.default-pipeline-changed`). Its issue switches (`domain/issue-settings.ts`), `PUT /projects/:id/issue-settings` (`changeIssueSettings`: a label set or changed records the signed-in user as `issue_import_label_set_by`, kept while the label stays, forgotten with none; `ProjectIssueSettingsChanged`, `project.issue-settings-changed`). The `issue_links` and `issue_write_backs` tables (`adapters/postgres/issue-links.schema.ts`, `IssueLinkRepository`), unique remote and number, a link never deleted once its Task is made. A Project's issues are on the host of the remote its base branch tracks, by the URL git resolves (`ProjectIssueHosts`; `readable` refuses, in the user's words, no remote, a repository on no host, or no one signed in). `codeHostNameOf` gives every Project response its `codeHost` (the host's name, null for none), read from git's config alone, never the host, so a Project list stays cheap; each import claims the link first (`claim`, insert on conflict do nothing, so two imports at once make one Task), then `IssueTasks.create` (Work fills it at start, as `TaskBases`), giving the claim back (`release`) when Work refuses, then names the Task (`attachTask`); `IssuesImported` → `project.issues-imported`. `GET /issue-links?taskId=` answers the link with its newest write-back problem, or JSON null. `IssueWatch` (`Schedule.every("issues")`, `ISSUE_WATCH_EVERY` 5 minutes, one check at a time): per Project on a host, passed over in silence while `whyCannotRead` says anything; auto-imports the open issues with its label not linked, oldest first, at most 50, `importedBy` The Office, created by the label's setter with `createdByTheOffice`; reads each link whose Task hasn't ended and keeps `closed_on_host_at`, or clears it (the Task never moves), `IssueLinkChanged` → `issue-link.changed` when that flips; then `IssueWriteBacks.retry`. `IssueWriteBacks` is bound as `IssueWriteBack`, which Work's forwarder calls on a Task's start (with its title), Done and Drop (a Duplicate with the other Task's title): Done and Dropped set `task_ended_at`; "Comment on start and Done" comments "Work on this issue started in The Office: <title>." and "Done in #<pull request>." (`Worktrees.landedOf`, the ref `refs/office/landed/<task>` a merge sets); "Close on Drop" comments the reason ("Closed: won't fix.", "Closed as a duplicate of #m." or "…of another Task in The Office: <title>.", "Closed: can't be reproduced.", "Closed: <words>", "Closed: the Task was dropped.") then closes as not planned. **Traps:** `PostgresProjectRepository.find` and `list` go through the platform's read scope (`readOnce`, platform MAP): within one GET they answer the same objects to every caller, who never changes them, and every write of their tables runs through `forgettingReads`, a new writer too.

- `ProjectService.add(given, answered?)`: only the user's add (`POST /projects`) answers the run environment question, with who answered (`RunEnvironmentAnswered`), which a Yes passes to Run environments' set-up; any other add, such as a Proposal's, leaves it Not decided yet.
- A Project's command may be not set: install and the three starting commands may be blank when it was added (`newProjectProblems` checks only that a command given is one line, `commandLineProblem`), while a change (`PUT /projects/:id/install-command`, `PUT /projects/:id/commands/:key`, Devops' Proposals) and any command added later refuse a blank one (`commandProblem`, `commandFieldsProblems`), so a set command is never cleared. A new command's key passes `commandKeyProblems` (`install` and `publish` reserved); a key is never changed, since Pipelines name commands by it. Nothing runs a blank line: with no install command `Worktrees.installOnce` installs nothing and writes no record, so setting it installs at the next Stage; a Script Stage's `ScriptCommands.run`, given a key the Project lacks or a blank line, answers `could-not-run` naming the key, with how to set it and an empty `commandLine`, which `scriptStageOutcome` gives as the failure alone; `AgentCommands` answers `no-command`; the environment check starts it `skipped` and still passes (`isCommandSet`).
- A Project's default Pipeline always runs there: `ProjectChecks` refuses a default that runs a key the Project lacks, and removing a command the default or a Kind's own default Pipeline runs, by hand or by Devops' Proposal (`removedCommandKeys`), naming the Kinds (`namedByDefaultPipelineProblems`). The default may be one of its own Project Pipelines, weighed by its built Stages; another Project's and a Broken one are refused (`defaultPipelineOwnerProblems`), and a new Project (Add a Project, onboarding) takes an office-wide one only. `KnownPipelines.commandsNamedBy` answers any Project's Project Pipeline with its Project, so `ProjectChecks` reads the owner's name from `ProjectRepository`. Removing a command another Pipeline runs isn't refused; its Stage fails could-not-run. Keys alone count, so a blank command passes.
- The test handling (one re-run on failure, tracked files restored, written files moved out, the screenshots folder put back) goes by the command's kind, not its key: `ScriptCommands.run` gives it to every command of kind `test` (a `test-full` too) and none to build or lint kinds.
- A condition command (`ScriptCommands.runCondition`) runs once, never again on failure, even of kind `test`, and whatever its kind gets the rest of the test handling (restore, written files moved out to `<stageRunId>/condition-<key>-<8 hex>` under `test-output`, an id per run since one Stage run may weigh the same key twice, the screenshots folder put back), as weighing a route must leave the work as it was. A missing key or blank line gives `could-not-run` as `run` does (`setCommandOf`). Its run tells the run environment it reads the Stage runs' file (`readsStageRuns`): one already running without that folder mounted refuses it `could-not-run`, nothing run, saying to stop and start the Task's run environment.
- Devops' Proposal of commands (`ProposedCommands`, `proposedCommandsProblems` in `domain/proposed-commands.ts`) keeps each field it changes as it was (`from`) and as proposed (`to`): the install command, the install inputs, the before and after publishing lines (blank `to` clearing one), and each command by key, `from` null for an added one and `to` null for a removed one. It applies all or nothing and is refused once any `from` no longer holds, by the same rules as the Project page.
- An image's bytes never change: every upload is a new id, so its address is cached for good and replacing one needs no cache busting; don't overwrite a file under an id. Its size limit is held twice, `IMAGE_SIZE_LIMIT` in the platform, for what doesn't come through the upload route, and the contracts' `IMAGE_UPLOAD_BYTES` for `uploadBody` and the web, as only adapters import the contracts; the controller's test at exactly the limit keeps them equal. The content route's headers are what stop an SVG's script when its address is opened directly, so keep them.
- A Secret variable's value never leaves the service (spec 5.5, "Secret variables"): responses and events take the environment through `shownEnvironment` (`toEnvironmentResponse`), and the environment check events carry no environment at all. The environment is saved only by the user's Save (`PUT /projects/:id/environment`, `ProjectService.changeEnvironment`), where a Secret variable sent without a value keeps the Project's (`editedEnvironment`); the environment check tries the saved one and saves nothing. The stored check record keeps the values it ran with. `ProjectRecords` (`list_projects`) names each Secret variable and secret Server value without its value. Rows saved before Secret variables have no `secret` flag (`environmentOfStored`). Output is masked by one `OutputMask` (domain, exported for the run environment's command): in `commandRunOf` and, chunk by chunk, in every file written while a command runs; Conversations gets it through `ProjectService.outputMaskOf`, bound to its `ProjectOutputMasks` port in app.module.ts.
- A `CommandRun` carries a command's output twice: `output`, filtered for an Agent to read, and `wholeOutput`, the last 64 KB for the user's Stage history. The shell runner's 16 MB tail feeds both, so `filteredOutput` sees failures long before the end; don't shrink it to the 64 KB. An environment check keeps only the first (`CheckedCommandRun`).
