# Projects: module map

**Owns:** each Project's recent CI runs, in memory only (`CiRunWatch`, no table): every 15 s (`Schedule.every("ci runs")`, `CI_RUN_WATCH_EVERY`) a round lists again, as `recentRuns(remote, 30)` on the code host that reaches the base branch's remote, each Project with a run queued, waiting or running (`isGoing`), each tried 60 s ago or more (`IDLE_CI_RUNS_EVERY`), and each a refresh or a re-run asked for; `whyCannotRead` giving a reason marks its runs stale with no problem and asks nothing; a `CodeHostRefused` keeps the last runs, stale, and holds a `cannot-read` problem in the host's words (any other failure an `unreachable` one with the host's name and when it first failed); `CiRunsChecked` only when the runs, their staleness or the problem changed, reaching the web as `ci-runs.changed`. `GET /ci-runs?projectId=` answers the runs newest first (`startedAt ?? updatedAt`, then id), each with the Task of its `office/<task id>` branch (`taskIdOf`), and each Project's listing (`checkedAt`, `stale`, `problem`); `POST /ci-runs/refresh?projectId=` answers 202 at once, coalesced and skipped within 10 s of the same refresh (`CI_REFRESH_AT_MOST_EVERY`). Projects' first Office action, `rerun_ci_run` (`ProjectOfficeActions`, its routes in `ProjectOfficeActionsController`, `POST /projects/:projectId/ci-runs/:runId/rerun`): the run found in the watch's last listing or else listed from the host, refused unless failed or cancelled (`ensureRerunnable`), re-run with all its jobs or the failed ones, then the Project listed again at once (`refresh(projectId, { force: true })`); the host's refusal, such as GitHub's 403 without Actions write, answered as a `ProjectRefused` (422, the Agent's tool an error) in its words. Starting a Workflow by hand, the Office action `start_workflow` (`POST /projects/:projectId/workflows/:workflow/start`, beside the re-run): the Workflow found by its file name among `manualWorkflows(remote, ref)`, refused when its file at the ref declares no `workflow_dispatch`; the inputs checked and sent as text, defaults filling the rest (`inputsToSend`, every reason refused at once before the host is asked); then `expectRun(projectId)` lists the Project at once and every round for 60 s (`EXPECTED_RUN_WITHIN`, asked again starting again), as the host answers a start with no run. What a start offers, read through `ManualWorkflows` (application) on the same code host: `GET /projects/:projectId/workflows?ref=` (the base branch when left out, the ref answered) and `GET /projects/:projectId/refs` (with `baseBranch`), both on `CiRunsController`, answering empty lists with `problem` in plain words, never an error, when the host can't be read (`whyCannotRead`), refuses or fails. The pull requests The Office opened (`pull_requests`, one row per remote URL and number, the Task by id alone with no foreign key, `ended_at` once merged or closed; `PullRequestRepository`): Push + PR's Publish records each it opens or finds open (`record` upserts on the remote and number, keeping the status read last) and publishes `PullRequestOpened`, a failure to record logged and never failing the Publish; `PullRequestWatch` refreshes them every minute (`Schedule.every("pull requests")`) and on `POST /pull-requests/refresh` (202, coalesced, skipped within 10 s of the last round): per Project, the base branch's remote URL as git resolves it, skipped without one or when no code host reaches it; `whyCannotRead` giving a reason marks its open rows stale and holds the reason as its problem; else one `openPullRequests` list, an `office/<task id>` branch with no row adopted, `pullRequestStatus` only for a row whose head or base commit moved or whose checks are pending or unknown or mergeable unknown (`needsStatus`), and one last read for an open row no longer listed, which ends it through the repository's conditional `end` (`UPDATE … WHERE ended_at IS NULL RETURNING`, the only way a row ends; `save` writes the status alone, never `state` or `ended_at`), publishing `PullRequestMerged`/`PullRequestClosed` by `ON_THE_CODE_HOST` only when that update ended it; a row kept as ended that is listed open again is reopened (`reopen`, conditional on `ended_at IS NOT NULL`) with `PullRequestReopened`; a `CodeHostRefused` keeps the last status, marks the rows stale and holds an `unreachable` problem with when it failed and when the list was last read, which the web words in the user's own time ("GitHub couldn't be reached at 14:02; showing what it said at 13:58."), until a good round (problems in memory only, dropped with their Project); `PullRequestsChecked` only when something shown changed; Work › Pull requests' Merge and Close (`PullRequestActions`: `GET /pull-requests/:id/merge-methods`, the host's allowed methods with `recommendedMergeMethod`, merge for an `initiative/` branch and squash otherwise, warning when an Initiative's can't be merged by a merge commit; `POST /pull-requests/:id/merge` `{ method }` at the row's `headCommit` as `expectedHeadCommit`, and `POST /pull-requests/:id/close`, each 204, refusing an ended row, a method not allowed and a status not read yet, then ending the row by the same `end` and publishing `PullRequestMerged`/`PullRequestClosed` by the user only when it ended it; neither deletes the branch, which Work's cleanup does through `BranchDeletions` once the setting is On; a refusal, `PullRequestRefused`, answers 409 `{ reason, refresh }` through `PullRequestRefusalsFilter`, never logged, `refresh` true for `CodeHostChangedSince` and an ended or unread row); every one of these events reaches the web as `pull-requests.changed`. `GET /pull-requests?projectId=` answers the open rows newest first and the problems, narrowed to one Project when named. - A clone is made in a hidden folder beside its own and moved there when complete (`adapters/git/git-clone.ts`), so a folder found there is a whole clone, used again, with `origin` pointed at the URL given last (one folder holds every spelling and transport of a URL) and fetched, so branches made on the remote since are there. A clone, `ls-remote` and their failure reasons decide the identity on the URL git reaches (`Git.reachedUrlOf`, `insteadOf` applied): the user's config may rewrite https to ssh, or, in the tests and e2e, a made-up host to a local folder. Only the default branch exists locally after a clone: adding it as a Project accepts a base branch that is only `origin/<branch>` and makes it locally, tracking that (`ProjectService.add`); a path-added repository's base branch must already be local.
- `GitProcess.output` decodes as UTF-8, which damages a picture: read bytes with `GitProcess.bytes` (`CommitTree.bytesOf`). Ask `sizeOf` before reading a file of unknown size, as output over 64 MB fails as if git couldn't run. A link's `kindOf` is "file" and its bytes are the target's path, so an image from one is refused by its contents; Git LFS pointers are too.
- `CommitTree.kindOf` asks `ls-tree` by a literal pathspec, since a path is someone's words: bare `:(…)` makes git fail. `readBranchTip` shares it (`adapters/git/git-commit-tree.ts`).
- An Initiative's branch is made by `Git.createRef` (`update-ref <ref> <commit> ""`), never `setRef`, which overwrites: git refuses a ref already there, so two Confirms can't take one branch, and the loser's refusal names it taken. `remoteHasBranch` asks the remote itself (`ls-remote`), not the remote-tracking refs known here, so a name taken there since the last fetch is refused too. `InitiativeBranches` never pushes; `removeRef` checks the expected commit, so a rollback can't drop a branch someone moved.
- A fetch or push runs on the URL git resolves for the remote name (`ls-remote --get-url`, `remote get-url --push`), never the name itself, which `parseGitRemote` would read as a local path; a remote with several URLs gets the identity of its first.
