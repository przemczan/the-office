# Office-updates: module map

## Owns

- Office updates and restarts for each install kind (`domain/install-kind.ts`: `checkout`, `release`, `container`, from `OFFICE_INSTALL` and the release's stamp; `InstalledOffice`).
- Sources: the Office's own checkout (`OfficeCheckout`→`CommandLineOfficeCheckout`, plain git as the service's user, never the Office identity), the release stamp (`OfficeReleaseStamp`, `office-release.json`), GitHub Releases (`OfficeReleases`→`GitHubOfficeReleases`, unauthenticated), the service's container (`OfficeContainer`→`DockerCliOfficeContainer`).
- `OfficeUpdates`: the check (`POST /office-update/check`, daily `OFFICE_UPDATE_CHECK`), Update (`POST /office-update/schedule`, refusals in `domain/update-refusal.ts`), Cancel, `GET /office-update`, the log, the hand-off (`LauncherHandOff`, `UpdaterHandOff`), the boot result (`OfficeUpdated`, `OfficeUpdateFailed`).
- `OfficeRestarts` (`POST /office-restart/schedule`, refusals in `domain/restart-refusal.ts`, `LauncherRestart`, `ContainerRestart`); `ScheduledExits` (goes ahead once nothing is busy; `office.ts` exits with code 75).

## Talks to

- Busy work (`BusyWork`, `ScheduledExitHold`, `BusyWorkChanged`, through `../busy-work/index.js`), Engine (`EngineModule`), the platform (`UpdateSystem` from `platform/os`).
- Others reach it: Work's Start waits on `ScheduledExitHold.waitWords()` and releases on `ScheduledExitCancelled`; Pipelines ends walks before Agent or Script Stages while scheduled; Notifications raises on the result events and reads `OfficeUpdates.available()` through `OfficeUpdateAvailable` (the one instance `AppModule` registers).

## Traps

- Busy work must never import this module (`ScheduledExits.scheduled` casts the hold's untyped target back to `OfficeUpdateTarget`). Modules counting work import `BusyWorkModule`, never `OfficeUpdatesModule`, so this module may import Engine without a cycle.
- The schedule is in memory: a restart cancels it. A failed hand-off leaves it scheduled silently until the next `BusyWorkChanged` or a cancel.
- `BusyWork.begin` announces in the background; the web hears it only while something is scheduled.
- Windows refuses every Update first: tests override `updateSystem()`, as does the e2e service.
- A Gate isn't held at the Stage boundary; a held Task stays In progress.
- The launcher, the Office updater (`tools/office-launcher/`) and `tools/release` share file names and shapes by convention only: change them together.
- A release's commit comes from its stamp, never git (which would read a repository above the install folder). A release's request is built from the last check, which `schedule` has just run.
- Tests of a release or container fake `OfficeReleases` and `OfficeContainer`: nothing reaches GitHub or Docker. A container updater's success is never seen by this service; the new container takes the result at boot.
