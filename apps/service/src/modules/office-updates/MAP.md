# Office-updates: module map

**Owns:** Office updates (spec §5.1 Defaults, "Updating The Office"; [docs/running-the-office.md](../../../../../docs/running-the-office.md)): The Office's own checkout (`OfficeCheckout`, bound to `CommandLineOfficeCheckout` on the checkout `AppModule.register` names, the service's own by default and `OFFICE_E2E_CHECKOUT` in the e2e service; plain git as the service's user, never the Office identity): the current commit, fetching `@{upstream}`, the commits behind it, local changes and commits its upstream doesn't have. `OfficeUpdates`: the check (`POST /office-update/check`, and the daily `OFFICE_UPDATE_CHECK` job, first at boot), kept in memory; Update (`POST /office-update/schedule`) after a fresh check, refused with the reason (`domain/update-refusal.ts`: the system's refusal from `platform/os`, no launcher, local changes, no upstream, diverged; or nothing newer); Cancel (`DELETE`); `GET /office-update` and the launcher's log (`GET /office-update/log`). The schedule lives in `OfficeUpdateHold` (in memory, so a restart cancels it). `BusyWork` counts the work an update waits for, which each module reports where it starts and ends it: Engine an Agent's turn (`EngineCallSpans`, labelled by `SessionSettings.turnLabel`), Pipelines a Script Stage and a Publish (`ScriptStageRunner`), Projects a clone (`RepositoryClones`) and an environment check (`EnvironmentChecks`). Once an update is scheduled and nothing is busy, `OfficeUpdates` writes `request.json` in the launcher's folder (`UpdateFolder`, `FilesystemUpdateFolder` on `OFFICE_UPDATE_FOLDER`) and calls `onReadyToUpdate`'s listeners: `office.ts` closes the app and exits with code 75. At boot it takes the launcher's `result.json`, keeps it as `last-result.json`, and publishes `OfficeUpdated` or `OfficeUpdateFailed`.

**Talks to:** nothing but the platform. The others reach it (CTO's choice, 2026-11-03): Engine, Pipelines and Projects count `BusyWork`; Work's Start conditions add `OFFICE_UPDATE_SCHEDULED` as a wait while `OfficeUpdateHold` holds, and `QueueService` releases on `OfficeUpdateCancelled`; Pipelines' `StageInterpreter` ends a walk before an Agent or Script Stage while one is scheduled and walks those Tasks again on `OfficeUpdateCancelled`; Notifications raises `office.update.done` and `office.update.failed` on the result events. They import `BusyWorkModule`, never `OfficeUpdatesModule`, which `AppModule` registers with the config.

**Traps:** `BusyWork.begin` announces `BusyWorkChanged` in the background, so a turn counted mid-call never waits on the reactions; the web hears it only while an update is scheduled. A Gate isn't held at the Stage boundary: it does no work and asks the user. A Task held at the boundary stays In progress; after the update's restart the Stage interpreter takes it up as after any restart. The launcher (`tools/office-launcher/`) and this module share the files' names and shapes by convention only: workspaces stay apart.
