**Traps:**

- A set-up Task is created by the user who asked (`SetUpTasks.add(projectId, by)`): Set up from the Project page, or the Yes to the question as the Project was added, which Projects' registry passes on (`RunEnvironmentSetUp(projectId, by)`).
- No variable's value is ever in a command line or the script (spec 5.5, "Secret variables"): `exec` gets each `set` variable by its carrier name alone (`carrierOf`, `--env OFFICE_VARIABLE_<n>`), its value in the compose CLI's environment, and the script exports it back under its own name; the install's build gets every `set` variable as a BuildKit secret by the same carrier ids (`installSecrets`). A Project's own names never go into the CLI's environment, where `PATH` or `DOCKER_HOST` would change the CLI. The output file is masked as it streams (`Execution.mask`), and the scripted runtime masks as the real one does.

- `ScriptedContainerRuntime` (`adapters/scripted/`) is built, not a fixture: the end-to-end service (`src/e2e.ts`) binds it as `ContainerRuntime` through `index.ts`, so every run environment and Hosted test instance there is scripted; tests still reach it through `index.fixtures.ts`. `keepExecsRunning()` holds every exec as an entry point; a test whose target has commands before the entry point holds only the entry point's (`keepExecsRunning((execution) => execution.arguments !== undefined)`), or its commands would never end.
- The Run environment routes live here, not in Projects or Work: this module imports Work's `index.ts` (for `TaskStateChanged`), and Work imports Projects', so neither could reach the definition's reading without an import cycle.
- Everything carries `office.instance`, a digest of the Office data directory, and the sweep and every removal look only at this instance's: the tests', the e2e service's and The Office's own share one runtime. Don't sweep by `office.managed` alone.
- The sweep runs from `office.ts`, never `onApplicationBootstrap`, so a test app never asks the runtime for anything; `remove` asks it only for a Task that has a folder or a running environment.
- Compose reads `$` in any compose file as a variable: a value The Office writes into the override goes through `composeLiteral`.
- The override is applied over the repository's files, which compose merges, so a definition setting its own limits, ports, container name, host mounts, privileges or an external network or volume is refused rather than merged (`readDefinition`); devcontainer.json's `workspaceFolder` is read but unused, as the spec mounts the worktree at its own path.
- A running container keeps the worktree folder it mounted at its start: `exec` into a worktree removed and added again fails in runc ("current working directory is outside of container mount namespace root") with exit code 128, which comes back as the command's exit code, not `ContainerRuntimeFailed`, so nothing would stop the environment. `started` compares the folder's identity instead; a stopped container mounts the path again when it starts.
- The git folder's mount (spec 5.5 Defaults, "The repository's git data in a run environment") is read-only on purpose: checks read the history, every git change is The Office's, and `git status` skips its index refresh when it can't write. Its target must be the path the worktree's `.git` file names, so it is git's own absolute path from Projects (`Git.repositoryGitFolderOf`), never realpath'd again or read from the `.git` file, which an Agent can rewrite. On a non-root Office (`ServiceOwner.owner` set) the worktree and the git folder belong to another user than the checks' root, which git refuses as "dubious ownership": the check's script then adds `safe.directory=*` through `GIT_CONFIG_*` (`commandScript`'s `trustRepositories`), counting on from any `GIT_CONFIG_COUNT` the Project sets. A root Office's script stays byte for byte as it was.
- The Stage runs' folder is mounted, never its file: a file's bind mount keeps the inode it started with, and Pipelines writes the file anew before each condition command. The folder is made (`mkdir` recursive, in `writeProject`, so in `prepare` and in `run`'s start alike) before `up`, as a long-syntax bind fails when its source is missing; Run environments only mounts the folder Projects hands it. A running container never gains a mount, so `RunningEnvironment.stageRunsFolder` records the folder its override mounted, and a check with `readsStageRuns` in one whose folder isn't the Task's now is refused (`STAGE_RUNS_NOT_MOUNTED`, `RunEnvironmentRefused` with no output file, so the reason is the whole output), nothing run; it is mounted at the next start. Since the startup sweep stops every open Task's run environment and the running state is in memory, this guards only an environment started without the folder within the same service's life.
- Ending `compose exec` leaves the command running in the container: a timed-out or stopped check restarts the checks' service.
- On a non-root Office every check is followed by a hand-back (spec 5.5 Defaults, "Run environments with a non-root Office"): a second `exec` as `0:0` running `handBackScript`, which gives every file another user owns to the service's uid:gid. It runs with no signal, after the restart of a timed-out or stopped check, inside the Task's exclusive step and before `stopWhenIdle`, so Projects' restore, move-out and removal find the files already handed back. It fails as `RunEnvironmentRefused` and stops the environment; a check whose own `exec` threw `ContainerRuntimeFailed` gets none, as the next check's covers it. `ServiceOwner` is none for root (uid 0) and on Windows; the testbed's is none unless a test gives one. Not handled: rootless Docker and userns-remap (root in the container can't give files away), a non-root check user (`remoteUser: node`, which can't write a worktree it doesn't own), and files a process left running writes after its check.
- A Hosted Test instance takes no Run environments at once slot and isn't `BusyWork`: Test instances at once limits it. Its resources carry no `office.task`, so the Tasks' sweep passes them by; `HostedServices.sweep` is theirs. Its variables reach compose only as `${OFFICE_VARIABLE_<n>}` in the override, their values in the CLI's environment (`ComposeProject.variables`), for every command naming its files. The entry point's `exec` never gets a signal or a real timeout: `down` ends it, and a stop never restarts the service as an ended check does. `down` takes `--rmi local` for an instance, as a devcontainer-service entry point's own `build` would otherwise leave an image per launch.
- The runtime's port proxy takes a connection on a published port whether or not the app listens, closing it once the app refuses: readiness counts a connection only once it stays open 300 ms (`tcpAnswers`).
- Running state, slots and builds in progress are in memory: the startup sweep stops every open Task's run environment so the slots start empty.
- The image sweep keeps the newest image of each Project, standing in for "the image no Project's current key uses" until a Project's current key is known here; an image a container still uses is kept by the runtime.
- The limits are read as the override is written, at a run environment's start: a change to the limits never reaches a running one, while Run environments at once applies at once. The cores are the service's own computer's: a service run in a container sees its cgroup's CPUs.
- `RunEnvironments.attach` bypasses `exclusively` and the slots on purpose: it is called from a `RunEnvironmentStarted` handler while the start holds the Task's step. It isn't a check either: it never cancels or resets the idle stop, so an attached program never keeps a run environment running (spec §2.13 "Lifecycle"), and the environment's stop or removal ends it with its container.
- `AttachedProcess.stop()` ends stdin (the helper exits at its end), then the CLI after 2 s; it never restarts the checks' service as a timed-out or stopped check's `exec` does, since the service is the Task's checks' too.
- `RunEnvironmentStarted` handlers run inside the Task's step, before the check that started the environment: the bus waits for them, so a handler that calls anything taking the Task's step (`prepare`, `run`, `remove`, or a check through Projects) waits for itself and the check never runs. Start long work in the background.
- The device helper's folder is made (`mkdir` recursive, in `writeProject`) before every `up`, whether or not the helper is built or copied, as a long-syntax bind fails on a missing source; a copy later shows inside a running environment, the folder being mounted, never its files. `DeviceHelperFiles.copy` runs from `office.ts`, never at the module's start, so a test app writes nothing; until it has ended, `executableFor`, `version` and `helloProblemOf` wait for it, and before it is started they answer the helper not built.
- `compose-command-line.test.ts`, `hosted-services-runtime.test.ts`, `projects-task-run-environments-runtime.test.ts` and `device-helper-runtime.test.ts` run on the real runtime when one answers (pulling `busybox:1.37.0`, and `alpine:3.21` with git added at the build for the git mount's check), and are skipped with the reason otherwise; `device-helper-runtime.test.ts` also needs `npm run build:device-helper`'s executables.
