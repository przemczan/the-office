# Engine: module map

**Owns:** the engines Settings › Engines lists (`Engine`, rows of `engines`: an id made from the name when added and kept on a rename, a name, a kind, `claude-code` with its `-p` switch, `codex` with the API key it may be signed in with (`CodexApiKey`, redacted, in the `key` column, set only by `setCodexApiKey` and kept by every Save), or `openai-compatible-api` with an API endpoint's base URL, key and models, and a default model; the upgrade made the first Claude Code engine, `claude-code`, and an engine of each API endpoint), which caps, readings and each day's use are kept by, and which a Role card names by id; the models each offers, by their ids there (`EngineModels`: `offeredOn(engineId)`, which People's card checks ask, and `engines()`, which other modules list the engines through); the Office-wide settings of Settings › Engines in `EngineSettingsModule`, which both `EngineModule` and `ScriptedEngineModule` hold (`GET`/`PUT /api/settings/engines`: the engines in order, a saved one left out refused, a new one given an id from its name (`engineIdFor`) apart from every listed engine's, each default model one it offers and each Default effort one its type takes, each engine added announced as `EngineAdded`; `DELETE /api/settings/engines/:engineId?replacement=` removes one (`EngineSettingsService.remove`, `engineRemovalAmong`; with no replacement only the only engine): every reference moves to the replacement by `movedEngineId` (a Task's or an Initiative's engine override shown by `movedEngineOverride`, a Stand-in Engine list by `movedStandInList`), or to none with the only engine, the registered checks weigh it first (`EngineSettingsSave.removal`), then the other modules' references move through `EngineReferenceMoves`, then the engine goes with the Office default moved (`settingsWithoutEngine`), all under the `EngineReferenceLock`, then announced as `EngineRemoved` (its id and kind only, never an API key) after the lock is released; what a removal would move is previewed by `removalPreview` (`GET /settings/engines/:engineId/removal`) through the same `plannedRemoval`, the Office default's move, the Office's Stand-in Engine list's move (`movedStandInList`, marked `standInList`, each side on its engine's default model) and each registrant's `movesOf` (`movedEngineReference`; Projects' own lists through `movedStandInList` too), with the checks' refusals in the answer, not thrown; each key never sent back, only `keySet`; the Office default (an engine type and one of its engines listed, `OfficeDefault`, running on that engine's default model; none only while no engine is listed, when the first engine saved takes it with its type, and no session starts meanwhile: `NoEngineListed`, which People's cascade throws) and the search endpoint in `engine_settings`, the Office default read as the first Claude Code engine while no row is kept, its type read from its engine's kind, `office_default_model` no longer read but written as that engine's default model for the release before, given to People's engine cascade and the registered checks as an engine and model by `officeDefaultEngineModel` (`EngineModels.officeDefault`, `EngineCascadeSettings`); each engine's Default effort (`default_effort`, null for Not set, one its type takes, `effortsTakenBy`, a Save leaving it out keeping the stored one); the Stand-in Engines, an ordered list of listed engine ids (each once), and the context size above which a switch of a running Stage asks first (`askBeforeSwitchAbove`, `DEFAULT_ASK_BEFORE_SWITCH_ABOVE`), both in `engine_settings` (`stand_in_engine_ids`, read without the ids no longer listed; `ask_before_switch_above`), a PUT leaving either out keeping it, a removal putting the replacement in the engine's place in the list, or just dropping it when the list already names the replacement or there is none (`standInListWithout`, which Projects uses for each Project's own list too; `standInListProblems` refuses an engine not listed or named twice in either list), given to later modules by `EngineModels.standIns()`; `engineToRunOn` (`domain/stand-in-engines.ts`) picks the engine to run on by id from the cascade's engine id and the stand-in list that applies, which the caller gives (the Project's own or the Office's, People's `standInsApplying`): the cascade's while the caller's `hasRoom` says so, else the first Stand-in Engine in order that is listed, isn't the cascade's own, passes the `capable` guard (the session's needed capabilities, `EngineSessions.capableOf`) and has room, of any engine type unless `sameEngineType`, else none; the caller resolves the model and effort for the picked engine's type (Work's Start, and `EngineSessions.standInFor(running, { standIns, sameEngineType, needs })`, which gives a running session's Stand-in Engine once its turn was refused, or, for a person's Thread, while `EngineSessions.usedUpUntil` says its engine is used up: never the running engine, one whose window isn't used up (`usedUpUntil`) and whose latest reading shows it free or that hasn't been read (`UsageWindowState.latestShowsFree`, the hold included); with `sameEngineType`, as a session that must be carried asks, only stand-ins of the running engine's type with the `carrySession` capability, and none for a running engine whose sessions can't be carried; without it a stand-in of another type starts fresh); the Model prices in `model_prices`, one per Claude model shared by every Claude Code engine and one per Codex model shared by every Codex engine (engine id null, the Codex models listed only while a Codex engine is) and one per API engine and model, for models offered now and a removed engine's kept so its history stays priced (`keptModelPrices`: an engine no longer listed, a null-engine price whose model isn't offered now (the Claude models' with no Claude Code engine, the Codex models' with no Codex engine), and a kept price while an engine taking the id back is saved unpriced), `GET` listing every offered model with its price or none; `ModelPrices.costOf` prices an engine's model by them, kind by kind, an unlisted engine with prices of its own as an API engine, undefined with no price); the `AgentEngine` port and its adapters in `AgentEngines`, keyed by the way they run a session (`EngineAdapter`) and picked by the engine's kind, or `-p` when its switch is on: the Agent SDK adapter, the fallback's (`adapters/claude-code-p/`: the pinned binary in `-p`, stream-json in and out through `StreamJson`), and the scripted engine every other test runs on (`adapters/scripted/`). The OpenAI-compatible API adapter (`adapters/openai-compatible-api/`) is The Office's own agent loop: `OpenAiCompatibleApiEngine` runs on the API endpoint its options name (`SessionOptions.engine`) and one of its models (`ModelNotOffered` when the endpoint doesn't list it or the engine is no API endpoint, a refusal, not the engine down), and each `ApiSession` turn sends the conversation through `ChatCompletionsClient` (streamed chat completions over `node:http`/`node:https`, the text as it comes and then the whole answer, tool calls assembled by index, aborted by a signal), runs the tool calls and sends again until an answer makes none. Its tools (`SessionTools.of`: Read, Grep, Glob, Edit, Write, the system's shells, TaskStop, WebFetch, WebSearch, the Office tools as `mcp__office__<name>`, the tools of the session's MCP servers as `mcp__<server>__<tool>` with the description and input schema recorded at their review (`mcpBuiltInTool`), and `StructuredOutput` when the session has an output schema) carry Claude Code's names and inputs, each a zod schema that also gives the model its JSON Schema (StructuredOutput's is the output schema, checked by Ajv); a call is refused by the engine when the tool is unknown, its arguments aren't JSON or don't fit, then judged by `toolDecision`, and only then run; an Office tool is judged again as it runs. Bash and PowerShell run one command line to its end through the platform's `agentShells` (`runShellCommand`), its tree ended by `ProcessTrees` on interrupt or timeout; with `run_in_background` the session's `BackgroundCommands` starts it instead and answers at once, as Claude Code does, with its id and its output file in the session's own folder (`backgroundCommandFolder`, `<temp>/office-sessions/<session id>/`, a readable folder of its rules, read with Read); TaskStop ends one with its tree, `interrupt` ends them all, and `end` ends them and removes the folder; one that ends by itself leaves Claude Code's `<task-notification>`, which lands as a user message where a `next` message would, or at the next turn's start, never starting a turn. Each is reported as a Process on the session's events, between turns too (`reportTo`): `process-started` with the Bash call's id (passed in `ToolContext.callId`) and its own id, its output read by bytes from its `<id>.output` file every half second (an unref'd timer per command, a `StringDecoder` keeping a split character) as `process-output`, and `process-ended` (exit 0 finished, else failed with its code; TaskStop, an interrupt or `close` stopped by the Agent, the interrupt or the session's end) only after its leftovers are ended and a last read, before `stop`, `endAll` and `close` return, so the session's events close after every end. WebFetch fetches the page itself (`fetchWebPage`: http or https, 60 s, 10 MB, redirects on the same host followed and one to another host reported to the model, HTML turned into Markdown by turndown, cut to 40 000 characters) and answers with it under the call's prompt, as there is no small model to answer the prompt. WebSearch goes through the search endpoint's port, `SearchEndpointClient`, whose one adapter is `SearxngClient` (`adapters/searxng/`, `<base URL>/search?format=json`, tested on `FakeSearxngServer`); the domain filters are applied to its results. With no search endpoint set WebSearch is still offered, and a call is refused by the engine once the Office rules allow it (`engineRefusal`). Each turn has its own abort controller: `interrupt` aborts the request and the commands and waits for the turn's end (`interrupted`); a `next` message lands after a batch of tool results, a `later` one waits for the turn's end. A session lists its skills as the SDK adapter's do (`listedSkills`: the plugin folder's as `office:<folder>`, the Project's skills and commands at the folder's top that the allowlist names), checked with `listingProblems` at start and on resume (`SessionSkillsDiffer` before any request), and the `Skill` tool, whose description is the listing, loads one by name (`Base directory for this skill:`, then its body with `$ARGUMENTS` filled in). A skill or command with `disable-model-invocation: true` (`ListedSkill.userOnly`, read by `isUserOnly` in `markdown-file.ts`) is left out of the model's listing and the start check (`modelListing`) and refused by `Skill`; only a skill command runs it. A skill command (`UserMessage.skillCommand`) is expanded by the session itself as it takes the message (`skillCommandText`: the skill loaded as `Skill` loads it, the input as its `$ARGUMENTS`, else appended as `ARGUMENTS: <input>`), and sent as written for a skill it doesn't list. The system prompt holds the Project's instruction files the SDK adapter's sessions load (`projectInstructions`: `CLAUDE.md`, `.claude/CLAUDE.md`, the rules in `.claude/rules/` without `paths`). After each turn the conversation, system prompt aside, is kept in `ConversationFile` (`<office-data>/sessions/<session id>/conversation.json`, written beside and moved into place), which `resume` reads back (`ConversationMissing` when there is none); Skills' `forget` removes it with the session's folder. `readContextUsage` gives the last request's prompt and answer tokens against the model's context window from Settings › Engines, estimated from the conversation's length when the server counts none; nothing is compacted. A request joins user messages that follow one another into one, as a strict chat template refuses two in a row; the kept conversation holds them apart. A message's images (`UserMessage.images`) go by the model's Sees images in Settings › Engines (`ApiEndpointModel.seesImages`, kept in the `models` JSON, missing read as off; `SessionOptions.engine` carries it to the session): on, as `image_url` content parts with a `data:` URL after the text, which the conversation file keeps whole so a resume still sends them; off, as one line of words per image naming its name and Attachment id (`userContent` in `user-content.ts`); an image counts as `ESTIMATED_IMAGE_TOKENS`, not by its data, in the context estimate. Its tests run on `FakeChatCompletionsServer`, which streams scripted answers and records each request. Each test has its own fake server, so a slow test's late requests never take the next test's answers. What every adapter judging Claude Code's tool names shares (`agentAction`, `toolDecision`, `sessionOfficeRules` with each engine's readable folders and the session's own `SessionOptions.readableFolders`, such as an Initiative's branch checkouts, read but never edited, the Office tools' names) is in `adapters/office-rules/`; what both Claude Code adapters share (the event mapping, tool refusals, the Office rules hook, `claudeCodeOfficeRules`) is in `adapters/claude-code/`. The fallback's hook reaches the service on `localhost` (`adapters/http/`, under `/api/engine/claude-code-p/`), behind a token per session (`SessionEndpoints`); its Office tools are served in-process through the binary's own stream (`OfficeToolServer` answering `mcp_message` control requests, which `StreamJson` routes to it), judging every call by the session's rules again as it runs. `ClaudeCodePEngine` opens both before it spawns the binary and closes them when the session ends. `EngineSessions` announces each `Skill` call a session reports, its Agent's or a subagent's, on every engine, as `SkillCalled` (`calledSkill`: the name without a leading `/`), awaited before the call is reported, for Skills to count; a skill command sent (`UserMessage.skillCommand`) is announced the same way, by the name the session lists it as, as the message is sent, since no engine reports a Skill call for it. Skill commands (spec §2.6): both Claude Code adapters write one as the user types it, `/<skill> <input>` (`userMessage` in `stream-events.ts`), with whatever priority it is sent, and the engine expands it; the same `userMessage` writes a message with images (brief, `next` or `later`) as content blocks, its text then one base64 `image` block per image, and one without as plain text; `SessionSkills.userOnly` names the skills only the user runs, never in `expected`, and the start check (`startCheckProblems`) compares the listing with `expected` without them, so a user-only skill neither fails a start or resume nor is held against one should the engine list it. `EngineSessions` starts and resumes a session on the engine id and model its settings name (`SessionSettings` is an `EngineModel`), on that engine's adapter, and reads capabilities per engine id; an engine Settings › Engines no longer lists is refused (`EngineNotListed`), not the engine down. Each adapter is handed the engine as Settings › Engines lists it as the session opens (`SessionOptions.engine`) and the model by its id there. Both Claude Code adapters run each session, started or resumed, with `CLAUDE_CONFIG_DIR` set to the engine's config folder (`engineConfigFolder`, `<office-data>/engines/<engine id>/`, made at a session's start when missing), which holds its account and its sessions' transcripts, so a session resumes only on the engine that started it, or on one it was carried to: `EngineSessions.carrySession(sessionId, fromId, toId)` (both listed Claude Code engines with the `carrySession` capability, else `EngineNotListed` or `CapabilityMissing`; counted as running on `toId` while it copies, so a removal waits; only for an idle session whose refused turn ended its engine session) calls the port's `carrySession`, which both Claude Code adapters answer with `carrySessionOver` (`adapters/claude-code/session-carry-over.ts`: `projects/<name>/<id>.jsonl` found by its file name under any `projects/*/`, the `<id>/` folder beside it and `todos/<id>-*.json` copied file by file into the same places in the other folder, each written beside its target and renamed into place, the transcript last, the first folder's path rewritten in every `.jsonl` as a POSIX path and as a Windows path inside JSON, `file-history/` left; idempotent, the source untouched, `SessionNotCarried` with no transcript); the scripted engine records each carry in `carried` and copies nothing; the Codex and API engines lack the capability; `EngineAccounts` makes it when a Claude Code engine is added and, ending any Sign in under way there, removes it once the sessions running on the removed engine have ended (`RunningEngineSessions`, which `EngineSessions` counts from before it looks the engine up, so a session that found it listed is waited for; awaited in the background, and the folder kept when the engine is added again meanwhile; `removeEngineConfigFolder`, which refuses an id leading anywhere but a folder directly in `<office-data>/engines/`), and at startup removes the folder of every engine not listed (`engineIdsWithConfigFolders`), one left by a service stopped before a removed engine's sessions ended; `sessionEnvironment` drops any given one first, and the Office rules expand the variable in commands to that folder, refused as the rest of the data directory. Each Claude Code engine's account (`EngineAccountsModule`, beside `EngineModule`): `EngineAccounts` reads it (`GET /api/settings/engines/:engineId/account`, from `auth status --json`, `engineAccountOf`: signed in, by a pasted token or not, email, plan; `API_KEY_ACCOUNT` without asking while its folder holds an API key) and signs in (`POST …/sign-in` runs `auth login --claudeai` on the engine's folder and gives the page that signs in by a pasted code; `POST …/sign-in/code` writes the code to the login's input), takes a pasted token (`PUT …/token`, "Paste a token instead": a `claude setup-token` token, `PastedToken`, written as the folder's `.credentials.json` with no refresh token by `engine-credentials.ts`, never answered back), takes an Anthropic API key (`PUT …/api-key`, "Use an API key": `AnthropicApiKey`, shaped `sk-ant-api…` or refused as `NotAnAnthropicApiKey`, written to the folder's own owner-only `.anthropic-api-key` by `writeApiKey`, never answered back, in no environment) and signs out (`DELETE …/sign-in`, removing both files), through the port `ClaudeCodeAccounts` (`ClaudeCodeCliAccounts` on the pinned binary: one login per engine, ended by another Sign in, a pasted token, an API key, Sign out, after 15 minutes or at shutdown); a login's end, a pasted token, an API key and Sign out are announced as `EngineAccountChanged`, forwarded to the web as `engine.account-changed`. Each Codex engine's account goes through the same routes and the port `CodexAccounts` (`CodexCliAccounts` on the pinned `codex`, `CODEX_HOME` the engine's folder, the environment as `codexEnvironment` gives it): the status from a short-lived app-server's `account/read` (`codexEngineAccountOf`: ChatGPT with its email and plan, an API key, or signed out), or `API_KEY_ACCOUNT` without asking while a key is kept; Sign in runs `codex login --device-auth` and answers its page and one-time code (`POST …/sign-in` with `userCode`), forgetting any kept key first; "Use an API key instead" (`PUT …/api-key`, 204, the same route, `EngineAccounts.setApiKey` taking the key's shape by the engine's kind) ends any login, signs the folder in with `codex login --with-api-key`, the key on its input only, then keeps it (`setCodexApiKey`); Sign out forgets the key and runs `codex logout`; each is announced as `EngineAccountChanged`. An API key signs a Claude Code engine's sessions in through `apiKeyHelper` in their session settings (`sessionSettings`, both Claude Code adapters, from `apiKeyHelperOf`): a command naming the key file, from the platform's `printFileCommand`, which the binary runs and takes over any login. `EngineModels` lists such an engine with `signedInByApiKey` (`recordApiKeySignIn`, which `EngineAccounts` keeps from each folder at startup, on `EngineAdded`, and before each `EngineAccountChanged`), so `hasUsageWindows` is false for it everywhere: no reading, no window caps, and a refused turn on it is an ordinary failure (`asFailedTurn`), never `usage-window-used-up`. `enterCode` and a pasted token stay Claude Code's (`NotAClaudeCodeEngine`), an API engine has no account (`NotAnEngineWithAnAccount`). A Codex engine's folder is made when it is added, kept at startup while it is listed and removed once it is removed and its sessions have ended, as a Claude Code engine's is. It reads the usage windows on each rate-limit signal (`readUsageWindows`, no model call), and as the service starts and every 5 minutes (`UsageWindowChecks`, `USAGE_WINDOW_CHECK_EVERY`, on the platform `Schedule.every`, so checks never overlap and a test runs one with `ManualSchedule.runRepeating`) with no session: each listed engine that has windows (`AgentEngines.readsUsageWindows`), one at a time, through the port's engine-level `AgentEngine.readUsageWindows(engine, signal)` (the SDK a short-lived query with `persistSession: false` on the engine's config folder, `-p` the pinned binary with `--no-session-persistence` and `get_usage`, Codex a short-lived app-server's `account/rateLimits/read`, the API engine none; each ended in `finally` by `engineRead`, `adapters/claude-code/engine-read.ts`, within `ENGINE_READ_TIMEOUT_MS` or as the service stops), a failed read logged as a warning and the next engine read. A session's reading and a timed one are kept alike by `UsageWindowReadings` (the Office's tokens so far, `readAt` on the `Schedule`'s clock, `UsageWindowState.update`, the samples), keeping each reading in `UsageWindowState` by engine id (`of(engineId)`, which Work's Start weighs; `readingsByEngine`, every engine's in the order first read, which Now shows; `UsageWindowsRead` on every reading, naming the engine's id and whether it shows the engine `free` (`showsFree` in `domain/usage-windows.ts`: every window below 100%, the one judgement, which Work's early resume reads; false while a hold stands), `UsageWindowsChanged`, naming the engine's id and name, only when that engine's windows differ) with when it was read and the Office's tokens so far (`readAt`, `officeTokensSoFar`: every turn's four kinds on the reading's engine id, in memory since the service started); each reading is paired with the last of its Reading source on its engine id (`UsageWindowSamples`, in memory, so no pair spans a restart), and a pair that counts (`sampleBetween`: the Office's tokens went up; a window's part when it neither reset nor went down, 0 included) is kept in `usage_window_samples`, the latest 500 per engine id, whose pooled changes over tokens (`ratios(engineId)`) Work's estimates take as window % per counted token, a failure to keep one logged; every turn's tokens also go to each day's use (`DayUsage`, `engine_day_usage` by local day, engine id and model; `today(engineId)`), awaited before the turn is reported and logged, not fatal, when the write fails; a removed engine's day usage, pairs, last readings and reading are forgotten, not moved, on `EngineRemoved` and again on `EngineAdded`, as `engineIdFor` gives an engine added again under its name the old id (`RemovedEngineUsage`); each window is judged on its own: the Claude Code adapters read a window the query gives without its `utilization` or `resets_at` as not begun, so unused (0%, `resetsAt` undefined), and the reading still stands. The Office rules in the `PreToolUse` hook (profiles, the git deny, the container runtime deny (`containerRuntimeReach`: its programs run, its sockets named, its variables set), secrets, protected paths, a command's output written outside the worktree refused in words naming the rule before the engine's own wordless refusal, PowerShell twins; the read-only git refusal names pipes and Read and Grep, as `READ_ONLY_SHELL_RULE` does in the chat, planning and shaping instructions that quote it), and before them a session's `ToolHold` (`SessionOptions.toolHold`, asked at every call: while it gives words, every call is refused in them, as the fire alarm does; the scripted engine honours it too, running no Office tool), Office tools (`OfficeToolRegistry`; an Office action's tool, made from its declaration by `officeActionTool` (`adapters/office-tools/office-action-tool.ts`, its description ending with `FOLLOW_YOUR_AUTHORITY`), carries `coveredBy`, the duties that cover it, and `coveredBy(duties)` answers those a person's held duties cover, which Conversations adds to every Thread the user talks to them in; every new action on a record is declared once as an Office action, never as a hand-written route plus a hand-written tool ([the module template](../../../docs/module-template.md)); an answer is words and optional pictures, `OfficeToolResult.pictures`: both Claude Code adapters give each as MCP image content up to `CLAUDE_CODE_PICTURE_LIMIT`, a larger one in words saying it is too large, the API loop names each in words as its tool answers are text only, and the scripted engine logs the words alone), and the 5-hour and 7-day windows (`UsageWindowsChanged`, `UsageWindowsRead`, `EngineDown`, which names the engine's id and its name as the session opened). Both Claude Code adapters run the session's MCP servers (`SessionOptions.mcpServers`) through the binary's MCP config (`mcpServerConfigs` in `adapters/claude-code/session-mcp-servers.ts`, in a file: `McpConfigFile`), beside the Office tool server, under strict MCP config, each server allowed by rule (`mcp__<server>`) so the hook judges its calls. The scripted engine judges an MCP call by `toolDecision` and runs it on the session's server through `McpServerConnections` (`adapters/mcp-servers/`, The Office's own `McpClient`, a server started at its first call and ended with the session), so the contract's `mcp-tool` scenario runs on the fake stdio server. The API engine's loop uses the same `McpServerConnections`, opening every server before the first turn (`open`, which gives an `mcp-server-not-started` event for each that failed, Server values replaced; a call's retry tells nothing) and ending them with the session (and when its opening fails). The Claude Code engines tell it once per session from the init message's `mcp_servers` (`McpServerStarts`, status `failed` with no reason, or `needs-auth`, which a 401 or 403 gives, the Office's own server left out); the scripted engine replays it as recorded. Its contract runs the `mcp-tool` scenario on the fake chat-completions server. A turn the engine refuses for a used-up usage window (spec 5.4): `RefusedTurns` in `adapters/claude-code/sdk-events.ts`, shared by both Claude Code adapters through `StreamEvents`, ends a failed turn after the turn's latest `rejected` rate-limit event as `usage-window-used-up` with its `usedUpWindow` (the window by `USAGE_WINDOW_NAMES`, a window the port doesn't name by its raw name, `unknown` when none; with no reset given, `UNKNOWN_RESET_RETRY_MS` on); `EngineSessions` settles the reset from the latest reading of that window and `UsageWindowState.refused` keeps which engine is used up until when (`usedUpUntil`), announcing `UsageWindowUsedUp` once per engine until the reset and `UsageWindowReset` at it, or sooner: a free reading taken after the window was used up resets it at once (`update`, its wait cancelled). A refusal while the latest reading shows the engine free is a limit the readings don't show: `refused` holds the engine's readings not free until that refusal's reset (`holds`), so its paused Tasks wait for the reset rather than resume into a refusal every check. A Codex engine signed in with ChatGPT reads its windows with the app-server's `account/rateLimits/read` (Reading source `usage-endpoint`), falling back to the latest `account/rateLimits/updated` (`rate-limit-headers`), each window told apart by its length in `adapters/codex/codex-usage-windows.ts` (5 hours and 7 days; a snapshot with a window of any other length is left unread, never read as 0%); a Codex engine on an API key has none (`hasUsageWindows`). `ChangedAccountUsage` (`application/changed-account-usage.ts`) forgets an engine's last readings on each `EngineAccountChanged`, so no pair of readings spans two accounts, and a Codex engine's reading and used-up window too, as the event doesn't tell an API key or a Sign out from a ChatGPT Sign in; a Claude Code engine's reading stands. The Codex adapter (`adapters/codex/`, `CodexAppServerEngine`, `CODEX_CAPABILITIES`: usage windows, no language servers) runs each session on one pinned `codex app-server` (`CodexAppServer`, JSON-RPC over stdio), `CODEX_HOME` the engine's folder (`preparedEngineConfigFolder`), its settings as `-c` overrides and `thread/start`'s, the same on `thread/resume` (`cwd` the folder, `untrusted` approvals, the `workspace-write` sandbox, effort `max` as `xhigh` and none sent while the session leaves its effort to the runtime, as the SDK and `-p` adapters leave out `effort` and `--effort`, the repository's main checkout named untrusted under `projects` (`mainCheckout`), `mcp_servers` on the session's `SessionMcpEndpoint`, `office` only with Office tools or skills the model loads), its developer instructions the Role's, the skill listing for the `office` server's `Skill`, `FILE_CHANGES` and `DECLINED_CALLS`; a model `CODEX_MODELS` doesn't list or another kind of engine is refused (`ModelNotOffered`), as is a session without exactly its skills, before any process starts. The thread's id is kept in `CodexThreadFile` (`<office-data>/sessions/<session id>/codex-thread.json`, written beside and moved), which `resume` reads (`CodexThreadMissing`). `CodexSession` makes the messages waiting one `turn/start` (a skill command expanded by `skillCommandText`, images as `data:` URLs), steers a `next` one into the running turn (`turn/steer` with `expectedTurnId`; its id joins the turn's `consumedMessageIds` once accepted, and one refused waits as `later`) and holds a `later` one; Stop sends `turn/interrupt`, then kills the app-server's tree, and the next message starts a new process that resumes the thread.
