# Conversations: module map

**Owns:** Threads, each one engine session (`threads`, `thread_messages`), and The Office's message log; Decisions as cards in the asking Thread (`decisions`), each open until answered or closed unanswered as its Task is dropped (`closed_at`, `closeDecision`, `DecisionService.closeOnDroppedTask` called by Work, publishing `DecisionClosed`: a closed one is out of every open read and refused an answer by anyone, in `closedDecisionRefusal`'s words), or, one on no Task in an Initiative's Thread, as the Initiative ends (`DecisionService.closeOnInitiative`, the same `DecisionClosed`; no column says why: the HTTP mapping derives `closedBecause` from whether it has a Task), each of a kind (`form`, `approval`, `request`, stored, never read from the wording; a form of one or more questions, stored beside its one-question view the previous release reads; `bug-task`, an Agent's proposed Bug Task, kept in `decisions.bug_task` beside a `question` kind and one choice, Create the Bug Task, Don't create it or Fix now (no Task: the Agent fixes it within its own Task), so the previous release reads it as a form) and on a Task: one open at a time in a Thread on a Task, and one per Task in an Initiative's planning Thread (`Thread.openDecisions`; `hiredKeys` once applied), applied all or nothing by People's `OfficeSetup` through `RoleProposals`, each hire proposed by its drafter; `initiative`, a change to an active Initiative by whoever shapes Initiatives; `project-commands` of the onboarder (whoever onboards Projects) (`changes`: the install command and install inputs, each `{ from, to }`, and `commands`, each by key with `from` null for one added and `to` null for one removed, applied all or nothing), `test-targets` of the onboarder (`changes.targets`, each by key with `from` null for one added, `to` null for one removed, and `userSet` the fields the user set that it changes, each named by the Agent in `changeUserSet`; Secret variables by name alone; applied all or nothing, each field it changes stamped set by `{ proposalId, agent }`), `pipeline`, `stage-template` (a Stage template's one Stage, kept unread as a Pipeline's Stages are) and `project-pipeline` (a new Project Pipeline of `projectId`, `from` null and `pipelineId` null until applied, or a change to one: its name, description and whole flow, the Stages kept unread as a Pipeline's are, and for a new one `copyOf`, the Pipeline it is copied from; never a removal or a Project's default), each with the values now (`from`) and as proposed (`to`), refused once those changed; the onboarder's `skill-install`, a skill in a Source's folder at its pinned version with its files hash; the onboarder's `skill-update`, an installed skill's update from and to with notes and its files hash; `skill`, a written skill anyone drafts in their chat) and applied only by the user; Link cards, a message in the chat of whoever holds Default person to talk to pointing the user to a person (about a Task when it names one) with a Handover note the user sends themselves (`LinkCards`), whether that person was let go read as the log is (`letGoIn`); an Idea's card in the chat it was captured in and the Office status's card, each only a pointer the web reads live from Work and Now, logged in chat Threads only (`ThreadService.postIdeaCard`, `postOfficeStatus`); the Context policy (resume, fresh, hand off, the Brief, Handover notes) and its size threshold in one row (`conversations_settings`), which Settings › Office limits changes; the Office instructions, each saved text a version (`office_instructions_versions`, `OfficeInstructions`; version 0, never stored, means none), which Settings › Office instructions changes (`OfficeInstructionsChanged` only when a new version was made) and every session gets after who the person is and before their Role's instructions (`SessionPerson`, `personInstructions`, which ends with `WRITING_FOR_THE_USER_RULE`: records mentioned as links to their pages by full ID, text to copy in a fenced code block), at both session starts (`ThreadRunner`, `StageThreads`): a new session takes the current text and records its version (`ThreadSession.officeInstructionsVersion`), a resume runs with the version it recorded, and one stored before them reads 0, so it keeps its cached prompt; the sessions behind Stage Threads (`ThreadRunner`); tokens per Thread and per Task (`TaskTokens`; `budgetTokensSoFar` is what a Stage's budget checks, leaving people's Threads out; `stageTokensSoFar` gives a Task's Stage Threads' by engine id, which Work's Daily caps read); **Traps:** Conversations' prompt templates render byte for byte as the code did before them: `conversations-prompts.golden.ts` holds that output and is never edited, and `conversations-prompts.golden.test.ts` renders `conversations-prompts.golden-cases.fixtures.ts` with the defaults against it. A test app that provides `SessionPlaces`, `Briefs`, `StageThreads` or `ThreadRunner` itself imports `ConversationsPromptTemplatesForTests`, and one that saves a real template's text overrides `PromptTemplateRepository` with `PromptTemplateRepositoryForTests`. a Stage Thread's engine is the cascade's mapped through the Task's `engineStandIns` (`engineThroughStandIns` with the list the cascade gives, `EngineInCascade.standIns`, before the Context policy compares it with the session's), its session recording `standInFor`, which the Live view shows, and working with the person's model and effort for the stand-in's type (People's `EngineCascade.onEngine`); a session never resumes on another engine (`engine-changed` starts fresh; the engine it stands in for counts as its own, `onEngine`, except under an engine override, `Continuation.forced`, which `StageThreads`, `ThreadRunner`, `ThreadContexts` and `ThreadSummaries` set from the cascade's `standIns` from `none`), and a stand-in no longer listed, or no longer in the list that applies, gives the cascade's back; under an engine override no list applies (`standIns` from `none`), so an override turned on while a Task ran on a stand-in starts its next Stage fresh on the forced engine.
