# Conversations: module map

**Owns:** Threads, each one engine session (`threads`, `thread_messages`), and The Office's message log; Decisions as cards in the asking Thread (`decisions`), each of a kind (`question`, `approval`, `request`, stored, never read from the wording) and on a Task: one open at a time in a Thread on a Task, and one per Task in an Initiative's planning Thread (`Thread.openDecisions`; the index `decisions_open_on_task_in_thread` holds one open per Thread and Task); a call made from a chat is on no Task (`taskId` undefined), only when put to someone, one at a time per chat Thread (`decisions_open_on_no_task_in_thread`, as nulls are distinct to the first index), and never in `openDecisions()`, Needs you or a Notification; Proposals as cards in the Thread they were drafted in (`proposals`), generic over what they change (`ProposedChange`: a Role's `hire` from scratch, `hire-from-preset` and `change`; the Office settings `office-wide-limit`, `size-threshold`, `office-instructions` and `duties` (who holds each duty, `from` and `to` naming only the duties that change, applied all or nothing); `office-setup`, the Caretaker's set-up of The Office (`hires`, each from a preset or from scratch, and `duties`, each `{ duty, from, to }` naming only the duties given to another Role than their default, `to` possibly a Role one of the hires fills; `hiredKeys` once applied), applied all or nothing by People's `OfficeSetup` through `RoleProposals`, each hire proposed by its drafter; `initiative`, a change to an active Initiative by whoever shapes Initiatives; `project-commands` of the onboarder (whoever onboards Projects) (`changes`: the install command and install inputs, each `{ from, to }`, and `commands`, each by key with `from` null for one added and `to` null for one removed, applied all or nothing), `pipeline`, `stage-template` (a Stage template's one Stage, kept unread as a Pipeline's Stages are) and `project-pipeline` (a new Project Pipeline of `projectId`, `from` null and `pipelineId` null until applied, or a change to one: its name, description, base Pipeline and Stage changes, the Stage changes kept unread as `PipelineStageChange`; never a removal or a Project's default), each with the values now (`from`) and as proposed (`to`), refused once those changed; the onboarder's `skill-install`, a skill in a Source's folder at its pinned version with its files hash; the onboarder's `skill-update`, an installed skill's update from and to with notes and its files hash; `skill`, a written skill anyone drafts in their chat) and applied only by the user; Link cards, a message in the chat of whoever holds Default person to talk to pointing the user to a person (about a Task when it names one) with a Handover note the user sends themselves (`LinkCards`), whether that person was let go read as the log is (`letGoIn`); an Idea's card in the chat it was captured in and the Office status's card, each only a pointer the web reads live from Work and Now, logged in chat Threads only (`ThreadService.postIdeaCard`, `postOfficeStatus`); the Context policy (resume, fresh, hand off, the Brief, Handover notes) and its size threshold in one row (`conversations_settings`), which Settings › Office limits changes; the Office instructions, each saved text a version (`office_instructions_versions`, `OfficeInstructions`; version 0, never stored, means none), which Settings › Office instructions changes (`OfficeInstructionsChanged` only when a new version was made) and every session gets after who the person is and before their Role's instructions (`SessionPerson`, `personInstructions`, which ends with `WRITING_FOR_THE_USER_RULE`: records mentioned as links to their pages by full ID, text to copy in a fenced code block), at both session starts (`ThreadRunner`, `StageThreads`): a new session takes the current text and records its version (`ThreadSession.officeInstructionsVersion`), a resume runs with the version it recorded, and one stored before them reads 0, so it keeps its cached prompt; the sessions behind Stage Threads (`ThreadRunner`); tokens per Thread and per Task (`TaskTokens`; `budgetTokensSoFar` is what a Stage's budget checks, leaving people's Threads out; `stageTokensSoFar` gives a Task's Stage Threads' by engine id, which Work's Daily caps read); reading Thread messages for every person's session (`read_threads`, spec 2.4: a range, a person, a Task, a Project and a text, capped at `THREAD_HISTORY_READ_LIMIT`, read on with `after`); what the user has seen in a chat (`thread_seen`, one row per chat Thread holding its last message seen, `ChatActivity`, pure `chatActivityOfPeople`): `PUT /threads/:id/seen` moves it forward only and raises `ThreadSeen`, `GET /chats/activity` gives who is answering and who has answered, and a Thread's response carries `answered` and `lastMovedAt`, null outside a chat; a Task's conversation (`TaskConversations`, pure `conversationTabs(planner | undefined)`, with no pinned planning tab while nobody holds Plans): who has a tab, each with their one Thread, whether their Stage runs and the Consultations waiting on them or answered by them, derived from the Task's Threads alone, the planner's (whoever holds Plans) tab also carrying the Initiative's planning Thread the Task is planned in (`planningThreadElsewhere`, from Work through `TaskThreadSetups`), and the person's Thread opened the first time a tab asks, never the planner's while the Task is planned in its Initiative's Thread; who is working on each Task now (`TaskConversations.peopleWorking`, pure `peopleWorkingOnTasks`, `GET /people-working`, the marks on the board's cards): a person with a Thread on the Task answering and no open Decision, as a Stage Thread stays answering while it waits on one, read in one go from `ThreadRepository.answering()`; each session's Sub-agents and Processes (spec 2.9, `SubAgentsAndProcesses`, tables `sub_agents_and_processes`, `sub_agent_messages`, `process_output`, keyed by the engine session id and the starting call's `callId`): kept from the session's events by a `SessionFollowing` per session, which both runners feed, with a Sub-agent's messages (its `withinToolCall` text and tool calls, and refusals of its calls, summed up as `sessionLogLines` does) and a Process's output in chunks, each numbered per item; the caps (`OUTPUT_KEPT_BYTES` counted after masking, `MESSAGES_KEPT`, `ENDED_ITEMS_KEPT` per session) held by the repository as it adds; Running ones Stopped with the session as its events finish, Stopped by `restart` at startup (`SubAgentsAndProcesses.recover`, beside `InterruptedAnswers.recover` in office.ts; each returns the Threads it cut short, the Threads that lost background Sub-agents and those left answering, which office.ts hands to Work's `PlanningAfterRestart`); while any background Sub-agent of a session runs, `SessionFollowing` holds one `BusyWork` item of kind `sub-agents` (Office-updates' `BusyWorkModule`), labelled by the Thread as its caller gives it (`FollowedSession.subAgentsLabel`: `ThreadRunner` with the turn label's words, `threadWords`, `StageThreads` by the Stage), ended with the last one or the session; foreground Sub-agents and Processes add none; `ThreadRunner`'s idle end (`IDLE_MS`) waits while one runs (`backgroundSubAgentsRunning`) and starts again once the last ends (`whenBackgroundSubAgentsEnd`), and never fires during a turn, one the engine begins on a Sub-agent's report too (`LiveSession.turnRunning`, `isAgentsOwnTurnEvent`); and removed when a fresh session replaces a Thread's (`ThreadRunner.answer`), never a Stage Thread's, whose run keeps them; read by `GET /threads/:id/sub-agents-and-processes`, `…/sub-agents/:callId/messages?after=` and `…/processes/:callId/output?after=`, and sent as `thread.sub-agent-*` and `thread.process-*` web events, the messages and output only to subscriptions scoped to their Thread. Each session's context reading (spec 2.5): `ThreadSession.contextTokens` and `contextWindow`, read at each turn's end only when the engine reports its context (`EngineSessions.reportsContext`), and moved live by the engine's `context-read` events while a turn runs (`readRunningContext`, `ContextRead`, the web event `thread.context-read`); the Context policy decides on the turn's end reading alone. A person's lists of Threads, a page at a time (the paging pattern in [the platform's map](../../platform/MAP.md)): `GET /chats/:roleKey/threads` and `GET /roles/:roleKey/task-threads` answer 30 summaries newest started first, by `(started_at, id)` with a cursor and the total (`ThreadSummaries`, `ThreadRepository.personsThreads` reading one row past the page, by the index `threads_person_newest`), a Thread on a Task named with its Task's title and Project (`WorkRecords.taskSubjects`, one read per page); a row's context is `summarizeContext`, `decideContext` without the Brief, as no move depends on its size, so a list builds no Brief and reads no log; the Role card, Duties, settings and Allow changes are read once per page, the engine cascade once per Project, and `answered`/`lastMovedAt` in one read (`ChatActivity.inThreads`). The full reading, Brief tokens and alternatives included, stays on `GET /threads/:id` and the single-Thread writes (`ThreadContexts`). Work's person's Tasks read the titles of the person's Threads on Tasks through `ThreadService.titlesOnTasksWith` and the Tasks with an open Decision through `DecisionService.tasksWithOpenDecisions`.

**Talks to:** calls Office-updates' `BusyWork` (background Sub-agents), Engine, People (`RoleCards`; `EngineCascade` for the engine and model of every session, in the Thread's Project (while no engine is listed a message is refused in words before it is logged, `ThreadRefused`): a Stage's and a Task Thread's, the context label's (`ThreadContexts`) as the runner asks, none for a chat or an Initiative; `EngineCascadeModule` comes in through `register`'s `imports`), Skills (session skills, prepared with the session's Project, its id included, so Skills counts each Project skill's uses in that Project) and MCP servers (`SessionMcpServers`: a session's servers, prepared and rebuilt beside its skills; those left out lead its Brief, or the first message it is resumed with, through `withLeftOutServers`, which the Thread's log doesn't keep; one the engine failed to start is an `mcp-server-not-started` line in the log, through `sessionLogLines`). Reads Project bases through its `ProjectBases` port, bound to Projects' `BaseCheckouts` in [app.module.ts](../../app.module.ts), and a Project's short record for an Open page through `ProjectRecordSource`, bound to Projects' `ProjectRecords`; a person's comes from People's `PersonRecords`. Work fills `FireAlarmInThreads` as it starts with the fire alarm it keeps, and tells it when it sounds and which Tasks go on at the all clear; `TaskThreadSetups`, with what a Thread on a Task works with (by `taskThreadRequest`: whose, a person's own or not, a first session or not) and readying a Task for a person's Thread, `InitiativeThreadSetups`, with an Initiative's record, instructions and Office tools by the Thread and its person (shaping with whoever shapes Initiatives, planning with whoever holds Plans, Work telling the two apart by the Thread; its session reads every Project's base branch, as a chat's does, but once an Initiative with a Pipeline is confirmed the setup's `branchReads` names the Projects read at its Initiative's branch: `SessionPlaces` then gives the session `ProjectBases.initiativeFolder` as a readable folder (`SessionPlace.readableFolders`, passed to the engine as `readableFolders`), readies it by `refreshOnInitiative`, and `Briefs` lists the Projects by `listOnInitiative`, so The Projects names the branch, or that it is gone; a chat mentioning the Initiative, a Thread on a Task and Stage sessions read as before, and gets no `change_role`; only the planning Thread's gets `open_decision`, with a `taskId` naming one of the Initiative's Tasks), `ThreadService.startOnInitiative` taking the Thread's id from Work when Plan the Initiative keeps it first, and `initiativeThreadInSession` telling Work's planning tools which Initiative's Thread a session is in, and `WorkRecords`, with the records of Tasks, Initiatives and Ideas a message mentions, a Link card's Task title and the ids of a Task's Attachments (`initiativeTaskAttachmentIds` too, undefined for a Task that isn't the Initiative's, which refuses a planning Thread's Decision on it), since Work calls Conversations. Pipelines and Work reach it through ports bound to `StageThreads`, `StageDecisions`, `ThreadRunner`, `ThreadService` and `DecisionService` (Work's `TaskDecisions`: `openOn` and `openInThread`, the planning Brief's Decisions, and `waitingOnTheUserOn`, the Task record's Decisions waiting on the user; Work's `TaskThreads` and `InitiativeThreads` also through `ThreadService.personsThreadOnTask` and `askAgain`, which wake a planning Thread after a restart); Work's `IdeaCards` and Notifications' `OfficeStatusCards` post their cards through `ThreadService`. Each kind of Proposal is applied by the module that owns it through `ProposalAppliers`, a registry filled as modules start: `RoleProposals` applies Roles through People's `RoleService` (`hireFromScratch`/`hire`/`changeCard` with who proposed it, and their dry runs as a Proposal is drafted); `SizeThresholdProposals` and `OfficeInstructionsProposals` (adapters, for the contracts' rule Settings saves by) apply the size threshold and the Office instructions; `DutyProposals` applies `duties` through People's `Duties` (`changeProblems` as drafted, `changeAll` with each duty's `from` when applied); `ProjectCommandProposals` applies `project-commands` through Projects' `ProjectService` (`changeCommandsAsProposed`), whose rules judge it, and `ProjectCommandOfficeTools` drafts them; `SkillInstallProposals` applies `skill-install` through Skills' `SkillLibrary.install` (The Office fetches it; chats only read), `SkillUpdateProposals` applies `skill-update` through Skills' `SkillUpdates.apply`, `SkillProposals` applies `skill` through Skills' `SkillLibrary.write` (judged as drafted by `writeProblems`), and `SkillOfficeTools` drafts them: `propose_skill` for everyone, and, for whoever onboards Projects, `list_source_skills` and `propose_skill_install`, which read the Source through Skills' `SkillSources` and draft one Proposal per skill; a module that calls Conversations registers its kinds itself, as Work does the Office-wide limit, `initiative` and `project` (a Project to onboard, with the `propose_project` tool) and Pipelines does `pipeline` (with the `list_pipelines` and `propose_library_pipeline` tools) `stage-template` (with `list_stage_templates` and `propose_stage_template`) and `project-pipeline` (with `propose_project_pipeline`, `PROPOSE_PROJECT_PIPELINE_TOOL`), and drafts them through a port bound to `ProposalService`. An Office setting registers with `registerSetting`, giving its value now, which a Proposal of it starts from (`ProposalService.draftSetting`), of the type `OfficeSettingValues` gives it. Every session's Office tools, Work's and Pipelines' lists too, start from `READING_OFFICE_TOOLS` (`domain/session-instructions.ts`, exported for them), so every session, chats and Consultations included, reads every record and Attachment; only the writing tools differ.

**Traps:** a session on a Task with no worktree yet (`TaskThreadSetup.folder` undefined, as a Task planned in its Initiative's Thread that a Consultation is asked on) reads the Projects' checkouts as a chat does, at the Initiative's branch where the setup's `branchReads` names (`SessionPlaces.checkoutsPlace`), its Project's skills from that Project's base checkout; never hand a session a folder that isn't there. A Consultation whose session fails or never starts (a `failure` line, never the fire alarm's `STOPPED_BY_THE_FIRE_ALARM`) puts its Decision to the user (`Consultations.afterFailure`, `putDecisionToUser` with why, kept in `passedOn` as passed on by the Consultant, which the card shows), and the asker's Thread logs a `consultation-line` saying so; from a chat The Office answers the caller instead. A session on an Initiative works in the base checkouts' folder (`ProjectBases.folder`) even once it reads the Initiative's branch, which comes as a readable folder: Claude Code keeps transcripts by the session's folder, so moving it at Confirm would stop a session started while shaping from resuming; a resumed one gets the readable folder and keeps its Brief. Its Brief is read before `ready()` refreshes, so `listOnInitiative` must not fetch. A Process's output is masked by whole lines (`WholeLines`): an unfinished last line waits for its newline, the Process's end, the session's end or about a second (`HELD_LINE_MS`), since the mask matches within a text and a secret split across two reads would pass it; a description, prompt, command line, what a Sub-agent reported back and why one failed are masked too. A `SessionFollowing` handles its events one after another (a held line's flush takes its turn among them) and, on a resume, first reads which Sub-agents its session started. A Stage session runs with `subAgentsInForeground` (`StageThreads.settingsOf`, spec 2.9): the end of its turn is the Stage's result, so its Sub-agents answer within the turn; every other Thread's session leaves it unset and keeps background Sub-agents. `StageThreads` reads a session's events with one reader for its whole life (`read`): Sub-agent and Process events are kept as they come, between turns and after the run's last turn, and every other event waits in a channel for the turn that reads it; `endSession` waits for that reader, so a turn awaited meanwhile fails before it returns. what a session on a Task writes into a Thread (its text, its tool calls' summaries, a refusal's reason) goes through the Project's mask in `sessionLogLines` before it is stored or sent live, from `ProjectOutputMasks`, which app.module.ts binds to Projects' `ProjectService`; a chat's, an Initiative's and the Caretaker's sessions have no Project and mask nothing (`NO_MASK`). A person's Thread on a Task (`isPersonsThread`: not a Stage's, not a Consultation's; that of whoever holds Plans is the Planning Thread) keeps `stageThread` false, or a message would wait for a safe point; its setup says `asking`, so `SessionPlace.callsCanWait` is false and it gets no `change_role`, and a later session gets `brief` undefined, briefed by `freshPersonsThreadBrief` from the Thread alone. An MCP tool at Consult or Ask me still opens its approval Decision there, in that Thread. A running session can't change its Office tools, so `ThreadRunner.answer` resumes one whose place's tools changed, as the planner's (whoever holds Plans) do once the Task is Ready. What a person's session may do follows the duties their Role holds (`HeldDuties`, read through People's `Duties.heldBy` by `SessionPlaces`, `StageThreads` and `ThreadContexts`, whatever the Role key): Default person to talk to gives `chatInstructions`/`chatOfficeTools` Proposals of Roles and Office settings, Link cards, the Office status and `create_initiative`, with no `create_task` and no `consult`; Onboards and repairs Projects gives `roleOfficeTools` and `read_repository`; Shapes Initiatives gives `create_initiative`; the Caretaker never holds a duty and keeps only its own tools. A session keeps `heldDuties` as it starts, and the Context policy starts fresh (`duties-changed`) once its person holds other duties, so a moved duty reaches them from the next session. A call behind an enforced Hard switch (`HeldCalls`, the `change_role` tool, Task Threads only: a chat has no Decision to wait in) never waits in the tool call: it opens an approval Decision, and the Agent's repeat of the identical call runs once after "Allow once" (`decisions.approval_spent_at`). An MCP tool at Consult or Ask me is held the same way (`HeldCalls.holdMcpToolCall`, its call words with the input's keys sorted, `mcpToolCallWords`), reached from the engine's hook through `SessionOptions.approvalHold`; the runners take it from `ApprovalHolds`, which `HeldCalls` fills on start, since `HeldCalls` reaches the runners through `Consultations`. In a chat it is refused in the Hard switch's chat words; only `application/thread-runner.test.ts` leaves Threads answering, and it alone recovers interrupted answers ([testing](../../../docs/testing.md)). A consult or call of a hired Consultant (`Consultations`, `Decision.putTo`, a `request` among them) is the same Decision the Agent waits on, put to them instead of the user: the Consultation Thread (`Thread.consultation`) opens on the asker's Task, or in the callee's own chat for a call from a chat (`consultationHome`), with The Office's `consultation-line` saying what was asked and, once `answer_consultation` succeeds, the answer, when the Agent's turn ends (`TurnEnded`), or at once for The Office's Decision a Pipeline puts first to whoever is asked first when a Stage runs out of tries (`StageDecisions.open` with `putTo`, spec 2.3; the user is asked instead while nobody holds that duty or its holder can't be consulted), which they answer only in their own words (`consultantAnswerProblems`) or passes on to the user; the Consultant answers with `answer_consultation` through `DecisionService.answer`, and the user answering first is the take-over. A Consultant asked to approve may pass it on (`passOn` on `answer_consultation`, `passDecisionOn`): the same Decision is put to the one they name, in a Consultation of its own, or to the user once the chain has asked `CALL_STEPS` people or for someone not hired; `Decision.passedOn` keeps who and why, and only the Consultant it waits on now may answer. A Consultation may call someone itself, so one chain of calls spans Consultations: `CallChains` walks up the `Consultation.askerThreadId` links and the pure `callChain`/`callProblems`/`passedOnTo` (`domain/consult.ts`) count nested calls and passes-on together and refuse anyone already in the chain, naming them. From a chat a fallback to the user never waits on them: `Consultations` answers the caller's Decision as The Office (`Answerer` `the-office`, `byTheOffice`), telling them to ask the user, and a call naming nobody who can be called is refused at the tool. Every chat has `consult` (`chatOfficeTools`, `CALLING_RULE` in its instructions; the Default person to talk to's with `DEFAULT_PERSON_CALLING_RULE` before it, as they still redirect rather than relay), as do Work's Planning Thread, a person's Thread on a Task and an Initiative's shaping and planning Threads. A call from an Initiative's Thread naming no Task is on no Task, as a chat's (`callOnNoTask` in `thread-changes.ts`, one at a time), its Consultation in the callee's own chat; one naming a `taskId` (the consult tool's input) is on that Task, its Consultation there (`consultationHome`). `SessionPlaces.of` adds to every Thread the user talks to a person in the Office actions' tools their held duties cover (`OfficeToolRegistry.coveredBy`, the Engine's), never to a Stage Thread. A Decision with `putTo` is left out of `openDecisions()` and raises no Notification (spec 6), while `unansweredOn(taskId)`, the Task page's read, keeps it; `putDecisionToUser` is the way back when the Consultant can't answer. An Initiative's planning Thread holds several open Decisions, each on its Task (`decisionTaskOf` in `openDecision`), and stays answerable while the planner (whoever holds Plans) works: an answer given then is recorded at once (`keepAnswerForTurnEnd`: the Decision is answered, so its Task is free for Ready, and its `decision-answer` line has `delivery: "waiting"`), and `ThreadRunner` hands every waiting answer over in one message as the turn ends (`deliverWaitingAnswers`), or with the next answer given while the planner waits, each naming its Task (`decisionAnswersOnTasksMessage`), marking the lines delivered; a hand-over that never reaches a session reopens every Decision it carried (`reopenDecision`). A person answers a Decision waiting on the user for them, when the user asks in a Thread they talk in, with `answer_decision` (`DecisionService.answerForUser`, in `CHAT_OFFICE_TOOLS` and Work's Task and Initiative Thread lists, never an Agent Stage's or `consultationOfficeTools`): refused by `answerForUserProblems` for a Stage Thread or Consultation caller, a Decision put to a Consultant, an approval (`isApproval`) and one in the caller's own Thread, then it follows `answer` as the user's would, the `Answerer` being `at-users-request`. The answer keeps it as `atUsersRequest` (`roleKey`, the `threadId` the user asked in), on the Decision and its `decision-answer` line, never as `answeredBy`, which stays the Consultant's alone: Consultation tabs (`isConsultantsOwn`) and the Pipeline (`StageDecisions.answerOf` drops it, so no `guidedBy`) read it as the user's own; `answerGivenBy` turns an `Answerer` into the two fields. Answers still waiting when The Office stops wait for the next turn's end or the next answer. A Thread on a Task still refuses an answer while the person answers. A Decision's `attachmentIds` name Attachments Work keeps, so no foreign key holds them: `open_decision` refuses any that isn't the Task's as it opens (`attachmentProblems`, through `WorkRecords.taskAttachmentIds`, asked only when it names some), and one removed later stays named, so a reader looks each id up among the Task's Attachments. While the fire alarm is on every tool call of a session `ThreadRunner` runs is refused (`toolHold`, `FireAlarmLifts.heldReason`, in `HELD_BY_THE_FIRE_ALARM`), except in a Thread the user lifted it for (`fire_alarm_lifts`, kept for the sounding it was made in, so it ends at the all clear; `GET /fire-alarm/lifts`, `PUT`/`DELETE /fire-alarm/lifts/:threadId`); a Stage Thread's session takes no hold, since its Stage is held at its safe point. No Consultation opens then, and as it sounds every Consultation answering stops (`ThreadRunner.stopAnswering`), its Decision still put to its Consultant: at the all clear, on each Task that goes on and for every call from a chat whose caller someone fills (`unansweredOnNoTask`), the Consultant is asked again in the Consultation it stopped (`ThreadRunner.askAgain`, its session continued or replaced under the Context policy) or in one it kept from opening (`Consultations.goOnAfterAllClear`). `StageThreads.sessionAhead` decides a Stage's session as `open` would, opening nothing, for the all clear's plan. A Consultation's session is built from its Consultant alone (`SessionPlaces.consultationTools`): `consultationOfficeTools(held, canCall)`, their chat's drafting tools and `consult` only while its chain may ask one more, read-only in either home and never `callsCanWait`, so it opens no Decision of its own and gets no `change_role`. A Brief's Memory is read by its `MemoryReach`: a Task's Project and all Projects on a Task, all Projects on an Initiative, every note in a chat, each labelled with its Project there. A message's mentions are the record links in it (`recordLinksIn` from the contracts, read in `ThreadsController.send`); `ThreadRunner.send` reads each record then (`MentionedRecords`) and puts them in the Brief of a session that starts on the message, or after the message into a running or resumed one: the log keeps the message as written, and a barge-in into a running Stage Thread gets no records. A message from the chat drawer may come with its Open page (`SentWith.openPage`, kept on the user message, which only a chat Thread takes; a Task's or Initiative's Thread drops it): its record (`MentionedRecords.openPage`) ends a new session's Brief, and goes after the message and its Mentions into a running or resumed one unless the message mentions it or the previous user message in the session, read back to the context line of the move that started it, had the same (`openPageToGive`, `domain/open-page.ts`). A test assembling `MentionedRecords` by hand provides `openPageRecordProviders()`. A Proposal is drafted by anyone's `propose_skill` in their chat (`CHAT_OFFICE_TOOLS`, so a test standing in for the chat tools registers it too, unless it boots `SkillOfficeTools`), by `propose_role` and `propose_office_setting` of whoever holds Default person to talk to (`chatOfficeTools(held)`, which also gives Work's `create_initiative`, `CREATE_INITIATIVE_TOOL`, to the chats of that holder and of whoever shapes Initiatives alone, never a Stage, planning, shaping or Consultation session), by the Caretaker's `propose_office_setup` (`caretakerChatOfficeTools(held)` adds it to the chat's own, its only drafting tool besides `propose_skill`: no `propose_role` or `change_role`, so its fixed Change Roles Never holds; `caretakerChatInstructions` carries one fixed set-up paragraph, `OFFICE_SETUP_RULE`, the same with changes allowed or not), by `propose_project_commands`, `propose_library_pipeline`, `propose_stage_template` and `propose_skill_install` of whoever onboards Projects (`roleOfficeTools(held)`, given in their chat and their Stage Threads alike, so their session needs Pipelines booted for its tools), or by the shaping tools of whoever shapes Initiatives on an active Initiative (Work's `ProposalDrafts`), returns at once and waits on nobody; the owner judges it as it is drafted, and the Agent reads its reasons as the tool's error (`ScriptedSession.reportedEvents` shows what the Agent read); applying holds its row (`updateProposal`) while the owner carries it out, so a refusal saves nothing and leaves it open. Applying a number setting overwrites whatever it holds, but `office-instructions` replaces a whole text, so `OfficeInstructions.replace` refuses it under the store's lock once the text is no longer `from`; only `apply` sees that, as `problemsWith` runs at the draft alone. `duties` must not overwrite either: `DutyProposals.apply` hands People each duty's `from`, so `Duties.changeAll` refuses them all (`DutyRefused`, read as `ProposalRefused`) once any one names another Role than it was drafted from; its value now names every duty (the Role key stored, hired or not), and `draftSetting` cuts it to the duties `to` names. The tool takes them as `duties`, a list of `{ duty, holder }`, each duty once. The session of whoever holds Default person to talk to keeps the version it started with, so `propose_office_setting` sends them to `read_office_instructions` first: a draft of an old copy still has `from` as the text now, and the card shows only `to`. The tool takes a number as `value` and the text as `text`, since an Office tool's input must stay one object for the Claude Code adapters, and trims the text before it is drafted, so "the same text" is judged as it would be saved. A `change` keeps only the fields it rewrites (`from`/`to`) and is merged onto the card as it is when applied, never a stale whole card.
