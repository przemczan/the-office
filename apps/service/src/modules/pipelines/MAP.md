# Pipelines: module map

**Owns:** the Pipeline library, its office-wide Pipelines (`pipelines`, its migration seeding the built-ins of `domain/built-in-pipelines.ts` once, each later built-in by a migration of its own that skips a name the user already took (Set up run environment, `0103`; Resolve conflicts with its Stage templates, `0172`, seeded as a flow; Set up test targets with its Stage template, `0179`, listed last as it was seeded last); Onboard, Set up run environment and Set up test targets stay in the library (`removalProblems`), as onboarding and a Project's set-up Tasks use them; `PipelineLibrary` reads it, `PipelineLibraryEditor` adds, copies, saves and removes), the Project Pipelines beside it (`project_pipelines`, migrations `0130` and `0205`: each its Project's, a full Pipeline of its own Stages, routes and places, made as a copy of an office-wide Pipeline or another of its Project's and keeping `copiedFrom` (name and when) for its words alone, pure `domain/project-pipeline.ts`; `PipelineLibraryEditor` adds (copies), checks, saves and removes them under the same `LIBRARY` lock, which `holdingLibrary` lends to `ProjectPipelineMoveOver`), the Stage templates beside it (`stage_templates`, its migration `0107` seeding `domain/built-in-stage-templates.ts` once; `StageTemplateLibrary` reads them, `StageTemplateLibraryEditor` adds, saves and removes, removing never refused: it unlinks the template's linked Stages, which keep their fields), the links of office-wide and Project Pipelines' Stages to their Stage template (an optional `templateId` in each Stage's jsonb, no column of its own; pure `domain/stage-template-link.ts` works out a Stage's template fields, how it differs and taking them back; `LinkedStages` lists a template's linked Stages, applies an edit to the chosen ones through the Pipelines' own saves, and unlinks them all as the template is removed), each Task's own copy of its Stages (`task_stages`, made at Start or at the user's first edit for the Task), and the Stage interpreter that walks them: Agent, Script, Gate and Publish Stages, loops and rounds, budgets, Stage runs (`stage_runs`), and their history for Work's Usage estimates (`UsageHistory`, pure `domain/usage-history.ts`) and the Briefs of people's Threads on Tasks and a Task's record in `read_task` (`StageResultWords`: each run's result, and a person's Handover notes with `of` or every one with its Stage and Role with `ofTask`; `outlinesOf` gives Work's Off-board Task cards each Task's own Stage names and its runs' Stage, Role, Thread, failure error and open `no-retries-left` Decision, the runs read at once), and when the last Gate run the user acted on ended, by which Work replaces an Agent's Attachment (`TaskGateRuns`, `lastActedOnGateRun` in `domain/gate.ts`, Work's `TaskGates` port), and a diagnosis of a Task's runs (`StageHistory`, pure `domain/stage-history-words.ts`, read by the Office tool `read_stage_history`, which `PipelineOfficeTools` registers and Conversations offers in every person's chat, Thread on a Task and Consultation, and `AGENT_STAGE_OFFICE_TOOLS` in every Agent Stage). An Agent run keeps its session's context after its latest turn (`StageRun.context`, `stage_runs.context`, from `StageTurn.context`), which an ended run's Thread tab shows, as a later run resuming the session moves the Thread's own.

**Talks to:** fills Work's `TaskEngineChecks` with the capability check of a change of Tasks' engines (`TaskRoleEngines`: the Roles each Task's Stages name, through `StageRoleEngines.workLevelsChangeProblems`; for a move choosing its Pipeline, the chosen Pipeline's Stages for the Task's Project after, `namedBefore` its Stages now), which also answers `GET /tasks/:id/engine-cascade` through the `RoleEngineCascade` port (`engine`: the one engine the Task's sessions run on, resolved once by `engineAt`; `people`: whoever plans, then each person the Stages name, once each, with the model and effort they work with there (`work`, from `applying`; null with no engine) and each of their Stages that sets its own effort); fills People's `PipelineRoleSources` with the Roles Agent Stages name (`RolesNamedInStages`: the library's everywhere, open Tasks' own Stages' by Project, pure `rolesNamedByOpenTasks`; a Task done or dropped, or Stages it no longer follows, don't count; and, for one Task, whom the Stages it works name, `rolesNamedByTask`); reacts to Work's events (`TaskStarted`, `TaskResumed`, `TaskPaused` (by the user or the fire alarm; one by the usage window is ignored, as the Stage runner held the run itself), `TaskStopped`, `AlarmSounded`, `TaskStateChanged` to Dropped (Resolve's merge aborted, and a started Task's running Stage interrupted as a Stop, whether the Task or its Initiative was dropped), and `TaskPipelineConfirmed`, which sets aside Stages edited for the old Pipeline) Conversations' `DecisionAnswered` and People's `RoleLetGo`; everything else goes through its ports, bound in [app.module.ts](../../app.module.ts): `StartedTasks` and `TaskRecords` to Work (the record an Agent Stage's Brief is made from, its "Linked records" and "Who asked" sections worded by Work; every Agent Stage reads every record with Conversations' `READING_OFFICE_TOOLS`, which `AGENT_STAGE_OFFICE_TOOLS` starts from, adding `read_stage_history` but never `read_threads`, and Conversations' `propose_bug_task` but never `create_task`; `StartedTasks.find` tells `StageHistory` an unknown Task from one not started), `KnownPeople` to People's `RoleCards` (`holderOf(duty)`: the Role holding a duty, undefined while nobody does; `dutyHolders()`: every held duty's holder in one read, which `RoleFillings.holders` reads for a Task's progress, so Now's read of every started Task asks People once per Task, not once per duty), `StageThreads`, `StageThreadMessages` (an Agent Stage run's Stage Thread messages for `read_stage_history`, worded by Conversations' `ThreadHistory` as `read_threads` words them), `StageDecisions` and `TaskThreadSessions` to Conversations, `TaskGit`, `TaskCommands` (Script Stages' commands, installs, and Agents' commands through `run_project_command`) and `TaskPublishing` to Projects' `TaskWorktrees`, `TaskScreenshots` to Work's `StageScreenshots`, `TaskUsage` to Conversations' `TaskTokens` (`budgetTokensSoFar`: a person's Thread, the planning one too, never counts to a Stage's budget), `ProjectDefaults` to Projects' `ProjectService` (each Project's default Pipeline, each Kind's own default (`kindDefaultPipelines`), which removal and the command checks count as its default too (`it is its default Pipeline for Bugs`), and command keys), `ProposalDrafts` to Conversations' `ProposalService`, `StageRoleEngines` to People's `PipelineRoleCapabilityChecks` (a library save or a Task's Stage list edit that newly names a Role whose engine can't work an Agent Stage is refused: the editor's saves, its check and a Proposal's Stages, and `TaskStagesService.review`; only Roles neither the library nor the Task's own Stages name yet are weighed, a Task's in its Project, `StartedTask.projectId`); `PipelineInitiatives` to Work's `InitiativeService` (`withPipelines`: every Initiative naming a Pipeline of its own, whatever its state); the library editor counts Tasks through `StartedTasks.list` and Initiatives through `PipelineInitiatives`: a library Pipeline's use (`initiatives`, the shaping and active ones by name; `GET /pipelines/:id/use` answers their number), its removal (refused per such Initiative) and its missing commands (each Project such an Initiative spans) weigh them. Proposals of a library Pipeline's Stages by whoever onboards Projects and the Caretaker (`pipeline`): `PipelineOfficeTools` registers `list_pipelines` and `list_stage_templates`, which every session reads with, and `propose_library_pipeline`, and `PipelineProposals` fills Conversations' `ProposalAppliers`, saving through `PipelineLibraryEditor.saveProposedStages`, which refuses once the Stages changed since the draft (`proposedStagesProblems`, comparing Stages as kept, so a field left undefined equals one left out); Conversations keeps the Stages unread, and they are parsed back with the contracts' `stageSchema`. A Stage template's new Stage (`stage-template`) is proposed alike: `list_stage_templates` and `propose_stage_template`, saved through `StageTemplateLibraryEditor.saveProposedStage` and judged by `proposedStageProblems` (refused once the template's Stage changed since the draft, compared as kept, and by what a template save refuses: a name another template has and a single Stage's rules; its Role is only flagged, as on a template save, and counts for no engine check). A Project Pipeline, new or changed (`project-pipeline`, `ProposedProjectPipelineChange`), is proposed with `propose_project_pipeline` (a change gives the whole flow, a field left out keeping its value; a new one needs `copyOf`, an office-wide Pipeline but Onboard or one of its Project's, and may give its Stages) and saved through `PipelineLibraryEditor.saveProposedProjectPipeline` under the `LIBRARY` lock, judged by `proposedProjectPipelineProblems` (pure `proposedProjectPipelineProblems` in `domain/project-pipeline.ts`: an unknown Project Pipeline or another Project's, "<name> changed since this was proposed." once its name, description or Stages differ from `from` as kept, the Stages' names in routes not counting, and nothing changing; then the add's or save's own `projectPipelineProblems`); it never sets a Project's default. A Proposal still open in the shape before flows of their own fails to parse and is refused as changed since proposed. `list_pipelines` (an optional `project`, or an optional `pipeline` for that one alone, an unknown id refused) answers the office-wide Pipelines, then each Project Pipeline with its Project, where it was copied from, its Stages with their routes and places, and, when flagged, why it was Broken before The Office updated. `ProposalDrafts` drafts any of them (`ProposedLibraryChange`). Other modules read the library, its Pipelines and Stage templates, through `PipelineLibraryModule`, never `PipelinesModule`; the library's writes live in `PipelinesModule`, since they ask Projects and Work, who import the library. `UsageHistory` prices runs through Engine's `ModelPrices` (by each run's engine id and model); a Stage run keeps its engine's id and its name at the time, which the Agent Stage runner reads from Engine's `EngineModels` (the id when the engine was removed since its session started) and is for Work's port, through `UsageHistoryModule`. Counts a running Script Stage and Publish as Office-updates' `BusyWork` (`ScriptStageRunner.run`); while an Office update or restart is scheduled (`ScheduledExitHold`) the walk ends before starting an Agent or Script Stage, a Gate still asking, and walks those Tasks again on `ScheduledExitCancelled`. Registers its Prompt templates in Prompt templates' catalog and renders them through `PromptTemplates`: the Stage Thread's instructions, the Brief, each Stage's message with its held, runs-again, sent-again and earlier-result parts (`agent-stage-brief-templates.ts`), the result correction, the Hard switches and commands sections, branch news and Resolve's briefs; `AgentStageRunner`, `StageGit`, `ResolveStageGit` and `StageResultWords` load the texts at use time (one `textsOf` each) and pass them to the pure domain functions. The Pipeline library's Stage briefs (the built-in Pipelines' too) are seed data edited there, not templates. Reads Conversations' `ConsultationsOnTasks` through its `TaskConsultations` port (bound in app.module.ts) to tell a Consultation on a Task from a Stage's session in `write_run_environment_definition`, and logs the commit line in the asking Thread through it. Asks `KnownPeople.holderOf("onboards-projects")` (`setUpByOf`, `application/command-set-up-by.ts`) before a Script Stage or a condition runs its command, so a command not set names whom to consult in its could-not-run words (Projects' `ScriptCommandOptions.setUpBy`).

**Traps:** `PostgresPipelineRepository`'s and `PostgresProjectPipelineRepository`'s reads go through the platform's read scope (`readOnce`, platform MAP): within one GET they answer the same objects to every caller, who never changes them, and every write of their tables runs through `forgettingReads`, a new writer too.

- The Task's commit message (spec §2.3): every Agent Stage's Brief shows it (`TaskRecord.commitMessage`, Work's, the default while none is written) and its Stage message tells only the last Agent Stage before a Publish that lands it to recheck it (`isLastAgentStageBeforePublish`: the conflict chain's Stages, `conflictOnlyStages`, passed over and never it, a `branch-only` Publish landing nothing), with the branch it lands on (`landsOn`) and the revisions its whole diff is read from (`changesFrom`, `TaskGit.changeBases`, the same `changesSoFar` counts from: a diff from one base, the Task's own commits with two). The Publish Stage sends it whole (`publishedMessage`) and, once a `merged` Publication carries a `subject` (one commit landed) or a pull request opened, marks it published (`StartedTasks.markCommitMessagePublished`); a Publishing Task's merge carries its commits unchanged, so it marks nothing. HEAD is expected at the `merged` Publication's `head`, never its `commit`, the landed commit no local branch names.
- A run held by the user's Pause or Stop names them: `TaskPaused`/`TaskStopped` carry the user, `StageRunInterruption.request` keeps it, `stage_runs.held_by_user` beside `held_by` for a start after a crash, and the outcome's `heldByUser` words the error, the history ("paused by the user Ann Lee") and the Brief's held section. Runs held before users existed name nobody ("the user"); there is no claim for them. A staffing Decision's answer drops (`StartedTasks.dropAsAnswered`, Work's one exception to an Agent Dropping only unstarted work, so a Consultant's Drop goes through) or resumes the Task, recorded by the user who answered or the Consultant (`answeredBy`); the Drop goes before the hold is released, so a refused one leaves the Task held.
- The devices connected as an Agent Stage starts (spec §2.13) come with Work's `TaskRecord.connectedDeviceLines`, so the port needs no new binding; `agentStageRecord` shows them in a "Connected devices" section only when there are some.
- Office-wide versus Project-aware: `PipelineLibrary.list`, `find`, `has` and `rolesNamed` read the office-wide Pipelines only; `read`, `listFor` and `commandsNamedBy`, which Work's and Projects' `KnownPipelines` bind, answer Project Pipelines too, each with its Project, where it was copied from (`copiedFrom`) and `broken` (its `brokenBeforeUpdate`, empty when not flagged), any Project's for `read` and `commandsNamedBy`, so each caller refuses another Project's and names it. `list`, `read`, `every` and `listFor` answer `ReadPipeline`s, every Stage there and the conflict chain's (`conflictOnlyStages`) marked `onlyAfterConflict`, which Work's Pipeline lines leave out (spec §2.3.5, "Library"); `find` and `forTask` answer the Stages unmarked, as a Proposal's `from` and Start's copy keep them. `forTask(pipelineId, projectId)` is the seam Start copies through (`TaskStagesService.pipeline`, so Start and a Task's first edit for itself copy a Project Pipeline's Stages as stored then), answering another Project's Project Pipeline as unknown and a flagged one with its reasons, which Start refuses (`StagesEditRefused`). `GET /pipelines` stays office-wide.
- Broken before The Office updated (spec §2.3.5) is the one Broken left: `project_pipelines.broken_before_update`, written only by the move (`movedProjectPipeline`: each Stage change that didn't apply, by `stageChangeWords`, then the rule reasons) and cleared only by the user's save, even unchanged (`savedProjectPipeline` without `keepsBroken`); applying a template edit to its linked Stages and removing a template keep it, as the repository's `save` writes the flag as given. While set, a Task, a default or Planning can't choose the Pipeline. A Project Pipeline's save is checked by the library's rules (`projectPipelineEditProblems`: names through `pipeline-names.ts`, `stageProblems`), the engine check in its Project and missing commands against its own Project alone; an office-wide save or removal never weighs, warns about or is refused for a Project Pipeline copied from it. A `project-pipeline` Proposal is refused for whatever its add or save is, through the same `projectPipelineProblems`: a command its Project lacks counts only once something runs it (its Project's default or a not-started Task), as on a save.
- Names span both tables: an office-wide Pipeline's against every Project Pipeline's (the refusal names the Project), a Project Pipeline's against the office-wide ones and its own Project's (`pipeline-names.ts`). Only `(project_id, lower(name))` is a unique index; the rest is checked in the application under the `LIBRARY` lock, so every write to either table takes it.
- `project_pipelines.project_id` has no foreign key (no module reads another's tables, spec 5.3), and migration `0205` dropped `base_pipeline_id`'s. The Office has no Project removal: one added must remove the Project's Project Pipelines with it, through a Projects event Pipelines reacts to. A Task moved to another Project already loses its Pipeline (`TaskMovedToProject`).
- The move from base Pipelines and Stage changes (spec §2.3.5): `movedProjectPipeline` in `domain/project-pipeline.ts` is the one converter, over `domain/stage-change.ts` (kept for the move alone). `ProjectPipelineMoveOver` stores each row whose `stages` is null through it on `onApplicationBootstrap`, under `PipelineLibraryEditor.holdingLibrary`, logging a failure for the next start to retry; `PostgresProjectPipelineRepository` converts such a row the same way on read until then. `buildStages` takes the base as `asFlow` reads it and works on it as the previous release kept it: a Stage's first route, when it is a failure route back, is its On failure setting, which only a Replace or a Change of On failure touches; each Publish Stage turns back into the kept Script `publish` Stage (`withKeptPublishStages`, a chain Gate as After a conflict: review), so the Stage changes apply to its target and After a conflict and the final `asFlow` draws the chain from what they built. A kept On failure above 9 rounds reads as 9, the most a limit may be (`withRoutesBack`). The legacy `base_pipeline_id` and `stage_changes` stay for a rollback (AGENTS.md): a new row writes `stage_changes = []` and the office-wide Pipeline at the root of its copy chain as `base_pipeline_id`, so the previous release reads it as a plain copy of that Pipeline. Nothing else reads or writes them; a later release drops them and the converter.
- A Project Pipeline's add, save and removal publish the office-wide `PipelineAdded`, `PipelineSaved` and `PipelineRemoved`, so the web's refetches cover both; its engine check names Roles in its Project (`RolesNamedInStages` registers its Stages' Roles as a second `PipelineRoleSources` source).

- A Task in Shaping keeps its Stages as Work keeps its Pipeline (`whyStagesAreKept`), and `library-pipeline.ts` lists the not-started states apart from Work's, Shaping among them; it lists an Initiative's open states (shaping, active) apart too, as Work's `withPipelines` answers done and dropped Initiatives as well.
- A Publish Stage's `publishTarget` absent means the Project's publishing mode: Stages stored before it was added carry none, so never require it.
- An Agent Stage's `permissions` narrow its Role card's profile through People's `narrowedPermissionProfile` (in `AgentStageRunner.open` and `sessionAhead`, the Brief's commands too); absent keeps the card's, and Stages stored before carry none. A setting wider than the card is flagged in the library and refused for a Task (`RoleFillings.permissionProblems`, not `staffingProblems`, which holds Tasks); at run time the card's applies. MCP tools the Role's servers don't have are ignored.
- An Agent Stage's `permissions.commands` is applied by Pipelines, not by `narrowedPermissionProfile`: the card has no list of commands. `stageProjectCommands` in `allowed-commands.ts` is its one source, read by `allowedCommands` (the Brief and the engine's allowed lines) and `commandKeyRefusal`, which `StageProjectCommands` (`run_project_command`) checks a key against, finding the running Stage in `asFlow` of the Task's Stages; install is never refused there. Under the run permission anything a narrowing is only told, so a command line the Agent writes out, even one extending a kept command's, is judged by the session's rules alone and still runs; only its key is refused.
- The built-ins live twice: `builtInPipelines` and the `pipelines` migration's seed, which `pipeline-library.test.ts` compares; a change to a built-in needs a migration too, as `0151` moved their Agent Stages from `developer` and `devops` to the duties `implements` and `onboards-projects`, in `pipelines` and `stage_templates` alike, wherever a built-in Stage still named its built-in Role (`stage-duties-migration.test.ts`). Once seeded, the table is the library, and the user's edits of a built-in stand. The built-ins are written as flows, each old "On failure go back" a failure route back placed first; `built-in-pipelines.full.test.ts` proves each is `asFlow` of the list the migrations seeded, kept in `built-in-pipelines-before-flows.fixtures.ts`, so a seeded Office and a new one walk alike.
- `PipelinesModule` exports `StageRunsRunningNow`, System health's Stage runs running: the Agent and Script Stage runs whose runner runs now, counted in memory around `StageInterpreter`'s runner call (a Gate never counts, and a restart starts it at 0). `UsageHistoryModule` also gives Telemetry's Stats `StageRunTotals` (the basic stats' Stage runs started since a time) and `RunningStageRuns` (the full stats' lane: `StageRunRepository.ranBetween`, every Agent Stage run overlapping a range with its `stage_runs.engine_id` and its Stage's name in `task_stages` now, its key once the Task no longer has the Stage; a run with no engine kept is left out) and `StageRunEngines` (the most expensive Tasks' tries: `StageRunRepository.enginesOfTasks`, each run of the Tasks named with an engine kept, by number, with its engine's name at the time, the engine it stood in for and its switches).
- `UsageHistoryModule` holds `StageRunRepository` and `UsageHistory` apart, as `PipelineLibraryModule` holds the library, so Work can import it: it must never depend on a port bound to Work. Work names the done Tasks (`UsageHistory.of(doneTaskIds)`, each Stage's median tokens; `dollarsPerToken(doneTaskIds)`; window % is the Engine's, not kept per run), as Pipelines keeps no Project or done time; the latest 20 by their last run's end are kept, chosen in SQL (`latestTasksUsage`), which reads only a run's usage columns: a whole run is about 2 KB of JSON, and every done Task's runs read whole blocked the event loop.
- The built-in Stage templates live twice too: `builtInStageTemplates`, worked out from `builtInPipelines` (the first Stage of each name, its key as the id), and `0107`'s, `0172`'s and `0179`'s seeds, which `stage-template-library.test.ts` compares; a new built-in Stage needs a migration of its own, and a migration test re-running an older migration over the built-ins leaves out those seeded after it (`stage-duties-migration.test.ts`).
- A Stage template has no routes or place: `templateStage` drops them on every add and save, so none is stored or returned. Its checks (`stageTemplateProblems`) are a single Stage's (`singleStageProblems` in `pipeline.ts`, which a Pipeline's checks share) and a name unique among templates in any case; key, "continue" and loop rules wait for the Pipeline or Task it is added to. Its problems and flags carry no Stage index.
- A template's Role is flagged like a library Pipeline's (`stageTemplateFlags`, `RoleFillings.stagePermissionProblems`), but a template is no Pipeline (spec 2.3): `RolesNamedInStages` and the engine checks leave its Role out, and the Stage it adds is checked when its Pipeline or Task is saved.
- A Stage's link to its template (spec §2.3.1) is only `templateId` in the Stage's jsonb, so the previous release reads and saves it, dropping it. Every office-wide and Project Pipeline save, its Proposal's included, drops a link whose template is gone or of another kind (`withLiveLinks`); a link never makes a save refused. A Task's own Stages never carry one (`makeTaskStages` and `editTaskStages` store `unlinked`). `LinkedStages.apply` saves each Pipeline under its own `holdingLibrary` through the editor's normal save, so one refused leaves the others applied. Removing a template takes `STAGE_TEMPLATES`, then `LIBRARY` for `unlinkAll`; nothing takes them the other way round, so keep it so.
- The service's tests share one database across files run in parallel: a test makes Pipelines and Stage templates of its own under a unique name and never changes or removes a built-in.
- `EventBus.publish` waits for its handlers, so the interpreter walks in the background (`walkInBackground`); awaiting the walk would hold Start's request for the whole Pipeline.
- An edit of a Task's Stages and the walk's start of each run take one per-Task lock (`TaskStagesService.holding`), and the walk reads the Stages afresh each move: start a run anywhere else and an edit can change the Stage under it.
- `POST /tasks/:id/stages/check` takes an optional `pipelineId`, the Pipeline the editor's draft follows: a Task with no Pipeline yet, or one swapped to before Save, is checked as if it followed it (`TaskStagesService.review`, through `ownOrCopied` and `forTask`, which refuse a Broken one or another Project's). Without it the check reads the Task's own Pipeline and refuses a Task with none. A refusal answers as `PUT /tasks/:id/stages` does (`StagesEditRefusalsFilter`, 422). Saving still needs the Pipeline set first (`PUT /tasks/:id/pipeline`).
- The walk is worked out from the Stage runs (`nextMove` in `domain/pipeline-walk.ts`): a Gate action, an answer or a send-back is data on a run, replayed, not a call.
- Reported met is one rule, `reportedMet`, over all the Task's runs in their order; a Stage's own `runs` won't do, as a loop's later run can sit under an earlier Stage. `GET /tasks/:id/stages` answers it as `definitionOfDoneMet`, beside each outcome's own report: read that one, never work it out from the outcomes. Both fold every done Agent report oldest first (`definitionOfDoneReports`): a statement stays met once reported until a report lists it in `definitionOfDoneNoLongerMet`, so a report leaving it out takes nothing back. Out of reach (`reportedOutOfReach`) adds up the same way, counting only statements not Reported met; it shows in the Definition of Done Decision (`definitionOfDoneNotMet`), whose question carries those statements apart from the unmet ones, and at the Gate that is the check.
- The Definition of Done check (`goTo` → `checkDefinitionOfDone`) runs as the walk enters a Publish Stage that isn't the first, asking on the run before it (`before` set), and at End only when the walk entered no such Publish on its path. Call it met (`mark-done` with `before`) sets `walk.calledMet`, so neither a later entry into Publish nor the end asks again; Continue at a Gate that is the check (`gateChecksDefinitionOfDone`, over `asFlow`'s Stages in the Pipeline's order: no Agent Stage nor later Gate before the Publish after it, the conflict chain's Stages passed over and its Gate never the check) sets it too, replayed from the Gate run's `gateAction`, and `GET /tasks/:id/stages` names those Gates in `gatesCheckingDefinitionOfDone`, beside `definitionOfDoneOutOfReach`, for the Gate card's unmet list. Conflict handling (`walk.conflictHandling`, set as the walk follows a Publish Stage's Conflict route, cleared as it enters a Publish or runs a Stage outside the conflict chain, `walk.chain`, as a send-back from a failure or a Gate does) doesn't check at the Publish it returns to, and the first Stage the check skips is the first not of the conflict chain, where the walk starts too. Runs from before the check moved: a `definition-of-done` Decision on any run is replayed where it is, and only the last run asks, so older runs that went past Publish unchecked replay on.
- `StageGit.start` is the only check that takes a moved HEAD: along the base (`TaskGit.movedAlongBase`) or after the user's Keep (`branchKept`), told to the Agent as `branchNews`. Any other move is a refusal, `branchMoved` on the outcome, walked by `afterBranchMoved`: no round, the user alone. The checks after a Stage (`checkHead`) stay strict; a refusal saves the expected commit, so the next run expects the same place.
- The Task's first Stage, the one no earlier run has a `headCommit` before, brings the branch to the base in `StageGit.start` (planning made the worktree, maybe hours ago). A conflict gives the branch back and only tells the Agent; a failed fetch doesn't stop the Stage.
- `run_project_command` (`StageProjectCommands`, the tool's name from Engine's `RUN_PROJECT_COMMAND_TOOL`, which the container runtime's refusal names) runs a command for the Agent of the running Agent Stage through `TaskCommands.runForAgent`: a command line it wrote only once the session's Office rules allow it as its own Bash call (`OfficeToolCall.judgeCommand`, so the profile, git, the secrets and the container runtime hold, and a read-only profile runs only the Project's own commands, by key); a key is not judged. A key is any command in the Project's list, or `install`; one it lacks, or whose line is blank, answers `no-command`. `allowedCommands` lists every command in the list but install, as "- key (Name): `line`", for the Brief and the engine's allowed lines. A Script Stage names any command by its key (or `publish`); `TaskCommands.runCommand` answers the command's kind beside its runs, and `ScriptStageRunner` leaves the branch as it was after a test-kind one, or a key the Project lacks, and commits a build or lint one; the test handling of the run itself goes by the kind, in Projects. A call's output goes to a file in the call's `outputFolder`, which the session may Read. Every such command belongs to its Stage run (`StageCommandRuns`): `AgentStageRunner.work` begins them as the Thread opens and ends them, with everything they started, before the session ends and git is read, whatever ended the Stage (result, failure, Stop, Pause, restart); the run's `commandsSignal` (the fire alarm, The Office shutting down) stops them at once. A call before `begin` or after `end` is refused, so none outlives its run.
