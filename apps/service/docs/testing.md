# Tests

Tests sit beside their code as `*.test.ts`; the support they share is in `test/`.

- **Postgres is needed:** `docker compose up -d` first. Each run creates a throwaway database on the server `DATABASE_URL` names (from the environment, else `.env`), migrates it and drops it at the end. Every test file in the run shares it, so a repository test makes its own rows and looks only at those.
- **A port's contract** (`*.contract.ts`, beside the port) is the tests every adapter of the port runs against itself; it is left out of the build, like fixtures.
- **No model calls by default:** sessions in tests run on the scripted engine (`modules/engine/adapters/scripted/`), which replays recordings or scripts written by hand; another module's test imports `ScriptedEngineModule.register(new ScriptedEngine(scripts))` from the Engine's index in place of `EngineModule`. The Agent SDK adapter's tests run live sessions only when `OFFICE_ENGINE_TESTS=live` is set; `OFFICE_ENGINE_TESTS=record` also re-records the engine contract's recordings from them, to be read in the diff and committed after an SDK bump. They run on the login in the engine `claude-code`'s config folder of the test's Office data directory (`<temp>/office-engine-data/engines/claude-code/` for the adapters' own tests), signed in there first: the pinned binary's `auth login` with `CLAUDE_CONFIG_DIR` set to it. With `OFFICE_TEST_PROJECT` set to the Test Project's folder, they also run task 06's check on it, traced to otel-lgtm, and task 07's skills check (`modules/skills/application/session-skills.test.ts`). The OpenAI-compatible API engine runs the contract on a live server when `OFFICE_API_BASE_URL` and `OFFICE_API_MODEL` are set as well (`OFFICE_API_KEY` for one that needs a key); a local server is slow, so pick the scenarios with `-t`. With `OFFICE_TEST_PROJECT` too, task 35's check (`conversations/application/openai-compatible-api-test-project-check`) asks a Role on that model a question in its chat, run alone.
- **A skill on and for everyone reaches every session prepared on the shared database,** whichever test prepares it, and its files are in its own test's folder. Tests that prepare sessions with one stay in `modules/skills/application/session-skills.test.ts`, whose tests run one at a time; no other test leaves a skill on and for everyone.
- **The skill update check reads the Source of every installed skill on the shared database,** so one file's check would note another file's updates first (its events on the wrong app's bus) and run git in that file's temporary Sources. No test app runs it by the clock (its `Schedule` is a `ManualSchedule`); a test that runs it (`runDaily(SKILL_UPDATE_CHECK)`) binds a fetcher that reads only its own Sources (`ownSources` from Skills' `index.fixtures.ts`), as `skill-updates.test.ts` and `devops-proposals.test.ts` do.
- **Only `modules/conversations/application/thread-runner.test.ts` leaves Threads answering,** and it alone recovers interrupted answers, which waits every answering Thread on the shared database; its sessions get no library skills, which other files may change meanwhile.
- **Outcomes landing close together collapse into one, across files,** and the delivery rules act on every open Notification the clock has reached: a test that looks at what Notifications raise or push sets its `ManualSchedule` to a day of its own in a year no other file's clock reaches (2001 in `notification-service.test.ts`), or keeps its Notifications in a fixture of its own (`NotificationsForTests`, as `notification-delivery.test.ts` does with the timing and the user's activity too); an open Notification also swallows a new one like it (one engine down at a time), so a test that raises one closes it again. Quiet hours written to the stored timing hold every file's Notifications, so only the timing route's test writes them, at hours the system's clock is outside of, and gives the defaults back.
- **The fire alarm holds every file's Starts and pauses every file's started Tasks,** so no test sounds the stored one: a test binds `FireAlarmRepositoryForTests` (and, to sound it, a `TaskRepository` narrowed to its own Project, as `tasks.controller.test.ts` does), turning it off before it drops its Tasks; the Postgres adapter's test rolls its transaction back. A test override may be a factory of other providers (`useFactory`, `inject`). Lifts are kept by when the alarm sounded, in a table every file shares, so a test lifting one gives `FireAlarmInThreads` a sounding at a moment of its own (a random offset).
- **The queue for Start is released by every app with Work, on its own events and weighed by its own stand-ins,** so one file's release would start or refuse another file's queued Tasks, and every file's started Tasks would hold its desks. Every such app binds the queue narrowed to its own Projects, which weighs only their started Tasks too (`ownProjectsQueue` from Work's `index.fixtures.ts`; `startWorkApplication` binds it with none): a test that queues Tasks names its Project (`tasks.controller.test.ts`, `task-walks.test.ts`), the others name none. The Start check and the caps read the Tasks themselves, so `tasks.controller.test.ts` also lists other Projects' started Tasks as none (its `OwnProjectTaskRepository`).
- **An app with the whole of Pipelines on Work's Tasks (the composition root, `AppModule`) takes up, as it starts, every run left running among the Tasks it lists,** ending each as The Office restarted during it and walking the Task on with its own scripted engine, which takes that file's queued scripts. Every such app binds the started Tasks narrowed to its own Projects (`ownProjectsStartedTasks` from Pipelines' `index.fixtures.ts`, beside `ownProjectsQueue`): `work/adapters/http/task-walks.test.ts` names its Project, `devops-proposals.test.ts` none.
- **The day's figures (tokens today, Tasks touched) are kept by day for every file,** so a test that looks at how they grow fakes `Date` to a day of its own (2002 in `now-service.test.ts`).
- **A Role hired from a preset has the preset's fixed key** (`planner`, `developer`, `reviewer`), so only `modules/people/adapters/http/roles.controller.test.ts` hires from the presets, removing those Roles and taking their skills away before each test. Other tests keep a Role of their own under a key of their own. The exceptions are the live checks of tasks 10 to 16, 26 and 27 (in `modules/work/application/`, `test-project-check.test.ts`, `planning-` and `fire-alarm-test-project-check.test.ts`, the last sounding an alarm of its own; in `modules/pipelines/application/`, `stage-interpreter-`, `running-task-`, `gate-publish-`, `parallel-work-` and `stage-editor-test-project-check.test.ts`; `modules/notifications/application/test-project-check.test.ts`; task 35's `modules/conversations/application/openai-compatible-api-test-project-check.test.ts`; task 36's `modules/mcp-servers/application/mcp-tools-test-project-check.test.ts`; task 37's `modules/pipelines/application/usage-estimates-test-project-check.test.ts`), which hire the Planner (and from task 12 the Developer) through the real People module and therefore each run alone: `npx vitest run work/application/test-project-check`, `pipelines/application/stage-editor-test-project-check` and so on, with the live variables set; their shared steps are in `test/live-check.ts`, and `OFFICE_CHECK_ENGINE=claude-code-p` runs the Roles they hire on the `-p` fallback (task 29). Check that the run reports one test: a filter that matches no file (a full path once did, from a shell whose drive letter was lower case) runs nothing and still exits 0.
- **A file's tests run one after another, and the run lasts as long as its slowest file,** so a file of many real git commands (git's process start is most of each test on Windows, about 2.5 times slower in a full run) is split by area into files of a few seconds each, as `projects/adapters/git/command-line-git-*.test.ts` and `projects/application/publishing-*.test.ts` are, each building its one repository in `beforeAll` (`WorktreeMaker`, `PublishingTestbed`). Measure a full run's per-file times with vitest's JSON reporter before and after.
- **`startTestApplication({ ...metadata, database })`** boots Nest providers, controllers and modules with HTTP configured as in production, on `127.0.0.1` and a free port; `database: true` adds `DatabaseModule` on the test database. Close its `app` in `afterEach`.
