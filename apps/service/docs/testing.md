# Tests

Tests sit beside their code as `*.test.ts`; the support they share is in `test/`.

- **Postgres is needed:** on the workstation, `docker compose up -d` first. A Task's run environment (`.devcontainer/compose.yaml`) brings its own Postgres and sets `DATABASE_URL`, so a Task's worktree needs neither that nor a `.env`, and an Agent runs the tests there through `run_project_command`. Each run creates a throwaway database on the server `DATABASE_URL` names (from the environment, else `.env`), migrates it and drops it at the end. Every test file in the run shares it, so a repository test makes its own rows and looks only at those.
- **A port's contract** (`*.contract.ts`, beside the port) is the tests every adapter of the port runs against itself; it is left out of the build, like fixtures.
- **No model calls by default:** sessions in tests run on the scripted engine (`modules/engine/adapters/scripted/`), which replays recordings or scripts written by hand; another module's test imports `ScriptedEngineModule.register(new ScriptedEngine(scripts))` from the Engine's index in place of `EngineModule`. The Agent SDK adapter's tests run live sessions only when `OFFICE_ENGINE_TESTS=live` is set; `OFFICE_ENGINE_TESTS=record` also re-records the engine contract's recordings from them, to be read in the diff and committed after an SDK bump. The contract's `usage-window-used-up` scenario runs live only with `OFFICE_ENGINE_USAGE_WINDOW_USED_UP=1` as well, on an account whose usage window is used up (record it then, too); `failed-after-allowed` runs on its recording only, as no live turn fails on purpose. They run on the login in the engine `claude-code`'s config folder of the test's Office data directory (`<temp>/office-engine-data/engines/claude-code/` for the adapters' own tests), signed in there first: the pinned binary's `auth login` with `CLAUDE_CONFIG_DIR` set to it. With `OFFICE_TEST_PROJECT` set to the Test Project's folder, they also run task 06's check on it, traced to the bundled Grafana, and task 07's skills check (`modules/skills/application/session-skills.test.ts`). The OpenAI-compatible API engine runs the contract on a live server when `OFFICE_API_BASE_URL` and `OFFICE_API_MODEL` are set as well (`OFFICE_API_KEY` for one that needs a key); a local server is slow, so pick the scenarios with `-t`. With `OFFICE_TEST_PROJECT` too, task 35's check (`conversations/application/openai-compatible-api-test-project-check`) asks a Role on that model a question in its chat, run alone. The Codex engine runs the contract live with `OFFICE_ENGINE_TESTS=live` (`modules/engine/adapters/codex/codex-engine.test.ts`, on `gpt-6-luna` at `low` effort) on the folder the engine check signed in (`OFFICE_CODEX_ENGINE_FOLDER`, by default `/root/.codex-engine-check`; skipped on Windows without it), deleting the threads it started there; `record` also writes each scenario's wire, which the default run replays on a stand-in app-server (`fake-codex-app-server.fixtures.ts`) with no model call, checking every message the engine sends and making the recorded MCP tool calls on the session's endpoint for real, and its events, which the scripted engine replays under Codex's capabilities.
- **A skill on and for everyone reaches every session prepared on the shared database,** whichever test prepares it, and its files are only in its own test's folder, so another file's session would list it and fail on its missing files. No test stores one: `modules/skills/application/session-skills.test.ts` makes its skills for everyone in its own app alone (`everyoneHere`, `adapters/postgres/everyone-here.fixtures.ts`), and `skills.controller.test.ts` marks one for everyone only while it is off. Task 07's live check, run alone, is the exception.
- **The skill update check reads the Source of every installed skill on the shared database,** so one file's check would note another file's updates first (its events on the wrong app's bus) and run git in that file's temporary Sources. No test app runs it by the clock (its `Schedule` is a `ManualSchedule`); a test that runs it (`runDaily(SKILL_UPDATE_CHECK)`) binds a fetcher that reads only its own Sources (`ownSources` from Skills' `index.fixtures.ts`), as `skill-updates.full.test.ts` and `devops-skill-sources.full.test.ts` do.
- **The Google OAuth client is one row of the shared database** (`google_client`), which every file's sign-in page would read, so only `modules/users/adapters/postgres/postgres-google-client-repository.test.ts` writes it; other tests bind `googleClientForTests()` (`users/ports/google-client-repository.fixtures.ts`), a client kept in memory.
- **Only `modules/conversations/application/thread-runner.test.ts` leaves Threads answering,** and it alone recovers interrupted answers, which waits every answering Thread on the shared database; its sessions get no library skills, which other files may change meanwhile.
- **Outcomes landing close together collapse into one, across files,** and the delivery rules act on every open Notification the clock has reached: a test that looks at what Notifications raise or push sets its `ManualSchedule` to a day of its own in a year no other file's clock reaches (2001 in `notification-service.full.test.ts`), or keeps its Notifications in a fixture of its own (`NotificationsForTests`, as `notification-delivery.full.test.ts` does with the timing and the user's activity too); an open Notification also swallows a new one like it (one engine down at a time), so a test that raises one closes it again. Quiet hours written to the stored timing hold every file's Notifications, so only the timing route's test writes them, at hours the system's clock is outside of, and gives the defaults back.
- **The fire alarm holds every file's Starts and pauses every file's started Tasks,** so no test sounds the stored one: a test binds `FireAlarmRepositoryForTests` (and, to sound it, a `TaskRepository` narrowed to its own Project, as `tasks.controller.test.ts` does), turning it off before it drops its Tasks; the Postgres adapter's test rolls its transaction back. A test override may be a factory of other providers (`useFactory`, `inject`). Lifts are kept by when the alarm sounded, in a table every file shares, so a test lifting one gives `FireAlarmInThreads` a sounding at a moment of its own (a random offset).
- **The daily archiving of finished Tasks weighs every Done or Dropped Task on the shared database,** so one file's run would archive another file's Tasks. No test app starts it (only `office.ts` does); `work/application/task-archiving.full.test.ts` starts it in its own app, on its own settings (`WorkSettingsForTests`) and a `TaskRepository` that lists its own Project's Tasks alone.
- **The queue for Start is released by every app with Work, on its own events and weighed by its own stand-ins,** so one file's release would start or refuse another file's queued Tasks, and every file's started Tasks would hold its desks. Every such app binds the queue narrowed to its own Projects, which weighs only their started Tasks too (`ownProjectsQueue` from Work's `index.fixtures.ts`; `startWorkApplication` binds it with none): a test that queues Tasks names its Project (`tasks.controller.test.ts`, `task-walks.test.ts`), the others name none. The Start check and the caps read the Tasks themselves, so `tasks.controller.test.ts` and its full-run sibling also list other Projects' started Tasks as none (`OwnProjectTaskRepository`, in Work's `tasks.controller.fixtures.ts`).
- **An app with the whole of Pipelines on Work's Tasks (the composition root, `AppModule`) takes up, as it starts, every run left running among the Tasks it lists,** ending each as The Office restarted during it and walking the Task on with its own scripted engine, which takes that file's queued scripts. Every such app binds the started Tasks narrowed to its own Projects (`ownProjectsStartedTasks` from Pipelines' `index.fixtures.ts`, beside `ownProjectsQueue`): `work/adapters/http/task-walks.test.ts` names its Project, `devops-proposals.full.test.ts` and `devops-skill-sources.full.test.ts` none.
- **A test of something timed moves The Office's clock, never waits on the system's:** code that weighs or waits for a moment reads `Schedule.now()` and waits by `Schedule.once`, so a test sets its `ManualSchedule` (`setTime`) and moves it past the moment (`advanceBy`, as the Window caps tests do), with no margin of real time that a loaded machine uses up.
- **Tokens today are kept by day for every file,** so a test that looks at how they grow fakes `Date` to a day of its own (2002 in `now-service.full.test.ts`).
- **A Role hired from a preset has the preset's fixed key** (`planner`, `developer`, `reviewer`), so only `modules/people/adapters/http/roles.controller.test.ts` hires from the presets, removing those Roles and taking their skills away before each test. Other tests keep a Role of their own under a key of their own. The exceptions are the live checks of tasks 10 to 16, 26 and 27 (in `modules/work/application/`, `test-project-check.test.ts`, `planning-` and `fire-alarm-test-project-check.test.ts`, the last sounding an alarm of its own; in `modules/pipelines/application/`, `stage-interpreter-`, `running-task-`, `gate-publish-`, `parallel-work-` and `stage-editor-test-project-check.test.ts`; `modules/notifications/application/test-project-check.test.ts`; task 35's `modules/conversations/application/openai-compatible-api-test-project-check.test.ts`; task 36's `modules/mcp-servers/application/mcp-tools-test-project-check.test.ts`; task 37's `modules/pipelines/application/usage-estimates-test-project-check.test.ts`; the Task 7828b36f's `modules/conversations/application/message-images-test-project-check.test.ts`, which sends a plain red PNG with the first message of a planning Thread, as the web sends a pasted screenshot, for the Planner to name its colour, then starts the Thread fresh for the new session to read it again with `read_attachment`; the Initiative 1116efba's `modules/work/application/initiative-pipeline-test-project-check.test.ts`, which also hires the CTO, shapes an Initiative with a Pipeline and publishes it by merge into a throwaway `office-check-init-<hex>` base, so it needs `OFFICE_PUBLISH_CHECK=merge` and `OFFICE_TEST_PROJECT` set to a clone made for the check), which hire the Planner (and from task 12 the Developer) through the real People module and therefore each run alone: `npx vitest run work/application/test-project-check`, `pipelines/application/stage-editor-test-project-check` and so on, with the live variables set; their shared steps are in `test/live-check.ts`, and `OFFICE_CHECK_ENGINE=claude-code-p` runs the Roles they hire on the `-p` fallback (task 29). Check that the run reports one test: a filter that matches no file (a full path once did, from a shell whose drive letter was lower case) runs nothing and still exits 0.
- **A file's tests run one after another, and the run lasts as long as its slowest file,** so a file of many real git commands (git's process start is most of each test on Windows, about 2.5 times slower in a full run) is split by area into files of a few seconds each, as `projects/adapters/git/command-line-git-*.test.ts` and `projects/application/publishing-*.test.ts` are, each building its one repository in `beforeAll` (`WorktreeMaker`, `PublishingTestbed`). Measure a full run's per-file times with vitest's JSON reporter before and after.
- **`startTestApplication({ ...metadata, database })`** boots Nest providers, controllers and modules with HTTP configured as in production, on `127.0.0.1` and a free port; `database: true` adds `DatabaseModule` on the test database. Close its `app` in `afterEach`.

## The Test Project

The real Project the live checks run on (`OFFICE_TEST_PROJECT`): `notnullsoft-admin` at `D:\Projects\notnullsoft-admin`, chosen by the user. Base branch `main`, remote `https://github.com/przemczan/notnullsoft-admin.git`; an npm workspace on Node 22 with `npm install`, `npm run build`, `npm run lint` and `npm test`. A push to its `main` deploys production (`.github/workflows/deploy-production.yml`), so a Publish check publishes into a throwaway base branch made from origin's `main` and deleted afterwards (push + PR, or merge), never into `main`. It is never this repository or `D:\Projects\software-factory`.

The checks that look up their traces read the bundled Grafana at `http://127.0.0.1:3300`: choose Bundled Grafana in the dev Office's Settings › Telemetry first, which starts it ([running-the-office.md](../../../docs/running-the-office.md#telemetry)). Task 12's check skips the lookup with `OFFICE_CHECK_GRAFANA=off`, on a machine without it.

## The default run and the full run

`npm run test` (and `npm run verify`) runs the **default run**: only the critical and the smoke tests. Every other test is in the **full run**, run on demand with `npm run test:full` (`npm run verify:full` runs every check on it), for example before a large refactor or when a full-run test's area changes.

- **Critical:** the Office rules and the permission hook (git deny, secrets, protected paths, read fences); each Postgres repository's main round trip; Task states, Start rules, limits, the queue, dependencies and the fire alarm; Pipeline Stage walking, the commit per Stage and Publish; the engine port contract on the scripted engine and recordings; migrations and app boot; a fix for data loss or security that once regressed.
- **Smoke:** one happy-path request per controller and its main refusal; `service-start-check`.
- **Everything else goes to the full run:** edge cases, wording and label helpers, cosmetic UI tests, cases of a rule beyond its main one. Such a test lives in `<name>.full.test.ts(x)` beside its default-run sibling `<name>.test.ts(x)`; setup both need goes in the `*.fixtures.ts` beside them. A fixtures file in a layer's folder may not import the module's wiring or another module's `index.fixtures.ts` (only a test may), so setup that boots the module's app goes in a fixtures file at the module root, named after the test (`pipelines/stage-interpreter-alarm.fixtures.ts`), and setup that needs another module's fixtures stays in each half. A file named above as the only one doing something on the shared database is never split, since its two halves would run at once: it goes whole to one run.
- The same rule holds for `apps/web` and `packages/*`, and for e2e tests, which carry Playwright's `{ tag: "@full" }` instead ([apps/web/e2e/MAP.md](../../web/e2e/MAP.md)).
- To run one full-run file: `npx vitest run <path>`; the exclude applies to `npm run test` only. The e2e full run is `npm run test:e2e:full` (after `npm run build`).
