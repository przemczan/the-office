# Tests

Tests sit beside their code as `*.test.ts`; the support they share is in `test/`.

- **Postgres is needed:** `docker compose up -d` first. Each run creates a throwaway database on the server `DATABASE_URL` names (from the environment, else `.env`), migrates it and drops it at the end. Every test file in the run shares it, so a repository test makes its own rows and looks only at those.
- **A port's contract** (`*.contract.ts`, beside the port) is the tests every adapter of the port runs against itself; it is left out of the build, like fixtures.
- **No model calls by default:** sessions in tests run on the scripted engine (`modules/engine/adapters/scripted/`), which replays recordings or scripts written by hand; another module's test imports `ScriptedEngineModule.register(new ScriptedEngine(scripts))` from the Engine's index in place of `EngineModule`. The Agent SDK adapter's tests run live sessions on the signed-in Claude Code login only when `OFFICE_ENGINE_TESTS=live` is set; `OFFICE_ENGINE_TESTS=record` also re-records the engine contract's recordings from them, to be read in the diff and committed after an SDK bump. With `OFFICE_TEST_PROJECT` set to the Test Project's folder, they also run task 06's check on it, traced to otel-lgtm, and task 07's skills check (`modules/skills/application/session-skills.test.ts`). The OpenAI-compatible API engine runs the contract on a live server when `OFFICE_API_BASE_URL` and `OFFICE_API_MODEL` are set as well (`OFFICE_API_KEY` for one that needs a key); a local server is slow, so pick the scenarios with `-t`. With `OFFICE_TEST_PROJECT` too, task 35's check (`conversations/application/openai-compatible-api-test-project-check`) asks a Role on that model a question in its chat, run alone.
- **A skill on and for everyone reaches every session prepared on the shared database,** whichever test prepares it, and its files are in its own test's folder. Tests that prepare sessions with one stay in `modules/skills/application/session-skills.test.ts`, whose tests run one at a time; no other test leaves a skill on and for everyone.
- **Only `modules/conversations/application/thread-runner.test.ts` leaves Threads answering,** and it alone recovers interrupted answers, which waits every answering Thread on the shared database; its sessions get no library skills, which other files may change meanwhile.
- **Outcomes landing close together collapse into one, across files,** and the delivery rules act on every open Notification the clock has reached: a test that looks at what Notifications raise or push sets its `ManualSchedule` to a day of its own in a year no other file's clock reaches (2001 in `notification-service.test.ts`), or keeps its Notifications in a fixture of its own (`NotificationsForTests`, as `notification-delivery.test.ts` does with the timing and the user's activity too); an open Notification also swallows a new one like it (one engine down at a time), so a test that raises one closes it again. Quiet hours written to the stored timing hold every file's Notifications, so only the timing route's test writes them, at hours the system's clock is outside of, and gives the defaults back.
- **The fire alarm holds every file's Starts and pauses every file's started Tasks,** so no test sounds the stored one: a test binds `FireAlarmRepositoryForTests` (and, to sound it, a `TaskRepository` narrowed to its own Project, as `tasks.controller.test.ts` does), turning it off before it drops its Tasks; the Postgres adapter's test rolls its transaction back. A test override may be a factory of other providers (`useFactory`, `inject`). Lifts are kept by when the alarm sounded, in a table every file shares, so a test lifting one gives `FireAlarmInThreads` a sounding at a moment of its own (a random offset).
- **A Role hired from a preset has the preset's fixed key** (`planner`, `developer`, `reviewer`), so only `modules/people/adapters/http/roles.controller.test.ts` hires from the presets, removing those Roles and taking their skills away before each test. Other tests keep a Role of their own under a key of their own. The exceptions are the live checks of tasks 10 to 16, 26 and 27 (in `modules/work/application/`, `test-project-check.test.ts`, `planning-` and `fire-alarm-test-project-check.test.ts`, the last sounding an alarm of its own; in `modules/pipelines/application/`, `stage-interpreter-`, `running-task-`, `gate-publish-`, `parallel-work-` and `stage-editor-test-project-check.test.ts`; `modules/notifications/application/test-project-check.test.ts`; task 35's `modules/conversations/application/openai-compatible-api-test-project-check.test.ts`), which hire the Planner (and from task 12 the Developer) through the real People module and therefore each run alone: `npx vitest run work/application/test-project-check`, `pipelines/application/stage-editor-test-project-check` and so on, with the live variables set; their shared steps are in `test/live-check.ts`, and `OFFICE_CHECK_ENGINE=claude-code-p` runs the Roles they hire on the `-p` fallback (task 29). Check that the run reports one test: a filter that matches no file (a full path once did, from a shell whose drive letter was lower case) runs nothing and still exits 0.
- **`startTestApplication({ ...metadata, database })`** boots Nest providers, controllers and modules with HTTP configured as in production, on `127.0.0.1` and a free port; `database: true` adds `DatabaseModule` on the test database. Close its `app` in `afterEach`.
