# Projects surface: map

**Owns:** the Projects page (a card each with its onboarding badge; adding one by asking Devops to onboard it, `AskDevopsButton`, or the user's own window, `add-project-dialog.tsx` (docs/design/add-project.html, its UI spec): a medium `Dialog` that keeps one height, in two steps with "Step 1 of 2" or "Step 2 of 2" in the bar. Step 1 is "Where it is" (`add-project-source.ts`): a folder's path then Continue, a git URL then Clone (`repository-clone-step.tsx`, its progress read live from `repository-clone.changed`), or From GitHub (`github-repository-picker.tsx`: the repositories the App is installed on as a card, Recent first by `github-repository-words.ts`, those already added as a Project, by its Repository URL in any form, last under "Already added" and not to be picked; searched by name, owner and description with the match marked; read as the window opens, `useGitHubRepositoriesEarly`, the shell's `BlockLoader` rows meanwhile; a pick clones at once, its progress or failure with Try again in its row, a refusal above the list; signed out or not registered, one block with Open Settings › Office identity and Use a git URL instead). Step 2, `project-details-step.tsx`, shows the source as one line with Change, which goes back to step 1 and forgets the clone and the name it gave, then the fields, filled once from the source: its path and Repository URL, its folder's or repository's name, a clone's default branch, the base branch picked from the remote's, and the run environment question, Decide later picked at first, its answer sent with Add the Project as `runEnvironmentAnswer`, in `packages/ui`'s `RadioList` as the design system's radios have no name) and a Project's page (`project-page.tsx`: the head above the left-hand menu of its sections, the shell's `SectionLayout`, beside the open one, each a child route in `project-sections.tsx` reading the Project from `useOpenProject`; Overview, with Onboarding, Environment and Work, keeps the Project's bare address, and Commands, Default Pipeline, Run environment, Engine, Skills, Server values and Appearance have their own; a new section is one row in `SECTIONS` and one route; its Repository URL in the head when cloned, and a line on which part of the Office identity its base branch's remote needs and what is missing, `remote-needs-words.ts`, read under `REMOTE_NEEDS`, apart from the Projects' key, which `github.changed` refreshes): its onboarding (`onboarding-block.tsx`, from Work's `GET /onboardings`, joined by Project and refreshed by any Task event since it sits under the Tasks' query key), commands, install inputs, publishing mode, default Pipeline, the Run environment block (`run-environment-block.tsx`: On and Off, with "Not decided yet" beside the title until one is picked, a refused On's reasons under it; whether `.devcontainer/` was found on the base branch as last fetched and is valid, each problem listed; why a set-up Task's Done left the setting as it was; Set up run environment, shown unless it is On with a valid definition and replaced by a link to the open set-up Task; read under `RUN_ENVIRONMENTS`, apart from the Projects' key, which the Project's events and any Task's creation or move refresh), the Engine block (`engine-block.tsx`: the engine cascade's Project levels, the Project default, "Use for every Role" and the Project's Role overrides, each saved at once, with the engine and model pair from `shell/engine-model-fields.tsx` that the Role card uses too; the engines offered come from `/role-card-options`), the environment check, the Project's skills (`skills-block.tsx`: the switch for all of them at the head, then a row each with its own switch, saved at once by the skill's key, each row's mutation in one scope so answers land in order), the MCP servers' Server values with the Project's own (`server-values-block.tsx`; every value of a server is sent back, a kept secret by its name alone, as one left out is cleared), and its Appearance (`appearance-block.tsx`: the Mark and Images cards beside How it looks, `appearance-preview.tsx`, which comes first in one column and stays in view beside them on a wide page; the Mark card holds `MarkPicker`, `mark-picker.tsx`, the one picker the add dialog uses too, its tile the letters on the colour, the four colours and Custom as round swatches, native radios on the shell's `mark-colour-*` classes, Custom with the browser's colour input, then Save and, while there is a draft, Discard; the Images card a `ProjectImageRow`, `project-image-row.tsx` (the shell's `ImageRow` with Choose from repository beside Upload), for the Icon and one for the Logo, each previewing only its image or a "No Icon" or "No Logo" place, saved as soon as a file is picked, uploaded or chosen in the shell's `RepositoryFileWindow`, a refusal staying in the row; How it looks draws the Project's page head, its card and its chip with the draft mark over the saved images, with a Not saved badge). It reads the service through `src/api/` (see [the web app's map](../../MAP.md)).

**Traps:** Add a Project lays its columns out by its own `add-project` container, as the window sits on the body, outside the page's. From GitHub fills the body's height so only the rows scroll; the other steps leave the body to scroll. A folder's Project has no Repository URL, so its repository is never marked Already added. The colour input shows while the mark's colour is a custom one, so that colour is all the state Custom has; choosing Custom again keeps it. Overview has no redirect, as one would drop a link's `?chat=…&thread=…`; `ProjectPage` reads the Project and shows `Missing`, so an unknown Project says so at every section's address. `Switch` with a `label` wraps a `<span role="switch">` in a `<label>` that flips it on a click anywhere and doesn't name it, and `design-system/` stays as exported: a skill row keeps a bare `Switch` beside its text, so selecting a path changes nothing, and its `role="group"` carries the skill's name for screen readers and the tests. The Project default can't be cleared while "Use for every Role" is on, so the block leaves out its "Office default" choice then; the switch needs a Project default. `AppearanceBlock` holds a draft only while it differs from the Project's mark, so a change from another tab shows when nothing is being edited; only How it looks shows the draft, and the page head above keeps the saved mark until Save. `MarkPicker` is handed the Project's name alone, so its tile shows the letters even with an Icon, which How it looks shows instead. How it looks shares the head's styles and the card's `.project-tile` classes, never `.project-head` or `.project-card`, which the real page and card own and the tests find them by. Every other mark is drawn by `ProjectMark` from a Project's record, so `project.mark-changed` and `project.image-changed` refreshing the Projects' key is what updates them. Only a Project's page and card show `ProjectLogo`, which falls back to `ProjectMark`; `ProjectMark` shows the Icon only when it is handed the Project's `id` and `icon`, so pass it the whole record. No event follows a Project's Server values, so a save puts the answer in the query; the query sits under the Project's key, so the library's events, which refresh the Projects, refresh it too.
